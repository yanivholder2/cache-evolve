# H03

Widening the target-to-probing promotion gate from "single hottest" to "top-quarter of the bucket" lifts hit-rate above v001's 0.6787 by protecting more warm keys without the flooding that sank v002.

## Parent

cycle/0001/v001

## Changes

v001 keeps baseline's strict gate: in `promotion_get`, a target-bucket hit
promotes to probing only when
`Some(item_idx) == core.buckets[target_idx].promotion_candidate_index()`
(the single MRU item). v002 removed the gate entirely and regressed
hit-rate by flooding the probing tier. This explores the middle ground the
cycle-0001 insight asked for.

In `src/dash/segments/dash_segment.rs`, replace the boolean `is_hottest`
test in the target-hit branch of `promotion_get` with a "top fraction"
test. Compute the bucket length `len = core.buckets[target_idx].get_items().len()`
and a promotion window `window = std::cmp::max(1, len / 4)`. Treat the
item as promotable when it lies within the `window` most-recently-used
positions — for `ClassicLRU` (MRU at the back) that is
`item_idx >= len - window`. When promotable, run the existing
`promote_to_probing` path; otherwise fall through to the existing
intra-bucket touch (`get_from_position`) exactly as v001 does.

Keep v001's `InsertPosition::Back` promotion placement, all demotion
cascade logic, and the stash/probing branches unchanged. Express the
window test via the bucket's position ordering (not a hardcoded LRU
assumption) so it degrades sensibly for other policies, but tune it for
the active `ClassicLRU` config. Preserve the `unreachable!`
post-conditions after each promote.

## Rationale (optional)

A single-item gate may be too tight: keys that are consistently 2nd-3rd
hottest never earn protection. A bounded top-quarter window widens the
protected set proportionally to bucket size while still filtering the
churn that made v002's ungated promotion lose.
