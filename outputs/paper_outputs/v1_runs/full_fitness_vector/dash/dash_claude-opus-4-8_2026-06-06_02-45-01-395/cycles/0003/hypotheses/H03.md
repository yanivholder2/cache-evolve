# H03

Reordering the slot lookups in `promotion_get` to probe target and probing before stash will cut a linear `get_position` scan off every hot-key hit and lower per-op-time.

## Parent

cycle/0002/v001

## Changes

In `promotion_get` (src/dash/segments/dash_segment.rs) the three slot
lookups run in the order stash → target → probing. Because the uniqueness
invariant (ADR 0004) guarantees a resident key lives in exactly one slot,
the order is purely a cost choice: it does not change which item is found
or how it migrates. Hot keys — the common hit case — have already been
promoted out of stash into target/probing, yet the current order pays a
`stash_buckets[stash_idx].get_position(key)` scan on every one of those
hits before reaching them.

Reorder the branches to: (1) target check + promote-to-probing /
intra-touch, (2) probing check + touch-in-place, (3) stash check +
promote-to-target, (4) miss → `None`. Move the existing stash block
verbatim to last; do not alter any block's body, the `insert_pos`
threading, or the demotion cascade. Compute `stash_idx` lazily inside the
stash block so its `get_index` call is skipped entirely on target/probing
hits.

Keep everything else from v001 (slim `Item`, `InsertPosition::Back`)
unchanged.

## Rationale

This is a pure hot-path latency play orthogonal to the hit-rate
hypotheses: same eviction behaviour, same hit-rate, fewer scans per hit.
A key resident in target now costs one `get_position` instead of two, and
a probing resident two instead of three, trimming the average per-`get`
work without changing any observable cache decision.
