# H01

Pre-reserve the trivially-hashed `target_heat` side table at construction to fuse the hasher (p50) and capacity (get-p99) wins into one additive per-op-time improvement.

## Parent

cycle/0006/v001

## Changes

In `src/dash/segments/mod.rs`, `SegmentCore::try_new`, change the
`target_heat` initialization from
`HashMap::with_hasher(U64BuildHasher)` to
`HashMap::with_capacity_and_hasher(settings.num_of_normal_buckets * settings.bucket_size, U64BuildHasher)`.

This is the composition the cycle-0006 insight explicitly flagged as
genuinely additive (not the substitutive stacks of cycle 0005): v001's
`U64BuildHasher` removed the SipHash permutation that bounds get-p50,
while v002's capacity pre-reservation removed the incremental-rehash
spikes (alloc + full reinsert) that bound get-p99. v001 carries the
hasher; this hypothesis adds the reservation *on top of the same
`U64BuildHasher`* so a single variant gets both. The capacity
`num_of_normal_buckets * bucket_size` is a safe upper bound — only
target-resident keys ever carry heat, so the table can never hold more
than the total normal-bucket capacity of live entries at once.

Keep everything else byte-for-byte: the `U64BuildHasher` type, the
`entry`/`saturating_add`/`remove` gate logic in `promotion_get`, the
`PROMOTE_AT` threshold, the `put`-side `target_heat.remove`, and all
migration/cascade code are untouched. This is a capacity-only addition
layered on the existing hasher, so hit-rate (0.6794), slot legality,
capacity bounds, and metadata-size (16) are bit-for-bit identical to the
parent; only get-tail latency should move. Confirm via the existing
`target_heat_uses_trivial_hasher_and_round_trips` test plus a new test
asserting the map's initial `capacity()` is at least the reserved size.

## Rationale (optional)

v001 and v002 target provably disjoint causes (median hasher cost vs.
get-tail rehash cost). This is the highest-confidence lever available:
both halves are already-proven Winners, and the only open question is
whether they compose — which this variant directly answers.
