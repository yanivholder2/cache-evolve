# H03

Gating the get-path stash-to-target promotion on a non-full target — touching the item in place in the stash when the target is full instead of evicting a target resident — removes the read-path eviction cascade and lowers get-p99 (per-op-time).

## Parent

cycle/0007/v001

## Changes

In `promotion_get` (`src/dash/segments/dash_segment.rs`), the stash-hit branch
(~lines 185-194) unconditionally removes the item from the stash and calls
`promote_to_target`, which evicts a target LRU victim and runs the demotion
cascade **on the get path** whenever the target bucket is full. Gate this
promotion: before removing from the stash, compute `target_idx` (already
available) and check `core.buckets[target_idx].is_full()`.

- If the target is **not full**, keep the existing behaviour exactly: remove
  from the stash, `promote_to_target`, and return the item from its new target
  slot.
- If the target **is full**, do NOT promote. Instead touch the item in place
  in its stash bucket (move it to the stash MRU end via the bucket's
  `get_from_position` on the position already found) and return that reference.
  No target resident is evicted and no cascade runs.

This keeps the conflict resolution off the stash-growth path entirely on the
read side: a get that would have triggered a full-target eviction cascade now
resolves with a single in-stash LRU touch, removing the cascade work that
bounds get-p99. Net stash occupancy does not grow (the item stays where it
already was). Preserve slot legality, the `target_heat` side table semantics
(the gated item never entered target, so its heat handling is untouched), and
the existing not-full path bit-for-bit. Score on hit-rate too: deferring
promotion leaves hot re-accessed keys in the volatile stash longer, so this is
a get-tail-vs-hit-rate trade, not a free win.

## Rationale (optional)

Cycle 0009 pinned the stash coupling but only ever attacked it from the put
(demotion) side; the get path *also* triggers the cascade, via the
stash-hit promotion. Gating that promotion is the get-side analogue of
0009/v001's non-full demotion guard, and tests whether removing read-path
cascade work pays more than the residency lost by under-promoting.
