# H01

Move the promotion heat counter out of `Item` into a segment-owned side table so `Item<u64,u64>` shrinks from 24 to 16 bytes while preserving the `PROMOTE_AT` frequency gate, targeting metadata-size.

## Parent

cycle/0003/v002

## Changes

The parent's `Item<u64,u64>` measures 24 bytes solely because the `u8
lfu_counter` field forces the struct up to the next 8-byte alignment
boundary — a 7-byte padding tax for a 1-byte signal. This hypothesis
relocates that signal out of the per-entry struct into the container,
which is exactly the "container/segment structure rather than per-entry
layout" lever the cross-cycle insights flag as the next size frontier.

Concretely:

1. In `src/shared/item.rs`, delete the `lfu_counter` field, its
   initialization in `Item::new`, and the `lfu_counter` references in
   `Display` and the unit tests. `Item<u64,u64>` then becomes
   `{ key, value }` = 16 bytes, restoring the metadata-size floor held
   by cycle/0002/v002.

2. In `src/dash/segments/dash_segment.rs` (or the `SegmentCore` source
   it lives in, which is overlay-editable), add a side structure that
   maps a resident target key to its current heat, e.g. a
   `HashMap<K, u8>` field on `SegmentCore` named `target_heat`. This
   field is NOT part of `Item<u64,u64>`, so it does not enter the
   measured per-entry footprint.

3. Rewrite the frequency gate in `promotion_get`: where the parent reads
   and writes `core.buckets[target_idx].get_items()[item_idx].lfu_counter`,
   instead read/write `target_heat.entry(*key)`. Keep the exact gate
   semantics — bump on each target hit, promote to probing once heat
   reaches `PROMOTE_AT == 2`, and clear the entry (remove from the map)
   when the key leaves the target tier (promotion to probing, demotion to
   stash, or eviction out of the segment) so heat stays per-target-residency
   exactly as today.

Preserve invariants: the uniqueness guarantee (a key resident in exactly
one slot), the demotion cascade, and `InsertPosition::Back` MRU
placement must all be unchanged. The only observable differences should
be `sizeof(Item<u64,u64>) == 16` and an unchanged hit-rate (the gate
decisions are bit-for-bit identical). Watch per-op-time: the map lookup
replaces an inline field access, so note any latency drift.

## Rationale (optional)

cycle/0003/v002 holds the best hit-rate (0.6794) but pays 24 bytes for
an 8-bit counter; cycle/0002/v002 holds 16 bytes but only 0.6634
hit-rate. This tests whether a struct-of-arrays relocation can occupy
the open Pareto corner — best hit-rate AT the 16-byte floor — that
neither incumbent reaches.
