# H01

Adding v002's devirtualized ClassicLRU hot path onto v001's side-table segment cuts per-op-time below v001's 86ns while holding the 16-byte Item floor, testing whether the size win and latency win stack.

## Parent

cycle/0004/v001

## Changes

v001 reaches the metadata floor (`Item` = 16 bytes, hit-rate 0.6794) but pays
86ns get-p50 because every bucket access dispatches the ClassicLRU policy
through the `Box<dyn EvictionPolicy>` vtable, and additionally probes the
`target_heat` HashMap on each target hit. Port cycle/0004/v002's
devirtualization onto this parent so the two proven wins are measured together:

- In `src/dash/dash_bucket.rs`: add the `is_classic_lru: bool` field to
  `DashBucket`, set it in `new()` from `eviction_policy.name() == "ClassicLRU"`,
  and override `get_from_position` to call the inlined `lru_get_from_position`
  free function when the flag is set, falling back to the trait object otherwise
  (exactly as v002 does).
- In `src/shared/traits/bucket.rs`: add the `#[inline]` `lru_get_from_position`,
  `lru_eviction_index`, `lru_promotion_index` free functions and the
  `is_classic_lru()` trait method (default `false`), and branch
  `eviction_candidate_index`/`promotion_candidate_index` on it, mirroring v002.

Keep v001's `target_heat` side table, the `PROMOTE_AT` gate, the `put`-time heat
clear, and the 16-byte `Item` (key+value only) entirely intact. Behaviour must
stay bit-for-bit: hit-rate 0.6794 and metadata-size 16 unchanged; only get/put
latency should move. This directly answers the cross-cycle open question of
whether the side-table's hot-path hashing eats the devirtualization gain or the
two wins compose into a single Pareto-dominant variant.

## Rationale (optional)

The cycle-0004 insight explicitly flagged this as the next experiment: v001 and
v002 each occupy a different Pareto corner, and the only way to know if they are
additive or substitutive is to build the union and measure it.
