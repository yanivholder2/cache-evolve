# H01

Promoting hit items to the MRU end instead of the LRU end speeds tier ascent and raises hit-rate on the LIRS workload.

## Parent

baseline

## Changes

In `src/dash/segments/dash_segment.rs`, change the single `get` entry point so
it calls `promotion_get(&mut self.core, key, InsertPosition::Back)` instead of
`InsertPosition::Front`. This flips where promoted/demoted items land: with
`Back`, a stash→target promotion lands at the MRU end, so one more access
promotes the key to probing (the docstring already describes this `Back`
behaviour), whereas the baseline `Front` forces a key to re-climb the whole
bucket before it can promote again.

Do not touch `promote_to_target`, `promote_to_probing`, or
`demote_from_normal_bucket` themselves — they already thread `insert_pos`
through, so the single argument change propagates to every insert site. Keep
the `is_hottest` promotion gate, the cascade order
`probing -> target -> stash`, and the one-more-chance retry intact.

The hypothesis is confirmed if hit-rate rises above the baseline 0.6634 on
`lirs:inputs/traces/workload-a.trace.gz` at size 2048, with per-op-time no
worse (this changes only which end of the `Vec` receives the insert, an O(n)
`insert(0, …)` vs `push`, so p50 may even improve). All P1–P6 invariants must
still hold, since slot legality and capacity are unaffected by insert position.

## Rationale (optional)

The baseline's `Front` promotion is deliberately conservative — it demands an
item prove itself twice before reaching probing. On a skewed (Zipfian-like)
LIRS trace, hot keys are re-accessed quickly; landing them at MRU lets them
reach the protected probing tier in a single extra hit, reducing the chance a
hot key is evicted mid-climb.
