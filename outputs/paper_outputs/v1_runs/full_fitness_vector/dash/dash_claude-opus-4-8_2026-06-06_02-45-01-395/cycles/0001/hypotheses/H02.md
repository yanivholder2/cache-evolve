# H02

Promoting any re-accessed target item to probing (dropping the hottest-only gate) protects recently reused keys and raises hit-rate.

## Parent

baseline

## Changes

In `src/dash/segments/dash_segment.rs`, modify the target-hit branch of
`promotion_get`. Today that branch computes
`let is_hottest = Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();`
and only calls `promote_to_probing` when `is_hottest` is true, otherwise it
falls through to `get_from_position` (an in-bucket LRU bump).

Replace the gate so that **every** target hit promotes to probing: remove the
`is_hottest` computation and the `else` in-bucket-bump path, and unconditionally
`remove_at(item_idx)` the key and call `promote_to_probing(core, data,
insert_pos)`, then return the reference resolved from the probing bucket (the
same `get_position` + `get_from_position` pattern the current `is_hottest`
branch uses). Keep the stash-hit branch, the probing-hit touch-in-place branch,
the cascade ordering, and the `unreachable!` post-promotion residency check
unchanged.

This makes the probing bucket a "reused at least once since landing in target"
tier rather than a "currently hottest in its target bucket" tier. Slot legality
is preserved because `promote_to_probing` already routes to the legal
`(target+1) % segment_size` bucket and cascades overflow correctly, so P1–P6
must still pass.

The hypothesis is confirmed if hit-rate exceeds 0.6634 on the eval trace. Watch
per-op-time: promoting on every target hit triggers more `put_at`/cascade work
per `get`, so a hit-rate gain must not be paid for by a large p50 regression.

## Rationale (optional)

The baseline gate is strict: a target item must be the single hottest resident
to earn probing, so a bucket churning among several warm keys may never promote
any of them. Promoting on any re-access widens the protected set, which on a
trace with many moderately-hot keys can retain more of the working set.
