# H02

Pre-reserve the `target_heat` side table at construction so it never rehashes mid-run, cutting get/put p99 tail latency without changing p50 or metadata size.

## Parent

cycle/0005/v001

## Changes

The cross-cycle insight notes side tables "trade tail latency for size": v001's
get p99 is 238 ns vs v002's 213 ns, and v003's ghost-laden side tables pushed
p99 to 286/348 ns. A growable `HashMap` that starts empty rehashes repeatedly as
it fills during the trace, and each rehash is an allocation + full reinsert spike
that lands in the tail percentiles.

Concretely, in `src/dash/segments/mod.rs`:

1. In `SegmentCore::try_new`, replace `target_heat: HashMap::new()` with
   `target_heat: HashMap::with_capacity(cap)` where `cap` is sized to the maximum
   number of keys that can simultaneously hold heat — i.e. the total normal-bucket
   capacity of the segment: `settings.num_of_normal_buckets * settings.bucket_size`
   (only target-resident keys ever carry heat, so this is a safe upper bound).
   Add a brief comment explaining the bound.
2. Do not change any gate logic, the `entry`/`remove` calls, or `PROMOTE_AT`.
   `with_capacity` only changes the initial allocation, so all hit-rate and
   slot-legality behaviour is bit-for-bit identical.

Invariants: `Item<u64,u64>` stays 16 bytes (this is segment container state, not
per-entry layout, so the metadata-size dimension is unaffected); hit-rate stays
0.6794; only the p99 of get/put should improve.

## Rationale (optional)

This directly targets the open question "Can any latency win reduce p99 rather
than just p50?" It is orthogonal to H01 (allocation/rehash cadence vs hash
function), so the two can be evaluated independently and, if both win, later
composed.
