# H01

Inserting stash-to-target promoted items at `InsertPosition::Back` (MRU end) instead of `InsertPosition::Front` will increase hit rate by letting recently accessed items skip the two-hit warm-up before advancing to the probing tier.

## Parent

baseline

## Changes

In `src/dash/segments/dash_segment.rs`, change the single argument in `DashSegment::get`:

```rust
// Before
fn get(&mut self, key: &K) -> Option<&Item<K, V>> {
    promotion_get(&mut self.core, key, InsertPosition::Front)
}

// After
fn get(&mut self, key: &K) -> Option<&Item<K, V>> {
    promotion_get(&mut self.core, key, InsertPosition::Back)
}
```

This one-line change propagates through `promotion_get` into every call to `promote_to_target`, `promote_to_probing`, and `demote_from_normal_bucket` that originates from a `DashSegment::get`. All stash→target and cascade inserts now land at the MRU end of their destination bucket.

The structural consequence: a freshly promoted stash item arrives in its target bucket already at the promotion-candidate position (`items.len()-1` for ClassicLRU). Its next access will therefore immediately promote it to probing rather than requiring it to first climb from LRU to MRU. This halves the number of hits an item needs in order to enter the probing tier.

Update the inline tests that verify post-promotion item order:

- **`stash_hit_inserts_at_front_of_target`**: With Back insertion, keys[1] lands at `items[1]` (the MRU end) rather than `items[0]`. Rename the test to `stash_hit_inserts_at_back_of_target` and change the assertions to `assert_eq!(items[0].key, keys[0])` and `assert_eq!(items[1].key, keys[1])`. Update the comment accordingly.

- **`target_hit_not_hottest_promotes_within_bucket`**: With Back insertion, keys[1] arrives already at the promotion-candidate position, so the very next `seg.get(&keys[1])` will promote it to probing rather than touching in place. Either remove this test (the scenario it exercises no longer arises from the default `get` path) or replace it with a two-key test where neither item is at the MRU position yet, which requires placing both in target via direct bucket manipulation rather than via `seg.get`.

Do not touch `promote_to_probing`, `demote_from_normal_bucket`, `promote_to_target`, or any eviction-policy logic. The `target_retry_lands_at_front_when_cold`, `cascade_to_stash_at_front_when_cold`, and the analogous `_when_hot` tests call those functions directly with an explicit `InsertPosition` argument and are unaffected by this change.
