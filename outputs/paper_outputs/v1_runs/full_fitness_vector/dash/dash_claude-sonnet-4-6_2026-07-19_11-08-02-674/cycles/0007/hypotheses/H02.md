# H02

Adding vacancy-gated probing re-entry to cycle/0006/v003 — incrementing probing items' `lfu_counter` on each hit and moving them back to target when the counter reaches 2 and target has space — will raise hit rate above 0.679 by recycling warm probing residents through both tiers.

## Parent

cycle/0006/v003

## Changes

`cycle/0006/v003` leaves the probing branch of `promotion_get` completely passive: a probing hit merely calls `get_from_position` (which rotates the item to MRU in place) and returns without touching `lfu_counter` or considering re-entry. `cycle/0006/v001` showed that tracking probing hit frequency and cycling items back to target when both counter and vacancy conditions are met yields a small additive hit-rate gain. This hypothesis tests whether that mechanism alone, grafted onto v003's cleaner clock base, produces a similar gain — without the non-hottest-target counter increment or vacancy-gated target promotion that v001 also carries.

### `src/dash/segments/dash_segment.rs`

In `promotion_get`, replace the passive probing branch with vacancy-gated probing re-entry. The current v003 code:

```rust
if let Some(item_idx) = core.buckets[probing_idx].get_position(key) {
    debug!("promotion_get: key={key:?} found in probing bucket={probing_idx}");
    return Some(core.buckets[probing_idx].get_from_position(item_idx));
}
```

Replace with:

```rust
if let Some(item_idx) = core.buckets[probing_idx].get_position(key) {
    core.buckets[probing_idx].get_items_mut()[item_idx].lfu_counter += 1;
    let counter = core.buckets[probing_idx].get_items()[item_idx].lfu_counter;
    let target_has_space = !core.buckets[target_idx].is_full();
    if counter >= 2 && target_has_space {
        debug!("promotion_get: key={key:?} found in probing bucket={probing_idx} lfu_counter={counter} target={target_idx} has space (vacancy-gated probing re-entry)");
        let data = core.buckets[probing_idx].remove_at(item_idx);
        promote_to_target(core, data, InsertPosition::Back);
        let item_new_idx = core.buckets[target_idx]
            .get_position(key)
            .expect("promote_to_target must leave key in target");
        return Some(&core.buckets[target_idx].get_items()[item_new_idx]);
    }
    debug!("promotion_get: key={key:?} found in probing bucket={probing_idx} lfu_counter={counter} (intra-probing stay)");
    return Some(core.buckets[probing_idx].get_from_position(item_idx));
}
```

Leave the stash branch, the hottest-target promotion branch, and the non-hottest-target branch (which in v003 does not touch `lfu_counter`) all unchanged from v003. Leave `promote_to_target`, `promote_to_probing`, `demote_from_normal_bucket`, and `clock_evict_prepare` unchanged from v003.

### `src/shared/item.rs`

Inherit unchanged from `cycle/0006/v003` (no `timestamp` field, `lfu_counter: usize` only).

### `src/shared/eviction_policy.rs`

Inherit unchanged from `cycle/0006/v003` (standard `ClassicLRU` with `eviction_candidate_index` returning `0`; `get_from_position` rotates to MRU back; no LFU scan).

## Rationale

`cycle/0006/v001` validated probing re-entry as a regression-free hit-rate mechanism, but v001 also carries the LFU-minimum O(n) scan that makes isolating contributions difficult. By grafting probing re-entry onto v003's scan-free, clock-eviction base, this hypothesis measures the mechanism's contribution cleanly. The probing re-entry counter is now the ONLY counter being incremented in the get path (non-hottest target hits still do not touch lfu_counter in this variant), so the gate fires only for items that have accumulated frequency specifically within the probing tier — items that have been in the probing bucket at least twice. The vacancy guard (target must have space) ensures re-entry never triggers a cascade eviction. On a Zipfian trace, the hottest items cycle through probing frequently and should consistently meet both conditions, while the gate naturally silences during high cache occupancy when target is full.
