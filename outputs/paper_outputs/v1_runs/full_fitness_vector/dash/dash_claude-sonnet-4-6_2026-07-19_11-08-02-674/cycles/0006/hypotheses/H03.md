# H03

Replacing positional LRU eviction with a two-chance clock algorithm that decrements and rotates items with `lfu_counter > 0` to the MRU end improves hit rate over the baseline without requiring an O(n) minimum scan.

## Parent

baseline

## Changes

Overlay three files. No Cargo.toml or trait changes.

### 1. `src/shared/item.rs`

Remove the `timestamp: Instant` field from `Item<K, V>` and the `use std::time::Instant` import. Update `Item::new` to not set `timestamp`. This reduces `size_of::<Item<u64,u64>>()` from 40 to 24 bytes. Preserve `key`, `value`, and `lfu_counter` fields unchanged. Update `Display` / `PartialEq` / `Eq` impls if they reference `timestamp`.

### 2. `src/shared/eviction_policy.rs`

Change `TimestampLRU::eviction_candidate_index` to return the constant `0` (matching `ClassicLRU`'s baseline behaviour) and remove the `Instant::now()` comparison logic along with any `use std::time::Instant` import. `ClassicLRU` stays exactly as it is in baseline (constant-0 eviction, move-to-back on access). All other policy structs and the `EvictionPolicyKind` enum are unchanged.

### 3. `src/dash/segments/dash_segment.rs`

Two changes:

**a. MRU-end insertion.** Change `InsertPosition::Front` to `InsertPosition::Back` in the `get` method's call to `promotion_get`. This aligns with every prior cycle's proven win.

**b. Two-chance clock eviction.** Add a free function `clock_evict_prepare` in `dash_segment.rs`:

```rust
/// Runs one pass of the clock (second-chance) algorithm over `items`.
/// Items at position 0 with lfu_counter > 0 are decremented and rotated
/// to the back; the first item found with lfu_counter == 0 is left at
/// position 0 as the eviction victim. If every item has counter > 0,
/// all counters are decremented by 1 and position 0 holds the victim.
fn clock_evict_prepare<K, V>(items: &mut Vec<Item<K, V>>)
where
    K: Clone,
    V: Clone,
{
    let n = items.len();
    for _ in 0..n {
        if items[0].lfu_counter == 0 {
            break;
        }
        items[0].lfu_counter -= 1;
        items.rotate_left(1); // move front to back
    }
    // position 0 is now the eviction victim
}
```

Call `clock_evict_prepare` on the target bucket's items immediately before any call to `core.put_at(Slot::Target, ...)` that could trigger eviction (i.e., when `core.buckets[target_idx].is_full()` is true). Specifically, add this call at the top of `promote_to_target` when the target bucket is full, and equivalently in `demote_from_normal_bucket`'s target-insertion path:

```rust
fn promote_to_target<K, V>(core: &mut SegmentCore<K, V>, item: Item<K, V>, insert_pos: InsertPosition) {
    let target_idx = get_index(&item.key, core.segment_size);
    if core.buckets[target_idx].is_full() {
        clock_evict_prepare(core.buckets[target_idx].get_items_mut());
    }
    let Some(evicted) = core.put_at(Slot::Target, insert_pos, item) else {
        return;
    };
    demote_from_normal_bucket(core, evicted, target_idx, insert_pos);
}
```

`ClassicLRU::eviction_candidate_index` returns 0 (constant), so after `clock_evict_prepare` positions the victim at index 0, the existing eviction machinery removes the correct item with no changes to the eviction policy trait or struct.

Do not add vacancy-gated promotion or probing re-entry logic — this hypothesis isolates the two-chance eviction algorithm as the sole new mechanism.

## Rationale

Positional LRU (constant-0 eviction) always evicts the oldest-inserted item regardless of access frequency, discarding items that may have been accessed recently but happened to be inserted early. The two-chance clock algorithm gives each item one opportunity to survive: on first encounter as eviction candidate, if it has any accumulated hits (lfu_counter > 0), its counter is decremented and it is moved to the MRU end; only items with zero accumulated hits are evicted immediately. This distinguishes cold items (never re-accessed after insertion, counter stays 0) from warm items (accessed at least once, counter > 0) without scanning the full bucket for the global minimum. The O(n) worst case matches the LFU-min scan but the expected case for Zipfian workloads — where a significant fraction of items are cold tail items with counter == 0 — terminates much earlier.
