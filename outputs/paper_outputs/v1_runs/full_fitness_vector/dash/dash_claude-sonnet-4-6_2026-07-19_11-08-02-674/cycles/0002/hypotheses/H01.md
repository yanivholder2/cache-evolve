# H01

Stacking v003's timestamp removal on top of v001's MRU-end insertion will reduce metadata-size from 40 to 24 bytes while preserving the 0.6787 hit-rate gain.

## Parent

cycle/0001/v001

## Changes

v001's overlay only contains `src/dash/segments/dash_segment.rs` (with `InsertPosition::Back`). Add two more overlay files on top of it, taken from v003's proven changes:

1. **`src/shared/item.rs`** — Remove the `timestamp: Instant` field entirely. The struct should contain only `key: K`, `value: V`, and `lfu_counter: usize`. Remove the `use std::time::Instant;` import and any reference to `timestamp` in `Item::new`. Keep the existing `PartialEq`, `Eq`, `Clone`, and `Display` implementations intact, updating `Display` to omit the timestamp field.

2. **`src/shared/eviction_policy.rs`** — In `TimestampLRU::get_from_position`, degrade from a timestamp-stamping operation to a position-based move: remove the `Instant::now()` call and replace the body with the same `items.remove(position); items.push(item); items.len() - 1` logic used by `ClassicLRU`. This eliminates the syscall on every `get` that uses `TimestampLRU`, matching what v003 measured. No other policies change.

3. **`src/dash/segments/dash_segment.rs`** — Keep exactly as in v001: `promotion_get` called with `InsertPosition::Back`. No further changes to segment logic.

The net result is v001's MRU-end promotion path combined with v003's slimmer `Item` struct: 24-byte items, no syscall on `put` or `get`, and the faster tier warm-up that lifted v001's hit-rate to 0.6787.

## Rationale

The cycle-1 insight explicitly identified the two winners as orthogonal (different subsystems, no shared code paths) and nominated stacking as the highest-priority next experiment. This hypothesis is the direct execution of that recommendation.
