Explore divisor 2 on baseline geometry to find the permissiveness frontier and improve hit-rate beyond divisor 3.

## Parent

baseline

## Changes

In `src/dash/segments/dash_segment.rs`, implement adaptive frequency-gating with divisor 2 on baseline 25/75 geometry:

1. Add a threshold calculation function with divisor 2:
   ```rust
   fn compute_promotion_threshold(stash_buckets: usize) -> u16 {
       ((stash_buckets / 2).max(1)) as u16
   }
   ```

2. Store the computed threshold as a field in DashSegmentCore (or pass it as a parameter to promotion_get()).

3. In the promotion_get() gating check (around line 166–170), replace any hardcoded constant with the adaptive value:
   ```
   if is_hottest && core.buckets[target_idx].get_items()[item_idx].lfu_counter >= core.promotion_threshold {
       // proceed with promotion to probing
   }
   ```
   - On baseline 25/75 (24 stash buckets): threshold = max(1, 24 / 2) = 12 (versus max(1, 24 / 4) = 6 in cycle 0005 v003, and max(1, 24 / 3) = 8 in cycle 0006 v003)
   - This lower divisor permits more items to promote, testing the permissiveness frontier

4. Stash→target promotion remains ungated (all stash hits promote immediately to target).

5. Keep baseline 25/75 bucket geometry, all other promotion logic, and demotion cascades unchanged.

## Rationale

Cycle 0005 v003 used divisor 4 (threshold=6 on baseline), achieving 43% get-latency improvement but matching baseline hit-rate (0.6634). Cycle 0006 v003 tested divisor 3 (threshold=8), showing that more permissive gating improves both hit-rate and latency without degradation. The cross-cycle insights note that the adaptive formula itself may be refined to shift the hit-rate/latency frontier. Testing divisor 2 (threshold=12 on baseline) explores whether allowing even more items to promote—with the gate becoming more lenient about frequency—can further improve hit-rate by reducing false negatives (items that should have promoted but were filtered). This pushes the permissiveness frontier downward to identify whether divisor 3 is optimal or whether a less selective gate better suits the candidacy distribution of balanced-geometry workloads.
