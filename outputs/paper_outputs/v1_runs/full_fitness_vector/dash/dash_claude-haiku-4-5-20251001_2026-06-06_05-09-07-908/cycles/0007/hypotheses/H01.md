# H01

Increase promotion threshold selectivity on 85/15 geometry using divisor 2 to reduce over-promotion cascades and recover hit-rate.

## Parent

cycle/0006/v001

## Changes

In `src/dash/segments/dash_segment.rs`, modify the adaptive threshold formula constant in the `compute_promotion_threshold` function (or equivalent helper used by v001):

1. Change the divisor from 4 to 2 in the adaptive threshold computation:
   ```rust
   fn compute_promotion_threshold(stash_buckets: usize) -> u16 {
       ((stash_buckets / 2).max(1)) as u16
   }
   ```

2. On v001's 85/15 geometry (5 stash buckets), this yields:
   - Old divisor 4: threshold = max(1, 5/4) = 1
   - New divisor 2: threshold = max(1, 5/2) = 2
   - The higher threshold filters more marginal items, reducing false-positive promotions

3. Store and apply this computed threshold in the promotion_get gating check (around line 166-170 in baseline dash_segment.rs):
   ```
   if is_hottest && core.buckets[target_idx].get_items()[item_idx].lfu_counter >= core.promotion_threshold {
       // promote to probing
   }
   ```

4. Keep all other logic unchanged: 85/15 geometry allocation, stash→target ungated promotion, and demotion cascades remain as v001 implemented them.

## Rationale

v001's variant insight revealed that threshold=1 (divisor 4 on 5-bucket stash) caused insufficient promotion selectivity, allowing too many marginal items into the hot tier and overwhelming the stash with cascading evictions. This degraded both hit-rate (0.7126 vs. v002's 0.7132) and put-latency. Cycle 0005 established that adaptive threshold scaling aligns selectivity to stash capacity. On 85/15 geometry, divisor 2 yields threshold=2, doubling the LFU counter requirement and filtering out single- or low-frequency accesses that flood the tier. This tests whether increasing selectivity on aggressive geometry can recover the hit-rate margin lost to composition interference, potentially achieving both the latency gains of v001 and the hit-rate margin of v002.
