# H01

Apply stricter divisor 2 to 80/20 geometry to test whether reduced promotion permissiveness further improves hit-rate on the optimal allocation.

## Parent

cycle/0007/v002

## Changes

In `src/dash/segments/mod.rs`, modify the adaptive threshold formula in the `compute_promotion_threshold()` function:

1. Change the divisor from 3 to 2:
   ```rust
   fn compute_promotion_threshold(stash_buckets: usize) -> u16 {
       ((stash_buckets / 2).max(1)) as u16
   }
   ```

2. On v002's 80/20 geometry (6 stash buckets), this yields:
   - Old divisor 3: threshold = max(1, 6/3) = 2
   - New divisor 2: threshold = max(1, 6/2) = 3
   - The higher threshold filters more marginal items, testing whether stricter selectivity on the optimal geometry recovers further hit-rate improvements

3. Keep 80/20 bucket geometry allocation, stash→target ungated promotion, and all other logic unchanged.

4. Store and apply the computed threshold in the promotion_get gating check (line 170 in v002's dash_segment.rs):
   ```rust
   if is_hottest && lfu_counter >= core.promotion_threshold {
       // proceed with promotion to probing
   }
   ```

## Rationale

v002's 80/20 geometry + divisor 3 (threshold=2) is the current best-of-cycle, but v001's divisor 2 on tighter 85/15 geometry (also threshold=2) achieves nearly equivalent hit-rate (0.7131 vs. 0.7166) with better latency. This suggests divisor 2's stricter selectivity may be underutilized on 80/20's larger stash capacity. Testing divisor 2 on 80/20 yields threshold=3, a middle ground between v003's permissive threshold=12 and v001's tight threshold=2. This explores whether v002's optimal geometry can be paired with stricter gating to trade a small amount of latency for marginal hit-rate gains at the 80/20 inflection point.
