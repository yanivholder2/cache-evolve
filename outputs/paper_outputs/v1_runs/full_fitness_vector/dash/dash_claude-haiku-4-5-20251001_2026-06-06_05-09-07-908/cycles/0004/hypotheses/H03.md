# H03

Apply back-insert promotion to 75/25 geometry to test latency-latency trade-off with the largest hash-indexed tier yet.

## Parent

cycle/0003/v003

## Changes

Keep v003's 75/25 bucket geometry (24 normal + 8 stash buckets) unchanged. In `src/dash/segments/dash_segment.rs`, modify the `get()` method (around line 68–69 in the current codebase) to change the promotion insertion position from the default `InsertPosition::Front` to `InsertPosition::Back`:

Change:
```rust
fn get(&mut self, key: &K) -> Option<&Item<K, V>> {
    promotion_get(&mut self.core, key, InsertPosition::Front)  // baseline behavior
}
```

To:
```rust
fn get(&mut self, key: &K) -> Option<&Item<K, V>> {
    promotion_get(&mut self.core, key, InsertPosition::Back)   // back-insert optimization
}
```

Keep all promotion logic, demotion cascades, and frequency counters unchanged (no gating).

## Rationale

v003 achieved the best hit-rate (0.714) and strong latency (109 ns) using only 75/25 geometry without back-insert. Earlier composition of back-insert with geometry regressed latency: cycle 0002 v001 (back-insert + 50/50 geometry) achieved per-op-time=122 ns versus cycle 0002 v002's 117 ns on 62.5/37.5 geometry alone. However, 75/25 represents the most aggressive hash-indexed allocation yet (27 of 32 buckets), substantially larger than the 50/50 baseline where composition failed. This greater primary-tier capacity may provide sufficient absorption for back-insert's MRU-insertion overhead without latency penalty. If back-insert successfully reduces demotion cascades on 75/25, it could amplify the hit-rate by keeping hot items in the normal tier longer. This tests whether composition improves at the boundary of aggressive geometry allocation, or whether simple geometry-only variants remain optimal across all concentrations.
