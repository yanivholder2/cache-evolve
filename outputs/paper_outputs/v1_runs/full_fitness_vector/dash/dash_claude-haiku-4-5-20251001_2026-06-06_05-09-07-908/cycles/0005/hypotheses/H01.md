# H01

Lower frequency-gating threshold to 1 to reduce latency overhead while preserving hit-rate gains on 75/25 geometry.

## Parent

cycle/0004/v001

## Changes

In `src/dash/segments/dash_segment.rs`, modify the `promotion_get()` function to use a lower frequency threshold:

1. Change the promotion counter threshold constant from `const PROMOTION_THRESHOLD: u16 = 2;` to `const PROMOTION_THRESHOLD: u16 = 1;`

2. Keep the gating logic in the "is_hottest" check identical (around line 166–170):
   ```
   let is_hottest = Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();
   if is_hottest && core.buckets[target_idx].get_items()[item_idx].lfu_counter >= PROMOTION_THRESHOLD {
       // proceed with promotion to probing
   } else if is_hottest {
       // increment lfu_counter and stay in target (intra-promote only)
   }
   ```

3. Keep all other promotion logic, demotion cascades, and 75/25 bucket geometry (24 normal + 8 stash buckets) unchanged.

## Rationale

v001 achieved the highest hit-rate (0.7161) through frequency-gating on 75/25 geometry, but its insight reveals a latency trade-off: added counter comparisons and longer dwell in the target tier before earning promotion introduce measurable get-latency overhead (112 ns). Lowering the threshold from 2 to 1 directly addresses this penalty by promoting more items earlier (threshold now triggers on first re-access instead of second), reducing the time items spend in the target tier without compromising gate selectivity—items still require at least one prior access to promote, filtering true single-access misses. On 75/25's concentrated stash (only 8 buckets), threshold=1 should filter enough false-positives to preserve hit-rate while restoring latency closer to pure-geometry baselines. This tests whether the latency/hit-rate frontier can be shifted favorably through threshold tuning rather than geometry adjustment.
