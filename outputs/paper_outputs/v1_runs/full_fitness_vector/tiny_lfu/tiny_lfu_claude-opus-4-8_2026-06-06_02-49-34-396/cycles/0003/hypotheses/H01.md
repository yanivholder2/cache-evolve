# H01

Narrowing v002's counters from u32 to u8 will cut per-op-time and sketch heap while preserving its admission semantics and hit-rate.

## Parent

cycle/0002/v002

## Changes

v002 already carries the proven efficiency levers — the `FastHasher`
multiply-xorshift hasher and single-base-hash double hashing
(`base_hash` + `position_for`) — but it still stores `Vec<Vec<u32>>`
counters (sketch heap 65536). Compose in the u8 narrowing that won as
v001:

- Change `const MAX_COUNT: u32 = u32::MAX;` to `const MAX_COUNT: u8 = u8::MAX;`.
- Change `CountMinSketch.counts` from `Vec<Vec<u32>>` to `Vec<Vec<u8>>`,
  and `CountMinSketch::new` to `vec![vec![0u8; width]; depth]`.
- Update `heap_bytes()` to use `size_of::<u8>()`.
- In `increment`, keep the saturating `if *counter < MAX_COUNT` guard
  (now comparing `u8`).
- In `estimate`, map each row counter `as u32` before `.min()` so the
  return type stays `u32` and the admission comparison in `put` is
  unchanged.

Leave `FastHasher`, `base_hash`, `position_for`, the strict-LRU-head
eviction, and all residency logic exactly as in v002. The hypothesis is
that the cheap hasher and the narrow counters are additive: per-op-time
should hold at or near v002's 43ns (no extra hashing) while the sketch
heap drops 4x, and hit-rate should stay within noise since the trace's
true frequencies never approached u8 saturation in cycles 0001–0002.
