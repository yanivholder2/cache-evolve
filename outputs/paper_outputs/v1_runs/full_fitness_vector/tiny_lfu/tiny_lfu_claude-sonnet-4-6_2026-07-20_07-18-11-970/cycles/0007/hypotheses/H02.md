# H02

Replacing `u32` sketch counters with `u16` halves the CountMinSketch heap footprint, allowing more hot-row data to reside in L1/L2 cache and reducing per-op-time on the critical get and put paths.

## Parent

cycle/0006/v002

## Changes

All changes are confined to the `CountMinSketch` struct and its methods inside `mod.rs`. The `TinyLfuCache` eviction and admission logic is unchanged.

1. **Counter type:** Change `counts: Vec<Vec<u32>>` to `counts: Vec<Vec<u16>>`.

2. **Capacity constant:** Replace `const MAX_COUNT: u32 = u32::MAX;` with `const MAX_COUNT: u16 = u16::MAX;` (65 535). The constant name can stay the same or be renamed to `MAX_COUNT_U16`; update all references in `increment()`.

3. **`heap_bytes()`:** Update the size factor:
   ```rust
   fn heap_bytes(&self) -> usize {
       self.depth * self.width * std::mem::size_of::<u16>()
   }
   ```

4. **`increment()`:** The guard and mutation change to u16 arithmetic:
   ```rust
   let c = &mut self.counts[0][pos0];
   if *c < MAX_COUNT { *c += 1; }
   // ... same pattern for rows 1–3
   ```
   No other changes to the increment logic.

5. **`estimate()`:** Read u16 values and widen to u32 before the min-chain so the rest of the codebase (admission gate comparisons in `put()`) continues to receive `u32` without any changes to call sites:
   ```rust
   fn estimate<K: Hash>(&self, key: &K) -> u32 {
       // ... compute h0, h1, mask as before ...
       let c0 = self.counts[0][(h0 as usize) & mask] as u32;
       let c1 = self.counts[1][((h0 >> 16) as usize) & mask] as u32;
       let c2 = self.counts[2][(h1 as usize) & mask] as u32;
       let c3 = self.counts[3][((h1 >> 16) as usize) & mask] as u32;
       c0.min(c1).min(c2).min(c3)
   }
   ```
   The return type stays `u32`; the widening cast is lossless (u16 fits in u32).

6. **`new()`:** No change — `vec![vec![0; width]; depth]` initialises to `0u16` correctly once the type of `counts` is `Vec<Vec<u16>>`.

**Invariants to preserve:**
- The `TinyLfuCache` struct size (160 bytes) is unchanged; the sketch heap size shrinks.
- `estimate()` return type stays `u32` so the admission gate comparisons (`incoming_freq > victim_freq.saturating_add(1)` etc.) compile without modification.
- Functional semantics are identical: the minimum of four row-counters is the frequency estimate; counters saturate at their type maximum. The maximum trackable frequency per key drops from ~4 billion to 65 535, which is sufficient for the LIRS trace's access counts.
- All unit tests must pass (they do not inspect sketch internals).

## Rationale

At benchmark capacity 1024 the current u32 sketch heap is 4 × 4 096 × 4 = 65 536 bytes (64 KB), which exceeds most L1 caches. With u16, the heap shrinks to 32 768 bytes (32 KB), a size that fits entirely in L1 on many microarchitectures. At capacity 2048 the benefit is proportionally the same. Every `get()` and every `put()` touches the sketch (at least one `increment` + optionally one `estimate`), so reducing cache-miss pressure on sketch rows is on the hottest code path. The functional loss — frequency saturation at 65 535 instead of 4 billion — is negligible for the LIRS workload's access distribution.
