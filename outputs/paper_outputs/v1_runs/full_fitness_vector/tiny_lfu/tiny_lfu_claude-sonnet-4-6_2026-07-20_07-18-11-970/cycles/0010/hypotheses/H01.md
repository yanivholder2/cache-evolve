# H01

Restricting SLRU promotion to the `get` path only (lazy promotion on `put`) will reduce put-path latency without meaningfully degrading hit rate.

## Parent

cycle/0009/v002

## Changes

In `put`'s existing-key update branch (the `if let Some(&idx) = self.map.get(&key)` block),
change the conditional promotion logic so that a probationary node is **not** migrated to
the protected chain on a write:

**Current behaviour (v002):**
```rust
if self.is_protected(idx) {
    self.prot_unlink(idx);
    self.prot_push_back(idx);
} else {
    self.unlink(idx);
    self.promote_to_protected(idx);   // ← cross-chain migration on every put-update
}
```

**New behaviour:**
```rust
if self.is_protected(idx) {
    // Already protected: just refresh MRU position within the protected chain.
    self.prot_unlink(idx);
    self.prot_push_back(idx);
} else {
    // In probationary: stay in probationary, only refresh MRU position.
    self.unlink(idx);
    self.push_back(idx);              // ← no cross-chain migration
}
```

The `get` method is **unchanged**: a probationary node hit via `get` is still promoted to the
protected chain via `promote_to_protected`, exactly as in v002.

No other logic changes: the amortised gate (`evict_counter`, 1-in-8 stricter threshold),
the protected chain structure (prot_head / prot_tail / prot_count / prot_capacity / prot_flags
bitset), and the 8× sketch with bijective remix hash are all preserved.

### Rationale

Cycle 0009 identified put-path dual-list bookkeeping as the binding latency cost of the SLRU
design and asked whether deferring promotion to `get` only could reduce it. A `put` for an
existing key is a write-only event; promoting the node to the protected segment on that event
means write-heavy keys consume protected slots even if they are never read again. Restricting
promotion to confirmed read events (`get`) aligns protected-slot allocation with the hit-rate
objective and removes one cross-chain relinking operation from the write hot-path.
