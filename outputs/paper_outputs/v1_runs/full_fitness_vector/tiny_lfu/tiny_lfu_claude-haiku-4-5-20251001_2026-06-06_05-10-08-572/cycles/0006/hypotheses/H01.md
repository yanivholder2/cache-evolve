# H01

Reduce frequency-aware victim candidate pool to N=2 to lower latency variance while preserving hit-rate gains from frequency-based eviction.

## Parent

cycle/0005/v001

## Changes

In the `put()` method (around line 98-120), modify the frequency-aware victim selection loop to scan only N=2 items instead of N=5. Replace the loop `for _ in 0..4` with `for _ in 0..1` to scan one additional item after the head (checking head + next item only, 2 total). Keep all other logic identical: maintain the minimum-frequency selection strategy, the admission condition `incoming_freq > victim_freq`, and the linked list order.

Pseudocode change:
```rust
// Scan only 2 items total (head + 1 next), find minimum frequency
for _ in 0..1 {  // Changed from 0..4 to 0..1
    if let Some(idx) = current {
        let freq = self.sketch.estimate(&self.nodes[idx].key);
        if freq < min_freq {
            min_freq = freq;
            candidate = idx;
        }
        current = self.nodes[idx].next;
    } else {
        break;
    }
}
```

This targets both hit-rate preservation and latency variance reduction by testing the cost-benefit frontier of frequency-aware selection.

## Rationale

Cycle 0005's v001 achieved +0.3% hit-rate over baseline but paid +96% p99 tail latency by scanning 5 candidates. The hypothesis proposes N=2 as the minimal candidate window—checking only the head and next item in the linked list. This drastically reduces scanning overhead while potentially preserving most frequency-aware benefits: the linked list is LRU-ordered, so the head + next item represent the two coldest candidates by recency, and comparing their frequencies is likely to identify the cold item unless the second-coldest item is paradoxically hot. Testing N=2 directly brackets the cost-benefit frontier recommended by cycle 0005's continuation guidance.
