# H01

Halving the second-chance scan window from 8 to 4 positions in `eviction_candidate_index` will eliminate the put-path scan overhead that cycle 0007 isolated as the surviving regression source in `cycle/0006/v003`, reducing per-op-time while retaining most of the hit-rate benefit because the vast majority of never-accessed cold items accumulate at the last 1–2 positions before the scan reaches position 4.

## Parent

cycle/0006/v003

## Changes

In `src/shared/eviction_policy.rs`, `ClassicLRU::eviction_candidate_index`, change the single line:

```rust
let scan_depth = len.min(8);
```

to:

```rust
let scan_depth = len.min(4);
```

The loop body, fallback, and everything else in the method remain identical. The effect is that only the 4 coldest positions are inspected per eviction call instead of 8, halving the worst-case number of item reads on every PUT that triggers eviction.

Also include `src/shared/item.rs` in the overlay, carrying it forward verbatim from the `cycle/0006/v003` overlay (32-byte `#[repr(C)]` struct: `key`, `value`, `lfu_counter: usize`, `_pad: u64`). This is required — prior cycles have repeatedly lost the compact layout by overlaying only `eviction_policy.rs`.

No changes to `get_from_position`, `promotion_candidate_index`, the trait, or any other file.

## Rationale

Cycle 0007 falsified swap-write pressure as the cause of `cycle/0006/v003`'s put-p99 elevation: three variants eliminating 1, then 0 promotion swaps showed no measurable per-op-time improvement at the 100 ns floor. The only remaining source of extra work on the PUT-triggered eviction path is the linear 8-item scan. Reducing it to 4 items is the minimum targeted test: if per-op-time improves, the scan depth is confirmed as the regression source and the next cycle can tune the exact threshold; if no change is measured, the 100 ns floor is masking the effect and a different diagnosis is needed.
