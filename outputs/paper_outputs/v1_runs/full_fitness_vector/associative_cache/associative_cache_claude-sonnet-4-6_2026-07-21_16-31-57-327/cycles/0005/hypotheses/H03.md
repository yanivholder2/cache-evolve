# H03

Using the `lfu_counter` to gate promotion distance — advancing 1 step on a first access but 3 steps on repeat accesses — will improve hit rate on Zipfian traces by fast-tracking confirmed hot keys to the head while avoiding over-promotion of items that were accessed only once.

## Parent

cycle/0004/v002

## Changes

In `eviction_policy.rs`, modify `ClassicLRU::get_from_position` to increment `lfu_counter` and then derive the promotion step count from the resulting counter value: 1 step when `lfu_counter == 1` (first access), 3 steps when `lfu_counter >= 2` (repeat access). The loop is otherwise identical to H01's unconditional multi-step loop, with an early-exit guard at `pos == 0`.

```rust
fn get_from_position(&self, items: &mut Vec<Item<K, V>>, position: usize) -> usize {
    if position == 0 {
        return 0;
    }
    items[position].lfu_counter += 1;
    // Hot keys (seen before) advance 3 steps; cold keys advance 1 step.
    let steps: usize = if items[position].lfu_counter >= 2 { 3 } else { 1 };
    let mut pos = position;
    for _ in 0..steps {
        items.swap(pos, pos - 1);
        pos -= 1;
        if pos == 0 {
            break;
        }
    }
    pos
}
```

Note: `items[position].lfu_counter` is read *before* any swap so the counter belongs to the correct item. After the first swap `pos` becomes `position - 1`; subsequent iterations continue moving the same item.

`eviction_candidate_index` stays at `items.len() - 1` (pure positional tail eviction, no counter scan). `promotion_candidate_index` stays at 0.

Carry the 32-byte `Item` struct from `cycle/0004/v002` forward unchanged: both `src/shared/item.rs` (with `_pad: u64`) and `src/shared/eviction_policy.rs` must be in the overlay.

## Rationale

Under Zipfian access patterns, a small fraction of keys account for the vast majority of requests — meaning most accessed items have been accessed before. v002 (single step, no counter) and H01 (three steps, no counter) treat all accesses uniformly. This hypothesis differentiates: a newly inserted key that is accessed once should advance conservatively (1 step), since one access is weak evidence it is hot. A key accessed a second time (counter ≥ 2) is confirmed hot and should advance aggressively (3 steps) to reach the head before eviction pressure can remove it. The threshold of 2 uses the already-maintained `lfu_counter` field as a proxy without introducing any additional state. If the Zipfian hot-key population is as concentrated as the trace suggests, the majority of gets will trigger the 3-step path after the warmup period, and the 1-step first-visit case will be rare in steady state.
