# H02

Replacing ClassicLRU's `remove+push` item promotion (O(n) Vec shift) with a single O(1) `swap` to the tail will reduce get-path latency below the baseline's 69 ns p50 while preserving approximate LRU eviction semantics.

## Parent

baseline

## Changes

Modify only `ClassicLRU.get_from_position` in `src/shared/eviction_policy.rs`. Replace the current body:

```rust
let item = items.remove(position);
items.push(item);
items.len() - 1
```

with:

```rust
let last = items.len() - 1;
items.swap(position, last);
last
```

`eviction_candidate_index` and `promotion_candidate_index` remain unchanged (returning `0` and `items.len()-1` respectively), so the eviction still removes from index 0 and the hottest item is considered to be the tail.

Semantics note: unlike the original `remove+push` which preserves strict relative order of all un-accessed items, `swap` moves the previously-MRU item (the one that was at `last`) to `position`. This introduces an approximation: the item displaced from the tail to `position` may appear to be "older" than items sitting between `position` and `last-1`, even though it was recently accessed. This is the same approximation used by CLOCK and second-chance algorithms and empirically causes minimal hit-rate divergence on Zipfian workloads. All other policy structs (`Lfu`, `TimestampLRU`, `Lifo`, `Fifo`, `Swap`) are left untouched.

## Rationale

The baseline's `Vec::remove(position)` in `get_from_position` shifts every item from `position+1` to `len-1` leftward by one slot — up to 15 element moves (each 40 bytes) on every cache hit. Replacing this with `swap` makes each hit O(1) regardless of position. Since the per-op-time benchmark measures p50 get latency on a primed, fully-occupied cache, and since the baseline is already the fastest at 69 ns, the only way to beat it is to reduce work on the hot get path — swap-to-back is the minimal O(1) change that preserves the MRU-at-tail invariant that `eviction_candidate_index` relies on.
