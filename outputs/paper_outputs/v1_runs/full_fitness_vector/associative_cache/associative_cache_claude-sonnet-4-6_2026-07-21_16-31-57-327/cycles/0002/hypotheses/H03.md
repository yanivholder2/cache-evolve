# H03

Padding the compact 24-byte Item struct from v003 to exactly 32 bytes with an explicit alignment attribute will eliminate the cache-line splitting that caused v003's per-op-time regression while retaining a metadata-size win over the 40-byte baseline.

## Parent

cycle/0001/v003

## Changes

Modify `src/shared/item.rs`, which in v003 already has the `timestamp` field removed (leaving `key`, `value`, `lfu_counter` — 24 bytes for `K=u64, V=u64`). Add one padding field and a repr attribute:

1. Add `#[repr(C)]` to the `Item<K, V>` struct to guarantee field-order layout rather than allowing the compiler to reorder.
2. Add a private padding field `_pad: u64` immediately after `lfu_counter`:

```rust
#[repr(C)]
#[derive(Debug, Clone)]
pub struct Item<K, V>
where
    K: Hash + Eq + Clone,
    V: Eq + Clone,
{
    pub key: K,
    pub value: V,
    pub lfu_counter: usize,
    _pad: u64,
}
```

3. Update `Item::new` to initialise `_pad: 0`.
4. Leave `PartialEq`, `Eq`, `Display`, and all tests unchanged — `_pad` is never compared or printed.

With `K=u64, V=u64` this makes `sizeof::<Item<u64,u64>>() == 32`. At 32 bytes, exactly **2 items fit per 64-byte cache line** with no cross-boundary splitting, regardless of offset within the `Vec`'s allocation. The 24-byte v003 struct instead crosses a cache-line boundary every third item (items at offsets 0, 24, 48 — the third item straddles bytes 48–71, spanning the 0–63 and 64–127 cache lines), which disrupts prefetch and increases cache-miss pressure during `get_position`'s sequential key scan.

The `geometry.rs` overlay is not changed (inheriting v003's baseline 128×16 geometry). The `eviction_policy.rs` overlay is also not changed (inheriting baseline ClassicLRU semantics).

## Rationale

The cross-cycle insight asks explicitly whether the cache-line regression from struct shrinkage is fixable with explicit alignment. v003 landed metadata-size at 24 bytes but regressed per-op-time from 69 to 100 ns. The 8-byte loss in each of the three fields leaves a 24-byte struct, and 24 does not divide 64 evenly, causing every third item in a Vec to straddle two cache lines. Padding to 32 bytes (a power-of-two divisor of 64) restores the natural two-items-per-line packing, which should recover the get-latency advantage. The resulting metadata-size (32) remains below the baseline (40), so this hypothesis wins on both metadata-size and, if the alignment hypothesis is correct, per-op-time.
