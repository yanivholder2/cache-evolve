# H03

Composing v003's 32-byte cache-line-aligned Item layout with the position-0 early-return guard and single-swap LFU from H01's strategy will simultaneously preserve the p99 tail-latency fix and improve hit rate while targeting baseline-competitive get-p50.

## Parent

cycle/0002/v003

## Changes

Two files are modified; `item.rs` is kept exactly as v003 left it, and only `eviction_policy.rs` changes.

**`src/shared/item.rs`** — no change. The `#[repr(C)]` layout with `_pad: u64` giving a 32-byte `Item<u64,u64>` is preserved as-is. The existing unit test `size_is_32_bytes_for_u64_keys_and_values` must still pass.

**`src/shared/eviction_policy.rs`** — modify `ClassicLRU::get_from_position` only:

1. If `position == 0`: return `0` immediately (no counter write, no neighbor load).
2. Otherwise: increment `items[position].lfu_counter` by 1, then perform at most one conditional swap — `if items[position].lfu_counter > items[position - 1].lfu_counter { items.swap(position, position - 1); return position - 1; }` — and return `position` if no swap occurred.
3. The existing `while` bubble loop is removed.

`eviction_candidate_index` stays `items.len() - 1` (tail = coldest under soft LFU ordering). `promotion_candidate_index` stays `0`. All other policy structs (`TimestampLRU`, `Lifo`, `Lfu`, `Fifo`, `Swap`) and the `EvictionPolicyKind` enum are left untouched, preserving JNI-visible ordinals and the exhaustive match that guards against accidental variant additions.

## Rationale

v003 proved that 32-byte alignment reliably halves p99 tail latency (200 ns → 100 ns) by packing two items per cache line and eliminating cross-boundary splits. v001 demonstrated that LFU ordering lifts hit-rate to 0.703 but the full bubble loop pushed per-op-time to 100 ns. The cycle-insight for cycle 0002 explicitly flagged "composing 32-byte alignment with guarded LFU" as the primary open question. This hypothesis closes that question: v003's Item layout eliminates cache-line splits on every swap (two items per line means a swap only touches one cache line), while the single-swap LFU guard ensures the hot path for position-0 items is a single comparison and branch with zero memory writes. The composition is expected to improve all three dimensions relative to v003: hit-rate (LFU over LRU), per-op-time (skip writes for hot items), and metadata-size (32 bytes, same as v003, below v001's 40 bytes).
