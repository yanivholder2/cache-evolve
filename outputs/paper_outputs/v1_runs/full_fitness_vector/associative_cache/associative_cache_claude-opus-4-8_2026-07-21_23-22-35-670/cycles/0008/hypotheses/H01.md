# H01

Skip the per-hit protected-MRU rotation while the protected segment is below its cap to cut per-op-time on the SLRU incumbent without moving hit-rate.

## Parent

cycle/0006/v001

## Changes

In the segmented bucket's `get_from_position` (src/associative_cache/associative_cache_bucket.rs), the protected-hit branch currently runs `self.items[position..].rotate_left(1)` unconditionally to keep the protected segment in MRU order. That ordering is only ever *consumed* by the demotion step, which removes the protected-LRU item at `boundary` when a probationary promotion pushes `protected_len` past `protected_cap()`. Demotion therefore cannot fire while `protected_len < protected_cap()`. Because `protected_cap()` is `max(1, max_size/2) < max_size`, the bucket is never fully protected, so index 0 is always a probationary item and eviction (`remove(0)`) never depends on protected order either.

Make the protected-hit branch conditional:
- When `self.protected_len >= self.protected_cap()` (segment saturated, a demotion is imminent on the next promotion), keep the existing `self.items[position..].rotate_left(1)` and return `len - 1` exactly as today — strict MRU order still governs which protected item is demoted.
- When `self.protected_len < self.protected_cap()`, do not rotate: return the item at `position` in place. No pending demotion reads the order, so eviction and demotion decisions are bit-for-bit identical.

Leave the probationary-promotion branch, `put`, front-admission, and all `protected_len`/`boundary` bookkeeping unchanged. The invariant to preserve: eviction still always targets the probationary front (index 0), and a saturated protected segment still demotes its true LRU. Hit-rate must be identical to the parent; the win is fewer element moves per protected hit (lower get p50/p99).
