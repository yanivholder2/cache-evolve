# H03

Removing the now-dead `lfu_counter` field on top of v003's already-trimmed `Item` shrinks `Item<u64,u64>` from 24 to 16 bytes, since the `ClassicLRU` eval path never reads it.

## Parent

cycle/0001/v003

## Changes

v003 dropped `timestamp` to reach `Item<u64,u64>` = key(8)+value(8)+
lfu_counter(8) = 24 bytes. But the configured eval policy is plain
`ClassicLRU`, whose `get_from_position` and `eviction_candidate_index`
never touch `lfu_counter` — it is pure dead weight on this path, exactly
like `timestamp` was. Cut it too.

In `src/shared/item.rs`:
- Remove the `pub lfu_counter: usize` field from `Item` and from
  `Item::new` (leaving `key` + `value` only → 16 bytes for `u64,u64`).
- Update the `Display` impl and the doc-test/unit tests in that file that
  reference `lfu_counter` so the file still compiles (mirror how v003
  handled the `timestamp` removal).

In `src/shared/eviction_policy.rs`, neutralise the policies that read
`lfu_counter` while keeping the type/ordinal surface intact (same tactic
v003 used to reduce `TimestampLRU` to FIFO):
- `Lfu::get_from_position` becomes a no-op returning `position`;
  `Lfu::eviction_candidate_index` returns `0` (front), and
  `promotion_candidate_index` returns `items.len() - 1`.
- Ensure `ClassicLRU` remains the baseline remove+push / evict-front form
  (do NOT add v002's reuse flag here — that needs the counter we are
  removing).

Keep every `EvictionPolicyKind` name/index/ordinal and the JNI-facing
enum unchanged so contracts don't shift. Target dimension: metadata-size,
pushing the frontier from 24 to 16.

## Rationale (optional)

The cycle continuation explicitly favours "cut dead weight off the eval
path" moves as cheap and monotonic. `lfu_counter` is only alive for the
off-path `Lfu` policy (and v002's counter trick), so on the pure-LRU eval
path it is removable with zero hit-rate cost — the same argument that made
v003's timestamp cut free, applied one field deeper.
