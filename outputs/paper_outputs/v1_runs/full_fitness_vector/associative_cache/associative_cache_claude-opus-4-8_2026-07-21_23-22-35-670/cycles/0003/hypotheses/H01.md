# H01

Relocate the binary reuse-protection bit out of `Item` into a per-bucket bitmask so scan-resistant eviction restores v001-level hit-rate while `Item` stays at the 16-byte metadata floor.

## Parent

cycle/0002/v003

## Changes

v003 reached the 16-byte metadata floor (`Item` = key + value only) but, by
dropping `lfu_counter`, lost v001's scan-resistant reuse-protection and fell
back to plain-LRU hit-rate (0.6611 vs v001's 0.7267). The metadata-size
metric measures only `size_of::<Item<u64,u64>>()` (see
`src/bin/evolve_metadata_size.rs`); the bucket struct is not measured. So
reuse state kept in the bucket is free for that dimension.

Reintroduce v001's mechanism without touching `Item`:

- In `src/associative_cache/associative_cache_bucket.rs`, add a bucket-side
  reuse set parallel to `items` — a `Vec<bool>` (or a `u64` bitmask, since
  buckets are small) tracking, per slot index, whether that resident item
  has been hit at least once since insertion. Keep `Item` exactly as v003
  left it (key + value, 16 bytes).
- Maintain the reuse set alongside every structural mutation of `items`.
  Override the concrete bucket's `put`/`get_from_position` and the eviction
  path so that: on insertion of a miss item the slot's reuse bit is cleared;
  on a hit the item's reuse bit is set; and when `items` is reordered
  (ClassicLRU moves a hit item to the back) the reuse bits move with them so
  index alignment is preserved.
- Reimplement the eviction candidate selection to mirror v001: evict the
  first slot in LRU-front order whose reuse bit is `false`
  (one-hit-wonder); if every resident item is protected, fall back to the
  LRU front (index 0). Because the policy trait's
  `eviction_candidate_index(&self, items)` cannot see bucket-side state,
  drive this from the concrete `AssociativeCacheBucket` (override
  `eviction_candidate_index` / `evict_item`) rather than from the
  `EvictionPolicy` impl.

Preserve capacity conservation, get-returns-last-put, and the reuse-set
length invariant (`reuse.len() == items.len()` at all times). Do not edit
any gate-integrity file. Success = hit-rate ≈ 0.7267 with metadata-size = 16.

## Rationale (optional)

This directly answers the standing cross-cycle question — "can scan
resistance be gained at the metadata floor?" — by exploiting that the metric
only weighs `Item`. If it lands it strictly dominates both incumbents on the
two movable dimensions simultaneously.
