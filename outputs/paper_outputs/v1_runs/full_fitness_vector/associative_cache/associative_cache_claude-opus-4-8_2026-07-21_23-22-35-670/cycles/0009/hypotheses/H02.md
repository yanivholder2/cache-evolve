# H02

Replace the bucket's parallel `reuse: Vec<bool>` with a single `u64` bitmask so per-hit reuse maintenance and eviction-victim selection become register bit-ops instead of heap-vector shifts, lowering per-op-time.

## Parent

cycle/0008/v002

## Changes

Target `src/associative_cache/associative_cache_bucket.rs`. v002 keeps a
parallel `reuse: Vec<bool>` index-aligned with `items`, and on every hit does a
`reuse.remove(position)` + `reuse.insert(index, bit)` (a second O(bucket) heap
shift layered on top of the policy's own item move) plus a linear scan in
`eviction_candidate_index`. Replace that `Vec<bool>` with a `reuse_mask: u64`
field (bit `i` == "slot `i` has been hit since insertion"; bits at positions
`>= items.len()` held at 0). Assume `bucket_size <= 64` (small associativity) and
`debug_assert!(self.max_size <= 64)` in `new`.

Rewrite the four touch points to keep `reuse_mask` bit `i` ↔ `items[i]` aligned:
- `new`: initialise `reuse_mask = 0`.
- `put` (miss branch): after `items.push`, the new slot is the top index and its
  bit must be 0 — clear it explicitly (`self.reuse_mask &= !(1u64 << idx)`).
- `get_from_position`: after the policy relocates the item from `position` to
  `index`, mirror that single-element move on the mask by splicing: extract the
  bit at `position`, close the gap (bits above `position` shift down one), open a
  gap at `index` (bits at/above `index` shift up one), reinsert the extracted
  bit, then set bit `index` to 1. Do it with masked shifts, no per-slot loop.
- `eviction_candidate_index`: `if items.is_empty() { None }` else compute
  `let live = (1u64 << len) - 1; let unreused = !self.reuse_mask & live;` and
  return `Some(unreused.trailing_zeros() as usize)` when `unreused != 0`,
  else `Some(0)` (all-protected fallback to LRU front) — an O(1) replacement for
  the linear scan.
- `remove_at(index)`: close the mask gap at `index` (bits above shift down one)
  before/after `items.remove(index)`.

Observable behaviour — hit/miss outcomes, the exact eviction victim, and item
ordering — must be identical to v002 (this is a pure representation change), so
hit-rate stays 0.7267 and the `Item` stays 16 bytes. The claim is that removing
the second heap vector and its per-hit shift (and the O(bucket) eviction scan)
lowers the get/put p50/p99.

## Rationale (optional)

v002 proved the scan-resistance state is free on metadata; this tests whether it
can also be made near-free on latency by folding the parallel `Vec<bool>` into a
scalar the CPU manipulates in a few instructions, while preserving v002's
bit-for-bit hit-rate and 16-byte floor.
