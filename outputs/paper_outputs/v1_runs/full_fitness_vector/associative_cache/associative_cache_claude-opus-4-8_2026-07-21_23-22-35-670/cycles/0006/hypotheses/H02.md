# H02

Make protected-segment hits skip the rotate-to-MRU reorder so the SLRU bucket sheds its per-access rebalance latency, cutting per-op-time while holding hit-rate.

## Parent

cycle/0005/v003

## Changes

The parent's `get_from_position` does structural work on *every* hit: even a hit
on an already-protected item runs `self.items[position..].rotate_left(1)` to
move it to the protected MRU (back). That rotation is O(segment length) per hit
and is the dominant driver of the get/put tail-latency regression flagged in the
parent's insight, yet it only reorders items *within* the protected segment —
which never changes membership and never changes which item is evicted (eviction
always removes index 0, a probationary slot unless the whole bucket is
protected).

Change the protected-hit branch to be a **lazy, no-op reorder**:

- In `get_from_position`, when `position >= boundary` (item already protected),
  return `position` unchanged instead of rotating it to `len - 1`. Do not touch
  `protected_len`. The item stays where it is; no `rotate_left`.
- Leave the probationary branch untouched: a probationary hit still promotes the
  item across the boundary via the existing `rotate_left` and increments
  `protected_len`, with the same cap/demotion bookkeeping.

Invariants to preserve: `protected_len` still counts exactly the top-of-Vec
protected slots; eviction still removes index 0; the probationary→protected
promotion path is unchanged, so the resident set — and therefore hit-rate —
should be **identical** to the parent (protected-MRU ordering does not affect
which items survive, only their intra-segment order, and eviction never touches
the protected segment while probationary items exist).

This is a pure latency play: the common case (a hit on an already-hot,
protected key) becomes a bare index return instead of a segment rotation.

## Rationale (optional)

Directly answers the cycle-5 open question — "can the SLRU win shed its
per-access rotate/rebalance latency via lazy demotion / cheaper boundary
bookkeeping?" — by removing the one reorder that carries no eviction-quality
information.
