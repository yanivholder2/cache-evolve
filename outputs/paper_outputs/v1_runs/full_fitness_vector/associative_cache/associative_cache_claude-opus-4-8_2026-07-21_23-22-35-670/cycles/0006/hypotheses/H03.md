# H03

Cap the number of protected (reuse-bit-set) slots on the best incumbent so a saturated bucket keeps a live probationary zone instead of collapsing to plain LRU, lifting hit-rate above the current 0.7267 ceiling.

## Parent

cycle/0003/v001

## Changes

The parent protects any resident that has been hit at least once: its
`eviction_candidate_index` scans `self.reuse` and returns the first slot whose
bit is `false`, falling back to index 0 only when *every* bit is set. On a
bucket under sustained reuse this fallback fires constantly — once all bits are
set the policy degenerates to evicting the ClassicLRU front (plain LRU), losing
the scan-resistance the reuse bit was meant to provide. This is the exact
"protection saturates and collapses back toward LRU" failure the cross-cycle
notes describe.

Introduce a **bounded protected set** — the counter-based analogue of SLRU's
capped protected segment, kept entirely off-`Item` on the bucket struct so the
16-byte metadata floor is preserved:

- Add a method `protected_cap(&self) -> usize` returning `max(1, max_size / 2)`
  (start here; the cap is the tunable knob).
- After `get_from_position` sets `self.reuse[index] = true`, count the set bits.
  If the count now exceeds `protected_cap()`, clear the reuse bit of the
  **least-recently-used protected slot** — i.e. scan `self.reuse` from index 0
  (the ClassicLRU eviction end) forward and clear the first `true` bit. This
  demotes the oldest protected item back to probationary, guaranteeing at least
  `max_size - protected_cap()` probationary slots always exist as eviction
  fodder.
- `eviction_candidate_index` is unchanged (first `false` bit, else index 0); the
  cap simply ensures a `false` bit almost always exists, so the index-0 fallback
  stops dominating.

Invariants to preserve: `reuse` stays index-aligned with `items` through the
existing `realign_reuse` / `remove_at` machinery; no new per-`Item` fields (all
state is the existing `Vec<bool>` plus the cap computation), so metadata-size
stays at 16 and the fresh-insert-is-probationary rule is unchanged.

## Rationale (optional)

The parent holds the best hit-rate at the metadata floor but degrades to LRU
under reuse pressure; bounding the protected set is the minimal, off-`Item`
change that emulates SLRU's protected cap on the proven floor-holding incumbent,
and it directly probes the open question of the optimal protected cap for short
buckets.
