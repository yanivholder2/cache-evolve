# H03

Raising the segmented incumbent's protected cap to near `max_size` — demoting only when protection is near-total — turns cycle-6's aggressive-cap hit-rate regression into a gain.

## Parent

cycle/0006/v001

## Changes

Overlay `associative_cache_bucket.rs` only, inheriting the rest of
`cycle/0006/v001` unchanged (the 16-byte `Item`, front-admission put,
single-element SLRU rotations). The single change is the
`protected_cap` knob and its demotion trigger in `get_from_position`.

Today `protected_cap()` returns `max(1, self.max_size / 2)`, and every
promotion that would exceed it silently decrements `protected_len` (a
soft boundary move that parks the item as probationary MRU). Cycle 6
proved `max_size/2` is far too aggressive for these short buckets: it
demotes genuine reuse winners back into scan-fodder and dropped hit-rate
to 0.7187 (v001) / 0.689 (v003, hard demotion). Both the cycle-6 and
cross-cycle insights converge on the fix: the cap must sit close to
`max_size` and demote only when protection is near-total.

Concretely:
- Change `protected_cap()` to return `max_size.saturating_sub(1)`
  (i.e. reserve exactly one probationary slot) so protection is allowed
  to grow until only a single live probationary slot remains, keeping a
  probationary victim at index 0 in the common case while never
  demoting reuse winners prematurely.
- Keep the existing soft-demotion mechanism (decrement `protected_len`
  when over cap) so the change is purely to *where* the cap sits, not
  how demotion works — this isolates the cap-position variable against
  v003's confound (v003 also changed the demotion to a hard
  evict-the-LRU-protected move).
- Preserve all other invariants: `protected_len <= items.len()`, the
  `boundary = len - protected_len` arithmetic, and the
  `protected_len == 0` sole-protected special case in the promotion
  branch.

This directly answers the standing open question ("where does the
optimal protected cap sit — near `max_size`, and does near-total-only
demotion turn the regression into a gain?"). It targets hit-rate at the
16-byte floor with no new per-op work, so metadata-size and per-op-time
should hold at 16 / 100 while hit-rate is the measured variable.
