# H01

Repartition the fixed total capacity into one-quarter as many buckets of quadruple width to raise hit rate by increasing set-associativity.

## Parent

baseline

## Changes

Overlay `src/shared/geometry.rs`. Keep the `BaselineGeometry` struct, its
fields (`num_of_buckets`, `bucket_size`), and the `for_settings` entry point
exactly as they are so the construction glue and the invariant gate still build
the geometry the same way. Change only the `BucketGeometry::layout`
implementation:

- Compute `total = self.num_of_buckets * self.bucket_size` (the budget that must
  be conserved).
- If `self.num_of_buckets` is divisible by 4 and `self.num_of_buckets / 4 >= 1`,
  return `(self.num_of_buckets / 4, self.bucket_size * 4)` — four times wider
  buckets, one-quarter as many. For the eval point (128 × 16) this yields
  `(32, 64)`.
- Otherwise return `(self.num_of_buckets, self.bucket_size)` unchanged.

This guarantees the returned `(num, size)` product always equals `total`, so
`factory::resolve_geometry`'s capacity-conservation check (P4) still passes, and
because keys are still hashed modulo the resolved bucket count, P2 slot-legality
holds. The hypothesis is that wider buckets absorb more hash collisions, cutting
conflict misses and lifting hit rate above 0.6611; the expected cost is a modest
per-op-time increase from longer linear scans, which the simulator will
quantify. Do not touch the eviction policy or item layout.
