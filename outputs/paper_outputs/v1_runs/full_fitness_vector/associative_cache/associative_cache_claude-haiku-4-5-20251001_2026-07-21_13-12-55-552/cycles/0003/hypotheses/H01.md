# H01

Narrow buckets (256×8) with ClassicLRU policy will achieve lower per-operation latency than baseline by reducing intra-bucket scan depth, compensating for expected hit-rate loss through improved latency on Zipfian workload.

## Parent

baseline

## Changes

Modify `src/shared/geometry.rs` in the `BaselineGeometry::layout()` method. Replace the identity return with a repartitioning that doubles the bucket count and halves the bucket size, preserving total capacity:

```rust
fn layout(&self, total_capacity: usize) -> (usize, usize) {
    // Narrow buckets: double bucket count, halve item count.
    // Preserve total capacity: num_buckets * bucket_size = total_capacity.
    let new_num_buckets = self.num_of_buckets * 2;
    let new_bucket_size = self.bucket_size / 2;
    (new_num_buckets, new_bucket_size)
}
```

For the baseline (128 × 16 = 2048), this yields 256 × 8 = 2048, preserving total capacity exactly.

Keep all other settings unchanged: eviction policy (ClassicLRU), all other cache parameters.

## Rationale

Cycle 0001 tested 256×8 geometry (halving the design one direction) but paired it with LFU eviction, which incurred additional bookkeeping overhead and resulted in +45% latency regression and hit-rate degradation (0.6611 → 0.6568).

This hypothesis revisits narrower buckets but with ClassicLRU—the baseline policy—to isolate the geometry effect from policy overhead. The rationale is that narrower buckets reduce the cost of sequential intra-bucket scans in the ClassicLRU's O(n) vector operations. For 128×16, ClassicLRU must scan up to 16 items; for 256×8 (or 512×4), it scans up to 8 (or 4) items. This reduction in scan depth could outweigh any hit-rate loss if the constant factors in scan operations dominate latency, which the cycle-2 insight suggests they do.

Even if hit-rate regresses on Zipfian access due to reduced collision tolerance, the latency improvement may yield better overall fitness if the per-operation cost drops sufficiently. This tests whether smaller buckets can achieve better absolute latency under ClassicLRU's optimized implementation, unlike the LFU variant that added semantic overhead.
