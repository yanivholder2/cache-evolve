# H02

Increase bucket count to 256 and reduce bucket size to 8 to isolate hot items from eviction pressure caused by hash collisions with cold items in Zipfian workloads.

## Parent

baseline

## Changes

Modify `src/shared/geometry.rs` in the `BaselineGeometry::layout()` method. Replace the identity logic that returns `(self.num_of_buckets, self.bucket_size)` with a repartitioning that doubles the bucket count and halves the bucket size:

```rust
fn layout(&self, total_capacity: usize) -> (usize, usize) {
    // Repartition to narrower buckets with higher bucket count.
    // Preserve total capacity: num_buckets * bucket_size = total_capacity.
    // Double the number of buckets, halve the bucket size.
    let new_num_buckets = self.num_of_buckets * 2;
    let new_bucket_size = self.bucket_size / 2;
    (new_num_buckets, new_bucket_size)
}
```

For the baseline (128 × 16 = 2048), this yields 256 × 8 = 2048, preserving total capacity and satisfying the invariant gate's capacity-conservation check.

Keep all other code unchanged: eviction policy logic, bucket implementation, item structure.

## Rationale (optional)

In a Zipfian workload, a small set of hot items dominates access, while many cold items access sporadically. With fewer, wider buckets (baseline: 128 × 16), hot items that collide with cold items in the same bucket face competition; when the bucket fills, the eviction policy may remove a hot item if a cold item is more recently used or less frequently accessed at that moment.

Increasing bucket count spreads items across more independent buckets. Hot items are more likely to occupy their own bucket or a bucket with fewer cold-item competitors. Even when collisions occur, each bucket is smaller (8 items vs. 16), so a hot item's slot is less likely to be displaced by transient cold accesses. This trading of bucket width for bucket isolation should increase hit-rate on Zipfian traces.
