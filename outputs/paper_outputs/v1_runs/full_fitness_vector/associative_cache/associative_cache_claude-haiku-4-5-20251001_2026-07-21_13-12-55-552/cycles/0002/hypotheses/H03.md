# H03

Switch to FIFO eviction policy to minimize per-operation overhead by eliminating all position tracking, targeting per-op-time improvement while testing hit-rate tolerance on Zipfian workloads.

## Parent

baseline

## Changes

Modify `src/associative_cache/associative_cache_settings.rs` in the `Default` implementation: change the `eviction_policy` field from `EvictionPolicyKind::ClassicLRU` to `EvictionPolicyKind::Fifo`.

FIFO (First-In-First-Out) is already implemented in `src/shared/eviction_policy.rs`. Unlike ClassicLRU, which moves items on hit, or TimestampLRU, which updates timestamps on hit, FIFO performs no bookkeeping on cache hits—`get_from_position()` returns the position unchanged. On eviction, FIFO removes the item at position 0 (the oldest inserted item).

This makes FIFO the minimal-cost eviction policy: no per-hit bookkeeping, no vector manipulations, no timestamp updates. Eviction is deterministic and predictable (always remove the front item). The policy trades hit-rate sensitivity for minimal implementation overhead.

Keep all other settings unchanged: bucket geometry (128 buckets × 16 items), bucket implementation, and all other cache parameters.

## Rationale

Cycle 0001 demonstrated that ClassicLRU's recency-tracking strategy (0.6611 hit-rate, 69ns get latency) is sound for Zipfian workloads, but the cost of maintaining that strategy—removing and re-inserting items on each hit—is measurable. Variant v001 (LFU) and v003 (Swap) both incurred latency penalties (40–200% slowdowns) despite semantic improvements, showing that bookkeeping overhead dominates at this cache size.

FIFO is the opposite extreme: zero bookkeeping on hit. It sacrifices recency awareness entirely and evicts items purely by insertion order. On a Zipfian workload, this risks hit-rate degradation because recency alone is insufficient to predict access patterns—hot items may be evicted if they happen to be old. However, if hit-rate degrades only modestly (e.g., 0.65 vs. 0.6611), FIFO's latency gain could yield a better fitness score overall.

This hypothesis tests the trade-off frontier: how much hit-rate can be sacrificed for latency efficiency? The answer will inform whether future variants should prioritize policy richness or implementation minimalism for this cache geometry and workload.
