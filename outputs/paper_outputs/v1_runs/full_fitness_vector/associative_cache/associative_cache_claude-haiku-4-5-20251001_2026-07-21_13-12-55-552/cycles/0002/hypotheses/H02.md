# H02

Switch to 64 buckets × 32 items geometry to reduce hash-table search overhead and improve cache locality by consolidating items into wider buckets, targeting per-op-time improvement.

## Parent

baseline

## Changes

Modify `src/shared/geometry.rs` in the `BaselineGeometry::layout()` method. Replace the identity logic that returns `(self.num_of_buckets, self.bucket_size)` with a repartitioning that halves the bucket count and doubles the bucket size:

```rust
fn layout(&self, total_capacity: usize) -> (usize, usize) {
    // Repartition to wider buckets with lower bucket count.
    // Preserve total capacity: num_buckets * bucket_size = total_capacity.
    // Halve the number of buckets, double the bucket size.
    let new_num_buckets = self.num_of_buckets / 2;
    let new_bucket_size = self.bucket_size * 2;
    (new_num_buckets, new_bucket_size)
}
```

For the baseline (128 × 16 = 2048), this yields 64 × 32 = 2048, preserving total capacity and satisfying the invariant gate's capacity-conservation check.

Keep all other code unchanged: eviction policy logic, bucket implementation, item structure, and settings.

## Rationale

Cycle 0001 variant v002 tested the opposite direction—increasing bucket count to 256 × 8—and observed that narrower buckets increased search overhead within buckets and reduced hit-rate (0.6611 → 0.6568), likely because smaller buckets increased fragmentation and the per-bucket search cost outweighed any isolation benefit.

This hypothesis tests the inverse: consolidating the same total items into fewer, wider buckets (64 × 32). The rationale is that larger buckets may improve memory locality—items are packed more densely, improving CPU cache line utilization and reducing memory latency on sequential searches within a bucket. A smaller hash table (64 vs. 128 buckets) also reduces the cost of the initial hash lookup itself.

The trade-off is collision handling: hot and cold items in the same bucket will contend for space, but baseline's ClassicLRU eviction should handle mixed-temperature items adequately. This geometry is the geometric opposite of v002 and tests whether the design space favors wider or narrower buckets for this cache size and workload.
