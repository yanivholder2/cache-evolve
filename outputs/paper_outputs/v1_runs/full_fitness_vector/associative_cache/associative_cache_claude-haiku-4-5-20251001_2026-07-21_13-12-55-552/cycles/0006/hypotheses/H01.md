# H01

Predict eviction targets via access-distance tracking to improve hit-rate by preferentially evicting cold items while avoiding per-hit bookkeeping overhead.

## Parent

baseline

## Changes

Add a `last_access_epoch` field (u32) to each `Item<K, V>`. Maintain a global operation counter (`epoch`) in the cache that increments on every get or put operation.

During get operations, update the item's `last_access_epoch` to the current epoch (same cost as ClassicLRU's position update, but recorded differently).

During eviction (in `evict_one()`), instead of blindly removing the first item, scan the bucket and compute reuse distance for each item as `current_epoch - last_access_epoch`. Evict the item with the maximum reuse distance (least recently used at distance scale). This is O(n) per eviction but eviction is rare, so the overall cost is amortized.

The key difference from ClassicLRU: we defer the decision logic to eviction time (rare path) rather than hit time (common path), trading per-hit cost for per-eviction cost.

## Rationale

Cycle 0005 showed that Zipfian workload hit-rate is indifferent to policy details (0.661–0.665 across all policies). This hypothesis targets predictive eviction without burdening the hit path. By tracking access recency and evicting based on distance, we capture locality at eviction time without the per-hit vector manipulation that ClassicLRU does. If hit-rate improves, it validates that access distance is a better eviction signal than strict LRU order for this workload; if hit-rate stays flat, we've proved that eviction policy is not the lever, and cycle 0006 recommendations (learned or architectural approaches) should be prioritized.
