# H03

Implement learned insertion positioning that predicts whether items will be reused based on recent access patterns, biasing insertion location to preserve hot items without metadata expansion.

## Parent

baseline

## Changes

Track the last N=16 access outcomes (hit or miss) in a rolling buffer. Before inserting a new item into a bucket, sample this recent history: if >50% were hits, insert the new item at the bucket head (prioritizing retention); otherwise insert at tail (lower priority for retention). During get operations, if the item is found, record a hit in the buffer; if not found, record a miss. Additionally, during bucket eviction, prefer to evict from the tail first, moving toward the head only if tail is empty or contains items not yet evaluated.

Maintain the 128×16 baseline geometry, ClassicLRU eviction policy, and single-vector bucket structure. The learned bias is purely positional: no additional fields per item, no frequency counters, no decay loops.

## Rationale

Cycles 0001–0007 demonstrate that explicit eviction policies (LFU, FIFO, Epoch-based, Hot/cold partitioning) do not improve hit-rate on Zipfian workloads because the workload is already well-served by ClassicLRU's recency tracking. However, all variants have assumed reactive eviction—responding to accesses after insertion. This hypothesis pursues a proactive strategy: learn from recent history whether the workload is in a high-reuse phase and bias insertion location accordingly.

The insight is that Zipfian workloads exhibit temporal locality: access clusters shift over time. If recent accesses have been mostly hits, the working set is hot and new items are likely to be used; inserting at head maximizes their retention. If recent accesses are misses, the working set may be shifting and new items should occupy lower-priority tail positions.

This follows Path B (orthogonal approaches) from the cross-cycle recommendation. Rather than changing eviction policy or expanding metadata, it uses algorithmic insight (predictive bias) to steer insertion position. The approach requires no metadata expansion (unlike v001, v002, v003) and minimal per-operation cost (a 16-element ring buffer), testing whether learning from history can improve hit-rate without the overhead that plagued prior variants.
