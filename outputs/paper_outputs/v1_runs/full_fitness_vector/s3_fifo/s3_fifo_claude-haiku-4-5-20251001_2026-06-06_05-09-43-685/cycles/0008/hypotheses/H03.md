# H03

Apply occupancy-gated ghost retention to cycle/0006/v001 to scale decay aggressiveness with main-queue occupancy, preserving more warm candidates when space is available.

## Parent

cycle/0006/v001

## Changes

In `src/s3_fifo/mod.rs`, modify the ghost-queue retention policy in `evict_main()` and `evict_small()` to adapt decay thresholds based on main-queue occupancy:

1. Keep the ghost structure as `VecDeque<(K, i8)>` unchanged (from v006/v001).

2. Keep the existing frequency decay logic in `evict_main()` and `evict_small()`:
   - Items decay by 1 frequency level: `ghost_freq = (tail.freq as i8).saturating_sub(1)`
   - This preserves the efficient eviction pipeline v006/v001 established

3. In both `evict_main()` and `evict_small()`, compute the main-queue occupancy ratio and use it to set the ghost-retention threshold:
   ```
   let occupancy_ratio = self.main.len() as f64 / self.main_size as f64;
   let discard_threshold = if occupancy_ratio > 0.8 {
       -1  // High occupancy: aggressive pruning, keep only freq >= -1
   } else if occupancy_ratio > 0.5 {
       -2  // Medium occupancy: balanced retention, keep freq >= -2
   } else {
       -3  // Low occupancy: lenient retention, keep freq >= -3
   };
   ```

4. When pushing to ghost, check the dynamic threshold:
   - Only push if `ghost_freq >= discard_threshold`
   - If pushing: `self.ghost.push_front((tail.key, ghost_freq))`
   - Otherwise: discard the item

5. In `put()`, when a ghost hit is detected, use v006/v001's existing re-admission logic unchanged:
   - Extract the ghost entry and its frequency
   - Compute occupancy-responsive boost: `boost = 2 + (occupancy_ratio * 2.0).floor() as i8`
   - Apply re-admission frequency: `boosted_freq = (ghost_freq + boost).max(0) as u8`
   - Clamp to MAX_FREQ and create entry

6. Keep v006/v001's small-queue occupancy-responsive thresholds, dynamic sizing adjustments, and all other mechanisms intact.

This targets the hypothesis that ghost-queue retention should be adaptive to queue pressure. When the main queue is full (>80% occupancy), eviction pressure is high and ghost space is precious—be aggressive and keep only the hottest items (freq >= -1). When the main queue has capacity (moderate to low occupancy), allocate more ghost space for warm candidates that might be re-accessed. This concentrates ghost-queue resources on valuable candidates during contention peaks while maximizing re-access opportunities during normal load. The occupancy computation happens at eviction time (infrequent), not on every operation, so overhead is minimal. Expected outcome: improved hit-rate by retaining more warm candidates during normal operation while protecting latency during contention, achieving better balance than fixed ghost-retention thresholds.

## Rationale

Cycle 0006/v001 introduced occupancy-responsive promotion thresholds but added per-operation overhead that eroded the latency advantage. The same insight—that queue state should inform policy decisions—can be applied at eviction time with zero additional hot-path cost. By scaling ghost-queue retention aggressively with occupancy, we implement a resource-allocation strategy: when competition for main-queue space is fierce, ghost should hold only proven-hot candidates (freq >= -1); when space is abundant, ghost can afford to hold warmer-but-not-hot candidates (freq >= -3). This prevents ghost from becoming a liability during high contention (wasting space on weak candidates) while maximizing its value as a warm-candidate pool during normal operation. The occupancy threshold is computed only during eviction (infrequent), preserving the latency efficiency v006/v001 demonstrated. Expected to unlock hit-rate improvement toward 0.725+ without incurring new per-operation costs.
