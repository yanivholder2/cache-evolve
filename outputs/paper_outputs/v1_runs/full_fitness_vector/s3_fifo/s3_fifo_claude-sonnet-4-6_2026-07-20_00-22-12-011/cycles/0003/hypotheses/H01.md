# H01

Replace the sequential second-chance scan in `evict_main()` with two-random-choices victim selection to reduce per-op-time to O(1) per eviction call.

## Parent

cycle/0002/v001

## Changes

Add a `rng: u64` field to the `S3Fifo<K, V>` struct. Initialise it in `try_new()` to `(capacity as u64).wrapping_mul(0x9e3779b97f4a7c15).wrapping_add(1)` (guaranteed non-zero). Add a private `fn next_rng(&mut self) -> u64` method that applies one XorShift64 step:

```rust
fn next_rng(&mut self) -> u64 {
    self.rng ^= self.rng << 13;
    self.rng ^= self.rng >> 7;
    self.rng ^= self.rng << 17;
    self.rng
}
```

Replace the entire body of `evict_main()` with the following O(1) implementation:

```rust
fn evict_main(&mut self) {
    let len = self.main.len();
    if len == 0 { return; }
    let a = (self.next_rng() as usize) % len;
    let b = (self.next_rng() as usize) % len;
    // Pick the lower-frequency candidate; tie-break toward higher index (older entry).
    let victim = if self.main_freq[a] <= self.main_freq[b] { a } else { b };
    // Swap victim to the back of both parallel deques, then pop — O(1).
    let last = len - 1;
    self.main.swap(victim, last);
    self.main_freq.swap(victim, last);
    self.main.pop_back();
    self.main_freq.pop_back();
}
```

This unconditionally evicts the lower-frequency of the two sampled entries; there is no frequency-decrement / second-chance cycling. `VecDeque::swap` and `VecDeque::pop_back` are both O(1), so `evict_main()` is now O(1) regardless of how many high-frequency entries sit at the back of the deque.

All other code from `cycle/0002/v001` is preserved without change: the parallel-freq-deque layout, the 1/10 small-queue fraction, the `ghost_set` O(1) membership oracle, and the lazy-deletion tombstone guard in `evict_small()`. The only two structural additions are the `rng: u64` field and the `next_rng()` method.

## Rationale

The cycle-0002 insight named `evict_main()` as the single remaining O(n) hotspot: under a main queue of ~1,843 entries (90 % of capacity 2048), the second-chance loop may traverse the entire deque before finding a zero-frequency victim when the hot set is large. Two-random-choices approximates frequency-aware eviction at constant cost — Redis uses the same technique and retains near-optimal hit rates. Any per-op-time regression from lost second-chance protection is expected to be small because hot-set keys re-accumulate frequency in main through `get()` hits and can be re-promoted via the ghost path if evicted prematurely.
