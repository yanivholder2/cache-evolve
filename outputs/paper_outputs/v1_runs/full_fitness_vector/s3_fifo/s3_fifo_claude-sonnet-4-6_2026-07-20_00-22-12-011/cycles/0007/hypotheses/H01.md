# H01

Pre-sizing `data`, `freq_map`, and `ghost_set` at `2 × capacity` to hold load factors near 50% will reduce hash-collision probe chains on the eviction-hot put path, lowering per-op-time for cycle/0006/v001's 1/80-small-fraction configuration.

## Parent

cycle/0006/v001

## Changes

In `try_new()`, change the two `HashMap::with_capacity(capacity)` calls — one for `data` and one for `freq_map` — to `HashMap::with_capacity(capacity.saturating_mul(2))`. Change the `HashSet::with_capacity(main_size)` call for `ghost_set` to `HashSet::with_capacity(main_size.saturating_mul(2))`. The `ghost` VecDeque cap remains `main_size` unchanged.

Concretely, the five allocation lines in `try_new()` after the size computation should become:

```
small:     VecDeque::with_capacity(small_size)          // unchanged
main:      VecDeque::with_capacity(main_size)           // unchanged
data:      HashMap::with_capacity(capacity.saturating_mul(2))   // was capacity
freq_map:  HashMap::with_capacity(capacity.saturating_mul(2))   // was capacity
ghost:     VecDeque::with_capacity(main_size)           // unchanged
ghost_set: HashSet::with_capacity(main_size.saturating_mul(2))  // was main_size
```

All other logic is preserved exactly as in cycle/0006/v001: the 1/80 small-queue fraction, the `freq > 1` small-queue promotion threshold, the split `data`+`freq_map` layout, and the ghost lazy-deletion pattern (tombstone-on-hit, capacity-guard drain in `evict_small()`).

The `S3Fifo<u64,u64>` struct stack size is unchanged (HashMap/HashSet fields are heap-allocated; only pointer+len+cap live on the struct). Per-entry `Entry<K,V>` footprint is unchanged at 8 bytes.

## Rationale

cycle/0006/v001's per-op-time=100 regression relative to cycle/0005/v001 (per-op-time=0) is attributed to more frequent `evict_small()` calls caused by the tighter 1/80 small-queue. Each `evict_small()` call touches `data`, `freq_map`, and `ghost_set` via hash probes. Rust's default `HashMap` targets a ~87.5% load factor; at capacity=2048 with a 1/80 small queue, the main hashmap runs near full occupancy for most of the trace, maximising collision chains. Halving the load factor to ~43% reduces the expected probe count per lookup, which compounds across the elevated eviction-call rate that the 1/80 fraction induces.
