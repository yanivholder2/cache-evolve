# H03

Raising `MAX_FREQ` from 3 to 4 in `evict_main()`'s second-chance loop improves hit-rate over cycle/0005/v001 while keeping per-op-time lower than cycle/0007/v003's `MAX_FREQ=5`, targeting the unexplored gap between the two cross-cycle winners.

## Parent

cycle/0005/v001

## Changes

Starting from cycle/0005/v001 (which has `MAX_FREQ = 3`, `small_size = capacity/40`, and the two-map structure `data: HashMap<K,V>` + `freq_map: HashMap<K,u8>` + `ghost_set: HashSet<K>`):

1. **Change the single constant** on line 26:
   ```rust
   // Before:
   const MAX_FREQ: u8 = 3;
   // After:
   const MAX_FREQ: u8 = 4;
   ```

2. **No other changes.** All struct fields, allocation sizes, eviction logic, promotion threshold (`freq > 1`), ghost capacity (`main_size`), and `small_size` (`capacity / 40`) remain exactly as in v001.

**Invariants to preserve**: The `repeated_get_clamps_frequency` test asserts that repeated gets do not push freq above `MAX_FREQ`. With `MAX_FREQ = 4`, the clamp is now 4; the test still passes because it only asserts the get returns `Some(10)`, not that freq equals a specific ceiling. The rest of the contract gate is unaffected.

## Rationale

The two cross-cycle winners on opposite ends of the MAX_FREQ spectrum are: cycle/0005/v001 (`MAX_FREQ=3`, hit-rate=0.7292, per-op-time=0) and cycle/0007/v003 (`MAX_FREQ=5`, hit-rate=0.7302, per-op-time=100). The cross-cycle insight notes that raising from 3 to 5 gave a small but real hit-rate gain at the cost of deeper `evict_main()` scans. The value `MAX_FREQ=4` has never been tested; it sits precisely in the unexplored gap. If the per-op-time metric is quantised at 100 ns intervals, `MAX_FREQ=4` may still round to per-op-time=0 (same as v001) while capturing part of the hit-rate uplift from fewer premature evictions of medium-frequency entries. At worst it is a neutral tuning; at best it achieves strictly better fitness than either current winner by combining v001's latency profile with a hit-rate closer to v003's.
