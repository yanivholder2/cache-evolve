# H01

Reducing the small-queue fraction from 1/40 to 1/80 on cycle/0005/v001's dual-HashMap design will further improve hit-rate on Zipfian workloads by shifting more capacity to the main queue, now that the position() scan overhead that caused the cycle/0004 crossover has been eliminated.

## Parent

cycle/0005/v001

## Changes

In `try_new()`, replace the single occurrence of `capacity / 40` with `capacity / 80`.
The expression is:
```
(capacity / 40).max(1).min(capacity - 1)
```
Change it to:
```
(capacity / 80).max(1).min(capacity - 1)
```
All other code — the dual-HashMap layout (`data: HashMap<K,V>` + `freq_map: HashMap<K,u8>`), the lazy ghost tombstoning, the `ghost_set` HashSet, the `evict_main()` unbounded second-chance loop, and the `evict_small()` `freq > 1` promotion threshold — must be preserved exactly as in the parent. Only the small-queue sizing constant changes.

## Rationale

cycle/0005/v001 proved that 1/40 is safe now that `position()` is gone: hit-rate rose to 0.7292 with no latency penalty. The cross-cycle insight explicitly asks whether 1/40-or-smaller remains viable. At 1/80 the small queue holds ≈1.25% of capacity and main holds ≈98.75%, giving the hot Zipfian working set even more residency. On Zipfian workloads one-hit-wonders are rare by definition, so the admission filter can be made very tight without materially worsening cold-miss handling. The claim is falsified if hit-rate regresses below 0.7292 or if latency increases.
