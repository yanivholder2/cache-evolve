# H03

Decrementing frequency by 2 instead of 1 in `evict_main()`'s second-chance re-admit path will shorten the scan length for moderately-warm entries and reduce get latency without the hit-rate cost of eliminating second-chance altogether.

## Parent

cycle/0003/v002

## Changes

In `evict_main()`, change the re-admission frequency from `freq - 1` to `freq.saturating_sub(2)`. The `if freq > 0` guard remains unchanged, so any entry with freq > 0 still receives at least one second-chance re-admission.

Before:
```rust
fn evict_main(&mut self) {
    while let Some(tail) = self.main.pop_back() {
        let freq = self.main_freq.pop_back().unwrap_or(0);
        if freq > 0 {
            self.main.push_front(tail);
            self.main_freq.push_front(freq - 1);
        } else {
            break;
        }
    }
}
```

After:
```rust
fn evict_main(&mut self) {
    while let Some(tail) = self.main.pop_back() {
        let freq = self.main_freq.pop_back().unwrap_or(0);
        if freq > 0 {
            self.main.push_front(tail);
            self.main_freq.push_front(freq.saturating_sub(2));
        } else {
            break;
        }
    }
}
```

No other changes. All struct fields, `try_new`, `put`, `get`, and `evict_small` are identical to `cycle/0003/v002`.

**Effect on re-admission counts** (with `MAX_FREQ = 3`):

| Initial freq | Step=1 passes to eviction | Step=2 passes to eviction |
|---|---|---|
| 1 | 2 (1→0→evict) | 2 (1→0→evict, same) |
| 2 | 3 (2→1→0→evict) | 2 (2→0→evict) |
| 3 | 4 (3→2→1→0→evict) | 3 (3→1→0→evict) |

Entries at freq=1 behave identically to step=1. Entries at freq=2 lose one protection round. Entries at freq=3 lose one protection round. The second-chance policy is preserved — no entry is ever evicted at first encounter without at least one re-admission attempt — but the worst-case scan length for a fully-warm queue is cut from 4× capacity to 3× capacity.

The existing unit test `main_eviction_uses_frequency_second_chance` checks that an entry with freq=1 survives and an entry with freq=0 is evicted immediately. Both assertions remain valid under step=2. Update the test comment to note that freq=2 entries now behave like freq=1 entries under step=2.

## Rationale

cycle/0003/v001's two-random-choices result confirmed that reducing `evict_main()` scan length yields latency gains, but that pure O(1) random victim selection sacrifices frequency-drain protection, causing material hit-rate regression. Frequency step=2 is a middle path: the scan loop terminates faster (freq drains to zero in fewer passes) while preserving the invariant that hot entries (freq=3) still receive multiple protection rounds. Unlike the bounded-cap approach (H01), which caps iteration count, step=2 caps per-entry survival rounds — the two mechanisms are complementary and target different sources of scan cost.
