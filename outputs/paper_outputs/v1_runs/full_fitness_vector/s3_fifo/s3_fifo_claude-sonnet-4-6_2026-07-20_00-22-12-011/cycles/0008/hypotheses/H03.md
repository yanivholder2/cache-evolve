# H03

Batch-draining the small queue to 75% of its capacity on each overflow event, instead of evicting one entry at a time, will reduce the fraction of put() calls that incur any eviction work and lower put-path p50 latency in cycle/0005/v001.

## Parent

cycle/0005/v001

## Changes

In `src/s3_fifo/mod.rs`, inside `put()`, replace the single-eviction overflow guard:

```rust
// Normal admission into the small queue.
if self.small.len() >= self.small_size {
    self.evict_small();
}
```

with a batch-drain that descends to 75% of `small_size` before admitting the new entry:

```rust
// Normal admission into the small queue.
// Batch-drain to 75% capacity on overflow to amortise eviction cost:
// most puts skip the eviction branch entirely.
if self.small.len() >= self.small_size {
    let target = self.small_size * 3 / 4; // 75% of small_size (rounds down)
    while self.small.len() > target {
        self.evict_small();
    }
}
```

The `push_front` into small and all subsequent code in `put()` are unchanged.

**Mechanics**: at `small_size = capacity / 40` (≈ 51 entries for capacity=2048) the drain target is ≈ 38. When small fills to 51, one put drains 13 entries in a burst, leaving 38. The next 12 puts add entries without touching `evict_small()` at all. Thirteen evictions happen per 13 puts — the total eviction throughput is identical to the current design — but they are concentrated in one put rather than spread one-per-put. P50 put latency falls because 12 out of 13 steady-state puts see no eviction cost; only 1 in 13 pays the combined cost of 13 evictions.

**Edge case — small_size = 1** (capacity = 4 in unit tests): `target = 1 * 3 / 4 = 0`. The while loop drains until `small.len() <= 0`, which is exactly one eviction (since small has exactly 1 entry when it fires). This degenerates cleanly to the original one-at-a-time behaviour. No changes to unit tests are needed; `capacity_bound_never_exceeded` and all other tests pass unchanged.

**Hit-rate invariant**: evictions are still FIFO (oldest tail entries evicted first) and the same entries are evicted over the same sequence of puts — they are just batched differently. The promotion and ghosting decisions are unchanged. Hit-rate should be identical to the parent variant.

## Rationale

Cycle 0007 identified `evict_small()` invocation frequency as the binding per-op-time cost driver (from v001's hash-pre-sizing experiment). Batching addresses this directly without changing queue sizes, eviction policy, or data-structure layout. The cost is that the 1-in-13 "drain put" is proportionally slower, but p50 is what the fitness summary measures, and 12/13 puts are now eviction-free. The implementation is a two-line change confined to `put()` and introduces no new data structures.
