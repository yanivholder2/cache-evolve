# H02

Maintaining a compact 256-entry frequency counter array in `LruCache` and using it to select the least-frequent among the four oldest probationary candidates for eviction improves hit-rate by preferentially retaining warm items over cold arrivals within the probationary queue.

## Parent

cycle/0007/v002

## Changes

This hypothesis tests frequency-biased eviction **ordering within the probationary queue** — not as a graduation gate (which has been conclusively closed) and not as a filter on admission. The mechanism only changes *which* probationary item is evicted when the probationary queue overflows; it does not change the protected-queue policy, the quota, or the promotion path.

**Implementation steps:**

1. Add a field `freq: [u8; 256]` to the `LruCache<K, V>` struct. Initialise it to `[0u8; 256]` in `LruCache::new()`. This adds 256 bytes to the `LruCache` struct but does not affect `Node` size (metadata-size fitness dimension is unchanged).

2. Define a cheap local frequency-index function that maps a key to one of 256 buckets without invoking the full `HashMap` hasher. For `K: Hash`, apply a single multiply-shift step on the key's raw bits:

   ```rust
   fn freq_bucket<K: std::hash::Hash>(key: &K) -> usize {
       let mut h = std::collections::hash_map::DefaultHasher::new();
       key.hash(&mut h);
       let bits = std::hash::Hasher::finish(&h);
       (bits.wrapping_mul(0x9e3779b97f4a7c15) >> 56) as usize
   }
   ```

   Alternatively, if the key type is known to be `u64`, use `((key.wrapping_mul(0x9e3779b97f4a7c15)) >> 56) as usize` directly for zero overhead.

3. **Increment counter on every access**: in `get()`, after confirming a cache hit (whether probationary or protected), increment `self.freq[freq_bucket(&key)]`, saturating at 255.

4. **Initialise counter on new insertion**: in `put()` for a cache-miss (new key), set `self.freq[freq_bucket(&key)] = 1` before linking the new node into the probationary queue.

5. **Frequency-biased eviction**: when the probationary queue must evict (probationary is full and a new item is being inserted), instead of always evicting the probationary head (oldest/LRU item), scan the **4 oldest** probationary nodes (the head and the next 3 nodes following `next` pointers from the LRU end). Among these 4 candidates, evict the one whose `freq[freq_bucket(&node.key)]` is smallest. Break ties by selecting the oldest (head-most) candidate. Unlink and evict that node, then insert the new item at the probationary MRU tail as normal.

   If probationary has fewer than 4 items, scan only what is available.

6. Keep `prob_cap = (capacity / 8).max(1)`, the Node layout (16 bytes), the protected-queue LRU order, the promotion/demotion logic, and all other paths exactly as in cycle/0007/v002.

**Invariants to preserve**: the probationary and protected queue doubly-linked list structure must remain consistent after evicting a non-head candidate (i.e., properly unlink the chosen node by updating its predecessor's and successor's `links` fields). The frequency counter array is a best-effort heuristic; counter aliasing (multiple keys mapping to the same bucket) is acceptable — the mechanism degrades gracefully to LRU order when all candidates share the same counter value.

## Rationale

The cross-cycle open questions explicitly identify "frequency sketch as within-probationary eviction ordering" as untested. Previous sketch-based attempts (cycle 0007 CountMin sketch as a graduation gate) failed because workload-a does not generate sufficient repeat accesses within a single window; however, using the sketch for *eviction ordering* rather than *admission filtering* is structurally different: every item in the probationary queue was already admitted (no gate), and the sketch only biases which of a small fixed-size candidate set is selected for removal. The bounded 4-item scan keeps the overhead constant and avoids the full-queue traversal cost that defeated earlier sweep-based approaches.
