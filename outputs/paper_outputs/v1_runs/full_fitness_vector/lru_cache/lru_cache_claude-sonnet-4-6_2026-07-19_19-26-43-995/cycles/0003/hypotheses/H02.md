# H02

Narrowing the probationary queue cap from `capacity / 4` to `capacity / 8` will increase available space in the protected LRU queue and raise hit rate above 0.7202 on Zipfian traces.

## Parent

cycle/0002/v001

## Changes

In `try_new()`, change the single line that sets `prob_cap`:

```rust
// Before:
let prob_cap = (capacity / 4).max(1);

// After:
let prob_cap = (capacity / 8).max(1);
```

No other code changes. All queue-management logic, eviction policy, and PROT_BIT encoding remain identical.

Rationale for the direction: the workload-a trace shows a Zipfian access pattern where a small hot set accounts for the majority of accesses. With `capacity / 4` as the probationary quota, 25% of slots are reserved for admission filtering while 75% can be protected. Shrinking admission to 12.5% gives the protected LRU queue 87.5% of capacity, reducing the rate at which hot items are demoted from protected back to probationary when the protected budget overflows. The demotion path (`if self.prot_len > prot_cap` in `promote()`) fires more often under the current 75% protected cap than under an 87.5% cap — reducing those demotions should keep more of the working set in protected and improve hit rate.

The `.max(1)` floor is preserved so that capacity=1 and capacity=2 still function correctly (with `capacity/8` = 0 otherwise).

All existing unit tests must pass; they exercise correctness invariants, not the specific quota ratio.
