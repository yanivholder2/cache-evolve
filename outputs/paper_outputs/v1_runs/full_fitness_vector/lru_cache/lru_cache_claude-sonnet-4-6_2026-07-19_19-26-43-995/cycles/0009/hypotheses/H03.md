# H03

Replacing the default SipHash hasher with an inline FNV-1a hasher, combined with `prob_cap = capacity/16`, will reduce per-map-lookup latency enough to keep per-op-time at 0 while achieving the 93.75% hit-rate gain.

## Parent

cycle/0006/v001

## Changes

Three modifications relative to cycle/0006/v001:

**1. Change the probationary capacity in `try_new()`:**

```rust
// Old:
let prob_cap = (capacity / 8).max(1);

// New:
let prob_cap = (capacity / 16).max(1);
```

**2. Add a custom FNV-1a hasher and builder before the `impl<K, V> LruCache<K, V>` block (after the `use` statements):**

```rust
/// FNV-1a hasher: processes 8 xor+multiply steps for an 8-byte i64 key,
/// avoiding SipHash-1-3's more expensive mixing rounds.
struct FnvHasher(u64);

impl std::hash::Hasher for FnvHasher {
    #[inline(always)]
    fn finish(&self) -> u64 { self.0 }
    #[inline(always)]
    fn write(&mut self, bytes: &[u8]) {
        for &b in bytes {
            self.0 ^= b as u64;
            self.0 = self.0.wrapping_mul(0x00000100000001b3);
        }
    }
}

#[derive(Clone, Default)]
struct FnvBuildHasher;

impl std::hash::BuildHasher for FnvBuildHasher {
    type Hasher = FnvHasher;
    #[inline(always)]
    fn build_hasher(&self) -> FnvHasher { FnvHasher(0xcbf29ce484222325) }
}
```

**3. Change the `map` field type and its constructor throughout:**

In the `LruCache<K, V>` struct definition, change:
```rust
map: HashMap<K, usize>,
```
to:
```rust
map: HashMap<K, usize, FnvBuildHasher>,
```

In `try_new()`, change:
```rust
map: HashMap::with_capacity(capacity),
```
to:
```rust
map: HashMap::with_capacity_and_hasher(capacity, FnvBuildHasher),
```

No other changes. All map operations (`get`, `remove`, `insert`) remain identical; only the hashing backend changes. The `K: Hash` bound is unchanged and equality semantics are unaffected (FNV-1a is deterministic and consistent).

**Mechanism:** The benchmark uses `i64` keys (8 bytes). For a `get()` call, the map performs one hash computation; for a `put()` with eviction, the map performs three (one `get`, one `remove` of the evicted key, one `insert`). SipHash-1-3 applies two full 64-bit mixing rounds per 8-byte input block; FNV-1a applies 8 sequential xor+multiply steps. On modern x86-64, FNV-1a for an 8-byte input is ~3-4 instructions vs. SipHash's ~20+ instructions — a savings of ~10-20 ns per map lookup. With the 93.75% quota adding ~30-50 ns of average demotion overhead per operation (as confirmed in cycle 0008), a 10-20 ns per-lookup saving across 1-3 lookups per operation could offset enough of the regression to keep p50 below the 100 ns measurement floor.

## Rationale

The cross-cycle insights list "hash-map lookup overhead reduction" as one of the few unexplored structural axes. This hypothesis applies it directly to the only quota setting known to improve hit-rate (93.75%) and tests whether the structural speedup can make that setting viable without policy changes. It is distinct from H01 (which probes an intermediate quota) and H02 (which amortises demotion events) because it targets the hash computation path rather than the quota level or demotion scheduling. If it works, the FNV hasher can also be carried forward to other parent variants.
