# H03

Replace bounded-window sequential scanning with random candidate sampling during eviction to reduce put p99 latency.

## Parent

baseline

## Changes

Implement an alternative eviction strategy that eliminates linear scanning:

1. Add a single `freq` counter field to each Node to track per-item access frequency (incremented on every access in get and put).
2. During eviction in `put()`, instead of scanning the first min(capacity/4, 256) nodes sequentially, randomly sample exactly 32 candidate nodes from the arena.
3. Among the 32 sampled candidates, select the node with the lowest frequency value. If there is a tie, prefer the earliest sampled candidate (deterministic).
4. Evict the selected low-frequency candidate and insert the new key in the same slot.
5. Maintain the frequency counters with simple increment-on-access logic; no bucketing structures, no frequency decay, no bounded-window linked-list traversal needed.

This approach reduces worst-case eviction latency by eliminating scan loops entirely: sampling 32 candidates is O(1) with respect to cache capacity, compared to O(min(capacity/4)) for sequential scan. The trade-off is slightly less precise frequency tracking (sampling may miss very-low-frequency items), but on Zipfian workloads where frequency is highly skewed, random sampling should select low-frequency candidates with high probability while dramatically improving tail latency.
