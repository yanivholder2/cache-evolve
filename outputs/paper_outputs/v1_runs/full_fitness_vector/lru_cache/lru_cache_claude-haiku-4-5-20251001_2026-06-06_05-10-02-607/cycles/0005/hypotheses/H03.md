# H03

Apply deferred frequency promotions conditionally based on cache saturation to avoid put latency penalty on underutilized caches.

## Parent

cycle/0004/v002

## Changes

Cycle 0004 V002 achieved 23% get p99 improvement but at the cost of 26-56% put regression. This trade-off may only be justified when the cache is under sustained load (high saturation) where the deferral actually reduces contention. On underutilized caches with balanced read/write patterns, the deferral queue overhead may create cost without corresponding benefit. Implement saturation-conditional deferral:

1. Add a `deferral_enabled` flag to LruCache, initialized to false.
2. Monitor saturation level (nodes.len() / capacity) during put() operations.
3. When saturation ≥ 80% (indicating high load where deferred work batching would reduce contention), set `deferral_enabled = true` and activate the deferred-promotion queue from v002.
4. When saturation drops below 60% (indicating low load), set `deferral_enabled = false` and immediately flush any pending promotions, then revert to immediate frequency updates on every access.
5. During mode transitions, flush pending promotions before switching modes.
6. Keep the bucket indexing, frequency tracking, and eviction logic from v002 unchanged; only toggle whether promotions are deferred or immediate.

This hybrid approach preserves v002's get p99 improvements during saturation-heavy periods when deferral prevents batching problems, while avoiding the put penalty during light-load phases where immediate updates are cheaper than maintaining a queue.

## Rationale

The cycle 0004 insight notes that "V002 is a viable optimization for read-dominated workloads where get p99 latency is the priority metric." But it also observes the workload is underutilized and saturation thresholds never trigger. The cross-cycle patterns show that "Workload-aware adaptive modes beat uniform strategies" (Cycle 0003 V003's success). By making deferral conditional on saturation, we leverage the deferred-promotion optimization when it actually helps (high saturation + batching) while avoiding its overhead when it hurts (light load + queue management cost).
