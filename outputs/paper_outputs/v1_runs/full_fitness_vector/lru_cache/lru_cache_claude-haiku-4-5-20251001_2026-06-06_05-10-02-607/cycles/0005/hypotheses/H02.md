# H02

Reduce put p99 latency spike from deferred promotions by spreading queue flushing across both get and put operations.

## Parent

cycle/0004/v002

## Changes

Cycle 0004 V002 improved get p99 by 23% via deferring frequency promotions from get to put, but this caused put p99 to regress 56% (190→297 ns) because all accumulated promotions flush at once during a single put operation. Implement incremental queue draining to amortize the deferred work:

1. Maintain the `pending_promotions` queue as currently designed in v002.
2. In get(), after processing the current node access, check if the queue size exceeds a threshold (e.g., 8 items).
3. If the threshold is exceeded, drain and process the first K items (e.g., 4) from the queue before returning from get(). This applies the frequency bucket updates for a small batch of pending accesses.
4. In put(), preserve v002's existing flush-before-eviction logic but reduce the expected queue size from N accumulated gets to ~(N % K) due to incremental draining during gets.
5. Adjust thresholds Q (drain-trigger) and K (batch-drain-size) empirically to find the optimal balance (suggested starting point: Q=8, K=4).

This spreads the bucket manipulation overhead across both get and put operations, reducing the peak work per operation during put() while maintaining most of get's latency improvement by keeping the common-case get() path lightweight (only triggering drain when queue is substantial).

## Rationale

The cross-cycle insights identify that "Deferral shifts cost between operations rather than eliminating it" and open the question: "Is there a buffering or batching scheme that improves both?" V002's current all-at-once flush is fundamentally a batching problem. Incremental draining is a standard amortization technique: instead of executing N updates at one point, spread them across multiple operations proportionally. This reduces the maximum latency spike while distributing the work load-proportionally, addressing the operation-shifting trade-off.
