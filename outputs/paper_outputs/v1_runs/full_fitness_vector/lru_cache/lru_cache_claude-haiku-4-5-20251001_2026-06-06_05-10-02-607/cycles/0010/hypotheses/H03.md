# H03

Implement opportunistic batch buffering of hot-path frequency updates, flushing accumulated promotions to bucket structures only when buffer depth exceeds a low threshold, reducing per-operation bucket-maintenance cost without per-operation conditional checks.

## Parent

cycle/0002/v002

## Changes

Introduce a fixed-size (16-entry) promotion buffer local to the cache structure that accumulates node indices of recently accessed items. On hot-path get(), append the accessed node index to the buffer without bucket-update cost (one vector push). On put() or when the buffer reaches half-full (8 entries), drain the buffer by updating each buffered node's bucket pointers in batch, then clear the buffer. This preserves the O(1) eviction-time bucket scan (bucket structures always accurate) while deferring the per-operation bucket pointer manipulation that Cycle 0009 V002 showed is expensive on the get path. Unlike Cycles 0005–0008 deferred-promotion strategies that required per-operation checks (introducing overhead), this uses deterministic threshold-based draining to avoid conditional logic on the hot path.

## Rationale

Cycles 0007–0009 demonstrated that per-operation adaptive logic (saturation checks, condition branches) introduces overhead that negates benefits on light-load workloads. However, Cycle 0007 V001's batched queue-flush showed that algorithmic batching (deterministic draining) can achieve simultaneous improvements in both get and put p99. This hypothesis applies that insight to frequency bucket updates: batch the updates that are necessary for correctness, but execute the batch deterministically and infrequently so hot-path overhead remains minimal. The fixed buffer size ensures no unbounded memory growth, and the threshold (8 items) ensures draining occurs frequently enough to maintain bucket accuracy.
