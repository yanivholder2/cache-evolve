# H02

Narrowing the LruCache control fields to u32 and eliminating struct padding shrinks the cache footprint and lowers put per-op-time, testing the repeatedly observed footprint-to-p50 coupling.

## Parent

cycle/0006/v003

## Changes

Directly probe the standing open question from the cycle-0008 and
cross-cycle insights: "Does growing the `LruCache` struct itself carry a
real latency tax worth treating as a constraint, given how consistently
footprint growth alone moved put p50 even when put was byte-identical?"
Run the experiment in the cheap direction — *shrink* the struct and see
if put p50 drops for free.

Concrete diff against the parent's `src/lru_cache/mod.rs`, all within the
`LruCache<K, V>` struct and the functions that touch its scalar fields:

- Change `prot_len`, `prot_cap`, and `capacity` from `usize` to `u32`.
  The four index fields (`prot_head`, `prot_tail`, `prob_head`,
  `prob_tail`) are already `u32`; grouping all seven as `u32` lets the
  scalar control block pack to 28 bytes with no interior padding.
- In `try_new`, compute `prot_cap` in `usize` as today, then store it
  (and `capacity`) via `as u32`.
- Update the few comparison/bookkeeping sites to keep casts off the
  hottest path: in `put()` the new-key branch becomes
  `self.nodes.len() >= self.capacity as usize` (one widening per insert);
  `prot_len`/`prot_cap` increment and the `prot_len > prot_cap` overflow
  check stay in `u32` arithmetic and only the comparison widens. Crucially
  do **not** introduce any cast into the protected-hit fast path in
  `get()`, which returns before reading `prot_cap`.

Keep behavior byte-for-byte identical: same SLRU policy, same 7/8
geometry, same `FastHasher`, same victim selection, same demotion. `Node`
is untouched, so the scored metadata-size stays 24. The only observable
change should be a smaller `size_of::<LruCache<u64,u64>>()` and,
hypothesis under test, a lower put p50.

## Rationale (optional)

Footprint growth repeatedly perturbed put p50 across cycles even with
identical code, so the coupling is empirically real; if it is causal and
symmetric, trimming the control struct is a free latency win. The
cross-cycle warning that "per-access width casts tax latency" is exactly
why the casts are confined to the insert path and kept out of the get
fast path — the experiment measures the net.
