# H02

Replace the `remove(position)+push` reorder in `get_from_position` with a single in-place `rotate_left(1)`, lowering per-op-time on the get hit path with byte-identical ordering.

## Parent

cycle/0007/v002

## Changes

In `src/associative_cache/associative_cache_bucket.rs`, inside
`get_from_position`, the current promotion/MRU-move performs
`let item = self.items.remove(position); self.items.push(item);`. This shifts
`[position+1, len)` left by one and then re-appends, and `push` additionally
re-checks capacity. Replace those two lines with a single rotation of the
suffix slice: `self.items[position..].rotate_left(1);` then return
`self.items.last()`. Rotating `[position..len)` left by one moves the element
at `position` to the back and slides the rest down by one — producing exactly
the same final vector as remove+push, in one contiguous memmove with no length
change and no capacity check.

Keep everything else intact: the H03 MRU-protected fast-path early return
(`position == len - 1 && lfu_counter >= 1`) must still short-circuit first, the
`lfu_counter == 0 -> 1` promotion plus `protected_count += 1` bookkeeping must
run before the rotate exactly as today, and the prefix/suffix invariant is
unchanged because the moved item lands at the protected MRU back as before.

## Rationale (optional)

This is a behavior-neutral, hit-rate-neutral cost rewrite in the same spirit as
the parent's O(1) eviction rewrite — it removes the redundant `push`
capacity/realloc check and the separate element re-insertion, targeting the
`get` p50 (69ns baseline) that the prior cost-side wins kept tying on.
