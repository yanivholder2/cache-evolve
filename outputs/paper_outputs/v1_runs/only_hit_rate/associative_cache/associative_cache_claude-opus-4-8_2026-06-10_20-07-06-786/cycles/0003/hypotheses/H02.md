# H02

Evict the oldest un-promoted probationary item instead of the newest, giving freshly admitted keys a full pass through the bucket to earn promotion and raising hit-rate.

## Parent

cycle/0002/v003

## Changes

Modify `eviction_candidate_index` in v003's segmented bucket (`src/associative_cache/associative_cache_bucket.rs`).

v003 admits new keys at the probationary front via `self.items.insert(0, item)`, so index 0 is the **newest** resident and higher indices are older. Its current `eviction_candidate_index` scans forward from index 0 and returns the first item with `lfu_counter == 0` — i.e. it evicts the *newest* probationary key, churning the front while older un-promoted keys linger. This denies a just-admitted rising key any time to register its second hit.

Change the probationary scan to evict the **oldest** un-promoted item: iterate the items in reverse (or scan forward but keep the last match) and return the highest index whose `lfu_counter == 0`. Keep the existing fallback unchanged: when every resident is protected (`lfu_counter >= 1`), evict the protected LRU end at index 0. Leave `put` (front admission) and `get_from_position` (promote-on-second-hit, move-to-back) exactly as in v003.

This converts probation from a front-LIFO into a FIFO queue: a new key now survives until it is the oldest un-promoted entry, getting a full lap of accesses to prove reuse before it becomes the victim. Preserve capacity invariants, the binary promote flag semantics, and the pristine policy enum / JNI mapping.

## Rationale (optional)

v003's open question is probation sizing/aging. Evicting the newest probationary key structurally starves rising keys of promotion opportunity; FIFO probation is the canonical fix and a clean, isolated test of whether that starvation is costing hit-rate.
