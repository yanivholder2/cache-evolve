# H02

Replacing the O(bucket_size) reverse scan in `eviction_candidate_index` with an O(1) lookup backed by a maintained protected-item count cuts per-op-time on the winner's wider buckets while leaving hit-rate exactly unchanged.

## Parent

cycle/0006/v001

## Changes

The parent's segmented bucket maintains a structural invariant that lets us
replace the linear scan with arithmetic: counter-0 (probationary) items always
occupy a contiguous **prefix** `[0, k)` and counter-1 (protected) items a
contiguous **suffix** `[k, len)`. This holds because new keys insert at index 0
(extending the zero-prefix), promotions `remove`+`push` the item to the back
(end of the protected suffix), protected hits stay in the suffix, and eviction
removes from the prefix end. Therefore the oldest probationary index is exactly
`k - 1`, and `k == 0` is the all-protected case.

In `src/associative_cache/associative_cache_bucket.rs`:

1. Add a `protected_count: usize` field to `AssociativeCacheBucket`, initialised
   to `0` in `new`.
2. Maintain it at every mutation site:
   - `put` of a brand-new key (insert at index 0, counter 0): no change.
   - `get_from_position`: when it promotes an item (`lfu_counter == 0` → set to
     `1`), increment `protected_count`. The MRU-protected no-op fast path and
     protected-on-protected hits leave it unchanged.
   - Eviction of a protected item: decrement `protected_count`. Since protected
     eviction happens only in the all-protected fallback, override `evict_item`
     (or the removal path) so that when the removed item's `lfu_counter >= 1`,
     `protected_count` is decremented; probationary evictions leave it unchanged.
3. Rewrite `eviction_candidate_index` to return, without scanning:
   `if self.items.is_empty() { None } else if self.protected_count == self.items.len() { Some(0) } else { Some(self.items.len() - self.protected_count - 1) }`.

This is provably behaviour-identical to the parent's reverse scan given the
prefix/suffix invariant, so hit-rate is unchanged; the win is purely the removed
per-eviction O(bucket_size) loop, which the parent's wider buckets made costlier.

## Rationale

The winner traded per-op-time (baseline still holds 69ns) for hit-rate via wider
buckets. This reclaims the cost regression on a real fitness dimension without
risking the hit-rate gain — a hit-rate-neutral, strictly-dominating cost win.
