# H03

Increase bucket size by 50% and decrease bucket count by 50% to reduce hash collision probability and raise hit rate while maintaining total capacity.

## Parent

baseline

## Changes

Modify BaselineGeometry::layout() to return (num_buckets / 2, bucket_size * 2) instead of the harness-provided split. For the baseline configuration (128 buckets × 16 items), this yields 64 buckets × 32 items, preserving the total capacity of 2048 items.

The rationale is that fewer buckets reduce the probability of hash collisions for the same key distribution, while wider buckets better absorb collision overflow without triggering eviction. Specifically:
- Wider buckets create more "breathing room" for keys that hash to the same bucket, allowing items to coexist longer before eviction is necessary.
- Fewer buckets reduce the chance that unrelated keys collide in the first place.

The trade-off is a small increase in per-bucket scanning time (linear scan through larger vectors) and potentially higher memory load per bucket, but the hit-rate gain from lower collision pressure should outweigh this cost.

## Rationale

The baseline uses a narrow bucket layout (128 buckets, 16 items each). This extreme width exacerbates hash collision impact. By rebalancing toward fewer, wider buckets, we shift from a collision-dominated regime to one where most items can coexist in their primary bucket without triggering eviction.
