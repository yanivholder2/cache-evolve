# H01

Reducing the bucket count from 128 to 32 (with proportionally wider buckets of 64 slots each) preserves total capacity at 2048 while expanding the per-set LRU window, which should increase hit rate on the LIRS workload-a trace.

## Parent

baseline

## Changes

In `src/shared/geometry.rs`, modify `BaselineGeometry::for_settings` so that the
constructed geometry divides `settings.num_of_buckets` by 4 and multiplies
`settings.bucket_size` by 4:

```rust
pub fn for_settings(settings: &AssociativeCacheSettings) -> Self {
    let factor = 4;
    BaselineGeometry {
        num_of_buckets: (settings.num_of_buckets / factor).max(1),
        bucket_size: settings.bucket_size * factor,
    }
}
```

With the evaluated configuration (128 buckets × 16 slots = 2048 total capacity) this
produces 32 buckets × 64 slots = 2048 — total capacity is conserved exactly. The
`layout()` method body does not change; it continues to return
`(self.num_of_buckets, self.bucket_size)` unchanged.

Rationale for the choice of factor 4: the baseline bucket width of 16 is narrow
relative to any hot working-set cluster that might exceed 16 items. Widening to 64
gives the LRU eviction policy a much larger pool of candidates before it is forced
to evict a still-relevant item. Factors smaller than 4 (e.g., 2) produce a modest
width of 32, which may still be insufficient; a factor of 8 would push to 16 buckets
which could increase bucket-scan cost during `get_position` linearly to 128
iterations. Factor 4 is the balanced midpoint.

No changes to `src/shared/eviction_policy.rs`,
`src/associative_cache/associative_cache_bucket.rs`, or any other file.
