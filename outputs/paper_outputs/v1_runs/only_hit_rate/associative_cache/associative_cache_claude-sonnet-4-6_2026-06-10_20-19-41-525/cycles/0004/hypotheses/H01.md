# H01

Adding a counter-decay pass to the cold-first eviction path — decrementing all item counters by 1 when no cold candidates exist at eviction time — will improve hit-rate over cycle/0003/v001 by preventing warm-lock in steady state.

## Parent

cycle/0003/v001

## Changes

Override the default `evict_item()` method directly on `AssociativeCacheBucket` in
`src/associative_cache/associative_cache_bucket.rs`. All other files from v001 are
preserved without change (`eviction_policy.rs` keeps cold-first ClassicLRU with
counter increment; `geometry.rs` keeps factor-4 wide-bucket layout; `put()` keeps
mid-point insertion).

The override logic in `evict_item`:

1. Scan `self.items` for the first item where `lfu_counter == 0`. If found at index
   `i`, call `self.remove_at(i)` and return `Some(evicted)`. This is identical to the
   current cold-first path.

2. If the scan finds no cold item (all `lfu_counter >= 1`, i.e., warm-lock): iterate
   over `self.get_items_mut()` and apply `item.lfu_counter -= 1` to every item (floor
   already guaranteed because all counters are ≥ 1, so no underflow). Then call
   `self.remove_at(0)` to evict the LRU front (now cold or near-cold after decay) and
   return `Some(evicted)`.

The decay step is a one-shot pass triggered only when no cold candidate exists, so it
fires rarely in a healthy cache but creates a self-correcting mechanism as the cache
warms up. The invariant that `evict_item` returns `Some` when items are non-empty is
preserved.

## Rationale

cycle/0003/v001 showed that cold-first + mid-point + wide-bucket is the strongest
configuration found so far. The open question from the cross-cycle insights is whether
cold pool exhaustion degrades hit-rate over a long trace as all items accumulate
counters ≥ 1. This change tests whether periodic forced decay of the warm pool, applied
only when the cold pool runs dry, can maintain the cold-first eviction advantage in
steady state without regressing the early-trace behaviour.
