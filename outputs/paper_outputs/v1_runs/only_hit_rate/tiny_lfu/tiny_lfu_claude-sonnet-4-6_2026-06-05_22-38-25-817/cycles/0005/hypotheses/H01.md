# H01

Grafting a PROMO_THRESHOLD gate with `was_protected` bypass onto the k=4 victim-scan SLRU reduces protected-segment churn and improves hit rate.

## Parent

cycle/0004/v003

## Changes

Starting from the cycle/0004/v003 overlay (SLRU 90/10, k=4 probationary victim scan, unconditional promotion in `get()`):

1. Add `const PROMO_THRESHOLD: u32 = 8;` near the other constants at the top of `mod.rs`.

2. Add a `was_protected: bool` field to `Node<K, V>`, defaulting to `false`:
   ```rust
   struct Node<K, V> {
       key: K,
       value: V,
       prev: Option<usize>,
       next: Option<usize>,
       in_protected: bool,
       was_protected: bool,   // ← new field
   }
   ```

3. In `get()`, replace the unconditional probationary→protected promotion block:
   ```rust
   // Promote probationary → protected unconditionally on access.
   self.prob_unlink(idx);
   self.probationary_len -= 1;
   self.prot_push_back(idx);
   self.protected_len += 1;
   self.maybe_demote_from_protected();
   ```
   with a frequency-gated version:
   ```rust
   let freq = self.sketch.estimate(&self.nodes[idx].key);
   if freq >= PROMO_THRESHOLD || self.nodes[idx].was_protected {
       self.nodes[idx].was_protected = false;
       self.prob_unlink(idx);
       self.probationary_len -= 1;
       self.prot_push_back(idx);
       self.protected_len += 1;
       self.maybe_demote_from_protected();
   } else {
       // Below threshold and not a protected overflow-demotee:
       // refresh MRU position within probationary only.
       self.prob_unlink(idx);
       self.prob_push_back(idx);
   }
   ```

4. In `maybe_demote_from_protected()`, set `was_protected = true` on the demoted node just before calling `prob_push_back(h)`:
   ```rust
   self.prot_unlink(h);
   self.protected_len -= 1;
   self.nodes[h].was_protected = true;   // ← new line
   self.prob_push_back(h);
   self.probationary_len += 1;
   ```

5. When constructing a new `Node` (arena-not-full path in `put()`), initialise `was_protected: false` (already the struct default, so just add the field in the literal).

6. All k=4 victim-scan logic in `put()`, the 90/10 SLRU split, and the admission gate (`incoming_freq > victim_freq`) remain identical to v003.

## Rationale

v003 won with unconditional promotion and a k=4 victim scan; cycle 0003 v003 won with PROMO_THRESHOLD+`was_protected` and no victim scan. The two positive axes have never been tested in combination. This hypothesis directly tests the open question from cycle 0004: does gating promotion reduce probationary churn enough to compound the victim-scan gain, or do the two mechanisms interfere on this trace?
