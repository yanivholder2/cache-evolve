# H03

Adding SLRU 90/10 segmentation plus frequency-sampled victim selection (k=4 scan of the probationary LRU tail) to the baseline will improve hit rate by evicting the least-valuable probationary item rather than always the least-recently-used one.

## Parent

baseline

## Changes

This hypothesis rebuilds the baseline's single-LRU cache into a two-segment SLRU with a frequency-sampled eviction path. No PROMO_THRESHOLD, no `was_protected` flag — those belong to v003's lineage; this is a clean experiment on the eviction lever alone.

### 1. Node struct — add `in_protected` field

```rust
struct Node<K, V> {
    key: K,
    value: V,
    prev: Option<usize>,
    next: Option<usize>,
    in_protected: bool,  // NEW
}
```

### 2. Cache struct — replace single head/tail with two segments

Remove `head` and `tail`. Add:
```rust
protected_capacity: usize,
probationary_capacity: usize,
protected_len: usize,
probationary_len: usize,
prot_head: Option<usize>,
prot_tail: Option<usize>,
prob_head: Option<usize>,
prob_tail: Option<usize>,
```

Initialise in `try_new`:
```rust
let protected_capacity = (capacity * 9) / 10;
let probationary_capacity = capacity - protected_capacity;
// zero-initialise all len/head/tail fields
```

### 3. Segment-maintenance helpers

Add `prob_unlink`, `prob_push_back`, `prot_unlink`, `prot_push_back` (identical to v003's implementation, setting `in_protected` appropriately in the push helpers).

Add `maybe_demote_from_protected`:
```rust
fn maybe_demote_from_protected(&mut self) {
    while self.protected_len > self.protected_capacity {
        if let Some(h) = self.prot_head {
            self.prot_unlink(h);
            self.protected_len -= 1;
            self.nodes[h].in_protected = false;
            self.prob_push_back(h);
            self.probationary_len += 1;
        } else { break; }
    }
}
```

### 4. `get()` — standard SLRU promotion

```rust
pub fn get(&mut self, key: &K) -> Option<&V> {
    self.sketch.increment(key);
    let &idx = self.map.get(key)?;
    if self.nodes[idx].in_protected {
        self.prot_unlink(idx);
        self.prot_push_back(idx);
    } else {
        // promote probationary → protected unconditionally on access
        self.prob_unlink(idx);
        self.probationary_len -= 1;
        self.prot_push_back(idx);
        self.protected_len += 1;
        self.maybe_demote_from_protected();
    }
    Some(&self.nodes[idx].value)
}
```

(No PROMO_THRESHOLD — items are promoted on any access, as in the vanilla SLRU used in cycles 0001 and 0002.)

### 5. `put()` — new items go to probationary; existing keys refresh in-place

For the existing-key update branch, mirror what standard SLRU does: if in protected, move to MRU of protected; if in probationary, move to MRU of probationary (no promotion on put).

For the pre-full arena branch, always insert into probationary.

### 6. `put()` — frequency-sampled victim selection (THE KEY CHANGE)

When the arena is full, instead of always evicting `prob_head`, select the minimum-frequency candidate among the k=4 least-recently-used probationary items:

```rust
// Walk up to K=4 candidates from the LRU end of probationary.
const K: usize = 4;
let mut victim_idx = self.prob_head
    .expect("TinyLfuCache: full cache, probationary non-empty");
let mut victim_freq = self.sketch.estimate(&self.nodes[victim_idx].key);

let mut cursor = self.nodes[victim_idx].next;
for _ in 1..K {
    let Some(c) = cursor else { break };
    let f = self.sketch.estimate(&self.nodes[c].key);
    if f < victim_freq {
        victim_freq = f;
        victim_idx = c;
    }
    cursor = self.nodes[c].next;
}
// Fall back to protected LRU head if probationary is somehow empty.
// (Handled above — if prob_head is None we'd panic; add the fallback
//  with prot_head as the baseline does.)
```

After selecting `victim_idx`, apply the existing TinyLFU admission gate:
```rust
let incoming_freq = self.sketch.estimate(&key);
if incoming_freq > victim_freq {
    // evict victim_idx, recycle slot for incoming key in probationary
    // (same as baseline eviction logic, adapted for two-segment accounting)
}
// else: reject newcomer, victim stays
```

The victim may be in probationary (the usual case) or protected (only if probationary is empty); handle both with the appropriate segment-length decrements and unlink calls.

### 7. Unit tests

Keep all existing baseline unit tests and update them to work with the two-segment structure (the `get()` now promotes, so the single-segment invariants still hold). Add a test verifying that among multiple candidates the minimum-frequency one is evicted.

## Rationale

Cycles 0001–0003 explored SLRU ratio, sketch aging, admission windows, ghost-set, and promotion gating — all targeting which items enter or stay in the protected tier. The victim selection within probationary has always defaulted to strict LRU. On a Zipfian workload, probationary can contain a mix of brand-new cold items and recently-demoted warm items; the LRU tail might be the most recently inserted cold newcomer rather than the least valuable item. Scanning k=4 candidates adds a lightweight frequency tiebreaker without a full sort, potentially keeping moderately-hot probationary items alive longer at the cost of one extra sketch lookup per eviction.
