# H03

A 2x-narrower sketch (width factor 64 to 32) — the untested middle between the current width and the refuted 4x cut — holds hit-rate while halving sketch memory footprint.

## Parent

cycle/0009/v002

## Changes

The estimator's *width* axis is the one place cross-cycle history left a gap:
widening the sketch was the single largest hit-rate lever (cycle 0002), and an
aggressive 4x-narrower cut was refuted (cycle 0007), but the 2x point in between
was never measured. The winners run `const SKETCH_WIDTH_FACTOR: usize = 64;`.

Concretely:

1. Change `const SKETCH_WIDTH_FACTOR: usize = 64;` to
   `const SKETCH_WIDTH_FACTOR: usize = 32;`. This is the only change.

Leave `MIN_SKETCH_WIDTH`, the `next_power_of_two()` derivation in `try_new`,
`SKETCH_DEPTH`, the pre-increment admission gate, `PROMOTE_FLOOR`, and all SLRU
logic exactly as in v002. The width computed in `try_new`
(`(capacity * SKETCH_WIDTH_FACTOR).max(MIN_SKETCH_WIDTH).next_power_of_two()`)
will halve, cutting each sketch row's `Vec<u32>` length and thus total sketch
memory by ~2x.

The testable assertion: 32x cells per capacity unit still removes essentially all
count-min collisions on this low-churn, popularity-stable trace, so hit-rate
holds at 0.744 while the estimator footprint drops by half. If hit-rate slips,
the 2x cut is already past the redundancy edge and bounds the free-trim region to
between 32x and 64x — distinct from H02, which probes the orthogonal depth axis.
