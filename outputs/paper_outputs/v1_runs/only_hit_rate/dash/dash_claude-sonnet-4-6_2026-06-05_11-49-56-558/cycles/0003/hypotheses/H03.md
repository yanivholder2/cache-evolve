# H03

Adding a threshold-gated decay policy where co-resident counter decrements only fire once the hit item's own counter reaches 4 will recover frequency-based eviction's benefits without draining mildly-warm co-residents, improving hit rate over the baseline's pure LRU.

## Parent

baseline

## Changes

Two overlay files are required: `src/shared/eviction_policy.rs` and `src/dash/dash_bucket.rs`.

**`src/shared/eviction_policy.rs`:** Copy the entire baseline file verbatim, then append a new struct `ThresholdAgingLfu` at the bottom. This struct implements `EvictionPolicy` with the following semantics:

- `get_from_position`: Increment the hit item's `lfu_counter` by 1 (not 2 as in the failed `AgingLfu`). Then, only if that item's counter has now reached `>= 4`, saturating-decrement every other item's `lfu_counter` by 1. If the hit item's counter is below 4, do not touch co-residents at all.
- `eviction_candidate_index`: Return the index of the item with the minimum `lfu_counter` (same as `Lfu`).
- `promotion_candidate_index`: Return the index of the item with the maximum `lfu_counter` (same as `Lfu`).
- `name`: Return `"ThresholdAgingLfu"`.

```rust
pub struct ThresholdAgingLfu;

impl<K, V> EvictionPolicy<K, V> for ThresholdAgingLfu
where
    K: Hash + Eq + Copy + Debug,
    V: Eq + Copy + Debug,
{
    fn name(&self) -> &'static str {
        "ThresholdAgingLfu"
    }

    fn get_from_position(&self, items: &mut Vec<Item<K, V>>, position: usize) -> usize {
        items[position].lfu_counter = items[position].lfu_counter.saturating_add(1);
        if items[position].lfu_counter >= 4 {
            let n = items.len();
            for i in 0..n {
                if i != position {
                    items[i].lfu_counter = items[i].lfu_counter.saturating_sub(1);
                }
            }
        }
        position
    }

    fn eviction_candidate_index(&self, items: &[Item<K, V>]) -> usize {
        items
            .iter()
            .enumerate()
            .min_by_key(|(_, item)| item.lfu_counter)
            .expect("eviction_candidate_index precondition: non-empty")
            .0
    }

    fn promotion_candidate_index(&self, items: &[Item<K, V>]) -> usize {
        items
            .iter()
            .enumerate()
            .max_by_key(|(_, item)| item.lfu_counter)
            .expect("promotion_candidate_index precondition: non-empty")
            .0
    }
}
```

Do not add `ThresholdAgingLfu` to the `EvictionPolicyKind` enum; it is wired in directly via `new_bucket` below.

**`src/dash/dash_bucket.rs`:** Copy the entire baseline file verbatim, then add a use-import for `ThresholdAgingLfu` at the top of the file and modify `new_bucket` to ignore the passed-in `eviction_policy` argument and instead construct every bucket with `ThresholdAgingLfu`:

## Rationale

Cycle 2's `AgingLfu` variant (v003, hit-rate 0.636) hurt performance by applying a blanket −1 decrement to all co-residents on every cache hit, draining mildly-warm items that plain LRU would have retained. The cross-cycle insight asks whether "a smaller decay increment or access-count-gated decay" can rehabilitate frequency discrimination. The threshold gate (decay fires only when the hit item's counter ≥ 4) means a freshly inserted or rarely accessed item never triggers collateral decay — only items that have proven themselves with repeated hits age their neighbours. This preserves LRU-like retention of mildly-warm items while still allowing truly cold slots to be displaced by persistently hot ones.
