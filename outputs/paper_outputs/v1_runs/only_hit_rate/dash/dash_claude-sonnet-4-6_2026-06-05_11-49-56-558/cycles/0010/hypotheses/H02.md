# H02

Changing `ClassicLRUFreqProtect.promotion_candidate_index()` to select the item with the highest `lfu_counter` (rather than the MRU-position item) will improve hit-rate by promoting the most in-tier-accessed item to the probing tier.

## Parent

cycle/0009/v003

## Changes

In `src/shared/eviction_policy.rs`, modify `ClassicLRUFreqProtect::promotion_candidate_index()`.

Current code:
```rust
fn promotion_candidate_index(&self, items: &[Item<K, V>]) -> usize {
    items.len() - 1  // same as ClassicLRU: MRU end
}
```

Replace with a scan that returns the index of the item with the maximum `lfu_counter`, breaking ties by choosing the MRU-most item (highest index):

```rust
fn promotion_candidate_index(&self, items: &[Item<K, V>]) -> usize {
    items.iter()
        .enumerate()
        .max_by_key(|(pos, item)| (item.lfu_counter, *pos))
        .map(|(i, _)| i)
        .unwrap_or(items.len() - 1)
}
```

The `(item.lfu_counter, *pos)` tuple key means: first prefer the highest frequency count; among equal counts, prefer the MRU-most item (highest position index). When all items have equal counters (e.g., all zero on a fresh bucket), this degenerates to `items.len() - 1`, identical to the current behaviour.

No other function changes. `get_from_position`, `eviction_candidate_index`, geometry, second-chance recovery, and stash-exit credit from the parent are all preserved unchanged.

## Rationale

The current `promotion_candidate_index` returns the MRU-front item (`items.len() - 1`). Because `get_from_position` moves the accessed item to MRU AND increments `lfu_counter`, the MRU item is always the item that was most recently touched — but not necessarily the item that has been touched the most times within this tier. Consider a bucket where item A has `lfu_counter == 1` (just accessed once, now at MRU) and item B has `lfu_counter == 6` (accessed six times, but bumped off MRU by A's recent access). The current policy promotes A; the proposed policy promotes B.

Promoting the highest-frequency item to the probing tier is the correct choice for a Zipfian workload: items with high in-tier counters are genuinely hot and deserve the probing tier's protection, not just items that happened to receive the most recent single access. This is not LFU eviction (which has consistently failed) — it is LFU-guided *promotion selection*, operating on already-warm items to choose which deserves to move up, not which should be discarded. The `lfu_counter` values accumulated by `ClassicLRUFreqProtect.get_from_position` are currently unused for promotion; this change makes them useful at the promotion decision point.
