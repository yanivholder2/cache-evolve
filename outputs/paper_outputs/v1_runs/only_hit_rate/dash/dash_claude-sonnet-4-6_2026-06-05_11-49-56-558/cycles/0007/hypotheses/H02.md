# H02

Combining ClassicLRUFreqProtect's zero-access eviction guard with TimestampLRU's recency-based promotion candidacy into a single `TimestampFreqProtect` policy will improve hit rate over cycle/0006/v001 by ensuring the item promoted from each target bucket is the genuinely hottest resident rather than merely the most recently inserted one.

## Parent

cycle/0006/v001

## Changes

In `src/shared/eviction_policy.rs`, add a new policy struct:

```rust
#[derive(Debug)]
pub struct TimestampFreqProtect;
```

Implement `EvictionPolicy<K, V>` for it with the following three methods:

- `name()`: return `"TimestampFreqProtect"`.
- `get_from_position(items, position)`: record the current wall-clock timestamp on `items[position].last_accessed` (same as `TimestampLRU`), increment `items[position].lfu_counter` by 1 (same as `ClassicLRUFreqProtect`), remove the item from `position` and push it to the end of the vector (MRU end), then return `items.len() - 1`.
- `eviction_candidate_index(items)`: return the index of the first item whose `lfu_counter == 0`; if no such item exists, return `0` (LRU-position fallback). This is identical to `ClassicLRUFreqProtect`.
- `promotion_candidate_index(items)`: return the index of the item with the maximum `last_accessed` value, using position (highest index = MRU end) as a tiebreaker. This is identical to `TimestampLRU`.

In `src/dash/dash_bucket.rs`, change `new_bucket` to instantiate `Box::new(TimestampFreqProtect)` instead of `Box::new(ClassicLRUFreqProtect)`.

No changes to `src/dash/segments/dash_segment.rs` or `src/shared/geometry.rs` relative to v001 — keep the `lfu_counter = 0` reset on stash demotion and the 24/8 normal/stash geometry exactly as in v001.

The eviction guard and promotion candidacy logic operate on independent code paths: eviction candidacy fires when a bucket must shed an item; promotion candidacy fires when the segment's target-bucket scan selects which item to elevate to the normal tier. They do not interfere.

## Rationale

v001 improved eviction selectivity but left promotion candidacy as MRU-position-based (same as ClassicLRU). v003's TimestampLRU improved promotion accuracy but had no eviction guard and scored lower (0.7136 vs 0.7194). The cross-cycle insight notes that TimestampLRU should be "tested as an addition to the winning frequency-guard baseline rather than as a standalone replacement." This hypothesis does exactly that: it grafts v003's promotion improvement onto v001's eviction improvement to test whether the two axes compound.
