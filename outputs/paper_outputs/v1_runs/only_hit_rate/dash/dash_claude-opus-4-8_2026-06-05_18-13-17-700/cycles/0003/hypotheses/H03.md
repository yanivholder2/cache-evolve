# H03

Reshaping the same capacity into fewer-but-wider buckets (double `bucket_size`, halve the bucket counts at the baseline ratio) deepens each hash bucket's LRU stack so hot keys colliding in a target bucket survive longer, raising hit-rate on the skewed trace.

## Parent

baseline

## Changes

In the overlaid `src/shared/geometry.rs`, change `BaselineGeometry::layout`
to trade bucket count for bucket width while conserving the budget. Read the
seeded topology, compute `total_slots = num_of_segments * (num_of_normal_buckets
+ num_of_stash_buckets) * bucket_size`, then return a `DashGeometry` with
`bucket_size = self.topology.bucket_size * 2` and bucket counts halved
(integer-divide both `num_of_normal_buckets` and `num_of_stash_buckets` by 2),
keeping `num_of_segments` as seeded. For the default 28/4 × 16 budget this
yields 14 normal / 2 stash × 32 (still 512 slots, 7:1 ratio preserved).
Guard validity: clamp `num_of_normal_buckets` to at least 2 and
`num_of_stash_buckets` to at least 1, and if halving would break the exact
capacity equality (e.g. odd counts), fall back to the seeded topology so P6
capacity_conservation never fails. This isolates per-bucket associativity
(stack depth) from the normal/stash split ratio, which H01 sweeps separately.

## Rationale (optional)

Cycles 1–2 only moved the split ratio; bucket width is an untouched geometry
axis. On a high-skew workload, deeper buckets give each hot hash bucket more
room before eviction, a different mechanism from reallocating buckets between
tiers. A clean baseline ablation tells us whether width helps before
combining it with v001's split.
