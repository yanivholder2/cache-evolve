# H03

A keys-only doorkeeper that withholds stash admission until a key's second sighting protects scarce stash capacity from one-hit-wonders and raises hit-rate on the skewed tail.

## Parent

baseline

## Changes

Add a TinyLFU-style doorkeeper in front of stash admission in the
baseline `DashSegment`. Introduce a bounded, keys-only recency set
`doorkeeper` (a `VecDeque<K>` + companion `HashSet<K>` for O(1)
membership, FIFO-evicted when full), sized to roughly the total stash
capacity (`num_of_stash_buckets * bucket_size`). It stores keys only, so
it adds no resident capacity and `capacity_conservation` /
`total_items` are untouched.

Change the cold-admission path in `put`:

- If `item.key` is already in `doorkeeper` (a proven second sighting),
  remove it from the doorkeeper and admit the item to stash as the
  baseline does today (MRU stash landing via the existing stash insert).
- If `item.key` is not in `doorkeeper` (a first-ever sighting within the
  window), record the key into `doorkeeper` and do NOT store the value —
  the one-hit candidate is held back so it cannot occupy a stash slot it
  may never reuse.

Leave the hit path (`get` / promotion logic) entirely unchanged: any key
that becomes resident is promoted exactly as in baseline. Drop a key's
doorkeeper entry once it is admitted so the structure only ever holds
not-yet-admitted candidates.

Preserve invariants: at most one new resident seat per `put`
(`single_eviction_per_put` holds — the first-sighting branch adds zero
residents), and the doorkeeper never holds values.

## Rationale (optional)

On a high-skew Zipfian trace the hot keys recur almost immediately and
clear the doorkeeper on their second request, while true singletons in
the long tail are blocked from ever displacing a stash resident. This is
a fresh, distinct mechanism from baseline (an admission *filter*, not an
admission removal or a front-landing change, both of which regressed), so
it diversifies the gene pool and hedges the per-bucket occupancy ceiling.
