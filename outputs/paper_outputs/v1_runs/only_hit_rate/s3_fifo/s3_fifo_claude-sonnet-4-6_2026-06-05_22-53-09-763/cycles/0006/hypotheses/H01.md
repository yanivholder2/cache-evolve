# H01

Restricting the move-to-front reprieve in `evict_main()` to items with freq ≥ 2 (pre-decrement) and immediately evicting items with freq = 1 will improve hit rate by reserving main-queue head positions for items with genuine ongoing popularity rather than nearly-cold survivors.

## Parent

cycle/0005/v001

## Changes

In `evict_main()`, change the reprieve condition from `if tail.freq > 0` to `if tail.freq > 1`.

Current code:
```rust
fn evict_main(&mut self) {
    while let Some(mut tail) = self.main.pop_back() {
        if tail.freq > 0 {
            tail.freq -= 1;
            self.main.push_front(tail);
        } else {
            break;
        }
    }
}
```

New code:
```rust
fn evict_main(&mut self) {
    while let Some(mut tail) = self.main.pop_back() {
        if tail.freq > 1 {
            tail.freq -= 1;
            self.main.push_front(tail);
        } else {
            // freq == 0 or freq == 1: evict immediately, no front reprieve
            break;
        }
    }
}
```

Items with `freq == 1` are treated the same as items with `freq == 0`: the loop breaks and the item is dropped (evicted without being reinserted). The `while` loop, the `push_front`, and the decrement logic for surviving items are all preserved. `main.len()` still decreases by exactly 1 per call. All other fields and methods (`evict_small`, `get`, `put`, ghost handling, `MAX_FREQ`, queue sizes) remain unchanged from cycle/0005/v001.

Rationale: An item with exactly 1 remaining frequency count is already committed to eviction — it has no further accesses pending, and the only thing push_front does is delay eviction by one full queue traversal. Those front-of-queue positions are more valuable as recency protection for genuinely hot items (freq ≥ 2). Making the second-chance gate slightly stricter (freq > 1 instead of freq > 0) may free up residency for hotter items at the cost of earlier eviction of barely-warm ones.
