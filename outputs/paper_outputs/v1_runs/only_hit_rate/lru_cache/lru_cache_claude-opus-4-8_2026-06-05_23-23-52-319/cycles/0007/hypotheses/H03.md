# H03

Enlarging the LIRS non-resident HIR history beyond one capacity raises hit-rate by detecting longer-reuse-distance second touches that the SLRU incumbent cannot catch.

## Parent

cycle/0005/v002

## Changes

The parent is the canonical LIRS rebuild (stack S, list Q, bounded non-resident
metadata). Its `evict_one` caps non-resident metadata with
`while self.nonresident_count > self.capacity { self.reclaim_oldest_nonresident(); }`,
so it remembers at most `capacity` evicted-HIR keys — the same horizon as the
resident set. LIRS's distinguishing power is its memory of *non-resident*
reuse, and the open question flagged across cycles is whether an untested LIRS
lever (here, the non-resident bound) actually moves it against the 95/5 SLRU
incumbent.

Introduce an explicit `nonresident_cap` field set to a multiple of capacity
(e.g. `2 * capacity`, or `capacity + l_lir`) and change the reclaim loop in
`evict_one` and any other bounding site to use `nonresident_cap` instead of
`capacity`. Keep memory O(capacity) — the multiple must be a fixed small
constant, not unbounded growth — and keep `nodes`, `free_slots`, and the
arena-reuse path correct as the larger non-resident population is allocated and
reclaimed. Preserve every existing invariant: `resident_count <= capacity`,
stack-S pruning so its bottom is always LIR, and the LIR-budget enforcement.
All current LIRS unit tests must still pass.

## Rationale (optional)

If workload-a's reuse distances frequently exceed `capacity` distinct
intervening keys, the parent forgets evicted-HIR metadata before the reuse
returns, so a short non-resident horizon blinds LIRS exactly where it should
beat SLRU. Widening only the non-resident history (not the HIR/LIR resident
split, whose SLRU-transplant tunings already regressed) is the one LIRS lever
that targets long-distance reuse without re-partitioning residents — settling
whether LIRS has any headroom over the converged SLRU optimum.
