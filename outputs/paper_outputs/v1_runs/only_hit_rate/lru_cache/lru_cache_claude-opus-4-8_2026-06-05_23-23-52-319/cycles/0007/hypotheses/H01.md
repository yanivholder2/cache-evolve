# H01

Adding a third "hot" recency tier inside the protected segment so demotion sheds twice-seen-cold keys before many-times-hot keys raises hit-rate on the reuse-heavy trace.

## Parent

cycle/0004/v001

## Changes

The parent is SLRU 95/5 with a single protected segment that behaves as a
plain LRU and demotes its LRU node (`prot_head`) whenever
`enforce_protected_budget` fires. Split the protected region into two
recency lists that together stay within the existing `protected_cap` (so the
P1 capacity bound and the `prob_len + prot_len == map.len()` invariant are
unchanged):

- a **cold-protected** list (keys promoted on their 2nd access), and
- a **hot** list (keys that earned a 3rd-or-later access).

Add the needed head/tail/len fields and a per-node tier marker (extend the
existing `protected` bool into a 3-state tier enum, or add a `hot: bool`).
Rework the hit path (`get` and the `put`-update branch) so that:

- a probationary node promotes into cold-protected (MRU end), exactly as today;
- a cold-protected node promotes into the hot list (MRU end);
- a hot node moves to the MRU end of the hot list.

Change `enforce_protected_budget` so the demotion victim is the LRU of the
**cold-protected** list first; only when cold-protected is empty does it demote
the LRU of the hot list. Demoted nodes re-enter probationary exactly as the
parent does (MRU/back end). Keep the combined `cold_len + hot_len <=
protected_cap` bound enforced after every promotion, and keep eviction on
insert taking the probationary LRU first as before. Preserve all existing
unit-test behaviors (the SLRU tests must still pass) and the
capacity-one/zero handling.

## Rationale (optional)

Protected is currently flat LRU, so when it must shed a member it can drop a
genuinely hot key as easily as a cold one. Distinguishing reuse *depth* by
recency-of-Nth-access (an LRU-K-like signal, not a frequency counter — those
have repeatedly lost here) targets retention of the truly hot working set
without touching the converged 95/5 geometry.
