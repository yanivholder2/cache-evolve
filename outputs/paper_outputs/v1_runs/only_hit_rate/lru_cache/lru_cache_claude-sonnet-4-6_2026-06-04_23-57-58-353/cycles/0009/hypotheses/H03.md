# H03

Replacing the raw IRR score with a staleness-weighted IRR score — `irr * (op_clock - last_access)` — in the cycle/0007/v003 eviction scans raises hit rate by evicting entries whose historical hotness has decayed, rather than entries that merely have a large absolute inter-reference gap.

## Parent

cycle/0007/v003

## Changes

Start from the cycle/0007/v003 overlay (SLRU + IRR timestamps, 80/20 split, LRU-quarter scan in protected, LRU-half scan in probationary, no ghost set, timestamps preserved across demotion).

**The problem being addressed:**
Pure IRR captures only the gap between an entry's last two accesses. An entry accessed at op-clocks 100 and 102 (IRR=2) will retain IRR=2 indefinitely even if `op_clock` later reaches 50000 — it appears maximally "hot" despite having gone untouched for 49998 operations. Meanwhile an entry with IRR=10 but accessed just 3 operations ago is treated as much colder, even though it is far more likely to be reaccessed soon.

**Replace `irr()` with `irr_score(idx, now)`:**
Add a new function:
```rust
fn irr_score(&self, idx: usize, now: u64) -> u64 {
    if self.nodes[idx].prev_access == 0 {
        // Single-access cold newcomer: remains maximally cold.
        u64::MAX
    } else {
        let irr = self.nodes[idx].last_access - self.nodes[idx].prev_access;
        let staleness = now.saturating_sub(self.nodes[idx].last_access).max(1);
        irr.saturating_mul(staleness)
    }
}
```
The `staleness` term is `op_clock - last_access` (how many operations ago the entry was last touched). Multiplying by IRR means: a small IRR (tight two-access burst) survives as long as `last_access` is recent, but degrades as the entry goes untouched. The `.max(1)` prevents an entry just accessed from getting a zero score. `saturating_mul` prevents overflow.

**Update victim selection in both scan functions:**
- In `evict_from_probationary()`, replace `let cur_irr = self.irr(cur);` with `let cur_score = self.irr_score(cur, self.op_clock);` and replace `if cur_irr > victim_irr` with `if cur_score > victim_score`. Also initialize `victim_score = self.irr_score(start, self.op_clock)` in place of `victim_irr`.
- In `demote_prot_head()`, apply the same substitution.
- Remove the old `irr()` function (or keep it as dead code if the test suite references it — but the scan functions should use `irr_score`).

**Keep unchanged:**
- IRR timestamp mechanics (`last_access`, `prev_access`, `op_clock`). The timestamps are still updated identically on every `get` hit and on new `put` insertion.
- 80/20 protected/probationary split (`prot_cap = capacity * 4 / 5`).
- LRU-quarter scan in protected (`scan_len = (prot_count / 4).max(1)`).
- LRU-half scan in probationary (`scan_len = (prob_count / 2).max(1)`).
- Single-hit promotion from probationary to protected.
- Timestamp preservation across demotion (do NOT reset `last_access` or `prev_access`).
- All linked-list helpers and the arena slot-reuse mechanism (`free_slots`).
- Unit tests: any test that calls `irr()` directly should be updated to call `irr_score(idx, self.op_clock)` or adjusted to match the new behavior.

## Rationale

This change addresses a systematic bias in pure IRR: entries that were accessed in a tight burst long ago "look hot" indefinitely, while entries with a moderate but recent access gap look cold. The product `irr * staleness` functions like a distance metric in two-dimensional (inter-reference gap, time-since-last-access) space. The LRU-K literature (specifically LRU-2) motivated a related idea: evict the entry whose second-most-recent access is furthest in the past. The weighted IRR score approximates this by penalizing entries where both the gap and the silence since the last access are large. Unlike LRU-K, this requires no structural change — it is purely a scoring change within the existing scan mechanism, preserving all other properties that have proven load-bearing across cycles 1-8.
