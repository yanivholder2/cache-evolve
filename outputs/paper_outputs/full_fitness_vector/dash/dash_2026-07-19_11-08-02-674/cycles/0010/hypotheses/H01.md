# H01

Lowering the two-chance clock's warm-protection threshold from freq≥3 to freq≥2 will raise hit rate by covering the genuine Zipfian working set, which concentrates at access counts 1–2.

## Parent

cycle/0009/v001

## Changes

In `src/dash/segments/dash_segment.rs`, make two changes — both thresholds must be updated together so the clock's warm-on-access signal and the warm-on-arrival guard stay consistent:

**1. In `promotion_get`, non-hottest target branch** (the block starting with `let items_mut = core.buckets[target_idx].get_items_mut();`): change the CLOCK_BIT set condition from `new_freq >= 3` to `new_freq >= 2`:

```rust
let old_freq = items_mut[item_idx].lfu_counter & !CLOCK_BIT;
let new_freq = old_freq + 1;
items_mut[item_idx].lfu_counter = if new_freq >= 2 {
    new_freq | CLOCK_BIT
} else {
    new_freq
};
```

**2. In `promote_to_target`**, change the warm-on-arrival guard from `>= 3` to `>= 2`:

```rust
if item.lfu_counter & !CLOCK_BIT >= 2 {
    item.lfu_counter |= CLOCK_BIT;
}
```

All other logic from cycle/0009/v001 remains identical: `clock_evict_prepare` is unchanged, the vacancy-gated frequency promotion gate stays at freq≥2, the probing re-entry gate stays at counter≥2, `promote_to_probing` and `demote_from_normal_bucket` are unchanged. Update the `DashSegment` doc comment to reflect the new threshold. No changes to `eviction_policy.rs` or `item.rs`.

## Rationale

Cross-cycle analysis confirmed freq≥3 cold-classifies items at counts 1 and 2, which represent a large fraction of the Zipfian hot set (cycle 9 v001 regressed from 0.692 to 0.6918). freq≥1 (cycle 8) was too dense — every resident looked warm. freq≥2 is the unexplored midpoint that should protect genuine reuse without saturating the warm flag.
