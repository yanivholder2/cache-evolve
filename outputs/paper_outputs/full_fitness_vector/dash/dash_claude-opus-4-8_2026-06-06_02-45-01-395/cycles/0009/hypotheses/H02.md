# H02

Defer the target/probing index computation until after the stash branch misses, removing two `get_index` calls from the median (stash-resolving) get and lowering get-p50.

## Parent

cycle/0007/v002

## Changes

Modify `promotion_get` in `src/dash/segments/dash_segment.rs`. The parent
computes all three indices up front:

```
let stash_idx = get_index(key, core.stash_size);
let target_idx = get_index(key, core.segment_size);
let probing_idx = (target_idx + 1) % core.segment_size;
```

but the get path is stash-first, and cycle 0008 established the median get hit
resolves in the **stash** — so on the dominant case `target_idx`/`probing_idx`
are computed and then never used before the function returns from the stash
branch.

Keep only `let stash_idx = get_index(key, core.stash_size);` before the stash
lookup. Inside the stash-hit branch, compute `target_idx` locally where it is
first needed (the `get_index(key, core.segment_size)` for the post-promotion
re-lookup). After the stash branch falls through (a stash miss), compute
`let target_idx = get_index(key, core.segment_size);` and
`let probing_idx = (target_idx + 1) % core.segment_size;` once, immediately
before the target branch, so both the target and probing branches still see them.

Preserve: branch order (stash → target → probing) is unchanged; every branch body
is byte-for-byte identical to the parent's; all returned items and all
heat/promotion side effects are bit-for-bit identical. Only the *placement* of
the two index computations moves, so resident behaviour, hit-rate (0.6794), and
metadata (16) are untouched.

## Rationale (optional)

Cross-cycle insight flags get latency as "possibly at the hasher floor"; this
tests whether removing two now-confirmed-wasted `get_index` evaluations from the
median path still buys get-p50, or whether the median is truly hasher-bound and
the two calls sit below the noise floor.
