# H02

Scanning the stash bucket back-to-front (MRU-first) on the get path lowers get-p50 (per-op-time) because the median get hit resolves in the stash on a recently-inserted key that sits near the bucket's MRU end.

## Parent

cycle/0007/v002

## Changes

The median get hit resolves in the stash (cycle 0008), and the stash lookup in
`promotion_get` (`src/dash/segments/dash_segment.rs`, the
`core.stash_buckets[stash_idx].get_position(key)` call, ~line 185) is a
front-to-back (LRU-first) linear scan via the default
`Bucket::get_position` (`src/shared/traits/bucket.rs`, ~line 133, using
`iter().position`). Fresh `put`s and demotions land at the bucket Back (MRU),
so a stash hit — the resident's first re-access shortly after its put — tends
to sit near the back and pays a near-full forward scan.

Add a reverse-scan lookup and use it **only** for the stash branch of the get
path. Concretely, add a `get_position_rev` method to the `Bucket` trait that
returns `self.get_items().iter().rposition(|d| d.key == *key)`, and call it in
`promotion_get`'s stash lookup in place of `get_position`. Because keys are
unique within a bucket, `rposition` returns the identical index `position`
would, so the item found, the subsequent `remove_at` + `promote_to_target`,
hit-rate, and metadata are all bit-for-bit unchanged — only the probe's scan
direction (and therefore its median cost) moves. Do NOT touch
eviction-candidate selection or any target/probing lookup; leave those on the
existing forward `get_position`.

## Rationale (optional)

Cycle 0009 closed get-p50 as hasher-bound, but that finding was about the
`target_heat` side-table probe and index arithmetic on the *target* path — the
stash-resolving median get touches neither. The stash bucket's linear-scan
*direction* is an untested lever sitting directly on the confirmed median
location, and it changes no behaviour, only cost.
