# H03

A segment-owned ghost list of recently-evicted keys that fast-tracks a re-inserted ghost key straight into its target bucket (instead of stash probation) raises hit-rate above the 0.679 ceiling by protecting proven-recurring keys over one-hit-wonders.

## Parent

cycle/0004/v001

## Changes

Every miss currently restarts a key in the stash, so a key that was admitted,
evicted, and requested again must re-earn its way up from probation — identical
to a never-seen key. That is pure LRU/recency admission, and the cross-cycle
notes show recency-only levers (placement, gate, associativity) have saturated
hit-rate at 0.679. Add a *frequency-aware admission* lever, a class not yet
tried:

- In `src/dash/segments/mod.rs`: add a bounded `ghost: VecDeque<K>` (plus a
  `HashSet<K>` membership index for O(1) lookup) to `SegmentCore`, capacity a
  small fixed multiple of `segment_size` (e.g. 2x). When any bucket eviction
  removes a key from the cache entirely (the terminal `Slot::Stash` overflow in
  `demote_from_normal_bucket`'s stash put, and stash-bucket eviction in
  `promotion_get`'s stash branch / `put`), record the evicted key into `ghost`,
  evicting the oldest ghost entry and its set membership when over capacity.
- In `DashSegment::put` (`src/dash/segments/dash_segment.rs`): if the incoming
  key is present in `ghost`, route it to `Slot::Target` at `InsertPosition::Back`
  (admit as proven-recurring) and remove it from `ghost`; otherwise keep the
  existing stash admission. Continue to clear `target_heat` for the key.
- Treat `ghost` purely as segment container state (like `target_heat`), so it
  does not enter the measured per-entry `Item` footprint; metadata-size stays 16.

Preserve the promotion gate, side table, and cascade logic. The testable claim
is that direct-to-target admission of recurring keys keeps the warm working set
resident longer and lifts hit-rate; if it stays bit-for-bit at 0.6794, that is
strong evidence hit-rate is fully compulsory/capacity-capped even against an
admission-class lever, resolving the standing open question.

## Rationale (optional)

This is the one remaining untried hit-rate class — admission/frequency rather
than placement/gate/associativity — so it is the right probe for "is any lever
left that can move hit-rate." Its side structures live off the `Item`, so a null
result costs nothing on size.
