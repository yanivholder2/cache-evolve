# H01

Replace the default SipHash hasher on the `target_heat` side table with a trivial multiplicative hasher to cut get p50 latency while holding the 16-byte metadata floor.

## Parent

cycle/0005/v001

## Changes

In `src/dash/segments/mod.rs`, the promotion-heat side table is declared as
`pub(crate) target_heat: HashMap<K, u8>`, which defaults to
`std::collections::hash_map::RandomState` (SipHash). The cross-cycle finding is
that this side-table probe — not the vtable — is what bounds v001's get p50 at
86 ns against v002's 81 ns. The keys are `u64`, so SipHash is gross overkill.

Concretely:

1. In the overlay (do NOT touch Cargo.toml — no external crates), define a
   small zero-state `BuildHasher` + `Hasher` pair, e.g. `struct U64Hasher(u64)`
   implementing `Hasher` with a single multiplicative mix on `write_u64`
   (Fibonacci constant `0x9E3779B97F4A7C15`) and a passthrough/panic for the
   byte-slice `write` path (the map is only ever keyed by the integer key, so
   `write_u64`/`write_i64` are the only paths exercised; route `write` through a
   simple FNV-style fold as a correctness fallback so the generic `K: Hash`
   bound still compiles for the test key type `i64`). Add a unit-struct
   `BuildHasher` that returns a fresh `U64Hasher(0)`.
2. Change the field type to `HashMap<K, u8, U64BuildHasher>` and initialize it in
   `SegmentCore::try_new` with `HashMap::with_hasher(U64BuildHasher)` (or
   `HashMap::default()` if you implement `Default`).
3. Leave every gate decision in `promotion_get` and `put` byte-for-byte
   unchanged: heat is still bumped on each target hit via `entry().or_insert(0)`,
   promotion still fires at `PROMOTE_AT`, and the `remove` resets still run. Only
   the hash function changes.

Preserve the existing `Debug` impl for `SegmentCore` (the new hasher type needs
no `Debug`; the map's `Debug` only requires `K`/`V` Debug, which still hold).
Invariants: gate semantics, slot legality, and `Item<u64,u64>` size (16 bytes)
must all be unchanged; only get/put latency should move.

## Rationale (optional)

This is the lowest-risk attack on the documented bottleneck: it keeps v001's
exact size-corner semantics and only removes the SipHash cost from the hot
target-hit probe, aiming to close the 86→81 ns gap at the metadata floor.
