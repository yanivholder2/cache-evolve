# H01

Probe the target and probing buckets before the stash in `promotion_get` to cut get-p50 by skipping the stash scan on the dominant hot hits.

## Parent

cycle/0007/v001

## Changes

In `src/dash/segments/dash_segment.rs`, reorder the three lookup branches
inside `promotion_get` so the normal-bucket slots are checked before the
stash. The current order is stash → target → probing; change it to
**target → probing → stash**, keeping each branch body byte-for-byte
identical (same heat bump/`PROMOTE_AT` gate in the target branch, same
`promote_to_target` call in the stash branch, same in-place touch in the
probing branch).

Rationale for safety: a resident key lives in exactly one slot, so the
order in which the three buckets are probed never changes which branch
fires or what it returns — only the number of negative `get_position`
scans paid before the hit. On this LIRS/Zipfian trace the hottest keys
live in the target and probing tiers (they earned promotion), so a hit
there currently pays a wasted `get_index(stash)` + linear stash-bucket
scan first. Moving those branches ahead of the stash removes that wasted
scan from the common hot get, which is exactly the op the per-op-time
summary measures (get-p50, held at 75 ns by the v001 parent).

Preserve every invariant: the stash branch must still call
`promote_to_target` and return the post-promotion reference via the
target bucket; the target branch must still bump heat through
`core.target_heat` and promote to probing at `PROMOTE_AT`; the probing
branch must still touch in place. Only the ordering of the three `if let
Some(...)` blocks changes. Keep `put`, `SegmentCore`, and the heat side
table untouched, so hit-rate and metadata-size stay bit-for-bit at their
floors.

## Rationale (optional)

Two cycles confirmed the side-table probe's *median* cost is gone, but
both routes only economized the heat touch — neither cut the redundant
stash scan that every target/probing hit still pays. This is an
untried get-p50 lever on the proven best incumbent.
