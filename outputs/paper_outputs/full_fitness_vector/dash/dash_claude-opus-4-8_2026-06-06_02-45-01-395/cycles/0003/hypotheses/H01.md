# H01

Porting cycle/0002/v003's top-quarter positional promotion window onto v001's slim+MRU base will raise hit-rate without re-introducing fat metadata or latency cost.

## Parent

cycle/0002/v001

## Changes

In `promotion_get` (src/dash/segments/dash_segment.rs), the target-tier
branch currently promotes a key to probing only when it is the single
hottest item:

```
let is_hottest = Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();
```

Replace this single-slot test with v003's proportional top-quarter
window. Add a helper `is_in_promotion_window(bucket, item_idx) -> bool`
that:
- reads `len = bucket.get_items().len()` and `w = max(1, len / 4)`;
- reads the bucket's promotion end from `bucket.promotion_candidate_index()`
  (for the active positional `ClassicLRU` this is `len - 1`, the MRU/back end);
- returns true when `item_idx` lies within the `w` slots ending at that
  promotion index — i.e. for the positional policy, `item_idx >= len - w`.

Use this helper in place of `is_hottest`; when it returns true, run the
existing `promote_to_probing(core, data, insert_pos)` path unchanged.
Keep v001's slim `Item` (the `u8 lfu_counter`, no `timestamp`) and v001's
`InsertPosition::Back` MRU placement in `DashSegment::get` verbatim — only
the gate width changes. Preserve the stash→target and probing-touch
branches and the demotion cascade exactly as-is.

## Rationale

This is the clean realisation of cycle 0002's open question 1: v003 proved
the wider gate lifts hit-rate but carried the fat 40-byte `Item`; v001
proved slim+MRU at 24 bytes / 81 ns. Stacking the gate onto the slim base
tests whether the two wins compound or whether MRU placement already
captures most of the warm mass the window would add.
