# H02

Replace the `target_heat` HashMap with a fixed direct-mapped open array indexed by the key, removing the SwissTable lookup machinery from the get-hot-path probe to lower get-p50.

## Parent

cycle/0006/v001

## Changes

Replace the `target_heat: HashMap<K, u8, U64BuildHasher>` field in
`SegmentCore` (`src/dash/segments/mod.rs`) with a flat, fixed-size
direct-mapped table: a `Vec<Option<(K, u8)>>` (or two parallel vecs —
a `Vec<K>` slot-key plus `Vec<u8>` heat with an occupancy marker)
sized to the next power of two ≥ `2 * num_of_normal_buckets * bucket_size`,
allocated once in `try_new`. Index a key with
`(hash_or_key_as_usize(key)) & (table_len - 1)` — reuse the existing
`U64Hasher` multiply (or `get_index`-style fold) to derive the slot, so
there is no SwissTable probe sequence, no control-byte scan, and no
`entry()` insert path.

Rewrite the four `target_heat` call sites accordingly:
- `promotion_get` target branch: index in; if the stored slot key equals
  the probed key, bump its heat (`saturating_add(1)`); otherwise treat
  heat as 0 and claim the slot for this key with heat 1. Keep the
  `heat >= PROMOTE_AT` promotion decision and clear the slot on promote.
- `put`: clear the slot if it currently holds this key.
- The `Debug` impl and the round-trip test: update to the new structure.

This is a standalone segment-side array, **not** the cycle-0006/v003
position-aligned per-bucket `Vec<u8>` that regressed: it never rides
along with items through a ClassicLRU remove+push, so there is no O(n)
ride-along shift — it is O(1) indexed and touched only on target hits.
The one behavioral difference from the parent is slot collisions: two
distinct target-resident keys mapping to the same slot clobber each
other's heat (a rare, bounded promotion-timing perturbation). Size the
table at 2× capacity to keep collisions negligible and measure whether
hit-rate stays at 0.6794; if it moves, the array is refuted as a
hit-rate-neutral substitute. metadata-size must stay 16 (this is
segment container state, like the HashMap it replaces, so it does not
enter the per-`Item` footprint).

## Rationale (optional)

The HashMap probe is the documented get-p50 bound. v001 already removed
the hasher cost; the remaining cost is the SwissTable group scan and
`entry` bookkeeping. A direct-mapped array collapses the probe to one
index + one key compare, a structurally cheaper access than any
HashMap can offer.
