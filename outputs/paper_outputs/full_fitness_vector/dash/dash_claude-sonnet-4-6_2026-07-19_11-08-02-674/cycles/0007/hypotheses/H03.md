# H03

Adding vacancy-gated frequency promotion from target to probing in cycle/0006/v003 — incrementing non-hottest target items' `lfu_counter` on each hit and promoting them when the counter reaches 2 and probing has space — will raise hit rate above 0.679 and simultaneously activate the existing two-chance clock to spare those same warm items from eviction.

## Parent

cycle/0006/v003

## Changes

`cycle/0006/v003` never increments `lfu_counter` in any normal get path: the non-hottest target branch calls `get_from_position` (which rotates to MRU but does not touch the counter), and the probing branch also does not touch the counter. As a result, all items in the cache have `lfu_counter == 0`, and the two-chance clock pre-pass in `promote_to_target` and `demote_from_normal_bucket` immediately exits at the first item (counter == 0) — making the clock a no-op for freshly inserted items. This hypothesis activates the clock by adding the counter increment to the non-hottest target branch, and simultaneously gates early target-to-probing promotion on a vacancy check, mirroring the mechanism validated in `cycle/0005/v001` and `cycle/0006/v001`.

### `src/dash/segments/dash_segment.rs`

In `promotion_get`, replace the passive non-hottest-target branch with vacancy-gated frequency promotion. The current v003 code in the `else` arm of the `is_hottest` check:

```rust
} else {
    debug!("promotion_get: key={key:?} found in target item_idx={item_idx} (intra-promote)");
    return Some(core.buckets[target_idx].get_from_position(item_idx));
}
```

Replace with:

```rust
} else {
    core.buckets[target_idx].get_items_mut()[item_idx].lfu_counter += 1;
    let counter = core.buckets[target_idx].get_items()[item_idx].lfu_counter;
    let probing_has_space = !core.buckets[probing_idx].is_full();
    if counter >= 2 && probing_has_space {
        debug!("promotion_get: key={key:?} found in target item_idx={item_idx} lfu_counter={counter} probing={probing_idx} has space (vacancy-gated frequency-promote)");
        let data = core.buckets[target_idx].remove_at(item_idx);
        promote_to_probing(core, data, insert_pos);
        let item_new_idx = core.buckets[probing_idx]
            .get_position(key)
            .expect("promote_to_probing must leave key in probing");
        return Some(&core.buckets[probing_idx].get_items()[item_new_idx]);
    }
    debug!("promotion_get: key={key:?} found in target item_idx={item_idx} lfu_counter={counter} (intra-promote)");
    return Some(core.buckets[target_idx].get_from_position(item_idx));
}
```

Leave the stash branch, the hottest-target promotion branch, and the probing branch all unchanged from v003 (in particular, do NOT add probing re-entry or a probing counter increment — the probing branch in this variant remains passive). Leave `promote_to_target`, `promote_to_probing`, `demote_from_normal_bucket`, and `clock_evict_prepare` unchanged from v003.

## Rationale

This hypothesis tests the vacancy-gated target promotion mechanism in isolation on v003's clock base, producing a clean ablation relative to H01 (which combines both gates) and H02 (which adds the probing re-entry gate instead). The mechanism change has a second-order effect that does not exist in H02: by incrementing `lfu_counter` on non-hottest target hits, this variant gives items non-zero counters before they are evicted. The `clock_evict_prepare` pre-pass in `promote_to_target` (already present in v003) then becomes effective — warm target items that have accumulated at least one hit survive the next eviction pass, reducing unnecessary cold-item displacement. The two mechanisms (vacancy-gated early promotion and clock eviction sparing) are therefore mutually reinforcing in this variant, even though only the promotion gate is new code. The vacancy guard ensures gate fires never cause cascade evictions, matching the structural safety property that has held across every winning promotion-gate variant since Cycle 3.
