# H02

Changing `ClassicLRU::promotion_candidate_index` from MRU-position selection to maximum-`lfu_counter` selection will promote the most-frequently-accessed target item to probing instead of the most recently accessed, improving hit rate on cycle/0006/v001.

## Parent

cycle/0006/v001

## Changes

In `src/shared/eviction_policy.rs`, modify `ClassicLRU::promotion_candidate_index`. The current implementation returns `items.len() - 1` (the MRU/back position, updated by `get_from_position` on every hit):

```rust
fn promotion_candidate_index(&self, items: &[Item<K, V>]) -> usize {
    items.len() - 1
}
```

Replace with a scan that returns the index of the item with the highest `lfu_counter`:

```rust
fn promotion_candidate_index(&self, items: &[Item<K, V>]) -> usize {
    items
        .iter()
        .enumerate()
        .max_by_key(|(_, item)| item.lfu_counter)
        .map(|(i, _)| i)
        .unwrap_or(items.len() - 1)
}
```

Rust's `max_by_key` returns the LAST maximum when counters are equal, so the behaviour on a bucket where all items have `lfu_counter == 0` (all new items) degenerates to `items.len() - 1` — identical to the current policy. No test changes are required to preserve existing test semantics.

`ClassicLRU::eviction_candidate_index` (minimum `lfu_counter` scan) and `get_from_position` (move to back on hit) are unchanged.

This overlay must include all three files from cycle/0006/v001's overlay: `src/shared/item.rs` (unchanged), `src/shared/eviction_policy.rs` (modified as above), and `src/dash/segments/dash_segment.rs` (unchanged). Carry forward every file the parent overlaid to avoid the silent struct-footprint regression seen in cycle 0004.

## Rationale

The current design uses frequency at the bottom of the bucket (LFU-min eviction) and recency at the top (MRU-position promotion). On a Zipfian workload, recency and frequency are strongly correlated for the hottest items, but they can diverge: if two popular items alternate accesses, the one that was hit last is at the MRU position and would promote, while the one with the higher cumulative frequency stays in target. Selecting by max frequency instead ensures the item with the strongest access evidence earns the probing slot, which is the tier it would most benefit from (higher hit-rate when re-accessed, fewer eviction events). The per-bucket scan cost is the same O(n) as the already-present eviction scan, so no new latency class is introduced.
