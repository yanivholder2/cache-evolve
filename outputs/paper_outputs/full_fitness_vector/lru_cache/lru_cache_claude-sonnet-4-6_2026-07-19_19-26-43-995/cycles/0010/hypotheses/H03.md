# H03

Deferring the protected→probationary demotion from the `get()` hot path to the `put()` eviction path via a single-bit pending-demotion flag encoded in the existing `Node.links[1]` field allows the protected quota to be tightened to 90% (capacity/10 probationary) without regressing get p50 latency.

## Parent

cycle/0007/v002

## Changes

This is a **structural mechanism change**, not a quota-only change. Previous cycle 0007–0009 attempts to exceed 87.5% all failed because the eager demotion sequence (unlink protected-LRU, insert into probationary tail) executed on the `get()` hot path every time a probationary hit promoted an item and the protected queue overflowed. This hypothesis decouples the quota from the per-get cost by deferring that work to the `put()` path, which already pays eviction costs.

**Implementation steps:**

1. **Steal bit 31 of `links[1]` as a demotion-pending flag.** Define at module scope:

   ```rust
   const DEMOTION_FLAG: u32 = 1 << 31;
   ```

   Define two inline helpers that mask the flag away when reading the actual index:

   ```rust
   #[inline(always)]
   fn next_idx(node: &Node<K, V>) -> u32 { node.links[1] & !DEMOTION_FLAG }

   #[inline(always)]
   fn is_pending_demotion(node: &Node<K, V>) -> bool { node.links[1] & DEMOTION_FLAG != 0 }
   ```

   Update every read of `node.links[1]` as an index throughout the file to call `next_idx(node)` instead of `node.links[1]` directly. Capacity values in the benchmark suite are at most a few thousand, so bit 31 is always zero in the original code; stealing it is safe.

2. **Change the quota**: set `prob_cap = (capacity / 10).max(1)` (90% protected, 10% probationary). This is the only quota change; no other policy parameters are modified.

3. **Modify `get()` — lazy demotion**: when a probationary hit would cause the protected queue to overflow (i.e., `prot_len >= prot_cap` before the promotion step), check whether the protected queue's LRU tail already has `DEMOTION_FLAG` set:
   - **If no pending demotion exists** (flag is clear on the protected-LRU tail): instead of executing the full demotion sequence, simply set `DEMOTION_FLAG` on that node's `links[1]` field (one bitwise-OR, no pointer manipulation) and proceed with the promotion of the probationary item into the protected queue. Increment `prot_len` by 1 for the newly promoted item; do NOT decrement it for the deferred demotion — the protected queue now transiently holds `prot_cap + 1` items with one flagged.
   - **If a pending demotion already exists** (the protected-LRU tail already has the flag): fall back to immediate eager demotion — execute the full unlink-from-protected, push-to-probationary-tail sequence synchronously on the get path. This ensures at most one item at a time carries the flag, bounding the transient over-capacity state to a single node.

4. **Modify `put()` — deferred demotion finalisation**: at the beginning of the eviction logic in `put()` (before selecting a probationary victim), check whether the protected queue's current LRU tail has `DEMOTION_FLAG` set. If so, finalise the deferred demotion now: clear the flag, unlink the node from the protected queue (update its predecessor's and successor's links), decrement `prot_len`, and push the node to the probationary MRU tail (incrementing the probationary size and triggering a further probationary eviction if that overflows). This moves the linked-list manipulation cost from `get()` to `put()`.

5. **Bookkeeping invariant**: `prot_len` is the count of nodes currently linked in the protected queue, including any with `DEMOTION_FLAG`. After lazy demotion is triggered, `prot_len == prot_cap + 1` transiently. After finalisation on the `put()` path, it returns to `prot_cap`. Code that checks `prot_len >= prot_cap` must be reviewed to ensure the transient over-cap state does not trigger a second lazy demotion for the same item.

6. **Node layout**: no change to `Node` size — the flag reuses a bit within the existing `links[1]` field. `Node<u64,u64>` remains 16 bytes.

7. Leave the Node layout, the FNV-vs-SipHash choice, the probationary eviction policy (strict LRU/FIFO head eviction), and all other paths as in cycle/0007/v002.

## Rationale

Cycles 0007, 0008, and 0009 confirmed from three independent angles (intermediate quota, demotion batching, FNV-1a offset) that the quota-latency coupling at the current policy is structural: any demotion work on the `get()` hot path shows up immediately in get p50. The cycle 0009 insight explicitly asks whether a policy redesign that avoids "eager per-operation demotion enforcement" could break this coupling. This hypothesis answers that question directly: by paying a single bit-OR on the `get()` path and deferring the full pointer manipulation to `put()`, we decouple the protected quota from the per-get cost. At capacity/10 (90% protected), the expected hit-rate improvement from holding more items in the hot tier should surface without the get-latency penalty that defeated all previous quota attempts.
