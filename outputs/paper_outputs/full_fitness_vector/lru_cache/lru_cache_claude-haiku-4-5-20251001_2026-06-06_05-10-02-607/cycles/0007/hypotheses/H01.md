# H01

Implement batched queue-flush coalescing at put() to reduce put p99 latency while preserving the complete-deferral get-path gains, improving per-op-time.

## Parent

cycle/0004/v002

## Changes

Cycle 0006's v002 achieved a landmark 59% get p99 improvement (151→62 ns) by eliminating all drain logic from get() and deferring promotion work to put(). However, this creates a put p99 regression to 191 ns (from prior 173 ns) because put() must flush the entire pending_promotions queue before eviction. Optimize the queue-flush operation itself:

1. Preserve the complete deferred-promotion design from cycle 0006 v002: get() appends to queue, put() flushes before eviction.
2. Implement a multi-pass flush strategy in put() to coalesce consecutive puts: instead of fully draining the queue in a single blocking operation, process the queue in fixed-size batches (e.g., 16 promotions per batch). If multiple consecutive puts arrive while the queue is draining, coalesce their promotion batches to avoid repeated flush overhead.
3. Alternatively, divide the queue into a "current" batch and "pending" batch: the current batch drains during put(), while new promotions append to pending. On the next put() call, swap and drain.
4. Measure flush time and throughput: target reducing put p99 to ≤175 ns while maintaining get p99 ≤65 ns.
5. Preserve the promotion queue capacity and node metadata structure from v002; changes are algorithmic only (flush order and batching).

This targets the put-side cost of deferral without reintroducing checks on the hot path, directly addressing the cycle 0006 insight that put-latency regression may be tunable.

## Rationale

Cycle 0006 v002 proved complete deferral wins over incremental amortization (get p99 62 ns vs. v001's 130 ns). But it trades this for higher put latency (191 ns). The cycle 0006 insight poses: "Can deferred-work trade-offs be tuned closer to Pareto optimality?" This hypothesis tests whether the put-side cost is inherent to deferral (unavoidable) or avoidable through smarter queue-draining algorithms. Batched coalescing is orthogonal to whether work is deferred; it optimizes the mechanics of flushing without changing the deferral strategy. Success validates the put cost as tunable; failure confirms that deferral-to-put is a fundamental trade-off worth accepting for the get gains.
