# H02

Reduce get p99 latency regression in incremental queue draining by deferring drain triggers entirely to put operations, improving per-op-time metric.

## Parent

cycle/0005/v002

## Changes

Cycle 0005's V002 achieved 42% put p99 improvement (297→173 ns) by implementing incremental queue draining, but incurred 32% get p99 regression (114→151 ns) because the drain-trigger check and batch-draining logic intrudes on the get() fast path. Minimize get latency impact by eliminating drain responsibility from get():

1. Preserve the pending_promotions queue infrastructure and frequency bucketing logic from Cycle 0005 v002.
2. Remove the drain-trigger check and draining logic from get(). The get() function processes the node and appends to the queue, but does not check queue depth or invoke drains.
3. In put(), before eviction, perform the drain as in v002's current design (or expand it to flush more aggressively).
4. As a variant: instead of removing drain-during-get entirely, increase the drain-trigger threshold Q from 8 to a high value (e.g., 32 items) so drains almost never fire during get.
5. Empirically tune the drain threshold to maximize per-op-time (p50 latencies for both get and put).

The explicit trade-off: get p99 regression may be reduced or eliminated (potentially restoring the baseline ~114 ns), while put p99 may worsen compared to v002's 173 ns (but should remain competitive vs. Cycle 0004 baseline's 190 ns). The net per-op-time (which prioritizes get p50, currently 35 ns in v002) should improve by reducing get-path overhead.

## Rationale

Cycle 0005 v002 showed that deferral shifts cost between operations rather than eliminating it: get latency traded for put improvement. This hypothesis tests the hypothesis that the get-path drain logic is the source of the get regression. By moving drain responsibility entirely to put, we create a simpler trade-off: (a) reduce get latency via a cleaner fast path against (b) accept higher put latency (similar to Cycle 0004 v002's behavior). This is strategically distinct from H01, which attempts to amortize work across operations; H02 intentionally accepts put cost to optimize get, prioritizing the per-op-time metric which is dominated by get p50.
