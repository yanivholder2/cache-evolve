# H01

Replace per-operation saturation division with counter-sampled approximation to recover adaptive bucketing's tail-latency gains without median-latency regression.

## Parent

cycle/0003/v003

## Changes

Modify the adaptive bucketing decision logic in `should_use_bucketing()` to compute saturation asynchronously rather than on every operation. Introduce a `saturation_sample_count` counter that increments on each operation. When `saturation_sample_count` reaches a sample threshold (e.g., 32 or 64), compute the actual saturation level and reset the counter. Between sampling points, use the cached `saturation_state` (either "low" or "high"). This eliminates the division and comparison on every operation that caused Cycle 0008 V003's 31% get p50 regression, while preserving the 36% get p99 improvement from deferred-promotion activation when saturation is high. Adjust the sample threshold empirically to balance accuracy of saturation tracking against the overhead of per-operation counter increment.

## Rationale

Cycle 0008 V003 achieved a breakthrough 36% improvement in get p99 latency through saturation-aware deferred promotion, but the per-operation saturation check (saturation = nodes.len() / capacity) introduced uniform overhead that caused a 31% get p50 regression, negating the broader benefit. The overhead is not the logic itself, but the arithmetic cost on the fast path. By sampling saturation state asynchronously at configurable intervals (every N operations), the cost of computing actual saturation is amortized across multiple operations, reducing per-operation intrusion from a division+comparison to a single counter increment. This directly addresses Cycle 0008's open question: "Can V003's saturation check overhead be eliminated by computing it asynchronously?" If the saturation sample threshold is tuned correctly, the technique should recover the p99 gain while reducing the p50 regression.
