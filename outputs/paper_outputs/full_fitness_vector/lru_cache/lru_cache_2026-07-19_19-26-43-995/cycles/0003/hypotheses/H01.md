# H01

Adding an MRU-tail guard to the `promote()` function in the 2Q layout will eliminate redundant pointer writes on protected-queue hits that are already at the MRU end, reducing per-op-time without sacrificing hit rate.

## Parent

cycle/0002/v001

## Changes

In `promote()`, after reading `raw_prev` and detecting the protected-queue case (`(raw_prev & PROT_BIT) != 0`), add a short-circuit guard before calling `unlink` + `push_back_prot`:

```rust
if protected {
    // Guard: already at the MRU end of protected — nothing to do.
    if idx as u32 == self.prot_tail {
        return;
    }
    self.unlink(idx);
    self.push_back_prot(idx);
    // prot_len unchanged
```

The probationary-to-protected graduation branch (the `else` arm) is unchanged — it must always run because the node is moving between queues and `prot_len`/`prob_len` must be updated. Only the already-protected re-access path gets the guard.

The same guard should be applied symmetrically in `put()` when updating an existing key that is already protected and at the protected tail: check `(self.nodes[idx].prev & PROT_BIT) != 0 && idx as u32 == self.prot_tail` before calling `self.promote(idx)`, and skip the promote call if true (only update the value). This mirrors what cycle/0002/v002 demonstrated for the plain LRU tail.

Invariants to preserve:
- `prob_len + prot_len == self.map.len()` must hold after every call.
- `prot_tail` must always point to a valid protected-queue node (or `NULL` when empty).
- The `PROT_BIT` encoding in `prev` must remain consistent: do not clear or set it in the new guard branches.

No struct fields are added. Node stays at 24 bytes. All existing unit tests must continue to pass.
