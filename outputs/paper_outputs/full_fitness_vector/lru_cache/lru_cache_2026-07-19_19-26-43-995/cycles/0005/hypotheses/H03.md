# H03

Expanding the protected-queue quota from 75% to 87.5% of capacity in isolation on cycle/0002/v001 should raise hit rate on the Zipfian workload by shielding 256 additional entries from demotion pressure, with no new per-op branches and fewer demotion events at steady state.

## Parent

cycle/0002/v001

## Changes

Start from the exact `src/lru_cache/mod.rs` of cycle/0002/v001 and make exactly one change:

In `try_new()`, change:
```rust
let prob_cap = (capacity / 4).max(1);
```
To:
```rust
let prob_cap = (capacity / 8).max(1);
```

No other lines are modified.

**Effect on queue sizes at capacity=2048:**
- Before: `prob_cap = 512` (25% probationary), `prot_cap = 1536` (75% protected)
- After:  `prob_cap = 256` (12.5% probationary), `prot_cap = 1792` (87.5% protected)

**Invariants to preserve:** The protected-budget enforcement branch `if self.prot_len > prot_cap` in `promote()` remains correct because `prot_cap` is computed from the stored `prob_cap` and `capacity` fields at promotion time (`let prot_cap = self.capacity - self.prob_cap;`). No other constant or branch references `prob_cap` directly, so the single initializer change propagates correctly through all policy paths.

## Rationale

Cycle 0003/v002 confirmed that expanding the protected quota to 87.5% improves hit rate on this Zipfian workload, but that experiment was confounded by also composing the MRU-tail guard — a separate mechanism whose unconditional branch degraded per-op-time. This hypothesis isolates the quota change: cycle/0002/v001 already runs at per-op-time=0 with the 2Q policy and no guard. Enlarging the protected quota only affects how often the `prot_len > prot_cap` demotion branch fires — at steady state on a full Zipfian trace the protected queue fills quickly and then receives mostly existing-item refreshes, meaning more capacity means fewer demotions, not more. The common-path instruction sequence (protected hit: unlink + push_back_prot; probationary hit: unlink + push_back_prot) is identical to the parent; only the threshold that triggers an additional demotion step shifts upward. Per-op-time should remain at 0 while hit rate rises from the reduced demotion pressure on borderline-frequent items in the 1537–1792 rank range.
