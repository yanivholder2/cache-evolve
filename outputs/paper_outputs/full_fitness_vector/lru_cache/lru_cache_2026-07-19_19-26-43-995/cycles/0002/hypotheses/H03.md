# H03

Replacing the two-step `map.get()` + `map.insert()` lookup pattern in `put()` with a single `map.entry()` call, and annotating `unlink()` and `push_back()` with `#[inline(always)]`, will reduce put-path latency on cycle/0001/v002 by eliminating one hash computation per new-key insertion and removing function-call overhead on the get/put fast paths.

## Parent

cycle/0001/v002

## Changes

Start from v002's `src/lru_cache/mod.rs` and make the following two independent changes:

**1. Replace double HashMap lookup in `put()` with the entry API**

Current pattern in `put()`:
```rust
if let Some(&idx) = self.map.get(&key) {
    self.nodes[idx].value = value;
    self.unlink(idx);
    self.push_back(idx);
    return;
}
// ... compute idx via evict or push ...
self.push_back(idx);
self.map.insert(key, idx);
```

Replace with:
```rust
use std::collections::hash_map::Entry;
match self.map.entry(key) {
    Entry::Occupied(e) => {
        let idx = *e.get();
        self.nodes[idx].value = value;
        self.unlink(idx);
        self.push_back(idx);
    }
    Entry::Vacant(e) => {
        let idx = if self.nodes.len() >= self.capacity {
            // Evict LRU head — identical to current v002 eviction block
            debug_assert!(self.head != NULL, "head must be valid when arena is full");
            let head_idx = self.head as usize;
            let evicted_key = self.nodes[head_idx].key.clone();
            self.map.remove(&evicted_key);
            self.unlink(head_idx);
            self.nodes[head_idx].key = e.key().clone();
            self.nodes[head_idx].value = value;
            head_idx
        } else {
            let idx = self.nodes.len();
            self.nodes.push(Node {
                key: e.key().clone(),
                value,
                prev: NULL,
                next: NULL,
            });
            idx
        };
        self.push_back(idx);
        e.insert(idx);
    }
}
debug_assert!(self.map.len() <= self.capacity);
```

Note: `e.key()` returns a reference to the key stored inside the `Entry`, so `key.clone()` on an `Entry::Vacant` is the same as before. The `map.remove(&evicted_key)` call in the eviction branch still uses a separate lookup (unavoidable), but the net effect is: new-key put now performs one hash probe (Vacant insert) instead of two (get miss + insert). Existing-key put performs one hash probe (Occupied) instead of two (get hit + the implicit cost of the update).

**2. Add `#[inline(always)]` to `unlink()` and `push_back()`**

These two private methods are called on every `get()` and `put()`. Annotate each:
```rust
#[inline(always)]
fn unlink(&mut self, idx: usize) { ... }

#[inline(always)]
fn push_back(&mut self, idx: usize) { ... }
```

The bodies remain bit-for-bit identical to v002. The annotation ensures the compiler always inlines these small, hot functions regardless of optimization heuristics, eliminating call overhead and enabling better register allocation across the inlined call sites.

**Invariants preserved**: All u32 sentinel logic, capacity checks (`capacity > (u32::MAX as usize - 1)`), arena slot reuse, and map/list consistency guarantees from v002 are fully preserved. Only the call structure and lookup pattern change.

## Rationale

v002's put p50 regressed to 100 ns vs the baseline's 75 ns; the cast overhead from u32 operations was identified as one cause. A second, unaddressed cost is the double HashMap probe on every put: one `get()` to check existence, then one `insert()` for new keys. The `entry()` API folds these into a single hash computation for new keys (the common case in a cache under load). The `#[inline(always)]` hints address the call overhead for `unlink`/`push_back`, which together execute 8-10 pointer-field reads/writes per operation and are small enough that inlining typically pays off. These two changes are additive and target the put path specifically, which is where v002's latency regressed relative to baseline.
