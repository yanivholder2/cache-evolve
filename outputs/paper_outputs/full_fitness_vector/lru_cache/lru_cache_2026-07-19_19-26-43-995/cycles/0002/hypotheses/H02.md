# H02

Skipping the unlink+push_back cycle in `get()` when the found node is already the MRU tail will eliminate unnecessary pointer writes and reduce get p50 latency on the baseline LRU implementation.

## Parent

baseline

## Changes

In `src/lru_cache/mod.rs`, modify `LruCache::get()` to add a no-op shortcut before the existing promote path.

Current `get()` body (simplified):
```rust
pub fn get(&mut self, key: &K) -> Option<&V> {
    let &idx = self.map.get(key)?;
    self.unlink(idx);
    self.push_back(idx);
    Some(&self.nodes[idx].value)
}
```

Insert a guard immediately after the map lookup, before `unlink`:
```rust
pub fn get(&mut self, key: &K) -> Option<&V> {
    let &idx = self.map.get(key)?;
    // Fast path: already MRU — skip the two relinking calls.
    if self.tail == Some(idx) {
        return Some(&self.nodes[idx].value);
    }
    self.unlink(idx);
    self.push_back(idx);
    Some(&self.nodes[idx].value)
}
```

This is the only code change. No other methods, fields, or struct definitions are modified.

**Why this is correct**: If `idx` is already at the tail, it is already the most-recently-used node. Unlinking it and immediately re-appending it at the tail is a no-op in terms of LRU ordering — the relative order of every other node is unchanged. Returning without the relinking preserves exact LRU semantics.

**What it avoids**: Each call to `unlink()` writes to up to 3 node fields (`prev.next`, `next.prev`, and the unlinked node's own `prev`/`next`); `push_back()` writes to up to 3 more. For a hot item that is repeatedly `get()`-ed (common in Zipfian workloads), all six pointer writes can be bypassed.

**Invariants preserved**: `self.tail` is always the arena index of the last node in the chain. After the shortcut, `tail`, `head`, and all `prev`/`next` links remain unchanged, which is consistent with the node already being at the tail.

## Rationale

The baseline `get()` always performs two full list-manipulation calls regardless of whether the promotion is a real move or a self-loop. On workloads with high temporal locality (e.g., the top-N hot keys), repeated gets to the same key repeatedly traverse the no-op promote path. Eliminating those writes reduces both instruction count and cache-line dirtying on the nodes Vec. Baseline get p50 is 41 ns; even a 10–20% reduction would be meaningful. The change is a two-line addition with zero risk to correctness.
