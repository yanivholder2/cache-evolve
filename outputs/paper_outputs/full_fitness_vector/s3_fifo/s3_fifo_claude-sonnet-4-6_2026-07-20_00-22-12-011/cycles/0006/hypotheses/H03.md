# H03

Splitting cycle/0005/v003's unified resident_map<K,(V,u8)> into a compact freq_map<K,u8> and a separate data<K,V> map will reduce get() latency from 100 ns to 0 ns p50 by improving cache-line utilization on the hot frequency-update path, matching cycle/0005/v001's latency while retaining v003's 1/20 small-queue fraction.

## Parent

cycle/0005/v003

## Changes

Replace the single `resident_map: HashMap<K, (V, u8)>` field with two fields:
- `data: HashMap<K, V>` — stores the value for every resident key
- `freq_map: HashMap<K, u8>` — stores only the frequency byte for every resident key

This mirrors cycle/0005/v001's dual-HashMap layout but preserves v003's 1/20 small-queue fraction and all other v003 invariants.

**`S3Fifo` struct**: remove `resident_map`, add `data: HashMap<K, V>` and `freq_map: HashMap<K, u8>`.

**`try_new()`**: initialize both maps with `HashMap::with_capacity(capacity)`.

**`get()`**: probe `freq_map` first (mutable, updates frequency), then `data` (immutable, returns value reference):
```rust
pub fn get(&mut self, key: &K) -> Option<&V> {
    if let Some(freq) = self.freq_map.get_mut(key) {
        *freq = freq.saturating_add(1).min(MAX_FREQ);
    } else {
        return None;
    }
    self.data.get(key)
}
```

**`put()`**: resident-update check uses `self.data.contains_key(&key)` (or `self.data.get_mut`); on update, replace `entry.0 = value` with `self.data.insert(key, value); return;`. Ghost-hit and normal admission paths insert into both `data` and `freq_map` (freq initialized to 0), then push a key-only `Entry` into the relevant deque (same Entry struct as the parent with `_phantom: PhantomData<V>`).

**`evict_main()`**: read frequency via `self.freq_map.get(&tail.key).copied().unwrap_or(0)`, update via `self.freq_map.insert(tail.key.clone(), freq - 1)`, and on eviction call both `self.data.remove(&tail.key)` and `self.freq_map.remove(&tail.key)`.

**`evict_small()`**: same pattern — read frequency from `freq_map`, on ghost-path call `self.data.remove` and `self.freq_map.remove`.

The `Entry<K, V>` struct (key-only + `PhantomData<V>`), the `ghost` deque, `ghost_set` HashSet, `ghost_set`-based lazy tombstoning, the `evict_main()` unbounded second-chance loop, the `evict_small()` `freq > 1` promotion threshold, and the 1/20 small-queue fraction must all be preserved exactly as in the parent.

## Rationale

cycle/0005/v001 (dual HashMaps, 1/40 queue) achieves get p50 = 0 ns while cycle/0005/v003 (single resident_map, 1/20 queue) achieves get p50 = 100 ns. The difference: for Key=u64, V=u64 the `resident_map` stores `(u64, u8)` tuples (≈16 bytes per slot), whereas `freq_map` in v001 stores only `u8` values (≈9 bytes per slot). Fewer bytes per slot means more entries per cache line, reducing TLB and L1/L2 pressure on the hot `get()` frequency-bump path — the most frequent operation. This hypothesis isolates the data-layout variable by holding queue fraction constant (1/20, as in v003), letting us confirm or refute the cache-line hypothesis independently of queue sizing. The claim is falsified if get p50 does not drop below 100 ns, or if hit-rate regresses below v003's 0.7279.
