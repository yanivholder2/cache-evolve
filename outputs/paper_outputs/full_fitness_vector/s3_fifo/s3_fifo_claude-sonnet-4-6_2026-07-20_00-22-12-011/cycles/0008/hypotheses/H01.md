# H01

Restoring MAX_FREQ to 3 in cycle/0007/v003 will eliminate the evict_main() scan-depth regression introduced by MAX_FREQ=5 and recover per-op-time efficiency while preserving most of v003's hit-rate advantage over cycle/0005/v001.

## Parent

cycle/0007/v003

## Changes

In `src/s3_fifo/mod.rs`, change the single constant:

```rust
// Before:
const MAX_FREQ: u8 = 5;

// After:
const MAX_FREQ: u8 = 3;
```

No other code changes are needed. This restores the second-chance ceiling that cycle/0005/v001 used. With MAX_FREQ=3, each main-queue entry can defer eviction by at most 3 decrements (instead of 5), shortening the average evict_main() scan length. Cycle 0007 cycle-insight established that the hit-rate gain from MAX_FREQ=5 was marginal (Zipfian hot-set was already well-retained at cap=3), while the latency cost of deeper scans was the primary source of the per-op-time=100 regression in v003 relative to cycle/0005/v001's per-op-time=0. The resulting variant is expected to show hit-rate near v003's 0.7302 (or slightly below) and per-op-time near cycle/0005/v001's 0. All existing unit tests should pass unchanged since they do not test the MAX_FREQ constant value directly.

## Rationale

cycle/0007/v003's per-op-time=100 is entirely attributable to the MAX_FREQ=5 → deeper evict_main() loops. The cycle 0007 insight confirmed MAX_FREQ is an exhausted hit-rate lever on Zipfian; the only remaining benefit of v003 over v001 would be if the MAX_FREQ=5 protects some fraction of the hot set, but that benefit was measured as marginal (0.7302 vs 0.7292). Returning to MAX_FREQ=3 tests whether the per-op-time cost can be shed without giving up any material hit-rate.
