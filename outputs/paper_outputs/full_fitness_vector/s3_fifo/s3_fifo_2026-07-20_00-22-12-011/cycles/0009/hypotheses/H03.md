# H03

Guarding the frequency write in `get()` with a `< MAX_FREQ` check eliminates unnecessary cache-line dirtying on hot entries and lowers get p50 latency.

## Parent

cycle/0007/v003

## Changes

In `src/s3_fifo/mod.rs`, change only the `get()` function body. Replace the unconditional
`saturating_add(1).min(MAX_FREQ)` write with a conditional that skips the write when the entry
is already at the ceiling:

**Before** (cycle/0007/v003):
```rust
pub fn get(&mut self, key: &K) -> Option<&V> {
    if let Some(freq) = self.freq_map.get_mut(key) {
        *freq = freq.saturating_add(1).min(MAX_FREQ);
    } else {
        return None;
    }
    self.data.get(key)
}
```

**After**:
```rust
pub fn get(&mut self, key: &K) -> Option<&V> {
    if let Some(freq) = self.freq_map.get_mut(key) {
        if *freq < MAX_FREQ {
            *freq += 1;
        }
    } else {
        return None;
    }
    self.data.get(key)
}
```

No other code is modified. Preserve all invariants from cycle/0007/v003: `MAX_FREQ = 5`,
`small_size = capacity / 40`, the two-map layout (`data` + `freq_map`), `freq > 1` promotion
gate in `evict_small()`, `freq = 0` on ghost-hit admission, lazy ghost tombstoning, and the
key-only `Entry<K, V>` struct.

Eviction behaviour is unchanged: `evict_main()` reads `freq_map` independently, so entries
still accumulate up to MAX_FREQ and require up to MAX_FREQ second-chance decrements before
eviction. The only difference is that a `freq = MAX_FREQ` entry no longer has its `freq_map`
cache line dirtied on each subsequent `get()`.

## Rationale

The current `get()` always writes back to `freq_map` via `get_mut`, even when the computed
result (`freq.saturating_add(1).min(MAX_FREQ)`) is identical to the existing value. On a
Zipfian workload, the top-N hot entries quickly saturate to `MAX_FREQ = 5` and remain there for
the duration of the run. After saturation, every subsequent `get()` on a hot entry computes
`5.saturating_add(1).min(5) = 5` and writes `5` back to the same byte — dirtying the
`freq_map` cache line without changing any observable state. This unnecessary write marks the
line dirty in L1, adding write-back pressure to L2/L3 that competes with the `data` lookups on
the same operation. The conditional guard avoids this write entirely for maxed-out entries.
The branch is easily predicted (hot entries are always at MAX_FREQ in steady state), so the
guard itself adds negligible overhead while eliminating the spurious write on the majority of
hot-path gets.
