# H02

Repartitioning the 2048-slot capacity from 128×16 to 32×64 (fewer, wider buckets) reduces premature hash-collision eviction and raises hit rate on the LIRS workload-a trace.

## Parent

baseline

## Changes

Edit `src/shared/geometry.rs`. Change only `BaselineGeometry::layout()` — leave `for_settings`
and the struct fields intact so the construction glue in `factory.rs` (protected) continues to
call `for_settings` without modification.

Replace the current body of `layout`:
```rust
fn layout(&self, _total_capacity: usize) -> (usize, usize) {
    (self.num_of_buckets, self.bucket_size)
}
```

with one that ignores the harness-provided split and computes a fixed 32-bucket factorisation
from the actual `total_capacity` parameter:
```rust
fn layout(&self, total_capacity: usize) -> (usize, usize) {
    let num_buckets = 32_usize;
    let bucket_size = total_capacity / num_buckets;
    (num_buckets, bucket_size)
}
```

For the swept total capacity of 2048 this returns `(32, 64)`, satisfying the gate invariant
`32 * 64 == 2048`. Do not change `for_settings`, the struct definition, or any other file.

## Rationale

The baseline layout of 128 buckets × 16 slots is narrow: any key whose assigned bucket receives
17 distinct insertions before its entries are re-accessed will lose one item to eviction, even if
those items are hot in the global working set. With 32 buckets × 64 slots, a bucket must absorb
65 distinct cold keys before it ejects anything, giving temporally local access patterns (as
found in LIRS workload-a) far more room to breathe. The trade-off is broader hash fan-out: each
bucket now covers 4× more of the key space, so intra-bucket competition increases — but on a
skewed LIRS trace the hot fraction of the key space is small relative to 64 slots, making wider
buckets a net win.
