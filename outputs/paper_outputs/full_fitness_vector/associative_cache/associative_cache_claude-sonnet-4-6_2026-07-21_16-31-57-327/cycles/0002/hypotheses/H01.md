# H01

Replacing ClassicLRU's O(n) remove-and-push promotion with a descending-sorted LFU that bubbles left on access and evicts from the tail in O(1) will recover v001's hit-rate gain without the linear-scan latency penalty.

## Parent

baseline

## Changes

Modify `ClassicLRU` in `src/shared/eviction_policy.rs` to implement frequency-based eviction while maintaining a descending sort invariant on `lfu_counter` within the bucket's `Vec<Item<K,V>>`:

- **`get_from_position`**: increment `items[position].lfu_counter`, then bubble the item leftward via successive swaps as long as `items[pos].lfu_counter > items[pos - 1].lfu_counter` and `pos > 0`. Return the final settled index. For hot items already near position 0 this loop runs zero iterations; newly promoted items traverse only the distance needed to restore sort order.
- **`eviction_candidate_index`**: return `items.len() - 1` (the tail, which always holds the item with the lowest counter under the descending invariant). `items.remove(len-1)` in `remove_at` requires no element shifting — O(1).
- **`promotion_candidate_index`**: return `0` (the head, which always holds the item with the highest counter).

The descending sort invariant is maintained by construction: new items are `push`-ed at the tail by `put` with `lfu_counter = 0`, which is always ≤ the counters of existing items, so the invariant holds after insertion without any extra work. Existing `Lfu`, `TimestampLRU`, and all other policy implementations are left untouched.

## Rationale

v001 showed that frequency-based eviction raises hit rate on the LIRS scan-heavy trace by 9.4 percentage points, but its O(n) `min_by_key` / `max_by_key` scans for eviction and promotion candidates blocked the win on per-op-time. This variant eliminates both scans: eviction is always the tail (O(1) removal), promotion candidate is always the head (O(1) index), and the per-access bubble step is amortized O(1) on Zipfian workloads because hot items, once near the head, incur zero swaps on subsequent accesses.
