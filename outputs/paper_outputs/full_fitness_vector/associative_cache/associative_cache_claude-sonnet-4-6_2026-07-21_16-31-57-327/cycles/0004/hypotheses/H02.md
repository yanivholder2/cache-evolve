# H02

Removing all lfu_counter reads and writes from ClassicLRU::get_from_position and replacing them with an unconditional single-step position swap will reduce per-op-time by eliminating the read-modify-write field access on every non-position-0 get.

## Parent

cycle/0003/v003

## Changes

In `eviction_policy.rs`, modify `ClassicLRU::get_from_position` to perform a pure positional LRU swap with no field writes:

```rust
fn get_from_position(&self, items: &mut Vec<Item<K, V>>, position: usize) -> usize {
    if position == 0 {
        return 0;  // already hottest: zero writes (preserved from v003)
    }
    items.swap(position, position - 1);
    position - 1
}
```

The `lfu_counter` field remains in `Item<K, V>` — `item.rs` is not changed. The field simply starts at 0 and is never incremented; it does not affect behaviour. `eviction_candidate_index` stays `items.len() - 1`. All other policy impls (TimestampLRU, Lifo, Lfu, Fifo, Swap) are unchanged.

The net effect is a pure positional-LRU: the most-recently-accessed item advances one slot toward the head per access with exactly one `swap` call and no other memory writes beyond the position-0 guard check. Items gradually migrate toward position 0 through repeated accesses; the tail is always the eviction candidate.

No changes to `item.rs` — the 32-byte aligned struct from v003 is preserved.

## Rationale

Every variant across all three cycles has measured per-op-time at 100ns p50, well above the baseline's 69ns. The sole difference between ClassicLRU's get path and the baseline's is the `lfu_counter += 1` field write, which dirties the cache line regardless of whether a swap follows. Eliminating that write is the minimum intervention that could recover the baseline's latency floor. Hit rate will likely fall toward baseline LRU levels (≈0.661) since ordering becomes positional rather than frequency-based, but if per-op-time drops below the baseline's 69ns summary the trade-off may still improve the composite score.
