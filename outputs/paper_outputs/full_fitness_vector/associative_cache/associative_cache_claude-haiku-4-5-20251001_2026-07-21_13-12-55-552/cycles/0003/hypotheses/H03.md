# H03

Push to even wider buckets (32×64) to continue v002's hit-rate improvement trajectory, testing whether hit-rate gains continue to outpace latency cost as buckets widen further.

## Parent

cycle/0002/v002

## Changes

Modify `src/shared/geometry.rs` in the `BaselineGeometry::layout()` method. Extend v002's halving transformation to apply one more level, reaching 32×64 from baseline 128×16:

```rust
fn layout(&self, total_capacity: usize) -> (usize, usize) {
    // Wider buckets: halve buckets twice, double items twice, relative to baseline.
    // Preserve total capacity: num_buckets * bucket_size = total_capacity.
    // From 128×16 → 64×32 → 32×64
    let new_num_buckets = self.num_of_buckets / 4;
    if new_num_buckets == 0 {
        return (self.num_of_buckets, self.bucket_size);
    }
    if total_capacity % new_num_buckets == 0 {
        let new_bucket_size = total_capacity / new_num_buckets;
        (new_num_buckets, new_bucket_size)
    } else {
        (self.num_of_buckets, self.bucket_size)
    }
}
```

For baseline (128 × 16 = 2048), this yields 32 × 64 = 2048, preserving total capacity exactly.

Keep all other settings unchanged: eviction policy (ClassicLRU), all other cache parameters.

## Rationale

Variant v002 (64×32) improved hit-rate by +0.24% (0.6611 → 0.6635) and achieved overall fitness gain (-0.0877 vs. -0.0899) despite incurring -45% latency regression. This indicates that on this workload and fitness function, hit-rate improvements are weighted favorably enough to overcome latency costs.

This hypothesis continues in the same direction: even wider buckets (32×64) consolidate the cache into fewer, denser buckets. The rationale is that wider buckets reduce fragmentation and hash-table overhead further, potentially continuing the hit-rate improvement trend observed in v002.

The trade-off is latency: ClassicLRU's O(n) operations will be even more expensive on 64-item buckets than on 32-item buckets. However, if the pattern from v002 holds—that hit-rate gain outweighs latency cost in fitness—then 32×64 may achieve further fitness improvement.

This hypothesis tests whether the frontier continues to favor wider buckets, or whether v002's 64×32 is a local fitness maximum and 32×64 represents diminishing returns. It also probes the limits of ClassicLRU's scalability with large bucket sizes before hitting a wall.
