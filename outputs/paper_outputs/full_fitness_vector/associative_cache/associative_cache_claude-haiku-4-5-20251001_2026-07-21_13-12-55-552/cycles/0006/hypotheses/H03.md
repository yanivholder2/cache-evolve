# H03

Partition each bucket into hot (working-set) and cold (infrequent) segments with different eviction strategies to reduce per-operation cost on the critical path while preserving hit-rate.

## Parent

baseline

## Changes

Modify `AssociativeCacheBucket` to maintain two separate `Vec<Item<K, V>>` instead of one: `items_hot` (capacity 60% of bucket size) and `items_cold` (capacity 40% of bucket size).

Add a `frequency_count` (u8) field to each `Item<K, V>`. On every get operation, increment the frequency count of the accessed item. Decay all frequency counts every 32 operations (divide by 2, rounded down).

During `get_position()`, search in both vectors (hot first, then cold). When found, if the item is in `items_cold` and its frequency ≥ 1, promote it to `items_hot` (move from cold Vec to hot Vec), evicting the lowest-frequency item from hot if needed.

During `evict_one()`, apply different strategies:
- If `items_cold` is not empty, prefer to evict from cold using FIFO (oldest insertion order)
- Only evict from hot if cold is empty or hot occupancy is >80%
- For hot items, continue using ClassicLRU's existing policy (track position for recency)

This creates a two-tier cache: hot segment uses ClassicLRU's per-hit bookkeeping (justified for working-set items), cold segment uses simple FIFO (no per-hit cost). The adaptive promotion mechanism learns which items are actually hot.

## Rationale

Cross-cycle analysis shows per-hit bookkeeping overhead is the dominant latency bottleneck (ClassicLRU's O(n) vector manipulation beats O(1) alternatives despite worse asymptotic complexity). Cycle 0005 confirmed that micro-optimizations alone cannot overcome this; the next step is algorithmic. This hypothesis proposes a hybrid strategy: apply expensive per-hit tracking only to the working set (items accessed >1× per 32 ops), leaving cold items to FIFO (which requires no bookkeeping). If the workload is strongly Zipfian (cycle 0005 confirmed this), the hot/cold split should capture most accesses in the small hot segment, amortizing ClassicLRU's cost and reducing total latency. Hit-rate should be unaffected (policy semantics don't matter for Zipfian, per cross-cycle findings), but latency should improve by reducing overhead on cold items.
