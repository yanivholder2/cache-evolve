# H02

Apply early-exit optimization exclusively to the eviction path to test whether micro-optimization benefits are viable on the less-common put operations without the full implementation overhead that hindered backporting in cycle 0005.

## Parent

baseline

## Changes

In the put() method, specifically within the code path that executes when a bucket is full and eviction is required, add early-termination logic: iterate through bucket items to find the least-recently-used candidate for eviction, and stop the scan immediately after identifying it rather than continuing to scan remaining items. Preserve the hit-path (get() method) completely unchanged—do not apply early-exit to hit-time searches. Keep the 128×16 bucket geometry and ClassicLRU eviction policy identical to baseline. The goal is to reduce the latency of put operations (which trigger eviction) without the compile-time or cache-layout side effects that affected attempts to optimize the more-frequent get path in cycle 0005.

## Rationale

Cycle 0004 v003 succeeded with early-exit on item search, but cycle 0005 failed to generalize this optimization to baseline 128×16 geometry. The failure in cycle 0005 applied early-exit to the common get-path, incurring overhead that hurt latency. This hypothesis tests whether early-exit is beneficial only when the hot path (hits) is optimized or whether the rarer eviction path can also benefit without incurring side effects. Eviction is less latency-critical than hits but still worth optimizing if the implementation cost is minimal. This pursues Path B (orthogonal micro-optimization) by targeting a different code path than prior attempts.
