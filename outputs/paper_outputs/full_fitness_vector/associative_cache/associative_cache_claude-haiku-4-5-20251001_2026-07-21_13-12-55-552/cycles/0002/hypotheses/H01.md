# H01

Switch to TimestampLRU eviction policy to eliminate ClassicLRU's expensive item repositioning while maintaining recency-awareness, targeting per-op-time improvement without harming hit-rate.

## Parent

baseline

## Changes

Modify `src/associative_cache/associative_cache_settings.rs` in the `Default` implementation: change the `eviction_policy` field from `EvictionPolicyKind::ClassicLRU` to `EvictionPolicyKind::TimestampLRU`.

TimestampLRU is already implemented in `src/shared/eviction_policy.rs` and differs from ClassicLRU in a critical way: on each cache hit, TimestampLRU only updates a timestamp field on the accessed item (single field assignment) rather than removing the item and appending it to the back of the bucket (O(n) vector operation). Eviction still targets the item with the oldest timestamp, preserving the recency-based eviction semantic.

This structural difference should eliminate the item-movement overhead that ClassicLRU incurs. By removing the expensive remove-and-push cost while retaining recency information, TimestampLRU should deliver lower per-operation latency. Hit-rate should remain stable because the eviction strategy—prioritizing items by recency—is unchanged; only the bookkeeping is lighter-weight.

Keep all other settings unchanged: bucket geometry (128 buckets × 16 items), bucket implementation, and all other cache parameters.

## Rationale

ClassicLRU achieves 0.6611 hit-rate with stable latency (69ns p50 get), but the `get_from_position()` method removes an item and pushes it to the back on every hit. This is an O(n) operation in the bucket's item vector. TimestampLRU implements the same recency-based eviction policy but with O(1) per-hit bookkeeping: only a single timestamp field update. On Zipfian workloads where hot items are accessed frequently, the per-access cost of ClassicLRU's vector manipulations dominates baseline latency. Replacing it with a timestamp-only approach preserves the proven recency-only strategy while reducing constant-factor overhead. This directly addresses the lesson from cycle 0001: added semantics (LFU, Swap) hurt latency; this variant adds no new semantics, only faster bookkeeping for an existing strategy.
