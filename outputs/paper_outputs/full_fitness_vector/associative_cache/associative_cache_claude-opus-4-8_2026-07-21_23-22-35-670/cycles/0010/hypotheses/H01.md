# H01

Port cycle/0009/v002's packed `u64` reuse-mask onto v001's integer-hash bucket to collapse v001's `put`/`get` p99 tails to the 100ns floor while holding its record 0.7272 hit-rate, targeting per-op-time.

## Parent

cycle/0009/v001

## Changes

v001 currently carries the scan-resistance reuse set as a parallel
`reuse: Vec<bool>` inside `AssociativeCacheBucket`
(`src/associative_cache/associative_cache_bucket.rs`), which forces a second
heap-vector shift (`reuse.remove(position)` + `reuse.insert(index, bit)`) on
every hit and a linear `for … if !reused` scan on every eviction — that is why
v001's `get` p99 and `put` p50 sit a bucket above the parent (200ns) even though
its FastHasher gives it the best measured hit-rate (0.7272).

Replace the `Vec<bool>` representation with the `u64` bitmask representation
proven bit-for-bit equivalent in cycle/0009/v002. Concretely, in
`associative_cache_bucket.rs`:

- Swap the `reuse: Vec<bool>` field for `reuse_mask: u64` and add the two free
  functions `mask_remove(mask, p)` and `mask_insert_set(mask, i)` exactly as in
  cycle/0009/v002 (close/open a one-bit gap, mirroring `Vec::remove`/`insert`).
- `put`: on a fresh push, clear bit `idx` (`reuse_mask &= !(1u64 << idx)`)
  instead of `reuse.push(false)`.
- `get_from_position`: after the policy relocates `position → index`, set
  `reuse_mask = mask_insert_set(mask_remove(reuse_mask, position), index)` in
  place of the `remove`/`insert`/`= true` triple.
- `eviction_candidate_index`: compute `live = u64::MAX >> (64 - len)`,
  `unreused = !reuse_mask & live`, return `Some(unreused.trailing_zeros())` when
  non-zero else `Some(0)`, replacing the linear scan.
- `remove_at`: `reuse_mask = mask_remove(reuse_mask, index)` before
  `items.remove(index)`.
- Add the `debug_assert!(bucket_size <= 64)` in `new()`.

Keep v001's `src/shared/utils.rs` FastHasher and every other file byte-for-byte
unchanged — the point is to inherit v001's hash-driven 0.7272 distribution while
paying v002's all-register maintenance cost. Because the mask splice mirrors the
single-element relocation exactly, hit-rate must hold at 0.7272 bit-for-bit;
only the two heap-vector tails move down to the 100ns floor.

## Rationale (optional)

v001 owns the hit-rate record and v002 owns the latency floor, but neither owns
both. The two changes are orthogonal (hash vs. reuse-set representation), so
composing them should yield a strict Pareto improvement over every current
incumbent at the 16-byte metadata floor.
