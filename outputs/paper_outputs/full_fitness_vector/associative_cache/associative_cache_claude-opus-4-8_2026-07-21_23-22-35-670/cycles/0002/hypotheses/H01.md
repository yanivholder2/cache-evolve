# H01

Stacking v003's timestamp-field removal onto the v002 hit-rate winner cuts `Item<u64,u64>` metadata from 40 to 24 bytes while preserving its 0.727 hit rate.

## Parent

cycle/0001/v003

## Changes

Cross-breed the two cycle-0001 winners: take v003's slimmed `Item` layout
(the parent already dropped the `timestamp: Instant` field, giving
`Item<u64,u64>` = key(8)+value(8)+lfu_counter(8) = 24 bytes) and graft
v002's scan-resistant `ClassicLRU` onto it.

Concretely, in `src/shared/eviction_policy.rs` replace this variant's
`ClassicLRU` implementation with v002's version:
- `get_from_position` still does `remove(position)` + `push`, then
  additionally `items.last_mut().unwrap().lfu_counter += 1` to mark the
  reused item as protected.
- `eviction_candidate_index` returns
  `items.iter().position(|it| it.lfu_counter == 0).unwrap_or(0)` — evict
  the first never-reused (one-hit-wonder) entry in LRU-front order, else
  fall back to the classic front.

Do not reintroduce the `timestamp` field or any `Instant` use — keep
v003's 24-byte layout, so any policy that referenced `timestamp` (e.g.
`TimestampLRU`) must remain in the FIFO-fallback form v003 left it in.
Preserve every `EvictionPolicyKind` name/index/ordinal so the JNI
contract is unchanged. Target dimension: metadata-size (24 instead of
40) while holding v002's hit-rate gain.

## Rationale (optional)

v002 owns hit-rate (0.727) but still carried the dead `timestamp` field
(metadata 40); v003 owns metadata (24) but only baseline hit rate. The
two changes touch disjoint parts of the code (`Item` layout vs.
`ClassicLRU` scan logic) and the reuse flag lives in `lfu_counter`, which
v003 kept — so the combination should be additive with no interaction.
