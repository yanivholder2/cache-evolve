# H03

Set the SLRU protected cap to a mid-range `3*max_size/4` to lift hit-rate by retaining reused items longer against scan pressure, without degenerating into LRU.

## Parent

cycle/0006/v001

## Changes

The protected-cap knob has been falsified at both extremes: `max_size/2` (this parent, aggressive — demotes real winners) and `max_size - 1` (cycle/0007/v003, near-total — degenerates the two segments into a single LRU list and loses scan-resistance). The strictly-mid-range setting between those walls is the one hit-rate lever the cross-cycle and cycle-7 insights flag as unexplored.

In src/associative_cache/associative_cache_bucket.rs, change `protected_cap`:

```
fn protected_cap(&self) -> usize {
    std::cmp::max(1, self.max_size * 3 / 4)
}
```

This sits strictly between `max_size/2` and `max_size - 1` (e.g. for `bucket_size = 8`: 6, versus 4 and 7). Change nothing else — `put`, `get_from_position`, front-admission, and `protected_len` bookkeeping stay exactly as the parent. A larger protected segment holds reused items against probationary scan churn longer than `max/2` does, while still reserving a real probationary zone (`max_size/4` slots) so segmentation does not collapse toward LRU the way `max_size - 1` did. Preserve invariants: the cap stays an off-`Item` bucket-struct computation so metadata holds at the 16-byte floor; the probationary front (index 0) remains the eviction target. Target dimension: hit-rate. Watch per-op-time — a deeper protected segment lengthens protected-MRU rotations, so this is a hit-rate-for-latency probe, expected to hold the per-op p50 summary at the floor.
