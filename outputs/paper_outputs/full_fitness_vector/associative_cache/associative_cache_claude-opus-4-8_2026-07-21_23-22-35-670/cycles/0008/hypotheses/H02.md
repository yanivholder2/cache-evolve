# H02

Replace the O(n²) key-matched reuse-vector rebuild with an index-preserving remove+insert to collapse the best-hit-rate incumbent's p99 tails while holding its hit-rate and 16-byte floor.

## Parent

cycle/0003/v001

## Changes

The parent carries scan-resistance in a parallel `reuse: Vec<bool>` and reaches the best hit-rate on record (0.7267), but every `get_from_position` snapshots `before: Vec<(K, bool)>` and calls `realign_reuse`, which linear-searches `before` per item — an O(n²) per-hit tax that shows up purely as blown-out p99 tails.

In src/associative_cache/associative_cache_bucket.rs, rewrite `get_from_position` to mirror the policy's single-element relocation directly onto `reuse` instead of rebuilding it:

```
fn get_from_position(&mut self, position: usize) -> &Item<K, V> {
    let index = self.eviction_policy.get_from_position(&mut self.items, position);
    let bit = self.reuse.remove(position);
    self.reuse.insert(index, bit);
    self.reuse[index] = true;
    &self.items[index]
}
```

Delete the now-unused `realign_reuse` method and the `before` snapshot. This is the exact fix cycle/0004/v001 proved works (clean p99, hit-rate bit-for-bit held), except anchored on this parent to avoid the trap that sank that variant: cycle/0004/v001 regressed metadata-size to 40 because its single-file overlay silently dropped the trimmed `Item`. Preserve invariants: keep the parent's trimmed `Item` (key+value only — do NOT reintroduce `lfu_counter`/`timestamp`) so metadata stays at 16; keep `eviction_candidate_index`, `put` (`reuse.push(false)`), and `remove_at` unchanged so `reuse[i] ↔ items[i]` and eviction decisions are identical. Target dimension: per-op-time (p99), holding hit-rate and metadata-size.
