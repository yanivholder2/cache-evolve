# H02

Flattening the CountMinSketch counter table from a `Vec<Vec<u32>>` (depth+1 separate heap allocations) to a single contiguous `Vec<u32>` with stride-based indexing reduces allocation overhead and improves cache-line utilization to lower per-op-time.

## Parent

baseline

## Changes

The baseline `CountMinSketch` stores rows as `counts: Vec<Vec<u32>>` — an outer `Vec` of `SKETCH_DEPTH` inner `Vec`s each of length `width`. Each inner `Vec` is a separate heap allocation with its own pointer, length, and capacity header. On the hot path, `increment` and `estimate` access one slot per row; with 4 rows pointing to 4 disparate allocations, the CPU must chase 4 pointers before reaching counter data.

Replace with a single flat allocation:

1. Change the field in `CountMinSketch` from `counts: Vec<Vec<u32>>` to `counts: Vec<u32>`. The logical layout is row-major: row `r`, column `c` maps to flat index `r * self.width + c`.

2. In `CountMinSketch::new`, change the initializer from:
   ```rust
   let counts = vec![vec![0; width]; depth];
   ```
   to:
   ```rust
   let counts = vec![0u32; depth * width];
   ```

3. In `heap_bytes`, update to:
   ```rust
   self.counts.len() * std::mem::size_of::<u32>()
   ```
   (numerically identical to the old `depth * width * 4`, but now correctly reflects the flat allocation).

4. In `increment`, change each row's counter access from:
   ```rust
   let counter = &mut self.counts[row][pos];
   ```
   to:
   ```rust
   let counter = &mut self.counts[row * self.width + pos];
   ```

5. In `estimate`, change:
   ```rust
   self.counts[row][self.position(key, row as u64)]
   ```
   to:
   ```rust
   self.counts[row * self.width + self.position(key, row as u64)]
   ```

6. The `position` function, the `CountMinSketch` `width` and `depth` fields, and all cache code (`get`, `put`, `unlink`, `push_back`, the JNI boundary, and the node layout) are unchanged.

## Rationale

Accessing `self.counts[row][pos]` requires the CPU to: load the outer Vec's data pointer, offset by `row`, dereference to get the inner Vec's data pointer, then offset by `pos`. With 4 rows, this is 4 independent pointer loads from potentially different cache lines. The flat layout collapses this to one load of the base pointer plus an integer multiply-add, and the stride between rows (`width * 4` bytes = 32 KB for cap-2048) means each row still fits a separate cache region while the single allocation eliminates the 4 indirection layers. The multiply `row * self.width` is cheap (shift for power-of-two widths) and the compiler may auto-vectorize or unroll the 4-row loop.
