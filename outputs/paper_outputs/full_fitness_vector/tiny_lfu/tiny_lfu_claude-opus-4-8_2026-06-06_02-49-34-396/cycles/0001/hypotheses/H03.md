# H03

Storing sketch counters as saturating `u8` instead of `u32` shrinks the fixed sketch metadata 4× (65536→16384 bytes) with negligible hit-rate loss.

## Parent

baseline

## Changes

In `src/tiny_lfu/mod.rs`, the `CountMinSketch.counts` table is `Vec<Vec<u32>>`,
costing `depth * width * 4` bytes (65536 at the evaluated capacity). Narrow the
counter element type to `u8`.

Concretely: change `counts` to `Vec<Vec<u8>>`; change the `MAX_COUNT` constant
used by the sketch to `u8::MAX` (255) or introduce a sketch-local cap so
`increment()` saturates at 255 instead of `u32::MAX`. Update `increment()` to
operate on `u8` counters with the same `if *counter < MAX { *counter += 1 }`
saturating guard. Update `estimate()` to return the minimum as before but widen
the returned `u8` to `u32` (e.g. `... .min().map(|c| c as u32).unwrap_or(0)`) so
the `put()` admission comparison `incoming_freq > victim_freq` continues to type-
check unchanged. Update `heap_bytes()` so it reflects `size_of::<u8>()` (the
existing `std::mem::size_of::<u32>()` must become `size_of::<u8>()`) — this is
what the metadata-size fitness bin reads.

Do not change `depth`, `width`, the LRU list, or admission ordering. The relative
ordering of frequencies is preserved for all keys whose true frequency is below
255 (the overwhelming majority under the evaluated trace), so hit-rate should be
essentially unchanged. All three invariants hold: counter width does not affect
which keys are resident, their stored values, or the capacity bound.

## Rationale (optional)

Real-world TinyLFU uses 4-bit counters; `u32` is far wider than admission needs.
This directly targets the metadata-size dimension (sketch heap 65536 bytes) and
is a clean, low-risk first step toward even tighter packing in later cycles.
