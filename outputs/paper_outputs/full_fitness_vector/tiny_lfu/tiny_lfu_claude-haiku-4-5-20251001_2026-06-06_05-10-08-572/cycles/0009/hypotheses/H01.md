# H01

Increase frequency-aware victim selection pool from N=2 to N=3 to improve hit-rate by capturing more frequency diversity without matching N=5's latency cost.

## Parent

cycle/0008/v003

## Changes

In `src/tiny_lfu/mod.rs`, in the victim selection loop within the `put()` method (around line 103-117 based on prior cycles), extend the loop that scans additional candidates from 1 iteration to 2 iterations:

```rust
// Old:
for _ in 0..1 {
    if let Some(idx) = current {
        // ... frequency comparison
    }
}

// New:
for _ in 0..2 {
    if let Some(idx) = current {
        // ... frequency comparison (unchanged logic)
    }
}
```

This evaluates 3 total candidates (LRU head + 2 scanned items) instead of 2, maintaining the existing minimum-frequency selection logic. Keep the sketch geometry (depth=3, width=3 inherited from parent), admission threshold (`incoming_freq > victim_freq`), and all other eviction mechanics unchanged.

## Rationale

Cycle 0006 proved that N=2 frequency-aware selection is superior to N=1 (pure LRU), achieving 30% p99 latency reduction with negligible hit-rate loss. Cycle 0008 confirmed that sketch geometry (depth-3, width-3) has reached a hard frontier below which hit-rate degrades sharply. However, the eviction pool size parameter remains under-explored between N=2 and N=5: cycle 0006 showed N=5 causes catastrophic tail-latency spikes (1200+ ns p99), but N=3 and N=4 are untested. This hypothesis conservatively extends the proven N=2 strategy by only 50% (+1 candidate evaluation), testing whether slightly deeper frequency-awareness captures additional diversity without matching N=5's latency pathology. Targets hit-rate directly while preserving the stable per-operation profile of cycle/0008/v003 (per-op-time=73ns, p99=166ns on get).
