Extend frequency-aware victim pool from N=3 to N=4 to test the upper bound of victim candidate scanning while remaining well clear of N=5's catastrophic tail latency.

## Parent

cycle/0009/v001

## Changes

In `src/tiny_lfu/mod.rs`, in the `put()` method, extend the victim scanning loop from 2 additional candidates to 3 additional candidates (lines 106-115):

```rust
// Old (N=3 total: LRU head + 2 scanned):
let mut current = self.nodes[victim_idx].next;
for _ in 0..2 {
    if let Some(idx) = current {
        let freq = self.sketch.estimate(&self.nodes[idx].key);
        if freq < victim_freq {
            victim_idx = idx;
            victim_freq = freq;
        }
        current = self.nodes[idx].next;
    }
}

// New (N=4 total: LRU head + 3 scanned):
let mut current = self.nodes[victim_idx].next;
for _ in 0..3 {
    if let Some(idx) = current {
        let freq = self.sketch.estimate(&self.nodes[idx].key);
        if freq < victim_freq {
            victim_idx = idx;
            victim_freq = freq;
        }
        current = self.nodes[idx].next;
    }
}
```

Keep the sketch geometry (SKETCH_DEPTH=2, SKETCH_WIDTH_FACTOR=3), admission logic (`incoming_freq > victim_freq`), and all other LRU mechanics unchanged.

## Rationale

Cycle 0006 established N=2 as superior to N=1 (pure LRU), achieving 30% p99 latency reduction. Cycle 0009 v001 showed N=3 yields +0.37% hit-rate improvement at tolerable cost (+119 ns p99 put). However, the boundary between optimality and catastrophe (cycle 0006 v001 showed N=5 causes 96% p99 spike) remains under-explored. N=4 represents a conservative extension (+1 candidate) to test whether deeper frequency diversity continues to yield marginal hit-rate gains or if diminishing returns tighten. The hypothesis directly addresses the cross-cycle insight: "What is the upper bound on N for victim selection?" This tests a checkpoint between proven N=3 and known-pathological N=5.
