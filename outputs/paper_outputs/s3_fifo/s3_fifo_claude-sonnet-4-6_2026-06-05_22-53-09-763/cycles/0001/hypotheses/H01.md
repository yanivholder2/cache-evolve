# H01

Shrinking the small queue to ~10% of capacity (instead of 25%) enlarges the main queue's resident footprint and raises hit rate on workloads with working sets that exceed the baseline main-queue capacity.

## Parent

baseline

## Changes

In `try_new()` in `src/s3_fifo/mod.rs`, change the `small_size` calculation from

```rust
let small_size = if capacity == 1 {
    1
} else {
    (capacity / 4).max(1).min(capacity - 1)
};
```

to

```rust
let small_size = if capacity == 1 {
    1
} else {
    (capacity / 10).max(1).min(capacity - 1)
};
```

`main_size` remains `capacity - small_size`, so for a 2048-slot cache this grows main from 1536 → 1843 slots (+307 resident slots). All other logic — ghost capacity (still `main_size`), eviction thresholds, promotion paths — stays unchanged.

## Rationale

The original S3-FIFO paper benchmarks suggest 10% small is often superior for workloads with temporal locality. The baseline's 25% small wastes resident capacity on the admission filter at the expense of the longer-lived main queue, which is where second-chance promotion keeps popular items alive. A smaller small queue means more capacity for resident items, reducing main-queue pressure and the rate at which popular items are evicted.
