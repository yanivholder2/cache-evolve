# H03

Dynamically adjusting the main-queue second-chance threshold based on the observed main-hit ratio allows the cache to self-tune across access phases and improve hit rate beyond what the static `freq > 1` gate in cycle/0006/v001 achieves.

## Parent

cycle/0006/v001

## Changes

Add two `u64` counters to the `S3Fifo` struct: `main_hits` and `total_gets`. Also add a `u8` field `evict_thresh` initialised to `1` (matching v001's static gate). Add a `u64` constant `ADAPT_PERIOD = 2048` (one full cache capacity worth of accesses, tunable).

In `get()`, increment `total_gets` on every call. When the hit is found in main (not small), also increment `main_hits`. After incrementing `total_gets`, check `if self.total_gets % ADAPT_PERIOD == 0 { self.adapt_threshold(); }`.

Implement `adapt_threshold(&mut self)`:
```rust
fn adapt_threshold(&mut self) {
    // main-hit ratio over the last ADAPT_PERIOD gets
    let ratio = self.main_hits as f64 / ADAPT_PERIOD as f64;
    // Reset window counters for the next period
    self.main_hits = 0;
    // If main is frequently serving hits, it is healthy — keep the threshold loose
    // so warm items survive longer.  If main hit rate is low, tighten the gate to
    // flush cold items faster.
    self.evict_thresh = if ratio >= 0.60 {
        0  // lenient: reprieve freq >= 1 items (freq > 0)
    } else if ratio >= 0.45 {
        1  // default: reprieve freq >= 2 items (freq > 1, same as v001)
    } else {
        2  // aggressive: reprieve only freq >= 3 items (freq > 2)
    };
}
```

In `evict_main()`, replace the hard-coded literal `1` in the condition `if tail.freq > 1` with `self.evict_thresh`:
```rust
fn evict_main(&mut self) {
    while let Some(mut tail) = self.main.pop_back() {
        if tail.freq > self.evict_thresh {
            tail.freq -= 1;
            self.main.push_front(tail);
        } else {
            break;
        }
    }
}
```

All other v001 parameters are unchanged: `small_size = capacity / 10`, `ghost_size = main_size / 2`, `MAX_FREQ = 5`, promotion threshold `freq > 1` in `evict_small`, move-to-front in `evict_main`. The `evict_thresh` starts at `1` so the initial behaviour is identical to v001 before the first adaptation fires.

Preserve the unit tests from v001 (they use the default threshold of 1, so they pass without modification). Add a new test that manually sets `evict_thresh = 0` or `2` and verifies that the eviction loop respects the changed threshold.

## Rationale

All prior cycles probed static threshold values. v001's `freq > 1` gate was the best static point, but it cannot adjust when the workload enters a scan-heavy phase (where main gets flooded with cold items and the ratio of main hits drops) versus a hot-set-stable phase (where loosening the gate would let warm items survive longer). The adaptation window of 2048 operations aligns with the cache capacity, giving the mechanism enough signal to detect phase shifts without reacting to noise. The three-level threshold (0/1/2) keeps the control surface narrow and avoids oscillation.
