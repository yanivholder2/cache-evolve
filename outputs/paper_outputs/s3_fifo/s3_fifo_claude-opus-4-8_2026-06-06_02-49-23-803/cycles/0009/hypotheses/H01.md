# H01

Port v002's PhantomData key-drop onto v001's O(1) ghost_set put path to shrink scored Entry to 16 bytes while keeping per-op-time at its best 22 ns.

## Parent

cycle/0008/v001

## Changes

v001 already has the fast O(1) put (separate `ghost_set: HashSet<K>` plus a
tombstoned `ghost: VecDeque<K>` for FIFO order) and the O(1)-get `entries`
HashMap keyed by `K`, but its per-entry record still carries a redundant `key`
field, fixing `size_of::<Entry<u64,u64>>()` at 24 bytes. The `entries` map is
keyed by the resident key, so that field is dead weight — exactly the
observation v002 exploited.

Apply v002's metadata change to v001 verbatim:

- Redefine `Entry<K, V>` as `{ value: V, freq: u8, _k: PhantomData<K> }`,
  dropping the `key: K` field. Keep `K` as a type parameter (the pinned
  metadata binary instantiates `Entry<u64,u64>` by arity), carried by the
  zero-sized `PhantomData<K>`.
- Change `Entry::new` to take only `value` and set `_k: PhantomData`.
- Update the two `self.entries.insert(...)` call sites in `put` (the
  ghost-promotion branch and the small-admission branch) and the unit-test
  `Entry { .. }` literals to the new field set.

Do NOT touch the `ghost_set`/`ghost` membership machinery, `evict_main`,
`evict_small`, `push_ghost`, or `small_size = capacity/32` — every eviction,
promotion, and ghost-trim decision must stay bit-identical so hit-rate holds at
0.7312. The expected result is a variant that strictly dominates both incumbents
on the scored axes: hit-rate 0.7312, metadata-size 16, per-op-time ~22.
