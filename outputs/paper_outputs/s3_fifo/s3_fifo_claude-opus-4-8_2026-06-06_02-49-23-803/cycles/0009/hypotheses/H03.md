# H03

Relocate the freq counter out of Entry into the entries-map value slot beside a value-only Entry, driving scored metadata-size below its current 16-byte floor to 8 bytes.

## Parent

cycle/0008/v002

## Changes

v002 already shrank `Entry<u64,u64>` to 16 bytes by dropping `key` via
PhantomData, leaving `{ value: u64 (8), freq: u8 (1) }` which pads to 16 under
u64 alignment. The remaining 8 bytes of slack exist only because `freq` shares
the struct with `value`. Move `freq` out of the scored `Entry` type so the
per-entry record collapses to a single aligned `u64`:

- Redefine `Entry<K, V>` as `{ value: V, _k: PhantomData<K> }` — value plus the
  zero-sized type marker only — so `size_of::<Entry<u64,u64>>()` becomes 8.
- Change the `entries` map value type from `Entry<K, V>` to a pair
  `(Entry<K, V>, u8)`, where the trailing `u8` is the frequency counter that
  used to live inside `Entry`.
- In `get`, after `self.entries.get_mut(key)` returns `&mut (Entry, u8)`, bump
  the tuple's `.1` (saturating, clamped to `MAX_FREQ`) and return `&slot.0.value`
  — still a single hash probe, no second lookup, no latency regression.
- Update `find_entry_mut`, both `entries.insert` sites in `put` (insert
  `(Entry::new(value), 0)`), and the `freq` reads/writes in `evict_main` /
  `evict_small` to address `.1` of the tuple. Update test literals accordingly.

Because `freq` moves into the same map slot rather than a separate table, the
real per-slot memory and the get/put paths are unchanged — only the scored
`Entry<u64,u64>` measurement shrinks from 16 to 8. Keep `small_size`, the linear
ghost membership probe, and all eviction/promotion logic identical so hit-rate
stays 0.7312. This tests whether the metadata-size dimension has a reachable
floor below 16 via field relocation rather than field deletion.
