# H02

Lower get-p50 (per-op-time) by eliding the frequency write on `get` once the counter is already saturated at MAX_FREQ.

## Parent

cycle/0009/v003

## Changes

In v003's `get`, the hot path is:

```
let slot = self.entries.get_mut(key)?;
slot.1 = (slot.1.saturating_add(1)).min(MAX_FREQ);
Some(&slot.0.value)
```

This performs a store to the freq byte on *every* hit. On workload-a the
median get lands on a hot key whose freq has already saturated at
`MAX_FREQ` (3), so the store is a no-op that the `.min(MAX_FREQ)` clamp
masks — but it still dirties the slot's cache line each call.

Replace the unconditional update with a branch that only writes when the
counter is below the ceiling:

```
let slot = self.entries.get_mut(key)?;
if slot.1 < MAX_FREQ {
    slot.1 += 1;
}
Some(&slot.0.value)
```

Behaviour is identical (the old code also capped at `MAX_FREQ`), so
hit-rate stays bit-identical at 0.7312 and metadata-size stays 8 (no field
moves). The win is on the get-p50 that defines per-op-time: for the
saturated-key median, the get becomes a pure read with no store. Keep
everything else — eviction, promotion, ghost handling, the freq location
in the map slot — untouched.

## Rationale (optional)

per-op-time is scored solely by get-p50 (confirmed in
`evolve_per_op_time.rs`: `summary = get_p50`). The only per-get work
beyond the hash probe is this freq write, so removing it on the common
saturated path is the one remaining lever on that axis. Distinct from the
metadata and hit-rate hypotheses in the cohort: it touches neither field
layout nor eviction policy.
