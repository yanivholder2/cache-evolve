# H02

Scan the main queue before the small queue in `get` so hot proven keys are found sooner, lowering the scored get p50 per-op-time without affecting hit-rate or metadata-size.

## Parent

cycle/0005/v003

## Changes

In `src/s3_fifo/mod.rs`, both `get` and `find_entry_mut` locate a key with
`self.small.iter_mut().chain(self.main.iter_mut()).find(...)`, scanning the
narrow small queue (≈ capacity/32) first and the large main queue second.
On this workload the overwhelming majority of hits land on durable, proven
keys that live in `main`, yet every such hit must first walk the entire
small queue before reaching main. Reorder the scan to visit main first:

- In `get`, change the iterator to
  `self.main.iter_mut().chain(self.small.iter_mut()).find(...)`.
- In `find_entry_mut`, apply the same reorder
  (`self.main.iter_mut().chain(self.small.iter_mut())`).

**Invariants to preserve:** the set of keys searched is identical, so
lookups still find exactly the same entries — hit-rate and correctness are
unchanged (a key is never simultaneously in both queues, so order is
semantically irrelevant). The frequency-increment-on-hit logic in `get`
stays exactly as is. No struct or `Entry` changes, so metadata-size stays
24. This is a pure ordering micro-optimization targeting the scored
per-op-time summary (get p50, currently 47 ns), which is floored by this
linear resident scan.

## Rationale (optional)

The scored per-op-time summary is get p50, and get has been stuck at
46–47 ns for many cycles — the floor is the linear resident walk. Because
hot keys reside in main, scanning main first shortens the expected probe
length for the common hit, a zero-risk way to test whether the get floor
is scan-order-sensitive.
