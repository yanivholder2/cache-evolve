# H03

Bounding the number of second-chance rotations per main eviction to a small constant caps the worst-case `evict_main` scan length, cutting put-tail latency (per-op-time) with negligible hit-rate cost.

## Parent

cycle/0003/v001

## Changes

In `evict_main()`, bound the second-chance loop so it performs at most a
fixed number of decrement-and-rotate passes before forcing an eviction.
Replace the unbounded `while let Some(mut tail) = self.main.pop_back()`
loop with a counted version: track `let mut chances = 0u8;` and inside the
`tail.freq > 0` branch only grant a second chance while
`chances < SECOND_CHANCE_CAP` (introduce `const SECOND_CHANCE_CAP: u8 = 8;`),
incrementing `chances` each time a survivor is rotated to the front; once
the cap is reached, evict the current tail (drop it) regardless of its
remaining freq. This bounds the per-eviction work at O(cap) instead of the
current O(main) worst case where every resident has `freq > 0` and the
whole queue rotates. Keep the freq-decrement-on-survival semantics and the
small/ghost promotion paths unchanged; do not add any per-entry struct
state, so metadata-size stays flat.

## Rationale (optional)

This attacks put latency through a different mechanism than H01's ghost
trim — the resident-queue rotation rather than the ghost membership scan —
and is a legitimately scored per-op-time change because it shortens an
actual traversal. The cap is large enough (8) that it almost never fires
on this trace's freq distribution, so hit-rate should be essentially
preserved while the tail of `put` is bounded.
