# H03

Widening the correlated-reference window only in large (halving-mode) buckets, from `small_len / 16` (16 slots) to `small_len / 8` (32 slots), raises web_0 hit-rate at 131072 and leaves both 16384 cells bit-identical to cycle 0009 v001.

## Parent

cycle/0009/v001

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0009/v001. Keep every other mechanism as it is: `GCLOCK_MAX`,
`probation_len`, `halving` and the decay rules, the probation test, reset-to-0
on promotion, the recent bit on every hit. Do not edit `Item` or `src/shared/`.

1. **Constants.** Keep `CRP_DIV = 16` for small buckets. Add
   `const CRP_DIV_LARGE: usize = 8;`.
2. **Window field.** Add `crp_window: usize` to `AssociativeCacheBucket`. In
   `new`, compute `halving` first, then set
   `crp_window = small_len / if halving { CRP_DIV_LARGE } else { CRP_DIV }`.
   With the evaluated sizes this gives 4 for 128-slot buckets (unchanged) and
   32 for 1024-slot buckets (up from 16). Plain-GCLOCK buckets get 0.
3. **`is_correlated_probation_hit`.** Replace `self.small_len / CRP_DIV` with
   `self.crp_window`. Nothing else in `get_from_position` or `put` changes.
4. **Doc comment.** Explain that the window depends on size and give both
   values.
5. **Tests.** Add `large_bucket_window_is_wider`. Assert
   `bucket(128).crp_window == 4` and `bucket(1024).crp_window == 32`. In a
   filled `bucket(1024)`, a hit on a probation item at age 20 is correlated
   (counter stays 0), and a hit at age 40 bumps the counter to 1. The existing
   `correlated_probation_hit_not_promoted`, `late_probation_hit_promoted`
   (age 10 against window 4) and `candidate_matches_sweep` tests must pass
   unchanged.

Invariants: unchanged from v001. This change only decides whether a
probation hit bumps the counter. The sweep and the predictor do not change.

## Rationale (optional)

The correlated-reference filter gave the lineage its largest single-cell gain
(web_0 at 131072 in cycle 0008). That gain came from a 16-slot window,
which is 1/16 of a 256-slot probation ring. Cycle 0009 v002 found that an
absolute 16-slot window hurts hm_0 in *small* buckets, because there it covers a
quarter of the ring. It never tested a wider window in large buckets, where
32 slots is still only 1/8 of the ring. Cycle 0009's advice was to stop widening
the window in small buckets, so this change leaves them alone, and the 16384
cells must come out identical. That makes any change easy to attribute.

Refutation: the claim fails if web_0 at 131072 does not beat v001's 0.5846.
If hm_0 at 131072 drops below 0.7388, then 32 slots already filters hm_0's
real reuse in large rings, and the window is used up at both sizes. Any change
in a 16384 cell means the size gate is wrong.
