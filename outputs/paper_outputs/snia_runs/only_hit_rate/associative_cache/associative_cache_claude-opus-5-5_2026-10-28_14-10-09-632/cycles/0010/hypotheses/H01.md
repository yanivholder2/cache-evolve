# H01

Adding cycle 0009 v003's one-shot main-only "veteran" grace bit to cycle 0009 v001 raises hit-rate on web_0 and hm_0 at 131072 while keeping both 16384 cells within ±0.0003 of v001.

## Parent

cycle/0009/v001

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0009/v001. Keep everything else unchanged: `GCLOCK_MAX = 7`,
`PROBATION_FLOOR = 64`, `probation_len`, `CRP_DIV = 16` and the
correlated-reference filter, `HALVING_MIN_MAIN = 256` and the `halving` field,
the probation test, **reset-to-0 and recent-bit clear on promotion**, and
setting the recent bit on every hit. Do not edit `Item` or `src/shared/`.

1. **State.** Add `veteran: Vec<bool>` (created with `Vec::with_capacity(max_size)`),
   index-aligned with `items` and `recent`:
   - push `false` next to every `recent.push(false)` in `put`'s fill path;
   - set `veteran[slot] = false` at every `std::mem::replace` of a slot: the new
     item in probation slot `p` (both the evict and the promote branch), the
     promoted item in main slot `m`, and the plain-GCLOCK victim slot;
   - `remove_at` calls `self.veteran.remove(index)`.
2. **Setting the bit.** In `get_from_position` and in `put`'s existing-key
   branch, after the counter and recent logic, set `veteran[position] = true`
   only if `!self.split_active() || position >= self.small_len`. Probation hits
   never set it, correlated or not. Setting it there would be the non-zero
   promotion credit that cycle 0005 retired.
3. **`sweep_visit(h)`.** If `recent[h]`, clear it and return `false`. Else, if
   `lfu_counter > 0`, halve it (`self.halving`) or decrement it (otherwise) and
   return `false`. Else, if `veteran[h]`, clear it and return `false`. Else
   return `true`.
4. **`steps(i)`.** Add `self.veteran[i] as usize` to both branches. Each
   visit still lowers `steps` by exactly one, so `scan_min_from` is still an exact
   predictor and does not change.
5. **Doc comment.** Extend the "Sweep rule" paragraph to describe the
   veteran step.
6. **Tests (`clock_tests`).** Assert `b.veteran.len() == b.size()` in
   `check_candidate_matches_sweep_mode`. In `promotion_clears_recent_bit`,
   assert `!b.veteran[pos9]`, and assert that the probation hit on key 9 left
   `veteran[p9]` false. Add `fresh_promotion_evicted_before_veteran`: in
   `bucket(8)`, bring a main resident V to counter 0 with `veteran` set, then
   promote a fresh item F. With both at counter 0 and no recent bit, the sweep
   evicts F even if the hand reaches V first, and `eviction_candidate_index`
   predicts F. Add `correlated_hit_sets_no_veteran` on `bucket(128)`. Recheck
   the hand-traced plain-GCLOCK tests (`clock_second_chance`,
   `gclock_frequent_item_outlives_once_hit`, `small_main_uses_linear_decay`,
   `stale_high_count_loses_to_recent_low_count`). Any `steps` assertion that
   now includes +1 for veteran should be updated, with a comment explaining why.

Invariants: three per-slot vectors of equal length `<= max_size`; counters
`<= 7`; both hands in bounds; at most one eviction per miss. Worst-case sweep:
5 rotations in halving mode, 9 rotations of a 64-slot main in linear mode.

## Rationale (optional)

This is the continuation that cycle 0009 prescribed. v001's linear decay
only touched 128-slot buckets: its 131072 cells were bit-identical to cycle 0008
v003. Cycle 0009 v003's veteran bit raised exactly those cells
(web_0 0.5846 → 0.5854, hm_0 0.7388 → 0.7392). The two changes should therefore
stack at the large size.

Refutation: the large-size claim fails if web_0 at 131072 does not reach at
least 0.5852, or if hm_0 at 131072 falls below 0.7390. The small-size
side-claim fails if hm_0 at 16384 drops more than 0.0003 below v001's 0.4549.
That would show the veteran step collides with linear tiers in a 64-slot
main, and the bit should then be gated to `self.halving` buckets only.
