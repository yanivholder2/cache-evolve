# H02

Promoting probation-hit items into cycle 0004 v002's GCLOCK main region with a carried-over reference counter of at least 1, instead of resetting it to 0, raises hit-rate on hm_0, because newly promoted reused blocks stop being the next sweep victim.

## Parent

cycle/0004/v002

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0004/v002. Leave `small_len = max_size / 4` and the probation FIFO logic
unchanged.

1. **Promotion counter.** In `put`, in the full-bucket "hit during probation"
   branch, replace `promoted.lfu_counter = 0;` with
   `promoted.lfu_counter = promoted.lfu_counter.min(2).max(1);`.
   - A block hit once in probation enters main with counter 1.
   - A block hit two or more times enters with counter 2.
   - Nothing enters main with `GCLOCK_MAX`. Saturation is reserved for items
     that keep being hit in main, so a burst of probation hits cannot make a
     block permanently resident.
2. **Sweep is unchanged.** The decrementing sweep over `[small_len, len)`, the
   placement of the victim at `m`, and advancing `hand` past `m` all stay as
   they are.
   - The promoted item is written at `m`, just behind the hand, so it gets a
     full main rotation plus its carried counter's worth of extra rotations.
   - The sweep still terminates: each step either finds a 0 or decrements.
3. **`eviction_candidate_index`** needs no logic change. It already predicts
   the main victim with the min-counter-from-hand scan, and the candidate
   depends only on the state before the promotion.
4. **Tests** (in the file's own `clock_tests`):
   - Update `probation_hit_item_survives_into_main` to assert
     `lfu_counter == 1` for key 9 after promotion, not `0`.
   - Add a test that an item hit twice in probation is promoted with counter 2.
   - Add a test that, right after promotion, the promoted item outlives a
     main-region item that has counter 0 when the next promotion sweep runs.
   - `candidate_matches_sweep` must still pass.

Invariants are those of v002: `items.len() <= max_size`, at most one eviction
per full-bucket miss, `lfu_counter <= GCLOCK_MAX`, both hands in bounds. No
new fields; metadata-size is unchanged. Per-op cost can rise slightly,
because promotion sweeps may decrement more items before finding a 0. Report
per-op-time.

## Rationale (optional)

In v002 a promoted block enters main with counter 0, the same standing as a
main block that has gone cold. If the main hand comes around before the
block's next hit, it is evicted even though it has already shown reuse. This
is the question cycle 0004 left open. The change does not touch
probation depth or where new items land, so it tests main-region retention
by itself. It should help hm_0 most (long-reuse blocks that are hit once in
probation and then reused much later), at both sizes. web_0's one-touch scan
blocks never reach main, so its large-bucket filtering should be kept.

Refutation: if hm_0 does not beat v002's 0.4485 / 0.7369 at either size, then
the counter a block carries on promotion does not matter, and main-region
retention is not the bottleneck.
