# H02

Adding a one-shot per-slot "veteran" bit, set by any hit in main, makes the main sweep evict fresh never-re-hit promotions before decayed counter-0 blocks that have proven reuse in main, raising hit-rate on hm_0 at 131072.

## Parent

cycle/0007/v001

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0007/v001. Keep `GCLOCK_MAX = 7`, `probation_len`, the probation test,
the recent bit, recency-gated halving, and **reset-to-0 on promotion: a
promoted item enters main with counter 0, recent = false and veteran =
false**. Do not edit `Item` or `src/shared/`.

1. **State.** Add `veteran: Vec<bool>`, created with
   `Vec::with_capacity(max_size)` and kept index-aligned with `items` and
   `recent` everywhere they are touched:
   - fill-up `push(false)`;
   - every `std::mem::replace` of a slot sets `veteran[slot] = false`. That
     covers the new item in probation slot `p`, the promoted item in main slot
     `m`, and the victim slot in plain GCLOCK;
   - `remove_at` does `veteran.remove(index)`.
2. **Setting the bit.** In `get_from_position` and in `put`'s existing-key
   branch, after the counter bump and recent-bit set, also set
   `veteran[position] = true` **only if the slot is in main**, meaning
   `!self.split_active() || position >= self.small_len`. Probation hits must
   not set it, because that would be the non-zero-promotion-credit idea that
   cycle 0005 retired. Plain-GCLOCK buckets treat every slot as main.
3. **Sweep rule (`sweep_visit`).** At slot `h`: if `recent[h]`, clear it; else
   if `lfu_counter > 0`, halve it; else if `veteran[h]`, clear `veteran[h]`
   (the slot survives exactly one more visit); else `h` is the victim. A later
   main hit sets the bit again.
4. **Prediction (`steps`).** Return
   `recent as usize + bit_length(counter) + veteran as usize`. Each visit
   still lowers `steps` by exactly one, so `scan_min_from` stays an exact
   predictor with no other change.
5. **Tests (`clock_tests`).**
   - Assert `b.veteran.len() == b.size()` in `check_candidate_matches_sweep`.
   - `promotion_clears_recent_bit`: also assert `!b.veteran[pos9]`, and that a
     probation hit (on key 9 before promotion) did not set `veteran`.
   - Add `fresh_promotion_evicted_before_veteran`: in a size-8 bucket, put a
     main resident V through hit → full decay to counter 0 with veteran still
     set, then promote a fresh item F into main. Show that with both at counter
     0 and no recent bit, the sweep evicts F before V, even when V is reached
     first from the hand, and that the prediction matches.
   - Recheck the existing hand-traced tests (`clock_second_chance`,
     `gclock_frequent_item_outlives_once_hit`,
     `stale_high_count_loses_to_recent_low_count`). Under the new steps they
     should still pick the same victims: the hit slots all gain +1 equally.
     Fix any assertion that doesn't hold and note why.

Invariants: the three per-slot vectors have equal length `<= max_size`; the
worst-case sweep is 5 rotations; at most one eviction per miss. Metadata grows
by one byte per slot.

## Rationale (optional)

Cycle 0007 found that under reset-to-0, main's victims are almost always
counter-0 slots, and it asked whether fresh promotions and decayed veterans
should be treated differently among them. Today the hand evicts whichever it
reaches first. A fresh promotion has only shown one probation-window reuse. A
veteran has been re-referenced at main-scale distance, which is the
long-distance reuse hm_0 depends on and that cycle 0005's ghost recovered
(at the cost of web_0). This keeps that history without changing admission.
The extra grace applies only to blocks hit after entering main, so web_0's
single-return promotions get no extra mass. The bit is consumed once, so it
cannot trap stale blocks for long.

Refutation: if hm_0 @ 131072 does not beat 0.7383, near-miss history inside
main is not the gap. If web_0 @ 131072 falls below 0.5731 by more than hm_0
gains, veterans are mostly stale once-hot web_0 blocks, which goes against
v001's finding.
