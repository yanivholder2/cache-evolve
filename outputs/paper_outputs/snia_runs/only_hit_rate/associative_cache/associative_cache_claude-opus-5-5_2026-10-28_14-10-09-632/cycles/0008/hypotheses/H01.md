# H01

Choosing main's decay rule by main-region size, so small main regions (under 256 slots) go back to linear decrement ranked by `recent + counter` while large ones keep recency-gated halving, raises hit-rate on hm_0 at 16384 without giving up cycle 0007 v001's web_0 gain at 131072.

## Parent

cycle/0007/v001

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0007/v001. Keep `GCLOCK_MAX = 7`, `PROBATION_FLOOR = 64`, `probation_len`,
the probation test (counter 0 at `small_hand` means evict, otherwise promote),
**reset-to-0 plus recent-bit clear on promotion**, and the recent-bit set on
every hit. Do not edit `Item` or anything in `src/shared/`.

1. **Decay-mode field.** Add `const HALVING_MIN_MAIN: usize = 256;` and a field
   `halving: bool` to `AssociativeCacheBucket`. In `new`, set
   `halving = max_size - small_len >= HALVING_MIN_MAIN`. For the evaluated
   sizes, 128-slot buckets (main = 64) get `halving = false` and 1024-slot
   buckets (main = 768) get `halving = true`. Plain-GCLOCK buckets
   (`max_size < 4`) get `false`.
2. **`sweep_visit(h)`.** If `recent[h]`, clear it and return `false` (no
   change). Otherwise, if `lfu_counter > 0`: when `self.halving`, do
   `lfu_counter >>= 1`; else do `lfu_counter -= 1`; return `false`. Otherwise
   return `true` (victim).
3. **`steps(i)`.** When `self.halving`, keep
   `recent + bit_length(counter)`. Otherwise return
   `recent[i] as usize + lfu_counter`. In both modes each sweep visit still
   lowers a slot's `steps` by exactly one, so `scan_min_from` (first minimum
   from the hand, wrapping, early exit at 0) still predicts the sweep victim
   exactly. Leave `scan_min_from`, `eviction_candidate_index`, `put`'s control
   flow and `remove_at` as they are.
4. **Tests (`clock_tests`).**
   - `stale_high_count_loses_to_recent_low_count` builds `bucket(2)`, which is
     now linear mode. Set `b.halving = true;` right after construction so it
     still tests the halving rule.
   - Add `small_main_uses_linear_decay`: assert `bucket(128).halving == false`
     and `bucket(1024).halving == true`. In a linear bucket, a counter-5
     non-recent slot has `steps == 5`, and one sweep visit leaves its counter at 4.
   - Extend `candidate_matches_sweep` with one forced-halving and one linear
     run at size 128 (for example seeds 7 and 99, key space 300), so the
     predictor is checked in both modes.
   - All other existing tests must pass unchanged. Work through
     `gclock_frequent_item_outlives_once_hit` under linear steps: key 1 has
     steps 1+3 = 4 and key 2 has 1+1 = 2, so the victim is still key 2.

Invariants: `items.len() == recent.len() <= max_size`; `lfu_counter <= 7`;
both hands in bounds; at most one eviction per miss. The worst-case sweep in
small buckets goes back to 8 rotations of a 64-slot main region (at most 512
visits). Large buckets keep the 4-rotation bound.

## Rationale (optional)

Cycle 0007 v001's insight blames its only regression (hm_0 @ 16384, from
0.4529 to 0.4525) on bit-length ranking. It merges counters 2–3 and 4–7 into
one tier each, which costs ranking resolution in the 64-slot main region. Its
web_0 gain was at 131072, and v001 found halving adds nothing at 16384 because
the short sweep already decays counters quickly. So the two rules can be split
by main size with no expected cost. The recent bit stays in both modes, so
small buckets now get 9 tiers (recent + 0..7), finer than either parent. This
answers the cycle 0007 open question about restoring small-bucket tiers under
the recency rule.

Refutation: if hm_0 @ 16384 does not exceed 0.4525, tier resolution was not the
cause of v001's small-bucket loss. If web_0 @ 16384 drops below 0.4182, linear
decay plus the recent bit keeps stale web_0 blocks too long in small main. The
131072 cells should be bit-identical to v001. Any change there means the mode
gate is wrong.
