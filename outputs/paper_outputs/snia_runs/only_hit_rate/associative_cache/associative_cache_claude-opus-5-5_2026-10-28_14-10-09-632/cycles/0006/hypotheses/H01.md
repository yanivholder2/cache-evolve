# H01

Raising cycle 0005 v003's probation fraction from a quarter to three-eighths of the bucket, which grows probation from 256 to 384 slots in 1024-slot buckets and leaves 128-slot buckets at 64, raises hit-rate on web_0 at 131072 without lowering hm_0 at 131072.

## Parent

cycle/0005/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0005/v003. Change only the sizing function. Everything else stays as it
is: the promotion counter reset to 0, `GCLOCK_MAX = 3`, the main sweep limited
to `[small_len, len)`, in-place replacement at `small_hand`,
`eviction_candidate_index`, and `remove_at`.

1. **Sizing.** In `probation_len`, replace
   `(max_size / 4).max(PROBATION_FLOOR.min(max_size / 2)).max(1)` with
   `((max_size * 3) / 8).max(PROBATION_FLOOR.min(max_size / 2)).max(1)`.
   Keep `PROBATION_FLOOR = 64` and the `max_size < 4 → 0` branch. Update the
   doc comment to match.

   Resulting sizes:

   | `max_size` | `small_len` | Note |
   | --- | --- | --- |
   | 8 | 4 | unchanged |
   | 16 | 8 | unchanged |
   | 64 | 32 | unchanged |
   | 128 | 64 | unchanged (floor still dominates, 48 < 64) |
   | 1024 | 384 | was 256 |

   `small_len < max_size` still holds for every `max_size >= 4`, because
   3/8 < 1, so the main region is non-empty once the bucket is full.
2. **Tests** (in `clock_tests`):
   - In `probation_sizing_table`, change the 1024 assertions (both
     `probation_len(1024)` and `bucket(1024).small_len`) to 384. Keep the
     `4..=4096` loop that checks `1 <= s < size`.
   - Add `check_candidate_matches_sweep(1024, 2500, 99)` to
     `candidate_matches_sweep`, so the prediction is checked at the size
     that changed.
   - The bucket(8) tests should not need changes, since `small_len` is
     still 4. Confirm they pass.

Invariants: the same as v003. No per-item state is added and metadata-size does
not change. In 1024-slot buckets the main sweep now covers 640 slots, not 768.

## Rationale (optional)

Cycle 0005 v003 changed only the small cells. Its 131072 cells are the same
as cycle 0004 v002's, and nothing has moved the large-bucket cells since
cycle 0004. v003 showed that in this lineage, deeper probation at the cost of
main slots is not zero-sum. With main counters decremented only on promotion,
a smaller frequency-ranked main still holds the hot set. This experiment tests
whether that also holds at 1024 slots, which is the open question in both
cycle-0005 and cross-cycle insights. 128-slot buckets are unchanged, so any
effect can only show up in the 131072 cells.

Refutation: if web_0 at 131072 does not beat 0.5694, probation depth does
not limit web_0 at the large size. If hm_0 at 131072 drops below 0.7369 by
more than web_0 gains, deeper probation in large buckets weakens the
filtering or the main capacity that cycle 0004 gained, and the 1/4 fraction
should stay.
