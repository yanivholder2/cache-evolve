# H02

Raising cycle 0005 v003's absolute probation floor from 64 to 96 slots, with the cap moved from half to three-quarters of the bucket, so that 128-slot buckets get 96 probation slots and 32 main slots, raises hit-rate on web_0 at 16384 and leaves the 131072 cells unchanged.

## Parent

cycle/0005/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0005/v003. Change only the probation sizing. The promotion counter reset
to 0, `GCLOCK_MAX = 3`, the main sweep limited to `[small_len, len)`, and the
hand handling in `put`, `eviction_candidate_index`, and `remove_at` all stay
the same.

1. **Sizing.**
   - Set `const PROBATION_FLOOR: usize = 96;`.
   - In `probation_len`, replace
     `(max_size / 4).max(PROBATION_FLOOR.min(max_size / 2)).max(1)` with
     `(max_size / 4).max(PROBATION_FLOOR.min((max_size * 3) / 4)).max(1)`.
   - Keep the `max_size < 4 → 0` branch. Update the doc comments.

   Resulting sizes:

   | `max_size` | `small_len` | Main slots | Note |
   | --- | --- | --- | --- |
   | 4 | 3 | 1 | |
   | 8 | 6 | 2 | was 4 |
   | 16 | 12 | 4 | |
   | 64 | 48 | 16 | |
   | 128 | 96 | 32 | was 64 |
   | 1024 | 256 | 768 | unchanged (1024/4 > 96) |

   `(max_size * 3) / 4 < max_size` for every `max_size >= 4`, so
   `small_len < max_size` and the main region is non-empty once the bucket
   is full. That keeps the promotion sweep terminating.
2. **Tests** (in `clock_tests`):
   - Rewrite `probation_sizing_table` to match the table above, keeping the
     `4..=4096` loop that checks `1 <= s < size`.
   - `never_hit_item_evicted_after_small_len_misses` and
     `probation_hit_item_survives_into_main` hard-code `small_len == 4` for
     `bucket(8)`. It is now 6. Either:
     - derive every expected key from `b.small_len`, or
     - switch those tests to `bucket(16)` with `small_len == 12` and
       recompute the expected victims.

     The promotion test's main victim must be the first main-region key
     (slot index `small_len`).
   - `candidate_matches_sweep` must still pass for sizes 5, 16, 64 and 128.
     With a 1–2 slot main region at size 5, this checks that the sweep still
     terminates.

Invariants: the same as v003. Metadata-size does not change. Main sweeps in
128-slot buckets now cover 32 slots, so promotion cost goes down.

## Rationale (optional)

This answers the open question in cycle 0005 and the cross-cycle notes: how
high can the small-bucket floor go before hm_0 loses main capacity? v003
halved main (96 → 64) and both traces still gained, but the web_0 gain was
modest. Going to a 32-slot main brackets the turning point. Either web_0's
late second touches keep paying off, or hm_0's hot set no longer fits in
main. 1024-slot buckets are unchanged, so only the 16384 cells can move.
This is the opposite size from H01, so the two results read independently.

Refutation: if web_0 at 16384 does not beat 0.4175, depth beyond 64 gives
nothing. If hm_0 at 16384 drops below 0.4521 by more than web_0 gains, 64
slots is about the limit, and any further small-size gain has to come from
something other than depth.
