# H03

Widening cycle 0005 v003's GCLOCK reference counter ceiling from 3 to 7, so that main ranks blocks by reuse frequency over a longer history, raises hit-rate on hm_0 at 131072 while probation admission stays exactly the same.

## Parent

cycle/0005/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0005/v003. The only change is the counter ceiling. `probation_len`
(floor 64, `len/4`) stays the same, as do the promotion counter reset to 0,
the promotion test (`lfu_counter == 0` at `small_hand` means evict, otherwise
promote), and the region and hand logic.

1. **Ceiling.** Set `const GCLOCK_MAX: usize = 7;` and update its doc comment
   to "3 bits of state". `gclock_bump` already saturates at `GCLOCK_MAX`.
   `Item::lfu_counter` is a `usize`, so it needs no layout change.
2. **No change to the probation path.** The probation decision only checks
   `== 0` against non-zero, so a counter above 1 in probation has no effect
   until the item is promoted. Promotion still resets the counter to 0. The
   sweep loop in `put` and `scan_min_from` in `eviction_candidate_index`
   already work for any ceiling, since the sweep decrements until it finds a
   0. Confirm that the prediction still equals the sweep's victim:
   `scan_min_from` returns the first minimum at or after the hand, and
   decrementing by the same amount everywhere keeps that order.
3. **Tests** (in `clock_tests`):
   - `gclock_counter_saturates` already loops 10 times (more than 7) and
     asserts `GCLOCK_MAX`, so it should pass unchanged.
   - `gclock_frequent_item_outlives_once_hit` should still pass. Confirm it
     does.
   - Add `gclock_counter_saturates_at_seven`: hit an item 20 times and
     assert its counter is 7.
   - `candidate_matches_sweep` must pass for all sizes. Also add a
     high-reuse case, `check_candidate_matches_sweep(64, 80, 2024)`, so that
     counters reach the new ceiling.

Invariants: the same as v003, with `lfu_counter <= 7`. Metadata-size does not
change (the `usize` field is reused). The worst-case promotion sweep grows
from 3 to 7 rotations of the main region. Sweeps run only on promotions, so
the amortised cost stays bounded. Note this for when per-op-time is measured.

## Rationale (optional)

Depth (H01, H02) and admission strength (retired in cycle 0005) are the
probation-side levers. This hypothesis pulls the other lever: how well main
keeps its residents. Main counters are decremented only during promotion
sweeps, which are rare. So with a ceiling of 3, every block hit three or more
times since the last sweep looks the same, and the sweep can't tell hm_0's
truly hot blocks from merely warm ones. GCLOCK's gains have been largest on
hm_0 in large buckets (cycles 0002–0004). The hm_0 large-bucket cell has
been stuck at 0.7369 since cycle 0004, and cycle 0005 v001 briefly reached
0.7387 there by keeping more near-miss reuse. A wider ceiling may keep more of
that reuse in a frequency-based way, without ghost admission.

This changes only main, so it is orthogonal to H01 and H02.

Refutation: if hm_0 at 131072 does not beat 0.7369, a ceiling of 3 is not
what limits main. If web_0 at either size drops by more than hm_0 gains,
long-lived counters make stale web_0 blocks stay in main too long, and the
ceiling should go back to 3 or lower.
