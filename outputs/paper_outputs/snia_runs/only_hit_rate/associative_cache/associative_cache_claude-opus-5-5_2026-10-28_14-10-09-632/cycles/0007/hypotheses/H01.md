# H01

Adding a per-slot recent-hit bit to cycle 0006 v003's main region, where a sweep visit only clears a set bit but halves the counter of an unreferenced slot, raises hit-rate on hm_0 at 131072 by evicting stale high-count blocks sooner than recently re-used ones.

## Parent

cycle/0006/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0006/v003. Keep `GCLOCK_MAX = 7`, `probation_len` (floor 64, `len/4`),
the probation test (`lfu_counter == 0` at `small_hand` means evict, otherwise
promote), and **reset-to-0 on promotion**. Do not edit `Item` or anything in
`src/shared/`.

1. **State.** Add a field `recent: Vec<bool>` to `AssociativeCacheBucket`,
   created with `Vec::with_capacity(max_size)` in `new`. Keep it the same
   length as `items` and index-aligned at all times:
   - `put` fill-up path: `self.recent.push(false)` next to `self.items.push`.
   - Every `std::mem::replace(&mut self.items[i], x)` must also set
     `self.recent[i]` to the incoming item's value: `false` for a new item and
     `false` for the promoted item (promotion clears both the counter and the
     bit).
   - `remove_at`: `self.recent.remove(index)` next to `self.items.remove`.
2. **Hits.** In `get_from_position` and in `put`'s existing-key branch, keep
   `gclock_bump` and also set `self.recent[position] = true`. This applies in
   either region. A set bit in probation does not change the probation
   decision, which still checks only the counter, and promotion clears it.
3. **Sweep rule.** Use this rule for both the split-active main sweep in `put`
   and the plain-GCLOCK sweep. At each visited slot `h`:
   - if `recent[h]`: set `recent[h] = false`, leave the counter as it is, and
     advance;
   - else if `lfu_counter > 0`: `lfu_counter >>= 1` (halve), and advance;
   - else: `h` is the victim.

   Every visit lowers a slot's remaining "visits to zero" by exactly one, so
   the sweep always ends: in the worst case it takes 1 + 3 = 4 rotations for
   a counter of 7, compared with 7 before.
4. **Prediction.** Change `scan_min_from` to rank slots by
   `steps(i) = recent[i] as usize + (usize::BITS - lfu_counter.leading_zeros()) as usize`
   (bit length of the counter) instead of by the raw counter. Return the first
   minimum at or after `start`, wrapping, with an early exit on `steps == 0`.
   This is exactly the sweep's victim: each rotation lowers every slot's
   `steps` by one, so the slot with the lowest `steps` hits zero first, and
   ties go to whichever comes first from the hand. In
   `eviction_candidate_index`, the probation check stays on the raw counter.
5. **Tests** (in `clock_tests`):
   - `candidate_matches_sweep` must pass for all existing cases. Also assert
     `b.recent.len() == b.size()` inside `check_candidate_matches_sweep`.
   - `clock_second_chance`, `clock_all_referenced_evicts_at_hand` and
     `gclock_frequent_item_outlives_once_hit` should pass unchanged (work them
     out by hand under the `steps` rule: the counter-3 item has steps 3 and
     the counter-1 item has steps 2). Fix them if they don't.
   - Add `stale_high_count_loses_to_recent_low_count`: in a plain bucket of
     size 2, give item A counter 7, run one sweep pass that clears its bit,
     then hit B once. Assert that A's steps fall below B's after a second
     pass, and that the predicted victim equals the actual one.
   - Add `promotion_clears_recent_bit`: an item promoted from probation has
     `lfu_counter == 0` and `recent == false`.

Invariants: `items.len() == recent.len() <= max_size`; `lfu_counter <= 7`;
hands stay in bounds; at most one eviction per miss. Metadata grows by one
byte per slot. The worst-case sweep drops from 7 to 4 rotations of main.

## Rationale (optional)

Cycles 0005–0006 point to a recency gap: hm_0 at 131072 (0.7375) is still
below what cycle 0005 v001's near-miss retention reached, and v003's insight
says frequency resolution is nearly used up. With linear decrement, a block
that reached 7 long ago outlasts a block hit twice just before the sweep.
Recency-gated halving decays frequency multiplicatively, but only for slots
that were not re-referenced since the last pass, which gives CLOCK-Pro/LRFU
style recency weighting at the cost of one bit. Promotion still resets
everything to 0, so web_0 blocks entering main gain no extra mass, which keeps
the cycle 0005 safety property.

Refutation: if hm_0 at 131072 does not beat 0.7375, recency weighting inside
main is not the remaining gap. If web_0 at 131072 drops below 0.5699 by more
than hm_0 gains, the faster decay is removing web_0's long-lived hot blocks,
and linear decrement should be kept.
