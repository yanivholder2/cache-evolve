# H01

Adding cycle 0008 v001's size-gated linear decay to cycle 0008 v003 (linear decrement ranked by `recent + counter` when main has fewer than 256 slots, recency-gated halving otherwise) raises hit-rate on hm_0 at 16384 while leaving both 131072 cells unchanged.

## Parent

cycle/0008/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0008/v003. Keep everything else exactly as it is: `GCLOCK_MAX = 7`,
`PROBATION_FLOOR = 64`, `probation_len`, `CRP_DIV = 16` and the
correlated-reference filter (`probation_age`, `is_correlated_probation_hit`,
and the no-bump branch in `get_from_position` and `put`'s existing-key path),
the probation test (counter 0 at `small_hand` means evict, otherwise promote),
**reset-to-0 and recent-bit clear on promotion**, and setting the recent bit on
every hit. Do not edit `Item` or anything in `src/shared/`.

1. **Decay-mode field.** Add `const HALVING_MIN_MAIN: usize = 256;` and a
   field `halving: bool` to `AssociativeCacheBucket`. In `new`, set
   `halving = max_size - small_len >= HALVING_MIN_MAIN`. With the evaluated
   sizes, 128-slot buckets (main = 64) get `halving = false` and 1024-slot
   buckets (main = 768) get `halving = true`. Plain-GCLOCK buckets
   (`max_size < 4`, `small_len = 0`) get `false`.
2. **`sweep_visit(h)`.** If `recent[h]`, clear it and return `false`.
   Otherwise, if `lfu_counter > 0`, do `lfu_counter >>= 1` when `self.halving`
   and `lfu_counter -= 1` otherwise, then return `false`. Otherwise return
   `true` (this slot is the victim).
3. **`steps(i)`.** When `self.halving`, keep the current
   `recent + bit_length(counter)`. Otherwise return
   `recent[i] as usize + lfu_counter`. In both modes each sweep visit lowers a
   slot's `steps` by exactly one, so `scan_min_from` (first minimum from the
   hand, wrapping, stopping early at 0) still predicts the sweep victim exactly.
   Do not change `scan_min_from`, `eviction_candidate_index`, `put`'s control
   flow or `remove_at`.
4. **Doc comment.** Update the struct doc's "Sweep rule" paragraph to say that
   a non-zero counter is halved in large main regions and decremented in small
   ones.
5. **Tests (`clock_tests`).**
   - `stale_high_count_loses_to_recent_low_count` uses `bucket(2)`, which is
     now in linear mode. Set `b.halving = true;` right after construction so
     the test still exercises the halving rule.
   - Add `small_main_uses_linear_decay`. Assert `!bucket(128).halving` and
     `bucket(1024).halving`. In a linear bucket, a non-recent slot with
     counter 5 has `steps == 5`, and one `sweep_visit` leaves its counter at 4.
   - Extend `candidate_matches_sweep` with one forced-halving run at size 128
     (set `b.halving = true` through a variant of the helper that takes a
     `halving: Option<bool>` override; for example seed 99, key space 300).
     The existing size-128 run then covers linear mode with the
     correlated-reference filter active.
   - All other existing tests must pass unchanged, including
     `correlated_probation_hit_not_promoted` and `late_probation_hit_promoted`,
     which depend only on probation counters. Under linear steps,
     `gclock_frequent_item_outlives_once_hit` gives key 1 steps 1+3 = 4 and
     key 2 steps 1+1 = 2, so the victim is still key 2.

Invariants: `items.len() == recent.len() <= max_size`; `lfu_counter <= 7`; both
hands in bounds; at most one eviction per miss. In small buckets the worst-case
sweep goes back to 8 rotations of a 64-slot main (at most 512 visits). Large
buckets keep the 4-rotation bound.

## Rationale (optional)

Cycle 0008 v001 and v003 act on paths that don't overlap. v001 changed only
the 64-slot main region, and its 131072 cells were bit-identical to its
parent. v003's filter matters almost entirely in 1024-slot buckets, where the
window is 16 slots. v001 raised hm_0 at 16384 from 0.4525 to 0.4533 and web_0
at 16384 from 0.4182 to 0.4185. v003's weakest cell is web_0 at 16384
(0.4178). Combining them should pick up v001's small-bucket tier-resolution
gain on top of v003's large-bucket filtering, with no interaction expected.

Refutation: if hm_0 at 16384 does not beat v003's 0.4531, or web_0 at 16384
does not beat 0.4178, the two changes interact in small buckets (for example,
correlated hits that set the recent bit without bumping now outrank warm
blocks under finer tiers). Both 131072 cells must match v003's exactly
(0.5846 and 0.7388). Any change there means the mode gate is wrong.
