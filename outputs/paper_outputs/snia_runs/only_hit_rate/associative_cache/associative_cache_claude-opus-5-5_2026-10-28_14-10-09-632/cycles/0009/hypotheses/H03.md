# H03

Adding cycle 0008 v002's one-shot "veteran" grace bit (set only by hits in main) to cycle 0008 v003 raises hit-rate on web_0 and hm_0 at 131072, because the two changes reduce wasted counter-0 promotions in different ways and their gains add up.

## Parent

cycle/0008/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from
cycle/0008/v003. Keep `GCLOCK_MAX = 7`, `probation_len`, the probation test,
the recent bit, recency-gated halving, the correlated-reference filter
(`CRP_DIV = 16`, `probation_age`, `is_correlated_probation_hit`) and **reset-to-0
on promotion**. A promoted item enters main with counter 0, recent = false and
veteran = false. Do not edit `Item` or `src/shared/`.

1. **State.** Add a field `veteran: Vec<bool>`, created with
   `Vec::with_capacity(max_size)`. Keep it index-aligned with `items` and
   `recent` wherever those are touched:
   - when the bucket fills up, `veteran.push(false)` next to
     `recent.push(false)`;
   - every `std::mem::replace` of a slot sets `veteran[slot] = false`. That
     covers the new item in probation slot `p` (both the evict and the promote
     branch), the promoted item in main slot `m`, and the victim slot in plain
     GCLOCK;
   - `remove_at` calls `veteran.remove(index)`.
2. **Setting the bit.** In `get_from_position` and in `put`'s existing-key
   branch, after the existing counter and recent-bit logic, set
   `veteran[position] = true` **only if the slot is in main**, meaning
   `!self.split_active() || position >= self.small_len`. Probation hits never
   set it, whether or not they are correlated. Otherwise this would be the
   non-zero promotion credit that cycle 0005 retired.
3. **Sweep rule (`sweep_visit`).** At slot `h`: if `recent[h]`, clear it and
   return `false`. Otherwise, if `lfu_counter > 0`, halve it and return
   `false`. Otherwise, if `veteran[h]`, clear it and return `false`, so the
   slot survives exactly one more visit. Otherwise return `true` (victim).
4. **Prediction (`steps`).** Return
   `recent as usize + bit_length(counter) + veteran as usize`. Each visit
   still lowers `steps` by exactly one, so `scan_min_from` stays an exact
   predictor with no other change.
5. **Tests (`clock_tests`).**
   - In `check_candidate_matches_sweep`, assert `b.veteran.len() == b.size()`.
   - In `promotion_clears_recent_bit`, also assert `!b.veteran[pos9]`, and
     assert that the probation hit on key 9 did not set `veteran[p9]`.
   - Add `fresh_promotion_evicted_before_veteran`. In a size-8 bucket, take a
     main resident V through a hit and then sweep decay to counter 0 with
     `veteran` still set. Then promote a fresh item F into main. Show that with
     both at counter 0 and no recent bit, the sweep evicts F before V even when
     the hand reaches V first, and that `eviction_candidate_index` predicts F.
   - Add `correlated_hit_sets_no_veteran`. In `bucket(128)`, an immediate
     probation hit leaves `veteran` false.
   - Recheck the hand-traced tests (`clock_second_chance`,
     `gclock_frequent_item_outlives_once_hit`,
     `stale_high_count_loses_to_recent_low_count`). In plain-GCLOCK buckets
     every hit slot gains +1 step equally, so the same victims should be
     chosen. If an assertion no longer holds, fix it and add a comment
     explaining why.

Invariants: the three per-slot vectors have equal length `<= max_size`; the
worst-case main sweep is 5 rotations; at most one eviction per miss. Metadata
grows by one byte per slot.

## Rationale (optional)

v002 and v003 were the two large-bucket winners of cycle 0008, and both worked
on counter-0 promotions in main. v003 reduces how many burst-only blocks get
in. v002 makes the sweep evict fresh promotions before blocks that have been
re-hit in main. The cycle insight flagged that their gains might overlap. Here
they are tested together, separately from H01 and H02, so any overlap can be
measured on its own. The two mechanisms are not the same. After v003's filter,
the remaining fresh promotions are blocks with real, separated reuse during
probation. v002's grace helps veterans only against blocks with no main-proven
reuse, so both effects should survive. v002 lifted web_0 at 131072 from
0.5731 to 0.5750, which is a large gain on top of its parent.

Refutation: if web_0 at 131072 does not beat v003's 0.5846, v003's filter
already removed the fresh promotions that v002's grace was outranking, so the
two overlap and the veteran bit should be dropped from this lineage. If hm_0
at 131072 falls below 0.7388, the grace is now keeping stale veterans ahead of
filtered, real promotions. The 16384 cells should be within ±0.0003 of v003,
as v002 was flat at that size.
