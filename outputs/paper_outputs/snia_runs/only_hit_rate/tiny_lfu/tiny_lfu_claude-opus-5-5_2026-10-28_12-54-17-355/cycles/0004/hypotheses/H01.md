# H01

Replacing the fixed 80% protected fraction with a second hill climber that alternates sample periods with the window climber will recover hm_0 hit-rate while keeping web_0's SLRU gains, raising the overall hit-rate summary.

## Parent

cycle/0003/v001

## Changes

Work in `src/tiny_lfu/mod.rs` of cycle/0003/v001.

- Add climber state for the protected segment: `protected_pct: isize` (initialised to `PROTECTED_PERCENT` = 80), `prot_step: isize` (initial 5 percentage points), `prot_prev_hit_rate: f64`, and a `climb_turn: bool` that flips each time `climb()` fires.
- Split `climb()` into two halves selected by `climb_turn`:
  - **Window turn** (existing logic): compare `hr` with `prev_hit_rate`, reverse/decay `step`, retarget `window_cap`/`main_cap`, store `prev_hit_rate = hr`.
  - **Protected turn** (new logic): compare `hr` with `prot_prev_hit_rate` using the same `REVERSE_TOLERANCE` rule. Reverse `prot_step` on a drop. Decay its magnitude by `STEP_DECAY` with a floor of 1 percentage point. Set `protected_pct = (protected_pct + prot_step).clamp(20, 95)`. Store `prot_prev_hit_rate = hr`. Do not touch `window_cap` on this turn.
  - Each climber therefore compares only against its own previous sample, so the two knobs do not score each other's moves.
- Everywhere `protected_cap` is computed (`try_new`, both climb turns), use `main_cap * protected_pct as usize / 100` instead of `PROTECTED_PERCENT`.
- Rebalancing stays lazy, as it is now. Demotion of protected-LRU entries to probation MRU happens in `promote()`'s existing `while self.protected.len > self.protected_cap` loop. When `protected_cap` grows, protected simply fills through future probation hits.
- Keep the sample period (`capacity.max(MIN_SAMPLE_PERIOD)`), the window step logic, the admission contest (`cand_freq > victim_freq`) and the sketch exactly as they are, so the only variable is the protected split.
- Update the in-file `check_structure` test helper so it asserts `protected_cap == main_cap * protected_pct / 100` and `20 <= protected_pct <= 95`, instead of using the constant.

## Rationale

The cycle 0003 insight blames v001's small hm_0 loss on the short 20% probation segment, which cuts short the stay of recency-driven entries. web_0, in contrast, benefits from a strong protected segment. A per-workload split should let hm_0 move toward a larger probation (lower `protected_pct`) while web_0 stays near 80%. Alternating turns avoids the two climbers fighting over the same hit-rate delta. The hypothesis is refuted if hm_0 does not recover at either size, or if web_0 at 131072 falls below 0.5846.
