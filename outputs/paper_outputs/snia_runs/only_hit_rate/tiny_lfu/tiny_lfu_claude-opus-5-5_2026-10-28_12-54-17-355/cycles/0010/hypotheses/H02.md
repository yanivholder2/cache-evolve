# H02

Halving the sketch every 2^19 `get` calls on a fixed period that does not scale with capacity, rounding up so the resident wins and keeping double counting, raises hit-rate on top of v001 by giving newcomers back recency weight without reopening the admission bar.

## Parent

cycle/0009/v001

## Changes

All edits go in `src/tiny_lfu/mod.rs`.

1. Add `const AGING_PERIOD: u64 = 1 << 19;` (524288). It is a fixed number of `get` calls and does NOT depend on `capacity`.
2. Add a field `aging_count: u64` to `TinyLfuCache`, set to 0 in `try_new`.
3. In `get()`, after `self.sketch.increment(key)`, increment `aging_count`. When it reaches `AGING_PERIOD`, call
   `self.sketch.halve()` and reset `aging_count` to 0. Only `get` calls count. `put` increments do not count toward the period.
4. Add `fn halve(&mut self)` to `CountMinSketch`. It sets every counter to `c = (c + 1) >> 1` (ceiling halving).
   A nonzero counter never drops to 0, so a resident with count 1 keeps 1 and cannot lose a tie to a newcomer because of
   rounding. Use `c / 2 + (c & 1)` so `u32::MAX` cannot overflow.
5. Keep double counting on miss-then-put (both `get` and `put` increment), strict `>` plus v001's late-hit tie,
   `LATE_HIT_DIVISOR = 4`, the coldest-of-4 victim sample, and both climbers exactly as in the parent.

Add one inline unit test: build a small cache, drive exactly `AGING_PERIOD` `get` calls on one key, then assert its estimate
was ceiling-halved and that a key with count 1 still estimates 1 after a halving. Keep all existing tests passing.

## Rationale (optional)

This answers the open question carried since c7/c9: are the losses from aging caused by halving itself, or by how often it
fires and the single counting paired with it? c9 v003 showed that ceiling rounding protects web_0 large, but its period scaled
with capacity, so it fired 8× more often at 16384 than at 131072. A fixed period inverts that ratio: about 32× capacity at
small and 4× at large. Double counting is kept so this variant isolates aging. The prediction is that hm_0 large and web_0
large gain from stale-count decay. web_0 small must not drop below v001's 0.4282.
