# H02

Adding cap-free sketch halving to the adaptive-window cache, with the period counted in `get` requests (10×capacity, floored at 50 000), will raise hit-rate on web_0 without repeating the hm_0 small-size regression.

## Parent

cycle/0002/v003

## Changes

Keep v003's adaptive window and single main LRU unchanged. Add periodic aging to `CountMinSketch`:

- Add the fields `ops: u64` and `reset_period: u64` to `TinyLfuCache`. Do not put them in the sketch. In `try_new`, set `reset_period = max(10 * capacity, 50_000)` (as `u64`).
- In `get`, after `self.sketch.increment(key)`, increment `self.ops`. When `self.ops >= self.reset_period`, call `self.sketch.halve()` and set `self.ops = 0`. `put` must NOT advance `ops`. This is the key difference from cycle 0002's v002, which counted every `increment` call, so each miss (get followed by put) aged the sketch twice as fast.
- Add `CountMinSketch::halve(&mut self)`, which right-shifts every counter in every row by 1 (`*c >>= 1`).
- Keep `MAX_COUNT = u32::MAX`, with no counter cap. Keep the strict `>` admission contest as it is, so this variant isolates the aging effect.

Do not change sketch width or depth, so metadata-size stays the same as v003. The halving sweep is O(depth×width) once per period. That cost is accepted here.

## Rationale

Cycle 0002 v002 showed that cap-free halving helps web_0 at both sizes and hm_0 at the large size, but hurts hm_0 at the small size. The likely cause was a period that was too short (counted per increment, with two increments per miss). Counting only `get` requests, and flooring the period so a 16384-entry cache waits at least 163 840 requests between halvings, should keep hm_0's steady hot keys ahead while still letting web_0's stale counts decay. A refutation would be hm_0 at size 16384 falling below v003's 0.4886, or web_0 showing no gain over v003.
