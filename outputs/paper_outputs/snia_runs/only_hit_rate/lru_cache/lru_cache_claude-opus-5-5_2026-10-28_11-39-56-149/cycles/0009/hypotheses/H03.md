# H03

At large size only, choosing the main-area victim as the colder of the probation LRU and the protected LRU (by sketch estimate) will raise large-size hit-rate, because stale protected entries get evicted instead of warm probation entries.

## Parent

cycle/0008/v002

## Changes

All changes are in `src/lru_cache/mod.rs`. Keep the parent's `main_victim()` for capacities ≤ 32_768: probation LRU, else protected LRU. Small size must be bit-for-bit unchanged.

For `capacity > 32_768`, change `main_victim()` (or add a `main_victim_large()` that it dispatches to under a `freq_victim: bool` field set in `try_new`):
- let `p = head[PROB]` and `q = head[PROT]`;
- if either is NIL, return the other, as the parent does;
- otherwise compute `ep = sketch.estimate(hash_key(&nodes[p].key))` and `eq = sketch.estimate(hash_key(&nodes[q].key))`;
- return `q` only if `eq < ep` (strictly colder); otherwise return `p`. Ties keep the parent's probation-first behaviour.

Use the returned victim unchanged in both branches of `put_tinylfu`: the window-growing duel and the window-at-target duel. The duel compares the candidate against whichever victim was chosen, and ties still admit. `evict()` already decrements `prot_len` when a protected node is evicted, so protected simply drops below its cap for a while and later `touch()` promotions refill it. Do not otherwise change `prot_cap` or the demotion loop.

To avoid hashing twice, have the large-size path return `(victim, victim_est)` and reuse that estimate in the duel instead of recomputing it. Keep the per-op cost to at most one extra `estimate` per eviction. Update the top-of-file doc comment. Add a unit test on a capacity of 40_000: one protected entry that has gone cold (aged out of the sketch) is evicted ahead of a probation entry with a higher estimate.

## Rationale (optional)

c8 showed that a static split only shifts hit-rate between large-size web_0 and large-size hm_0. This rule adjusts the split per eviction from the frequency signal the cache already has. On web_0, medium-reuse probation keys that have built up counts survive, while protected keys that have gone stale are evicted. On hm_0, the hot protected set keeps high estimates, so it is never chosen, and the rule falls back to the parent's behaviour. This is different from H01: it is a per-eviction frequency comparison, not a hill climber on `prot_pct`.
