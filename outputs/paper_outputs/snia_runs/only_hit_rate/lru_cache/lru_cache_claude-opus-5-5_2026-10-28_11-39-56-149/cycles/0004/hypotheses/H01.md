# H01

Reverting only the sketch reset period from `16 * capacity` back to `10 * capacity` in cycle/0003/v002 will recover small-size web_0 hit-rate while keeping v002's hm_0 gains from dedup, the 4x width and the doorkeeper.

## Parent

cycle/0003/v002

## Changes

Change exactly one line in `src/lru_cache/mod.rs`. In `FreqSketch::new`, change
`reset_at: std::cmp::max(1, capacity.saturating_mul(16))` to
`reset_at: std::cmp::max(1, capacity.saturating_mul(10))`. Leave everything else as it is in v002:
- the width stays `max(capacity * 4, 64).next_power_of_two()`;
- the doorkeeper bitset, `door_contains`, and the doorkeeper clear on halving stay as they are;
- the miss-then-put dedup (`last_miss_hash` / `last_miss_valid`) stays;
- the tie-admitting duel (`cand_est >= victim_est`) and the 1% window / 80% protected split stay.

Update the unit test `sketch_saturates_and_halves` so it matches the new period. With `FreqSketch::new(4)`, `reset_at` is now 40, so the halving fires on the 40th increment and `count` becomes 20 afterward. Rework the loop counts and assertions to match. For example, do 1 doorkeeper increment plus 19 more to reach saturation at an estimate of 16, then 20 more to trigger the halving, then assert `count == 20` and `estimate <= 7`. Do not touch any other test.

## Rationale

The cycle 0003 insight could not say which of v002's four sketch changes caused the web_0 @ 16384 loss. Its leading suspect is the longer reset: probation victims keep stale counts longer, so a recency-reused candidate with an estimate around 2 loses the duel. This variant changes that one lever so the cause can be attributed. If web_0 @ 16384 goes back up to around 0.413 or higher and hm_0 @ 16384 stays near 0.48, the reset period was the cause. If web_0 doesn't move, the doorkeeper is the remaining suspect.
