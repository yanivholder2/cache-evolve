# H02

Adding a hill-climbed window/main split to cycle/0003/v002, with a climb step and sample period capped at absolute values instead of scaled with capacity, will raise small-size web_0 hit-rate without giving back large-size web_0.

## Parent

cycle/0003/v002

## Changes

All changes are in `src/lru_cache/mod.rs`. Keep v002's sketch (width, doorkeeper, 16x reset, dedup) and its tie-admitting duel exactly as they are.

1. **Climber state** on `LruCache` (only active when `win_cap > 0`, which means capacity >= 3):
   `sample_hits: u32`, `sample_accesses: u32`, `prev_hit_rate: f64` (start at 0.0),
   `step: isize` (signed), `sample_period: usize`, `min_win: usize`, `max_win: usize`.
   - `sample_period = clamp(10 * capacity, 2_000, 50_000)`. The cap of 50_000 accesses is
     the key fix. At 131072 it gives about 26x more climb rounds than cycle 0003's v001.
   - Initial `step = +min(max(1, capacity / 64), 256)`. That is a fixed cap of 256 entries,
     so at 131072 the first move is +256 and not +8192.
   - `min_win = max(1, capacity / 100)` (v002's current window, so the climber can't shrink
     below the proven 1%). `max_win = capacity * 40 / 100`.
2. **Sampling.** In `get`, when `win_cap > 0`, increment `sample_accesses` and, on a hit,
   `sample_hits`. When `sample_accesses >= sample_period`, call `fn climb(&mut self)`:
   compute `hr = hits / accesses`. If `hr < prev_hit_rate`, flip the direction (`step = -step`).
   Then shrink the magnitude: `|step| = max(1, |step| * 98 / 100)`, and if it reaches 1, reset it to
   the initial magnitude with the current sign so the climber keeps adapting.
   Set `win_cap = clamp(win_cap + step, min_win, max_win)`, store `prev_hit_rate = hr`,
   and zero both counters.
3. **Recompute protected cap** after each change. `main = capacity - win_cap`;
   `prot_cap = max(1, main * 8 / 10)`. If `prot_len > prot_cap`, demote protected-LRU nodes to
   probation MRU until `prot_len <= prot_cap` (same move as the overflow branch of `touch`).
4. **Resizing without bypassing the gate.** Don't evict anything eagerly when `win_cap` changes.
   - Window shrink: in `put_tinylfu` on a full arena, while `win_len > win_cap`, move the window
     LRU to probation through the normal duel path. Run the duel once for the current candidate and
     move any extra window-LRU nodes straight to probation MRU, with no eviction, since the total
     count is unchanged.
   - Window grow: when `win_len < win_cap` and the arena is full, the new key still needs a
     slot. Run the normal duel between the window LRU candidate and the main victim. If the
     candidate wins, evict the main victim but do **not** move the candidate out (the window
     grows by one). If it loses, evict the main victim anyway only when the victim's estimate is
     <= 1. Otherwise evict the candidate as usual. This keeps the TinyLFU gate in force while the
     window grows, which fixes the bypass that hurt cycle 0003's v001 at 131072.
5. Keep `debug_assert!(self.map.len() <= self.capacity)`, and keep `win_cap == 0` paths
   (capacity < 3) unchanged. Update existing unit tests only where they assert on `win_len`.
   Add one test that runs > `sample_period` accesses and checks
   `min_win <= win_cap <= max_win`.

## Rationale

In cycle 0003, v001's climber helped both traces at 16384 and lost web_0 @ 131072. That loss came only from a step and sample period that grew linearly with capacity, plus the gate bypass during growth. Capping both at absolute values, and keeping the duel while the window grows, tests whether adaptive sizing can stack on v002's sketch.
