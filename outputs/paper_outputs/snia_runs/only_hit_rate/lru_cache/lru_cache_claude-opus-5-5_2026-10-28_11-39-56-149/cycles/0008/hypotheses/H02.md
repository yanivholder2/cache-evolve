# H02

Shrinking the protected share of the main area from 80% to 75% at large capacity only will raise hit-rate on web_0 @ 131072 while leaving small-size cells unchanged.

## Parent

cycle/0007/v001

## Changes

Cycle 0007 v002 shrank protected globally. That helped web_0 @ 131072 (medium-range reuse gains from a longer probation) but hurt hm_0 at both sizes, and most of all at 16_384. This variant applies a milder version of the change and gates it by size, following the pattern of the winning `step_init` gate.

Concrete edits:

1. Add a field `prot_pct: usize` to `LruCache`. In `try_new`, set `prot_pct = if capacity > 32_768 { 75 } else { 80 }`.
2. Replace both occurrences of the protected-cap formula with `main * self.prot_pct / 100` (in `try_new` use the local `prot_pct`). One is `main * 8 / 10` in `try_new`, which keeps the `main == 1 => 0` degenerate branch and the `max(1, ..)`. The other is `max(1, main * 8 / 10)` in `climb()`. The demotion loop in `climb()` that enforces `prot_len <= prot_cap` stays as it is.
3. Change nothing else: the window, the climber (period, step gating, decay), the sketch, the doorkeeper and the duel. For capacity ≤ 32_768, behaviour must be identical to the parent (80% is the same as 8/10 under integer arithmetic for these values, so check `main * 80 / 100 == main * 8 / 10`, which holds).
4. Update the header comment. Add a unit test asserting `LruCache::<i64,i64>::new(131_072).prot_pct == 75` and `new(16_384).prot_pct == 80`, and that `prot_cap` equals `(capacity - win_cap) * prot_pct / 100` right after construction.

Expected effect: web_0 @ 131072 goes up by roughly v002's +0.001. hm_0 @ 131072 may lose a little, because its reuse set already fits at this size and 75% is milder than v002's split. Small cells should not change. Strict gain if the web_0 increase exceeds the hm_0 loss.
