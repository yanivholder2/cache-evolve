# H01

Enlarging the doorkeeper bitset fourfold at small capacity, so it stops saturating within a reset period, will raise hit-rate on web_0 @ 16384 without hurting hm_0.

## Parent

cycle/0007/v001

## Changes

Only `FreqSketch` changes. Today the doorkeeper has `width` bits (4 × capacity, so 65_536 bits at capacity 16_384) and uses 4 probes, but it is cleared only every `reset_at = 16 × capacity` increments (262_144 at 16_384). On a trace with many distinct keys, a 65_536-bit Bloom filter with k=4 that sees up to ~260k distinct keys before it is cleared ends up nearly all ones. Then `door_contains` returns true for almost every first touch, so cold one-shot keys go straight into the count-min counters and also get the +1 door bonus in `estimate`. The doorkeeper's one-shot filtering disappears late in each period. This hypothesis tests that saturation as the remaining limit on small-size web_0.

Concrete edits:

1. Add a field `door_shift: u32` to `FreqSketch`. In `FreqSketch::new(capacity)` compute `door_bits = if capacity <= 32_768 { width * 4 } else { width }` (still a power of two). Allocate `door: vec![0u64; door_bits / 64]` and set `door_shift = 64 - door_bits.trailing_zeros()`.
2. In `door_bit`, use `self.door_shift` instead of `self.row_shift` to compute `pos`. Leave the multiplier `DOOR_MUL`, the 4 probes and the seeds as they are.
3. Leave everything else alone: the counter table width, `reset_at`, the halving, the doorkeeper `fill(0)` on reset, `estimate`, the dedup of miss-then-put, the duel, the climber and `step_init`. Large capacity (> 32_768) must behave exactly like the parent, bit for bit. Use the same `32_768` gate as `step_init`.
4. Tests: `sketch_saturates_and_halves` uses `FreqSketch::new(4)` (small), which now has 256 door bits. Its assertions on estimates are unaffected, because one key sets the same number of bits. Keep `door.len()` at least 1 word. Add a unit test asserting `FreqSketch::new(16_384).door.len() * 64 == 4 * FreqSketch::new(16_384).width` and that `FreqSketch::new(65_536)` keeps `door.len() * 64 == width`.

Expected effect: lower false-positive first-touch counts at 16_384, so one-shot candidates lose ties against real reuse more often. web_0 @ 16384 should improve and hm_0 @ 16384 should be neutral or better. The large cells should be unchanged. Metadata grows by 24 KB at 16_384 (the doorkeeper goes from 8 KB to 32 KB), which is small next to the arena and the map.
