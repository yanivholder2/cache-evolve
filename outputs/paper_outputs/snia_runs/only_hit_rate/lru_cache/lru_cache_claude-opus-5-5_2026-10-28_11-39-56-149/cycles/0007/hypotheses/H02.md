# H02

Shrink the protected segment from 80% to 60% of the main area so that newly admitted keys stay in probation longer, to raise small-size web_0 hit-rate.

## Parent

cycle/0004/v002

## Changes

The only lever is the probation/protected split of the main area, which has
not been tuned since cycle 0001. Every place that computes `prot_cap` as
`main * 8 / 10` changes to `main * 6 / 10`:

1. In `LruCache::try_new`, `let prot_cap = if main == 1 { 0 } else { std::cmp::max(1, main * 8 / 10) };`
   becomes `... std::cmp::max(1, main * 6 / 10) ...`. Keep the `main == 1`
   → 0 degenerate case.
2. In `climb()`, `self.prot_cap = std::cmp::max(1, main * 8 / 10);` becomes
   `std::cmp::max(1, main * 6 / 10)`. Keep the demote-while-over-cap loop that
   follows it.

Leave the climber, sketch, doorkeeper, dedup, the duel and victim selection
(probation LRU, else protected LRU) unchanged. Fix the in-file test comments
that state numeric prot_cap values. For example, `scan_does_not_flush_protected`
has capacity 10, main 9, so prot_cap is now 5. The test's logic should still
pass, because the demoted hot keys have high sketch estimates and win every
duel against estimate-1 scan keys. Update the header comment (~20%/~80%) to
~40%/~60%. Capacities 1 and 2 must behave as before: with main 2, prot_cap
is max(1, 1) = 1, the same as now.

## Rationale (optional)

Cycle 0006 concluded that the small-size web_0 gap is structural (admission
or main-area split), not where the window settles. With 80% protected, a
probation segment of about 20% of 16k is short. Admitted keys with
medium-range reuse are evicted as the main victim before their second hit
can promote them. A larger probation segment gives them more time. The
risk, a weaker shield for hm_0's frequent keys, is limited because the
duel still guards entry.
