# H02

Doubling the direct-mapped ghost table to twice the segment's resident item capacity will raise hit-rate on hm_0 at the large cache size by remembering stash drops across reuse gaps longer than one cache's worth of evictions.

## Parent

cycle/0005/v001

## Changes

Start from cycle/0005/v001's overlay. Edit only `src/dash/segments/dash_segment.rs`. Keep the admission counter on a ghost hit at `lfu_counter = 1`. Keep the fingerprint at 16 bits (top bits of the hash, 0 remapped to 1), the splitmix64 index derivation, the `record`/`take` semantics (overwrite on collision, clear on match), and every call site unchanged.

1. Add `pub const GHOST_CAPACITY_MULTIPLIER: usize = 2;` next to `GHOST_MIN_SLOTS`.
2. In `DashSegment::try_new`, construct the table as `Ghost::new((normal_cap + stash_cap) * GHOST_CAPACITY_MULTIPLIER)`. `Ghost::new` already rounds up to a power of two with a floor of `GHOST_MIN_SLOTS`, so no other sizing code changes.
3. Leave the `info!` log of `ghost_slots` in place so the doubled size shows up in logs.
4. Tests: in `ghost_table_is_power_of_two_and_covers_capacity`, change the coverage assertion to `len >= seg.core.max_capacity() * GHOST_CAPACITY_MULTIPLIER`. Keep all other tests unchanged.
5. Report metadata-size: about 4 bytes per resident slot for the ghost, up from about 2. Per-op-time is unchanged (still one mix plus one compare), apart from somewhat worse cache locality in the table.

## Rationale (optional)

At 1×, a direct-mapped table loses about 1/e of its entries to collisions before one capacity's worth of drops has passed, so its effective reach is below one cache. ARC/LIRS-style schemes keep non-resident history of about 1–2× capacity. Every ghost change so far has left hm_0 at 131072 untouched. Cycle 0005 v002 showed that admission strength alone does not move that cell, so the remaining explanation is reach: hm_0's lost reuse at the large size lies beyond about 1× drops. This variant tests that explanation and changes no other factor. web_0 should stay flat: fingerprints stay full width, and a 2× table at 16 bits still has a false-match rate per lookup of about 1/65536.
