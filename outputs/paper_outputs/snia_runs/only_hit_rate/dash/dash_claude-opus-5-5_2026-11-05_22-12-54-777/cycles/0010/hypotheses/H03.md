# H03

Detecting sequential-key runs at the table level and inserting run members (from the 4th consecutive key onward) at the stash's LRU end without ghost recording will raise web_0 hit-rate by keeping scan blocks from pushing reusable keys out of the stash.

## Parent

cycle/0009/v002

## Changes

This is a structurally different lever aimed at web_0 outside the ghost path. MSR block traces contain sequential LBA scans, and the direct scan defence tried in c0007 (a promotion gate) never fired because one-hit scan keys never reach promotion. This change acts at stash insertion instead.

1. In the top-level Dash table's `put`, before dispatching to the segment, keep a small piece of per-table state: `last_key: u64` and `run_len: u8`.
   - This is the table struct that owns the segments, not `src/dash/jni.rs` or any gate-integrity file.
   - If the existing `&self`/`&mut self` signature requires it, use relaxed atomics.
   - On each *miss-insert* (a new key, not an update or a hit), if `key == last_key + 1` (wrapping), increment `run_len`, saturating at 255. Otherwise set `run_len = 0`. Then set `last_key = key`.
   - Hits and updates do not touch this state.
2. Pass a `scan: bool` flag down to `DashSegment::put`, true when `run_len >= SCAN_RUN_MIN`. `SCAN_RUN_MIN` is a new named const, set to 3. Add the flag as an internal parameter or a sibling method so that the public signature, if gate files use it, is unchanged.
3. In `DashSegment::put`, for a new key with `scan == true` that is not a ghost hit:
   - Insert it into the stash at the LRU/Back end with `lfu_counter = 0`, so it is the next stash victim, instead of the normal stash insert position.
   - When such a scan-marked key is later dropped from the stash, do not write it into the ghost. Use a spare metadata bit on the stash slot, or skip the ghost write if the slot is still at counter 0 and flagged.
   - If it is hit while in the stash, it is promoted normally and the flag is cleared.
4. Ghost hits, existing-key updates and non-scan inserts follow the parent's path exactly. Leave everything else unchanged: the gate, the probing fallback, window 8, the ageing rules, ghost size and fingerprint, and the 24/8 topology.

Expected effect: web_0 rises at both sizes, most at 16384, where stash pressure is highest. Ghost entries are no longer spent on scan keys, so real returners keep their entries. hm_0 should stay flat, because its accesses are less sequential. If hm_0 drops, raise `SCAN_RUN_MIN`. If web_0 does not move, keys in the trace are not sequential at the table level (for example, they are hashed or remapped). In either case, report how many inserts were flagged if any counter is available, and per-op-time.

## Rationale (optional)

Every web_0 gain so far has come through the ghost. The cross-cycle insights ask whether there is any web_0 lever outside it. This tests scan resistance at the point where scan keys actually enter (stash insert), not at promotion, where they never arrive. Landing at the LRU end applies only to cold first-time inserts, not to promotions, so it avoids the insert-position failures recorded for MRU promotion landing.
