# H03

Gating stash→target promotion with a TinyLFU-style comparison against the target bucket's would-be victim will raise hit-rate on web_0, because one-hit scan keys will stop displacing established target residents.

## Parent

cycle/0006/v003

## Changes

Start from cycle/0006/v003's overlay. Edit only `src/dash/segments/dash_segment.rs`. Keep `eviction_policy.rs` (window 8, cap 15, halve-on-cap), the ghost (capacity-sized, credit 1), v003's demotion halving, the 24/8 topology, and every landing position unchanged. The only change is an admission check on the stash-hit branch of `promotion_get`.

1. In `promotion_get`'s stash-hit branch, keep `record_hit(core.stash_buckets[stash_idx].get_items_mut(), item_idx)` as is. Then, before removing the item, read `cand = stash item's lfu_counter`.
2. Check the target bucket `core.buckets[target_idx]`:
   - If it is **not full** (`size() < get_max_size()`), promote exactly as today.
   - If it **is full**, compute `v = lru_tail_lfu_victim(core.buckets[target_idx].get_items())` (import it from `crate::shared::eviction_policy`) and `victim_cnt = items[v].lfu_counter`. Promote as today when `cand >= victim_cnt`. Ties go to the newcomer, which preserves today's behaviour whenever residents are cold.
   - **Rejected** (`cand < victim_cnt`): do not promote. Remove the item with `remove_at(item_idx)` and re-insert it with `core.put_at(Slot::Stash, InsertPosition::Back, data)`. This cannot evict, because a slot was just freed; `debug_assert!` that it returns `None`. The item keeps the counter it just earned and moves to the stash MRU end, so a later hit can retry once its count has grown. Return a reference to it from the stash bucket via `get_position(key)`.
3. Do not change the target-hit or probing-hit branches, `put`, or the demotion cascade.
4. Tests:
   - `stash_hit_promotes_when_target_has_room`: equivalent to `stash_hit_counts_and_carries_counter`, which must keep passing.
   - `stash_hit_rejected_when_target_victim_hotter`: fill target 0 to capacity, set every resident counter to 5, `put` a new key mapping to target 0, then `get` it once (counter 1 < 5). Assert that it is still in the stash with counter 1, that it sits at the last index of its stash bucket, and that the target contents are unchanged.
   - `stash_hit_promotes_when_count_reaches_victim`: same setup with residents at 1. Assert that the newcomer is promoted and one resident is demoted with its counter halved.
   - Keep all existing tests passing. Adjust any test that relied on unconditional promotion into a full target with hotter residents.
5. Report per-op-time: one extra 8-slot scan of the target bucket per stash hit when the target is full.

## Rationale (optional)

web_0 has not responded to any lever in six cycles, because every lever so far works through the ghost and web_0's ghost rarely fires. The remaining damage a scan can do is in promotion. Today any single stash hit unconditionally promotes, and it can push out a target resident with a higher count. TinyLFU's admission rule (admit only if the candidate's frequency is at least the victim's) is the standard defence against this. With ties admitted, cold targets behave as before. For hm_0, items with real reuse accumulate stash hits and pass the gate on a later hit. That trade-off (slower promotion versus target protection) is the experiment: if hm_0 drops, the stash is too short-lived for a retry, and the gate should be loosened to `cand + 1 >= victim_cnt`.
