# H02

Let a ghost hit bypass the stash only when the target bucket has a cold (counter-0) slot in its tail window, to raise small-size web_0 hit-rate without losing v002's large-size gains.

## Parent

cycle/0007/v002

## Changes

In v002's `DashSegment::put`, a ghost hit always calls
`promote_to_target(..., Front)` with `lfu_counter = 1`. When the target bucket
is full, this forces a `demote_from_normal_bucket` cascade that can push a
useful resident into the stash. That is why web_0 at 16384 stays flat.

1. Before the bypass, look at the target bucket's 8-slot tail window, using
   the same slots the frequency-aware victim scan reads. Take the bypass
   (current v002 behaviour) only if at least one of these holds:
   - the target bucket has a free slot, or
   - some slot in the tail window has `lfu_counter == 0`.
2. Otherwise, fall back to the cycle 0006 behaviour: insert the ghost-hit key
   into the stash at its normal position with `lfu_counter = 1`. In this case,
   do not invalidate the ghost entry, if that is consistent with the current
   code, so a second return can try the bypass again. If keeping the entry
   makes the code harder to follow, clearing it as today is fine.
3. Combine the gate check with the victim scan that follows so the window is
   read only once on the bypass path. Return the candidate index from one
   helper. Do not add a second pass.
4. Keep everything else unchanged: window 8, ageing rules, ghost table size and
   fingerprint, and the stash→target promotion path.

Expected effect: web_0 at 16384 goes up slightly, because fewer warm residents
are swapped out for one-time returners. hm_0 at 16384 stays the same, and the
131072 cells keep v002's gains, because large targets usually have cold tail
slots. Report per-op-time.

## Rationale (optional)

This answers the cycle 0007 question about making the bypass selective. The
condition depends on actual contention, not on cache size, so it adapts at
both sizes without a size threshold.
