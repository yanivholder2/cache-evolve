# H01

Placing promoted items at the MRU end of their destination bucket while keeping demoted items at the LRU end of stash will raise hit-rate, because baseline promotions are currently the very next eviction victims.

## Parent

baseline

## Changes

Edit only `src/dash/segments/dash_segment.rs`.

In the baseline, `DashSegment::get` calls `promotion_get(&mut self.core, key, InsertPosition::Front)`, and that one `insert_pos` is used for every `put_at` in the cascade. That covers promotions (stash→target in `promote_to_target`, target→probing in `promote_to_probing`) and demotions (`demote_from_normal_bucket` to its target and to stash). With ClassicLRU, index 0 is the eviction candidate. So an item that just earned a stash hit is inserted at index 0 of its 64-slot target. It is then evicted by the next insertion into that bucket unless it gets hit again first. The protected tier gives almost no protection.

Split the single `insert_pos` into two parameters:

1. Change `promotion_get`, `promote_to_target` and `promote_to_probing` to take `promote_pos: InsertPosition` and `demote_pos: InsertPosition` instead of one `insert_pos`.
2. Use `promote_pos` for the `core.put_at(Slot::Target, ..)` call in `promote_to_target` and for the `core.put_at(Slot::Probing, ..)` call in `promote_to_probing`.
3. Pass `demote_pos` to `demote_from_normal_bucket` and use it for every `put_at` there: the foreign-resident retry into `Slot::Target` and both `Slot::Stash` inserts. The function's signature can stay the same, since it only gets one position.
4. In `DashSegment::get`, call `promotion_get(&mut self.core, key, InsertPosition::Back, InsertPosition::Front)`. Promotions land at MRU, and demoted items land at the LRU end so they are the first to leave.

Keep these unchanged: the "hottest in target → probing" trigger (`promotion_candidate_index`), the touch-in-place on probing hits, the lookup order stash → target → probing, the `unreachable!` post-insert lookups, and the default `Segment::put` (stash, Back).

Because of the MRU landing, a stash-hit item now sits at `items.len()-1` of target. The next target hit on it therefore immediately promotes it to probing, which is expected. Update the in-file unit tests that assert Front placement after a stash hit (`stash_hit_inserts_at_front_of_target`, `target_hit_not_hottest_promotes_within_bucket`, `target_hit_hottest_promotes_to_probing`, `cascade_demotion_probing_to_full_target_to_stash`) to match the new ordering. Update the helper-level tests that call `promote_to_*` directly to the new signatures.

## Rationale (optional)

Baseline hit-rate summary is 0.5099 on MSR web_0/hm_0. The target/probing tier holds 25% of capacity (8 of 32 buckets). With Front-insert it behaves almost like FIFO admission, not a protected segment. Moving promotions to MRU turns it into a real SLRU protected segment, and leaving demotions at the LRU end keeps stash pollution low. Per-op time should not change, because this only moves where an existing insert lands.
