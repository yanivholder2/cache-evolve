# H03

Probing the target and probing buckets before the stash bucket in `promotion_get` will lower get p50 per-op-time by sparing hits on hot, normal-tier items a wasted 64-slot linear scan of the stash.

## Parent

baseline

## Changes

All edits are in `src/dash/segments/dash_segment.rs`, in `promotion_get`. The result stays the same for every input: only the order of the bucket checks changes.

Today `promotion_get` checks the stash first: `core.stash_buckets[stash_idx].get_position(key)` is a linear scan over up to 64 items. Only after that does it check `buckets[target_idx]` and then `buckets[probing_idx]`. Hot items mostly live in the normal tier (target/probing), because that is where promotion sends reused items. So nearly every hit on a hot key pays for a full failed stash scan first.

New order:

1. Target check: `core.buckets[target_idx].get_position(key)`. If found, run the existing target-hit logic unchanged: the hottest-check via `promotion_candidate_index()`, then either `promote_to_probing` plus the `unreachable!` re-lookup in `probing_idx`, or an intra-bucket `get_from_position`.
2. Probing check: `core.buckets[probing_idx].get_position(key)`. If found, touch in place via `get_from_position` exactly as today.
3. Stash check: `core.stash_buckets[stash_idx].get_position(key)`. If found, run the existing `remove_at`, `promote_to_target(core, data, insert_pos)` and re-lookup in `target_idx`.
4. Otherwise, return `None` on a miss.

Correctness argument to keep in a comment: thanks to the uniqueness invariant (ADR 0004), a key is resident in at most one of the three slots, so the order of the checks cannot change which branch fires. Hit/miss outcomes and item movement are therefore exactly the same as the baseline, and hit-rate should be bit-identical. Misses still scan all three buckets, so miss cost is unchanged.

Keep the stash/target/probing index calculations at the top of the function. Compute `stash_idx` lazily, just before step 3, so the target/probing hit paths skip that hash too. Do not change `SegmentCore::contains_key`, the put path, or any test expectation: all existing `dash_segment.rs` tests should pass unmodified.

## Rationale (optional)

This is a cost-only control for the cohort. It tests whether lookup order inside the segment is a meaningful share of get latency, with zero risk to hit-rate. It isolates the per-op-time dimension, so a win here can later be stacked on any hit-rate winner.
