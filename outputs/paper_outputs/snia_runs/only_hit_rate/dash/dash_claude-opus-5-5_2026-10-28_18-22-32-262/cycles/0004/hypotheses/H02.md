# H02

Requiring a stash→target promotee to get one target hit before it can move to probing will raise mean hit-rate above 0.398925, mainly by lifting `web_0` at 128K, because fresh promotees will stop displacing proven probing residents on their first target hit.

## Parent

cycle/0003/v003

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Keep the two-hit stash gate, `STASH_DEMOTION_POS = Back`, `STASH_PROMOTION_TARGET_POS = Back`, the stash branch and the probing-hit/miss branches unchanged. `Item::lfu_counter` is not used by ClassicLRU, and while an item is in the stash it is its stash-hit counter. This change reuses it as a target-hit counter while the item is in a normal bucket.

1. Add `const TARGET_HITS_BEFORE_PROBING: usize = 1;`, documented as "target hits an item must have collected during its current target stay before a hit at the hottest position moves it to probing".
2. Stash→target promotion already resets `lfu_counter = 0` before `remove_at`. Keep that, so a fresh promotee arrives with 0 target hits.
3. In the target-hit branch of `promotion_get`, read the item's current count: `let prior = core.buckets[target_idx].get_items()[item_idx].lfu_counter;`. Then increment it in place with `get_items_mut()[item_idx].lfu_counter = prior.saturating_add(1)`. Promote to probing only if `is_hottest && prior >= TARGET_HITS_BEFORE_PROBING`. In that case, reset `lfu_counter = 0` on the removed `data` before `promote_to_probing`. Otherwise use the existing `get_from_position(item_idx)` refresh. That refresh keeps the item at MRU, so its next hit is eligible.
4. In `demote_from_normal_bucket`, for the foreign-resident retry into the true target (the `else` branch), set `item.lfu_counter = TARGET_HITS_BEFORE_PROBING` before `put_at(Slot::Target, ...)`. Items that came down from probing have already proven themselves and keep the one-hit route back up they had before. The cascade-to-stash and direct-to-stash resets stay at 0.
5. Items put directly into normal buckets by tests have counter 0. Treat them like fresh promotees.

Tests: `target_hit_hottest_promotes_to_probing` and `last_bucket_probing_wraps_to_zero` need one extra `seg.get(&keys[1])` before the probing assertion (the first target hit only counts). Update their comments. In `cascade_demotion_probing_to_full_target_to_stash`, add one extra `get(&target_keys[1])` before the promotion. `probing_eviction_demotes_to_target` puts a key directly into the target with counter 0, so it now needs two `get`s. Add `fresh_promotee_needs_target_hit_before_probing`: promote a key via two stash hits, `get` once more, and assert it is still in the target. `get` again and assert it is in probing. `target_hit_not_hottest_promotes_within_bucket` is unaffected.

Invariants: no new data movement. The change only delays the existing target→probing move by one hit for items whose counter is below the threshold. The no-duplicates rule and the `unreachable!` postconditions still hold.

## Rationale (optional)

v003's insight says the flat `web_0` 128K cell likely comes from the MRU-placed promotee being the `promotion_candidate_index()` immediately, so a single hit moves it to probing. That evicts a probing resident, which then cascades. This hypothesis tests that mechanism directly. It is independent of H01 (when the gate applies) and H03 (which stash item is evicted).
