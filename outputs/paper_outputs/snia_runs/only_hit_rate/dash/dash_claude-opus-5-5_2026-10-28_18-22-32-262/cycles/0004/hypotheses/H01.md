# H01

Skipping v003's two-hit stash gate only when the target bucket has at least two free slots will raise mean hit-rate above 0.398925, because it recovers `web_0` at 128K without the last-free-slot cascade that cost cycle-0003 v002 its 16K gains.

## Parent

cycle/0003/v003

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Keep `STASH_DEMOTION_POS = Back`, `STASH_PROMOTION_TARGET_POS = Back`, the `lfu_counter` resets, the two-argument `promote_to_target(core, item, place_pos, retry_pos)`, and the target-hit, probing-hit and miss branches unchanged.

1. Add `const STASH_GATE_BYPASS_FREE_SLOTS: usize = 2;`, documented as "minimum number of free slots in the target bucket for a stash item to promote on its first hit".
2. In the stash-hit branch of `promotion_get`, after computing `hits`, compute `let free = target_capacity - core.buckets[target_idx].get_items().len();`. Take `target_capacity` from the bucket's capacity accessor, or from the segment's per-bucket slot count in `SegmentCore`/`DashSettings` if the bucket has no accessor. Use `saturating_sub`. Then set `let target_has_room = free >= STASH_GATE_BYPASS_FREE_SLOTS;`.
3. Change the gate from `if hits < STASH_PROMOTION_HITS` to `if hits < STASH_PROMOTION_HITS && !target_has_room`. When the gate is bypassed, the item takes the existing promotion path unchanged: reset the counter, `remove_at`, `promote_to_target(core, data, STASH_PROMOTION_TARGET_POS, insert_pos)`, then the `unreachable!` lookup. This promotion cannot evict anyone, because the target has room.
4. Check only the target bucket, not probing.
5. Update the doc comments on `STASH_PROMOTION_HITS` and `promotion_get` to describe the bypass.

Tests: with the `small_dash_settings` bucket capacity (2 slots), an empty target has exactly 2 free slots, so a single hit now promotes when the target is empty. Update `single_stash_hit_stays_in_stash_at_mru` so it first puts one filler key directly into `core.buckets[target_idx]` (leaving 1 free slot, below the threshold). Pick stash keys whose target is that bucket, using `find_keys_for_bucket` on the segment size and then filtering by stash index. Then assert that one hit stays in stash and a second hit promotes. Add `stash_hit_bypasses_gate_when_target_has_two_free_slots`: put one key into an empty segment, `get` once, and assert it is in its target. Wherever the extra promotion changes order or `get` counts, adjust the tests that `put` and then `get` twice (`stash_hit_inserts_at_back_of_target`, `target_hit_*`, `cascade_demotion_*`, `last_bucket_probing_wraps_to_zero`) so each still exercises its named path. The second `get` would now be a target hit that may move the key to probing.

Invariants: unchanged. The new condition only chooses between the two existing paths.

## Rationale (optional)

Cycle 0003 found that v002's `!is_full()` bypass and v003's `Back` placement fix opposite cells. v002 lost at 16K because one-hit items took the last free slot. Requiring two free slots keeps the bypass in roomy (128K) buckets and turns it off in contended ones. This is the top continuation candidate from the cycle-0003 insight.
