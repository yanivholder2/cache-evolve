# H02

Making v001's two-hit stash-promotion gate occupancy-aware, so a stash item promotes on its first hit whenever its target bucket has a free slot, will raise mean hit-rate above 0.395975 by removing the gate's cost in roomy 128K caches while keeping it where targets are contended.

## Parent

cycle/0002/v001

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Keep `STASH_DEMOTION_POS = Back`, the counter resets in `demote_from_normal_bucket`, and every non-stash branch of `promotion_get` unchanged.

1. In the stash-hit branch of `promotion_get`, after incrementing `lfu_counter` and reading `hits`, compute `let target_has_room = !core.buckets[target_idx].is_full();`. Change the gate condition from `if hits < STASH_PROMOTION_HITS` to `if hits < STASH_PROMOTION_HITS && !target_has_room`. When the target has room, the item promotes on its first hit. That promotion evicts nobody, so it cannot start a `target -> stash` cascade. When the target is full, the current two-hit rule applies.
2. Leave the promotion path as it is: reset `lfu_counter = 0`, `remove_at`, `promote_to_target(core, data, insert_pos)`, then the `unreachable!` lookup.
3. Check only the target bucket's fullness, not the probing bucket's. Promotion inserts only into the target, so the target alone decides whether a swap happens.
4. Update the doc comment on `STASH_PROMOTION_HITS` and `promotion_get` to describe the occupancy condition.

Tests: `single_stash_hit_stays_in_stash_at_mru` now has an empty target, so a single hit will promote. Change it to fill `core.buckets[target_idx]` first (direct `core_mut().buckets[target_idx].put(...)` with keys from `find_keys_for_bucket(target_idx, seg_size, n)` until `is_full()`), and pick the stash keys so they map to that target. Then assert that one hit stays in stash at the MRU end and a second hit promotes. Add `stash_hit_promotes_immediately_when_target_has_room`: put one key into an empty segment, `get` once, and assert that it is in its target and not in stash. Other tests that do two `get`s after a put still pass, because the first hit now promotes and the second is a target hit. Check each assertion about item order in the target (for example `stash_hit_inserts_at_front_of_target`) and remove the redundant second `get` wherever the extra target hit would reorder items.

Invariants: unchanged. The new branch only selects between the two existing code paths.

## Rationale (optional)

Across both cycles the gate helped at 16K and hurt `web_0` at 128K, and the cross-cycle notes say first-hit promotion is near-optimal "when target buckets have spare room". This hypothesis encodes that condition directly, per bucket, instead of using a global threshold. It is a different lever from H01: H01 changes which items are gated (demoted vs fresh), and this one changes when the gate applies (contended vs free target).
