# H02

Promoting a target-bucket item to its probing bucket on any target hit, not only when it is at the hottest position, will raise mean hit-rate above 0.39905, mainly by lifting `web_0` at 128K, where hot items need to move from target to probing faster.

## Parent

cycle/0004/v001

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Keep the stash branch unchanged, including the two-hit gate, the two-free-slot bypass, `STASH_PROMOTION_TARGET_POS = Back` and `STASH_DEMOTION_POS = Back`. Keep the probing-hit and miss branches, `promote_to_probing`, and `demote_from_normal_bucket` unchanged.

1. Add `const TARGET_ANY_HIT_PROMOTES: bool = true;`, documented as "if true, any hit on an item in its target bucket moves it to probing; if false, only a hit at `promotion_candidate_index()` does".
2. In the target-hit branch of `promotion_get`, replace `let is_hottest = Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();` with `let promote = TARGET_ANY_HIT_PROMOTES || Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();`. Use `promote` in the `if`. The promote path is unchanged: `remove_at`, `promote_to_probing(core, data, insert_pos)`, then the `unreachable!` probing lookup. The `else` intra-bucket refresh (`get_from_position`) stays as dead-but-compiled code for the `false` setting.
3. Update the doc comment on `promotion_get` and the struct doc to describe the new trigger.

Tests: `target_hit_not_hottest_promotes_within_bucket` no longer holds when the constant is true. Rename it to `target_hit_not_hottest_promotes_to_probing`. After `fill_target_via_stash`, hit `keys[0]` (the LRU-end item) and assert that it is now in `probing_idx` and not in the target, and that `keys[1]` is still in the target. `target_hit_hottest_promotes_to_probing`, `cascade_demotion_probing_to_full_target_to_stash`, `last_bucket_probing_wraps_to_zero` and `probing_eviction_demotes_to_target` already hit the MRU item and are unaffected. Check that `fill_target_via_stash` never hits a key once it is in the target. It doesn't today, so it needs no change.

Invariants: no new data movement types. This only widens the condition for an existing move. No-duplicates and the `unreachable!` postconditions still hold.

## Rationale (optional)

Cycle 0004 v002 delayed the target→probing move and lost hit-rate on `web_0` 128K. The cycle insight therefore names the opposite direction as the next experiment. This hypothesis tests that direction directly. In 2-slot buckets the non-hottest item is the LRU one. Today, hitting it only swaps it to MRU, so it needs a second hit to reach probing, and in the meantime it is the next target victim. The risk is extra churn in probing, which `hm_0` may dislike, so compare per-trace cells as well as the mean. This hypothesis is independent of H01 (where probing arrivals land) and H03 (re-admitting recently evicted keys).
