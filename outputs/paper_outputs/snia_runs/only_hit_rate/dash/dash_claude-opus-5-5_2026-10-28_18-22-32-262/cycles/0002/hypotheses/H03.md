# H03

Inserting brand-new `put` arrivals at the stash LRU end (Front) and moving them to the MRU end only on a later stash hit will raise hit-rate over v001 on the scan-heavy MSR traces, because one-hit-wonder keys get evicted ahead of demoted items that have already shown reuse.

## Parent

cycle/0001/v001

## Changes

Edits go in `src/dash/segments/dash_segment.rs`. Do not touch the gate-integrity files.

1. Override `put` in `impl Segment<K, V> for DashSegment<K, V>` so a new key enters its stash bucket at `InsertPosition::Front`, not the default `Back`. Implement it by copying the default `Segment::put` body from the segments module and changing only the stash insert position. Keep any existing-key update/overwrite handling (a put to a key that already exists anywhere in the segment must update it in place and not duplicate it) and any overflow/eviction return value exactly as the default has them. If the default `put` is not overridable as a trait method, add a `stash_put_pos()` hook with default `Back` to the segments module's `Segment` trait instead, and override it in `DashSegment` to return `Front`. The segments module is part of the overlay, not the gate surface.
2. Bimodal escape: so that a recurring working set larger than the stash doesn't thrash, keep a `u32` `put_counter` in `DashSegment` and insert at `Back` once every 32 puts (`put_counter % 32 == 0`). All other puts go to `Front`. This is the BIP rule from Qureshi et al.'s "Adaptive Insertion Policies" paper (ISCA 2007).
3. Keep v001's demotion stash position (`Back`) and all `promotion_get` logic unchanged. A first stash hit still promotes to the target, so a new item that is reused before falling off the LRU end behaves as it does in v001.

Tests: `put_goes_to_stash` still passes. Add a test: put two distinct keys mapping to the same stash bucket, then check that the second put sits at index 0 (Front), unless it was the 1-in-32 Back insert. Reset or seed `put_counter` so the test is deterministic. Also check that a demoted item still lands behind (at a higher index than) a fresh Front-inserted put.

Invariants: a key still goes only to its own `Slot::Stash` bucket, an existing key is never duplicated, and stash overflow still evicts the LRU (index 0) item.

## Rationale (optional)

v001 fixed demoted items being ranked below new arrivals by moving demotions to the Back. New puts still share the Back with them, so a scan of cold keys still pushes reused items toward eviction. This hypothesis changes stash *insertion of fresh keys*, a third lever separate from H01 (stash exit gate) and H02 (frequency admission into target). Risk to watch: at 16K, keys with a short first reuse distance may be evicted before their first hit. The 1/32 Back escape and comparing results across both sizes will show whether that happens.
