# H03

Shrinking the small admission queue from 25% to 10% of capacity, the paper's default, will raise hit rate on the larger MSR cache sizes by giving more room to the main queue.

## Parent

baseline

## Changes

In `src/s3_fifo/mod.rs`, `S3Fifo::try_new()`:

- Replace `(capacity / 4).max(1).min(capacity - 1)` with `(capacity / 10).max(1).min(capacity - 1)`. Keep the special case that sets `small_size = 1` when `capacity == 1`, and keep `main_size = capacity - small_size`.
- The ghost queue stays sized to `main_size`, and its `VecDeque::with_capacity` stays the same. The ghost queue therefore grows with main, which matches the paper, where ghost is about the size of main.
- Do not change `get`, `put`, `evict_small` or `evict_main`. Graduation stays at `freq > 1` and `MAX_FREQ` stays at 3. This keeps the experiment down to a single variable: the small/main partition.

Invariants to keep: `small_size >= 1`, `main_size >= 1` whenever `capacity >= 2`, and `small.len() + main.len() <= capacity`.

Check the in-file unit tests that use `new(4)` and `new(5)`. With integer division, `4/10` and `5/10` are 0, which gets clamped to 1, while the baseline gave 1 for both. So the small size doesn't change in these tests and they should still pass unchanged.

## Rationale (optional)

Yang et al. report that a 10% small queue is robust across production traces. A 25% small queue holds new keys for longer, so more one-hit-wonders survive and the main queue loses capacity. The main queue holds the frequently reused working set, so a larger main should help most on hm_0 and web_0. The likely risk is traces with long reuse distances, where keys may get demoted before their second access. The ghost queue partly makes up for that.
