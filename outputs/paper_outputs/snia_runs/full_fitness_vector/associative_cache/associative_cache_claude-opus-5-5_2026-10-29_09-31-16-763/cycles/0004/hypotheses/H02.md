# H02

Replacing BIP's fixed every-32nd-miss MRU admission with a per-bucket hashed "recently evicted" bit set sized to 2× bucket width will raise hit rate on both hm_0 and web_0.

## Parent

cycle/0002/v001

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`.

1. Remove `BIP_MRU_PERIOD` and the period test that uses it. Add these fields to `AssociativeCacheBucket`:
   - `ghost_bits: Vec<u64>` with `ghost_words = max(1, (2 * max_size + 63) / 64)` words. That is 2 bits per slot: 4 words for 128-wide buckets, 32 words for 1024-wide buckets.
   - `ghost_mask: usize`: the number of bits rounded down to a power of two, minus 1.
   - `ghost_evictions: u32`.

   Allocate them in `new()` only when `lip` is true. Otherwise use an empty Vec.
2. Hash: `h = (key_hash as u64).wrapping_mul(0x9E37_79B9_7F4A_7C15) >> 32`, masked with `ghost_mask`. Compute `key_hash` with a cheap `std::hash::Hasher` such as `DefaultHasher`, or with `FxHash`-style mixing if `K` hashing is already available in the crate. The bucket index is derived from the key's hash too, so use high bits that are independent of it (multiply-shift as above).
3. New-key `put` under `self.lip`, in this order:
   - (a) Test the bit for `item.key`. If it is set, clear it and remember `reuse = true`.
   - (b) If the bucket is full, evict as now. If the evict returns `Some(ev)`, set the bit for `ev.key` and increment `ghost_evictions`. When `ghost_evictions >= 2 * max_size`, zero all of `ghost_bits` and reset the counter. This is coarse aging, so the filter covers about two bucket-widths of eviction history.
   - (c) If `reuse` is true, push at the MRU end. Otherwise insert at quarter depth (`len / INSERT_DEPTH_DIVISOR`), as the parent does.
4. Keep unchanged: `get_position`, `get_from_position`, the existing-key path, and the non-LIP policies. Nothing on the get path touches the bit set. You can drop `bip_tick` or leave it unused, but drop it if possible.

Invariants: `items.len() <= max_size`. The return semantics are those of the parent. False positives only cause an occasional MRU admission, which is harmless.

## Rationale (optional)

Cycle 3 showed that the reuse window must match the workload's reuse distance. A 16-key ghost missed hm_0's slow-shifting reuse on 128-wide buckets, while BIP's blind period hurt web_0. A bit set sized to the bucket covers a reuse distance of about 2·W evictions at every geometry. It costs O(1) per miss (one hash and two bit ops) instead of a 16-entry scan, so it should also avoid the put-latency penalty of cycle 3's v002. One-touch scan keys never come back within the window, so they stay at quarter depth (web_0). Keys from a shifting working set return and are admitted at MRU (hm_0). Note: the metadata-size metric cannot see this per-bucket state (about 2 bits per slot).
