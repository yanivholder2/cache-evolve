# H01

Merging the full-bucket "evict index 0, then insert at quarter depth" into a single short `rotate_left` over the first quarter of the bucket will cut put p50/p99 (per-op-time) with hit rate exactly unchanged.

## Parent

cycle/0003/v001

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`.

In the parent, when the bucket is full, a new-key `put` under `self.lip` runs two moves. First `self.evict_item()` calls `remove_at(0)`, which memmoves all `len-1` items left by one. Then `self.items.insert(len'/4, item)` memmoves another ~3/4 of the bucket right by one. Added together, about 1.75 × bucket width of 40-byte items move on every miss. The final layout is the same as `items[1..=q] ++ [new] ++ items[q+1..]`, where `q = (max_size - 1) / INSERT_DEPTH_DIVISOR`, so only the first `q+1` slots need to move.

1. In `put`, on the new-key path with `self.lip == true` and `self.is_full()`, and when this is NOT a BIP MRU tick, do not call `self.evict_item()`. Instead:
   - First check that the policy's victim is index 0: `self.eviction_policy.eviction_candidate_index(&self.items) == 0`. It should be for ClassicLRU, but verify it. If it is not 0, fall back to the parent's two-step path.
   - Let `q = (self.items.len() - 1) / INSERT_DEPTH_DIVISOR`. This matches the parent's `insert_pos`, which is computed after removal.
   - `self.items[0..=q].rotate_left(1);` then `let old = std::mem::replace(&mut self.items[q], item);`.
   - Return `(&self.items[q], Some(old))`.
2. BIP MRU ticks (`bip_tick % BIP_MRU_PERIOD == 0`) on a full bucket: replace `remove(0)` + `push` with `self.items.rotate_left(1)` + `mem::replace` of the last slot. This is the same layout with one memmove instead of two. It is optional but cheap.
3. Increment `bip_tick` exactly as the parent does, at the same point, so BIP admission timing is identical.
4. Leave unchanged: the non-full insertion path, the existing-key path, the reverse-scan `get_position`, `get_from_position`, and all non-LIP policies. Do not add fields.

Invariants: the item order after every operation must be byte-identical to the parent's, so all four hit-rate cells must match cycle/0003/v001 exactly (0.4138 / 0.558 / 0.4558 / 0.7347). If any cell differs, the rewrite is wrong. The evicted item returned is the same item (old index 0). `items.len() <= max_size`.

## Rationale (optional)

Cross-cycle insights name the quarter-depth `Vec::insert` memmove as the dominant put cost that "nothing has removed". This change does not alter the policy at all. It only removes redundant data movement: about 1.75·W item moves per miss become about 0.25·W (W = 128 or 1024). Put p50 is 123 ns in the parent, so a large drop is expected, especially at 1024-wide buckets. Get is untouched.
