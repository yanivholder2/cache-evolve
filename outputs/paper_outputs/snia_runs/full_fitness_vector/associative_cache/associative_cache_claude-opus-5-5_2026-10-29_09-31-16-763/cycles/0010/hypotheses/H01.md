# H01

Merging cycle 0009/v002's top-eighth lazy promotion into cycle 0009/v003's single-multiplicative-hash base lowers get p50 per-op-time below v003's 35 ns while keeping hit-rate within ±0.0005 of 0.541075.

## Parent

cycle/0009/v003

## Changes

Start from v003's overlay (`src/associative_cache/associative_cache_bucket.rs`, `src/associative_cache/mod.rs`, `src/shared/utils.rs`, `src/shared/item.rs`). Leave the hashing path as it is: `tag_hash` is computed once per op, `bucket_index_from_hash` uses bits 24..=55, and `tag_from_hash` uses bits 56..=63.

In `associative_cache_bucket.rs`:

1. Add `const LAZY_PROMOTE_SHIFT: u32 = 3;` beside `INSERT_DEPTH_DIVISOR`. Add a doc comment saying that a hit within the last `len/8 + 1` slots is not moved.
2. In `Bucket::get_from_position`, add an early return at the top of the `if self.lip` branch. This is exactly v002's logic:
   ```rust
   let n = self.items.len();
   if position + (n >> LAZY_PROMOTE_SHIFT) >= n - 1 {
       return &self.items[position];
   }
   ```
   It must run before the dynamic `self.eviction_policy.get_from_position(...)` call and before the `tags.remove`/`tags.push` mirror. The existing move-to-back code stays for every other position, and so does the existing `debug_assert_eq!(index, n - 1)`. Do not change the non-lip branch, which re-stamps from the per-bucket clock.
3. Both `get_hashed` and the put-update path in `put_lip` already route through `get_from_position`, so they pick up the skip automatically. Don't add a second check anywhere.

Invariants to keep:
- `tags.len() == items.len()`.
- `tags[i] == tag_of(items[i].key)`.
- The 80-byte bucket stride (`bucket_size_matches_parent` must still pass).
- No new fields.
- No writes on the get path apart from the existing move.

Tests:
- `fused_matches_reference_remove_insert` uses `RefBucket`. Update its `get` so that a hit at position `p` with `p + (len >> 3) >= len - 1` leaves the key in place. Without that it will diverge.
- Keep `hashed_paths_match_trait_paths` and `tag_hash_selection_spreads_keys` passing.

## Rationale

The two cycle-9 winners removed independent work. v003 removed a SipHash per op, above the bucket. v002 removed two memmoves and a virtual call on near-MRU hits, inside the bucket. Each beat the cycle-8 base on get p50 and p99. If the effects add up, get p50 should drop clearly below 35 ns. v002's hit-rate cost was about 1e-4, so the hit rate should land at about 0.541. Cross-cycle insights name this stacking test as the top open question. The result will confirm or refute that the two savings are independent.
