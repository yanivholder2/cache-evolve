# H03

Removing `lfu_counter` and `timestamp` from `Item` and moving per-item bookkeeping into a policy-gated per-bucket side vector shrinks `Item<u64,u64>` from 24 to 16 bytes and so cuts metadata-size, while ClassicLRU hit-rate stays bit-identical.

## Parent

cycle/0007/v003

## Changes

Start from cycle 0007/v003's overlay. It is a cross-cycle winner with the 24-byte `Item`, byte tags, the fused rotation, and the per-bucket clock.

**Precondition (check first):**
- Search the gate surface for direct uses of `.lfu_counter` or `.timestamp`: `tests/`, `src/test_utils/`, `src/bin/`, `src/factory.rs`, `src/lib.rs` and `associative_cache_jni.rs`. These files cannot be edited.
- If any of them read or write those fields, this hypothesis is infeasible as written. In that case fall back to keeping exactly one `u32` field: a single `meta: u32`, exposed via `timestamp()`/`lfu_counter()` accessor methods. Report that the size stays at 24, since 8 + 8 + 4 pads to 24.

**Main change:**

1. `src/shared/item.rs`:
   - `Item` becomes `{ key: K, value: V }`.
   - Update `Item::new`, `Display` and the module docs.
   - Replace the `item_u64_u64_is_24_bytes` test with `item_u64_u64_is_16_bytes`.
   - The `LOGICAL_CLOCK`/`tick`/`now` helpers may stay.
2. Eviction policies that read per-item state (TimestampLRU, LFU, CLOCK/GCLOCK and others under `src/shared/eviction_policy*`):
   - Change the `EvictionPolicy` trait methods that take `&[Item]`/`&mut Vec<Item>` to also take `meta: &mut Vec<u32>`, a side vector in lockstep with `items`.
   - Each policy reads and writes `meta[i]` where it used to use `items[i].timestamp` or `items[i].lfu_counter`.
   - ClassicLRU, FIFO and other policies that don't use the side vector ignore the argument.
3. `AssociativeCacheBucket`:
   - Add no field. Reuse the existing `tags: Vec<u8>` slot's role pattern by adding a second side vector only through a non-growing representation: store `meta` in the same allocation as `tags`, i.e. repurpose `tags: Vec<u8>` as a raw byte buffer.
   - On lip buckets it holds one tag byte per item, as today.
   - On non-lip buckets it holds 4 bytes per item, interpreted as `u32` via `from_le_bytes`/`to_le_bytes` helpers.
   - Every `insert`/`remove`/`push` on `items` must apply the matching operation on the buffer: 1 byte stride for lip, 4 bytes for non-lip.
   - The bucket stride must stay at 80 (`bucket_size_matches_parent`).
   - Stamping from the per-bucket `clock` now writes `meta[index]` instead of `items[index].timestamp`.
4. ClassicLRU/lip paths keep the same operations and order. `fused_matches_reference_remove_insert` and `tags_stay_in_lockstep` must pass unchanged.
5. `timestamp_lru_uses_bucket_clock` reads the stamps from the side buffer through a test helper instead of from `items[i].timestamp`.

## Rationale

Cross-cycle insights record that shrinking `Item` is the only lever that moves metadata-size, and it has been stuck at 24 since cycle 4. On the ClassicLRU main line both 4-byte fields are dead weight, because ClassicLRU never stamps or counts. Moving them into a policy-gated side buffer removes 8 of 24 bytes per item at the measured `Item<u64,u64>` type. It should also help per-op time a little, because the moves in the fused rotation and on the hit path copy 16-byte items instead of 24-byte ones. The claim is refuted if the gate surface blocks the field removal, or if hit-rate moves at all on ClassicLRU cells.
