# H02

Taking the `Box<dyn EvictionPolicy>` virtual calls off v003's ClassicLRU hit and put-update path, by moving the hit inline inside the bucket, lowers get and put p50 per-op-time with bit-identical hit-rate.

## Parent

cycle/0009/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`, starting from v003's overlay. Do not add lazy promotion; that is H01's experiment. This change isolates the cost of dynamic dispatch.

1. In `Bucket::get_from_position`, the `if self.lip` branch currently calls `self.eviction_policy.get_from_position(&mut self.items, position)`, which goes through a vtable and cannot be inlined. Replace that call with a direct move-to-back:
   ```rust
   let it = self.items.remove(position);
   self.items.push(it);
   let t = self.tags.remove(position);
   self.tags.push(t);
   let index = self.items.len() - 1;
   ```
   Add one fast path before it: when `position == self.items.len() - 1`, return `&self.items[position]` immediately. That case is already a no-op in ClassicLRU, so order is unchanged.
   This is the same order ClassicLRU produces. The existing `debug_assert_eq!(index, len - 1)` already documents it. Because `lip` is only true when `eviction_policy.name() == "ClassicLRU"`, this cannot change any other policy.
   Do not use `rotate_left` or a hand-written `ptr::copy`. Earlier cycles found both slower than plain `remove`/`push`. The goal here is only that the compiler can see and inline the moves.
2. `put_lip` and the non-full insertion branch already avoid the policy except through `evict_item`. On the lip path, replace the call there with the known index:
   - In `evict_item`, when `self.victim_is_front` is true, use `idx = 0` instead of calling `eviction_policy.eviction_candidate_index`.
   - Leave the non-lip branch untouched.
3. Keep the `debug!` and `log_enabled!` guards as they are. Keep the 80-byte stride, the tag lockstep invariant, and all existing tests unchanged; they should pass as they are, because the behaviour is identical.
4. Add one test that runs `fused_matches_reference_remove_insert`-style random traffic at bucket sizes 1, 2, 17, 300 and 1024, with hits concentrated on the last slot. It checks that the order still matches `RefBucket`.

## Rationale

After v003 removed the redundant hash, the get-hit path on ClassicLRU still pays for an opaque virtual call. That call hides `Vec::remove`/`push` from the optimizer, which therefore cannot specialise them for `Item<u64,u64>`. This is the "remove a whole unit of work" pattern, not a rewrite of the move primitive. If get p50 does not fall, the virtual call is not a significant cost, and the next profile should look at the full-key compare or bucket indexing.
