# H02

Replacing BIP's blind every-32nd-miss MRU admission with ghost-hit admission (a small per-bucket ring of recently evicted keys) will raise hit rate by restoring web_0 scan resistance while keeping the hm_0 small-bucket gain.

## Parent

cycle/0002/v001

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs`.

1. Remove `bip_tick` and `BIP_MRU_PERIOD`. Add a fixed-size ghost ring to `AssociativeCacheBucket`: `ghost: [Option<K>; GHOST_SIZE]` with `const GHOST_SIZE: usize = 16`, plus `ghost_pos: u8` (or `usize`). Initialise it to all `None` in `new`. `K: Copy`, so the array is `Copy`-initialisable as `[None; GHOST_SIZE]`. Keep it inline in the struct, not in a separate heap Vec.
2. In `put`, on the new-key path when `self.lip` is true: if the bucket is full, call `self.evict_item()` as now. When it returns `Some(evicted)`, write `evicted.key` into `ghost[ghost_pos]` and advance `ghost_pos` modulo `GHOST_SIZE`.
3. Choose the insertion position. Scan `ghost` for `Some(item.key)`. If found, the key was evicted recently and is coming back, which is evidence of reuse. In that case, set that ghost slot to `None` and insert the item at the MRU end with `self.items.push(item)`. If it is not found, insert at quarter depth (`len / INSERT_DEPTH_DIVISOR`), exactly as the parent does now.
4. Do the ghost lookup before recording the new eviction, so a key cannot match itself.
5. Leave untouched the non-LIP policies, the existing-key update path and `get_from_position`. The ghost is touched only on put misses, never on get.

Invariants: `items.len() <= max_size`. The returned `(&Item, Option<Item>)` keeps the same semantics as the parent. The ghost never holds a key that is currently resident, because a ghost hit clears its slot and the key is only re-recorded when it is evicted again.

## Rationale (optional)

The cycle 0002 v001 insight showed that BIP's fixed counter regularly promotes dead one-hit items, which costs web_0, and that the MRU path is what helped hm_0 on 128-wide buckets. Ghost-hit admission is a reuse-aware signal, as the open questions suggested. Scan items are never seen twice in the short term, so they stay at quarter depth. Items whose working set is shifting return soon after eviction and enter the protected end. The 16-entry scan runs only on put misses, so it should not affect the get p50 summary.
