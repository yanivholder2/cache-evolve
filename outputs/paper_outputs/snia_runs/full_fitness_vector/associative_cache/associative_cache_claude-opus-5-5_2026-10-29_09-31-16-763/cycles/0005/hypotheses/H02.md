# H02

Adding a dense per-bucket 1-byte key-fingerprint array, kept in lockstep with `items` and scanned in 16-tag chunks before any full-key compare, will cut get p50 (per-op-time), because absent-key scans touch 1 KB of tags instead of 24 KB of items on 1024-wide buckets, with hit rate exactly unchanged.

## Parent

cycle/0004/v003

## Changes

Edit only `src/associative_cache/associative_cache_bucket.rs` (and add a small private hasher in that file or a new non-gated module under `src/shared/`). Do not touch the gate-integrity surface.

1. **Cheap tag hash.** Implement a minimal `struct TagHasher(u64)` implementing `std::hash::Hasher`. `write_u64(x)`: `self.0 = (self.0 ^ x).wrapping_mul(0x9E37_79B9_7F4A_7C15)`. Generic `write(&[u8])` folds 8-byte chunks the same way. `finish()` returns `self.0`. Define `#[inline] fn tag_of(key: &K) -> u8` as `key.hash(&mut h)`, then `(h.finish() >> 56) as u8`. Use the top byte so the tag is independent of whatever low bits the cache uses to pick the bucket. Do NOT use `DefaultHasher`/SipHash (cycle 0004 showed SipHash on the miss path is too costly).
2. **New field** `tags: Vec<u8>` with `Vec::with_capacity(settings.bucket_size)`. Invariant: `tags.len() == items.len()` and `tags[i] == tag_of(&items[i].key)` after every public operation. Maintain it only when `self.lip` is true. For non-LIP policies leave `tags` empty and keep the parent's plain `position` scan, so their behaviour and cost are unchanged.
3. **`get_position` (lip path).** Compute `t = tag_of(key)`. Walk `tags` in chunks of 16 (`chunks_exact(16)` plus remainder). For each chunk, build a `u16` match mask with a branch-free fold (`m |= ((c[j] == t) as u16) << j`) so LLVM can vectorise it. For each set bit (`trailing_zeros` loop), compare `items[base + j].key == *key` and return the first match. Keys are unique in a bucket, so a forward scan returns the same index as the parent's `rposition`.
4. **Mirror every mutation of `items` on the lip path:**
   - The hit path, `get_from_position(position)`: ClassicLRU moves `position` to the back. After the policy call, do `let t = self.tags.remove(position); self.tags.push(t);`. Debug-assert that the returned index is `len-1`.
   - Eviction: override `evict_item` in this impl, replacing the trait default. Call `self.eviction_policy.eviction_candidate_index(&self.items)` and remove that index from both `items` and `tags`. Keep the same return value as the trait default.
   - The quarter-depth `items.insert(insert_pos, item)` is paired with `tags.insert(insert_pos, t)`. The BIP `items.push` is paired with `tags.push(t)`. Compute `t` once per put and reuse the tag already computed by `get_position`. The simplest way is a private `get_position_tagged(&self, key, t)` helper called from both `get_position` and `put`, so the hash runs once per op.
   - Find every caller of `get_items_mut()` in non-gated code (for example `associative_cache.rs`). If any caller can reorder or resize items, rebuild `tags` from `items` after it returns, or route that caller through a bucket method that keeps both in sync.
5. Leave unchanged: the `Item` layout (24 bytes), the atomic tick, LIP divisor 4, BIP period 32 and `bip_tick` timing, and the two-step evict-then-insert.

Invariants: the four hit-rate cells match the parent exactly. Add a `debug_assert!` at the end of `put` and `get_from_position` that `tags.len() == items.len()`. The gated tests compile and pass unchanged.

## Rationale (optional)

All four cycle insights conclude that get cost follows the number of full-key compares across the wide bucket. Every cycle has recommended the inline fingerprint pre-filter, and it has never been tested. The cycle 0002 key mirror failed because a `Vec<u64>` is only ~3–5× denser than items and adds a second stream on hits. A `u8` tag array is 24× denser than 24-byte items, and with 256 tag values a 1024-wide scan does about 4 false-positive key compares. Misses dominate on these traces (hit rate ~0.54), and every new-key put also runs `get_position`, so both get p50 and put p50 should fall. The extra hit-path cost is a ≤1 KB byte memmove next to the existing ≤24 KB item memmove.
