# H03

Remove the global atomic `tick()` from `Item::new` and give non-ClassicLRU policies their timestamps from the existing per-bucket `bip_tick`, so the bucket keeps the parent's size, to lower put latency (per-op-time) on the fused-rotation base.

## Parent

cycle/0006/v002

## Changes

This re-applies cycle 0006 v001's clock removal on the v002 base, without the extra `clock: u32` bucket field that is suspected of growing bucket stride.

- `src/shared/item.rs`: `Item::new` sets `timestamp: 0` and no longer calls `tick()`. Keep `tick()` / `now()` / `LOGICAL_CLOCK` defined, so that code outside the overlay scope still compiles. Keep the `item_u64_u64_is_24_bytes` test.
- `src/associative_cache/associative_cache_bucket.rs`:
  - Rename `bip_tick` to `clock: u32`, with a doc comment saying it is shared. It stays the only counter field, so `size_of::<AssociativeCacheBucket<u64,u64>>()` is unchanged. Add a unit test that asserts this size is the same as the parent's value. Compute that value from the parent layout (a `Vec`, a `Vec`, a `usize`, a `Box<dyn>`, two `bool`s and a `u32`), and assert it as a literal.
  - Lip path (ClassicLRU): `clock` is used only as the BIP miss counter, exactly as `bip_tick` was. ClassicLRU never reads `timestamp`, so no stamp is written.
  - Non-lip path: in `put`, before `self.items.push(item)`, do `self.clock = self.clock.wrapping_add(1); item.timestamp = self.clock;` (bind `item` as `mut`). In `get_from_position` for non-lip, after the policy call, stamp `self.items[index].timestamp` from a fresh `clock` increment. Do this only if the parent's policy `get_from_position` for timestamp-reading policies used `tick()`. Read the policy impls under `src/shared/` to confirm which policies stamp on a hit. Any policy-side `tick()` call that stays in place must be replaced with a bucket-provided stamp, or left alone if it is behind a policy this cache does not benchmark. Write down which choice you made.
- Add a test, `timestamp_lru_uses_bucket_clock`, that checks a TimestampLRU (or the equivalent timestamp-reading policy) bucket still evicts its oldest-touched item.
- Do not touch the tag scan, the fused rotation, the BIP period or the insertion depth.

## Rationale (optional)

Every ClassicLRU put currently runs `Item::new`, and with it a `LOCK XADD` on a shared cache line whose value ClassicLRU never reads. v001 removed this, but it also added a bucket field, and it regressed in a run that was likely noisy. This variant isolates the atomic removal while keeping bucket stride fixed, which answers cycle 0006's open question directly. The expected outcome is that all hit-rate cells stay exactly the same, put p50 goes down, and get is flat. Judge it against v002 in the same session.
