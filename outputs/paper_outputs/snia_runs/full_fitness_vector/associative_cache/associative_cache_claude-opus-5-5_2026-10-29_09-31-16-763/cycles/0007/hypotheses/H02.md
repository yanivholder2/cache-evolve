# H02

Scale the BIP MRU-admission period with bucket width (keep 1/32 on buckets of 256 slots or fewer, use 1/128 on wider buckets) to raise the hit-rate summary by recovering web_0 scan resistance on wide buckets without giving up BIP's small-bucket hm_0 gain.

## Parent

cycle/0006/v002

## Changes

All edits are in `src/associative_cache/associative_cache_bucket.rs`.

- Replace the single `BIP_MRU_PERIOD: u32 = 32` constant with two constants: `BIP_MRU_PERIOD_NARROW: u32 = 32` and `BIP_MRU_PERIOD_WIDE: u32 = 128`. Add a threshold `BIP_WIDE_BUCKET: usize = 256`.
- Pick the period once, at construction, from `settings.bucket_size`. Do not store it in a new struct field, because that would change bucket stride. Instead, use a power-of-two mask kept in the existing `bip_tick: u32` budget:
  - Keep `bip_tick` as the miss counter.
  - Derive the mask in `put` as `if self.max_size > BIP_WIDE_BUCKET { 127 } else { 31 }`. This is a single compare on `max_size`, which `put` already loads for `is_full()`, so it adds no new memory traffic.
  - Test `bip` with `self.bip_tick & mask == 0`, not with `%`.
- The fused path (`p = if bip { n - 1 } else { (n - 1) / INSERT_DEPTH_DIVISOR }`) and the non-full LIP/BIP insert branches stay as they are. Only the `bip` decision changes.
- Update the `RefBucket` reference model in `fused_matches_reference_remove_insert` to use the same width-dependent period, so it still checks lockstep order. Add bucket sizes 300 and 512 to its size list (with a smaller iteration count if runtime matters), so the wide branch is exercised.
- Do not touch the get path, the tag filter, `Item`, or any other policy.

## Rationale (optional)

The cycle 0002 data shows BIP's blind 1/32 MRU admission helped hm_0 at the 128-wide bucket and cost web_0 scan resistance at the 1024-wide bucket. Five adaptive reuse signals have failed since then, but the simplest fix has never been tried: a static period chosen per bucket width. On a 1024-slot bucket, a 1/128 rate still admits about 8 items to MRU per bucket turnover, which lets a shifting working set enter. Scan keys are pushed into the protected region 4× less often. Narrow buckets keep their current behaviour, so the 16K cells should stay exactly the same as the parent's. The expected effect is concentrated in the 131072-size cells (web_0 up, hm_0 roughly flat). Per-op cost should not change.
