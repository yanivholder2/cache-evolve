# H02

Skipping the MRU move on a ClassicLRU hit when the item already sits in the top eighth of the bucket (lazy promotion) will lower get p50 per-op-time while keeping hit-rate within ±0.0005 of the parent.

## Parent

cycle/0008/v002

## Changes

Edit `src/associative_cache/associative_cache_bucket.rs`, in `Bucket::get_from_position`, lip branch only.

Today every lip hit calls `self.eviction_policy.get_from_position(&mut self.items, position)` through a dynamic call. That runs `items.remove(position)` + `push`, a memmove of `n-1-position` 24-byte items, followed by `tags.remove(position)` + `tags.push(t)`, a second memmove. Lazy promotion removes both memmoves and the dynamic call for hits on items that are already near MRU.

1. Add `const LAZY_PROMOTE_SHIFT: u32 = 3;`, so the window is `n >> 3`.
2. At the top of `get_from_position`, when `self.lip`:
   ```
   let n = self.items.len();
   if position + (n >> LAZY_PROMOTE_SHIFT) >= n - 1 { return &self.items[position]; }
   ```
   This returns without reordering when the hit lies in the last `n/8 + 1` slots, which includes the existing case `position == n-1`. For `n < 8`, the window covers only the MRU slot, so narrow and tiny buckets behave exactly as before, apart from the no-op skip at `n-1`.
3. Otherwise, keep the existing policy call plus the `tags` remove/push unchanged. Do not hand-write the move: cycle 0008 v001 showed that `ptr::copy` on this path was slower.
4. The put-update path (an existing key in `put`) calls `get_from_position`, so it inherits the same rule. That is intended.
5. No new fields. Stride stays at 80. BIP, insertion depth and the fused rotation are untouched.

Tests:
- Update `RefBucket::get` in `fused_matches_reference_remove_insert` to apply the same window rule: only `remove`+`push` when `p + len/8 < len - 1`. Order must still match exactly at every listed size.
- Add `lazy_promote_window`: on a full 64-slot bucket, a hit at index 63-8 leaves the order unchanged, and a hit at index 63-9 moves the item to the back.

Expected result: the 16384 cells move very little. The wide 131072 cells may shift slightly in either direction. Get p50 should drop because the hottest keys (hm_0 and web_0 are skewed) mostly sit near MRU and no longer pay two memmoves. If hit-rate falls by more than 0.0005, retry with shift 4 (`n/16`). If it is flat, try shift 2.

## Rationale (optional)

Earlier hit-path reorderings failed because they added writes (swaps) or replaced the move primitive. This change removes the move entirely for a well-defined class of hits. It is the "lazy promotion" idea from FIFO-reinsertion/CLOCK work, applied to the LRU list. Moving an item from position n-1-k to n-1 changes only its rank among the top k items, all of which are far from the eviction end. So under a quarter-depth LIP policy the eviction order should barely change.
