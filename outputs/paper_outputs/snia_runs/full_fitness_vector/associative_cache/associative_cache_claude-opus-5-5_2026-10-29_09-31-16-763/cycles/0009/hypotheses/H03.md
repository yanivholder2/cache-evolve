# H03

Computing one cheap multiplicative hash per operation at the cache level, using it for both bucket selection and the 1-byte tag, will lower get and put p50 per-op-time by removing the separate bucket-index hash.

## Parent

cycle/0008/v002

## Changes

Location: the cache-level `get`/`put` in `src/associative_cache/` (the `AssociativeCache` impl that picks a bucket for a key; not the JNI file), plus `associative_cache_bucket.rs`.

Today each op hashes the key twice: once at the cache level to choose a bucket, and once more inside the bucket in `tag_of` (`TagHasher`, a single multiply for integer keys). This change removes the cache-level hash.

1. First, read how the cache maps a key to a bucket index and write down what you find in the variant notes. If it uses `DefaultHasher`/SipHash or any `BuildHasher`, this is the main cost being removed. If it already uses a trivial integer hash, keep the change anyway (it still removes one hash) and say so.
2. Make `tag_hash<K: Hash>(key) -> u64` a `pub(crate)` function in the bucket module that returns the full `TagHasher` finish value `h`. `tag_of` becomes `(h >> 56) as u8`.
3. At the cache level, compute `h` once per op. Choose the bucket with bits 24–55, so it does not overlap the tag byte (bits 56–63) and avoids the weak low bits of a multiplicative hash: `idx = (((h >> 24) as u32) as usize) % num_of_buckets`. If `num_of_buckets` is always a power of two, use a mask instead. Keep the `%` fallback for other values.
4. Add inherent `AssociativeCacheBucket` methods `get_hashed(&mut self, key, t: u8)` and `put_hashed(&mut self, item, t: u8)`. They are the lip branches of the existing `get`/`put` with the tag passed in. The cache calls them when the bucket is lip. Non-lip buckets and the `Bucket` trait methods stay as they are, so trait callers and tests keep working.
5. Do not change BIP, insertion depth, the fused rotation, `Item`, or stride.

Expected effect: the bucket mapping changes, so hit-rate cells will move a little, with no systematic direction. Accept the change if the summary stays within ±0.0005 of the parent. Get and put p50 should both drop by about one hash's cost (several ns if SipHash was in use).

Tests: add an overlay test checking that `tag_hash`-based selection spreads 1<<20 sequential and strided keys (stride 8 and 4096, matching MSR block addresses) across 64 and 1024 buckets with a max/min occupancy ratio below 1.5. Keep all existing bucket tests passing.

## Rationale (optional)

The cycle 8 open question was "where does the remaining miss-path time go: key compare, rotation, or bucket hashing/indexing?". Cycles 5 to 8 worked only inside the bucket. This is the first hypothesis aimed at the per-op cost above it, and it removes a whole unit of work rather than reshaping a loop.
