# H02

Aging the count-min sketch by halving every counter after each `10 × capacity` increments, with counters capped at 15, will raise mean hit-rate on the MSR grid by letting stale formerly-hot keys lose admission contests.

## Parent

baseline

## Changes

Keep the residency structure (single LRU recency list plus the admission contest in `put`) exactly as it is. Change only `CountMinSketch` in `src/tiny_lfu/mod.rs`:

- Add `additions: usize` and `sample_size: usize` fields. Set `sample_size = 10 * capacity` (at least 16), passing capacity through `CountMinSketch::new(width, capacity)` from `TinyLfuCache::try_new`.
- Change `MAX_COUNT` from `u32::MAX` to `15`, so that halving has a meaningful bounded range like Caffeine's 4-bit counters. The storage type can stay `u32`; this hypothesis is about aging, not about bytes.
- `increment`: use conservative update. Compute the current minimum across the rows, then bump only the rows whose counter equals that minimum, and only if it is below `MAX_COUNT`. Increase `additions` by 1 only if at least one counter was bumped. When `additions >= sample_size`, call a new `reset()`.
- `reset()`: shift every counter in every row right by one (`c >>= 1`), and set `additions = additions / 2` (Caffeine-style).
- Leave `estimate` unchanged (row minimum). Leave the strict `>` admission test unchanged.
- Invariants: counters never go above `MAX_COUNT`. `heap_bytes()` still reports `depth * width * size_of::<u32>()`. `get` and `put` must still call `increment` before any residency change.

## Rationale (optional)

The baseline's counters only ever grow. Over a multi-million-request MSR trace, blocks that were hot early on build up large estimates and win every later contest against fresh working-set blocks. This pins dead data in the cache. Periodic halving is the standard TinyLFU freshness mechanism, and it is absent here.
