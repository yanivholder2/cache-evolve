# H01

Merging cycle 0005's window floor and pairwise conservative update into the 24-byte u32-link line, with `increment_hashed` forced inline, will raise hit-rate to at least 0.559 while keeping metadata-size at 24 and per-op-time near v001's 39 ns.

## Parent

cycle/0005/v001

## Changes

All edits go in `src/tiny_lfu/mod.rs`. Keep the residency layer exactly as it is in the parent: u32 links, tagged single-store `prev`, `get_unchecked` node access, the 4-slot `lists` array, and the `node_is_24_bytes` and `mixed_ops_keep_lists_consistent` tests.

1. **Window floor (from cycle/0005/v002).** In `TinyLfuCache::try_new`, replace
   `let window_cap = (capacity / 100).max(1);` with a size-aware floor:
   `let pct1 = (capacity / 100).max(1); let pct5 = capacity * 5 / 100; let window_cap = pct1.max(pct5.min(820));`.
   Guard against `window_cap >= capacity` for tiny capacities: clamp to `capacity.saturating_sub(1).max(1)` when capacity > 1. At capacity 2, `window_cap` must stay 1 so the existing eviction tests still pass. `main_cap` and `protected_cap` keep the same derivation: `protected_cap = 0.8 * (capacity - window_cap)`. At 131072, pct1 = 1310 is larger than min(pct5, 820), so the large size stays bit-identical to the parent.

2. **Pairwise conservative update (from cycle/0005/v003).** Replace the body of `CountMinSketch::increment_hashed` with the branchless pairwise form:
   - Read all four counters `c0..c3` using the existing `position(h, i)`. Rows own disjoint word pairs, so no re-read is needed.
   - Compute `m01 = min(c0,c1)`, `m23 = min(c2,c3)`, `live01 = m01 < 15`, `live23 = m23 < 15`.
   - Add `((c_i == m_pair) & live_pair) << s_i` to each word.
   - Increase `additions` by `(live01 | live23)`, then run the existing reset check.

   Keep v001's `reset()` exactly as it is, **including** the odd-count correction (`additions = (additions - min(odd >> 2, additions)) >> 1`). Do not copy v003's simplified `additions >>= 1`. That reset difference is the leading suspect for the unexplained hit-rate mismatch between the 24-byte and 40-byte lines. Keeping v001's reset makes this merge's sketch differ from v001's only in the update rule.

3. **Inlining.** Change `increment_hashed` and `estimate_hashed` from `#[inline]` to `#[inline(always)]`. This checks the open question of whether conservative update's latency cost was really an out-of-line call. `reset` stays `#[cold]`.

4. Update the sketch unit tests that assumed plain increment (`sketch_ages_by_halving` expects exact counts for a single key). Under conservative update with a single key, all four counters stay equal, so the expected values should not change. Verify this and adjust only if needed. Add one test showing that, for two keys sharing a block, a counter that is not the pair minimum is not bumped.

## Rationale (optional)

Cycles 2–5 found every time that winners from separate axes add up. v002's floor (small-size gain) and v003's pairwise conservative update (large-size gain) each still sit on the 40-byte line. v001 has none of either hit-rate lever. This merge puts all three axes on the cheapest residency layer. The prediction: hit-rate is about v002's 0.5592 (within ±0.001), and per-op-time is within noise of v001. If per-op-time regresses again despite `inline(always)`, conservative update's latency cost is real and not an inlining artifact.
