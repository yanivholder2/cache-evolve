# H02

Letting each sketch row address all 128 counters of its 64-byte block instead of a private 32-counter word pair will raise hit-rate at the 131072 size, with no change to sketch heap bytes or node size.

## Parent

cycle/0005/v001

## Changes

Edit only `CountMinSketch` in `src/tiny_lfu/mod.rs`. Leave the residency layer, `try_new` and the hasher untouched.

1. **Wider in-block addressing.** Rewrite `CountMinSketch::position(h, i)` so that row `i` takes 7 bits from byte `i` of the low 32 hash bits:
   `let b = (h >> (i * 8)) as u32 & 0x7F; let word = ((b >> 4) & 7) as usize; let shift = (b & 0xF) << 2;`.
   Each row then chooses any of the 8 words (128 positions) rather than only words `2i`/`2i+1` (32 positions). The block index (high 32 bits) and the block count stay the same, so `heap_bytes()` is unchanged (8192 at cap 1024; `sketch_heap_within_budget` must still pass).

2. **Intra-key collisions.** Two rows of the same key may now land on the same nibble (probability about 6/128 per key). Make `increment_hashed` safe for this case: keep the per-row loop, but for each row read the current value from `block[w]` at the moment of increment. The existing loop already does this, so a duplicated counter is simply bumped twice and saturates at 15 as before. `estimate_hashed` needs no change, because a min over duplicate positions is still valid. Do **not** add de-duplication logic to the hot path.

3. Keep plain increment, which is the parent's update rule. This isolates the addressing change from conservative update, so its large-size effect can be compared directly with conservative update's known gain (+~0.005 on web_0 at 131072).

4. Add a unit test: for 10k random hashes, the 4 `(word, shift)` positions are spread over all 8 words (each word gets at least 5% of placements).

## Rationale (optional)

The cross-cycle insights attribute the large-cache slip to correlated in-block overestimation. At 131072, about 80 additions per aging period land in each block, but each row spreads them over only 32 nibbles. That saturates 4-bit counters and inflates `victim_freq`/`cand_freq` in close contests. Spreading each row over 128 nibbles cuts the expected collision load per counter by about 4×, at no memory or extra-instruction cost. This is the "lever beyond conservative update" the open questions ask for. Prediction: web_0 and hm_0 at 131072 rise by roughly as much as conservative update gave, and the small size stays flat. If it works, it should combine with H01's conservative update in a later cycle.
