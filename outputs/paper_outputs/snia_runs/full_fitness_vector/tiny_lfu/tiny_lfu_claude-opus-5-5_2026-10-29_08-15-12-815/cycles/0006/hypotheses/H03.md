# H03

Prefetching the sketch block as soon as the key hash is known, and doing the map probe before the sketch increment, will cut per-op-time (get p50/p99 and put p50) below v001's 39 ns by overlapping the two independent cache misses on each op.

## Parent

cycle/0005/v001

## Changes

Edit only `src/tiny_lfu/mod.rs`. Hit-rate must stay bit-identical to the parent: the sketch update rule and the admission order stay the same, and only the instruction order changes.

1. **Prefetch helper.** Add `CountMinSketch::prefetch(&self, h: u64)` with `#[inline(always)]`. It computes `block_index(h)` and issues a read prefetch of that block. On x86_64, use `core::arch::x86_64::_mm_prefetch(ptr as *const i8, _MM_HINT_T0)` inside `unsafe`. On aarch64, use `core::arch::aarch64` `_prefetch` if stable, otherwise a no-op. Gate it with `#[cfg(target_arch = ...)]` and use an empty fallback elsewhere. No new dependency and no `Cargo.toml` change.

2. **`get` reorder.** `h = key_hash(key)`, then `self.sketch.prefetch(h)`, then the map probe (`self.map.get(&probe)`, copying the index out), then `self.sketch.increment_hashed(h)`, then `on_hit` on a hit. The increment must still run on a miss, so restructure to `let found = self.map.get(&probe).copied(); self.sketch.increment_hashed(h); let idx = found?; ...`. This also stops the increment's store from sitting in front of the map's dependent loads.

3. **`put` reorder.** Same pattern: hash, prefetch, map probe, then increment before any branching on the probe result. Semantics are unchanged because the increment happens before `evict_one` either way.

4. **`evict_one`.** After computing `cand_h` and `victim_h`, call `prefetch` on both before the two `estimate_hashed` calls, so the two block loads are in flight together instead of in series.

5. Change `increment_hashed` and `estimate_hashed` to `#[inline(always)]` so the reordered code is not split across a call boundary.

6. Add a test that runs the same 10k-op skewed sequence as `mixed_ops_keep_lists_consistent` and checks the final resident key set against a copy of the parent logic. Alternatively, simply keep that test and add a hit-count assertion against a recorded constant.

## Rationale (optional)

At 131072 the sketch is about 1 MB and the map is several MB, so every op takes one likely-missing sketch block load and one likely-missing map bucket load. Today the increment's load is issued first, and the map probe's loads issue only after its store sequence. Moving the prefetch up and the increment after the probe lets both misses overlap, a memory-level-parallelism win that affects tails most. The idea is new: the earlier latency attempts went after branches or the min chain, which the cross-cycle insights rule out. Because per-op-time is noisy, the implementer should judge this only from repeated runs interleaved with v001.
