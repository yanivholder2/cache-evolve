# H03

Suppressing the duplicate sketch increment when `put` immediately follows a missed `get` of the same key will raise hit-rate above v001's 0.5603, because newcomers will stop getting a +2 frequency head start over residents.

## Parent

cycle/0006/v001

## Changes

On a miss, the trace driver calls `get(k)`, which increments, and then `put(k, v)`, which increments again. A key's first appearance therefore counts 2, while a hit on a resident counts only 1. This inflates one-hit-wonder candidates in the `evict_one` contest and makes conservative-update counters saturate and alias sooner.

In `src/tiny_lfu/mod.rs`:

1. Add a field `last_miss_h: u64` to `TinyLfuCache`, initialised to a value that can never be a real hash match. Use `0` together with a `last_miss_valid: bool`, or reserve a sentinel. The fixed struct grows by at most 16 bytes, and node size and sketch bytes do not change, so metadata-size stays 24.
2. `get`: keep `increment_hashed(h)` as is. On the miss return path, set `self.last_miss_h = h` and mark it valid. On a hit, clear the valid flag.
3. `put`: compute `key_h`. If `last_miss_valid && key_h == last_miss_h`, skip `increment_hashed(key_h)`. Otherwise increment as today. Clear the valid flag in both cases. Leave the update-in-place and insertion logic unchanged.
4. Do not change `evict_one`, the window floor, pairwise conservative update or `reset()`. `additions` now advances about once per access instead of twice per miss, so the effective aging period lengthens for miss-heavy traces. Keep `SAMPLE_FACTOR = 10` so this is a single-variable test.

Tests: a standalone `put` with no prior `get` still increments. `get(k)` miss followed by `put(k)` yields an estimate of exactly 1. `get(a)` miss followed by `put(b)` increments `b`. Update the existing eviction tests' expectations if their frequency arithmetic relied on the double count.

## Rationale (optional)

Cross-cycle notes say large-size hit-rate needs better frequency evidence, not counter placement. Removing a systematic per-miss overcount is a direct accuracy fix at zero metadata cost, and it should help most at the large size, where v001 dipped on hm_0.
