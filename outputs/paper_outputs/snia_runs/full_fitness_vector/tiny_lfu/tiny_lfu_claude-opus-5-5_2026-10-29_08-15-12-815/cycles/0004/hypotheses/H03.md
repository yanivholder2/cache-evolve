# H03

Raising the fixed admission window from 1% to 5% of capacity, with the frequency contest kept on every window eviction, lifts hit-rate at the 16384 cache size without adding any per-op work.

## Parent

cycle/0003/v001

## Changes

In `TinyLfuCache::try_new` (`src/tiny_lfu/mod.rs`), change `let window_cap = (capacity / 100).max(1);` to `let window_cap = (capacity * 5 / 100).max(1);`. Add a named constant `WINDOW_PERCENT: usize = 5` and use it there. Keep `main_cap = capacity - window_cap` and `protected_cap = (main_cap as f64 * 0.8) as usize` as they are. For `capacity == 1`, also clamp so that `window_cap <= capacity`. The existing tests for capacities 1 and 2 must still pass, since `(2*5/100).max(1) = 1`.

Make no other changes. `put`, `evict_one`, `on_hit` and the sketch stay identical. In particular, every candidate leaving the window must still go through the `cand_freq > victim_freq` contest in `evict_one`. The only extra contest-free migration is the existing warm-up path ("spare room in main"), which already exists.

## Rationale (optional)

Cycle 0002's hill climber gained hit-rate only at the small cache size and paid per-op latency for its runtime bookkeeping. The open question is whether that gain came from a larger window or from skipping the contest. This variant fixes a larger window at zero runtime cost and keeps the contest on every window eviction. If 16384-size hit-rate rises, a static window explains the climber's gain. If it does not, the gain came from skipping the contest, and adaptivity can be dropped for good. The MSR web/hm traces have recency bursts that a 1% window (164 entries at the small size) is likely too small to absorb.
