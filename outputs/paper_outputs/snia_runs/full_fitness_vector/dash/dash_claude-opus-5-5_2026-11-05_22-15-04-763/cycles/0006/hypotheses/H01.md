# H01

Allowing the single deferred promotion only when the stash bucket has free slots will recover small-cache hit rate while keeping cycle 0005 v002's `put` p99 gain.

## Parent

cycle/0005/v002

## Changes

Edit the second-stash-hit branch on the `get` stash-hit path. This is the branch that today defers promotion once when the target and probing normal buckets are both full. Add a stash-pressure condition to it:

- Defer (keep the item in stash, record the deferral in the existing `lfu_counter` state, MRU-touch as today) only if target and probing are both full **and** the stash bucket holding the item has at least one free slot (`stash_bucket.len() < STASH_SLOTS`, using the existing capacity constant for stash buckets).
- If target and probing are both full and the stash bucket is full, promote immediately. Use the parent's normal second-hit chain, `remove_at` → `promote_to_target` → `demote_from_normal_bucket` with MRU demotion into stash. This is the same as cycle 0004 v002's behaviour.
- Leave every other branch unchanged: the first-hit gate, probing-room overflow, and the forced promotion on the third hit for items that were deferred.

Read the stash bucket length once, next to the two normal-bucket lengths the branch already reads, so the hit path gains no extra bucket access. Do not add new per-item fields. Metadata must stay at 40 B.

## Rationale (optional)

Cycle 0005 v002 gained at 131072 and lost at 16384. The insight says this is because deferred items take up stash slots under pressure. The stash bucket's fill level is a direct local signal of that pressure. When it is full, deferring would push out a candidate still waiting for its second hit, so the parent's immediate promotion is the better choice there. Expected result: 16384 hit rate back to cycle 0004 v002 levels, 131072 roughly the same, and `put` p99 between the two parents.
