# H01

Keeping a twice-hit stash item in stash (touched to MRU, mark kept) whenever both its target and probing buckets are full, instead of forcing a promotion that evicts a target resident, lowers `get` p50/p99 on top of cycle/0003/v002 while holding hit rate.

## Parent

cycle/0003/v002

## Changes

All changes are in `src/dash/segments/dash_segment.rs`, inside the stash branch of
`promotion_get` (the `counter != 0`, second-stash-hit path).

Today the second hit always calls `remove_at` up front. It then chooses between
probing overflow (`t_len >= max && p_len < max`) and `promote_to_target`. The
second option runs the full `put_at(Target)` → `demote_from_normal_bucket` →
`put_at(Stash, Back)` chain and then re-scans the target with `get_position`.

New behaviour:

1. Read `max`, `t_len`, `p_len` **before** removing the item from stash.
2. If `t_len < max`: same as today. `remove_at`, clear `lfu_counter = 0`,
   `promote_to_target(core, data, insert_pos)` (no eviction happens, since the target has room),
   return it from target.
3. Else if `p_len < max`: same as today's overflow branch (`remove_at`, clear
   mark, `promote_to_probing`, return it from probing).
4. Else (target and probing both full): **do not promote.** Leave the item in
   stash with its `lfu_counter` unchanged (still ≥ 1, so the next hit tries to
   promote again), and return
   `Some(core.stash_buckets[stash_idx].get_from_position(item_idx))`. This
   matches the first-hit path, so under ClassicLRU it moves the item to stash MRU.
   Add a `debug!` line for this "deferred promotion" case.

Do not change `demote_from_normal_bucket`, `promote_to_*`, the first-hit marking,
the target or probing branches, or `put`. With this change the stash-hit path never
starts a demotion cascade. Cascades now come only from target-hottest → probing
promotions.

Tests: replace `second_stash_hit_falls_back_to_target_when_both_full` with
`second_stash_hit_defers_when_both_full`. With target and probing pre-filled, it
asserts that after put + get + get the key is still in its stash bucket at the
MRU end with `lfu_counter >= 1`, that target and probing contents are unchanged,
and that no target filler appears in any stash bucket. Then free one slot in target
(e.g. `remove_at(0)`), call get again, and assert the key is now in target. Keep
every other test. `second_stash_hit_promotes_to_target` and
`second_stash_hit_uses_probing_when_target_full` must still pass. Do not touch
`tests/`.

## Rationale (optional)

In cycle 0003, v002's overflow cut cascades and that recovered most of the
`put` p99 regression. That is the clearest evidence that cascade count drives the
tail. This change removes the remaining cascades on the stash-hit path. Retention
should hold for two reasons. Stash is searched first, so a hot item kept in stash
is still a cheap hit. Also, the target LRU resident it would have evicted only
gets an MRU stash slot anyway (c3: placement on top of MRU demotion adds little).
Risk to watch: more stash occupancy could push `put` p99 back up. hm_0 at the
large size is the cell that will show any retention loss.
