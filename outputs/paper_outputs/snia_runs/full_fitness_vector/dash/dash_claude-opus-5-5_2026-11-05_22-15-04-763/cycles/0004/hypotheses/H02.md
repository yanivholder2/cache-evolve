# H02

Gating the target-hottest → probing promotion in `promotion_get` on the probing bucket having free space (otherwise touching the item in place in target) removes the probing → target → stash demotion cascade from normal-tier hits and lowers `get` p50 relative to cycle/0003/v002.

## Parent

cycle/0003/v002

## Changes

All changes are in `src/dash/segments/dash_segment.rs`, inside the target branch
of `promotion_get` (`if let Some(item_idx) = core.buckets[target_idx].get_position(key)`).

Today, when `is_hottest` is true, the item is removed with `remove_at` and
`promote_to_probing` is called. If probing is full, that evicts the probing
LRU, which then runs `demote_from_normal_bucket`. A foreign resident is retried
into its own target at Front, and may cascade a second item into stash. Then
`get_position` re-scans probing.

New behaviour:

- Compute `probing_has_room = core.buckets[probing_idx].size() <
  core.buckets[probing_idx].get_max_size()`.
- If `is_hottest && probing_has_room`: keep today's path (`remove_at`,
  `promote_to_probing`, return from probing). No eviction can happen here.
- Otherwise (not hottest, or hottest but probing is full): return
  `Some(core.buckets[target_idx].get_from_position(item_idx))`, the existing
  intra-bucket touch. The item stays at target MRU and tries again on its next hit.
  Add a `debug!` line for the "hottest but probing full → stay" case.

Leave the stash branch (two-hit gate, overflow, fallback to target) unchanged.
Also leave `demote_from_normal_bucket`, the `promote_to_*` helpers, the probing
branch and `put` unchanged. The cascade code is still reachable from
`promote_to_target` on the second stash hit.

Tests: `probing_eviction_demotes_to_target` and
`cascade_demotion_probing_to_full_target_to_stash` set up a full probing bucket
and expect `get` to promote into it. Rewrite them to assert the new behaviour: the
hottest target item stays in target, and probing contents are unchanged. Keep the
cascade mechanics covered by the direct-call tests (`evicted_from_probing_cascades_to_target`,
`target_retry_*`, `cascade_to_stash_at_mru`, which call `promote_to_probing`
directly and are unaffected). Add `target_hottest_promotes_when_probing_has_room`,
which asserts that the promotion still happens with an empty probing bucket.
Do not touch `tests/`.

## Rationale (optional)

H01 targets cascades on the stash-hit path. This hypothesis targets the other
source: normal-tier hits that start the probing eviction chain. That chain does
up to three bucket mutations and a stash insert on a `get` that was already a
hit. Testing the two paths separately shows which one carries the remaining
`get` p50 gap to baseline (93 vs 75 ns). Hit-rate risk: the probing tier fills
less aggressively with hot items. Expect a small effect, because under ClassicLRU
the item is still protected at target MRU.
