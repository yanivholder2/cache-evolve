# H01

Making bucket key lookup (`get_position`) scan from the MRU end toward the LRU end, instead of from the LRU end, shortens the common hit path in `promotion_get` and lowers `get` p50 compared with cycle/0004/v002, while hit rate stays exactly the same.

## Parent

cycle/0004/v002

## Changes

This is a lookup-only change. Placement and eviction decisions stay exactly as they are,
so the hit rate must be identical to v002's on every cell. This doubles as the test that
the change is purely a cost change.

1. Find the bucket implementation behind `get_position(&K) -> Option<usize>`. That is the
   bucket type used by `SegmentCore::buckets` and `SegmentCore::stash_buckets`, reached
   through `crate::shared::traits::bucket`. It lives under `src/shared/` (not on the
   gate-integrity surface). Today the linear scan goes over `items` in index order
   (`0..len`). Under ClassicLRU, index 0 is the LRU end (`InsertPosition::Front`) and the
   last index is the MRU end (`InsertPosition::Back`, where `get_from_position` moves
   touched items).
2. Change the scan to go in reverse: `items.iter().rposition(|it| it.key == *key)`, or an
   equivalent reverse index loop. It must return the same index the forward scan would.
   Keys are unique within a bucket, so the result is unchanged. Only the number of
   comparisons changes.
3. If the bucket also has a separate `contains`/`get`/lookup helper used by `put` (for the
   update-in-place check), change it to the same reverse order so `put` updates of hot keys
   get cheaper too. Leave any eviction-victim selection (`promotion_candidate_index`, LRU
   victim choice) untouched.
4. Do not change `dash_segment.rs` logic. The two-hit gate, MRU demotion, probing overflow
   and the probing room gate all stay as they are in v002.

Tests: add a unit test next to the bucket code that fills a bucket, then checks that
`get_position` returns the right index for the first, middle and last item, and `None` for
an absent key. Every existing `dash_segment.rs` test must pass unchanged. Do not touch
`tests/`.

## Rationale (optional)

Four cycles of cascade work never moved `get` p50 (93 vs baseline 75). Cycle 4 placed the
gap on the common hit path. Under this policy line, re-referenced items sit at the MRU end
on purpose: first stash hits move to stash MRU, demotions enter stash at MRU (`Back`), and
target/probing hits move to MRU. A forward scan reaches the item it is most likely to find
last, and it does this in every bucket probed (stash, then target, then probing). The
baseline promotes stash items out on the first hit, so fewer hot hits land at the far end
of a scan, which plausibly explains part of the gap. If p50 does not move, scan length is
ruled out and the gap must be in the move-to-MRU shifting cost instead.
