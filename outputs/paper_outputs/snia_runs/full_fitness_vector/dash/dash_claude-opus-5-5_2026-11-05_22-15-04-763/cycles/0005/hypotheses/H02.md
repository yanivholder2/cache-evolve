# H02

Limiting deferred stash promotions to one deferral (when target and probing are both full, the second stash hit defers and the third force-promotes through the target cascade) recovers v002's `put` p99 regression without giving up its hit-rate gain.

## Parent

cycle/0004/v002

## Changes

All changes are in `src/dash/segments/dash_segment.rs`, in the stash branch of
`promotion_get` (the `counter != 0` path after the first-hit early return). Use
`lfu_counter` as a small stash-hit count: 0 means unmarked, 1 means hit once, and 2 means
promotion deferred once.

1. Before calling `remove_at`, read `counter`, `max`,
   `t_len = core.buckets[target_idx].size()` and
   `p_len = core.buckets[probing_idx].size()`.
2. If `t_len < max`: `remove_at`, set `lfu_counter = 0`, call `promote_to_target`, and
   return the item from target (same as today; no eviction).
3. Else if `p_len < max`: same as today's probing overflow. `remove_at`, clear the mark,
   call `promote_to_probing`, and return the item from probing.
4. Else (both full) and `counter == 1`: **defer once.** Leave the item in stash, set
   `get_items_mut()[item_idx].lfu_counter = 2`, and return
   `Some(core.stash_buckets[stash_idx].get_from_position(item_idx))`. Under ClassicLRU this
   moves the item to stash MRU. Add a `debug!` line.
5. Else (both full and `counter >= 2`): **force the promotion.** `remove_at`, set
   `lfu_counter = 0`, call `promote_to_target` (the existing MRU-demotion cascade), and
   return the item from target with the existing `unreachable!` guard.

Under the `Lfu` policy, `get_from_position` increments the counter. Because of that, write
step 4 as `counter == 1` and step 5 as `counter >= 2`, so an Lfu increment can only move an
item toward forced promotion and can never trap it. Leave `demote_from_normal_bucket`, the
first-hit path, and the target and probing branches (including the room gate) unchanged.

Tests: replace `second_stash_hit_falls_back_to_target_when_both_full` with two tests.
`second_stash_hit_defers_once_when_both_full`: after put + get + get with both buckets
full, the key is still in stash at MRU with `lfu_counter == 2`, and target and probing are
unchanged. `third_stash_hit_forces_promotion_when_both_full`: one more `get` moves the key
into target, and the former target LRU ends up at stash MRU with `lfu_counter == 0`. All
other tests must pass. Do not touch `tests/`.

## Rationale (optional)

Cycle 4 v001 showed that unlimited deferral traps items in stash (`put` p99 went from 146
to 175). Cycle 4 v002 showed that the room gate leaves target buckets fuller, so the
both-full cascade fires more often on `put`. A single deferral filters out items that are
hit exactly twice: they never pay for the cascade or evict a resident. Items that keep
getting hit still leave stash on their third hit, so stash keeps draining. This answers
cycle 4's open question about whether a limited deferral works. Watch hm_0
at the large size: if it slips as it did in v001, the limit of one deferral is too strict.
