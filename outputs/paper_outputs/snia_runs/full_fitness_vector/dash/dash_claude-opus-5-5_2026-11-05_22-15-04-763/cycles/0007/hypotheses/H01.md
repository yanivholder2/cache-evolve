# H01

Hashing the key once per `promotion_get` and deriving the stash, target and probing indices from that one hash (instead of calling `get_index` separately for each) will lower `get` p50 toward baseline with bit-identical hit rate.

## Parent

cycle/0004/v002

## Changes

This is a cost-only change in `src/dash/segments/dash_segment.rs`. It may also touch `src/shared/utils.rs` (wherever `get_index` lives), which is not part of the gate surface.

1. Read `get_index` in `crate::shared::utils`. It almost certainly hashes the key (e.g. `DefaultHasher`/SipHash) and then reduces it modulo `size`. Split it into two parts: `hash_key(&K) -> u64`, which is exactly the hash `get_index` computes today, and `index_from_hash(h: u64, size: usize) -> usize`, which is exactly the reduction `get_index` applies today. Rewrite `get_index` as `index_from_hash(hash_key(k), size)` so every other caller behaves the same. Mark both helpers `#[inline]`.
2. At the top of `promotion_get`, compute `let h = hash_key(key);` once. Derive `stash_idx = index_from_hash(h, core.stash_size)` and `target_idx = index_from_hash(h, core.segment_size)` from it. `probing_idx` stays `(target_idx + 1) % segment_size`.
3. The stash-hit promotion path then calls `promote_to_target` / `promote_to_probing`, which rehash `item.key` through `get_index`. Add internal variants `promote_to_target_at(core, item, insert_pos, target_idx)` and `promote_to_probing_at(core, item, insert_pos, probing_idx)` that take the precomputed index, and call them from `promotion_get`. Keep the existing `promote_to_target` / `promote_to_probing` signatures as thin wrappers so the unit tests that call them directly still compile unchanged.
4. If `SegmentCore::put_at` (used by those helpers) rehashes the key internally to find the target/probing/stash bucket, give it the same treatment where possible: a `put_at_idx` that takes a bucket index, called from the promote helpers. `demote_from_normal_bucket` has to hash the *evicted* item's key, which is a different key, so leave its `get_index` call alone.
5. If the Dash top level (`src/dash/` outside the gate files) also hashes the key to pick a segment before calling `Segment::get`, do not try to share that hash across the trait boundary in this variant. Note it in a comment for a follow-up.

Invariants: every index must equal what `get_index` returns today, so bucket contents, hit rate and metadata (40 B) are bit-identical. Any hit-rate difference means a bug. Do not change lookup order (stash first), the two-hit gate, MRU demotion, probing overflow or the room gate. Do not touch `tests/`.

## Rationale (optional)

Six cycles have ruled out scan order, scan direction, the MRU shift and cascades as the source of the 18 ns `get` p50 gap. The common hit path still computes `get_index` twice up front, plus a third time inside `promote_*` on stash promotions. With a SipHash-class hasher that is roughly 10–20 ns per extra hash, which is about the size of the gap. Policy is unchanged, so this cleanly tests whether hashing cost explains the gap. A p50 drop with identical hit rate confirms it. A flat p50 points back to the stash probe itself (see H02).
