# H03

Allowing the single deferral only when the stash bucket's LRU slot holds a never-hit item (`lfu_counter == 0`) will keep cycle 0005 v002's `put` p99 gain while recovering its small-cache hit-rate loss.

## Parent

cycle/0005/v002

## Changes

All edits are in the stash branch of `promotion_get` in `src/dash/segments/dash_segment.rs`, in the "both full and `counter == 1`" defer-once step.

1. When target and probing are both full and `counter == 1`, read the stash bucket's LRU item. Under ClassicLRU that is `core.stash_buckets[stash_idx].get_items()[0]`; use the same end that stash eviction actually takes from, and check it in the bucket code. If `item_idx` itself is the LRU slot, treat it as "LRU is waiting" (see step 3).
2. **Defer** (today's behaviour: leave the item in stash, set `lfu_counter = 2`, return via `get_from_position`) only if the stash bucket is full **and** the LRU item has `lfu_counter == 0`. That LRU item was never re-hit since it entered stash, so the next stash eviction it suffers costs nothing proven. Defer as well if the stash bucket is not full, because no eviction is pending.
3. Otherwise, when the stash LRU is marked (`lfu_counter >= 1`, an item waiting for its second hit or itself already deferred), **promote now** through the existing forced path: `remove_at`, `lfu_counter = 0`, `promote_to_target` with the MRU-demotion cascade, and return from target with the existing `unreachable!` guard. Keeping the deferred item in stash here would push a reusing item out on the next `put`.
4. Leave the `counter >= 2` forced third-hit path, the first-hit marking, the probing-room overflow, the room gate and `demote_from_normal_bucket` exactly as in the parent. Do not use the fused `swap_promote` from cycle 0006 v003.
5. Tests: inside the module's `#[cfg(test)]` block only, add one test where the stash LRU is marked, so the second hit promotes immediately. Add another where the stash LRU is unmarked, so it defers once. Existing tests must pass. Do not touch `tests/`.

Metadata stays at 40 B, because the gate reuses the existing `lfu_counter`.

## Rationale (optional)

Cycle 0006 v001 showed that fill level is useless as a gate: the stash is nearly always full, so the gate never lets a deferral through and the `put` p99 gain disappears. What actually separates a harmful deferral from a harmless one is *who* the deferral's extra stash occupancy pushes out. On the small cache the LRU is more often an item still waiting for its second hit (the 0005 v002 loss). On the large cache it is mostly cold one-shot inserts, so the deferral and its `put` p99 benefit stay. Check hm_0 and web_0 at 16384 for hit-rate recovery, and confirm that `put` p99 stays near the parent's level instead of rising toward 0006 v001's 190 ns.
