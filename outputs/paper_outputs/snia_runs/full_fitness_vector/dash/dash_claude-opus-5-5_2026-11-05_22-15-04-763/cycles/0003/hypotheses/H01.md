# H01

Reordering `promotion_get` on v003 to search target, then probing, then stash (instead of stash first) lowers `get` p50/p99 per-op time without changing hit rate, because under the two-hit gate most hits land on normal-tier residents that today pay a full stash-bucket scan first.

## Parent

cycle/0002/v003

## Changes

All changes are in `src/dash/segments/dash_segment.rs`, function `promotion_get`.

The function currently has three lookup blocks, in this order: (1) the stash block
`if let Some(item_idx) = core.stash_buckets[stash_idx].get_position(key)` with the
two-hit gate, (2) the target block, which includes the hottest→probing promotion,
and (3) the probing block. Move the stash block, unchanged, so it runs **after**
the probing block. The new order is target → probing → stash → `None`. Do not change
the body of any block. Keep the first-hit mark/MRU touch, the second-hit
`remove_at` + `promote_to_target` + `unreachable!` guard, the target hottest →
`promote_to_probing` branch, and the probing touch-in-place exactly as v003 has
them. Keep the index computations (`stash_idx`, `target_idx`, `probing_idx`) at
the top.

Correctness invariant: a key lives in at most one of {its stash bucket, its target, its
probing bucket}. Every promotion and demotion path already does `remove_at` before
re-inserting. Before relying on this, the implementer must check the default
`Segment::put` / `SegmentCore` put path in `src/dash/segments/` (the module that
defines `Segment`, `SegmentCore` and `Slot`). An update of an existing key must
either overwrite it in place wherever it lives or remove the old copy, and must never
leave a stale duplicate in stash. If `put` can leave a duplicate, also change the
segment's update path in that module (not in the gate-integrity files) to overwrite in
place. If `contains_key` or a similar lookup helper in that module hard-codes stash
first, reorder it the same way for consistency. This is optional, since it does not
affect correctness when keys are unique.

Tests: add `target_resident_found_without_stash_scan_semantics`. Promote a key into
target with two gets, then `get` it again. Assert the value matches and that the key
is still only in the normal tier. Add `stash_item_still_gated_after_reorder`. Put a
key, `get` once, and assert it is still in stash and marked. `get` again and assert
it is in target. All existing in-file tests should pass unchanged. Do not touch
`tests/`.

## Rationale (optional)

Every gated variant has `get` p50 around 93–96 ns, against the baseline's 75 ns,
even v001, which removed the first-hit reorder. That shows the cost is not in the
promotion work itself. Under the gate (and more so with v003's MRU demotion), stash
buckets stay fuller with marked and demoted items. Meanwhile the reused items that
take most hits sit in target or probing, and each of those hits first runs a
linear `get_position` over a fuller stash bucket. Searching the normal tier first
removes that scan from the common hit path. It also removes a scan from the probing
case that v002 identified as its tail cost. Hit rate should be identical, because
the reorder changes no placement decision. Only one-hit-wonder lookups and misses
still pay the stash scan, and misses already scan all three buckets.
