# H03

Replacing the SipHash-class key hasher behind `get_index` (and the stash mask's `stash_bit`) with a cheap 64-bit multiplicative mixer, computed once per `promotion_get`, will cut `get` p50 below 84 ns and shrink 0007 v002's mask-refresh cost on `put` (per-op-time), with hit rate within ±0.001.

## Parent

cycle/0007/v002

## Changes

This change targets the cost of hashing itself, not mask upkeep or stash structure.

1. In `crate::shared::utils` (wherever `get_index` lives, not a gate file), add `#[inline(always)] fn fast_hash(k: u64) -> u64` using a splitmix64/murmur3-fmix64 finalizer: `x ^= x >> 33; x *= 0xff51afd7ed558ccd; x ^= x >> 33; x *= 0xc4ceb9fe1a85ec53; x ^= x >> 33;`. Keys are `u64` in the measured configuration (`Dash<u64,u64,…>`). For generic `K: Hash`, add a small `Hasher` impl (`FastHasher`) whose `write_u64` stores the value and whose `finish` applies the finalizer, with a fallback `write(&[u8])` that folds bytes 8 at a time. Then hash keys through `BuildHasherDefault<FastHasher>` instead of `DefaultHasher`.
2. Split the hash from the reduction: `hash_key(&K) -> u64` (now the fast hash) and `index_from_hash(h, size) -> usize`. Keep `get_index(k, size) = index_from_hash(hash_key(k), size)` for the other callers. Use a multiply-shift reduction `((h as u128 * size as u128) >> 64) as usize` instead of `%` if the existing code uses `%`. That makes the index depend on the high bits, so the stash fingerprint/mask bit must come from the low bits (`1u64 << (h & 63)`) to stay independent. Update `stash_bit` to match.
3. In `promotion_get`, compute `h = hash_key(key)` once and derive the stash index, target index and mask bit from it (fold in 0007 v001's single-hash idea). Pass the precomputed index into the stash-promotion helpers through `_at` variants. Keep the existing helper signatures as wrappers so the unit tests compile.
4. `refresh_stash_mask` stays as it is in v002, but every re-hash it does now uses the cheap hasher, so the per-removal cost drops sharply without any structural change.
5. If the Dash top level under `src/dash/` (excluding `jni.rs`) uses the same hasher to pick a segment, switch it to `fast_hash` as well, using bits that are disjoint from the segment-level index bits (e.g. `h >> 32` for the segment and the low 32 bits for the in-segment index). Do not touch `src/dash/jni.rs`, `src/factory.rs` or `src/lib.rs`.

Invariants: the mapping from key to bucket changes, so hit rate is not bit-identical, but the policy (gate, MRU demotion, probing overflow, room gate, stash-first lookup and stash mask) is unchanged. Treat any hit-rate move larger than about 0.001 as a sign of a bad distribution and check the bucket-load spread. `Item` stays 40 B and `Dash` stays 24 B. Do not touch `tests/`.

## Rationale (optional)

Cycle 0007 v001 removed repeated hash calls and p50 did not move, but the hasher itself was never cheapened. With SipHash, each hash call is about 15–20 ns, which is about the same size as the remaining 84 → 75 ns gap to baseline. `refresh_stash_mask` re-hashes every stash item on each removal, so a cheaper hasher should also visibly shrink v002's `put` regression. That gives a second, independent check of the upkeep diagnosis that H01 and H02 attack structurally. If p50 drops and `put` improves with hit rate flat, hash cost is confirmed as a remaining common-path cost.
