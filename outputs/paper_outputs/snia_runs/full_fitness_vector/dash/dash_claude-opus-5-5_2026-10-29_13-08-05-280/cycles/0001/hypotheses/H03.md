# H03

Requiring a second stash hit before an item can move from stash to target, with each item's stash hits counted in its existing `lfu_counter`, will raise hit-rate on the scan-heavy MSR traces by keeping one-hit items out of the protected normal tier.

baseline

## Changes

Edit only `src/dash/segments/dash_segment.rs`. ClassicLRU never reads `Item::lfu_counter`, so the segment can use that field as a reuse counter without changing the Item layout.

1. **Stash hit (`promotion_get`, first branch).** On a stash hit, add 1 to the item's counter. Use `core.stash_buckets[stash_idx].get_items_mut()[item_idx].lfu_counter = lfu_counter.saturating_add(1)`.
   - If the new counter is below `PROMOTE_THRESHOLD` (a new module `const PROMOTE_THRESHOLD: usize = 2;`), do not promote. Touch the item in place with `core.stash_buckets[stash_idx].get_from_position(item_idx)`, which moves it to the stash MRU under ClassicLRU, and return that reference.
   - Only when the counter reaches the threshold, do `remove_at` and promote to target as today.
2. **Admission comparison.** At the promotion step, if the target bucket is full, compare the candidate with the target's eviction victim (`buckets[t].eviction_candidate_index()`).
   - If the victim's `lfu_counter` is strictly greater than the candidate's, skip the promotion. Leave the candidate in stash (touched to MRU) and return it from there.
   - Otherwise promote as today.
3. **Counter lifecycle.**
   - Reset `lfu_counter` to 0 when an item is promoted into target. It has used up its stash credit.
   - In the target / probing branches of `promotion_get`, add 1 to the item's `lfu_counter` on every hit (saturating) before calling `get_from_position`, so normal-tier residents build up the frequency used in the comparison in step 2.
   - When `demote_from_normal_bucket` sends an item to stash, halve its counter (`>>= 1`) so old popularity fades over time.
   - Keep everything else in the demotion cascade and the target → probing rule unchanged.
4. Uniqueness and slot legality still hold, because an item either stays in its own stash bucket or moves to its target exactly as before.
5. Update the unit tests that expect one stash hit to promote. They must now hit twice: `stash_hit_inserts_at_front_of_target`, `target_hit_*`, `cascade_demotion_*` and `last_bucket_probing_wraps_to_zero`. Add tests that check:
   - one stash hit keeps the key in stash;
   - two hits promote it;
   - a candidate with a lower counter than a full target's victim stays in stash.

Expected outcome: higher hit-rate on web_0 and hm_0 at both sizes, because the normal tier keeps items that are reused often instead of items that appear once in a scan. Metadata-size should not change. Per-op time on a stash hit should be about the same or lower, because there are fewer promotions and fewer cascade moves.
