# H03

Make v003's full-probing guard strict, so that any non-hottest hit on a target resident resets its hottest-hit count, to raise large-cache hit-rate on web_0 by admitting only keys that stay at the hottest position.

## Parent

cycle/0004/v003

## Changes

In v003, the target-hit path in the Dash segment increments a key's `lfu_counter` on a deferred hottest-position hit to a full probing bucket. It promotes on the second such hit and resets the counter only when the key is promoted or demoted. So a counter of 1 survives any number of later non-hottest hits, and the rule is really "two hottest hits during one residence".

Change the **non-hottest target-hit arm** (the branch where the hit item is not at the hottest position and v003 currently just does the normal `get_from_position` reorder): if the item's `lfu_counter != 0`, set it to 0. Read first and write only when the value is nonzero, so the common case is a load that's already in cache plus a branch that is almost always predicted correctly. It must never be an unconditional store. As a result, promotion into a full probing bucket needs two hottest-position hits *with no non-hottest hit in between*.

Do not change:
- the `is_hottest` arm (the `is_full()` check, increment on a deferred hit, promote at 2, reset on promotion),
- promotion into non-full probing buckets (still one hit),
- the stash-side counter semantics. The reset applies only to keys that are already in target. A key's stash hit count is consumed when it is promoted into target, so the two uses do not conflict. If the parent shares `lfu_counter` between the stash gate and the probing guard, make sure the counter is 0 when the key lands in target, as v003 already does.

## Rationale

This is the stricter variant left as an explicit open question in the v003 insight and in the cross-cycle insights ("What still limits web_0 at the large size?"). web_0 at 131072 is the cell with the most headroom. The stricter rule filters keys whose popularity only flickers, and those keys trigger the full-probing cascade and displace stable probing residents. The claim is refuted if hit-rate drops, especially in small-cache cells, because target residence there is too short for two hits in a row. It is also refuted if median get rises measurably from the added check on the common hit path.
