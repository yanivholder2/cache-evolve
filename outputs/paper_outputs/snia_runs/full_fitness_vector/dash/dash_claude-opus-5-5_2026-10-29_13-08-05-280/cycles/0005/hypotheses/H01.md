# H01

Fold cycle 0004 v001's 24-byte Item layout, using a segment-local tick instead of the global `AtomicU32`, together with v002's size-gated stash guard into v003 to bring metadata-size to 24 bytes while keeping v003's hit-rate.

## Parent

cycle/0004/v003

## Changes

Start from v003 (full-target stash guard plus the new full-probing guard that needs two hottest-position hits). Apply two changes that have already been proven on their own:

1. **Item layout (from cycle/0004/v001).** In the `Item` struct, replace `timestamp: Instant` with `timestamp: u32` and make sure `lfu_counter` is `u8`. Keep the field order key, value, timestamp, counter, so that `Item<u64,u64>` is 8+8+4+1 = 21 bytes, which rounds up to 24. Do **not** reintroduce v001's process-wide `static TICK: AtomicU32`. Instead, give `DashSegment` its own `tick: u32` counter. `Item::new` (or the segment insert path that builds the Item) takes its timestamp from that counter. Every segment insert bumps it with `wrapping_add(1)`. If the insert path only has `&self`, use a per-segment `AtomicU32` with `Ordering::Relaxed`, which bounces between cores only among threads that hit that segment. Any code that used to read `Instant` (`elapsed()`, comparisons) must compare u32 ticks with wrapping-aware subtraction. ClassicLRU never reads this field, so hit-rate must stay exactly the same as v003's. The size test `item_u64_u64_smaller_than_40_bytes` already exists, so leave tests alone.
2. **Size gate (from cycle/0004/v002).** Add `full_target_guard: bool` to `DashSegment`. Set it at construction to `settings.capacity() >= GUARD_MIN_CAPACITY`, using the same constant and value as v002 (the geometric middle of 16384 and 131072). In the stash→target promotion branch, require the extra (third) stash hit for a *full* target only when `full_target_guard` is true. Small caches go back to promoting at two hits. Leave v003's full-probing guard ungated at every size. Its insight shows it already helps small caches.

Do not change anything else: get/put hit paths, eviction, the probing guard counter logic.

## Rationale

The cycle-0004 Continuation names this merge directly. It also tests the open question of whether v002's size gate still adds small-cache hit-rate once v003's target-side guard is present. The segment-local tick removes the most likely cause of v001's put-p50 regression (a contended global atomic on every insert) and keeps the 24-byte win. Expected result: metadata-size 24, hit-rate ≥ 0.3948, per-op-time no worse than v003.
