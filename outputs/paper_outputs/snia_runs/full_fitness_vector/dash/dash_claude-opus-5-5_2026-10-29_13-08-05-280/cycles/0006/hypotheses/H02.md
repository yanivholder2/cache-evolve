# H02

Replace the full-probing guard's "two hottest hits per residence" rule with a lazy tick-window check that runs only on the rare hottest arm, to capture cycle 0005 v003's large-cache hit-rate gain without adding any work to the common target-hit path.

## Parent

cycle/0005/v001

## Changes

cycle/0005/v001's Item already carries a `u32` `timestamp` taken from the per-segment tick. ClassicLRU never reads it, so this change can reuse the field as the time of the "first hottest hit" without changing the layout. Item stays 24 bytes.

In the Dash segment target-hit path, change **only** the `is_hottest` arm where the destination probing bucket `is_full()`:

- **Counter is 0 (first hottest hit):** keep the current behaviour (set `lfu_counter = 1`, defer the promotion, do the normal reorder). Also store the segment's current tick in `item.timestamp`.
- **Counter is ≥ 1 (second hottest hit):** compute `age = seg_tick.wrapping_sub(item.timestamp)`. If `age <= PROBE_WINDOW`, promote as v001 does today (same move path, same counter reset). Otherwise treat this hit as a new first hit: keep `lfu_counter = 1`, refresh `item.timestamp` to the current tick, and do not promote.
- Define `PROBE_WINDOW` as a per-segment value computed once at construction: the segment's total slot count (all buckets plus stash). The second hit must then arrive within about one segment's worth of inserts, which is roughly how long a target resident would survive anyway. Store it as a `u32` field on `DashSegment`, or compute it from existing constants if the slot count is a compile-time constant.

Do **not** touch the non-hottest target-hit arm. It must not read or write `lfu_counter` or `timestamp`; this is the key difference from cycle/0005/v003. Do not change the stash→target guard, the size gate, put, eviction, or promotion into non-full probing buckets. The per-segment tick keeps being bumped only on insert, exactly as in v001.

## Rationale

cycle/0005/v003's strict reset improved web_0-large (0.4233 → 0.4245) and hm_0-large (0.4437 → 0.4443), but the reset sat on the common hit path and raised get p50 and p99. Its real effect is to filter keys whose two hottest hits are far apart in time. A tick-age check gives the same recency filter, and it runs only when the guarded promotion is about to fire. The cycle 0005 insights say that arm fires rarely, so the median should not move. Confirmation: hit-rate ≥ 0.3954 with get p50 ≤ 76 and metadata-size 24. Refutation: hit-rate equal to v001's, which would mean the gain came from the "any non-hottest hit" signal and not from recency. Or small-cache cells drop, which would mean the window is too tight there.
