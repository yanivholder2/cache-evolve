# H01

Replacing `Item::timestamp: Instant` with a 4-byte logical access tick (`u32`) placed next to v002's `u8` counter will shrink `Item<u64,u64>` from 40 to 24 bytes, cutting metadata-size, with hit-rate unchanged.

## Parent

cycle/0003/v002

## Changes

v002 showed that `timestamp: Instant` (16 bytes, align 8) is what sets Item's size: key(8) + value(8) + Instant(16) + u8 = 33, which rounds up to 40. With a `u32` tick the layout is key(8) + value(8) + tick(4) + counter(1) = 21, which rounds up to 24.

1. In `src/shared/item.rs`, change `pub timestamp: Instant` to `pub timestamp: u32`. Keep the field name so callers can keep their call sites. Declare fields as key, value, timestamp (u32), lfu_counter (u8). Add a module-level `static TICK: AtomicU32 = AtomicU32::new(0);` and a `pub fn next_tick() -> u32 { TICK.fetch_add(1, Ordering::Relaxed) }` (`Relaxed` is fine; only relative order matters). `Item::new` sets `timestamp: next_tick()`. Update the `Display` impl to print the tick. Remove the `Instant` import.
2. Find every reader and writer of `.timestamp` in the writable overlay. That means the eviction policies in `src/shared/` (the timestamp-ordered LRU policy and any others), the buckets, and `src/dash/`. Change each `= Instant::now()` refresh on access to `= next_tick()`. Change each `Instant` comparison or `min_by_key`/`max_by_key` to compare the `u32` directly. Smaller tick = older, which is the same ordering as before. Wraparound after 2^32 accesses is acceptable for the benchmark traces. If any code computes a `Duration`/`elapsed()` from the timestamp, turn it into a tick difference using `wrapping_sub`.
3. Do not change any segment, promotion or gate logic. For ClassicLRU, which is the policy under evaluation, behaviour must match v002 bit for bit, and hit-rate must be identical.
4. Gate-integrity check: if `src/dash/jni.rs`, `tests/`, `src/test_utils/` or `src/bin/` name `Instant` in connection with `Item::timestamp`, don't edit those files. Keep the field type `u32` only if everything still compiles. Otherwise report the conflict instead of changing the protected files.

Tests: un-ignore `item_u64_u64_smaller_than_40_bytes` and add `assert_eq!(size_of::<Item<u64,u64>>(), 24)`. Add a policy unit test showing that an item touched later has a larger tick and is not chosen as the timestamp-LRU victim.

## Rationale (optional)

Metadata-size hasn't moved in three cycles. Both v002's insight and the cross-cycle open questions name this exact change as the next lever. A smaller Item also packs more items per cache line in bucket scans, which may help get latency a little. Each insert pays one atomic `fetch_add` instead of a `clock_gettime` call through vDSO, which should make it cheaper.
