# H03

Giving target residents a re-admission credit when they are demoted into stash (counter set to `PROMOTE_THRESHOLD - 1`, so one stash hit brings them back) will raise large-cache hit-rate on top of v001's gate, without adding any cost to the get hit path.

## Parent

cycle/0002/v001

## Changes

Edit `src/dash/segments/dash_segment.rs` (v001's version), function `demote_from_normal_bucket`.

1. On both stash-landing paths, replace `item.lfu_counter >>= 1` (direct `true_target == source_idx` path) and `cascade.lfu_counter >>= 1` (cascade path) with an assignment of `PROMOTE_THRESHOLD - 1` (= 1). Every item in the normal tier already passed the two-hit gate, so landing in stash with credit 1 lets a single further stash hit re-promote it. A fresh `put` still starts at counter 0 and needs two stash hits.
2. Do not change `promotion_get`. The stash-hit branch already increments the counter and promotes when `count >= PROMOTE_THRESHOLD`, so it handles credited items with no new branch. Target and probing hits stay as they are.
3. Make sure `put` (the fresh-insert path into stash) still sets or leaves `lfu_counter = 0`. If an update-in-place `put` hits a key already in stash, keep its existing counter.

Tests: replace `demotion_to_stash_halves_counter` with `demotion_to_stash_grants_readmission_credit`, which asserts that the demoted victim's counter is 1. Add a test showing that one `get` on a demoted key promotes it back into target. Keep the other tests; any test that depends on the halving semantics should be updated to the new value. Do not touch the gate-integrity files.

## Rationale (optional)

In v001, a reused target resident pushed out by a new 2-hit key lands in stash with counter 0 (0 >> 1). It then needs two more stash hits to return, and in the meantime it competes with one-hit scan keys for stash eviction. The large-cache cells, hm_0 especially, lost hit-rate for exactly this reason. Unlike H01, this does not block the newcomer. It makes the displaced resident cheap to restore, so the two versions of the gate can be compared directly. All of the extra work is one store on the demotion path, which per-op-time should show as roughly flat.
