# H02

Restructuring SLRU `put` around a single `HashMap::entry` lookup, and swapping the evicted key out of the node instead of cloning it, will cut put latency (per-op-time) by removing one hash probe per insert, while hit rate and metadata stay exactly unchanged.

## Parent

cycle/0002/v003

## Changes

This is a representation and insert-path change only, in `src/lru_cache/mod.rs`. Policy, eviction order, node layout and `on_hit` stay byte-for-byte identical, so hit rate must match the parent exactly.

Today `put` costs 2 hashes for a fresh key while the cache is filling (`map.get` + `map.insert`). A fresh key with eviction costs 3 (`map.get` + `map.remove(evicted)` + `map.insert`), plus a `clone()` of the evicted key and two clones of the new key. Rewrite `put` as follows:

1. `match self.map.entry(key)`. Add `use std::collections::hash_map::Entry;`.
   - `Entry::Occupied(e)`: `let idx = *e.get();` then update `self.nodes[idx].value` and call `self.on_hit(idx)`. That is 1 hash, the same as now.
   - `Entry::Vacant(v)`: take the key back with `v.key().clone()` only where the node needs its own copy. Then:
     - Filling phase (`nodes.len() < capacity`): push the node with the cloned key, `v.insert(idx)` and `push_back(idx, false)`. That is 1 hash instead of 2.
     - Eviction phase: choose `victim` (probation head, else protected head). Then `let old_key = std::mem::replace(&mut self.nodes[victim].key, v.key().clone());`, set the value and call `v.insert(victim)`. After that, call `unlink(victim)`, `set_protected(false)`, `self.map.remove(&old_key)` and `push_back(victim, false)`. The borrowing note below gives the exact order. That is 2 hashes instead of 3, with no clone of the evicted key.
   Borrowing: take the entry first and branch on it. Do not unlink a victim before you know the key is fresh. Reading `victim = if prob_head != NIL {prob_head} else {prot_head}` is a read of plain `u32` fields, so it is fine inside the Vacant arm. `unlink` and `push_back` take `&mut self`, so call them only after `v.insert(..)` has consumed the vacant entry. The order in the eviction arm is: compute `victim` → `mem::replace` the node key and value through `self.nodes` (this is a disjoint field borrow, which is fine) → `v.insert(victim)` → `self.unlink(victim)` → `self.map.remove(&old_key)` → `self.push_back(victim, false)`. Calling `unlink` after the key and value swap is safe because `unlink` reads only the links and flag. No `unsafe`.
2. Because the new key is inserted before the victim's key is removed, the map briefly holds `capacity + 1` entries. Change `HashMap::with_capacity(capacity)` to `HashMap::with_capacity(capacity + 1)` so this never triggers a rehash or resize. Keep the `capacity >= IDX_MASK` guard.
3. Keep the `debug_assert`s on `map.len() <= capacity` and on the segment lengths, checked after the remove.
4. Tests: keep all existing tests. Add one that fills the cache, churns 10× capacity fresh keys, and asserts `map.capacity()` did not change after the warm-up, which proves no resize happened. Also run `check_segments()`.

## Rationale (optional)

Cross-cycle evidence says the put path is bound by hashing and memory, not by list logic, and that the cost tracks the number of hash operations. Removing a full SipHash plus a probe from every miss-insert is the most direct lever on put p50 that has not been tried. It is policy-neutral, so it should move only per-op-time.
