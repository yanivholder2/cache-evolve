**What changed, following H03's `## Changes`:**
1. **Second-chance bit.** It lives in bit 31 of `Node::next`, so `Node<u64,u64>` should still be 24 bytes. Reading a link masks the bit off, and setting a link keeps it. The bit is cleared when a node is promoted to protected, and is set or cleared on a reused slot depending on the ghost lookup. The `on_hit` promote/demote logic is unchanged.
2. **Ghost array.** The cache header gets a zero-filled `ghost: Box<[u16]>` sized to `capacity.next_power_of_two()`. Slot and tag are computed as the hypothesis specifies, and a tag is never 0. Keys are hashed only when `put` inserts a new key or evicts one, never in `get`. A new key whose tag is in the ghost gets the bit and the slot is cleared. It still enters probation at the MRU end; it never goes to protected and never forces a demotion.
3. **Eviction.** If the probation LRU has the bit, the bit is cleared and that node moves to the probation MRU end. The new probation LRU is then evicted, even if it also has the bit, so at most one node is skipped per eviction. The fallback to the protected LRU is unchanged.
4. **Checks and tests.** `check_segments` now confirms every link index is in range or `NIL` and that no protected node has the bit. New tests cover:
   - a re-inserted key surviving exactly one extra eviction round, then being evicted;
   - the ghost tag being cleared on use;
   - promotion clearing the bit;
   - capacity 1, where a key with the bit is still evicted because there is nothing else;
   - ghost sizing;
   - randomized workloads at capacities 1, 2, 7 and 33 with value checks;
   - the 24-byte node size.

**Ordering choice:** the hypothesis lists the eviction step before the insert step but doesn't say which runs first. I look up the new key's ghost slot *before* writing the evicted key's tag. That way an eviction can't overwrite the new key's entry first, and a collision with the key just evicted can't wrongly give the new key the bit.

**Tests can rarely flake:** `HashMap` seeds its hasher randomly on each run, so the 16-bit tags differ every time. An accidental tag match could give an unrelated key the bit and break one of the exact-order tests. The odds are about 1 in 32,768 per lookup.
