# H02

Replacing v002's single CLOCK reference bit with a 2-bit saturating frequency counter (GCLOCK, max 3) stored in the node's existing padding byte will raise the MSR hit-rate summary above 0.529875 while keeping `Node<u64,u64>` at 24 bytes.

## Parent

cycle/0001/v002

## Changes

Keep v002's ring and hand structure in `src/lru_cache/mod.rs`. Change only the meaning of the per-node bit and how the sweep uses it.

- In `Node`, replace `referenced: bool` with `freq: u8`. It sits in the same padding byte, so `size_of::<Node<u64,u64>>()` must stay 24. Add a test asserting this. Add `const FREQ_MAX: u8 = 3;`.
- `get` on a hit: `if node.freq < FREQ_MAX { node.freq += 1; }`. Write nothing else and do no relinking. Keep the branch so a hot key does not dirty its line on every hit, or use `node.freq = (node.freq + 1).min(FREQ_MAX)` if that benchmarks faster.
- `put` for an existing key: overwrite the value and apply the same saturating increment.
- `put` for a new key while the arena has room: push with `freq = 0`.
- `put` for a new key when the arena is full: sweep from `hand`. While `nodes[hand].freq > 0`, decrement it by 1 (do not clear it to 0) and advance `hand` with the existing compare-and-reset wrap. At the first slot with `freq == 0`, evict it as v002 does: remove the old key from `map`, overwrite key and value in place, set `freq = 0`, insert into `map`, and advance `hand` once. The loop terminates within `FREQ_MAX` full rotations.
- To bound the worst-case sweep (put p99), cap the loop at `2 * capacity` steps. If the cap is hit, evict the slot currently under the hand regardless of its count. Document this as a liveness bound. With `FREQ_MAX = 3` it is normally unreachable within 3 rotations, so set the cap to `FREQ_MAX as usize * capacity + 1` if the strict-terminating form is preferred.
- Rewrite the CLOCK-order unit tests to GCLOCK semantics. For example, `repeated_get_sets_single_bit` becomes a test that a key hit 3 times survives two sweeps past it while a key hit once survives only one. Add a test that a key hit 3 times survives 3 consecutive evictions passing its slot. P1–P3 invariants must hold.

## Rationale (optional)

v002's insight named the cause of its weakness directly: a single bit "can't tell a key hit once apart from one hit many times", and that cost hit rate on web_0 at the large size. v001's SLRU showed that frequency filtering is worth roughly +1 point on these traces (0.5379), but it paid for that with a 56-byte node. A 2-bit counter recovers the frequency signal inside v002's 7 bytes of padding, so it costs no metadata and get stays a single byte write. Hit rate is the target. Put p99 may rise because hot slots need several passes, and the sweep cap is there to contain that.
