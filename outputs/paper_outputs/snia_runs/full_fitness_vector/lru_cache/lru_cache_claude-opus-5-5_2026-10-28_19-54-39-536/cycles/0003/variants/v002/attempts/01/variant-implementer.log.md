Here is how each of the hypothesis's changes was applied to v003's `mod.rs`:

1. **Early exit:** `on_hit` reads the segment flag once. It returns straight away if the node is protected and already `prot_tail`, or if `protected_cap == 0` and the node is already `prob_tail`. Old and new code leave the lists in the same state in both cases.
2. **Same-segment moves:** new `move_to_prot_mru` and `move_to_prob_mru` routines take a node out of its list and re-append it at the MRU end. They skip the tail check, which isn't needed because the node is never the tail. They don't change `prot_len` or `prob_len`, and the flag and prev index are written together in one store.
3. **Promotion and demotion:** `promote` moves a node from probation to protected, and `demote_prot_head` moves the protected LRU node to the probation MRU end. Each handles only its own segment, with no per-call choice between the two segments.
4. **Dead stores:** the generic `unlink`, still used by eviction, no longer resets the node's own `prev`/`next`. The `push_back` that always follows overwrites both.
5. **Puts on existing keys** still go through `on_hit`, so they get the same fast paths.
6. **Tests:**
   - All existing unit tests are kept unchanged.
   - The old generic hit path is kept as a test-only reference (`on_hit_generic`, `get_generic`, `put_generic`).
   - A new test, `specialised_hit_path_matches_generic_reference`, replays the random workload, including some puts on existing keys, at capacities 1, 2, 3, 4, 7, 10 and 32. After every operation it checks that `check_segments()` gives the same result for the new path and the reference.
