# H03

Widening the probation share only at large capacities, from 20% to 33%, on the ghost-free incumbent should raise hit-rate at 131K while leaving get-path code and per-op-time unchanged.

## Parent

cycle/0004/v002

## Changes

In `src/lru_cache/mod.rs` of the cycle-0004 v002 single-`Entry` SLRU, change
only how `protected_cap` is computed in `try_new`:

- `capacity == 1` → 0, unchanged.
- `capacity <= 32768` → `max(1, capacity * 8 / 10)`, unchanged, so the 16K
  results stay byte-identical to the parent.
- `capacity > 32768` → `max(1, capacity * 2 / 3)`, so roughly a third of the
  cache is probation.

Put the threshold in a named const, `LARGE_CAPACITY: usize = 32768`. Do not add
any field, side structure, ghost, or per-op work. `get`, `on_hit`, `unlink`,
`push_back` and `put` must stay instruction-for-instruction the same as the
parent's, and the `Node` and header layouts must not change.

Update `protected_cap_formula` to cover the new large-size branch, for example
asserting that `new(131072).protected_cap == 87381`. Keep the small-size
assertions as they are.

## Rationale (optional)

Every history mechanism so far has cost get p50 through its side structure, while
the incumbents' strength is speed. A probation share set only at construction is the
one hit-rate lever with zero runtime footprint. Cycle 5 tried a 1/3 share only at
small sizes, where it helped hm_0 but hurt web_0. The 131K point is untested. At that
size the ghost results show web_0 benefits from giving returning keys about
capacity/2 of extra probation time, which a wider probation window gives every key
without any ghost. The risk is hm_0/131K, which the protected segment keeps safe from
loops.
