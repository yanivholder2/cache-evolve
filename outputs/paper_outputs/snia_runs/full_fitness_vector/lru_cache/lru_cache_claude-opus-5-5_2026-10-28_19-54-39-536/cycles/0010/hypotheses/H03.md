# H03

Moving the `prev`/`next` links out of `Node` into a parallel dense `Vec<Link>` (8 bytes per entry) will lower get p50, because relinking neighbours on a hit then touches 8-byte link records instead of 24-byte nodes.

## Parent

cycle/0004/v002

## Changes

This is a structure-of-arrays split in `src/lru_cache/mod.rs`. Policy (SLRU 20/80), the single-`Entry` put, and the insert-before-remove order all stay the same as the parent.

- New `#[derive(Debug, Clone, Copy)] struct Link { prev: u32, next: u32 }`. Bit 31 of `prev` is still `PROT_BIT`. Move the accessors `prev_idx`, `is_protected`, `set_prev`, `set_protected`, `next_idx` and `set_next` from `impl Node` to `impl Link`, with the same bodies.
- `Node<K, V>` keeps only `key` and `value`.
- Add a `links: Vec<Link>` field to `LruCache`, created with `Vec::with_capacity(capacity)` next to `nodes`. Index `i` in `links` always belongs to `nodes[i]`.
- `unlink`, `push_back` and the `is_protected` check in `on_hit` read and write only `self.links[..]`. They must not index `self.nodes` at all. That way a protected hit touches `nodes[idx]` only for the returned value, and touches `links[prev]`, `links[next]` and `links[tail]` for the relinks.
- `put` filling phase: push a `Node { key, value }` and a `Link { prev: NIL, next: NIL }`, then call `push_back`. Eviction phase: unchanged, except that `unlink(victim)` and `set_protected(false)` act on `links[victim]`. The key/value replacement still goes through `nodes[victim]`.
- `get` stays `let &idx = self.map.get(key)?; self.on_hit(idx); Some(&self.nodes[idx as usize].value)`.
- `check_segments`: walk `links`, and read keys from `nodes`. Replace the test `node_u64_is_24_bytes` with `node_u64_is_16_bytes` and `link_is_8_bytes`. Keep every other test. Note for the implementer: if a gate test outside the overlay pins `Node` at 24 bytes, report that rather than working around it.

Invariants: the relink sequence is exactly the parent's, so hit-rate must be bit-identical, and the map must never resize. The total per-entry bytes stay at 24 (16 node + 8 link). The metadata-size figure will report 16 because only `Node` is measured, but the bytes have been moved, not removed. The evaluation should treat per-op-time as the real target of this hypothesis.

## Rationale (optional)

Cycles 1, 3 and 5 showed that removing relinks does not change get p50. They never tested how dense the relinked memory is. Today each neighbour update loads a 24-byte node whose key and value are never read, and at 131K the 3 MB arena does not fit in L2. A 1 MB link array holds 8 entries per cache line, so the `prev`/`next`/`tail` touches are more likely to hit in cache. The hot hit path and the header layout gain no instructions, only one extra `Vec` pointer.
