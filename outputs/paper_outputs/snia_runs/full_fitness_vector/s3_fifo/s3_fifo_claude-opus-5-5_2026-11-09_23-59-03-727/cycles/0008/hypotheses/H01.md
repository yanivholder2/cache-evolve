# H01

Raising the main-queue frequency cap from 7 to 15 gives heavily reused keys more main tenure and raises hit rate, mainly on hm_0 at the 16384 size.

## Parent

cycle/0005/v002

## Changes

In `src/s3_fifo/mod.rs`, change `const MAX_FREQ: u8 = 7;` to `const MAX_FREQ: u8 = 15;`. Make no other policy change: keep the 1/4 small share, the `freq > 1` graduation threshold, the freq/reused reset on graduation, reuse-gated main-victim ghosting, the `main_size` ghost bound, and the decrement-by-one sweep in `evict_main()`. `freq` stays a `u8`, so `Entry<u64, u64>` stays 24 bytes and `entry_fits_in_padding` must still pass. Update the in-file test `repeated_get_saturates_at_max_freq`: it should do at least 20 `get` calls, then assert `MAX_FREQ == 15` and that the stored freq equals `MAX_FREQ`. Update the header comment to say "Cycle 8 H01: MAX_FREQ 7 -> 15". Leave the code paths in `evict_main()` unchanged. Each sweep still pops at most one victim, and a reinsertion still costs one decrement.

## Rationale (optional)

Two results point the same way: raising the cap from 3 to 7 (cycle 5) helped hm_0 at 16384, and faster aging (halving, cycle 7) hurt that same cell. Strongly reused keys with long gaps between hits need more tenure in main. Cycle 5 guessed that raising the cap further would not pay off, but nobody tested it. This is a single-variable test of that guess. If hit rate stays flat or web_0 at 131072 drops, the cap lever is saturated. Treat any timing change as noise unless `put` p99 rises noticeably, since longer sweeps are possible.
