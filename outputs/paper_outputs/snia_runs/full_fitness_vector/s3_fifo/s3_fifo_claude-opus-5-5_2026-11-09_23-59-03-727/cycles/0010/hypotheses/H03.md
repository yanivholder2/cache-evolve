# H03

Capping the main-queue second-chance sweep at 32 reinsertion steps per eviction, then force-evicting the next back entry, lowers the `put` p99 (per-op-time) and keeps hit rate within noise.

## Parent

cycle/0009/v001

## Changes

Edit only `evict_main` in `src/s3_fifo/mod.rs`. Add `const MAX_SWEEP_STEPS: u32 = 32;`.

Rewrite the loop to count reinsertions:
- `let mut steps = 0;` then `while let Some(i) = self.main.pop_back()`.
- If `entry.freq > 0 && steps < MAX_SWEEP_STEPS`: decrement freq, `push_front(i)`, `steps += 1`, continue. This is the same as the parent's behaviour.
- Otherwise (freq == 0, **or** the cap was reached): evict `i` as the parent does. Read `entry.reused`, call `release(i)`, and call `push_ghost(key)` only if `reused`. Then `break`. A force-evicted entry with freq > 0 was necessarily reused in main, so it gets ghosted. That gives it the usual ghost → main return path, which softens the policy change.

Keep everything else the same: `MAX_FREQ` 7, decrement-by-one aging, the reset on graduation, the reuse-gated ghost, the size-gated 1/5 / 1/4 split, and `evict_small`. Existing unit tests must still pass. Add one test that fills main with more than 32 entries, all at freq ≥ 1, triggers `evict_main`, and asserts that exactly one key left main and that it landed in the ghost.

## Rationale (optional)

Cycles 8–9 tied the `put` tail to the number of sweep steps per miss. With `MAX_FREQ` 7, a run of hot keys at main's tail can make one eviction decrement hundreds of entries. Hit rate is near-converged, so this hypothesis trades a possible tiny hit-rate change for bounded work per miss. If the cap rarely binds, eviction order matches the parent in practice. That answers the cross-cycle open question about bounded sweeps.
