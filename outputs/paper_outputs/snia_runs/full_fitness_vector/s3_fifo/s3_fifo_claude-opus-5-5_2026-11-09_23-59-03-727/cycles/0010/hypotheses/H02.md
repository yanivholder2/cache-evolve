# H02

Replacing the ghost deque's rare O(n) `retain` compaction with bounded incremental trimming of stale tail tuples on each `push_ghost` lowers the `put` tail (per-op-time) and leaves hit rate bit-identical.

## Parent

cycle/0009/v001

## Changes

Edit only `push_ghost` in `src/s3_fifo/mod.rs`. The policy stays the same: which keys are live ghosts, and in what FIFO order, must match the parent exactly.

1. Keep the existing "ghost full → pop_back until the oldest live tuple is found and removed" loop unchanged.
2. Before pushing the new tuple, add a bounded trim. Repeat at most `TRIM_STEPS` times (new constant, `const GHOST_TRIM_STEPS: usize = 4;`): look at the back with `self.ghost.back()`. If that tuple is stale (`self.ghost_index.get(&k) != Some(&s)`), `pop_back()` it. If it is live, stop. This uses only `get` (no `entry()`, nothing that reserves) and never removes a live tuple. A stale tuple is never consulted for policy, so eviction order is unchanged.
3. Keep the `self.ghost.len() > 2 * self.main_size` → `retain` block as a safety fallback, so the inline test invariant `ghost.len() <= 2 * main_size` still holds. With incremental trimming it should almost never fire. Stale tuples are created at most one per ghost hit, and each push pops up to 4 from the back.

Do not change the `VecDeque` capacity pre-sizing, the ghost bound (`main_size`), `ghost_seq` handling, or any other function. Add a unit test that drives many ghost hits (put/evict/re-put cycles on a small cache) and asserts that live ghost membership matches a reference run of the same trace, or at least that the `ghost_live_bound_and_disjoint_from_resident` invariants still hold.

## Rationale (optional)

Cycles 7–9 found that the `put` tail tracks rare expensive events (rehash, `retain`) and sweep steps, not per-op bookkeeping. The full `retain` walks up to 2×`main_size` tuples (~200k at 131072) in a single `put`. Spreading that work as at most 4 cheap back-checks per ghost insert keeps work per miss bounded. It also avoids cycle 7's mistake (a ring with a liveness probe on *every* insert that always ran): here the probe stops at the first live tuple, which is the common case.
