# H03

Pre-sizing the resident and ghost hash indexes to twice their maximum live occupancy, so they never run near the load-factor ceiling, lowers per-op time (especially p99) while leaving hit rate bit-identical.

## Parent

cycle/0004/v001

## Changes

This is a structural change only, in `S3Fifo::try_new` in `src/s3_fifo/mod.rs`. Policy decisions must stay bit-identical to cycle/0004/v001.

- `index`: change `HashMap::with_capacity_and_hasher(capacity, ...)` to `HashMap::with_capacity_and_hasher(2 * capacity, ...)`. The resident index never holds more than `capacity` keys, so occupancy stays at or below about 50% of the requested capacity and below roughly 45% of the actual bucket count. It also never triggers a resize/rehash during warm-up.
- `ghost_index`: change `with_capacity_and_hasher(main_size, ...)` to `with_capacity_and_hasher(2 * main_size + 1, ...)`. Its live size is bounded by `main_size`, but `insert` runs right after the oldest live ghost is removed, and tombstone/deleted-slot buildup in hashbrown from churn can force in-place rehashes when the table sits near 7/8 load. The headroom avoids those rehash spikes in steady state.
- Do not change the `slab`, `free`, `small`, `main` or `ghost` deques.
- Do not change hashing (the Fx hasher stays).
- Do not change control flow in `get`, `put`, `alloc`, `release`, `push_ghost`, `evict_main` or `evict_small`.
- `Entry` stays 24 bytes. The `S3Fifo` struct size is unchanged because only heap allocation sizes change.

If a capacity multiplication could overflow for very large `capacity`, use `capacity.saturating_mul(2)`. Capacity is already bounded by `u32::MAX`, so on 64-bit this is just defensive. All existing unit tests must pass unchanged.

## Rationale (optional)

Cycle 4's v003 showed that hash occupancy and bucket width, not probe count, drive timing, and that tails suffer most under higher load. This variant tests that finding in the other direction on the incumbent: lower occupancy means shorter probe sequences on misses (the dominant `put` path does `index.get`, `ghost_index.remove`, then `index.insert`, and two of those three are misses), and fewer tombstone-driven rehashes in the high-churn ghost table. Because it is a pure layout change with identical decisions, any timing gain is attributable to the diff. The cost is extra heap that the metadata metric does not see; record it as an explicit trade-off.
