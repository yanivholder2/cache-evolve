# H02

Raising the main-queue frequency cap `MAX_FREQ` from 3 to 7 on the two-filter parent raises hit rate on hm_0 while leaving web_0 unchanged.

## Parent

cycle/0004/v001

## Changes

This changes one constant in `src/s3_fifo/mod.rs`: set `const MAX_FREQ: u8 = 7;` (previously 3). `freq` stays a `u8`, so `Entry<u64,u64>` remains 24 bytes, and the `entry_fits_in_padding` test must still pass.

Do not change any other logic. The effect of the new cap comes through two existing paths:
- `get()` already saturates at `MAX_FREQ`.
- `evict_main()` already decrements `freq` by 1 per second-chance pass and reinserts at the front of main. With cap 7, a heavily reused main resident can survive up to 7 sweeps of main instead of 3.

Graduation is not affected. `evict_small` still requires `freq > 1` and resets `freq` and `reused` to 0/false on graduation, so the cap matters only for reuse that happens inside main. Keep these unchanged:
- Reuse-gated ghosting.
- Small-queue sizing (`capacity / 4`).
- The ghost bound (`main_size`).
- The Fx hasher, slab and indexes.

The test `repeated_get_clamps_frequency` only checks returned values, so it should pass as-is. If it is useful, add a unit test asserting that after 10 `get`s the slot's `freq == MAX_FREQ`.

## Rationale (optional)

Every cycle shows hm_0 responding to main retention. The cycle-4 graduation reset means main `freq` now counts only reuse inside main, so a higher cap gives credit only to keys proven hot inside main. That credit stays out of the small-queue admission path that web_0 is sensitive to. The risk is a longer `evict_main` sweep (more reinsertion passes) and slower eviction of formerly-hot keys. If hm_0 gains and web_0 holds, main-retention depth is still underexploited. If web_0 drops, hot-key stickiness is crowding out its working set.
