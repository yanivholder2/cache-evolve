# H03

Replacing SipHash in the resident and ghost hash indexes with an inline Fx-style multiplicative hasher will lower per-op-time below v003's 37 ns get p50, with hit rate exactly unchanged.

## Parent

cycle/0002/v003

## Changes

This is a pure implementation change in `src/s3_fifo/mod.rs`. Policy decisions must stay identical, and hit rates must match v003 on every trace and size.

- Define a small hasher inside `mod.rs`, because `Cargo.toml` can't be edited and no new crates are allowed. `struct FxHasher { hash: u64 }` implements `std::hash::Hasher`:
  - `write_u64(&mut self, x)` does `self.hash = (self.hash.rotate_left(5) ^ x).wrapping_mul(0x51_7c_c1_b7_27_22_0a_95)`.
  - `write_u32`, `write_u8` and `write_usize` widen to u64 and go through the same path.
  - `write(&mut self, bytes)` processes 8-byte chunks with `u64::from_le_bytes`, then the remainder byte by byte, so generic `K` still works.
  - `finish()` returns `self.hash`.
  - Add `type FxBuild = std::hash::BuildHasherDefault<FxHasher>;` and derive or implement `Default` for `FxHasher`.
- Change the field types to `index: HashMap<K, u32, FxBuild>` and `ghost_index: HashMap<K, u64, FxBuild>`. In `try_new`, construct them with `HashMap::with_capacity_and_hasher(cap, FxBuild::default())`.
- Struct bounds don't change: `K: Eq + Hash + Clone` is still enough. The `framework::Cache` impl and the JNI file need no edits. Do not touch `s3_fifo_jni.rs`.
- Keep everything else byte-for-byte the same: slab, free list, queues, lazy-deletion ghost deque, `retain` compaction, eviction and promotion logic, `MAX_FREQ`, and the graduation threshold. The existing in-module tests must pass unchanged.

## Rationale (optional)

v003 made `get` a single hash lookup plus a slab access, and on a miss `put` performs several hash operations: `index.get`, `ghost_index.remove`, `index.insert`, `index.remove`, and `ghost_index.insert/get` during `push_ghost`. With `u64` keys, SipHash-1-3 is now the main per-op cost. A single-multiply hasher should cut that substantially. It doesn't change any policy decision, so any hit-rate drift would point to an implementation bug, and any timing gain can be credited to the diff. HashDoS resistance isn't a concern for trace replay.
