# H03

Building the protected normal-tier buckets with an LFU eviction policy (while leaving stash buckets on the seeded policy) raises hit-rate by retaining the most-frequently-accessed keys under the trace's heavy skew.

## Parent

baseline

## Changes

In `src/dash/segments/mod.rs`, modify `SegmentCore::try_new` so the normal
(`buckets`) tier is constructed with a fixed `EvictionPolicyKind::Lfu`
policy regardless of `settings.eviction_policy`, while the `stash_buckets`
continue to use `settings.eviction_policy.build()` as today:

```
use crate::shared::eviction_policy::EvictionPolicyKind;
...
let buckets: Vec<_> = (0..settings.num_of_normal_buckets)
    .map(|_| new_bucket(settings.bucket_size, EvictionPolicyKind::Lfu.build()))
    .collect();
let stash_buckets: Vec<_> = (0..settings.num_of_stash_buckets)
    .map(|_| new_bucket(settings.bucket_size, settings.eviction_policy.build()))
    .collect();
```

Leave the rest of `try_new` (validation, field assignment) and all other
files unchanged. The promotion path in `dash_segment.rs` already consults
`promotion_candidate_index` / `eviction_candidate_index` through the bucket
trait, so an LFU normal tier transparently promotes the max-counter key to
probing and evicts the min-counter key — no segment-level changes needed.
Preserve every invariant: bucket counts, `bucket_size`, slot legality, and
capacity bound are all untouched, so `P6` and the slot-legality gate still
pass.

This is a deliberately different lever from the cycle-0001 family (which all
reshaped the stash/normal balance): it changes *how* the protected tier
ranks its residents rather than *how much* room it gets, hedging in case the
capacity-reallocation axis is near saturation.

## Rationale (optional)

The LIRS workload-a trace is strongly skewed; recency-based ClassicLRU can
evict a hot-but-momentarily-cold key, whereas LFU in the protected tier keeps
the genuinely frequent working set resident, which should lift hit-rate
independent of the stash split.
