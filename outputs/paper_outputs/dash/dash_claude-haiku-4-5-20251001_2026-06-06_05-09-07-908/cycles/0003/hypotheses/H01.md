# H01

Apply frequency-gated promotion to the best-hit-rate incumbent to reduce latency overhead while preserving hit-rate gains.

## Parent

cycle/0002/v002

## Changes

In `src/dash/segments/dash_segment.rs`, modify the `promotion_get()` function (around lines 141–189) to gate target→probing promotion on a frequency threshold, applied on top of v002's back-insert promotion and 50/50 geometry:

1. Add a promotion counter threshold constant at module level: `const PROMOTION_THRESHOLD: u16 = 2;`

2. In the section checking "is_hottest" (around line 166), add a condition before promoting to probing:
   ```
   let is_hottest = Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();
   if is_hottest && core.buckets[target_idx].get_items()[item_idx].lfu_counter >= PROMOTION_THRESHOLD {
       // proceed with promotion to probing
   } else if is_hottest {
       // increment lfu_counter and stay in target (intra-promote only)
   }
   ```

Stash→target promotion remains ungated (all stash hits promote immediately). Keep v002's back-insert promotion (InsertPosition::Back) and 50/50 geometry (16/16 bucket split) unchanged.

## Rationale

v002 achieved the best hit-rate (0.7078) by combining back-insert promotion with 50/50 geometry, but at a per-op-time cost of 117 ns. Cycle 0003's v003 demonstrated that frequency-gated promotion reduces cache churn and per-op-time (to 103 ns) by filtering false-positive promotions to the probing tier. This hypothesis tests whether frequency gating is compatible with v002's winning configuration—can we reduce v002's latency cost without sacrificing its hit-rate advantage? Since gating operates orthogonally to promotion order and geometry allocation, we expect to inherit both v002's hit-rate strength and v003's latency efficiency.
