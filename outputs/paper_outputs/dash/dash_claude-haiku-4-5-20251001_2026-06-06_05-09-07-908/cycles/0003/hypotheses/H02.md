# H02

Combine frequency-gated promotion with aggressive 62.5/37.5 geometry to improve both hit-rate and latency.

## Parent

cycle/0002/v001

## Changes

In `src/dash/segments/dash_segment.rs`, modify the `promotion_get()` function (around lines 141–189) to gate target→probing promotion on a frequency threshold, applied on top of v001's aggressive 62.5/37.5 geometry:

1. Add a promotion counter threshold constant at module level: `const PROMOTION_THRESHOLD: u16 = 2;`

2. In the section checking "is_hottest" (around line 166), add a condition before promoting to probing:
   ```
   let is_hottest = Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();
   if is_hottest && core.buckets[target_idx].get_items()[item_idx].lfu_counter >= PROMOTION_THRESHOLD {
       // proceed with promotion to probing
   } else if is_hottest {
       // increment lfu_counter and stay in target (intra-promote only)
   }
   ```

Stash→target promotion remains ungated. Keep v001's aggressive geometry (20/12 bucket split, 62.5%/37.5%) unchanged.

## Rationale

Cycle 0002's open question directly addresses this composition: "Do aggressive geometry (62.5/37.5) and frequency gating compose without regression?" v001 achieved solid hit-rate (0.6991) through aggressive geometry concentration but with higher per-op-time (122 ns). v003 demonstrated that frequency-gated promotion improves both hit-rate and latency by reducing false-positive promotions and cascading demotions. This hypothesis tests whether adding frequency gating to v001's geometry variant improves both dimensions: the gating reduces churn in the smaller stash tier (12 buckets in v001's 62.5/37.5 split), while the aggressive geometry already concentrates capacity where it matters most on Zipfian workloads. Together they should reduce latency overhead while maintaining or improving hit-rate.
