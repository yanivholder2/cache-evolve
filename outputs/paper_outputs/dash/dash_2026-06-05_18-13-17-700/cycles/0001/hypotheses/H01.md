# H01

Landing promoted items at the MRU (Back) end instead of the LRU (Front) end raises hit rate by letting genuinely recurring keys climb the stash→target→probing tiers in fewer accesses.

## Parent

baseline

## Changes

In `src/dash/segments/dash_segment.rs`, the `Segment::get` impl for
`DashSegment` calls `promotion_get(&mut self.core, key, InsertPosition::Front)`.
Change that single argument to `InsertPosition::Back`.

Effect: every promotion (`promote_to_target`, `promote_to_probing`) and every
one-more-chance demotion (`demote_from_normal_bucket`) routed through
`promotion_get` will insert at the bucket's MRU end. A stash hit then lands the
item at the back of its target bucket, so under `ClassicLRU` it is immediately
the `promotion_candidate_index()` (last element) — one further hit promotes it
to probing, versus the baseline where a Front-inserted item must first re-climb
the whole target bucket. This deliberately trades the baseline's one-hit-wonder
protection for faster retention of hot keys.

Keep everything else intact: the promotion-candidate gate
(`is_hottest` check), the probing→target→stash cascade routing in
`demote_from_normal_bucket`, the wraparound probing index math, and the
`Slot`-derived placement in `SegmentCore::put_at`. The slot-legality and
capacity-bound invariants (P-series gate) are unaffected because only the
*position within* a bucket changes, never which bucket an item lands in.

The baseline unit tests in this file that hard-code Front ordering
(`stash_hit_inserts_at_front_of_target`, `target_retry_lands_at_front_when_cold`,
`direct_to_stash_at_front_when_cold`, and the `*_when_hot` pairs) assert the
old behaviour; update their expected indices to match Back-insertion so the
crate still compiles and its tests pass.
