# H01

Using `min_by_key(lfu_counter)` as the fallback eviction victim in `ClassicLRUFreqProtect` when no zero-count item exists will improve hit-rate by evicting the least-frequently-accessed resident rather than the arbitrary LRU-front item.

## Parent

cycle/0009/v003

## Changes

In `src/shared/eviction_policy.rs`, modify `ClassicLRUFreqProtect::eviction_candidate_index()`.

Current code:
```rust
fn eviction_candidate_index(&self, items: &[Item<K, V>]) -> usize {
    items.iter()
        .enumerate()
        .find(|(_, item)| item.lfu_counter == 0)
        .map(|(i, _)| i)
        .unwrap_or(0)
}
```

Replace `.unwrap_or(0)` with a secondary scan that picks the item with the minimum `lfu_counter` when no zero-count item is found:

```rust
fn eviction_candidate_index(&self, items: &[Item<K, V>]) -> usize {
    if let Some((i, _)) = items.iter()
        .enumerate()
        .find(|(_, item)| item.lfu_counter == 0)
    {
        return i;
    }
    // All items have been accessed at least once; evict the one with the
    // lowest in-tier access count rather than the pure LRU-front item.
    items.iter()
        .enumerate()
        .min_by_key(|(_, item)| item.lfu_counter)
        .map(|(i, _)| i)
        .unwrap_or(0)
}
```

No other function changes. The first pass (zero-count preference) is preserved exactly; only the fallback path changes. The `get_from_position`, `promotion_candidate_index`, and all other logic in `ClassicLRUFreqProtect` remain identical to the parent. The geometry (7/8), second-chance recovery, and stash-exit credit from the parent are all preserved unchanged.

## Rationale

The current fallback evicts index 0 (the LRU-front item), which is correct when all items are equally uncertain. However `ClassicLRUFreqProtect.get_from_position` accumulates `lfu_counter` values that are never used once the primary zero-count guard is bypassed. When the normal tier is well-provisioned (7/8 geometry, 28 normal buckets) and the workload is Zipfian, buckets frequently reach a state where every resident has been touched at least once — the fallback path fires regularly. At that point, a resident with `lfu_counter == 1` (touched once and sitting at LRU-front) is a meaningfully worse eviction choice than a resident with `lfu_counter == 8` (repeatedly accessed), even though the current code treats them identically. Using the accumulated counter as a frequency tiebreaker costs nothing beyond an additional linear scan and directly improves victim selection quality in the most-common fallback scenario.
