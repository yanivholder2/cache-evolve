# H02

Defend v001's segmented-LRU hit-rate record (0.724) while cutting its per-op-time penalty by adopting v003's integer hasher and eliminating redundant list surgery on protected-segment hits.

## Parent

cycle/0001/v001

## Changes

Start from v001's segmented-LRU (SLRU) implementation, which won hit-rate
(0.7241) but regressed per-op-time to 77 ns get p50 from the extra
promote/demote branching. Make two cost-cutting changes that leave the
segmentation policy — and therefore the hit-rate win — intact:

- Adopt v003's hashing path. Add the `FastHasher` / `FastBuildHasher`
  (zero-sized, single xor + wrapping-multiply by `0x517cc1b727220a95`) and
  change `map` to `HashMap<K, usize, FastBuildHasher>`, constructed with
  `with_capacity_and_hasher`. The hash-cost reduction (~38 ns of v003's
  win on these 8-byte keys) is meant to offset the segment-bookkeeping
  branches so net per-op-time lands well below v001's 77 ns.
- Remove wasted work on the common protected-segment hit. In v001's `get`,
  a hit on an already-`protected` node still calls `unlink` then
  `push_back`. Add a fast path: if the touched node is already the
  protected MRU (`idx == prot_tail`), return immediately without touching
  any links. Apply the same `idx == <segment MRU>` short-circuit before
  the `unlink`/`push_back` pair in the `put`-update branch.

Do not change `prot_cap` geometry, the probation-first eviction order, or
the demote-on-overflow logic — those produce the hit-rate gain and must be
preserved (hit-rate must stay at v001's ~0.724). The target dimension is
hit-rate: the goal is to keep the 0.724 record while bringing per-op-time
back toward v003's range so the SLRU lever stops trading against latency.
