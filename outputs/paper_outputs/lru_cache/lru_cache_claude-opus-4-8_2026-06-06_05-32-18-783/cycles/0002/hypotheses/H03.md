# H03

Cut v003's per-op-time further — especially the regressed get p99 tail — by short-circuiting the recency-list surgery when the accessed key is already the MRU node.

## Parent

cycle/0001/v003

## Changes

Keep v003 entirely as-is (the `FastHasher`/`FastBuildHasher` path and the
arena doubly-linked list). Add a single hot-path guard:

- In `get`, after resolving `let &idx = self.map.get(key)?;`, check
  `if self.tail == Some(idx) { return Some(&self.nodes[idx].value); }`
  before calling `unlink`/`push_back`. When the looked-up node is already
  the MRU (tail), it is already in its final position, so the
  detach-and-reattach is pure wasted work — five-plus field writes across
  `unlink` and `push_back` that touch up to three nodes' cache lines.
- Apply the same guard in the `put` update branch (the
  `if let Some(&idx) = self.map.get(&key)` arm): after writing the new
  value, skip `unlink`/`push_back` when `self.tail == Some(idx)`.

On the LIRS/Zipfian harness trace a large fraction of accesses fall on a
small hot set that repeatedly lands on the MRU, so this removes the most
common case's link churn. Because the skipped path is the longest
straight-line sequence of writes in `get`, this should pull down the get
p99 tail that v003's insight flagged as regressed, not just the median.

Preserve LRU ordering exactly: the guard only fires when the node is
already tail, which is observationally identical to unlink-then-push_back
of the tail. Hit-rate and metadata-size must stay identical to v003
(0.6652 and 48 bytes). The target dimension is per-op-time, with the
specific aim of improving both get p50 and the get p99 tail below v003's
39 ns / 91 ns.
