# H03

Add an already-MRU fast path to the compact 24-byte LRU so the metadata-record holder also drops per-op-time from 52 toward v003-class latency.

## Parent

cycle/0002/v001

## Changes

Take v001 — the compact plain-LRU Variant that holds the metadata-size
record (24-byte `Node`, `u32` NIL-sentinel links, `FastHasher`) — and
graft on v002's order-preserving short-circuit, which v001 lacks because
its `get`/`put` unconditionally call `unlink` + `push_back` even when the
touched node is already the MRU (tail).

In `src/lru_cache/mod.rs`:

- In `get`, after the map lookup yields `index`, return early without any
  link surgery when the node is already the MRU: `if self.tail ==
  link(index) { return Some(&self.nodes[index].value); }`. Only fall
  through to `unlink(index); push_back(index)` when the node is not the
  tail.
- In `put`, on the existing-key update branch, after writing
  `self.nodes[index].value = value`, skip the `unlink`/`push_back` pair
  when `self.tail == link(index)` (the update leaves order unchanged);
  otherwise relink as today.
- Leave everything else byte-for-byte: the `u32`/`NIL` link encoding and
  `idx`/`link` helpers, the `FastHasher`/`FastBuildHasher`, eviction of
  the `head` (LRU), and slot reuse. The `Node` layout is unchanged, so
  metadata-size stays at the 24-byte record and hit-rate stays at 0.6652.

The claim is that skipping no-op list surgery on already-MRU touches —
the cheaply predictable `tail == idx` position check that won inside
v002's segments — pulls v001's per-op-time (52) down toward v003's 39
without disturbing its metadata-size record.

## Rationale (optional)

Cycle 0002 showed the surgery-skip helps when gated on a cheaply
predictable position (MRU within a segment) and only mispredicted as a
bare branch on a universal hot path. On single-segment plain LRU the tail
check is exactly that predictable position gate, and it occupies a Pareto
point neither incumbent holds: the 24-byte node with sub-52 latency.
