# H02

Replace the single last-key cache with a small fully-associative hot-key side table so the HashMap probe is skipped for several alternating hot keys, lowering get p50 (per-op-time) more robustly than a one-entry cache.

## Parent

cycle/0006/v003

## Changes

This is a distinct, more aggressive design point than H01's single-entry
cache: it targets the same named hot-path cost (the HashMap hash + probe)
but keeps a handful of recent keys and skips the probe even when the
accessed node still needs relinking, so it does not collapse on traces
where two or three hot keys alternate (the exact case where a one-entry
last-key cache mispredicts).

Add two arrays to `LruCache`, sized by a `const HOT: usize = 4`:
`hot_keys: [Option<K>; HOT]` and `hot_idx: [u32; HOT]`, initialized to
`None` / `NIL` in `try_new`, plus a `hot_next: usize` round-robin cursor.
These live on the cache struct, not on `Node`, so `Node<u64,u64>` stays
24 bytes and the scored metadata-size (the Node size) is unchanged; only
the `LruCache` footprint grows. Indexing is by linear scan and key
equality only — no hashing — so it stays generic over `K: Eq` and never
re-incurs the cost it is trying to avoid.

At the top of `get`, before `self.map.get(key)?`, scan the up-to-`HOT`
cached entries: for each slot `i` where `hot_idx[i] != NIL` and
`hot_keys[i].as_ref() == Some(key)`, let `idx = hot_idx[i] as usize`; if
`self.nodes[idx].key == *key` (liveness guard against slot reuse by
eviction), treat this as a resolved hit and jump straight into the
existing post-lookup logic (protected-MRU fast path, protected refresh,
or probationary promotion) using `idx` — skipping the HashMap probe
entirely, including in the cases that still perform link surgery. On any
miss in the side table, fall through to `self.map.get(key)?` exactly as
today.

On every get that resolves an index (whether via the side table or the
map), record the key into the table at the round-robin slot `hot_next`
(`hot_keys[hot_next] = Some(key.clone()); hot_idx[hot_next] = link(idx);
hot_next = (hot_next + 1) % HOT`). No explicit invalidation on
eviction/demotion is needed — a stale entry simply fails the
`nodes[idx].key == *key` guard. Do not change put, eviction, geometry,
promotion, or node layout.

Confirmed if get p50 drops at or below H01's while staying low under
alternating-hot-key access; refuted if the up-to-4 linear compares on
every cold get and miss cost more than the probe they save (the trade
H01 avoids by checking only one key).
