# H01

Gating probationary→protected promotion on a TinyLFU frequency threshold (not a single touch) raises hit-rate by keeping low-reuse keys out of the protected segment.

## Parent

cycle/0002/v002

## Changes

In v002's `promote(idx)`, change the probationary→protected branch so that a
single hit no longer unconditionally moves a node into the protected segment.
Read the node's key and compute its count-min `estimate(&key)`. Promote into the
protected MRU tail (current behaviour: set `protected = true`, `prot_len += 1`,
`demote_one()` on overflow) ONLY when the estimate clears a reuse threshold —
specifically `estimate(&key) >= 2` (i.e. the key has been seen at least twice in
the sketch, the genuine second-reference signal). When the estimate is below the
threshold, treat the hit as recency-only: `unlink(idx)` then `push_back(idx)`
keeping `protected == false`, so the key moves to the probationary MRU tail
without entering protected. Leave the already-protected branch (move to protected
MRU tail) unchanged, and leave the admission gate in `put()` and the `bump()`
call sites untouched. The sketch already records every get-hit via `bump()` before
`promote()` is invoked, so the estimate reflects the current access. Invariants to
preserve: `prot_len` continues to track exactly the count of nodes with
`protected == true`; `prot_len <= prot_cap` after every operation; eviction still
prefers the probationary-LRU. This targets the promotion gate — the lever the
cross-cycle notes call load-bearing — rather than the admission gate v002 already
tunes.

## Rationale (optional)

v002 admits selectively but promotes indiscriminately: any one-shot hit on a
probationary key floods it into protected and can displace genuinely hot keys.
Frequency-gating the promotion keeps protected reserved for proven-frequent keys,
attacking hit-rate from an axis v002 leaves open.
