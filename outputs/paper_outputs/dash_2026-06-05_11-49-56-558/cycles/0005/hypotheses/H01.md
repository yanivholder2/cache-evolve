# H01

Inserting ghost-re-admitted items at `Back` (MRU end) of their target bucket instead of `Front` will improve hit-rate by allowing re-admitted items to immediately qualify as promotion candidates rather than needing to earn MRU position first.

## Parent

cycle/0004/v002

## Changes

In `src/dash/segments/dash_segment.rs`, inside the `put()` method of `DashSegment`, find the ghost re-admission branch that fires when a key is found in `self.ghost_keys`:

```rust
if let Some(pos) = self.ghost_keys.iter().position(|k| *k == item.key) {
    self.ghost_keys.remove(pos);
    promote_to_target(&mut self.core, item, InsertPosition::Front);  // ← change this
    return;
}
```

Change `InsertPosition::Front` to `InsertPosition::Back`:

```rust
if let Some(pos) = self.ghost_keys.iter().position(|k| *k == item.key) {
    self.ghost_keys.remove(pos);
    promote_to_target(&mut self.core, item, InsertPosition::Back);   // ← Back
    return;
}
```

All other ghost set logic is unchanged: the 32-entry FIFO capacity (`GHOST_CAPACITY = 32`), the recording of stash-evicted keys into `ghost_keys`, and the ghost-key removal on re-admission. The normal cold insertion path (`core.put_at(Slot::Stash, InsertPosition::Back, item)`) is also unchanged.

The `promote_to_target` helper itself is unchanged; only the call-site in the ghost branch changes its `insert_pos` argument.

## Rationale

The cycle/0004/v002 insight explicitly identified `Front`-insertion as the likely reason ghost re-admission yielded near-zero gain: "the Front-insertion position chosen for re-admitted items (requiring them to earn MRU before promoting) neutralises most of the latency savings the bypass was meant to deliver." Using `Back` instead places re-admitted items at MRU of their target bucket immediately, making them the promotion candidate on the very next access — which is the full benefit the ghost bypass was designed to deliver.
