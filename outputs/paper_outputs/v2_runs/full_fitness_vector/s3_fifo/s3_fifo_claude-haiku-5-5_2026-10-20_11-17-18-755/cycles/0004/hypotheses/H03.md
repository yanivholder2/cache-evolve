# H03

Moving the frequency counter out of `Entry` into a parallel side array should shrink `Entry<u64,u64>` from 24 to 16 bytes, lowering metadata-size with hit rate unchanged at 0.7195 on workload-a at capacity 2048, targeting metadata-size.

## Parent

cycle/0002/v003

## Changes

Start from cycle/0002/v003. Remove the per-entry frequency counter from `Entry` and store it as a `u8` (saturating at the same maximum v003 uses) in a parallel array indexed by the same slot index as the entry storage. Entry should then hold only the key and value, which is 16 bytes for `<u64,u64>`. First read the `Entry` struct in v003 and confirm which fields it carries beyond key and value. If a queue-membership tag also lives in `Entry`, keep it in the same side array as the counter so the entry holds only key and value.

Every read or write of `entry.freq` in `get()`, `evict_small()`, `evict_one()`, and the promotion check must go through the side array at the same slot index. Preserve the 20% small-queue share, the main-queue second-chance budget, the `freq > 1` promotion condition, and the ghost queue as v003 has them. The policy must be unchanged: an entry's counter value at every decision point must equal what v003 would hold.

Invariants: a slot's counter is reset when the slot is reused; the side array length matches the entry storage length at all times; total resident entries never exceed capacity.

## Rationale (optional)

Metadata-size has been 24 in every variant of every cycle, so this dimension has never been moved, and the leaderboard has no metadata leader beyond baseline. The `Entry` size is set by the counter padding sitting beside an 8-byte key and value. Moving the counter out gives a clean metadata win with a predictable policy outcome, since the counter values are identical. The risk is a per-op cost from the extra indirection on the get path, which the fitness vector will show, so per-op-time is the regression to watch.
