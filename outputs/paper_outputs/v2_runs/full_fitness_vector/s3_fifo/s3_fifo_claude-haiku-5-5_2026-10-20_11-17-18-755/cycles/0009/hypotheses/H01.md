# H01

Aging the main-queue frequency counters periodically should raise hit rate on workload-a at 2048 by letting stale hot entries become evictable, without adding per-op cost on the hit path.

## Parent

cycle/0008/v001

## Changes

Keep the id-keyed `index` and the head counters exactly as the parent has them. Add one aging step on the main-queue path, not on get:

- Add a `u32` counter (for example `ops_since_age`) to the cache struct. Increment it once per `put` that inserts a new key.
- When the counter reaches the capacity of the cache (the number of resident slots), reset it to zero and halve every main-queue frequency counter: `freq >>= 1` on each resident main entry. Iterate the index (or the main deque, whichever the parent already walks cheaply) once per aging pass.
- Leave the small queue's counters untouched. Leave the second-chance rotation in the main-queue eviction path, `MAX_FREQ`, the promotion rule (`freq > 0`), and the ghost logic unchanged.
- Hit-path code (`get`) must not change. Aging runs only on the insert path, so it amortizes to O(1) per insert.

Invariants to preserve: `freq` stays a saturating `u8` bounded by `MAX_FREQ`; resident-key puts still write through the index slot; container fields other than the new counter are unchanged.

## Rationale (optional)

Insights from cycles 0002 and 0008 note that frequency aging has not been tested for hit rate, only checked once on one trace, so it is untested rather than neutral. The second-chance budget can keep entries that were hot long ago. Halving counters once per capacity's worth of inserts should let those entries age out, which is the one hit-rate lever the current lineage has not tried.
