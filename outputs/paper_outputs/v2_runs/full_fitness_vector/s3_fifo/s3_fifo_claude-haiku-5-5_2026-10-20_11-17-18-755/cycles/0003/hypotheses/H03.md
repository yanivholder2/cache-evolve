# H03

Storing 64-bit key fingerprints in the ghost queue instead of full keys should reduce put median and tail latency by removing per-eviction key clones, targeting per-op-time with hit-rate expected to stay within noise of baseline.

## Parent

baseline

## Changes

Start from baseline. Change the ghost queue to hold `u64` fingerprints of evicted keys, computed once with the same hasher the cache already uses, rather than cloned `K` values. The ghost membership test checks the fingerprint set, and the overflow path pops the oldest fingerprint from a fixed-capacity ring buffer sized to the ghost capacity, so no key is cloned on eviction and no tombstone or sequence tag is used. Keep the ghost membership structure a hash set of fingerprints so the membership test stays O(1), as the cycle 0001 hash index did. Do not change the small-queue promotion rule, the queue sizes, the main-queue second-chance budget, or `get()`. Keep `Entry` at 24 bytes. A ghost hit on a fingerprint collision is accepted as a ghost hit, so report hit rate both before and after the change to measure the collision effect.

## Rationale (optional)

Cycle 0002 showed that sequence-tagging the ghost queue added put cost, and cycle 0001 showed the O(1) membership test is a cost-side win with no policy effect. What remains open is the cost of moving full keys through the ghost queue on the put miss path. Replacing keys with fixed-size fingerprints and a ring buffer removes the clone and the pop-back cost together, and it avoids the per-eviction map insert that made the cycle 0002 variant slower. The main risk is hit-rate drift from fingerprint collisions, which the hypothesis states explicitly so the result can refute it.
