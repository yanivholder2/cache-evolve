# H03

Make `get` skip the `freq` store when the counter is already saturated at `MAX_FREQ`, so hot-key hits stop dirtying slab cache lines, lowering per-op-time with hit-rate unchanged.

## Parent

cycle/0006/v002

## Changes

This is a policy-neutral trim of `S3Fifo::get` only. The parent's `get` always does a read-modify-write: `e.freq = (e.freq + 1).min(MAX_FREQ)`. On a Zipfian workload most hits land on hot keys whose freq is already 3. Each of those hits still stores to the slab line, which turns a read-mostly hit path into a write on every hit.

- Rewrite the body to:
  ```
  let i = *self.index.get(key)? as usize;
  let e = &mut self.slots[i];
  if e.freq < MAX_FREQ { e.freq += 1; }
  Some(&e.value)
  ```
  The branch is highly predictable on hot keys. Its semantics are identical to the saturating min.
- Do not touch `put`, eviction, the index, `keys`, or the ghost. The layout stays exactly as in the parent (16-byte `Entry`, narrow `(K, u32)` index).
- Tests: keep `repeated_get_clamps_frequency`. Add a test that runs 10 `get`s on one key and asserts `freq == MAX_FREQ` after each `get` from the third onward, and that `freq` goes 1, 2, 3 on the first three.
- The hit-rate must be bit-identical to the parent. State the settled `small_size` from `h01_split_report` in the insight; it should equal the parent's.
- In the insight, compare `get` p50/p99 against the parent and note that the `get` code path did change, so a move can be credited. Cross-cycle notes flag `get` noise, so report the delta at both percentiles.

## Rationale (optional)

v002 showed that `get` responds to how much slab memory it touches. A store to a line that is otherwise only read costs more than a load: it can't stay clean, and with eviction going on it competes with write-back. This is the cheapest remaining `get`-path lever that does not change policy. It is independent of H01's layout change, so a win can be stacked onto it later.
