# H03

Adaptively resize the small/main partition from ghost-hit feedback, growing main by one slot whenever a ghosted key is re-put, to raise hit-rate on workload-a.

## Parent

baseline

## Changes

In `src/s3_fifo/mod.rs`, make `small_size` and `main_size` adapt at runtime (still with
`small_size + main_size == capacity`), similar to ARC's target-size adaptation:

1. Add a `capacity: usize` field to `S3Fifo` (store it in `try_new`). Keep the initial
   split `small_size = capacity / 4` (clamped to `[1, capacity-1]`) as in the baseline.
   Leave the capacity == 1 special case unchanged (no adaptation when `capacity < 4`).
2. **Ghost hit → grow main.** In `put()`'s ghost-hit branch (`in_ghost == true`), before
   admitting, if `small_size > max(1, capacity / 16)` then `small_size -= 1; main_size += 1`.
   Demoted keys coming back is a sign that the small queue is too short-sighted
   and main needs more room for them.
3. **Small-queue graduate with main full → grow small.** In `evict_small()`, when a
   tail graduates (`freq > 1`, threshold unchanged from baseline), if
   `main.len() >= main_size` and `small_size < capacity / 2` then `small_size += 1;
   main_size -= 1`. This pushes back when main is crowded with frequently reused small-queue keys.
4. **Enforce bounds after every resize.** After a resize, if `small.len() > small_size`,
   call `evict_small()`. If `main.len() > main_size`, call `evict_main()`. Each resize
   is only ±1 slot, so one eviction is enough. Don't recurse from inside `evict_small()`.
   For step 3, do the bound fix-up after the graduated entry has been pushed.
5. Keep the ghost queue bound at the *initial* main size, stored as a separate
   `ghost_cap` field, so ghost memory doesn't change as the split moves.

Keep these invariants:
- `small.len() + main.len() <= capacity` after every public `put`/`get` returns.
- `small_size >= 1`, `main_size >= 1`.
- `get()` only bumps `freq` and never moves entries.
- Field names `small`, `main`, `ghost` and the `evict_small`/`evict_main` methods stay,
  because inline tests reference them.

## Rationale (optional)

The baseline's fixed 25/75 split can't adapt to workload-a's mix of recency and frequency. H01 and H02
change which keys move between queues. This hypothesis changes how much room each queue
gets and leaves the per-key movement rules as they are in the baseline. If the cohort shows this helps, it can be
stacked with H01/H02 later.
