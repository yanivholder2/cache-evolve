# H01

Port cycle 0005 v001's `capacity/64` small-queue floor onto the 16-byte slab-free layout to raise hit-rate to about 0.731 while keeping metadata-size at 16.

## Parent

cycle/0005/v003

## Changes

There is one change, a policy constant, in `src/s3_fifo/mod.rs`. In `S3Fifo::put`, the ghost-hit branch currently guards the shrink with `self.small_size > (self.capacity / 16).max(1)`. Replace it with `self.small_size > self.small_floor()`. Add a private `#[inline] fn small_floor(&self) -> usize { (self.capacity / SMALL_FLOOR_DIV).max(1) }` and a module constant `const SMALL_FLOOR_DIV: usize = 64;`. This is the same lever cycle 0005 v001 applied to the slab layout.

Everything else stays byte-identical to the parent:

- `get`, which is a single probe into `index: FxHashMap<K, Entry<K,V>>`.
- `evict_main`, `evict_small_inner`, including the `freq > 1` graduation, the `capacity/2` upper clamp in `grow_small`, and the fix-up evictions.
- The ghost ring, `ghost_cap = initial main_size`, and `ring_len`. Do not resize the ghost.
- The `Entry` layout. It must stay 16 bytes, so keep the `entry_is_16_bytes` test.

Add a `#[cfg(test)]` test that builds `S3Fifo::new(2048)` and drives it with a workload that produces many ghost hits, for example a cyclic scan over 3000 keys repeated several times. The test asserts:

- `small_size` can drop below 128, the old floor.
- `small_size` never drops below 32.
- `small_size + main_size == capacity` always holds.

Do not add any release-build fields.

## Rationale (optional)

v001 showed the floor binds on workload-a and gave the only hit-rate gain since cycle 0001 (0.7283 → 0.7309). v003 got the best metadata-size, and its policy is identical to v001's parent. The two levers are orthogonal: one is a policy constant, the other is the storage layout. So this variant should match v001's hit-rate at v003's metadata-size and dominate both incumbents on those two axes. If hit-rate does not reach about 0.7309, then the gain from the floor depended on something in the slab layout, which would be surprising and worth knowing. `get` is unchanged from v003, so `get` latency should match v003's.
