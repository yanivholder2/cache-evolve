# H02

Recording main-queue eviction victims in the ghost queue (with the ghost bound raised to `capacity`) on top of v003 raises hit-rate on workload-a by letting evicted hot keys go straight back into main.

## Parent

cycle/0001/v003

## Changes

In `src/s3_fifo/mod.rs`:

1. `evict_main()`: right now, when the loop pops a tail with `freq == 0` it `break`s
   and the entry is dropped. Change this so the victim's key goes into the ghost
   queue before it is dropped: `if self.ghost.len() >= self.ghost_cap { self.ghost.pop_back(); }
   self.ghost.push_front(tail.key);` and then `break`. Do this only for an actual
   victim (freq 0), never for entries that are recycled with `freq -= 1`.
2. `try_new()`: set `ghost_cap: capacity` instead of `main_size`, and size
   `VecDeque::with_capacity` for ghost to match. The ghost now covers victims from
   both queues, so it needs roughly one cache-worth of history.
3. Leave the ghost-hit path in `put` as it is: on a ghost hit the key is removed
   from ghost, v003's adaptation shrinks small by one slot (still clamped at
   `capacity/16`), and the key is inserted at the front of main. Main-victim ghost hits
   therefore also count as "main is too small" evidence, which is consistent with
   ARC.
4. Note that the fix-up `evict_main()` calls inside the adaptation code will now
   also ghost their victims. That is intended.

Keep the graduation rule (`freq > 1`), `MAX_FREQ`, and the size clamps unchanged.
Make sure `adaptive_split_keeps_bounds` still holds (`ghost.len() <= ghost_cap`).
Add a unit test checking that a freq-0 main victim's key is in `ghost` after
`evict_main()`, and that a later `put` of that key lands it in `main`.

## Rationale (optional)

This was cycle 0001's H02. It was never evaluated because of the Maven 429 failure. It
changes a different movement rule from H01 (ghost coverage of main rather than the
small→main threshold), so the two results can be attributed separately.
