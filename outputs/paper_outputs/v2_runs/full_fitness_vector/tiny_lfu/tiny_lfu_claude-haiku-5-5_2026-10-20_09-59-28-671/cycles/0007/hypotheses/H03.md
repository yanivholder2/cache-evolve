# H03

Choosing each key's cache-line block from the key hash, and deriving each row's column inside that block from the seeded per-row hash, will keep the block-grouped per-op speedup of v003 while raising its hit-rate from 0.7261 back to the incumbent level of 0.7379 on workload-a at size 2048.

## Parent

cycle/0006/v003

## Changes

Keep v003's grouping of one key's sketch counters into a single 64-byte block so that all rows of an access touch one cache line. Change the block-selection and column-selection so collisions are no longer driven by the block hash alone: the block index comes from the key hash modulo the number of blocks, and each row's column within the block comes from that row's seeded per-row hash modulo the block's counter count. The row seeds must be the module-level constant table from cycle 0005 v002, not per-instance fields. Keep the counter width and the aging schedule unchanged. Do not add struct fields and do not change the sketch heap size or the TinyLfuCache layout. Keep the get and put control flow of v003 as written, and verify that the metadata breakdown matches the parent's per-struct sizes; if a field grows, the variant is not valid.

## Rationale (optional)

v003 cut both get and put p50 by putting a key's rows in one cache line, but its block hash changed which keys share counters and cost roughly 0.0118 hit rate. The cross-cycle record says index layouts that change collisions move hit rate, so the claim here is that a within-block row index keeps the speedup while restoring the collision spread. The hypothesis is refuted if hit-rate stays below 0.7379 or if per-op-time returns to the parent's level, since either would mean the speedup depended on the collision change.
