# H01

Switching the frequency sketch to conservative update will raise hit rate on workload-a at size 2048 by reducing over-estimated candidate and victim counts caused by hash collisions, without changing per-row indices.

## Parent

cycle/0006/v002

## Changes

Change only the sketch increment path, not its index computation or its estimate path. In the function that bumps a key's counters (the increment routine called from the get and put paths), first read the current counter at each of the key's rows, compute the minimum of those values, and then increment only the counters whose value equals that minimum (still saturating as the current code does). Counters above the minimum are left untouched. Keep the per-row index derivation exactly as it is now, so every key still maps to the same counters. Keep the estimate function as the minimum across rows, unchanged. Do not change aging, the doorkeeper-free admission flow, the protected/probation lists, eviction order, or any struct layout; the change must add no per-instance fields. The expected cost is one extra pass over the key's rows per increment, so report get and put timing against the parent to confirm the overhead is small.

## Rationale (optional)

Recent cycles showed that index-preserving speedups leave hit rate flat, and that index-altering changes move hit rate. Conservative update keeps indices fixed but changes what the sketch records under collisions, which is the one lever on the admission gate that has not been tried. Earlier attempts (doorkeeper, shorter aging, tie-breaking) altered what is counted or when it decays; this one alters only how collided counts accumulate.
