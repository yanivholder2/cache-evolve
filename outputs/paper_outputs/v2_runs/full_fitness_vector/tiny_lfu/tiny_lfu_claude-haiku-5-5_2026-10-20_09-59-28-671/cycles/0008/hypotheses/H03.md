# H03

Reshaping the frequency sketch to more columns and fewer rows at the same total counter memory will raise hit rate on workload-a at size 2048 by reducing the collision rate per counter.

## Parent

baseline

## Changes

Change only the dimensions of the CountMinSketch allocation and the code that derives row and column indices from them. Keep the total counter bytes equal to the current sketch allocation (the 65536 bytes reported in the metadata breakdown). Reduce the row count by one, from the current depth to depth minus one, and increase the column count so the product of rows and columns, multiplied by the counter width, still equals that byte budget. Derive per-row indices with the same seeded mixing function as today, so the scheme stays public-path-compatible; only the modulus changes to the new column count. Leave the estimate function as the minimum across rows, and leave aging, admission, eviction order, and the segment lists unchanged. Do not add any struct field beyond what the resize requires, and do not change the metadata reporting code. Report the new row and column counts in the variant's insight so the cross-cycle record shows which shape was tested.

## Rationale (optional)

Index-altering changes have been the only class that moved hit rate in this lineage, and collision spread in the sketch is the most sensitive area recorded so far. Earlier cycles changed indexing formulas and layouts but kept the sketch's shape fixed. Trading depth for width at constant memory tests whether the current shape overcounts collided keys more than the extra row helps. Because the memory budget is fixed, any gain or loss is attributable to shape rather than size, and the result stands on its own against baseline.
