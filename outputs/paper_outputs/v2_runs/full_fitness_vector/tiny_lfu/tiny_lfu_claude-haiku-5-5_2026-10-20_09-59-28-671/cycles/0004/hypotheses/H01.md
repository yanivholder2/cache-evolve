# H01

Precomputing the per-row sketch seeds once at cache construction will cut the per-op-time cost of the public seeded row indexing while leaving every counter index, and therefore hit rate, unchanged, targeting per-op-time.

## Parent

cycle/0003/v002

## Changes

Parent v002 switched the frequency sketch's row indexing to the public per-row seeded scheme, which derives each row's index from the base hash and a per-row seed on every sketch access. That derivation is the source of the speed loss recorded for v002 (get and put both slower than v001).

Modify the sketch's index derivation so that the per-row seeds are computed once, when the sketch is constructed, and stored in a fixed-size array field on the sketch struct (one seed per row). The per-access index function should then read `seeds[row]` and compute the index with the same arithmetic as the public path, rather than re-deriving the seed each call.

Invariants to preserve:
- For any key, the counter index used in every row must be identical to the index the public per-row seeded method produces. Add a debug assertion or a small test-local comparison of the two derivations over a range of keys to confirm this, without editing `tests/` (gate-integrity surface).
- Sketch width, depth, counter layout, and the aging logic are unchanged.
- The `put()` and `get()` control flow is unchanged; only the sketch index helper changes.
- Do not add a doorkeeper or change the admission threshold.

Keep the struct growth to the seed array only. If the array would increase the sketch's size measurably, prefer deriving the seeds from a constant table in a `const` item instead of a field, so metadata-size stays at the parent's value.

Verify in the implementer's notes which function(s) now compute per-row indices, since the parent's source was not available during hypothesis authoring.
