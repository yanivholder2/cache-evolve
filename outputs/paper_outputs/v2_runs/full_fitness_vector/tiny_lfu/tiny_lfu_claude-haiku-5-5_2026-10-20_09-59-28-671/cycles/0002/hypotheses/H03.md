# H03

Adding a one-hit doorkeeper bit-vector in front of the CountMinSketch raises hit rate by keeping single-access keys out of the frequency counts that the admission gate reads.

## Parent

baseline

## Changes

Add a small doorkeeper bit-vector to `TinyLfuCache`, sized to a fixed number of bits (for example 1 bit per 8 sketch counters, so about 8 KiB for the existing sketch capacity of 1024). Consult it in `put()` and `get()` before touching the CountMinSketch. On a key's first sighting in a reset window, set its doorkeeper bits and do not increment the sketch. On later sightings, increment the sketch as the baseline does. Use the same hash family as the sketch for the doorkeeper indices. Clear the doorkeeper whenever the sketch's existing aging or reset step runs, so both structures age together. Leave `evict_one()`, the LRU list operations, and the admission comparison unchanged, so the only behavioural difference is which keys contribute frequency counts. Do not add any recency-based victim handling.

## Rationale (optional)

Cycle 0001 found that the frequency admission gate is the component doing useful work, and that recency rotation on top of it hurt. A doorkeeper does not add recency logic. It changes what the gate sees, by filtering one-hit wonders out of the frequency estimates, which is the standard TinyLFU design. The expected cost is metadata for the bit-vector, so the measured metadata-size will rise. The hypothesis is confirmed if hit rate on lirs workload-a rises above 0.736 at a metadata cost that is reported, and refuted if hit rate is flat or lower.
