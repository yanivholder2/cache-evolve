# H01

Hashing each key once per put() and reusing that hash for the admission check and the sketch update lowers per-op-time on the put path without changing eviction order or hit rate.

## Parent

cycle/0001/v002

## Changes

In `put()`, compute the key's hash once at the top of the function and pass that value to both the admission-gate lookup and the CountMinSketch increment, instead of rehashing the key in each call. Add a private helper that takes a precomputed hash (for example `sketch_increment_hashed(hash)` and `sketch_estimate_hashed(hash)`), and have the existing public sketch methods delegate to it so their behaviour is unchanged. Do not alter the order of the admission decision, the victim choice in `evict_one()`, or the LRU relinks, so the hit rate stays identical to the parent. Keep the tail guard added by v002 in both `get()` and the update branch of `put()`. Do not change the on-disk or in-memory size of `Node` or `TinyLfuCache`.

## Rationale (optional)

v002 showed that constant-factor work on the hot path is a safe source of speed. put() has the highest p50 and p99 of the two operations in the cycle 0001 measurements (put p50 121 ns versus get p50 92 ns on v002), so it is the place where removing repeated work should show up. This hypothesis trades nothing in hit rate or metadata for a latency gain.
