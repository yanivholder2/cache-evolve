# H01

Fusing the conservative-update increment into one register-held pass, and giving `get` a non-returning increment, will lower per-op-time without changing hit rate.

## Parent

cycle/0003/v003

## Changes

Only `CountMinSketch` and `TinyLfuCache::get` in `src/tiny_lfu/mod.rs` change. Hit-rate behaviour must stay bit-for-bit identical to v003: same index function, same depth/width, same "bump only counters equal to the minimum, saturating at `MAX_COUNT`" rule.

1. Rewrite `increment_hash(&mut self, h: u64) -> u32` so that each counter is loaded from memory once. Compute the 4 flat indices up front with `index(h1, h2, row)` for rows 0..4, unrolled by hand (no `iter_mut().enumerate()`). Load the 4 values into locals `c0..c3`. Compute `min` with branch-free `min()` calls. Compute `inc = (min < MAX_COUNT) as u32`. Write back `counts[iK] = cK + (((cK == min) as u32) & inc)` from the locals, with no reload. Use `get_unchecked`/`get_unchecked_mut` inside an `unsafe` block, with a `debug_assert!` that every index is `< counts.len()`. This is sound because `index` masks with `width - 1` and adds `row * width` with `row < SKETCH_DEPTH`. Return `min + inc`.
   Caveat: two rows can map to the same flat index only when they are the same row, so the 4 indices are always distinct (each is in its own row's range). Writing back from locals is therefore equivalent to v003's reload loop. Put this reasoning in a comment.
2. Add `#[inline(always)] fn increment_only(&mut self, h: u64)` that does the same thing but returns nothing, so `get` doesn't keep the `min + inc` result live. Change `TinyLfuCache::get` to call `self.sketch.increment_only(key_hash(key))`. `put` keeps calling `increment_hash` and reuses its return value as `incoming_freq`.
3. Unroll `estimate_hash` the same way: 4 hand-unrolled unchecked loads and a branch-free min. Drop the dead `if self.depth == 0` branch, because depth is the constant `SKETCH_DEPTH` (> 0). Keep the `depth` field for `heap_bytes`, or replace it with `SKETCH_DEPTH`.

Keep the existing tests passing, including `conservative_update_bumps_only_minimum_counters` and `conservative_update_saturates`. Add one unit test that `increment_only` and `increment_hash` leave identical counter states for the same hash sequence.

## Rationale (optional)

v003's insight blames its `get` p50 regression on the two-pass, reload-heavy increment loop. That loop runs on every `get`, and `get` gets nothing back from it. This change checks whether conservative update can cost the same as v001/v002's fused increment (≈33 per-op) while keeping v003's best hit rate (0.7401). Evaluate it side by side with v003, since per-op drift has been seen before.
