# H02

Upgrading SIEVE's single visited bit to a 2-level saturating counter (0..=2) that the hand decrements by one per pass will raise hit-rate above v003's 0.7264 on workload-a.

## Parent

cycle/0002/v003

## Changes

Work in `src/lru_cache/mod.rs` of cycle/0002/v003.

1. **Node field.** Replace `visited: bool` with `freq: u8` in the same padding slot, so
   `Node<u64,u64>` stays at 32 bytes. Add `const FREQ_MAX: u8 = 2;`. Use 2, not GCLOCK's 3, to bound the extra
   sweep work to at most two revolutions.

2. **Hit path.** In `get()` and in the update-in-place branch of `put()`, replace
   `node.visited = true` with the branch-free saturating bump
   `node.freq += (node.freq < FREQ_MAX) as u8;`. There is still no relinking.

3. **Insertion.** New and reused slots are initialised with `freq = 0`, which preserves SIEVE's quick demotion of
   one-touch keys.

4. **`find_victim()`.** Walk from `hand` (or `head` if `NIL`). If `freq == 0`, return the node.
   Otherwise decrement `freq` by 1 and advance via `next`, wrapping to `head` at `NIL`. Update the doc comment and
   add a `debug_assert!` that the walk ends within `FREQ_MAX as usize * capacity + 1` steps.
   The rest of `put()` (hand resumes at `victim.next`, unlink, reuse slot in place, push_back
   at the tail) stays exactly as in the parent.

5. **Tests.** Rename the `visited` assertions to check `freq`. Adjust `visited_key_survives_eviction_without_moving`
   to assert `freq == 0` after one hit followed by one pass. Add a test showing that a key hit twice survives two
   hand passes, while a key hit once survives only one. Add a test that the all-saturated sweep terminates and
   evicts the slot where the hand started. Keep `randomized_workload_preserves_structure`,
   with an added check `freq <= FREQ_MAX`.

## Rationale (optional)

GCLOCK (cycle/0002/v002) showed that a multi-level counter adds hit-rate over a single reference bit on
this trace (CLOCK 0.675 → GCLOCK 0.687). SIEVE already has the best single-bit result. Combining SIEVE's
quick demotion of new keys with frequency credit for reused keys is the SIEVE/GCLOCK hybrid that both
insight files list as an open question. Capping the counter at 2 rather than 3 tests whether the gain survives
with a smaller sweep penalty. Metadata stays flat because the counter sits in existing padding.
