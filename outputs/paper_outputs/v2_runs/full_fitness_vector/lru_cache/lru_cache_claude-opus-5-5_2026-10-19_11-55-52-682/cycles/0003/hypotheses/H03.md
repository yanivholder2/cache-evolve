# H03

Capping SIEVE's hand sweep at 32 steps per insert, with forced eviction of the 32nd node examined, will reduce per-op-time (especially put p99) without materially lowering v003's hit-rate.

## Parent

cycle/0002/v003

## Changes

Work in `src/lru_cache/mod.rs` of cycle/0002/v003.

1. Add `const MAX_SWEEP: u32 = 32;`.

2. **`find_victim()`.** Keep the parent's walk: start at `hand` (or `head` if `NIL`), clear `visited`
   on visited nodes, advance through `next` and wrap to `head` at `NIL`. Also count the nodes examined.
   If the walk reaches the `MAX_SWEEP`-th node examined without finding an unvisited one, return that node as the
   victim even if its `visited` bit is set. It has just been cleared or is about to be, so set
   `visited = false` before returning. Whenever an unvisited node appears earlier, the parent's behaviour is unchanged.
   This bounds the insert path to O(MAX_SWEEP) node touches instead of O(capacity).

3. Everything after `find_victim()` in `put()` stays unchanged: hand resumes at `victim.next`,
   the old key is removed from the map, the slot is unlinked, reused in place and pushed back at the tail.
   `get()` and update-in-place are unchanged.

4. **Tests.**
   - Add `sweep_is_bounded`. Build a cache of capacity 128, fill it, `get` every key so all are visited, then
     `put` a new key. Assert that the evicted key is the `MAX_SWEEP`-th node from the hand's start position, that
     exactly the first `MAX_SWEEP` nodes had their visited bit cleared, and that the remaining nodes are still visited.
   - Keep all existing tests. They use capacities ≤ 16 or runs shorter than 32, so their expected
     eviction order is unchanged.
   - `scan_of_unique_keys_does_not_evict_visited_key` (capacity 8, below the cap) must still pass
     without modification.

## Rationale (optional)

Both cycle insights name hand-sweep length as the remaining cost on the put tail. v003's put p99 (108 ns)
is about 2× its p50, because long runs of visited nodes force O(run) bit-clears. At size 2048, a run of more than 32
consecutive visited nodes ahead of the hand should be rare enough that forced evictions affect only a small
fraction of inserts, so hit-rate should drop by no more than about 0.002. If hit-rate drops more, that tells us long
visited runs carry real reuse signal on workload-a. This is the "cap on steps per insert" option listed in
cross-cycle open questions. It is distinct from H01, which changes layout, and from H02, which deepens the counter.
