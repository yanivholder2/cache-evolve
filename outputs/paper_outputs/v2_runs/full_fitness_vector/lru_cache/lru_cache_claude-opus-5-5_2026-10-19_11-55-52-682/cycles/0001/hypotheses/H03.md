# H03

Inserting new keys at the LRU (head) end and only rarely at the MRU end (bimodal insertion, 1 in 32) will raise hit-rate on the looping LIRS workload-a trace at size 2048 above the baseline's 0.6652, because a looping working set larger than the cache keeps a stable resident fraction instead of thrashing.

baseline

## Changes

Edit `src/lru_cache/mod.rs` only (do not touch `lru_cache_jni.rs`; keep the public API, the `Node` layout and the `framework::Cache` impl). The recency list, arena and `get` promotion stay exactly as they are in the baseline. Only the insertion position of new keys changes.

1. Add a helper `fn push_front(&mut self, idx: usize)` that links `idx` at the head (LRU end). Set `node.prev = None` and `node.next = self.head`. If there is an old head, set its `prev = Some(idx)`. Otherwise also set `tail = Some(idx)`. Then set `head = Some(idx)`.
2. Add `insert_tick: u32` to `LruCache`, initialised to 0.
3. In `put`, new-key path only, replace the final `self.push_back(idx)` with:
   - `self.insert_tick = self.insert_tick.wrapping_add(1);`
   - if `self.insert_tick & 31 == 0`, call `push_back(idx)` (an occasional MRU insert so the cache can still adapt when the working set changes); otherwise call `push_front(idx)`.
   - Use the counter rather than an RNG, so results are deterministic and there are no extra dependencies.
4. Warm-up exception: while `nodes.len() < capacity` (the arena-has-room branch), always use `push_back`. This fills the cache in plain LRU order, so filling it does not cost hits.
5. Leave the existing-key path in `put` and all of `get` unchanged. Both still promote to MRU via `unlink` + `push_back`, so a key that is hit once is protected from the next eviction.

Behaviour to note: a key inserted at the head is the very next eviction victim unless it is hit before the next miss. Eviction still always takes `head`.

Invariants to preserve: `map.len() <= capacity`, links stay consistent, and no phantom keys.

In-file unit tests that depend on new-insert order after the cache is full (`eviction_chain`, `slot_reuse_after_promotion_and_re_eviction`, `overwrite_mru_at_capacity`) need their expectations updated for head insertion. Tests that only fill up to capacity are unaffected because of the warm-up exception. The gate tests must pass unchanged.

## Rationale (optional)

This is the BIP policy from Qureshi et al., ISCA 2007. Unlike H01 (SLRU), it adds no segments or per-node state and costs one counter increment per miss. It tests whether insertion position alone, with no change to how keys move on a hit, captures the loop-resistance gains on this trace.
