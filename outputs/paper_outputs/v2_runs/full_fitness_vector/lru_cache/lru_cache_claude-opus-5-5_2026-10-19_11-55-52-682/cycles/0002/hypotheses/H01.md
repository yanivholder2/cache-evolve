# H01

Inserting new keys at the LRU end of SLRU's probationary segment (bimodal, 1 in 32 at the probationary MRU end) will raise hit-rate on LIRS workload-a at size 2048 above v001's 0.7241, keeping v001's 32-byte node.

## Parent

cycle/0001/v001

## Changes

Edit `src/lru_cache/mod.rs` only (do not touch `lru_cache_jni.rs`; keep the public API `try_new`, `new`, `get`, `put` and the `framework::Cache` impl). Keep v001's `Node` layout (`u32` prev/next with `NIL = u32::MAX`, `seg: u8`) exactly as it is. The metadata bench reports `size_of::<Node<u64,u64>>()`, so do not add any per-node fields.

1. Add `fn push_front(&mut self, idx: u32, seg: u8)`, the mirror of the existing `push_back`. It links `idx` at the LRU (head) end of the given segment: set `seg`, `prev = NIL`, `next = old head`. If the old head exists, set its `prev = idx`. Otherwise also set the segment's tail to `idx`. Then set the segment head to `idx`, and increment `prot_len` if `seg == PROT`. In practice it is only called with `PROB`, but keep it general.
2. Add `insert_tick: u32` to `LruCache`, initialised to 0. It should fit next to the existing fields; a fixed per-cache word is acceptable.
3. In `put`, new-key path only:
   - In the arena-has-room branch (`nodes.len() < capacity`, warm-up), keep `push_back(idx, PROB)` unchanged.
   - In the arena-full (eviction) branch, replace the final `push_back(idx, PROB)` with: `self.insert_tick = self.insert_tick.wrapping_add(1); if self.insert_tick & 31 == 0 { self.push_back(idx, PROB) } else { self.push_front(idx, PROB) }`. Because the code is currently written as one `push_back` after the `if/else`, restructure so that each branch chooses its own insertion.
4. Leave `on_hit` unchanged: promotion from probation to protected, protected MRU moves, and demotion of the protected LRU to the probationary **MRU** end all stay as they are. Demoted keys have proven reuse and should keep their full probationary lifetime. Eviction still takes `prob_head`, falling back to `prot_head`.

Effect: a new key that is not hit before the next miss is the very next victim. The rest of the probationary segment (demoted keys and the occasional 1/32 MRU insert) therefore stays resident long enough to get its second touch, instead of being pushed out by a loop that is larger than the cache.

Invariants: `map.len() <= capacity`, each resident key is in exactly one segment list, `prot_len` matches the protected list length, and there are no phantom keys. Update `check_structure` if needed (it should still pass as written). Update the in-file tests that depend on post-full insertion order (`eviction_chain`, `slot_reuse_prefers_probation_victims`, `overwrite_mru_at_capacity`, `victim_falls_back_to_protected_when_probation_empty`) to match head insertion. Add a test showing that a scan of unique keys after the cache is full evicts only through one probationary slot (the earlier probationary residents survive, apart from the 1/32 MRU inserts). Keep `node_fits_in_32_bytes_for_i64`. The gate tests must pass unchanged.

## Rationale (optional)

Cycle 0001 found that SLRU (v001) and BIP (v003) each beat LRU, and suggested the mechanisms could stack. In v001, every miss still pushes a probationary key toward eviction, so a long loop can flush probation before its keys get their second touch. BIP inside probation stops that at the cost of one counter. If hit-rate does not move past 0.7241, the two mechanisms overlap on this trace.
