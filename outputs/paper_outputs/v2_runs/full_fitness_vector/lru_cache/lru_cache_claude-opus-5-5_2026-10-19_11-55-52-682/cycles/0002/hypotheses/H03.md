# H03

Replacing LRU with the SIEVE policy (FIFO queue with `u32` links, a visited bit, and a hand that keeps survivors in place) will raise hit-rate on LIRS workload-a at size 2048 above the best so far, v001's 0.7241, with a 32-byte node and no relinking on a hit.

## Changes

Rewrite `src/lru_cache/mod.rs` (do not touch `lru_cache_jni.rs`; keep the public API `try_new`, `new`, `get`, `put` and the `framework::Cache` impl exactly as they are).

Data structure:
- `const NIL: u32 = u32::MAX;`
- `Node<K, V> { key: K, value: V, prev: u32, next: u32, visited: bool }`. This is the `u32`-link compaction from v001, which should give 32 bytes for `Node<u64,u64>`. Add an in-file test asserting `<= 32`.
- `LruCache { map: HashMap<K, usize>, nodes: Vec<Node<K,V>>, head: u32 /* oldest */, tail: u32 /* newest */, hand: u32, capacity: usize }`. `try_new` rejects `capacity >= NIL as usize`, as v001 does.
- Helpers `unlink(idx)` and `push_back(idx)` (append at `tail`, the newest end), written with `u32`/`NIL` as in v001 but for a single list.

Behaviour:
- `get` hit: set `nodes[idx].visited = true` and return the value. No unlink or push.
- `put` on an existing key: update the value in place and set `visited = true`. No relinking.
- `put` on a new key while `nodes.len() < capacity`: push the node with `visited = false` via `push_back` and insert it into `map`.
- `put` on a new key when full (SIEVE eviction):
  1. `let mut h = if self.hand == NIL { self.head } else { self.hand };`
  2. While `nodes[h].visited`: clear it, then `h = nodes[h].next`. If that is `NIL`, wrap to `self.head`. This terminates within `capacity + 1` steps because one pass clears every bit.
  3. Victim is `h`. Before unlinking, save `self.hand = nodes[h].next`. It may be `NIL`, which means start again at `head` next time. The hand must never point at the slot being reused.
  4. Remove the victim's key from `map`, `unlink(h)`, overwrite the key and value in place, set `visited = false`, `push_back(h)` (newest end), and insert into `map`.
- The key difference from CLOCK (v002): a surviving visited key is **not** moved, and new keys are inserted at the newest end, behind the hand's direction of travel. One-touch keys therefore become eviction candidates quickly ("quick demotion"), while keys that are reused stay in place indefinitely ("lazy promotion").

Invariants: `map.len() <= capacity`. The list contains exactly the resident slots. `hand` is `NIL` or a linked slot. No phantom keys. With capacity 1, the victim's `next` is `NIL`, so the hand resets. Add a test for this case.

Replace the baseline's LRU-order in-file tests with SIEVE-semantics tests: a visited key survives an eviction without moving, the hand resumes after the victim, a scan of unique keys does not evict a visited key, and a structural check (walk from `head`, verify prev/next and the map, and that `hand` is linked or `NIL`) runs after a randomized 20k-op workload. The gate tests must pass unchanged.

## Rationale (optional)

Cycle 0001's lesson was that departing from strict recency helps on this trace and that relink-free hits help speed. SIEVE (Zhang et al., NSDI 2024) combines both: lazy promotion like CLOCK and quick demotion of new keys similar to BIP/SLRU probation, in one queue with one bit. It is a different strategy from stacking the existing winners, and tests whether a single simple policy can beat SLRU's 0.7241.
