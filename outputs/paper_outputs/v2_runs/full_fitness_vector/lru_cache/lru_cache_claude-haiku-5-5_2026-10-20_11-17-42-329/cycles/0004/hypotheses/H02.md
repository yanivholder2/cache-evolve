# H02

Hoisting the arena index conversions in cycle/0002/v003 to one node lookup per operation lowers get p50 while keeping the narrowed u32-style links and their smaller metadata-size.

## Parent

cycle/0002/v003

## Changes

Keep the narrowed arena-index representation from the parent unchanged, including its link width and node layout. Add two private helpers on the cache, `node(&self, idx) -> &Node` and `node_mut(&mut self, idx) -> &mut Node`, each marked `#[inline(always)]`, that perform the single `idx as usize` conversion and bounds-checked index. Rewrite `get()` so it resolves the map entry to an index once, takes one reference through `node()` for the hit check, and then performs move-to-front using that same index, instead of re-indexing the arena for each link read and write. In `unlink` and `push_back`, read each neighbour link through one `node()` call and reuse the resulting reference rather than indexing `nodes[idx as usize]` repeatedly within the same function. Do not change eviction, admission, or the replacement policy; hit-rate should match the parent exactly. Do not add fields to `Node` or `LruCache`.

## Rationale (optional)

The cycle 0002 insight found that narrowing the indices saved memory but made `get` slower, and it attributes the cost to width conversions and arena lookups at hot call sites rather than to the policy. The cycle 0003 insight points the same way, saying the next gains are in arena access patterns, not link encoding. This hypothesis keeps the smaller links and attacks only the repeated index work. If `get` does not improve, the regression is more likely a layout effect than an access-count effect.
