# H01

Lowering the protected-segment share from 4/5 to 3/4 of capacity raises hit-rate on the scan-heavy LIRS workload-a trace without adding per-operation or metadata cost.

## Parent

cycle/0005/v002

## Changes

Change only the body of `protected_cap()` in `src/lru_cache/mod.rs`: replace `(self.capacity * 4 / 5).max(1)` with `(self.capacity * 3 / 4).max(1)`. Leave `select_victim`, `demote_prot_head`, `unlink`, `push_back`, and the `u32` arena layout exactly as in the parent. The `debug_assert!(self.prot_len <= self.protected_cap())` checks in `select_victim` and the bound in `demote_prot_head` still hold because `prot_len` is only ever compared against the same function. Keep the `.max(1)` guard so the protected cap is never zero (it only applies for capacity 1, where `3 / 4` yields zero).

Expected effect: a smaller protected segment leaves more probationary room for one-hit keys to be evicted, so frequently re-referenced keys are demoted sooner and the cache spends less capacity on stale protected entries. The hypothesis is that this moves the hit-rate, not the per-op cost, so the get and put medians should stay near the parent's values.

## Rationale (optional)

v002 showed the narrowed layout is policy-neutral, so the segment ratio is the cheapest remaining policy knob. Cycle 0004 and 0005 insights note that protection depends on actually moving the head, so shrinking the protected share is a direct test of how much protected capacity the workload needs. Both directions are plausible; the implementer should measure only this one-line change.
