# H03

A bounded ghost ring of recently evicted key fingerprints, consulted only on misses, admits returning keys straight to the protected segment and raises hit-rate on the scan-heavy workload-a trace while leaving the get path untouched.

## Parent

baseline

## Changes

Work from the baseline's segmented/second-chance structure as it is on the baseline source (do not import the `u32` arena from cycle 0005).

1. Add two fields to `LruCache`: `ghost: Vec<u32>` (a fixed-size ring of fingerprints, initialised to zeros with length `capacity`) and `ghost_pos: usize` (next write position). Initialise both in `try_new`.
2. Add a helper `fn fingerprint(key: &K) -> u32` that hashes the key with a cheap non-cryptographic mix (for example, `std::collections::hash_map::DefaultHasher` is acceptable only if the implementer finds it fast enough; a hand-rolled multiply-rotate over the `Hash` output is preferred). Force the result to be nonzero by OR-ing in 1, so zero means "empty slot".
3. In `put`, on the eviction branch, before `self.map.remove(&evicted_key)`, write `fingerprint(&evicted_key)` into `ghost[ghost_pos]`, then advance `ghost_pos` modulo `capacity`.
4. In `put`, for a new key (not present in the map), compute `f = fingerprint(&key)` once. Scan `ghost` for `f`. If found, set that slot to zero and insert the node into the protected segment: if `prot_len >= protected_cap()`, call `demote_prot_head()` first, then `push_back(idx, true)`. If not found, keep the existing probationary `push_back(idx, false)`. Apply this to both the "arena has room" and "arena full" branches, after the victim is chosen and before the node is linked.
5. Leave `get`, `select_victim`, `demote_prot_head`, `unlink`, and `push_back` as they are. The get path must not hash anything new. The ghost check runs only on misses, inside `put`.
6. Keep the overwrite branch of `put` (existing key) unchanged.

Expected effect: a returning key that was evicted recently has shown reuse, so admitting it directly to protected should keep it resident through the scan, which is the pattern cycle 0003 identified as the source of the admission filter's hit-rate gain. The hypothesis is that this gives hit-rate gains similar to the sketch lineage without its per-access hashing, because the ring is consulted only on misses.

## Rationale (optional)

This is a different strategy from the sketch admission filter in cycles 3 to 5 (it remembers evicted keys rather than counting accesses) and from the credit and sparing variants (it changes insertion, not demotion). The metadata cost is a per-cache ring of `capacity` u32 values, not per-node fields, so metadata-size for the node should stay at the baseline's 48 bytes. The main risk is that the ring's length equals capacity, so the implementer should check that the ring does not dominate the struct's reported size; if it does, report the size honestly.
