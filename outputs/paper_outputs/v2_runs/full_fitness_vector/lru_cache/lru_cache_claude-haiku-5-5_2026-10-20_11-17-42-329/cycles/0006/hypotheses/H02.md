# H02

Replacing the default SipHash hasher on the key-to-index map with a cheap non-cryptographic hasher lowers get and put median latency without changing hit-rate or metadata size.

## Parent

cycle/0005/v002

## Changes

Keep the `u32` arena, the `NIL` sentinel, the segmented lists, the second-chance logic, and every eviction path exactly as in the parent. Change only the map's hasher:

1. In `src/lru_cache/mod.rs`, add a small hasher type in the same file, for example `struct FastHasher(u64)` implementing `std::hash::Hasher`. In `write_u64`, `write_usize`, and `write`, fold input into the state with a multiply-and-rotate step (an FxHash-style mix). Implement `finish()` as returning the state. `Default` must start the state at zero.
2. Add `pub struct FastBuildHasher;` implementing `std::hash::BuildHasher` with `type Hasher = FastHasher` and a `build_hasher()` that returns `FastHasher::default()`.
3. Change the field `map: HashMap<K, u32>` to `map: HashMap<K, u32, FastBuildHasher>`. In `try_new`, construct it with `HashMap::with_capacity_and_hasher(capacity, FastBuildHasher)` instead of `HashMap::with_capacity(capacity)`.
4. Add `use std::hash::{BuildHasher, Hasher};` alongside the existing `use std::hash::Hash;`.

Do not change the `Node` layout or `LruCache` fields other than the map's type, so metadata-size should match the parent's 32/104 bytes. Keep the byte-wise `write` path correct for arbitrary `Hash` impls, since `K` is generic. All existing unit tests in the module must still pass. The hasher is not required to resist adversarial keys; it only needs to distribute the workload's keys well enough to keep map probes short.

Expected effect: the parent's `get` runs a SipHash on every hit, which is the largest per-op cost left on the read path. Cycle 0004 found that a cheaper shared hash lowered read cost without changing hit-rate, so the same mechanism is tested here on the map itself.

## Rationale (optional)

This is orthogonal to the policy: hit-rate should stay at 0.7058 on workload-a. The change targets the per-op-time dimension, which the parent has held at 46 ns for get since cycle 0004, so any gain would be a clear improvement rather than noise.
