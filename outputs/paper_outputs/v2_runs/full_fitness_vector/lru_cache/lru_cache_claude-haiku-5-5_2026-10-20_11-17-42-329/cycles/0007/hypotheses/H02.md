# H02

Add a bounded ghost set of recently evicted keys with O(1) hashed lookup, so a key that returns while still in the ghost set is admitted straight to the protected segment, to raise hit-rate on the scan-heavy workload-a trace.

## Parent

cycle/0006/v002

## Changes

Add a ghost structure to `LruCache`: a `HashSet<K>` built with `FastBuildHasher`, plus a `VecDeque` ring of `(K, u64 seq)` entries, capped at `capacity` entries. Use lazy deletion to keep every operation O(1): the set maps each ghost key to its current sequence number, and a deque entry is authoritative only if its seq matches the set's seq for that key. Stale deque entries are skipped when popped.

Eviction side: in `put`, after `select_victim()` picks the victim and before the slot is reused, record the victim's key in the ghost (new seq, insert into the set, push to the back of the ring). If the ring exceeds `capacity`, pop front entries until it is within bound, and for each popped entry that is still current in the set, remove it from the set.

Miss side: in `put`, in the new-key branch (not the existing-key branch), check the ghost set first. If the key is present, remove it from the set (its deque entry becomes stale), and insert the key with the PROTECTED flag set instead of probationary: call `push_back(idx, true)` in place of `push_back(idx, false)`. Protected overflow is still handled by `select_victim` and `demote_prot_head` as today. Ghost keys that are not hit simply age out of the ring.

Hit path: `get` is unchanged. Do not touch the ghost on `get`, so the hit path keeps its current cost.

Preserve the current `select_victim` second-chance logic, `demote_prot_head`, `unlink`, and `push_back`. Keep `protected_cap()` at 4/5 of capacity. Add a `ghost_len()` or equivalent debug-only accessor only if needed for tests; do not change the `framework::Cache` impl.

## Rationale (optional)

Cycle 0006 v003 showed a ghost ring of recently evicted keys gains scan resistance, but its linear scan on every miss cost put time, and its heap storage is not in the metadata-size metric. Here the ring's lookup becomes a hashed set, which is the open question recorded in cycle 0006's insight. The main risk is put-side cost: the set insert and lookup add work on the miss path, so expect a put regression. Report the ghost's heap footprint (about `capacity` keys plus the set and deque overhead) alongside struct size, so the metadata cost is visible. Success means a hit-rate gain over 0.7058 with get unchanged.
