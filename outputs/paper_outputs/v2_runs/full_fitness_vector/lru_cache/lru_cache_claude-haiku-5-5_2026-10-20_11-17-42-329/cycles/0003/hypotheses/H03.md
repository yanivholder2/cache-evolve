# H03

Adding TinyLFU-style frequency admission to the baseline LRU, so a miss at capacity only evicts the LRU victim when the candidate is at least as frequent, raises hit-rate on the LIRS workload-a trace.

## Parent

baseline

## Changes

Start from the baseline LRU (`src/lru_cache/mod.rs`, HashMap plus an arena-based doubly-linked list, with move-to-MRU on `get`). Keep the link structure and `get()`'s move-to-MRU behaviour as is. Change `put()` and add a frequency sketch.

1. Add a sketch field to `LruCache`: two rows of saturating 4-bit counters (store as `Vec<u8>`, one counter per byte is acceptable), each of length `next_power_of_two(capacity)`, plus a `sample_count: usize` and a `sample_limit: usize = 10 * capacity`.
2. Add `fn sketch_index<Q: Hash + ?Sized>(&self, key: &Q, row: u64) -> usize`. Compute the index with `std::collections::hash_map::DefaultHasher`, seeding it with `row` before hashing `key`, then masking to the row length.
3. Add `fn record(&mut self, key: &K)`. Increment one counter in each row (saturating at 15), then increment `sample_count`. When `sample_count >= sample_limit`, halve every counter and reset `sample_count` to 0, so old frequency ages out.
4. Add `fn estimate(&self, key: &K) -> u8`, returning the minimum of the two rows' counters for `key`.
5. In `get()`, call `record(key)` before the existing lookup. The `map` lookup and move-to-MRU stay as in baseline.
6. In `put()`, call `record(&key)` first. For an existing key, keep the baseline update-and-promote path. For a new key at capacity, let `victim = self.head` (the LRU). If `estimate(&key) < estimate(&self.nodes[victim].key)`, reject the insertion: return without changing `map`, `nodes`, or the list. Otherwise, use the baseline eviction path unchanged.
7. Keep `debug_assert!(self.map.len() <= self.capacity)`. A rejected insertion never grows the map.

Do not change `try_new`'s capacity check except to size the sketch. Do not edit `tests/`, `lru_cache_jni.rs`, or `Cargo.toml`. If a crate-local `#[cfg(test)]` test is added, keep it inside `src/lru_cache/mod.rs`.

## Rationale (optional)

Every cycle 0002 variant and the cycle 0001 variants stayed in the recency-or-referenced-bit family and moved hit-rate by under 0.06. None of them filtered admission. The LIRS workload-a trace has one-hit scans, which an admission filter targets directly. This hypothesis is the only one in the cohort that changes what enters the cache, not how it is ordered, so it tests a different lever. Expected cost is a hash on every `get` and `put`, so `get` p50 will likely regress. The claim targets hit-rate; per-op time is a tradeoff to report, not to optimise here.
