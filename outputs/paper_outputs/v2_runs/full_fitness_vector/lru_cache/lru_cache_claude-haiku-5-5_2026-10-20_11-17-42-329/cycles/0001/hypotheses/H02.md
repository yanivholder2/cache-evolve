# H02

Replacing move-to-MRU on every `get` with a per-node referenced bit (lazy promotion, CLOCK-style) will reduce get p50 latency below the baseline's 41 ns without lowering hit-rate.

## Parent

baseline

## Changes

In `src/lru_cache/lru_cache.rs`, change `get` so that a hit does not unlink and re-push the node. Instead set a `referenced: bool` field on the node (add it to `Node<K, V>`, default `false` in both construction sites) and return `&self.nodes[idx].value` directly after the map lookup.

Change the eviction path in `put` so that when the arena is full, it scans from `head` for a victim: while `nodes[head].referenced` is true, clear the bit, unlink the head, and push it to the tail (second chance); stop at the first unreferenced head. Evict that node as the baseline does (remove its key from `map`, reuse its slot, link the new key at the tail). The scan terminates because each pass clears one bit. Keep the existing overwrite path in `put` for existing keys, but set `referenced = true` there instead of unlinking/re-pushing, so the list order is only changed on eviction.

Keep `try_new`/`new`/`put`/`get` signatures and the `framework::Cache` impl unchanged. No `unsafe`, no external crates. Preserve the `debug_assert!` on map length. Add a unit test where a referenced head survives one eviction and the next unreferenced node is evicted instead.

Do not modify `lru_cache_jni.rs`, `Cargo.toml`, `src/lib.rs`, `tests/`, `src/test_utils/`, or `src/bin/`.

## Rationale (optional)

The baseline pays an unlink and re-link on every hit, which is the dominant cost of `get`. Deferring that work to eviction should cut the get path to a map lookup plus one store. The hit-rate risk is that CLOCK-style approximation differs from exact LRU ordering, so the hypothesis predicts a small or zero change in hit-rate on workload-a at size 2048.
