# H03

Storing the arena links as `u32` indices instead of `Option<usize>` will shrink `Node<u64,u64>` from 48 bytes to 32 bytes, reducing metadata-size without changing hit-rate or the eviction order.

## Parent

baseline

## Changes

In `src/lru_cache/lru_cache.rs`, change the `prev` and `next` fields of `Node<K, V>` from `Option<usize>` to `u32`, using `u32::MAX` as the "none" sentinel. Add two private helpers, `fn link(i: usize) -> u32` (asserting `i < u32::MAX as usize`, which holds for any capacity this cache can reasonably hold) and `fn idx(u: u32) -> Option<usize>`. Update `unlink`, `push_back`, `put`, and `get` to go through these helpers. The `head` and `tail` fields of `LruCache` may stay `Option<usize>`.

Keep the arena (`Vec<Node<K, V>>`), the `HashMap<K, usize>` map, the eviction policy (strict LRU, evict head, reuse slot in place), and all public signatures unchanged. Do not change `capacity`'s type. No `unsafe`, no external crates.

Verify with `std::mem::size_of::<Node<u64, u64>>()` in a unit test that the node is 32 bytes on this target (u64 key + u64 value + two u32 links). Keep the existing unit tests passing without modification.

Do not modify `lru_cache_jni.rs`, `Cargo.toml`, `src/lib.rs`, `tests/`, `src/test_utils/`, or `src/bin/`.

## Rationale (optional)

The baseline `Node<u64,u64>` is 48 bytes: 8 (key) + 8 (value) + 16 (`Option<usize>` prev) + 16 (`Option<usize>` next). Compacting the links to `u32` removes 16 bytes per node with no algorithmic change. Smaller nodes may also improve cache-line density on `get`, but the hypothesis's primary prediction is the metadata-size dimension.
