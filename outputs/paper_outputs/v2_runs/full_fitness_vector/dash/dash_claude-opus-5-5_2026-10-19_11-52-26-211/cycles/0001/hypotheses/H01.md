# H01

Insert items demoted from a normal bucket into the stash at its MRU end (Back) instead of its LRU end (Front), so items that already proved reuse outlive never-reused new arrivals, to raise hit rate.

## Parent

baseline

## Changes

All edits are in `src/dash/segments/dash_segment.rs`.

Today `promotion_get` passes a single `insert_pos = InsertPosition::Front` through `promote_to_target` / `promote_to_probing` into `demote_from_normal_bucket`. That one value is used for promotions *and* for both stash inserts in `demote_from_normal_bucket`. So an item pushed out of its target is placed at index 0 of its stash bucket. That is the ClassicLRU eviction candidate, so the very next stash overflow evicts it. Meanwhile new `put`s land at the stash's Back (`Segment::put` uses `InsertPosition::Back`). The net effect is that the stash favours never-reused new arrivals over items that were reused before. That is the opposite of SLRU, where items demoted from the protected segment go to the MRU end of the probationary segment.

Change:
- Keep promotion placement as it is. `put_at(Slot::Target, ..)` in `promote_to_target` and `put_at(Slot::Probing, ..)` in `promote_to_probing` still use the caller's `insert_pos` (Front).
- In `demote_from_normal_bucket`, change both `core.put_at(Slot::Stash, insert_pos, ..)` calls (the direct `true_target == source_idx` branch and the `cascade` branch) to `InsertPosition::Back`.
- Leave the one-more-chance retry `core.put_at(Slot::Target, insert_pos, item)` using `insert_pos` (Front).
- To keep the signature honest, either add a separate `demote_pos: InsertPosition` parameter that `promotion_get` threads through as `Back`, or hard-code `Back` for the stash inserts. Either works. Add a short doc comment explaining the SLRU rationale.

Invariants to keep: no item may be lost or duplicated. Every eviction still flows probing → target → stash → out. Slot legality stays unchanged, because only positions within buckets change, never which bucket an item goes to. The in-file unit tests `direct_to_stash_at_front_when_cold` and `cascade_to_stash_at_front_when_cold` encode the old behaviour. Update their expected index to match the new Back placement (the stash-resident `stash_pre` is at index 0, so the demoted item is expected at index 1 in both Front- and Back-caller cases).

## Rationale (optional)

The stash holds 24 of the 32 buckets (75% of capacity), so the order of evictions there drives most of the hit rate. The test is clean: if reuse is common in workload-a, hit rate should rise above 0.6634. If demoted items are mostly dead, it should stay flat or fall slightly.
