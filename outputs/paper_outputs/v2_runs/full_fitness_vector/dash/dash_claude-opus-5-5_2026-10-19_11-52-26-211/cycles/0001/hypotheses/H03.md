# H03

Reorder the lookup in `promotion_get` to scan the target and probing buckets before the stash bucket, cutting p50 get latency without changing which items are cached.

## Parent

baseline

## Changes

All edits are in `src/dash/segments/dash_segment.rs`, function `promotion_get`.

Today `promotion_get` always calls `core.stash_buckets[stash_idx].get_position(key)` first. That is a linear scan of up to 64 items, and every hit in a normal bucket and every miss pays for it before the target and probing buckets are checked. Under the uniqueness invariant (ADR 0004), a key lives in at most one slot, so the order of the checks does not change the result or the movement that follows.

Change:
- Restructure `promotion_get` so the lookups run in this order:
  1. target: `core.buckets[target_idx].get_position(key)`, keeping the existing hottest → `promote_to_probing` vs. intra-bucket `get_from_position` logic.
  2. probing: `core.buckets[probing_idx].get_position(key)`, touched in place as today.
  3. stash: `core.stash_buckets[stash_idx].get_position(key)`, with the existing `remove_at` + `promote_to_target` + re-lookup in target.
  4. miss: return `None`.
- Compute `stash_idx` lazily, only when step 3 is reached, to avoid an extra hash on hits in normal buckets.
- Do not change the semantics of any branch, the `InsertPosition` values, or the demotion cascade. This variant must produce exactly the same sequence of cache states as the baseline for any trace, so hit-rate must equal 0.6634.
- Watch out for borrows. Each branch returns a reference borrowed from `core`, so use the `if let Some(idx) = ... { ...; return ...; }` early-return form the current code already uses. Do not hold a borrow across branches.

Invariants to keep: identical hit/miss results and identical item placement compared with the baseline. All existing in-file unit tests must pass unchanged. Optionally add a test that runs the same random get/put sequence against a copy of the old function and the new one and compares the per-bucket key layouts.

## Rationale (optional)

This targets per-op-time only (get p50 = 183 ns, p99 = 376 ns) as a controlled experiment, with hit-rate and metadata-size held fixed. If most hits on workload-a land in normal buckets, skipping the 64-entry stash scan should cut get p50 noticeably. If most hits are stash hits, the gain will be small, and that also tells future cycles where hits are actually served.
