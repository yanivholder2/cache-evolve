# H03

Store `SegmentCore`'s normal and stash buckets as a contiguous `Vec` of a concrete, statically dispatched bucket type instead of `Vec<Box<dyn Bucket>>`, cutting cycle-7 v002's get p50 below 69 ns by removing a heap indirection and a vtable call from every bucket probe, with hit-rate unchanged at 0.7095.

## Parent

cycle/0007/v002

## Changes

Edits go in `src/dash/segments/mod.rs`, `src/dash/segments/dash_segment.rs`, and the bucket constructor module `src/dash/dash_bucket.rs` (where `new_bucket` lives). Do not touch the gate surface (`src/dash/jni.rs`, `src/factory.rs`, `src/lib.rs`, tests/, test_utils, bins). The public `Segment` trait signature must not change.

1. **Find the concrete type.** Read `new_bucket(bucket_size, policy)` in `src/dash/dash_bucket.rs` and identify the concrete struct it boxes, for example `DashBucket<K, V>`.
   - Change `SegmentCore::buckets` and `SegmentCore::stash_buckets` from `Vec<Box<dyn Bucket<K, V>>>` to `Vec<ThatConcreteType<K, V>>`.
   - Add a `new_bucket_concrete(...)` that returns the struct by value, and build the vectors with it in `try_new`.
   - Keep `new_bucket` returning `Box<dyn Bucket>` for any other caller.
   - If the eviction policy inside the bucket is itself a `Box<dyn EvictionPolicy>`, leave it boxed. Only the bucket layer becomes concrete. Method calls should then resolve statically through the `Bucket` trait impl on the concrete type, or through inherent methods.

2. **Inline the hot methods.** Mark `get_position`, `is_full`, `size`, `get_items`, `get_from_position`, `remove_at`, `put_at` and `promotion_candidate_index` `#[inline]` on the concrete impl. Where `get_position` is a plain key-equality scan over the items slice, make it an inherent `#[inline]` method so the 2-slot loop can unroll. Do not change any policy-touch side effects: `get_from_position` must still update recency exactly as before.

3. **Fix the call sites.** Code that relies on `Box<dyn Bucket>` must still compile: the `Debug` impl's `get_items()`, `force_push_normal_bucket`'s `get_items_mut()`, and the tests that index `core.buckets[i]` or `core.stash_buckets[j]` and call trait methods. Bring `Bucket` into scope where needed. If some test-visible API returns `&dyn Bucket`, return `&self.buckets[i] as &dyn Bucket<K, V>`. If the concrete type is private to `dash_bucket.rs`, make it `pub(crate)`.

4. **Fallback if the type is not uniform.** If `new_bucket` can return different concrete types depending on settings, introduce a small `enum DashBucketKind { … }` that holds each variant by value, and forward the hot methods with an `#[inline] match`. A branch the CPU predicts well is cheaper than a vtable call plus a pointer chase.

Invariants: no behaviour change at all, meaning the same items, positions, victims and recency updates, and `Item` stays 40 bytes. `Dash<u64,u64,DashSegment>` must stay 24 bytes; the change is behind the segment's `Vec`, so it should. All existing tests must pass unchanged in meaning, along with `check_foreign_counts` and `check_borrowed_counts` in the random-op tests.

## Rationale (optional)

Every `get` in v002 probes 1–4 buckets. Each probe today loads a `Box` pointer from the `Vec`, follows it to a separate heap allocation, then makes an indirect call through the vtable. The bucket body is only 2 slots, so the indirection and the call can cost as much as the scan. The lossless gates have already removed whole probes. This change makes every remaining probe cheaper without touching cache state, a latency lever the history marks as reliable and that no cycle has tried. It is independent of the hash count (H01) and of residency (H02), so the gains can stack later. **Confirmed** if hit-rate is exactly 0.7095 and get p50 drops clearly below 69 ns, with put p50 also no worse. **Refuted** if p50 doesn't move, meaning the compiler already devirtualised the calls or memory layout isn't on the critical path. Any change in hit-rate means behaviour was altered by mistake.
