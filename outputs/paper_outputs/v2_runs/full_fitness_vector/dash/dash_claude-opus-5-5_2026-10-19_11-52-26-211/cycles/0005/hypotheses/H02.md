# H02

Stack cycle-4 v003's normal-tier victim rescue on top of cycle-4 v002's two-choice stash, both ported onto cycle-4 v001, to raise hit-rate above v002's 0.7095.

## Parent

cycle/0004/v001

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Where needed, they also go in the `SegmentCore` helpers in `src/dash/segments/mod.rs`.

1. **Two-choice stash, ported as in cycle/0004/v002.** Add `SegmentCore::stash_indices(&key) -> (s0, s1 = (s0 + 1) % stash_size)` and a `stash_insert(core, pos, item) -> Option<Item>` helper that fills `s0`, else `s1`, else evicts from `s0`. Make every key-based stash membership helper (`contains_key`, remove/get-by-key, legality checks) accept either bucket. In `promotion_get`'s stash branch, check `s0` then `s1` (v002's `find_in_stash`), and keep the stash-first order. Keep v001's precomputed-index `promote_to_*` signatures and its `inserted_position` return path.

2. **Rescue on full two-choice overflow, as in cycle/0004/v003.** Wrap `stash_insert` in `stash_insert_with_rescue(core, pos, item)`. If `stash_insert` returns `Some(victim)`, which only happens when both `s0` and `s1` were full:
   - Let `t = get_index(&victim.key, segment_size)` and `p = (t + 1) % segment_size`.
   - If `!buckets[t].is_full()`, run `core.put_at(Slot::Target, InsertPosition::Front, victim)`. This cannot evict.
   - Else if `!buckets[p].is_full()`, run `core.put_at(Slot::Probing, InsertPosition::Front, victim)`. This cannot evict.
   - Else drop the victim.
   Route all three stash inserts through `stash_insert_with_rescue`: the fresh put (Front) and both demotion inserts in `demote_from_normal_bucket` (Back).

3. Add `const RESCUE_STASH_VICTIMS: bool = true;`. When it is false, behaviour must equal two-choice-only.

4. Do not change positions (`FRESH_PUT_STASH_POS = Front`, `DEMOTE_TO_STASH_POS = Back`), the `is_hottest` rule, or the cascade.

Tests: all v001 tests pass. Adjust setups where a victim would now be rescued: pre-fill the victim's target and probing buckets, or the neighbour stash bucket `s1`, so the old assertion still holds. Add a test: `s0` and `s1` both full, the victim's target has one free slot, a fresh put overflows, and the victim ends at target index 0 and `get` returns it. Add a test: `s0` full and `s1` free, so no rescue happens and the item lands in `s1`. Add a test: everything full, so the victim leaves the cache.

Invariants: no duplicate keys. Rescue never evicts, so there are no new cascades. No new fields. `Item` stays 40 bytes.

## Rationale (optional)

This answers cycle 4's open question of whether the two idle-capacity levers stack. They draw on different spare capacity: the neighbour stash bucket versus holes in normal buckets left by promotion `remove_at`. Rescue now fires only after both stash choices are full, so it triggers less often than in v003. Its put-path cost should therefore be lower than v003 alone, and whatever it retains is extra on top of v002. Confirmed if hit-rate rises clearly above 0.7095. Refuted if it stays at or below 0.7095, which would mean two-choice already absorbs the overflow that rescue recovered. Expect get/put p50 at or slightly above v002's 81/104 ns. Judge the gain against that cost.
