# H01

Add the two-choice stash to cycle-4 v001 but check the neighbour stash bucket `s1` last (s0 → target → probing → s1), to keep v002's 0.7095 hit-rate while bringing get p50 back below v002's 81 ns.

## Parent

cycle/0004/v001

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Where needed, they also go in the `SegmentCore` helpers in `src/dash/segments/mod.rs`, as cycle-4 v002 did.

1. **Port two-choice stash placement from cycle/0004/v002, unchanged in effect.** Add `SegmentCore::stash_indices(&key) -> (s0, s1)` with `s0 = get_index(key, stash_size)` and `s1 = (s0 + 1) % stash_size`. Add the `stash_insert(core, pos, item) -> Option<Item>` helper: fill `s0` if it is not full, else fill `s1` if `s1 != s0` and it is not full, else insert into `s0` and return its eviction. Route all three stash inserts through it: the fresh put in `DashSegment::put` (Front) and both stash inserts in `demote_from_normal_bucket` (Back). Make every key-based stash membership helper (`contains_key`, remove/get-by-key, `check_slot_legality` if it checks stash placement) accept a key in either `s0` or `s1`, exactly as v002 did. Keep v001's precomputed-index signatures for `promote_to_target(core, item, target_idx, pos)` and `promote_to_probing(core, item, probing_idx, pos)`, and keep its `inserted_position` + `debug_assert_eq!` return path in place of the post-promotion `get_position` re-scan.

2. **New lookup order in `promotion_get`.** Do not use v002's combined `find_in_stash` (s0 then s1) at the top. Use this order instead:
   a. `stash_buckets[s0].get_position(key)`: on a hit, run the existing stash-hit branch (`remove_at` on `s0`, `promote_to_target`, return at `inserted_position`).
   b. The target branch, unchanged (hottest → probing, else intra-bucket touch).
   c. The probing branch, unchanged.
   d. `stash_buckets[s1].get_position(key)`, only if `s1 != s0`: on a hit, run the same stash-hit branch as (a) but `remove_at` on `s1`.
   e. Miss.
   Factor the stash-hit branch into a small `#[inline]` helper that takes the stash bucket index, so (a) and (d) share it.
   Compute `s1` lazily, only when step (d) is reached.

3. Leave everything else exactly as in v001: `FRESH_PUT_STASH_POS = Front`, `DEMOTE_TO_STASH_POS = Back`, the `is_hottest` rule, and the cascade.

Since a key is resident in at most one slot, the lookup order cannot change which slot is found. So the mutation sequence, and with it hit-rate, must match v002 (0.7095) apart from measurement noise.

Tests: all existing v001 tests must pass. Port v002's two-choice tests: with `s0` full and `s1` free, a fresh put lands in `s1` and evicts nothing; with both full, `s0`'s LRU is evicted. Add a test: a key resident in `s1` whose target holds other keys is found by `get` and promoted to target index 0. Add a test: a key in target is returned without touching `s1`. For this one, assert on the result only, not on internals.

Invariants: no duplicate keys across target, probing, s0 and s1. No new per-item fields. `Item` stays 40 bytes.

## Rationale (optional)

v002 put the second 2-slot scan in front of every target hit, every probing hit and every miss. Most keys found in the stash are in `s0`, because `s1` is only used as overflow. So moving `s1` to the end means target and probing hits no longer pay for it. Misses still scan everything. This tests whether the get-p50 regression comes from hits or from misses. Confirmed if hit-rate is about 0.7095 and get p50 is clearly below 81 ns in the same run. Refuted if p50 stays at about 81, which would mean misses dominate the median, so only an `s1` filter could help. A hit-rate change would mean a bug.
