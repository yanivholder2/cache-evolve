# H03

Place a fresh `put` straight into a free slot of its target bucket (at the LRU/Front end) before falling back to the stash, so idle normal-tier capacity is used at insert time, which raises hit-rate and lets a key's first reuse skip the stash→target promotion cascade, which lowers get p50.

## Parent

cycle/0004/v001

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Do not add two-choice stash or rescue. This tests a separate, single lever.

1. **`DashSegment::put`.** Keep the `debug_assert!(!core.contains_key(..))`. Then compute `t = get_index(&item.key, core.segment_size)`.
   - If `!core.buckets[t].is_full()`, run `core.put_at(Slot::Target, InsertPosition::Front, item)` and return. The bucket has room, so this cannot evict and starts no cascade.
   - Otherwise fall through to the existing `core.put_at(Slot::Stash, FRESH_PUT_STASH_POS, item)` (Front). Any eviction there leaves the cache, as today.
   Do not try the probing bucket. Probing stays reserved for items that earned promotion.

2. Add `const FRESH_PUT_FILLS_TARGET_HOLE: bool = true;` with a doc comment. When it is false, `put` must behave exactly like v001.

3. **No change to `promotion_get`.** A fresh item placed at target Front is found by the existing target branch:
   - If it is the only item in the bucket, it is the promotion candidate, so its first reuse promotes it to probing. This matches what a stash hit followed by a target hit would earn, but with one move fewer.
   - Otherwise its first reuse is an in-bucket touch (ClassicLRU bump) with no `remove_at` or cascade.
   If it is never reused, it is the bucket's LRU victim. A later stash→target promotion evicts it through `demote_from_normal_bucket`. A native victim goes to stash Back, so it gets one more probationary life there. Keep that behaviour unchanged.

4. Keep `FRESH_PUT_STASH_POS = Front`, `DEMOTE_TO_STASH_POS = Back`, the lookup order (stash → target → probing), v001's precomputed-index promotion signatures, and its `inserted_position` return path.

Tests: update `put_goes_to_stash` and `fresh_put_evicted_before_demoted_item` so their keys' target buckets are pre-filled to full first. That keeps the stash path under test. Add a test: with the target bucket empty, `put(k)` lands at target index 0, the stash is untouched, and `get(k)` returns it. Add a test: with the target full, `put(k)` lands at stash index 0 as in v001. Run `check_slot_legality()` after each test.

Invariants: no duplicate keys. A fresh put never evicts a normal-bucket resident. No new fields. `Item` stays 40 bytes.

## Rationale (optional)

Cycle 4 showed that normal buckets have idle holes and that filling them helps hit-rate (v003 rescue: 0.7074). But rescue fills them late and at a cost: only on stash overflow, with an extra hash, two `is_full` checks and a second insert on the put path. This fills the same holes early, with one `is_full` check. It also takes pressure off the 2-slot stash buckets, so their reuse-proven demotees are evicted less often. On the get side, keys whose first reuse would have been a stash hit (remove → promote → possible demote → stash insert) now get a cheap target touch. That targets the slowest common hit path that cycles 2–4 identified. Risk: cold one-hit items now sit in target and later re-enter the stash at Back as false "demotees". Cycle-4 v003 showed this risk did not outweigh the extra residency. Confirmed if hit-rate rises above 0.702 and get p50 is at or below v001's 72 ns in the same run. Refuted if hit-rate is at or below 0.702.
