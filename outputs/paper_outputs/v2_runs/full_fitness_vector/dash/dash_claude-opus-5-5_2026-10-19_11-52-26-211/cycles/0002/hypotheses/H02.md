# H02

Place stash-hit promotions at the MRU end (Back) of the target bucket instead of its LRU end (Front), so an item that just proved reuse is not the next target victim, raising hit rate.

## Parent

cycle/0001/v001

## Changes

All edits are in `src/dash/segments/dash_segment.rs`.

In v001, `DashSegment::get` calls `promotion_get(core, key, InsertPosition::Front)`. In the stash-hit branch, `promote_to_target(core, data, insert_pos)` therefore places the re-read item at index 0 of its target bucket. That is the ClassicLRU eviction candidate. The next insert into that full target (another stash hit, or a cascade) pushes it straight back to the stash. Normal buckets are tiny (a 2-slot target in the small settings), so a promoted item rarely survives long enough to be hit in the target.

Change only the stash → target promotion position:
- Add `const STASH_PROMOTE_POS: InsertPosition = InsertPosition::Back;` with a doc comment explaining the rationale.
- In `promotion_get`, stash-hit branch: call `promote_to_target(core, data, STASH_PROMOTE_POS)`. `promote_to_target` passes its argument into `demote_from_normal_bucket`, which uses it only for the one-more-chance retry. Thread the original `insert_pos` (Front) through separately, so the retry position does not change. Either add a second parameter `retry_pos` to `promote_to_target`, or inline the `put_at(Slot::Target, STASH_PROMOTE_POS, ..)` + `demote_from_normal_bucket(core, evicted, target_idx, insert_pos)` in that branch.
- Leave the target-hit-hottest → `promote_to_probing(.., insert_pos)` path, the probing-hit touch, and `DEMOTE_TO_STASH_POS = Back` unchanged.
- Note the side effect: an item placed at Back is already the hottest. So one more target hit promotes it to probing, instead of first climbing within the bucket. This is expected, and it is part of what the experiment tests.
- Update the `stash_hit_inserts_at_front_of_target` test, renaming it to `stash_hit_inserts_at_back_of_target`. After the two put/get pairs, the expected order is `items[0] == keys[0]`, `items[1] == keys[1]`. Check that `target_hit_not_hottest_promotes_within_bucket` and `target_hit_hottest_promotes_to_probing` still hold, or adjust their setup and expected counts to match the new placement. Do not weaken them to permissive assertions.

Invariants: every item stays in exactly one legal slot. Every eviction still flows probing → target → stash → out. Metadata-size stays unchanged at 40.

## Rationale (optional)

Both cycle 0001 insights list promotion placement as an untested lever. v001 showed that keeping proven-reuse items away from LRU ends raises hit rate. This applies the same idea one tier up. If target residents hit on re-read, hit-rate should rise above 0.684. If the faster path into probing churns probing, hit-rate stays flat or falls, which is also informative.
