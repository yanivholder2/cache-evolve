# H01

Port cycle-5 v002's normal-tier victim rescue onto cycle-5 v001 (two-choice stash, `s1` probed last) to reach v002's 0.7118 hit-rate while keeping get p50 near v001's 77 ns rather than v002's 92 ns.

## Parent

cycle/0005/v001

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. Do not change `SegmentCore` in `src/dash/segments/mod.rs` unless a small helper is needed.

1. **Add rescue as a wrapper around the existing `stash_insert`.** Add `fn stash_insert_with_rescue(core, pos, item)`. It calls `stash_insert(core, pos, item)`. If that returns `Some(victim)`, which only happens when `s0` and `s1` were both full and `s0`'s LRU was evicted:
   - Let `t = get_index(&victim.key, core.segment_size)` and `p = (t + 1) % core.segment_size`.
   - If `!core.buckets[t].is_full()`, call `core.put_at(Slot::Target, InsertPosition::Front, victim)`. This cannot evict. Add a `debug_assert!` that it returned `None`.
   - Else if `!core.buckets[p].is_full()`, call `core.put_at(Slot::Probing, InsertPosition::Front, victim)`. This cannot evict either.
   - Else drop the victim, as v001 does today.
   Add `const RESCUE_STASH_VICTIMS: bool = true;`. When it is false, the wrapper must behave exactly like plain `stash_insert`.

2. **Send all three stash inserts through the wrapper:** the fresh put in `DashSegment::put` (`FRESH_PUT_STASH_POS`), and both `stash_insert(core, DEMOTE_TO_STASH_POS, …)` calls in `demote_from_normal_bucket`.

3. **Keep `promotion_get` exactly as it is in v001:** `s0` → target → probing → lazily computed `s1`, with the shared `stash_hit` helper. Rescue never creates a second copy of a key and never adds a lookup step. So this order stays correct, and lookups touch the same buckets as before.

4. Leave everything else unchanged: positions, the `is_hottest` rule, the one-more-chance cascade, and the `inserted_position` debug assertions. Rescue can write into `t` or `p` during a cascade started by `stash_hit` or the hottest→probing branch. Check that the "cascade never writes back into target_idx / probing_idx" assertions still hold. Rescue only fills a bucket that is not full, and the bucket that just took the promoted item is full or was the source of the cascade. If a case breaks the assertion, find the returned item with `get_position(key)` in that branch instead of asserting.

Tests: all v001 tests pass. Where a test expects a stash victim to leave the cache, also fill the victim's target and probing buckets. Add a test where `s0` and `s1` are full, the victim's target has a free slot, and a fresh put overflows: the victim ends at target index 0 and `get` returns it. Add a test where everything is full: the victim is gone and `check_slot_legality()` holds.

Invariants: no duplicate keys, no new fields, and `Item` stays 40 bytes.

## Rationale (optional)

This is the continuation cycle 5 asked for. v002 = v001 placement + rescue, but with stash-first lookup. A key lives in only one slot, so lookup order is state-neutral. The mutation sequence should therefore match v002, which means a hit-rate of about 0.7118. Rescue adds nothing to the lookup path. **Confirmed** if hit-rate is about 0.7118 and get p50 is clearly below 92 ns, within a few ns of v001. **Refuted** if get p50 stays near v002's level, which would mean fuller normal buckets (not stash-first order) cause v002's latency. A hit-rate that differs from 0.7118 points to a porting bug.
