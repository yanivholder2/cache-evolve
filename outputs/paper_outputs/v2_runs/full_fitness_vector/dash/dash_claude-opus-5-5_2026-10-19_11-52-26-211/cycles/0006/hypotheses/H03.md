# H03

When an item is pushed out of its own target bucket, place it in a free slot of its probing bucket before falling back to the stash, to raise cycle-5 v001's hit-rate by keeping reuse-proven items in the normal tier.

## Parent

cycle/0005/v001

## Changes

All edits go in `demote_from_normal_bucket` in `src/dash/segments/dash_segment.rs`.

1. **Native branch (`true_target == source_idx`).** Today the item goes straight to `stash_insert(core, DEMOTE_TO_STASH_POS, item)`. Instead:
   - Let `p = (source_idx + 1) % core.segment_size`. This is the item's own probing bucket, so placing it there is legal.
   - If `!core.buckets[p].is_full()`, call `core.put_at(Slot::Probing, InsertPosition::Front, item)`. It cannot evict; add a `debug_assert!` that it returned `None`. Then return.
   - Otherwise, fall back to the existing stash insert, unchanged.
   Use `Front`, the LRU end, so the item does not outrank probing residents that have proven themselves. It must still earn its place by being touched.

2. **Foreign branch.** The retry into the true target is unchanged. The `cascade` item it evicts is native to `true_target`, and its probing bucket is `true_target + 1 == source_idx`. That bucket has just received the promoted item and is full, so do **not** try a probing hole for it. Keep it going straight to the stash.

3. **Write-back safety.** The callers' `inserted_position` assertions assume the cascade never writes into the bucket that has just received the promoted item:
   - From `stash_hit` (`promote_to_target` at `target_idx`), the native victim's `p` is `target_idx + 1`, not `target_idx`. Safe.
   - From the hottest→probing branch (`promote_to_probing` at `probing_idx`), a native victim of `probing_idx` would go to `probing_idx + 1`. That bucket differs from `probing_idx` when `segment_size >= 2`. Safe.
   Keep both `debug_assert_eq!` checks. Also add a short doc comment on `demote_from_normal_bucket` explaining why the new write target can never be `source_idx`.

4. Add `const NATIVE_DEMOTE_TO_PROBING_HOLE: bool = true;`. When it is false, behaviour must be exactly v001's. Do not change `promotion_get`, the stash positions, two-choice placement or the `is_hottest` rule.

Tests: all v001 tests pass. Tests that expect a native target victim to land in the stash (`direct_to_stash_position`, `fresh_put_evicted_before_demoted_item`) must pre-fill the victim's probing bucket `target_idx + 1` so the old path still runs. New tests:
- (a) Target full, probing bucket empty, `promote_to_target` of a third key: the victim ends at probing index 0, not in the stash, `get` returns it, and `check_slot_legality()` holds.
- (b) Target full, probing full: the victim goes to the stash at Back, as before.

Invariants: no duplicate keys, no new evictions (only free slots are filled), no new fields, and `Item` stays 40 bytes.

## Rationale (optional)

Cycles 4 and 5 showed that idle capacity is the only hit-rate lever, and that the timing of a fill matters. Eager fresh fills (c5 v003) clog target slots. Rescue of stash victims helps, but only after a stash victim has already been chosen. This lever fills probing holes with items that have *already proven reuse* (they were in target) at the moment they would otherwise join the crowded 2-slot stash. That also eases pressure on the stash. Probing holes left by promotions' `remove_at` currently go unused until a hottest item climbs into them. Lookups already scan probing before `s1`, so a later hit on a rescued item costs a cheap in-place touch instead of a stash→target promotion cascade. That could also help get p50. It is a different hole source and timing from H01's rescue, so a later cycle can stack the two. **Confirmed** if hit-rate rises clearly above 0.7095 and get p50 does not exceed v001's 77 ns by more than noise. **Refuted** if hit-rate is at or below 0.7095. That would mean probing holes are rare in steady state, or that occupying them blocks later hottest→probing promotions, which would then evict instead of filling a free slot.
