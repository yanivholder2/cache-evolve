# H03

Rescue each stash-eviction victim into a free slot in its own target or probing bucket, when one exists, instead of dropping it from the cache, to use normal-bucket holes and raise hit rate.

## Parent

cycle/0002/v003

## Changes

All edits go in `src/dash/segments/dash_segment.rs`.

Background: in the parent, a hottest-target hit runs `remove_at` on the target bucket and moves the item to probing. That leaves a free slot in the target, which stays empty until a later stash→target promotion or one-more-chance retry lands there. Meanwhile, every stash overflow (fresh `put` at Front, or demotion at Back) throws its LRU victim out of the cache even when its own normal buckets have spare room.

1. Add a helper `fn stash_insert_with_rescue(core, pos: InsertPosition, item)`. It calls `core.put_at(Slot::Stash, pos, item)`. If that returns `Some(victim)`:
   - Let `t = get_index(&victim.key, core.segment_size)` and `p = (t + 1) % core.segment_size`.
   - If `!core.buckets[t].is_full()`, run `core.put_at(Slot::Target, InsertPosition::Front, victim)`. This cannot evict, because the bucket has room.
   - Else if `!core.buckets[p].is_full()`, insert the victim into the probing slot at `InsertPosition::Front` (`Slot::Probing`). This cannot evict either.
   - Otherwise drop the victim, as today.
   Inserting at Front (LRU end) keeps the rescued item at the bottom of the normal bucket. It is the first to leave if real promotions need the slot, and it must climb before it can promote to probing, so the existing admission rules still apply.

2. Route all three stash inserts through this helper: the fresh insert in `DashSegment::put` and both stash inserts in `demote_from_normal_bucket`. Keep their positions (`FRESH_PUT_STASH_POS = Front`, `DEMOTE_TO_STASH_POS = Back`).

3. Add a module-level `const RESCUE_STASH_VICTIMS: bool = true;` with a doc comment. When it is false, the helper behaves exactly like the parent.

4. Do not change `promotion_get` lookup order, `is_hottest` logic, or promotion positions. A rescued item later evicted from its target goes through `demote_from_normal_bucket` like any resident.

Tests: all existing tests must pass (check that `fresh_put_evicted_before_demoted_item` still finds the expected key gone; if the fresh victim is now rescued into an empty target bucket, pre-fill that target bucket in the test setup, or assert the victim is in the target instead of the stash). Add a test: fill a stash bucket, leave the victim's target bucket with one free slot, overflow the stash, and assert the victim sits at index 0 of its target and `get` returns it. Add a test: with target and probing both full, the victim leaves the cache as before.

Invariants: no duplicate keys (the victim was only in the stash). A rescue never evicts anything, so there are no new cascades. No new fields. `Item` stays 40 bytes.

## Rationale (optional)

This is distinct from H02. H02 widens the stash with a second stash bucket. This one fills capacity left idle in the *normal* tier, which is the open "spare-neighbour placement" question applied to the path that triggers most often (every stash overflow), not to rare corner cases like cycle-1 v002. Holes reliably appear after each target→probing promotion. Risk: rescued items are mostly never-reused fresh arrivals. If a later promotion pushes one out of its target, it re-enters the stash at Back (MRU) as a "demotee" and could outrank genuinely reused items. Confirmed if hit-rate rises above 0.702. Refuted if it stays at or below 0.702, which would show that the stash-Back re-entry of rescued cold items costs more than the extra residency gains.
