# H01

Cut the redundant re-hashing and post-promotion bucket re-scans from `promotion_get`'s promotion paths to lower get per-op-time while leaving cache state, and so hit-rate, exactly unchanged.

## Parent

cycle/0002/v003

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. This is a pure refactor for speed: the sequence of cache mutations must stay byte-for-byte identical to the parent's.

1. **Pass the precomputed indices down.** `promotion_get` already computes `target_idx` and `probing_idx`. Today `promote_to_target` and `promote_to_probing` each call `get_index(&item.key, core.segment_size)` again, which hashes the key a second time on every promotion. Change their signatures to take the index from the caller: `promote_to_target(core, item, target_idx, insert_pos)` and `promote_to_probing(core, item, probing_idx, insert_pos)`. Update every caller, including the tests that call them directly (`fresh_put_evicted_before_demoted_item`, `evicted_from_probing_cascades_to_target`, `target_retry_position`, `direct_to_stash_position`, `cascade_to_stash_position`), by computing the index in the test with `get_index` (plus `+1 % seg_size` for probing). In `demote_from_normal_bucket`, keep the single `get_index` call on the evicted item's key. It is a different key, so it is needed.

2. **Drop the post-promotion `get_position` re-scan.** After `promote_to_target(...)` in the stash-hit branch, and after `promote_to_probing(...)` in the hottest-target branch, the parent scans the destination bucket again with `get_position(key)` just to find the item it inserted. Its position follows from the insert: the cascade from `demote_from_normal_bucket` never writes back into the destination bucket. A native victim goes to the stash. A foreign victim from target `t` retries in `t-1`, and a foreign victim from probing `t+1` retries in `t`, never in `t+1`. So the new item sits at index `0` when `insert_pos == Front`, or at `len()-1` when `insert_pos == Back`. Return `&core.buckets[idx].get_items()[pos]` with that computed `pos`. First check `Bucket::put_at` in `src/shared/traits/bucket.rs` (and the ClassicLRU bucket implementation) to confirm that on a full bucket the LRU victim is removed *before* the Front insert, so the new item ends at index 0. Keep a `debug_assert_eq!(core.buckets[idx].get_position(key), Some(pos))` in place of the `unreachable!` so tests still catch any violation. Release builds skip the scan.

3. Leave everything else alone: lookup order (stash → target → probing), `FRESH_PUT_STASH_POS = Front`, `DEMOTE_TO_STASH_POS = Back`, the `is_hottest` rules, and `DashSegment::put`.

Tests: all existing tests must pass unchanged in what they assert (only call signatures change). Add one test: after a stash hit on a key whose target bucket is full, the returned reference's key equals the requested key, and it sits at index 0 of the target bucket.

Invariants: identical mutation sequence, no new fields, `Item` stays 40 bytes.

## Rationale (optional)

Cycles 1–3 found that the only trustworthy latency gains come from skipping work. The two cycle-3 latency wins both skipped the cascade by promoting less, and that cost hit-rate. This instead removes work that has no effect on cache state: one extra key hash plus one extra bucket scan on each stash-hit and hottest-target promotion. Stash hits are common on this lineage (cycle-3 v001), so the saving lands on a hot path. Confirmed if hit-rate stays exactly 0.702 and get p50 drops below 71 ns. Refuted if p50 stays the same. A hit-rate change of any size would mean an implementation bug, not a refutation.
