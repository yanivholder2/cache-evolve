# H02

Give each key two candidate stash buckets (its home stash bucket and the next one), filling a free slot in either before evicting, to raise the stash's effective associativity and so raise hit rate.

## Parent

cycle/0002/v003

## Changes

This is a structural change to stash associativity. The configured bucket sizes and counts stay the same (`DashSettings` and `src/factory.rs` are not touched). Edits go in `src/dash/segments/dash_segment.rs`. Where needed, they also go in `SegmentCore` (`src/dash/segments/mod.rs`), but only in the helpers DashSegment relies on.

Definitions: `s0 = get_index(key, core.stash_size)`, `s1 = (s0 + 1) % core.stash_size`.

1. **Stash insert helper.** Add `fn stash_insert(core, pos: InsertPosition, item) -> Option<Item>`. If `stash_buckets[s0]` is not full, insert there at `pos`. Otherwise, if `stash_buckets[s1]` is not full, insert there at `pos`. Otherwise insert into `s0` at `pos` and return its eviction, which leaves the cache as today. Use the bucket-level insert that `SegmentCore::put_at(Slot::Stash, ..)` delegates to, so the bucket can be chosen explicitly. Route all three stash inserts through this helper: the fresh insert in `DashSegment::put` (`FRESH_PUT_STASH_POS = Front`) and both `core.put_at(Slot::Stash, DEMOTE_TO_STASH_POS, ..)` calls in `demote_from_normal_bucket` (`Back`). Positions stay exactly as in the parent.

2. **Lookup.** In the stash branch of `promotion_get`, check `s0` first and then `s1`. Whichever bucket holds the key is the one passed to `remove_at` before `promote_to_target`. Everything after that is unchanged.

3. **Membership helpers.** Every `SegmentCore` path that finds a stash item by key, including `contains_key` (used by the `put` debug_assert) and any remove/get-by-key helper the `Segment` trait uses, must also check `s1`. Otherwise the no-duplicates invariant and the gate tests break. If those helpers are shared with other segment types, add a DashSegment-only override or a `two_choice: bool` parameter so other segments behave exactly as before.

4. Do not change the lookup order (stash first), promotion positions, `is_hottest` rules, or the cascade.

Tests: keep all existing tests (`fresh_put_evicted_before_demoted_item` still holds, because `s1` there should be checked as full or empty; adjust the setup so `s1` is pre-filled if needed). Add a test: with `s0` full and `s1` holding one free slot, a fresh put lands in `s1`, evicts nothing, and is found by `get`. Add a test: with both full, a fresh put evicts `s0`'s LRU as in the parent.

Invariants: a key lives in at most one slot across target, probing, `s0` and `s1`. No new per-item fields. `Item` stays 40 bytes.

## Rationale (optional)

The stash holds most of the capacity and is the only hit-rate lever that has paid off. Its 2-slot buckets are so small that cycle 3 concluded "no filter can beat plain recency". Every stash hit runs `remove_at` and leaves a hole, while the neighbouring stash bucket may at the same moment be evicting a reuse-proven demotee. Two-choice placement turns that wasted capacity into retained items, much like cuckoo or d-left hashing, without new metadata. This tests the open "stash associativity" question. Expected cost: misses and stash hits found in `s1` pay one extra 2-slot scan, so get p50 may rise slightly. Confirmed if hit-rate rises above 0.702. Refuted if it stays at or below 0.702, which would mean stash holes are refilled too quickly to matter.
