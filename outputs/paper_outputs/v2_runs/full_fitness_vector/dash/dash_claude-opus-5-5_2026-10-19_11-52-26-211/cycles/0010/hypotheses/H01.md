# H01

Shrinking the `DashBucket` header back to one cache line, using a capacity-sized tag array and a `u8` `max_size`, will lower get p50 below 67 ns while hit-rate stays exactly at 0.7095.

## Parent

cycle/0009/v002

## Changes

Only `src/dash/dash_bucket.rs` changes, plus any in-file tests that use `MAX_SLOTS`. This is a pure layout change and must not change behaviour.

- Replace `pub const MAX_SLOTS: usize = 64` with a small constant that covers the parent's real bucket capacity. Normal and stash buckets share `settings.bucket_size`. Use the default `bucket_size` from `DashSettings` rounded up to the next multiple of 8, for example `MAX_SLOTS = 8` if `bucket_size <= 8`. Keep the existing fallback: when `max_size > MAX_SLOTS`, `tag_ok` starts false and the bucket uses the plain key scan. This keeps small-settings test fixtures and odd configurations correct.
- Change `max_size: u32` to `max_size: u8`. In `DashBucket::new`, use `u8::try_from(max_size).expect(...)`. `SegmentCore::try_new` already asserts `bucket_size < u8::MAX`, so the conversion cannot fail for real configurations, and capacity is never silently truncated.
- Reorder the fields so the hot ones come first and padding is minimal. Drop `#[repr(C)]`, or keep it with this exact order: `items: Vec<Item<K,V>>` (24 B), `eviction_policy: Box<dyn EvictionPolicy>` (16 B), `max_size: u8`, `tag_ok: bool`, `tags: [u8; MAX_SLOTS]`. With `MAX_SLOTS = 8` the struct is 24 + 16 + 1 + 1 + 8 = 50 B, padded to 56. That is ≤ 64 B, so one header fits in one cache line, down from about 112 B today. Add a `const _: () = assert!(std::mem::size_of::<DashBucket<u64,u64>>() <= 64);` compile-time check (inside the module, not in `tests/`).
- Make sure nothing indexes `tags` beyond `len`. Check `put_at_tagged`'s Front-insert shift (`copy_within`) and the `rebuild_tags` and `tags_consistent` bounds checks against the new `MAX_SLOTS`.
- Do not touch `Item`, `Dash`, `SegmentCore`, the lookup order, or any counter. Metadata-size stays 40/24.

## Rationale (optional)

The cycle-9 v002 insight states that its gain is a lower bound. The tag array is sized for 64 slots, so the header is about 112 B and covers two cache lines, while a probe only reads the first few tag bytes. With a 64 B-or-smaller stride, more of the hot headers stay in L1 or L2 across the segment's bucket array. Each probe also reads `len`, `tags` and the tag compare from one line. Pass: hit-rate exactly 0.7095, and get p50 < 67 ns (or get p99 < 123 ns with p50 flat). Refuted if all get metrics are flat. That would mean the extra header line was never on the critical path.
