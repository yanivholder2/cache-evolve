# H03

Making each stash bucket twice as wide and halving the stash bucket count, with total capacity unchanged, will raise hit-rate above 0.7095 by pooling stash overflow, with no rescue cascades into target buckets.

## Parent

cycle/0009/v002

## Changes

Change the stash geometry inside `SegmentCore`, in `src/dash/segments/mod.rs`, without changing `DashSettings` or anything in the gate-integrity surface.

- In `SegmentCore::try_new`, derive the stash geometry from the settings. If `settings.num_of_stash_buckets` is even and ≥ 2, set `stash_size = num_of_stash_buckets / 2` and build each stash bucket with `new_bucket_concrete(2 * settings.bucket_size, ...)`. Otherwise keep the current geometry unchanged, so tiny test fixtures still work. Total stash slots, and therefore `max_capacity()`, stay exactly the same. Size `borrowed` as `vec![0u8; stash_size]`, and extend the existing `debug_assert` so that `2 * bucket_size < u8::MAX`.
- Every stash index computation already uses `self.stash_size` (`stash_indices`, `stash_neighbor`, `put_stash_at_index_h`'s `h % self.stash_size`, `put_at_h`'s `Slot::Stash` arm, `check_borrowed_counts`, `check_slot_legality`). Audit `dash_segment.rs` for any use of `settings.num_of_stash_buckets` or a hard-coded stash count, and switch it to `core.stash_size`. Keep two-choice placement (`s0`, then `s1 = (s0+1) % stash_size`), the `borrowed` gate on `s1`, and the lookup order.
- Make sure the tag array covers the wider stash buckets. The parent's `MAX_SLOTS = 64` already does. If the parent's tags are disabled for `max_size > MAX_SLOTS`, the plain scan still keeps behaviour correct.
- Keep stash ordering semantics inside the wider buckets: fresh puts at Front (the LRU end), demotees at Back (the MRU end), a stash hit promotes to target at Front, and the victim is the policy's eviction candidate.
- Update the in-file tests in `segments/mod.rs` that assume `stash_buckets.len() == num_of_stash_buckets` or `num_of_stash_buckets * bucket_size` stash capacity per bucket (e.g. `borrowed_starts_zero`, `max_capacity_matches_settings`, the 4-stash-bucket fixtures). `max_capacity` must still equal `(normal + stash) * bucket_size`. Leave `tests/` untouched. If an integration test there relies on the stash bucket count, keep the original geometry for that configuration.
- `Item` and `Dash` are unchanged, so metadata-size stays 40/24.

## Rationale (optional)

Stash geometry has been open since cycle 3, and cycle 9's attempt produced no result, so this is a careful retry. Every hit-rate gain so far has come from giving overflowing keys more places to land. A 2×-wide stash bucket pools four slots across two keys' worth of hash space, plus its neighbour. Unlike rescue, this does not fill target buckets, so the target-scan and cascade cost that hurt cycle 8 does not apply. The parent's tags also make the longer stash scans mostly free on misses. Confirmed if hit-rate is > 0.7095 and get p50 is ≤ 70 ns. Refuted if hit-rate is flat, which would mean overflow is not clustered enough for pooling to matter, matching cycle 7's independent-hash result.
