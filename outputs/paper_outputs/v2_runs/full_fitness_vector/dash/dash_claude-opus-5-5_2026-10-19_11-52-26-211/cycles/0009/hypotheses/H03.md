# H03

Doubling the slots per stash bucket and halving the number of stash buckets, at the same total segment capacity, will raise hit-rate above 0.7095 by letting the probationary queue hold reuse candidates longer.

## Parent

cycle/0006/v002

## Changes

Change only the stash geometry in the segment constructor of the parent, plus the index math that depends on it.

- Find the constants or constructor arguments in `SegmentCore` / `DashSegment` that set the number of stash buckets and the slots per stash bucket (currently 2-slot stash buckets). Set the slots per stash bucket to twice the current value and the number of stash buckets to half the current value, so that total stash slots, and therefore total cache capacity at size 2048, stay exactly the same. Do not change normal (target/probing) buckets.
- Update every function that maps a key to a stash bucket index (the `s0` computation and the `s1 = (s0 + 1) % num_stash_buckets` neighbour) so it uses the new stash bucket count. Keep two-choice placement: fill a free slot in `s0`, then `s1`, before evicting. Keep the `s1`-probed-last lookup order and the `borrowed` counter gate. Size the `borrowed` counter type so it can count up to the new slots per bucket.
- Keep the stash ordering semantics unchanged within the larger buckets: fresh puts go in at the LRU end (Front), demotees go in at the MRU end (Back), a stash hit promotes to the target at Front, and the victim is the LRU-end item.
- Do not change `Item` or the `Dash` struct; metadata-size stays 40/24.

## Rationale (optional)

Every hit-rate gain so far has come from giving the stash more effective capacity per key (two-choice, rescue), and cycle 3 attributed the failure of reuse-based filtering to tiny 2-slot buckets that evict before a second touch can arrive. Stash size and associativity are the main structural lever never tested (an open question since cycle 3). Wider buckets pool overflow across more keys, the same pooling effect two-choice gave, without any new hashing or rescue cascades into target buckets. That makes this the rescue-free alternative for hit-rate. Pass/fail criteria: the hypothesis is confirmed if hit-rate rises above 0.7095 (towards the 0.711–0.713 range of rescue variants) while get p50 stays within about 5 ns of the parent's 72 ns. It is refuted if hit-rate is flat or lower, or if longer stash scans add more than the hit-rate is worth.
