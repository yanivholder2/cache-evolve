# H01

Port the target→probing→stash lookup order with a lazy `stash_idx` onto cycle/0002/v003, so it keeps v003's 0.702 hit rate and lowers get p50 (per-op-time) below v003's 71 ns.

## Parent

cycle/0002/v003

## Changes

All edits go in `src/dash/segments/dash_segment.rs`. v003's `promotion_get` still uses the old stash-first order. It computes `stash_idx = get_index(key, core.stash_size)` eagerly at the top, checks the stash, then the target, then probing. Rewrite only `promotion_get` so it matches cycle/0002/v001's version exactly:

1. Compute `target_idx` and `probing_idx` only. Do not hash for the stash yet.
2. **Target** check, unchanged logic. If the item is the hottest (`promotion_candidate_index`), `remove_at`, then `promote_to_probing(core, data, insert_pos)`, then return the item from probing. Otherwise return `get_from_position(item_idx)` (intra-bucket climb).
3. **Probing** check: `get_from_position` in place.
4. **Stash** check: compute `stash_idx` here, lazily. If the key is found, `remove_at`, then `promote_to_target(core, data, insert_pos)`, then return it from the target with the same `unreachable!` guard as before.
5. Miss: return `None`.

Use the early-return `if let Some(idx) = ... { ...; return ...; }` form so no borrow is held across branches. Update the doc comment on `promotion_get` to describe the lookup order and note that it can't change cache state because of the uniqueness invariant.

Do not touch anything else: `DashSegment::put` with `FRESH_PUT_STASH_POS = Front`, `DEMOTE_TO_STASH_POS = Back`, `promote_to_target`, `promote_to_probing`, `demote_from_normal_bucket`, and `get` passing `InsertPosition::Front`. All existing tests should pass unchanged.

Invariants: a key lives in at most one slot, so the cache-state sequence for any trace must match v003's exactly. Hit-rate must therefore equal 0.702, and metadata-size stays 40.

## Rationale (optional)

This is the open question carried over from cycles 1 and 2. v003 holds the best hit rate but was built on cycle/0001/v001, so it never got the lookup-order gain that cycle 1's v003 measured. Most hits come from normal buckets, so skipping the stash hash and scan for them is a free get-path win with a clear code-level cause. Falsification: a hit-rate other than 0.702 means a bug. A get p50 at or above v003's, measured in the same run, means the lookup-order gain doesn't survive the bigger share of stash hits in this cache state.
