# H02

Require a second hit at the stash bucket's MRU end before a stash item is promoted to its target, so one-off stash re-reads stop evicting proven target residents, raising hit rate.

## Parent

cycle/0002/v003

## Changes

All edits go in `src/dash/segments/dash_segment.rs`, in the stash-hit branch of `promotion_get`. Today any stash hit runs `remove_at` and then `promote_to_target(core, data, insert_pos)`. In a tiny target bucket, that pushes a resident to the LRU end or evicts it, plus a possible cascade.

New stash-hit behaviour. It mirrors the target tier's existing "hottest → next tier, otherwise climb" rule:
- Compute `is_hottest = Some(item_idx) == core.stash_buckets[stash_idx].promotion_candidate_index()`.
- If `is_hottest`: keep today's path. `remove_at`, then `promote_to_target(core, data, insert_pos)`, then return the item from the target bucket, keeping the existing `unreachable!` guard.
- Otherwise: touch it in place with `return Some(core.stash_buckets[stash_idx].get_from_position(item_idx));`. Under ClassicLRU this moves the item to the stash bucket's MRU end. Nothing else moves, and no cascade happens.

Add a module-level `const STASH_SECOND_HIT_PROMOTION: bool = true;` with a doc comment explaining the admission filter. Gate the new branch on it so the change is easy to read.

Do not change anything else: the stash-first lookup order, `FRESH_PUT_STASH_POS = Front`, `DEMOTE_TO_STASH_POS = Back`, the target and probing branches, and `demote_from_normal_bucket`.

Tests:
- Update `stash_hit_inserts_at_front_of_target`. Each key now needs enough gets to reach its stash bucket's MRU end before it promotes. With one resident per stash bucket, the sole item is already the promotion candidate, so check what `promotion_candidate_index` returns for a single-item bucket and adjust the test.
- Add a test: put two fresh keys that share a stash bucket. A get on the LRU-end key must leave it in the stash at the MRU end, with the target bucket untouched. A second get must move it into its target at the Front.

Invariants: no duplicate keys; every hit returns the item; slot legality holds; metadata-size stays 40 (no new fields).

## Rationale (optional)

Cycle 2's v002 showed that making stash→target promotion hotter hurts, because one stash re-read evicts target residents that have already proven themselves. This tests the opposite direction: stricter admission into the target tier, using the bucket position as a free one-bit reuse counter. Side benefit: first stash hits become an in-place touch instead of remove + promote + cascade, which goes straight at the slow-path cost cycle 2 flagged. Risk: with 2-slot stash buckets, a fresh Front arrival is pushed out by the next fresh put unless it is touched first, so some reuse may be lost. A hit rate below 0.702 refutes the idea.
