# H03

Block a target→probing promotion whenever it would evict a native resident of the neighbouring bucket, so the probing tier only takes in items that fit, raising hit rate.

## Parent

cycle/0002/v003

## Changes

All edits go in `src/dash/segments/dash_segment.rs`, in the target-hit branch of `promotion_get` (the `is_hottest` case).

Background: `promote_to_probing` puts the item into bucket `probing_idx = target_idx + 1`. If that bucket is full, it evicts the bucket's eviction victim, which then goes through `demote_from_normal_bucket`:
- A **foreign** victim (a probing resident whose true target is `target_idx`) is retried in `target_idx`, into the slot the promoted item just left. That is a cheap swap.
- A **native** victim (true target `probing_idx`) is sent straight to the stash. A key that earned its own target slot gets demoted because of its neighbour. This cross-key churn is the probing-tier pollution that cycles 1 and 2 pointed to.

New rule, added before `remove_at` in the `is_hottest` branch:
- Let `pb = &core.buckets[probing_idx]`. Promotion is allowed if `!pb.is_full()`, or if the victim `pb` would evict next has `get_index(&victim.key, core.segment_size) != probing_idx` (foreign).
- To find the victim, use the bucket's eviction-candidate accessor if `Bucket` has one (the counterpart of `promotion_candidate_index`). Otherwise use the index that `put_at` evicts under the current policy (index 0 / Front for the LRU-ordered layout). Read the bucket trait in `src/shared/traits/bucket.rs` to confirm. Don't add any new state.
- If promotion is allowed, keep today's path unchanged.
- If it is blocked, treat the hit as a non-hottest target hit: `return Some(core.buckets[target_idx].get_from_position(item_idx));`. The item stays at the target MRU end and tries again on its next hit, when the neighbour may have a foreign victim or a free slot.

Add a module-level `const PROTECT_NATIVE_NEIGHBOURS: bool = true;` with a doc comment, and gate the rule on it.

Do not change anything else: the lookup order, both stash insert positions, `promote_to_target`, and `demote_from_normal_bucket`.

Tests:
- Keep `target_hit_hottest_promotes_to_probing` and `probing_eviction_demotes_to_target`, adjusting their setup only if they rely on evicting a native neighbour.
- Add a test: fill `probing_idx` with two native keys (true target `probing_idx`). Put a lone item in `target_idx` and get it twice. It must stay in `target_idx`, and both native keys must stay in `probing_idx`.
- Add a test: fill `probing_idx` with a foreign key as the LRU victim plus a native key. The promotion must go ahead, and the foreign key must land in `target_idx`.

Invariants: no duplicate keys, slot legality holds, metadata-size stays 40.

## Rationale (optional)

This answers the open question "would stricter admission into probing protect the hottest tier?" in a different way from H02. H02 filters the stash→target edge; this filters the target→probing edge, using foreign-vs-native ownership instead of a hit count. Allowed promotions become swaps that never push an item out of the normal-bucket tier. Expected per-op-time side effect: fewer `promote_to_probing` cascades, so a shorter get tail. Falsification: a hit rate at or below 0.702 means neighbour-bucket overflow space is worth more to hot keys than native residency is to their neighbours.
