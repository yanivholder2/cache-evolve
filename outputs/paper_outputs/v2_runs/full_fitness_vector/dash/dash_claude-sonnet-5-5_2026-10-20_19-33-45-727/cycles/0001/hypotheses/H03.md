# H03

Requiring a second hit before a stash item is moved into its target bucket (first hit only touches it in place in stash) filters one-hit-wonders and raises hit-rate, at some cost in metadata-size.

## Parent

baseline

## Changes

Add a `hit: bool` field (default false) to `Item` in `src/shared/item.rs`. Keep `Item::new(key, value)` constructible and the key/value fields present. In `promotion_get` in `src/dash/segments/dash_segment.rs`, change the stash-hit branch. If the item's `hit` flag is false, set it to true, call `stash_buckets[stash_idx].get_from_position(item_idx)` to refresh recency inside the stash bucket, and return a reference to it without moving it. If the flag is already true, run the existing path: `remove_at`, then `promote_to_target` with `InsertPosition::Front`. Return the reference via the same residency lookup. The tier cascade, and the target and probing branches, stay as in the baseline. Return the item from the stash bucket at its new position (`get_from_position` returns the index). Size impact: the `bool` may fit in existing padding. Item is 40 bytes for `<u64,u64>`, so verify it does not grow.

## Rationale (optional)

Different strategy from H01 and H02: it changes admission to the hot tiers instead of insert position, and it co-evolves the item metadata.
