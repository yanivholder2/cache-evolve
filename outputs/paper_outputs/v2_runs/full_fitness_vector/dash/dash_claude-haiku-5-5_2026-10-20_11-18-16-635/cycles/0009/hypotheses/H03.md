# H03

Starting a newly inserted entry's access counter at one instead of zero keeps fresh inserts from being the first eviction victims, raising hit rate on workload-a without changing metadata size.

## Parent

cycle/0004/v002

## Changes

Keep the parent's full-scan, non-decaying saturating access counter and its full-scan lowest-counter victim choice. The only change is the initial counter value written when an entry is first inserted into a bucket.

Locate the insert path in the parent overlay where a new entry's counter is set, and change its initial value from 0 to 1. Leave the per-hit increment, the saturation cap, and the tie-break order of the victim scan as they are. The initial value must not exceed the existing cap.

Keep these unchanged:
- the stash-to-target promotion and its deferral;
- the `get` lookup order;
- the record layout, so metadata size stays at the parent's value;
- counter decay, which the parent does not use.

Measure hit rate on workload-a at the parent's size. If the change helps, the expected mechanism is that a fresh entry no longer ties with zero-hit residents at the bottom of the victim scan, so it survives long enough to be re-referenced. If hit rate falls, the parent's retention is depending on fresh inserts being cheap to evict.

## Rationale (optional)

The cross-cycle history credits the full-scan saturating counter as the one consistent retention gain, but it has not tested how a new entry enters that ranking. Cycle 0008 v001 tested the per-hit increment, which was flat, so the initial value is a separate, untested knob on the same counter.
