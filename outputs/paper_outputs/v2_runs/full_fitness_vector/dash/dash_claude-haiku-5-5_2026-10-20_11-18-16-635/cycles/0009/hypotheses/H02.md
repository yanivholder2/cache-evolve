# H02

Incrementing the access counter on only a deterministic one-in-four subset of get hits removes most of the per-hit counter write from the get path while keeping hit rate near the parent's.

## Parent

cycle/0008/v002

## Changes

Keep the parent's packed `Item<u64,u64>` layout with the access counter packed into it, so metadata stays at 32 bytes.

Change only the counter update on the get hit path. Gate the existing saturating increment on a deterministic test of the key, for example a fixed bit of the key hash being zero, so that about one in four hits performs the increment and the others skip it. Use a deterministic test, not a random one, so reruns on the same trace give the same result.

Keep these unchanged:
- the full-scan lowest-counter victim choice and its tie-break order;
- the saturation cap on the counter value;
- the `put` path, including the packed decode it already performs;
- the stash-to-target promotion and the lookup order in `get`.

Do not change how a counter is read during eviction. Only the number of increments on hits changes.

Report get p50 and p99 against the parent, and hit rate on workload-a, so the trade-off between get cost and retention is visible.

## Rationale (optional)

Cycle 0008 v002 kept the best hit rate measured so far (0.6909) but its get p50 rose from 76 to 106 ns, which the insight attributes to the per-hit counter update on the hit path. Sampling the update targets that cost directly while keeping the retention signal from the full-scan counter, which the cross-cycle history shows is the only consistent hit-rate gain.
