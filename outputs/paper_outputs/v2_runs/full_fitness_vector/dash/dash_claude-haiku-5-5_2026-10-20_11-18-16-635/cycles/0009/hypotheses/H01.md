# H01

Probing the target and probing buckets before the stash in `get`, on top of the packed-counter victim choice, lowers get latency while hit rate and metadata size stay at the parent's values.

## Parent

cycle/0007/v003

## Changes

Keep the parent exactly as it is except for the `get` lookup order. Locate the `get` path in the parent overlay and change it so the target bucket and its probing buckets are checked first, and the stash scan runs only when those miss. This is the reordering that cycle 0008 v003 proposed on an earlier base.

Keep these unchanged:
- the saturating access-counter update on a hit, including its increment and cap;
- the full-scan lowest-counter victim choice and its tie-break order;
- the promotion of a stash hit into the target bucket, including its timing;
- the `put` path and the packed `Item<u64,u64>` layout.

A stash hit must still return the same value and take the same promotion and counter actions as before. Only the order of the lookups changes, so a key found in the stash must not be reported as a miss.

Report get p50 and p99 for target hits and for stash hits separately. The stash-hit tail is the risk this change carries and is the number the previous cycle could not split out.

## Rationale (optional)

Cycle 0008 v003 showed that moving the stash scan off the common target-hit path lowered get latency without touching replacement. That run was on a different base. Cycle 0007 v003 is now the best proven base for hit rate and metadata, so this checks whether the get win carries onto it.
