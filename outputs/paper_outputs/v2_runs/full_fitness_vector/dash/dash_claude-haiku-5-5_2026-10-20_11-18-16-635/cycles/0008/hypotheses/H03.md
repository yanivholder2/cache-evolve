# H03

Checking the target bucket before the stash on `get` cuts get latency on target hits without changing any hit or miss outcome.

## Parent

baseline

## Changes

Change the tier lookup order inside the baseline `get` path. Cycle 0001 found that the stash scan currently runs before the target and probing scans, and that skipping it on common target and probing hits was the clearest per-op gain in its cohort.

- Scan the target bucket first, then its probe sequence, and only scan the stash after both miss.
- Return the same value for every key the baseline returns: same hit/miss result, same value, and no change to the stored data.
- Do not add an occupancy check or a stash-empty fast path. Cycle 0002 v002 showed such checks raise latency, which points to stash buckets being rarely empty on these traces.
- Leave insert, promotion, eviction and the victim scan in `evict_one()` untouched.

Invariants: `get` must be semantically identical to baseline for every key, including keys that live only in the stash, and `put` must not change.

## Rationale

Every variant to date that tried to move hit rate has been tuned on workload-a, and the cohorts keep attributing per-op movements that their edits do not reach. This hypothesis instead targets get latency directly, on a path the change does reach. Target-hit gets should get cheaper because they no longer pay for a stash scan first. Hit rate and metadata size should match baseline exactly (0.663 and 40 bytes), which makes the result easy to check. The risk is that stash-hit gets now pay for two scans before the third, so the get tail on stash hits may rise; report stash-hit latency separately from target-hit latency so the trade-off is visible.
