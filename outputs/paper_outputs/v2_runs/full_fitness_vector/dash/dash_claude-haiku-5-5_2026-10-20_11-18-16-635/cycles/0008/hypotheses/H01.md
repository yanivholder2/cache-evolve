# H01

Doubling the saturating access-counter increment on a target hit in the packed record raises hit rate on workload-a over cycle/0007/v003 at no metadata or put-path cost.

## Parent

cycle/0007/v003

## Changes

Start from the cycle 0007 v003 overlay, which ports the saturating access counter and the full-scan lowest-counter victim choice onto the packed `Item<u64,u64>` record.

- In the target-hit path (the one saturating increment that v003 adds on `get`), change the increment from +1 to +2. Keep the saturation ceiling at the counter's existing maximum so the value cannot wrap.
- Leave `evict_one()` unchanged: it must keep the full scan for the lowest-counter resident and the same tie-breaking as the parent.
- Do not add any decay or halving of counters (cycle 0007 v002 showed decay lowers hit rate).
- Leave the counter's initial value on insert unchanged.
- Do not change the packed layout. Metadata size must stay at 32 bytes.

Invariants: the stored counter must stay within its existing bit width, and no change may touch the insert or promotion position logic.

## Rationale

Cycles 0002, 0004 and 0007 all point to the never-decaying frequency counter as the one hit-rate lever that has shown a gain. v003 reached 0.6679 but, per its own insight, by less than the hypothesis targeted. A larger per-hit increment makes frequently hit residents harder to pick as victims, which strengthens the retention effect at eviction rather than at insert, where earlier cycles show losses. The change adds one constant to an existing saturating add, so it should leave put and metadata cost essentially unchanged. Measure on workload-a first; the second-trace check remains outstanding and should be run before this result is trusted.
