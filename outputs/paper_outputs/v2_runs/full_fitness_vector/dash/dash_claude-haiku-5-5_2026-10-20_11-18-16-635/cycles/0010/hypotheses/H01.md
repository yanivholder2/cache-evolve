# H01

Count re-use on put-updates of resident keys raises hit rate on Zipfian traces by letting hot keys keep climbing in the lowest-counter victim scan.

## Parent

cycle/0007/v003

## Changes

Keep the full-scan, lowest-counter victim selection and the non-decaying saturating counter exactly as they are. Only the put path changes: when `put` is called for a key that is already resident in the target bucket or its probe bucket (an overwrite, not an insert), apply the same saturating counter increment that the get-hit path applies to that slot. Do not change the insert-time counter value (keep it at 0), do not sample the increment, and do not alter the value write itself. Do not touch the get path or the stash-to-target promotion logic. Preserve the 32-byte packed record layout; the change must not widen any field.

## Rationale (optional)

Cycle 0009 v003 showed that seeding new counters at 1 is inert, so the retention effect comes from counts accumulated after insertion. Cycle 0009 v002 showed that gating the increment hurts hit rate. This hypothesis extends the accumulation to a reuse event that currently earns no count. Expected signature: hit-rate moves above 0.6679 on workload-a with metadata-size still at 32 and no change to eviction code. Source of the overlay could not be inspected while drafting, so the implementer should confirm the put path's bucket probe before editing.
