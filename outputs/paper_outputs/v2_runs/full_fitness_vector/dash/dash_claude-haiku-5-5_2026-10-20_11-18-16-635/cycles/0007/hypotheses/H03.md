# H03

Porting the full-scan saturating-counter victim selection from cycle/0004/v002 onto the packed `Item<u64,u64>` layout of cycle/0004/v003 should keep metadata size at 32 while recovering the parent's hit-rate gain.

## Parent

cycle/0004/v003

## Changes

Keep the `Item<u64,u64>` packing from cycle/0004/v003 exactly as it is, and leave `DashSegment` at its baseline layout so that the packed-segment decode cost from cycle 0006 v002 does not return. Take the saturating access counter and the full-scan lowest-counter victim choice from cycle/0004/v002, and add them to the parent:

- Store the saturating counter in spare bits of the packed per-item record that v003 already uses, so the record stays at its current size. If there are not enough spare bits, use the packed `u8` slot and report it; do not add a separate array.
- In the target-hit branch of the get path, saturating-increment the item's counter. This is the only get-path write.
- In `evict_one()`, replace the parent's victim choice with a scan of the target bucket that takes the slot with the lowest counter, using the same tie-break as cycle/0004/v002.
- Leave insert placement, stash-to-target promotion, and the stash scan as they are in the parent.

Invariants: metadata size must stay at 32, and hit rate should be at least the parent's 0.6909 on workload-a. Report the hit rate on a second non-workload-a trace, since that check is still outstanding.

## Rationale (optional)

Cycle 0004 v002 has the best hit rate (0.6909) and cycle 0004 v003 has the smallest metadata size (32), but no variant combines them. Cycle 0006's insights say layout and replacement are separable, since repacking left eviction order unchanged. This hypothesis tests that claim directly: if the hit-rate gain holds on the packed base, the two incumbents can be merged without either one's cost. If the counter does not fit in the record's spare bits, that is also a finding about the layout's limits.
