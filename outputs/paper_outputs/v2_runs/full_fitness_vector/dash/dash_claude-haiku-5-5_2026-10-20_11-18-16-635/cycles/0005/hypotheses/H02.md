# H02

Confine the saturating access counter to stash-bucket residents so frequency-aware eviction protects hot stash entries without adding work to target-bucket eviction.

## Parent

cycle/0004/v001

## Changes

Start from v001, which keeps the deferred stash-to-target promotion and stores its first-hit state in existing stash slot metadata. Add the saturating access counter from v002, but apply it only where `evict_one()` chooses a victim among stash-bucket slots. Target-bucket victim selection keeps v001's existing choice unchanged, so the lowest-counter search runs only on stash eviction. Increment the counter on stash hits using the same flag-bit state v001 already keeps, and do not add a separate load or conditional update on the stash-hit branch. Keep the promotion condition, the first-hit flag semantics, and the get path otherwise identical to v001.

## Rationale (optional)

v002 showed frequency-aware victims give the cycle's only clear hit-rate gain, and v001 showed the deferred promotion keeps its gain with cheap first-hit state. Neither change has been combined. Restricting the counter to stash slots should keep the hit-rate gain if it comes from stash residents, and it should keep put-path cost below v002's because target-bucket puts skip the new scan. If hit rate falls back to v001's level, the gain came from target-bucket residents.
