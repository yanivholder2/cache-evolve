# H03

Shrink the per-segment bookkeeping of `Dash<u64,u64,DashSegment>` from 24 bytes to 16 bytes so metadata-size drops below v003's 32 without changing eviction order.

## Parent

cycle/0004/v003

## Changes

Start from v003, which packs the per-item fields of `Item<u64,u64>` into spare key and value bits and reports metadata-size 32. Target the `DashSegment` struct that the `Dash<u64,u64,DashSegment>` type reports at 24 bytes. Remove its alignment padding by reordering its fields from largest to smallest, and fold any per-segment counters that fit within 8 bits into a single packed `u8` or into spare bits of an existing field. Do not change the slot count per segment, the bucket indexing, the stash size, or the victim-selection and promotion logic. `evict_one()` and the promotion path must read the same field values as before, so eviction order is unchanged. Add a compile-time size assertion (`size_of::<DashSegment>() == 16`) inside the overlay's own module, not in the gate-integrity files.

## Rationale (optional)

v003 showed a layout-only repack reduces metadata-size and leaves hit rate unchanged, which lets layout be tested separately from replacement policy. Its per-op gain is unexplained, so this hypothesis claims only the metadata-size and hit-rate dimensions. Hit rate should match v003's 0.6634 exactly, since eviction is unchanged. Any per-op movement should be re-measured with only this change applied before it is credited.
