# H02

Landing stash-to-target promotions at MRU instead of LRU raises hit rate on the LIRS workload-a trace at 2048 entries by letting a promoted item survive one more eviction round.

## Parent

baseline

## Changes

In `src/dash/segments/dash_segment.rs`, change the `Segment::get` implementation for `DashSegment` from `promotion_get(&mut self.core, key, InsertPosition::Front)` to `promotion_get(&mut self.core, key, InsertPosition::Back)`. This is the only production-code edit. It changes the `insert_pos` used by the stash-to-target path in `promotion_get()`, and by every cascade that `promote_to_target`, `promote_to_probing`, and `demote_from_normal_bucket` pass through `put_at`. Leave the bucket, eviction policy, and geometry code alone.

Update the in-file unit tests that encode the Front default: `stash_hit_inserts_at_front_of_target` asserts `items[0].key == keys[1]` and will flip to the Back ordering, and the `*_at_front_when_cold` / `*_at_back_when_hot` helpers should be checked for consistency with the new default. Keep the stash-hit control flow and the `unreachable!` invariant intact.

## Rationale (optional)

The baseline's own docs call Front insertion the cold-entry position: a promoted item must climb back to MRU through a second hit before it can move to probing. Under LIRS, many stash hits are one-shot reuse that gets evicted before a second access. Landing them at MRU instead gives each promotion one extra eviction round, which is a direct hit-rate lever that does not change topology or per-op work.
