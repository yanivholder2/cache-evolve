# H03

Probing the key's target and probing buckets before the stash bucket in `promotion_get` lowers p50 get latency on target and probing hits without changing hit rate.

## Parent

baseline

## Changes

Reorder the three lookup blocks in `promotion_get()` in `src/dash/segments/dash_segment.rs`. Currently the function scans `stash_buckets[stash_idx]` first, then `buckets[target_idx]`, then `buckets[probing_idx]`. Change it to scan `buckets[target_idx]` first, then `buckets[probing_idx]`, and only then `stash_buckets[stash_idx]`. The bodies of each branch stay as they are: the target-hit branch still promotes the hottest item (`promotion_candidate_index`) to probing and returns the probing position, and the stash-hit branch still calls `promote_to_target(core, data, insert_pos)` and keeps its `unreachable!` check. `insert_pos` stays `InsertPosition::Front`.

Before the change, confirm in the code (and add an assertion-based test if needed) that a key is never resident in more than one tier at once, since reordering only changes which copy is returned if duplicates exist. If the invariant does not hold, the hypothesis is refuted and the implementer should stop and report that.

## Rationale (optional)

Each `get` walks the tiers in a fixed order and does one linear key scan per bucket. The baseline pays for the stash scan on every target or probing hit, even though stash hits are a minority of the traffic under this workload. Probing the hot tiers first removes that scan from the common path. The tradeoff is that stash hits now also pay for the two earlier misses, so the net effect depends on the hit mix; the per-op-time dimension is where that shows up. Hit rate and metadata size should be unchanged.
