# H01

Removing the extra first-hit branch from the stash-hit path will recover the get-tail regression of cycle/0003/v002 while keeping its hit-rate gain, targeting per-op-time (get p99).

## Parent

cycle/0003/v002

## Changes

Keep the deferred stash-to-target promotion from v002 (a stash hit promotes only on the key's second stash hit) unchanged in behaviour, but move its first-hit state out of the per-hit path. Specifically:

- Store the first-hit flag in a bit that already exists in the stash slot metadata, so the stash-hit branch in the get path does not perform a separate load and conditional update on every hit. The write to the target bucket on second hit stays as it is.
- Do not change the admission path, the target-bucket eviction path, or `evict_one()`.
- Only touch the get path's stash branch. The put path should be byte-for-byte equivalent to the parent's, so any put-side movement is attributable to the stash flag change alone.
- Preserve the invariant that a one-touch stash entry never enters a target bucket on its first hit.

Measure against workload-a at size 2048 (the only trace measured so far). Success means get p99 at or below the parent's 162 ns with hit-rate at or above 0.6807.

## Rationale (optional)

v002's insight attributes the get-tail regression to the first-hit bit check running on every stash hit. Folding that state into existing metadata targets the cost directly without giving up the hit-rate lever.
