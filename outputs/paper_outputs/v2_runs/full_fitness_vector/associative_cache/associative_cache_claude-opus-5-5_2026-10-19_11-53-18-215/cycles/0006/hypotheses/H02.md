# H02

Skipping the rotate on protected hits that already sit in the MRU quarter of protected will cut get per-op-time on cycle 0005 v003 with negligible hit-rate loss.

## Parent

cycle/0005/v003

## Changes

In `src/associative_cache/associative_cache_bucket.rs`, change only the
protected-hit branch of `AssociativeCacheBucket::hit()` (the `pos >= self.len0`
case on the SLRU path).

Today every protected hit runs `self.items[pos..].rotate_left(1)` and returns
`self.items.len() - 1`. That memmoves the whole tail of protected even when
the item is already near MRU, and hot keys are almost always near MRU.

New behaviour:

```rust
if pos >= self.len0 {
    let n = self.items.len();
    let prot_len = n - self.len0;
    let hot_zone = (prot_len / 4).max(1);   // MRU quarter of protected
    if pos >= n - hot_zone {
        return pos;                          // already near MRU: no move
    }
    self.items[pos..].rotate_left(1);
    return n - 1;
}
```

Invariants to keep:
- The returned index must still be the item's actual position. `pair_get`
  and `get_from_position` index `items` with it.
- `len0` is not touched on this path.
- The probation-hit (promotion) branch, the `protected_cap == 0` branch, the
  non-SLRU fallback, and all `pair_put` paths stay exactly as in the parent.
- The resident-update path in `pair_put` calls `hit(p)`, so it inherits the
  same lazy behaviour. That is fine.
- `Bucket::put` still re-finds by key, so it is unaffected.

Add one unit test on `bucket8()`:
- Fill protected with 6 items.
- Get the MRU item. Its index must not change.
- Get the protected-LRU item (index `len0`). It must move to `items.len() - 1`.
- Call `check_structure` after each step.

## Rationale (optional)

Every cycle has found the same thing: this design's cost is memmove, and moves
that span protected are the most expensive ones. Rotating an item that is
already in the top quarter of protected changes the order of only a few hot
items, so the next eviction choice is almost the same. Protected items are
only demoted one at a time from its LRU end, and a hot-zone item is far from
that end. This is the "lazy promotion" idea (as in CLOCK-like and S3-FIFO-style
caches), applied only inside protected, so scan resistance and probation are
untouched. Expected result: lower get p50/p99, put roughly unchanged, and hit
rate within noise of 0.7242.
