# H01

Raising the protected cap of cycle 0005 v003's 16-byte-Item SLRU bucket from 3/4 to 7/8 will lift hit-rate to about 0.7295 while keeping metadata-size at 16.

## Parent

cycle/0005/v003

## Changes

Edit only `AssociativeCacheBucket::with_layout` in
`src/associative_cache/associative_cache_bucket.rs`. Leave `src/shared/item.rs`
as it is in the parent: `Item` must stay `{ key, value }`, 16 bytes for
`<u64,u64>`. Do not let the merge bring back the 24-byte item. Losing the
shrunken item in a merge is the regression seen in cycle 0005 v001.

Replace

```rust
let protected_cap = (max_size * 3 / 4).min(max_size.saturating_sub(1));
```

with a 7/8 cap that keeps the probation floor scaled to bucket size. This
avoids cycle 0005 v002's fixed 2-slot floor, which cancelled the gain at 8
slots and shrank protected at 4 slots:

```rust
let probation_min = if max_size >= 16 { 2 } else { 1 };
let protected_cap = (max_size * 7 / 8).min(max_size.saturating_sub(probation_min));
```

So 4 slots → protected 3, 8 → 7, 16 → 14, 32 → 28. A 1-slot bucket still gets
`protected_cap == 0` and keeps the existing plain-LRU branch in `hit()`.

Everything else stays the same:
- the ghost ring and its size
- mid-probation cold insertion (`len0 / 2`)
- the ghost-hit and `len0 == 0` paths
- probation-only eviction
- the forward `find`

Update the test comment and helper doc that say "protected cap 6" for
`bucket8()`. The new cap is 7. Check that `check_structure`,
`cold_key_lands_at_probation_middle`, and `long_scan_never_evicts_protected`
still pass. If a test hard-codes the old cap, change its expected value, not
the invariant.

## Rationale (optional)

Cycle 0005 showed that the axes are independent. v002's 7/8 cap gained hit
rate (0.7242 → 0.7295) on the 24-byte item, and v003's 16-byte item won on
metadata and latency with hit rate exactly flat. Combining them should give
the best hit rate and the smallest metadata in a single variant. With a
narrower stride, the longer protected-side rotates that 7/8 causes also move
fewer bytes, so this also tests whether v002's slowdown was real.
