# H03

Promoting probation hits to the midpoint of protected instead of protected MRU, so newly promoted keys must earn a third hit before they outrank long-standing hot keys, will raise hit rate.

## Parent

cycle/0009/v001

## Changes

Edit only the SLRU probation-hit branch of `hit()` in `src/associative_cache/associative_cache_bucket.rs`. Leave everything else as in the parent: the 15/16 cap with a floor of 2, LRU cold entry, the ghost ring, tag-first find, and the 16-byte `Item`.

Current behaviour: a probation hit at `pos < len0` does `items[pos..].rotate_left(1)` (mirrored on `tags`), so the item lands at protected MRU (`len - 1`). Then `len0 -= 1`, and if `len - len0 > protected_cap`, `len0 += 1` demotes protected LRU.

New behaviour on a probation hit (only when `protected_cap > 0`):

1. Let `n = items.len()` and `prot = n - len0`, the protected size before promotion. If `prot < 4`, keep the parent behaviour (promote to MRU) so that tiny protected segments are unchanged.
2. Otherwise compute the target index `t = len0 + prot / 2`, the first slot of protected's upper (MRU-side) half. Do `items[pos..t].rotate_left(1)` and `tags[pos..t].rotate_left(1)`. The promoted item now sits at index `t - 1`, which is just below the midpoint of the post-promotion protected segment, and everything between `pos` and `t - 1` shifts down by one.
3. `len0 -= 1`. Then, as before, if `n - len0 > protected_cap`, set `len0 += 1`. The item demoted this way is the one at the new `len0`: the oldest protected item, not the newly promoted one, because that one sits in the middle.
4. Return `t - 1` as the item's new index. `pair_get_tagged` and `Bucket::get_from_position` already use the returned index.

Protected hits are unchanged: `items[pos..].rotate_left(1)` to MRU. A key that gets a third hit while in protected therefore jumps to MRU, so protected behaves like a two-level frequency/recency ladder (an S3LRU-style idea) inside the existing segment, with no new metadata. The promotion rotate also becomes about half as long, which is a small get-tail bonus.

Invariants: `tags` stays parallel to `items`; the protected cap and the probation floor are untouched; get never drops an item; nothing is ever placed outside the hashed bucket. Update the `cold_newcomer_is_next_victim` and `slru_second_hit_protects` tests if their expected positions change. Add a unit test where a key promoted once is demoted before a key with three or more hits under a stream of fresh promotions.

## Rationale (optional)

Every hit-rate gain so far came from how well protected keeps keys that were really re-referenced. At 15/16, any key with two hits jumps over keys that have been hit many times, and a burst of second hits from a loop pushes those hot keys toward demotion. Midpoint insertion keeps protected's size and scan resistance intact, so it neither shrinks nor displaces protected as a whole (the recurring failure). It only changes the order within protected, ranking keys with three or more hits above keys with exactly two.
