# H01

Carrying cycle 0007 v003's 15/16 protected cap onto v001's tag-first single-hash bucket will raise hit-rate to at least 0.7303 while holding per-op-time at about v001's 45 ns get p50.

## Parent

cycle/0007/v001

## Changes

Edit only `AssociativeCacheBucket::with_layout` in
`src/associative_cache/associative_cache_bucket.rs`. Replace the current
7/8-cap computation:

```rust
let probation_min = if max_size >= 16 { 2 } else { 1 };
let protected_cap = (max_size * 7 / 8).min(max_size.saturating_sub(probation_min));
```

with cycle 0007 v003's rule:

```rust
let protected_cap = if max_size >= 16 {
    max_size - (max_size / 16).max(1)
} else {
    (max_size * 7 / 8).min(max_size.saturating_sub(1))
};
```

This gives 4 -> 3, 8 -> 7, 16 -> 15, 32 -> 30, 64 -> 60, and 1 -> 0.

Keep everything else from v001 exactly as it is:
- the `tags: Vec<u16>` array and `find_tagged`;
- one hash per op in `mod.rs`;
- tag reuse in `record_ghost` and `take_ghost`;
- mid-probation cold insertion and ghost-hit insertion at probation MRU;
- the ghost ring length `(max_size + 1) / 2`;
- the 16-byte `Item`.

Do not regress the carried-forward `item.rs`. Update the unit test
`protected_cap_is_seven_eighths_with_scaled_floor` to the new expected
values: (8, true) -> 15 and (16, true) -> 30. Rename it to match. Every
`check_structure` invariant must still hold.

## Rationale (optional)

v003 gained hit rate at no latency cost, but on the untagged parent. v001
got its latency win without changing any replacement decision. The two
changes touch separate code, so they should stack. Hit rate should match
v003 and latency should match v001. The cycle 0007 continuation asked for
exactly this merge. This variant tests whether carrying it forward works,
since earlier cycles lost improvements this way.
