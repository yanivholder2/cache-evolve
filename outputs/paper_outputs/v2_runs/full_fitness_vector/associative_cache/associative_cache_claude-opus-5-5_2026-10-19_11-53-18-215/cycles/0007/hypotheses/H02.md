# H02

Capping each protected-hit promotion at 4 slots toward MRU, instead of rotating the hit item all the way to protected MRU, will lower the get-p50 per-op-time of cycle 0006 v001's 7/8-cap SLRU and lose at most 0.002 hit rate.

## Parent

cycle/0006/v001

## Changes

Start from cycle/0006/v001's `src/associative_cache/associative_cache_bucket.rs`. Keep the 16-byte `Item`, the 7/8 cap, the ghost ring and the cold/ghost insertion rules unchanged.

Add `const PROMOTE_STEP: usize = 4;`.

In `hit()`, change only the **protected-hit** branch (`pos >= self.len0`):

```rust
let last = self.items.len() - 1;
let dst = (pos + PROMOTE_STEP).min(last);
self.items[pos..=dst].rotate_left(1);
return dst;
```

The hit item moves up by at most `PROMOTE_STEP` slots. The up-to-4 items it passes each shift down one slot. Items beyond `dst` do not move. The memmove is bounded at 5 × 16 bytes no matter how deep the hit is. Hits within 4 slots of MRU behave exactly as before, landing at `last`.

Leave the **probation-hit promotion** path unchanged: a full rotate to protected MRU, then the demote-at-cap rule. A probation item has only shown one reuse, so it still enters protected at MRU. Only protected-to-protected reordering becomes incremental. This works like a CLOCK/"move-ahead-k" approximation of LRU inside protected. Repeatedly hit keys still climb to MRU, and keys that are hit once drift toward the protected LRU end and get demoted first.

Leave `Bucket::put`'s re-find, the resident-update path in `pair_put` (which calls `hit`, and so also gets bounded promotion) and the fallback path unchanged.

Tests:
- Update any test that asserts a protected hit lands at `items.len() - 1` so that it expects `min(pos + 4, len - 1)`.
- Add a test that a deep protected hit at `pos = len0` on a full 16-slot bucket moves the item to `len0 + 4`, and that the slots above that keep their order.
- Keep `long_scan_never_evicts_protected` passing.

## Rationale

Cycle 0006 showed that the latency cost of the 7/8 cap lives in deep protected hits, which run `items[pos..].rotate_left(1)` across the now-longer protected segment. Skipping shallow moves (lazy promotion near MRU, 0006 v002) saved nothing. This change does the opposite: it bounds the *deep* moves and keeps the shallow ones exact. Protected membership, and therefore scan resistance, is untouched. Only recency order within protected becomes approximate, so the hit-rate risk is confined to which protected item gets demoted. The experiment checks whether 0006 v001's get-p50 (59 ns) falls toward the 3/4-cap level (53 ns) while hit rate stays near 0.7295.
