# H03

Adding a doorkeeper admission gate that rejects a put miss on its first sighting will raise hit-rate on workload-a by keeping one-shot inserts out of the cache.

## Parent

baseline

## Changes

Add a fixed-size doorkeeper bitset to the cache struct (for example 4096 bits, held as a boxed array of u64 words, sized at construction). Use a single hash of the key, with the bit index taken from the high bits so it is independent of the set-index bits. On a put miss, test the doorkeeper bit: if it is clear, set it and return without inserting, so the victim scan is skipped entirely; if it is set, proceed with the baseline insert path unchanged. Clear the doorkeeper, all words to zero, once every N put misses, where N equals the number of cache slots, so stale sightings age out. Leave get, eviction order, and the baseline recency policy unchanged.

Invariants to preserve: a key that is already resident is never rejected (the gate is consulted only on the miss path after the lookup fails); the doorkeeper never affects get results for resident keys; no allocation happens on the hot path after construction.

Verification target: hit-rate above the baseline's 0.661 on lirs workload-a at size 2048; put median time no worse than baseline's 69 ns per-op summary. Metadata-size will rise by the bitset size; record the actual figure, since the size probe may not count it.

## Rationale (optional)

Every cohort so far has changed how existing items are ordered or scored inside a bucket. None has changed which keys are admitted. The cycle 0001 through 0005 history identifies one-shot inserts as the pollution pattern that frequency and second-chance signals fix on workload-a, and a doorkeeper removes most of that pollution before it reaches the victim scan, so it targets the same pattern from the admission side. It is also an independent axis from the bucket-level work, which the cohort has been exhausting.
