# H02

Skipping the per-slot access-counter store on get hits once the counter has saturated will lower get p50 latency with hit-rate and metadata unchanged.

## Parent

cycle/0005/v001

## Changes

In the get-hit path, read the hit slot's saturating access counter first. Perform the increment-and-store only when the counter is below its saturation cap; when it is already at the cap, return the hit without writing. Keep the increment rule identical when the counter is below the cap, so eviction order and the periodic halving schedule behave exactly as in the parent. Leave the put path, the victim scan (including the zero-counter early return), and the metadata layout unchanged. Do not add fields.

Invariants to preserve: hit-rate on the workload must match the parent exactly, because the counter value observed by eviction is unchanged for every slot that is below the cap and at the cap for both variants; the miss path is untouched.

Verification target: hit-rate equal to 0.7278, metadata-size 40, get p50 at or below the parent's 72 ns across two runs. Treat any get gain smaller than run-to-run variance as noise, as earlier cycles recommend.

## Rationale (optional)

Cycle 0002 v003's insight records an extra counter write on every get hit as a cost on the get path, and the cycle 0003 insight says the get side pays for that write on every hit. Most hits on a hot working set hit a saturated counter, so the store-skip should remove most of that write while leaving the counter values that eviction sees unchanged. This is a narrow get-side test; a null result would confirm the get-side cost is not the store.
