# H02

Replacing the per-slot loop in the per-bucket reference-mask clock walk with a single rotate-and-trailing-zeros bit operation will cut the put-side per-op time lost by the bitmask variant while keeping its 40-byte metadata.

## Parent

cycle/0004/v001

## Changes

In the eviction clock walk over the per-bucket `u32` reference bitmask, replace the loop that tests and clears one slot bit at a time with a word-level search:

- Let `hand` be the clock position for this bucket (the same position the parent's walk uses). Compute `candidates = !mask` rotated so that bit `hand` becomes bit 0, then take `trailing_zeros()` of that value. If it is 32 (no clear bit in the word), treat the bucket as fully referenced: clear the whole mask to 0 and select slot `hand` as the victim, matching the parent's walk on a fully-referenced bucket.
- When a clear bit is found at offset `k`, clear every reference bit that the parent's walk would have passed over in this search, which is the contiguous run of set bits from `hand` up to `k`. Do this with one mask operation (`mask &= !(run_mask)`), not a per-slot loop.
- Update `hand` to the slot after the chosen victim, as the parent does.

The get-hit path stays a single bucket-word OR setting the slot's bit. Do not add any per-slot state or counters. Keep the metadata layout exactly as in v001 (one `u32` per bucket, no per-item reference field), so metadata-size stays 40.

Invariant to preserve: for any mask and hand, the victim slot and the resulting mask must equal what v001's loop produces. Hit-rate on workload-a should match v001 exactly (0.7244).

## Rationale (optional)

v001 showed that moving reference state into a per-bucket mask saves metadata with no hit-rate loss, but both get and put regressed. The insight attributes the put regression to bit-scanning in the clock walk and the get regression to the bucket-word write. This hypothesis targets the put-side scan directly and leaves the get-side write alone, so if get stays slow, the get cost is a fixed cost of the bucket-word write and the scan is not the cause. Either outcome answers the open question from cycle 0004.
