# H01

Adding an early exit to the frequency victim scan on put, stopping at the first zero-counter slot, will cut put-side per-op time on the frequency policy while leaving hit-rate unchanged.

## Parent

cycle/0002/v003

## Changes

In the put-side victim selection for the frequency policy (the minimum-counter search over all slots of the target bucket), change the scan loop so it returns immediately when it encounters a slot whose access counter is 0, instead of finishing the full bucket pass. A counter of 0 is the global minimum possible value, so the first zero-counter slot is exactly what the full scan would return when ties are broken by first-found slot index; the eviction result is therefore identical to the parent.

Keep everything else intact: the get-hit counter increment, the periodic halving schedule, the insert-time counter initialisation, and the victim tie-break order. Do not add any cached-minimum or per-bucket index state; the scan must read counters directly, as in the parent. No new metadata fields.

Invariant to preserve: for any bucket state, the chosen victim must equal the victim the parent's full scan would choose. Hit-rate on workload-a should therefore match the parent exactly (0.7278); any hit-rate change indicates a bug in the early exit.

## Rationale (optional)

Cycle 0004 showed the full-bucket minimum scan on put is the main put-side cost of the frequency line, and cycle 0003 showed that cached-minimum shortcuts fail because get-hit counter updates invalidate them. This hypothesis avoids that invalidation problem by not caching anything: it only shortens the scan when the answer is already known to be the global minimum. The benefit depends on how often zero counters occur after halving, so the gain may be small on workloads without many one-shot inserts.
