# H03

Replacing the bucket-index function with a multiplicative hash of the key reduces conflict misses on workload-a and raises hit-rate with zero per-item metadata and no extra per-op work.

## Parent

baseline

## Changes

Change only the function that maps a key to its bucket index (the set-index computation used by get, put, and eviction; locate it in the baseline associative_cache source). Currently the index is taken from the low bits of the key or of a simple hash. Replace it with:

- A multiplicative hash: `h = key.wrapping_mul(0x9E37_79B9_7F4A_7C15)`, then take the top `log2(bucket_count)` bits of `h` as the bucket index (a Fibonacci-hash shift, not a modulo).
- Keep the bucket count and the power-of-two sizing unchanged, so capacity and bucket width are the same as baseline.
- Do not change the bucket scan, the eviction policy, the item layout, or the get and put paths beyond the index call.

Invariants to preserve: every key still maps to exactly one bucket, the index is deterministic across calls, and the bucket count stays a power of two so the shift is valid. Metadata-size should be unchanged (no new fields), and the per-op cost change should be limited to one multiply and one shift.

Rationale: the cycle 0001 and 0002 insights attribute the workload-a misses partly to conflict within buckets, and no cycle has changed how keys are spread across buckets. A better spread should lift hit-rate under the same policy, which tests whether the remaining misses are index conflicts rather than policy errors. Measure hit-rate on workload-a at size 2048 against baseline's 0.661. If hit-rate does not move, the conflict-miss hypothesis is refuted for this trace.
