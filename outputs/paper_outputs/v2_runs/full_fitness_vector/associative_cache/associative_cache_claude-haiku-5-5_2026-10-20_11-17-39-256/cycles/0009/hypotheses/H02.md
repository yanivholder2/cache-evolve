# H02

Replacing the whole-structure periodic counter halving with incremental per-bucket halving, done inside the put path that already scans the bucket, will cut the put-side p99 tail (per-op-time) without changing hit-rate.

## Parent

cycle/0002/v003

## Changes

Start from cycle/0002/v003, the frequency-based victim selection with per-slot access counters and periodic halving. Keep the exact minimum-counter victim search and the counter increment on hits unchanged.

Remove the global periodic halving pass that walks every bucket on the halving interval. Instead, keep a per-bucket epoch value (one small integer per bucket, stored alongside the bucket's existing state). Halving of a bucket's counters happens lazily: when a put or get touches a bucket whose epoch is behind the global epoch, halve that bucket's counters by the number of elapsed epochs, then set its epoch to the current value. The global epoch counter advances on the same schedule as the current halving interval, so the total decay per counter stays equal to the parent's.

Do the lazy catch-up inside the put-side bucket scan that already runs on a full bucket, so no extra pass over the structure is added. Do not add extra decay on top of the schedule (cycle 0003 showed that erases frequency protection).

Keep the cache struct's public fields and the metadata layout unchanged except for the per-bucket epoch.

## Rationale (optional)

The put tail has resisted scan shortcuts and aging rewrites in cycles 0004 to 0008, but none of those attacked the periodic whole-structure halving. A global pass produces occasional very slow operations that would show up in p99 and be invisible in p50, which fits the tail-only pattern seen across cycles. Hit-rate should stay the same because the decay schedule is unchanged, just applied per bucket rather than all at once.
