# H03

Choosing the eviction victim by lowest per-slot access-frequency counter within the bucket will raise hit-rate on workload-a by keeping frequently re-referenced keys that recency-based eviction currently drops.

## Parent

baseline

## Changes

Add a one-byte saturating access counter to each occupied slot. Initialise it to 0 on insert. Increment it (saturating at 3) on every get hit in `get_position()`'s hit path. In the baseline victim-selection routine used by `put` when a bucket is full, scan the bucket's slots and evict the slot with the smallest counter, breaking ties by the baseline's existing choice order so behaviour is deterministic. Age the bucket every 256 insertions into it by halving every counter in that bucket, so stale frequency does not pin slots forever. Leave the promotion logic, bucket geometry, and get/put return semantics unchanged. Expect metadata-size to grow by one byte per slot, which the size probe must report.

## Rationale (optional)

Cycle 0001 explored only positional and bucket-geometry changes, and all of them missed on the recency side. A frequency signal is a different strategy: it asks whether re-referenced keys should survive a burst of one-shot insertions, which is the pollution pattern the cycle 0001 insights describe. Starting from baseline keeps this as a clean test of the signal rather than a stack on the widened-bucket variant.
