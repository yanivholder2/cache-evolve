# H01

Moving cycle/0003/v003's second-chance reference bit out of each item and into a per-bucket bitmask will restore metadata-size to the baseline's 40 bytes while keeping workload-a hit-rate at or above 0.7244, targeting metadata-size.

## Parent

cycle/0003/v003

## Changes

Keep v003's CLOCK-style victim selection and its reference-bit semantics exactly as they are. Change only where the reference state is stored.

- Remove the per-item reference field from the stored item type, so the item layout returns to the baseline's `Item<u64,u64>` footprint.
- Add one `u32` reference bitmask per bucket (one bit per slot, buckets are 32 slots). Store it alongside the existing per-bucket state, next to the clock hand.
- In the get hit path (`get_position()`), set the slot's bit in the bucket mask with a single OR. Do not clear anything on get.
- In the full-bucket victim routine used by put, read the bucket mask. Walk from the clock hand: if a slot's bit is set, clear that bit and advance; if clear, evict that slot, store the hand after it, and stop. Bound the walk to one revolution.
- On insert into a slot, clear that slot's bit in the mask so a fresh item is evictable on the next pass unless hit again.
- Keep the insert, get-miss, and key-lookup code unchanged. Do not add counters, ghost memory, fingerprints, or any change to bucket width.

Expected test: metadata-size should report 40 for `Item<u64,u64>`, and hit-rate on workload-a should match cycle/0003/v003's 0.7244 within noise. Put p50 should not regress relative to v003. Get p50 should stay within noise of v003's 71 ns, since the write is now a bucket-word OR instead of an item-field store.

## Rationale (optional)

Cycle 0003 left open whether the second-chance gain needs more than one bit per item, and v003's metadata grew from 40 to 48 bytes. Moving the single bit into a per-bucket word tests whether the gain survives without per-item state, which is the open question the cross-cycle insights flag as most useful to resolve.
