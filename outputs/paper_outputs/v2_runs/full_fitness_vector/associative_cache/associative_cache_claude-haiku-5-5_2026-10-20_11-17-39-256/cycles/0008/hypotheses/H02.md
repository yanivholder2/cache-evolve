# H02

Porting the Fibonacci multiplicative bucket hash onto the frequency-retention parent lowers per-op get time below 60 ns while keeping workload-a hit-rate at 0.7278.

## Parent

cycle/0002/v003

## Changes

Replace the bucket-index computation in the key-to-bucket function with a Fibonacci multiplicative hash: `bucket = (hash64(key).wrapping_mul(0x9E3779B97F4A7C15) >> (64 - log2_buckets))`. Require the bucket count to be a power of two; if it is not already, derive `log2_buckets` from the configured bucket count and assert it at construction.

Change nothing else. Keep the frequency counters, the per-slot counter store on get hits, the periodic halving schedule, the exact minimum victim search, and the put and get control flow exactly as in cycle/0002/v003. The only intended difference is which bucket a key lands in.

Expected effect: hit-rate stays at 0.7278 within run-to-run noise, since cycle 0007 v003 showed the hash does not change workload-a hit-rate. Per-op get p50 should fall toward the 51 ns seen in cycle/0007/v003. If p50 stays near 71 ns, the timing gain in cycle 0007 was measurement noise, and the hash should be dropped as a timing lever.

Repeat the measurement across at least three runs and report the spread of per-op get and put times, so the timing claim is checked against noise.

## Rationale (optional)

Cycle 0007 v003 won on timing alone (per-op 51 ns, hit-rate unchanged from baseline), but its own insight treats the timing shift as probably noise because one multiply and shift should not produce a speedup that large. This hypothesis tests whether the hash's timing effect survives on the frequency parent, where hit-rate is already 0.7278. It costs one line and makes the timing question directly testable.
