# H03

Moving the per-slot access counters out of the item struct into a parallel array removes the get-side tail movement that the cache struct layout seems to cause, while hit-rate and policy stay fixed.

## Parent

cycle/0006/v002

## Changes

Keep the saturated-counter store skip from cycle/0006/v002 exactly as written: on a get hit, skip the counter store once the counter is saturated. Change only where the counter lives. Store the per-slot access counters in a separate contiguous array owned by the cache, indexed by the global slot index (bucket * ways + way), instead of as a field in each item or inside the bucket struct.

Concretely: the get-hit path reads and writes the counter at `counters[slot]`, the put path initialises `counters[slot]` on insert, and the victim search reads `counters[slot]` across the bucket's slots. The halving pass walks the same array. Do not change the halving schedule, the saturation threshold, the victim selection rule, or the admission path.

Do not add any new fields to the inline item or cache struct. Confirm the item struct size is unchanged from cycle/0006/v002 and report it under metadata-size.

Expected effect: hit-rate stays at 0.7278 exactly, since policy is unchanged. Get p99 should stay at or below the cycle/0006/v002 tail. If the get-tail gain disappears when the counter moves out of the struct, the struct-layout explanation is refuted and the get-side movement is more likely noise.

Measure over three runs and compare get p50 and p99 against cycle/0006/v002 measured in the same session, not against the stored figures.

## Rationale (optional)

Several cycles recorded get-side movement with no get-path change, and the open question is whether struct size or layout causes it. The cycle 0007 insight asks for a layout-only probe to settle this. This hypothesis is that probe, applied to the incumbent that showed a get-tail gain, and it leaves the retention policy untouched so any change is attributable to layout.
