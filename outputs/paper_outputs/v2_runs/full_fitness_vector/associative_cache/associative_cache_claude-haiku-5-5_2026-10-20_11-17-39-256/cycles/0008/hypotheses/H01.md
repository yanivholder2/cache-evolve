# H01

Admitting a key only on its second sighting, via a side-table doorkeeper, raises workload-a hit-rate above the 0.7278 incumbent by keeping one-shot keys out of the victim scan.

## Parent

cycle/0002/v003

## Changes

Add a doorkeeper on the put-miss path, placed before the victim scan in the insert routine. Store the doorkeeper bitset in a separate heap-allocated array owned by the cache, not as a field inside the inline cache struct, so the struct layout is unchanged. Size it to a fixed number of bits per bucket (for example 4 bits per slot, as a power of two) and index it with the same key hash already used for the bucket index.

Admission rule: on a put miss, if the doorkeeper bit for the key is unset, set it and bypass the insert (return without evicting or writing a slot). If the bit is already set, admit the key through the existing frequency-based insert path unchanged, including the initial counter value. Do not clear the bit on admit.

Clearing: reuse the existing periodic halving schedule. On each halving pass, clear the doorkeeper array in the same loop, rather than adding a separate whole-structure clear. Do not change the halving schedule itself.

Preserve: the exact minimum-counter victim search, the get path, and the counter update on get hits. Keep the frequency counters and their halving exactly as in the parent.

Expected effect: workload-a hit-rate should rise over 0.7278 on the 2048-item run. If it instead falls, the admit-on-second-sighting rule is refuted for this trace. Metadata-size is expected to grow only by the side array, which is outside the struct, so note the reported figure.

## Rationale (optional)

Cycle 0006 gained hit-rate with a doorkeeper, and cycle 0007 lost it with a reject-on-first-recurrence rule. The cycle 0007 insight recommends testing a looser admit-on-second-sighting rule with the bitset kept out of the inline struct. This hypothesis does exactly that, on the stronger incumbent parent, so it isolates the admission rule from the parent change.
