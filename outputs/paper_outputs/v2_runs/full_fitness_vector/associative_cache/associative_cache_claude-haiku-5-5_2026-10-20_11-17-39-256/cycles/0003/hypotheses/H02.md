# H02

Folding counter aging into the put-side min scan will keep v003's frequency hit-rate gain on traces with shifting working sets without adding any extra per-op work.

## Parent

cycle/0002/v003

## Changes

v003 never decays its access counters, so a key that was hot early can hold its slot indefinitely. Add aging that piggybacks on the scan v003 already performs on put.

- In the full-bucket scan on put, which already visits every slot to find the minimum counter, also halve (right-shift by one) the counter of every slot visited, except the slot chosen for eviction.
- Do not add a second pass and do not touch the get path beyond v003's existing counter increment on hit.
- Keep the eviction choice itself identical to v003: pick the minimum using the pre-decay values from the same scan, so the only behavioural change is that counters carry less stale history.
- Keep the counter type and saturation as in v003. Do not change the bucket layout or the ghost and fingerprint code (both were dropped in cycle 0002).

Expected test: on workload-a, hit-rate should stay at or above roughly 0.72 (the aging is allowed to cost a little). The main claim to test is that hit-rate holds on a second trace with a shifting working set, where v003 is expected to lose ground. Per-op time should stay close to v003's put p50 of 168 ns, since no extra scan is added.

## Rationale (optional)

Cycle 0002 left open whether the frequency gain depends on workload-a's one-shot insert pattern. Aging is the standard answer to stale frequency, and folding it into an existing scan keeps the cost question separate from the policy question.
