# H03

Halving every shared frequency counter once per sample window on top of the admission gate raises workload-a hit-rate by stopping stale keys from winning the incoming-versus-victim comparison.

## Parent

cycle/0005/v001

## Changes

Start from the cycle 0005 v001 incumbent in `src/associative_cache/mod.rs`. Keep the admission comparison in `put()`, the probationary-first eviction, and the promotion logic unchanged.

Add a TinyLFU-style periodic reset to the shared `freq` counter, which is the counter the admission gate reads:

- New field: `ops_since_reset: usize`, initialised to 0 in `try_new()`. Sample window `W = 10 * num_of_buckets * bucket_size`.
- In `get_and_update_item()`, after the existing `freq` bump, increment `ops_since_reset`. When it reaches `W`, halve every counter with `for v in self.freq.values_mut() { *v /= 2; }`, remove entries whose counter is now 0, and reset `ops_since_reset` to 0.
- The halving runs only from `get_and_update_item()`, so each reset is triggered by a get and happens after the bump for that get. Do not halve inside `put()`.
- Keep the `.max(1)` floor on the incoming count in `put()`, so an incoming key always has at least 1 to compare.
- Do not change eviction order, bucket logic, or the `bucket.put` path. Do not add an aging step to the eviction policy itself; the cycle 0001 and 0002 aging results were for the eviction policy alone.

Log the number of resets per run at `info!` level so the next cycle can check that the reset fires under the harness.

## Rationale (optional)

The incumbent's admission gate compares counters that only grow, so a key that was hot early can keep a victim's displacement-proof count long after its reuse has stopped. Cycle 0008 pruned singleton history and regressed. This hypothesis is different: it keeps every key but halves counts on a fixed window, preserving relative order among recently active keys. The gate's decision rule is unchanged, so any hit-rate difference comes from the counter's freshness alone.
