# H02

Halving the shared frequency counters on a fixed access window, without removing any entries, will raise hit-rate on workload-a over cycle/0005/v001 by letting stale hot keys lose admission weight.

## Parent

cycle/0005/v001

## Changes

Add aging to the shared frequency map in `AssociativeCache` (`src/associative_cache/mod.rs`, where `freq` lives). Add an `accesses: u64` field that counts calls to `get_and_update_item()`. Set the window to `W = 10 * (buckets.len() * bucket_size)`, computed once in `try_new()`.

When `accesses % W == 0` after the increment in `get_and_update_item()`, halve every value in `freq` with `*v /= 2` (floor). Do not remove any key, including keys that reach 0. Do not change the bucket code or the admission comparison in `put()`. The gate continues to use `incoming.max(1)` and strict `incoming > victim`.

Invariants to preserve: the set of keys in `freq` only grows through the existing `entry(...).or_insert(0)` call, halving never changes which items are resident, and the miss and hit paths return the same values as the parent aside from the changed counts.

## Rationale (optional)

Earlier aging tests either zeroed entries or changed counter width, and both were flat or lost (Cycles 0001, 0002, 0009). The zero-pruning step was the likely loss, because it erases the one-hit history that the gate uses. This variant keeps every entry and only decays the magnitudes, so the aging effect is tested alone and separately from the admission rule.
