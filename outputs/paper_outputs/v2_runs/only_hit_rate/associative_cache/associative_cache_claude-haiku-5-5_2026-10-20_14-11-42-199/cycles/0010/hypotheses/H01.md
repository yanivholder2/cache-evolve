# H01

Evicting the lowest shared-frequency probationary entry, and gating admission against that same entry, will raise hit-rate on workload-a over cycle/0005/v001.

## Parent

cycle/0005/v001

## Changes

Change the probationary victim choice so that it is not the policy's ordering alone. In `AssociativeCacheBucket` (`src/associative_cache/associative_cache_bucket.rs`), `probation_victim()` should return the index of the probationary item with the smallest shared frequency, taken from the `freq` map owned by `AssociativeCache`. Ties go to the index the existing eviction policy would pick, so the current ordering is kept when frequencies are equal.

Pass a frequency lookup (or the precomputed victim index) from `AssociativeCache::put()` down into the bucket. Use the same victim in both places: the admission check in `put()` and the actual removal in `evict_victim()`. The two must not diverge, so an admitted key always displaces the entry it was compared against.

Leave the protected-region victim, `promote()`, `touch()`, and the demotion path unchanged. Keep the strict `incoming > victim` comparison from cycle/0005/v001 and the `incoming.max(1)` rule. Do not change the insert position (new misses still go at the probationary front as in the parent).

Invariants to preserve: a bucket never exceeds `bucket_size`, `prob_len` stays consistent after every removal, and a bypassed insert leaves the bucket untouched.

## Rationale (optional)

The incumbent's gate uses the policy's victim, so it can bypass a key that is more frequent than the probationary entry that would really be displaced. Making the victim the lowest-frequency probationary entry changes which items leave the cache, which is where the earlier scan-resistance gains came from. The change adds no per-entry metadata.
