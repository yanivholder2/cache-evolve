# H03

Gating insertion of a new key on a single shared frequency estimate, compared against the victim's estimate, will raise hit-rate on workload-a by rejecting one-shot inserts that would displace reused entries.

## Parent

baseline

## Changes

Add one frequency counter table that is used for both incoming and resident keys, so the two estimates are on the same scale. Use a small saturating counter per key hash (for example a 4-bit count, halved periodically by the insert count), updated on every access, hit or miss.

On a miss that would evict a resident entry, compare the incoming key's count with the chosen victim's count, using the same table for both. Admit the new entry only if its count is strictly greater than the victim's count; otherwise skip the insert and leave the victim in place. Do not change the victim-selection order itself, so the admission gate is the only behaviour change.

Keep the gate off for inserts into empty slots. Preserve the existing hit path and the bucket layout. The counter table is the only new state and must not be exposed through the fitness-vector schema.

## Rationale (optional)

The cycle-0002 admission variant lowered hit-rate, and the cycle-0003 insight attributes that to comparing two frequency estimates on different scales, not to the idea being weak. This hypothesis re-tests admission from baseline with a single estimator, so a null or negative result would refute the admission idea itself rather than the comparison.
