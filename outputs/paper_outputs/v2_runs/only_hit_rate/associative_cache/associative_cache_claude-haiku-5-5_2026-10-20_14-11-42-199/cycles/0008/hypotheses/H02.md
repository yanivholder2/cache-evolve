# H02

Pruning singleton counts of non-resident keys from the shared frequency map when it grows past 4x capacity cuts metadata-size on the incumbent with hit-rate held within noise.

## Parent

cycle/0005/v001

## Changes

Change only the bookkeeping of the shared `freq: HashMap<K, usize>` field in `AssociativeCache` (`src/associative_cache/mod.rs`). Keep it an exact `HashMap`, with no hashing, aliasing, saturating counters, or halving. Keep the admission logic in `put()` and the counter bump in `get_and_update_item()` unchanged.

Add a bounded cleanup step. After the increment in `get_and_update_item()`, if `freq.len()` exceeds `4 * settings.capacity()` (store the capacity on the cache at construction in `try_new()`), remove every entry whose count is 1 and whose key is not currently resident in its bucket. A resident check is `self.buckets[get_index(&k, self.buckets.len())].get_position(&k).is_some()`. Run the cleanup as a single `retain` pass, not per access. Resident keys and any key with count 2 or more are never pruned.

This keeps the gate's decisions identical for the common case. A non-resident key with no stored count already reads as `max(1)` in `put()`, so dropping a singleton changes the gate only when that key is accessed again. The expected effect is a bounded map and a lower metadata-size, with a small or zero hit-rate change. Report `metadata-size` in the fitness vector, along with `hit-rate` on workload-a. A hit-rate drop beyond noise falsifies the claim that singleton history is free to discard.
