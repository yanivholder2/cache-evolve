# H02

Gating inserts on frequency, so a new key replaces a victim only when its count is at least the victim's, raises hit-rate on workload-a.

## Parent

cycle/0002/v001

## Changes

Keep the per-bucket fingerprint filter from this parent unchanged. Add an admission check on the insert path, before `evict_one()` is called on a full bucket. Compare the incoming key's frequency estimate against the chosen victim's counter. Use the bucket's existing hit counter as the estimate for resident keys. For the incoming key, use a small per-cache table of 4-bit saturating counters indexed by the key's hash, incremented on every get and put that misses. If the incoming estimate is strictly less than the victim's counter, do not insert: return the same result the parent returns for a rejected put, and leave the bucket unchanged. Otherwise evict and insert as the parent does. Do not change the fingerprint comparison, the promotion logic, or the aging counter. The frequency table must be reset whenever the cache is cleared.

## Rationale (optional)

Both cycle 0001 and cycle 0002 left hit-rate flat or marginal, and every aging variant was null. This hypothesis moves the lever from eviction order to the admission decision, so it does not depend on the AgedLfu halving that has not been confirmed as active. Zipfian-like traces are where one-hit wonders displace frequent keys, which is the case an admission gate targets.
