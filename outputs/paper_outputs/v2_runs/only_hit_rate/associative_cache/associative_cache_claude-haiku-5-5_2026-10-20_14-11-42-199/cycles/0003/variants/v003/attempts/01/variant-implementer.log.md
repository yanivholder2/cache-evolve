**What the overlay does:**
- Each bucket keeps one `items` vector ordered as `[probationary | protected]`, with `prob_len` marking the boundary. `get_items()` still returns that full vector, so the invariant gate's `P2 slot_legality` check, which iterates `get_items()`, still sees every item.
- Probationary capacity is `max(1, round(25%))` of `bucket_size`. Protected capacity is the remainder.
- A miss inserts into probation. When the bucket is full, the victim comes from probation first and falls back to protected only if probation is empty.
- A probationary hit promotes the entry to protected. If protected is full, its policy-chosen LRU entry is demoted back to probation.
- The configured eviction policy (`ClassicLRU`, `Lfu`, and so on) still orders entries within each region. Its `get_from_position` side effects are applied to the region that was touched.
- `new`, `get`, `put`, the bucket indexing, key comparison, geometry and the `Display` impl are unchanged. Only the bucket file is overlaid.

**Things to check when the gates run:**
- The hypothesis names `evict_one()`, which doesn't exist here. I mapped it to the bucket's `evict_item`, which the trait default and my override both use.
- Probation is not capped on insert. A miss into a non-full bucket always lands in probation, so probation can exceed 25% until the bucket fills. I read "fixed split" as the protected cap plus eviction order, not a hard probation cap. If you want the strict cap, the insert path needs changing.
- With `bucket_size = 1` there is no room for both regions. The protected capacity is 0, so probation hits skip promotion and the bucket behaves as a single probationary slot.
- The invariant suite's `baseline_settings()` uses `bucket_size = 3`, which gives 1 probationary and 2 protected slots.
