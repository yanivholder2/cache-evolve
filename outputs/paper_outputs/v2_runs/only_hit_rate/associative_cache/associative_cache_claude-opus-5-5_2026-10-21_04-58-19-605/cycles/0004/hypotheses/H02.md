# H02

Promoting a key to the MRU tail only on its second hit, with its first hit moving it just to the bucket midpoint, will raise v001's hit rate on workload-a above 0.7206 by keeping keys that were hit once from displacing keys that were hit repeatedly.

## Parent

cycle/0003/v001

## Changes

Only `src/associative_cache/associative_cache_bucket.rs` changes. It keeps v001's 1/8 insertion
depth and miss path exactly as they are.

1. Newcomers: on the miss path in `put` (the `midpoint_insert` branch), set
   `item.lfu_counter = 0` before `self.items.insert(idx, item)`. Make `item` a `mut` parameter.
2. Hit path: in `get_from_position`, when `self.midpoint_insert` is true, stop delegating to
   `ClassicLRU::get_from_position`. Implement a two-step promotion in the bucket instead:
   - Remove the item at `position` with `let mut it = self.items.remove(position);`.
   - If `it.lfu_counter == 0` (first hit since insertion), set `it.lfu_counter = 1` and
     reinsert it at `mid = self.items.len() / 2`, which is the midpoint of the remaining items.
   - Otherwise (`lfu_counter >= 1`), keep the counter at 1 and `push` the item to the MRU tail.
   - Return a reference to the item at its new index.
   When `midpoint_insert` is false, keep delegating to the eviction policy exactly as the
   baseline does.
3. Keep the update-existing-key branch in `put`. It calls `get_from_position`, so a value
   update also counts as a hit. Keep eviction at index 0 through the existing
   `evict_item`/`ClassicLRU` path. Do not change the counter on eviction.
4. Invariants: the bucket size never exceeds `max_size`, since a hit only moves an item and never
   adds one. Lookup stays a linear scan. Non-ClassicLRU policies are untouched. Do not edit
   `src/shared/traits/bucket.rs` or the policy trait defaults.

## Rationale (optional)

The cross-cycle insights say frequency failed at the eviction end (cycle 0003 v002) but is
untested on the promotion side. This is a two-segment SLRU inside each bucket. A key that is hit
once lands mid-bucket and must be hit again before it can occupy the protected MRU region. Under
v001, one lucky hit sends a key straight to MRU, where it pushes every established key one slot
toward eviction. Refutation: a hit rate at or below 0.7206 means a single hit already predicts
reuse well on workload-a, and promotion should stay one-step.
