# H03

Giving a newcomer a GCLOCK counter of 1 instead of 0 when its key appears in a small per-bucket ring of recently evicted keys will raise v003's hit rate on workload-a above 0.716 by sparing keys that come back after a short reuse distance from the one-miss filter.

## Parent

cycle/0003/v003

## Changes

Only `src/associative_cache/associative_cache_bucket.rs` changes. Keep everything else from
cycle/0003/v003 as it is: the `clock_mode` gate (ClassicLRU only), `CLOCK_MAX = 3`, saturating
increments in `get_from_position`, `clock_find_victim`, and the in-place `std::mem::replace`
with `self.hand = idx` resting on the newcomer.

1. Add a ghost ring to `AssociativeCacheBucket`. Add `ghosts: [Option<K>; GHOST_LEN]` and
   `ghost_pos: u8`, with `const GHOST_LEN: usize = 4;`, and initialise them to `[None; GHOST_LEN]`
   and `0` in `new`. `K: Copy` already holds.
2. Record evictions only of keys that were never hit. In both GCLOCK eviction sites (the in-place
   replacement in `put` and the `clock_mode` branch of `evict_item`), write `evicted.key` into
   `ghosts[ghost_pos]` and advance `ghost_pos` modulo `GHOST_LEN` (overwriting the oldest
   entry). Because `clock_find_victim` returns only zero-count slots, every victim qualifies.
3. Use a conservative admission rule. In `put`, in the `clock_mode` miss paths (both the full
   bucket in-place branch and the non-full push branch), scan `ghosts` for `item.key` before you
   set the counter. If it is found, set `item.lfu_counter = 1` and clear that ghost entry to
   `None`. Otherwise set `item.lfu_counter = 0`. A returning key therefore survives exactly one
   extra sweep pass, not a full MRU promotion. In the full-bucket branch the hand still rests on
   the newcomer. A ghost-admitted newcomer is decremented to 0 on the next miss and skipped once,
   but gets no more protection than that.
4. Invariants: the bucket size never exceeds `max_size`. The ghost ring is bounded at 4 keys per
   bucket. The sweep still terminates within `CLOCK_MAX * len + 1` steps. Non-ClassicLRU
   policies behave exactly as in the baseline. Lookup of live items is unchanged, and the ghost
   ring is never consulted on `get`.

## Rationale (optional)

v003's one-miss grace window is the most aggressive filter tried so far. It probably loses keys
whose reuse distance is just over one bucket miss. In cycle 0002, MRU-on-ghost-hit hurt because it
handed out full protection. The insights explicitly allow a conservative form, such as a partial
promotion or a small, recent ghost ring, and this hypothesis tests that form on the CLOCK line,
which is the one with the strongest latency case. Refutation: a hit rate at or below 0.716 means
one-shot reuse at short distances is not worth protecting on workload-a. Metadata-size grows by
4 keys per bucket.
