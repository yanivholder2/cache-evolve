# H03

Making v003's newcomer grace adaptive per bucket will raise hit rate on workload-a above 0.731, by parking the hand one slot past the newcomer only while ghost hits outnumber evictions of never-hit newcomers.

## Parent

cycle/0004/v003

## Changes

Only `src/associative_cache/associative_cache_bucket.rs` changes. Keep everything else from
cycle/0004/v003: `GHOST_LEN = 4`, `CLOCK_MAX = 3`, the ghost admission rule (counter 1 on a ghost
hit, the entry consumed), `record_ghost` at both eviction sites, `clock_find_victim`, and the
saturating increments on hit.

1. New per-bucket state: add `grace: u8`, a saturating score in `0..=GRACE_MAX` with
   `const GRACE_MAX: u8 = 15;` and `const GRACE_ON: u8 = 8;`, initialised to `0`. Also add
   `rest: Option<usize>`, the slot index where the most recent newcomer was placed by the
   full-bucket in-place path, initialised to `None`.
2. Positive signal: in `admission_counter`, when a ghost match is found and returns 1, also do
   `self.grace = (self.grace + 1).min(GRACE_MAX)`.
3. Negative signal: in the full-bucket `clock_mode` branch of `put`, after
   `let idx = self.clock_find_victim();` and before the replacement, check whether
   `Some(idx) == self.rest` and `self.items[idx].lfu_counter == 0`. If so, the previous newcomer
   was evicted without being hit, so do `self.grace = self.grace.saturating_sub(1)`. A slot that
   was hit has counter > 0 and is decremented by the sweep instead. To keep the signal sound, set
   `self.rest = None` in `get_from_position` (clock branch) whenever the hit slot equals
   `self.rest`.
4. Adaptive hand placement: after `std::mem::replace` in that branch, set `self.rest = Some(idx)`.
   - If `self.grace >= GRACE_ON`, set `self.hand = (idx + 1) % self.items.len()`. The newcomer
     is now examined last in the next sweep, so it gets roughly one full sweep of grace.
   - Otherwise keep v003's `self.hand = idx`, the strict one-miss filter.
   In `evict_item` (clock branch), set `self.rest = None` after the removal, because indices
   shift.
5. Invariants: the bucket never holds more than `max_size` items. The sweep still terminates
   within `CLOCK_MAX * len + 1` steps. `grace` stays bounded. When `grace < GRACE_ON` the bucket
   behaves exactly like v003, so a bucket starts in v003 behaviour. Non-ClassicLRU policies keep
   baseline behaviour.

## Rationale (optional)

The depth sweep showed that the strict filter peaked: pure LIP lost and 1/8 won. Yet v003 showed
that some keys do deserve more grace. A single fixed grace window is a compromise across buckets
whose reuse behaviour differs. This is a per-bucket, DIP-style duel between a strict filter and a
lenient one, driven by signals already present: ghost hits favour leniency, one-shot evictions
favour strictness. It does not touch ring size (H01) or the LRU line (H02). Refutation: a hit
rate at or below 0.731 means a lenient filter never pays on workload-a even where returners are
frequent, and the strict filter plus ghost admission is already the right shape.
