# H01

Replacing the bucket-index computation on cycle/0009/v002 with a well-mixed single hash (finalised 64-bit mix plus multiply-shift range reduction) will raise hit rate on workload-a above 0.731 by spreading hot LIRS keys more evenly across buckets and cutting conflict misses, while each key still maps to exactly one bucket.

## Parent

cycle/0009/v002

## Changes

This is the only "which bucket" lever the slot-legality invariant still allows. Each key keeps exactly one home bucket, and that bucket is a pure, deterministic function of the key. Nothing else in the CLOCK line changes.

1. **Locate the bucket-index function.** It lives in the `AssociativeCache` container under `src/associative_cache/`, in the get/put/remove code that maps a key to `buckets[idx]`. It is probably a `DefaultHasher` hash followed by `% n_buckets`, or a similar helper. Do NOT edit `associative_cache_jni.rs`, `src/factory.rs`, `src/lib.rs`, `tests/`, `src/test_utils/` or `src/bin/`. If the container exposes a public or `pub(crate)` helper that tests or the invariant checker call to compute a key's bucket (for example `get_bucket_index` or `bucket_for`), change that helper's body in place, not its signature. That way every caller, including the invariant check, sees the new mapping. Any path that computes the index without the helper must be routed through it, so get, put, update and remove can never disagree.
2. **New mapping.** `fn bucket_index(&self, key: &K) -> usize`:
   - Hash the key with the same hasher the container already uses, giving `h: u64`. Keep using the existing hasher so that hash-quality differences come only from the finaliser.
   - Apply the splitmix64/murmur3 finaliser: `h ^= h >> 30; h = h.wrapping_mul(0xbf58_476d_1ce4_e5b9); h ^= h >> 27; h = h.wrapping_mul(0x94d0_49bb_1331_11eb); h ^= h >> 31;`.
   - Reduce with multiply-shift on the HIGH bits: `((h >> 32) * n_buckets as u64) >> 32`, cast to `usize`. This works for any `n_buckets`, power of two or not, and uses bits that are independent of the low bits.
   - If `n_buckets == 1`, return 0.
3. **Decorrelate from the ghost fingerprint.** `ghost_fp` in `associative_cache_bucket.rs` takes the top 16 bits of its own FNV + mix hash. That hasher is different, so there is no direct correlation, but to be safe add a distinct salt to the ghost hasher (`FpHasher::new()` starts from `OFFSET ^ 0x9e37_79b9_7f4a_7c15`). Fingerprints within one bucket must not collapse into a few values. Membership semantics are unchanged.
4. **Keep everything else in cycle/0009/v002 unchanged:** GCLOCK +1 hit step, `CLOCK_MAX = 3`, hand resting on the newcomer, the 4-entry fingerprint ghost ring with consume-on-match, and the compact 24-byte `Item`.
5. **Invariants:** total capacity and per-bucket size are unchanged. Every lookup for a key probes exactly one bucket, the same bucket every time. Non-ClassicLRU policies use the same new index function, which is harmless because it is only a placement function.

## Rationale (optional)

Nine cycles have tuned which slot to evict inside a bucket, and every knob has peaked. Cycle 0009 showed that alternate placement is forbidden. The open question it left is whether a better-mixing single hash, which still passes the invariant, can reduce conflict misses. LIRS-style traces often use sequential or strided integer keys. If the current index uses weakly mixed low bits (for example `DefaultHasher` output `% n`, or worse, an identity-like hash), loops can pile onto a subset of the 128 buckets. Confirmation: hit rate above 0.731. Refutation: hit rate unchanged (±0.001), which would mean the existing index is already well balanced and workload-a's misses at 2048 entries are capacity misses. A drop would mean the old mapping happened to favour the trace.
