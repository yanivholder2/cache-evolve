# H02

Moving the GCLOCK counter out of `Item` into a per-bucket packed 2-bit counter word on cycle/0009/v002 will cut metadata-size per `Item<u64,u64>` from 24 to 16 bytes, while keeping hit rate on workload-a exactly at 0.731.

## Parent

cycle/0009/v002

## Changes

This is a cost-only change (metadata-size). The GCLOCK counter range is 0..=3, so it fits in 2 bits, and a 16-way bucket needs only one `u32` for all of its counters. Any field left in `Item` beyond key and value rounds the item up to 24 bytes because of u64 alignment. The only way to shrink it is to take ALL per-item metadata out of `Item`.

1. **`src/shared/item.rs`:** reduce `Item<K, V>` to `pub key: K, pub value: V`. Remove `lfu_counter`, `stamp`, `LOGICAL_CLOCK` and `next_stamp` from the struct path. Keep `Item::new(key, value)` with the same signature, and update `Display`. If a protected file (`tests/`, `src/bin/`, `src/test_utils/`, JNI) reads `item.lfu_counter` or `item.stamp`, the build will fail. In that case fall back to keeping exactly that one field as-is and still move the GCLOCK counter into the bucket (step 2). Report the fallback in the attempt notes.
2. **`src/associative_cache/associative_cache_bucket.rs` (CLOCK mode):**
   - Add `clock_bits: u32` to `AssociativeCacheBucket`. Slot `i` holds its counter in bits `2i..2i+2`. Add the inline helpers `fn ctr(&self, i) -> u32 { (self.clock_bits >> (2*i)) & 3 }` and `fn set_ctr(&mut self, i, c)`.
   - `get_from_position`: `if ctr(pos) < CLOCK_MAX { set_ctr(pos, c+1) }`.
   - `clock_find_victim`: same sweep, reading and decrementing via `ctr`/`set_ctr`.
   - `put` replace-in-place path: `set_ctr(idx, admission_counter(..))`.
   - Push path: `set_ctr(items.len(), admission)` before pushing.
   - `evict_item`'s `remove_at(idx)`: `Vec::remove` shifts the later items down, so also shift the counter word. Let `low = clock_bits & ((1 << 2*idx) - 1)` (use 0 when `idx == 0`) and `high = (clock_bits >> (2*idx + 2)) << (2*idx)`. Then `clock_bits = low | high`.
   - Add `debug_assert!(max_size <= 16)` in clock mode. If `bucket_size > 16`, use a `u64` (32 slots) or fall back to a `Vec<u8>`. Pick the type from `settings.bucket_size` once in `new`.
   - Behaviour must be bit-for-bit identical to cycle/0009/v002.
3. **Other policies (LFU, TimestampLRU in `src/shared/eviction_policy.rs`):** give the bucket a parallel `meta: Vec<u32>` (counter or logical stamp), allocated only when `!clock_mode`. Keep it in lockstep with `items` in every bucket push, remove and replace. Pass it to the eviction policy by extending the `EvictionPolicy` trait methods in `src/shared/traits/eviction_policy.rs` with a `&mut [u32]` meta argument. Plain LRU ignores it. If this trait change spreads into protected files, keep the old `Item` fields for non-clock policies behind the step-1 fallback instead.
4. Update the in-crate `item_is_compact` test to assert `size_of::<Item<u64,u64>>() == 16`.
5. **Invariants:** the GCLOCK victim sequence and hand placement are identical to the parent, the ghost ring is untouched, and the slot legality of keys is unchanged.

## Rationale (optional)

The leaderboard still shows metadata-size 40 held by baseline. Cycle 0009 brought the item down to 24, but its own insight asks whether more can be removed "since its range is tiny". 24 → 16 bytes is a third of the per-entry footprint, and the replacement costs 4 bytes per bucket. Confirmation: metadata-size reports 16 and hit rate stays exactly 0.731. Any hit-rate change means the counter bookkeeping drifted out of sync with `items`, most likely on the `remove_at` shift path.
