# H01

Inserting new items at the bucket midpoint instead of the MRU tail, while hits still move to the tail, will raise hit rate by evicting one-hit-wonder and scan keys before they push out reused keys.

## Parent

baseline

## Changes

Only `src/associative_cache/associative_cache_bucket.rs` changes. The intra-bucket order stays the same as ClassicLRU: index 0 is the eviction end (LRU) and the tail is the MRU end.

1. Add a field `midpoint_insert: bool` to `AssociativeCacheBucket`. In `new()`, set it to
   `settings.eviction_policy == EvictionPolicyKind::ClassicLRU`. The eval path uses
   ClassicLRU. Other policies keep the exact baseline behaviour.
2. Add a module constant `INSERT_DEPTH_NUM: usize = 1; INSERT_DEPTH_DEN: usize = 2;`
   (i.e. insert at the midpoint). Later cycles can tune the fraction from one place.
3. Override the trait-default `put` in `impl Bucket for AssociativeCacheBucket`:
   - If the key already exists, keep the baseline behaviour exactly: update the value, then
     call `self.get_from_position(position)` so it moves to the tail, and return `(ref, None)`.
   - If `!midpoint_insert`, use the baseline miss path (evict if full, push to tail).
   - Otherwise: if the bucket is full, evict via `self.evict_item()` (index 0, as before).
     Then compute `idx = self.items.len() * INSERT_DEPTH_NUM / INSERT_DEPTH_DEN`. That is
     `len/2`, computed after the eviction. Call `self.items.insert(idx, item)` and return
     `(&self.items[idx], evicted)`.
4. Leave `get_from_position` unchanged. A hit still calls `ClassicLRU::get_from_position`
   (remove + push to tail), so a key that is reused once gets the full MRU protection.

Invariants to preserve: the capacity check runs before the insert, so size never exceeds `max_size` (P1). The bucket only ever receives keys routed to it by the cache, so P2 holds. Lookups are still a linear key scan, so P3 holds. Geometry is untouched (P4). Do not edit `src/shared/traits/bucket.rs` defaults: the trait tests use their own `TestBucket` and must keep passing.

## Rationale (optional)

At 2048 slots / 128 buckets each bucket holds 16 items. With pure MRU insertion, a burst of never-reused keys hashing to one bucket can flush the whole bucket. Midpoint insertion (LIP/BIP-style) gives a new key about half the bucket's lifetime to prove itself. To confirm or refute, compare the hit rate on workload-a against 0.6611. Per-op time should stay close to baseline because insertion still costs one Vec shift.
