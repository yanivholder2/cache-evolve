# H01

Giving each key two candidate buckets (two-choice skewed placement) on top of cycle/0007/v001, and inserting each newcomer into whichever candidate offers the colder victim, will raise hit rate on workload-a above 0.731 by removing conflict misses that no per-bucket replacement rule can fix.

## Parent

cycle/0007/v001

## Changes

This is a cache-level change. It is gated on ClassicLRU (the same `clock_mode` condition the bucket already uses), so every other policy keeps the baseline single-bucket behaviour exactly. Files: the cache container that maps keys to buckets (the `AssociativeCache` get/put/remove implementation under `src/associative_cache/`, but NOT the protected `associative_cache_jni.rs`), and `src/associative_cache/associative_cache_bucket.rs`.

1. **Second index.** Keep the existing bucket-index computation as `b1`. Add a private `fn alt_bucket(key, b1, n_buckets) -> usize`. Hash the key with the bucket file's FNV-1a + 64-bit mix (make `FpHasher` / the mix reusable via a `pub(crate)` helper that returns the full mixed `u64`). Take bits 16..32 of the mixed value (not the top 16 bits, which the ghost fingerprint uses, and not the low bits used for `b1`) `% n_buckets`. If the result equals `b1`, use `(b1 + 1) % n_buckets`. Because `b2` is a pure function of the key, lookup is deterministic. If `n_buckets == 1`, skip all of this and use single-bucket behaviour.
2. **get.** Probe `b1` first, then `b2` only if `b1` misses. A hit in either bucket calls that bucket's `get_from_position` as now (in-place +1, ceiling 3).
3. **put / update.** First look the key up in both buckets. If it is present in either, update it in place (existing update path). Invariant: a key lives in at most one bucket.
4. **put / miss: choose the target bucket.**
   - If exactly one candidate is not full, insert there. If both are not full, use `b1`.
   - If both are full, ask each bucket for a read-only `victim_score(&self) -> usize`, a new inherent method on `AssociativeCacheBucket`. It returns 0 if the item at `self.hand` (after wrapping `hand` into range) has `lfu_counter == 0`, meaning an unproven newcomer is the immediate victim. Otherwise it returns `1 + sum of all lfu_counter` in the bucket. Insert into the bucket with the lower score. On a tie, use `b1`.
5. **Ghost check across both candidates.** Before the eviction, compute the fingerprint once and test both buckets' ghost rings (add a `pub(crate) fn take_ghost(&mut self, fp: u16) -> bool` that consumes a match). If either ring matches, the newcomer is admitted with counter 1. Refactor `put` so the cache can pass in the precomputed admission counter (e.g. a `put_with_counter(item, counter)` inherent method used by the cache in two-choice mode). The normal `Bucket::put` keeps calling `admission_counter` itself. Evicted keys are still recorded in the ghost ring of the bucket that evicted them.
6. **remove/delete** (if the cache exposes one): try `b1`, then `b2`.
7. Keep the rest of cycle/0007/v001 unchanged: `CLOCK_MAX = 3`, the 4-entry 16-bit fingerprint ring, consume-on-match, `clock_find_victim`, the hand resting on the newcomer, and both eviction sites recording ghosts.
8. **Invariants:** total capacity is unchanged (same number of buckets, each holding at most 16 items). No key is ever resident in both buckets. Non-ClassicLRU policies never compute `b2`.

## Rationale (optional)

Eight cycles have tuned *which slot* to evict inside a fixed 16-way bucket, and every knob there now peaks at its current setting. One lever has never been touched: *which bucket* a key may live in. A LIRS trace with hot loops can overload some of the 128 buckets while others hold cold newcomers. Two-choice placement lets a newcomer displace the colder of two candidate victims, and in the well-known result, the effective associativity approaches that of a much larger set. This is a different strategy from every prior cycle, not another single-knob probe. Refutation: hit rate at or below 0.731 would mean workload-a's misses at 2048 entries are capacity misses rather than conflict misses, and per-bucket placement is not a bottleneck. The cost is an extra bucket probe on misses only, which per-op-time should show once it is recorded.
