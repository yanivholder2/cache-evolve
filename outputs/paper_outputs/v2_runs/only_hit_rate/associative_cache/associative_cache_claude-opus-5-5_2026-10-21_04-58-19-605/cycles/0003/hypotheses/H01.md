# H01

Moving v001's insertion point for new keys from 1/4 to 1/8 of the bucket length from the eviction end will raise hit rate on workload-a above 0.7139 by evicting keys that are used only once even sooner.

## Parent

cycle/0002/v001

## Changes

Only `src/associative_cache/associative_cache_bucket.rs` changes. Everything else stays exactly as in cycle/0002/v001.

1. Change the module constants to `INSERT_DEPTH_NUM: usize = 1; INSERT_DEPTH_DEN: usize = 8;`
   and update the doc comment to match. In `put`, the miss path still computes
   `idx = self.items.len() * INSERT_DEPTH_NUM / INSERT_DEPTH_DEN` after the eviction. With a
   full 16-slot bucket, len = 15 after the eviction, so new keys now go to index 1 instead of
   index 3. Update the inline comment ("len = 15 here, so idx = 1").
2. Keep the hit path unchanged: `get_from_position` still delegates to
   `ClassicLRU::get_from_position`, which removes the key and pushes it to the MRU tail.
3. Keep the update-existing-key branch, the `midpoint_insert` gate (ClassicLRU only), and the
   rule that the capacity check runs before the insert. Bucket size never exceeds `max_size`,
   lookup is still a linear scan, and geometry is unchanged.
4. Do not touch the trait defaults in `src/shared/traits/bucket.rs`.

## Rationale (optional)

Hit rate went up from the midpoint (0.695) to 1/4 (0.7139), so the best depth lies at 1/4 or
deeper. 1/8 gives a newcomer about 2 misses in its bucket to prove reuse, but still not zero.
This brackets the optimum. If hit rate is above 0.7139, the trend continues and pure LIP
(index 0) is worth testing next. If it is at or below 0.7139, the peak lies between 1/8 and 1/4,
and keys with short reuse distances are being lost. Each `Vec::insert` at index 1 shifts about
14 elements, so record per-op-time.
