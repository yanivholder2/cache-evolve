# H01

Moving v001's insertion point for new keys from the bucket midpoint (1/2) to a quarter of the way up from the eviction end (1/4) will raise hit rate on workload-a by evicting keys that are used only once even sooner.

## Parent

cycle/0001/v001

## Changes

Only `src/associative_cache/associative_cache_bucket.rs` changes. Everything else stays exactly as in v001.

1. Change the module constants to `INSERT_DEPTH_NUM: usize = 1; INSERT_DEPTH_DEN: usize = 4;`.
   In `put`, the existing miss path computes `idx = self.items.len() * INSERT_DEPTH_NUM / INSERT_DEPTH_DEN`
   after eviction. With a full 16-slot bucket, len = 15 after the eviction, so new keys go to
   index 3 instead of index 7.
2. Keep the hit path exactly as it is: `get_from_position` still delegates to
   `ClassicLRU::get_from_position`, which does remove + push to the tail. A key gets full MRU
   protection on its first re-reference.
3. Keep the update-existing-key branch, the `midpoint_insert` gate (ClassicLRU only), and the
   rule that the capacity check runs before the insert. Bucket size still never exceeds
   `max_size`. Lookup is still a linear scan. Geometry is unchanged.
4. Do not touch the `Bucket` trait defaults in `src/shared/traits/bucket.rs`.

## Rationale (optional)

v001 showed that insertion position, not eviction order, limits the baseline. Insertion depth is
the knob v001's insight flagged. 1/4 sits between v001 (1/2) and pure LIP (index 0). It halves the
time a new key that is never reused stays resident, but it still gives a new key a few misses'
worth of grace before eviction, so keys with short re-reference distances are not lost. To
confirm, check that hit rate is above 0.695. To refute, hit rate at or below 0.695 means the
midpoint is already at or past the optimum depth. There is a cost: `Vec::insert` at index 3
shifts about 12 elements instead of about 8. Per-op-time should be recorded, and a small
regression on misses is expected.
