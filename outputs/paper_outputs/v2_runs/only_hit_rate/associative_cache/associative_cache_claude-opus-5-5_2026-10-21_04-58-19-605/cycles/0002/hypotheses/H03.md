# H03

Replacing v002's single CLOCK reference bit with a saturating 2-bit frequency counter (GCLOCK: increment on hit, capped at 3; decrement on each hand pass) will raise hit rate above v001's 0.695, because frequently reused keys survive several sweeps.

## Parent

cycle/0001/v002

## Changes

Only `src/associative_cache/associative_cache_bucket.rs` changes. Keep v002's structure: the `clock_mode` gate (ClassicLRU only), the per-bucket `hand`, in-place victim replacement with `std::mem::replace`, and no `Vec` shifting.

1. Add the constant `CLOCK_MAX: usize = 3`. Keep using `Item::lfu_counter` as the counter, so
   per-item metadata does not grow. If the field's type is not `usize` in this tree, cast the
   constant to that type.
2. `get_from_position` in `clock_mode`: replace `lfu_counter = 1` with
   `if c < CLOCK_MAX { lfu_counter = c + 1 }`, a saturating increment. Return the item in place, as now.
3. `clock_find_victim`: change the test from `== 1` to `> 0`. If the slot's counter is greater
   than 0, decrement it by 1 and advance the hand (wrapping at `len`). Otherwise return
   `self.hand`. This still terminates: each full pass lowers every counter by 1, so the loop ends
   within `CLOCK_MAX * len + 1` steps.
4. Miss path in `put`: new items still enter with `lfu_counter = 0`. The filter for keys used only
   once is the same as v002's. Update-existing-key: update the value and call
   `get_from_position`, which increments the counter.
5. `evict_item` in `clock_mode` keeps using `clock_find_victim` and then
   `remove_at(idx)` / clamps the hand, as now.

Invariants: in-place replacement means size never exceeds `max_size`. Lookup is still the
`get_position` linear scan. Geometry is unchanged. Non-ClassicLRU policies behave exactly as in
the baseline. The trait-default tests in `src/shared/traits/bucket.rs` use `TestBucket` and are
unaffected.

## Rationale (optional)

v002's 1-bit CLOCK cannot tell a key hit once since the last sweep from one hit 50 times. Both get
exactly one second chance. On workload-a, which is evaluated as a LIRS trace, a small hot set is
mixed with a long tail. A 2-bit GCLOCK gives the hot set up to 3 extra sweeps of protection and
still evicts zero-count newcomers first. This tests a different open question from the other two
hypotheses: whether frequency information inside the bucket adds anything beyond the
low-protection-on-insert effect. To confirm, check that hit rate is above 0.695 (v001) and above
0.6706 (v002). If hit rate lands at or below 0.6706, frequency does not help on this trace.
Hits stay a single store and Item size is unchanged, so per-op-time and metadata-size should match v002.
