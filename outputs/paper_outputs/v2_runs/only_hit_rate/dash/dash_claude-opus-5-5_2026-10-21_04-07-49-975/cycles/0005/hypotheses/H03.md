# H03

Add a per-segment ghost fingerprint table that covers about one cache's worth of stash evictions, where a ghost hit makes a returning fresh key enter the stash at the MRU end instead of the BIP LRU end, to raise hit-rate for keys with long reuse distances.

## Parent

cycle/0004/v003

## Changes

Cycle 0004 v001's ghost attempt failed because its window was per-bucket and tiny, and because a ghost hit only pre-credited the counter. This hypothesis changes both and applies them on top of v003's BIP insertion:

1. Add a per-segment ghost table: a fixed array `ghost: [u16; GHOST_SLOTS]` of 16-bit key fingerprints, direct-mapped by a secondary hash of the key (use different hash bits from those used for bucket selection). Size `GHOST_SLOTS` so that, summed over all segments, the table holds roughly as many entries as the cache holds items, i.e. about the segment's total slot count (normal + stash) rounded to a power of two. A fingerprint of 0 means empty; map any computed fingerprint of 0 to 1.
2. On every eviction **out of the stash** (the victim chosen by `stash_put`'s second-chance scan, i.e. the key leaves the cache completely), write the victim's fingerprint into `ghost[h2(key) & (GHOST_SLOTS-1)]`, overwriting any existing entry. Direct-mapped overwrite is the aging mechanism, so no other clock or reset is needed.
3. In the fresh-key insert path of `DashSegment::put`, before the BIP decision, check the ghost slot for this key. On a fingerprint match, clear the slot and insert the key at the stash **MRU end** with counter 0, overriding BIP. Do not pre-credit the counter: the lesson from 0004 is that placement, not counter, is the lever. On no match, use v003's BIP decision unchanged.
4. Demoted ex-residents, the second-chance scan, `PROMOTE_THRESHOLD`, normal-tier landing and cascades are unchanged.

Invariants: ghost lookups and writes must not allocate. Report the added metadata (2 bytes × `GHOST_SLOTS` per segment) explicitly so the metadata-size dimension can see it. False-positive matches only cause an MRU insert, so they are safe.

## Rationale (optional)

BIP sends a key returning after a long reuse distance to the probation slot every time, so it can never prove itself. A ghost window about the size of the cache identifies exactly those keys. Giving them the MRU (protected) position lets them survive long enough to collect a stash hit, while one-touch scan keys, which never appear in the ghost table, still churn through probation. This answers the cycle-0004 open question about ghosts with a cache-size window that act on placement.
