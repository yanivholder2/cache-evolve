# H02

Give a key that is admitted on a ghost hit one free pass through the stash's second-chance scan, so it is not aged out before its first reuse, raising hit-rate.

## Parent

cycle/0005/v003

## Changes

Keep v003's ghost table size, fingerprinting, write-on-stash-eviction and BIP-on-miss exactly as they are. Change only how a key admitted on a ghost hit is treated by the stash victim scan:

1. In the fresh-key insert path of `DashSegment::put`, on a ghost fingerprint match (where v003 currently inserts at the stash MRU end with counter 0), also set that slot's second-chance / reference marker, the same bit or field the CLOCK-like scan in `stash_put` checks and clears. That way, the first time the scan reaches the slot it clears the marker and skips it rather than evicting it. If the scan has no separate reference bit and keys only on counter == 0, add a 1-bit "ghost-protected" flag to the stash slot metadata, using a spare bit in an existing per-slot byte if one exists. The scan treats a set flag as "skip once, then clear".
2. Do not raise the promotion counter. `PROMOTE_THRESHOLD` progress for these keys stays at 0, which follows the lesson that counter credit is not the lever. The protection only affects whether the key is chosen as a victim.
3. The protection is one-shot. Once the flag is cleared, the key ages like any other stash resident. A stash hit clears it as well.
4. Bound the scan. If every candidate in the bucket is protected or credited, fall back to the scan's existing fallback victim so `stash_put` always terminates.
5. Demoted ex-residents, BIP fresh-key insertion, normal-tier logic and cascades are unchanged.

Invariants: no allocation, and scan termination is guaranteed. Report any added per-slot bit in the metadata notes.

## Rationale (optional)

The other cycle 0005 open question was whether a ghost hit should also protect the key from the next scan pass. MRU placement alone may still lose a ghost-admitted key with counter 0 to the second-chance scan when stash pressure is high. This change targets the survival of keys that already have evidence of reuse, and leaves the window size alone, so it is distinct from H01.
