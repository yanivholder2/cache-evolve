# H01

Quadruple the per-segment ghost table to about four caches' worth of stash-eviction fingerprints so more long-reuse-distance fresh keys get ghost-guided MRU stash placement, raising hit-rate.

## Parent

cycle/0005/v003

## Changes

Change only the ghost window size of v003. Everything else stays as it is: what the ghost does on a hit (MRU stash insert, counter 0, slot cleared), BIP on a ghost miss, the second-chance scan, `PROMOTE_THRESHOLD`, demoted-ex-resident MRU re-entry, normal-tier landing and cascades.

1. Set the ghost table's `GHOST_SLOTS` constant to 4× its current value. It must stay a power of two so that `h2(key) & (GHOST_SLOTS-1)` indexing still works. If `GHOST_SLOTS` is derived from the segment's slot count, multiply the derived value by 4. The table remains a fixed-size inline array (`[u16; GHOST_SLOTS]`) with no heap allocation on lookup or write.
2. Keep the direct-mapped overwrite on stash eviction as the aging mechanism. A larger table makes collisions between still-relevant fingerprints rarer, so the effective window grows from well under one cache to roughly four.
3. Keep 16-bit fingerprints. The false-positive rate per lookup stays about 1/65536 per occupied slot. A false positive only causes an MRU insert, so it is safe.
4. Update any metadata accounting or comments to report 2 bytes × `GHOST_SLOTS` per segment, which is now 4× larger.

Expected outcome: if hit-rate rises, a meaningful share of the remaining misses have reuse distances between one and four caches. If it stays flat, those misses are mostly true one-touch keys and the ghost lever is saturated.

## Rationale (optional)

The cycle 0005 open question was whether a larger ghost window recovers more long-reuse misses. A direct-mapped table sized to one cache keeps far fewer than one cache's worth of distinct evictions, because collisions overwrite live entries. This change tests the window size and nothing else, and it takes no capacity from the protected ex-resident region.
