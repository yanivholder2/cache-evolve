# H03

Inserting fresh keys into the stash bimodally, at the LRU end except for 1 in 16 at the MRU end, will raise hit-rate by making the stash resistant to the loop and scan patterns in the LIRS trace.

## Parent

cycle/0003/v002

## Changes

All edits are in `src/dash/segments/dash_segment.rs`. This changes only where *fresh* keys (from `DashSegment::put`) land in the stash. It applies BIP (bimodal insertion) from Qureshi et al. to the stash. Demoted ex-residents keep landing at MRU through `DEMOTE_TO_STASH_POS = Back`.

1. Add a field `bip_tick: u32` to `DashSegment`, initialised to 0 in `try_new`.
2. In `DashSegment::put`, increment `bip_tick` with wrapping arithmetic. If `bip_tick % BIP_PERIOD == 0` (`BIP_PERIOD = 16`), call `stash_put(core, InsertPosition::Back, item)`, as today. Otherwise call `stash_put(core, InsertPosition::Front, item)`, which places the fresh key at the LRU end.
3. Victim interaction: v002's second-chance scan in `stash_put` picks the victim *before* the new item is inserted, so the incoming key itself is never the victim. A Front-inserted fresh key with counter 0 becomes the first candidate on the *next* insert into that stash bucket, unless a hit refreshes it first. A hit on a fresh key raises its counter to 1, and ClassicLRU's touch moves it toward MRU, so one reuse is enough to escape. Do not change the scan.
4. Keep `PROMOTE_THRESHOLD = 2`, the demotion pre-credits and `DEMOTE_TO_STASH_POS = Back`, and leave all normal-tier logic unchanged.
5. Tests: `put_goes_to_stash` still passes. Add one test: fill a stash bucket, `put` a new key with `bip_tick` set so the Front path is taken, and assert that it sits at index 0. Add another test showing that the 16th put lands at the MRU end. If the stash bucket is already full, `stash_put` removes the victim before `put_at`, so the Front insert must not evict anything further. Keep the existing double-eviction `debug_assert`.

Invariants: there is no new per-item metadata, and only one `u32` per segment. Capacity and uniqueness are unchanged, because all inserts still go through `stash_put`/`put_at`.

## Rationale (optional)

LIRS-style traces contain loops and one-touch scans longer than the cache. Under MRU insertion of fresh keys, those keys push out partially proven keys and pre-credited ex-residents. BIP keeps most one-touch keys at the bottom of the stash, where they are evicted first, while a small fraction still enters at MRU, so a working set that changes is still learned. This is insertion position for fresh stash keys, a lever not tested before. The placement failures in 0001 were about normal-tier landing, which is coupled to the probing bar. Stash position has no such coupling. The change is also distinct from H01 (history-based pre-credit) and H02 (a comparative bar at the promotion edge).
