# H02

Tracking per-bucket occupancy incrementally in the baseline eviction path should lower per-op-time while leaving hit-rate exactly at the baseline value.

## Parent

baseline

## Changes

Change only how `evict_one()` determines bucket fullness and free-slot presence; the victim choice must stay identical to baseline on every access.

- Add a per-bucket occupancy counter (a `u8` or `u16` array indexed by bucket id) to the cache struct, initialised to zero at construction.
- Increment the counter when a slot transitions from empty to occupied, and decrement it when a slot is vacated. Update these in every place that writes or clears a slot: insert, promotion, demotion, eviction, and any removal path. Find these by searching the baseline for slot writes.
- In `evict_one()` and any helper that currently scans a bucket's slots to count occupied entries or test for a free slot, replace the scan with a read of the counter. Keep the scan-based result as a `debug_assert_eq!` check so the invariant is verified in debug builds.
- Do not change the order in which candidate victims are considered, the tie-breaking rule, or any promotion or landing decision.
- Preserve all public function signatures and the on-disk or in-memory entry layout.

Expected result: hit-rate identical to baseline (0.663 on LIRS workload-a at size 2048). Record per-op-time; the claim is confirmed if per-op-time drops below the baseline value of 183 with hit-rate unchanged.

## Rationale (optional)

Every cycle so far has measured hit-rate only, and per-op-time has never been recorded. Cycle 0004 asked for the cost side to be measured. This hypothesis is a pure efficiency change with a strict equivalence requirement, so it isolates the cost of the eviction path from any hit-rate effect and gives the leaderboard a real per-op-time reference for the other lineages.
