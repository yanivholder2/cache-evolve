# H03

Storing the seen-in-stash marker in an existing slot tag bit instead of a new entry field keeps metadata-size at the baseline's 40 while holding the second-hit filter's hit-rate.

## Parent

cycle/0002/v002

## Changes

Start from cycle/0002/v002, which adds a one-bit "seen in stash" marker to each stash entry. Keep its admission behaviour exactly: the first stash hit sets the marker and returns without promotion, and a later hit calls `promotion_get` with the default `InsertPosition::Front`. Change only where the marker is stored. Do not add a field to the entry struct. Instead, use an unused bit in the entry's existing tag or fingerprint field, or in the slot-occupancy bitmap if the stash keeps one, so that the entry's size is unchanged. Add accessor helpers that set, clear, and read the bit, and route every marker access through them. Clear the bit when an item leaves the stash, as before. Do not change the probing-tier logic, `promotion_get`'s signature, or the demotion path. If no spare bit exists in those fields, make no change and record that in the variant's insight.

## Rationale (optional)

Cycle 0002 left metadata-size unmeasured, and the leaderboard lists 40 as the best value held by baseline. The marker is the only place where cycle 0002's variant could add to entry size, so whether the filter costs metadata is the open question. This hypothesis holds the admission rule fixed and moves the storage, so any change in metadata-size is attributable to the storage choice and any change in hit-rate to the marker's placement. It is a cost-side test, and it should be measured on hit-rate and metadata-size together.
