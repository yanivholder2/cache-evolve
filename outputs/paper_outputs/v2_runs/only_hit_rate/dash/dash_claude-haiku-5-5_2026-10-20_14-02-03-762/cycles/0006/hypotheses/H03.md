# H03

Maintaining a per-bucket occupancy counter so victim search reads a stored count instead of scanning slots will reduce per-op-time relative to baseline without moving hit-rate.

## Parent

baseline

## Changes

Add a per-bucket occupancy counter to the normal and stash tier bucket structures, updated on every insert, remove, promotion, and demotion. Use it in victim search so the code does not scan every slot of a bucket to count occupied slots.

- Add an integer field per bucket that holds the count of occupied slots. Initialise it to 0 when the bucket is created.
- Increment it wherever a slot becomes occupied and decrement it wherever a slot is freed. This must cover insert, eviction in `evict_one()`, stash promotion, and probing-to-normal demotion.
- In `evict_one()` and in any helper that checks whether a target bucket is full, replace the slot-scan count with a read of the counter. Keep the scan-based result available under a debug assertion so the counter can be checked against it in tests.
- Victim choice must be identical to baseline. Keep the same candidate ordering and tie-breaking. Only the cost of determining fullness changes.
- Do not change the eviction policy, promotion rules, or the probing tier. Hit-rate must match baseline exactly on every measured trace.

## Rationale (optional)

Cycle 5's occupancy-counter variant matched its parent's hit-rate exactly, which confirms the counter is hit-rate-neutral, but its speedup was never measured because per-op-time was not recorded. This hypothesis starts from baseline and makes per-op-time the target dimension, so the measured result answers the open question directly. Metadata-size should be recorded too, since the counter adds one integer per bucket.
