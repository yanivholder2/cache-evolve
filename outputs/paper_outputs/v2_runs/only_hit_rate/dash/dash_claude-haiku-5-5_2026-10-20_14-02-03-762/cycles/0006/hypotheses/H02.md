# H02

Short-circuiting the seen-in-stash check so it runs only on stash hits will reduce per-op-time of cycle/0004/v001 while leaving hit-rate exactly unchanged.

## Parent

cycle/0004/v001

## Changes

Keep v001's promotion behaviour and landing logic exactly as they are. Change only the evaluation order in the promotion gate so cheap checks run first and the marker read is skipped when it cannot change the outcome.

- In the promotion-gate function that v001 modifies, compute the stash occupancy comparison (threshold 0.75) first. When occupancy is below the threshold, return the first-hit promotion result immediately, without reading the seen-in-stash marker.
- Read the seen-in-stash marker only on the path where occupancy is at or above the threshold, which is the only path where v001's gate uses it.
- In the lookup path, avoid recomputing the target bucket's occupancy if it has already been computed for the same access. Reuse the value.
- Do not change any state transition, eviction order, or marker write. The hit-rate on every trace must match v001 exactly. If it does not, the change is wrong and the variant should be rejected.

## Rationale (optional)

The ledger shows that per-op-time and metadata-size have never been measured in any cycle 1 through 5, so the cost side of the marker and occupancy work is unknown. This hypothesis isolates a pure cost change with a zero hit-rate budget, which makes its result easy to read: any hit-rate movement indicates a bug, and any per-op-time gain is the claim.
