# H02

Skipping the reuse-counter write on hits to entries whose counter is already saturated should cut per-op-time while leaving hit-rate exactly equal to its parent.

## Parent

cycle/0007/v002

## Changes

Start from the cycle/0007/v002 overlay. On a hit to a resident entry, if its 2-bit reuse counter already holds the saturated value, skip the counter store (and any dependent metadata write that exists only to update that counter). The read needed to test saturation stays on the hit path; only the redundant write is removed.

Invariants to preserve:

- Every eviction, promotion, demotion, and landing decision must produce the same outcome as the parent for every access sequence. A saturated counter stays saturated on a further increment, so skipping the write is behaviour-preserving; the implementer should confirm no other reader depends on the write (for example a last-touch field updated in the same branch).
- Do not change the halve-on-demotion reset, the second-hit gate, MRU landing, or the occupancy branch.
- Do not add any new per-entry field.

Expected result: hit-rate identical to cycle/0007/v002 on the measured trace; per-op-time is the dimension to check against the baseline value of 183. If hit-rate differs at all, the change is not equivalence-preserving and the implementer should report it instead of tuning further.

## Rationale (optional)

No variant has ever recorded per-op-time, and the leaderboard still lists the baseline as holding the per-op-time best. This hypothesis targets that dimension with a change that is designed to be neutral on hit-rate, so it can be judged purely on cost.
