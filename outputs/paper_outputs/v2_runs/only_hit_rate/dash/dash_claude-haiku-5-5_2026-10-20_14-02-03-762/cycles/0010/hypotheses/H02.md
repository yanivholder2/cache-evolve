# H02

Folding the one-bit seen-in-stash marker into the spare bits of each existing slot record, rather than a separate per-item field, will cut metadata-size below the baseline value of 40 while leaving hit-rate within tolerance of the baseline.

## Parent

baseline

## Changes

Find where the baseline stores its per-item re-reference state (the seen-in-stash marker and, if present, the reuse counter) and where the per-slot record is laid out. If the record has padding or unused bits after the key and value fields, place the marker in those bits instead of in a separate field or array, and update every read and write of the marker to go through the new location. Do not change when the marker is set or cleared, and do not change any promotion, landing, or eviction decision.

If the baseline has no spare bits, the variant may instead narrow the reuse counter to the smallest width that still represents the saturation threshold the baseline uses, provided the saturation behaviour is unchanged for every value the counter can reach.

Keep the public interface and the gate-integrity surface untouched. Verify that the derived slot size and the total capacity accounting still match the size-2048 budget.

Expected outcome to test: metadata-size falls below 40, and the hit-rate matches the baseline exactly, since no decision changes. Any hit-rate difference points to an unintended change in the marker's semantics.
