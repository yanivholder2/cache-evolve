# H03

Choosing the eviction victim as the least-hit of the four least-recent entries should raise hit-rate on workload-a at size 2048 by protecting re-referenced keys near the tail.

## Parent

cycle/0004/v001

## Changes

Keep the parent's hit-path key lookup collapse as is. Change only the victim selection in the eviction routine (the function that removes the tail entry when the cache is full): instead of always evicting the tail entry, examine the last four entries of the recency list from the tail and evict the one with the fewest recorded hits, breaking ties toward the tail. Add a small per-entry hit counter, incremented on each hit and reset to zero on insertion. Do not change the move-to-front rule on hits, the insertion position of new keys, or the recency order of the remaining entries. The victim is removed from the list in the normal way, so the list structure and head/tail invariants stay intact. Window size four is a fixed constant; expose it as a named constant so later cycles can vary it.

## Rationale (optional)

Every earlier eviction-order change in this lineage (segmentation, second-chance, second-hit promotion, stacked tail insertion) lowered or failed to move hit-rate, but none of them looked at access frequency. No non-LRU or frequency-aware policy has been evaluated yet. Restricting the choice to a four-entry tail window keeps the policy close to LRU, so the change is a bounded test of frequency awareness. The per-entry counter adds metadata, so the size cost is a known risk to record, not a settled gain.
