# H01

Adding a probation/protected segmentation of the recency list to the cycle/0002/v002 incumbent, with victims taken from probation first, raises hit-rate above 0.7348 on workload-a at size 2048.

## Parent

cycle/0002/v002

## Changes

Keep v002's sentinel-index node layout, key index, capacity accounting, and return values exactly as they are. Split the single recency list into two segments: a probation list and a protected list. Add one segment flag per node (or reuse a spare bit if the layout has one) and a second head/tail pair for the protected list. Confirm the existing list head/tail field names and the get/promote and evict function names against v002's overlay before editing, since they may differ from baseline.

Apply these rules:

- On a miss, insert the new node at the MRU end of probation.
- On a hit to a node in probation, move it to the MRU end of protected. If protected now holds more than 80 percent of capacity, demote its LRU node to the MRU end of probation.
- On a hit to a node in protected, move it to the MRU end of protected, as the current promotion code does.
- In the eviction path, evict the LRU node of probation when probation is non-empty, and fall back to the LRU node of protected otherwise.

Do not add a ghost list or any admission filter. Do not change the key index or the public operations' return values on hit, miss, or absent keys. Report the hit-rate delta against 0.7348 and the per-op time and metadata-size delta against v002.

## Rationale (optional)

Cycle 0004 v003 showed that segmenting the baseline list lifts hit-rate on workload-a from 0.665 to 0.7241, so the segmentation is the only hit-rate-moving mechanism seen so far. Its gain is not yet tested on top of the stronger incumbent. Scan keys that are never re-hit should push out only probation entries, leaving the re-referenced set that v002 already keeps intact.
