# H03

Inserting new keys at a midpoint of the recency list, about three-eighths of the way from the LRU end, will raise workload-a hit-rate at size 2048 over baseline by keeping one-time scan keys out of the hot head without giving them the zero-protection of tail insertion.

## Parent

baseline

## Changes

Add a single midpoint marker to the recency list, tracked by a node reference or index. Newly inserted keys (cache misses that fill a slot) are linked at the marker position instead of at the MRU head. Existing keys that hit still move to the MRU head as in the baseline.

Maintain the marker in O(1) per operation: after each insert, advance the marker one node toward the MRU end whenever the list length has grown past the target fraction of capacity; after each eviction, step it back toward the LRU end when the list shrinks below the target. The target is three-eighths of the current capacity, as a named constant.

Keep eviction order exactly as in the baseline: victims are still taken from the LRU end. The change is only where a newly inserted key starts its life in the list. Do not add a second list, a ghost set, or any counters, and do not change the key index.

Record in the insight whether any insertion landed at or near the marker for the first time, so a flat result can be checked for engagement.

## Rationale (optional)

Cycle 0005 and cycle 0006 gave conflicting results for tail insertion, which places new keys at the LRU end with zero protection. Cycle 0007's null on the same change was not checked for engagement. A midpoint insertion point is a different point on that same axis. It is the scan-resistance idea used in some production caches, and it differs from the segmented probation/protected list tried in cycle 0005 because there is only one list and no protected cap.
