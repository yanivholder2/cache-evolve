# H02

Counting only uncorrelated re-references as frequency, rather than every hit, will make the incumbent's least-hit tail eviction protect genuinely re-used keys instead of keys that were merely touched in a burst.

## Parent

cycle/0007/v003

## Changes

In the incumbent's hit-count update (the code that increments the per-entry hit counter on a lookup hit), add a correlated-reference filter. Record for each entry the access sequence number of its most recent counted hit. On a hit, increment the counter only if the gap since that last counted hit is at least K accesses to the cache, where K is a named constant (start at 16). Otherwise leave the counter unchanged. The first hit on an entry always counts.

Leave the recency update on every hit exactly as in the parent: the entry still moves to the MRU position regardless of whether its counter was incremented. The victim scan over the four-entry tail window is unchanged; only the values it reads differ.

Store the sequence number in the entry's existing record if it fits the current layout; if it does not, store it as a 32-bit value and note the extra bytes per entry in the variant's insight. No new lists, no admission checks, no changes to the lookup path's structure.

## Rationale (optional)

The incumbent's frequency signal is a raw hit count, so one burst of repeated lookups to a key can make it look hot the same way a steady re-use pattern does. The cycle 0008 insight reports that counter-based changes have so far been flat or slightly down, and it does not separate burst hits from re-use. Filtering correlated hits is a different change: it alters what the counter means, not how big it is or how it decays.
