# H02

Short-circuiting `get()` and the existing-key path of `put()` when the hit node is already the MRU tail will lower get p50 per-op time below the baseline 41 ns on the lirs workload-a trace at size 2048 while leaving hit rate unchanged.

## Parent

baseline

## Changes

Add a fast path that skips the unlink/re-link work when the hit node is already the most-recently-used entry, since relinking a tail node to the tail is a no-op on the list structure.

- In `get()`, after `let &idx = self.map.get(key)?;`, add `if Some(idx) == self.tail { return Some(&self.nodes[idx].value); }` before the `unlink`/`push_back` calls.
- In the `put()` existing-key branch, after `self.nodes[idx].value = value;`, return early when `Some(idx) == self.tail`, skipping `unlink`/`push_back`.
- Leave the new-key insertion and eviction path in `put()` byte-for-byte unchanged.
- Do not add fields to `Node` or `LruCache`; the metadata-size dimension must stay at baseline.
- Keep all public signatures and the `framework::Cache` impl as they are.

Invariant to preserve: eviction order is unchanged, because a tail node is already in the correct position. The hit-rate summary must therefore remain exactly 0.6652 on the lirs trace. Any change in hit rate indicates a bug in the fast path, not a tradeoff.

## Rationale (optional)

`get()` currently always performs two list-pointer rewrites and two `Option` matches even when the node is already at the tail, which is common under temporal locality. This hypothesis isolates per-op time: it should move get p50 without touching any other fitness dimension.
