# H01

Linking new probation entries at a midpoint marker inside the probation list instead of its MRU tail raises hit-rate on workload-a at size 2048 over the cycle/0009/v002 Winner.

## Parent

cycle/0009/v002

## Changes

Keep the segmented protected/probation structure, the ghost admission filter, the frequency-aware victim window, and the correlated-reference counting exactly as in the parent. Change only where a new key lands in the probation list.

- Add two fields to `LruCache`: `prob_mid: Option<usize>` (first "hot" probation node; `None` means the marker sits at the probation tail) and `prob_cold: usize` (number of probation nodes before the marker). Initialise both in `try_new()`.
- Add a `rebalance_probation()` helper that moves the probation marker toward a target of `prob_len * 3 / 8` (where `prob_len` is the current probation length), at most one node per step, using the same marker-stepping logic as the midpoint marker in the cycle 0009 v003 overlay, but scoped to the probation list only.
- In `put()`, replace the `self.push_back(idx, false)` for new entries with a link immediately before the probation marker (a `link_before`-style insert into the probation list, or push to the tail when the marker is `None`). Re-entry after a ghost admission follows the same rule.
- In `unlink()` / `touch()`, when a probation node is removed (promotion to protected, demotion-free eviction, or slot reuse), keep the marker consistent using the same detach rule as the v003 `detach()`: if the node is cold decrement `prob_cold`, and if it is the marker advance the marker to its `next`.
- Promotions (`touch()` on a probation node) and protected-segment behaviour are unchanged, so the protected MRU fast-path in `get()` is untouched.
- Victim selection is unchanged: `select_victim()` still scans `VICTIM_WINDOW` entries from the probation head (falling back to the protected head).

Invariants to preserve: at most `capacity` nodes; `prot_len <= prot_cap`; the ghost set and its generation handling are unchanged; every existing unit test in `mod.rs` still passes (none of them depend on the exact probation position of a freshly inserted key except where the test already names the LRU victim, which is unchanged).

## Rationale (optional)

Cycle 0009 v003 showed that linking fills at a 3/8 midpoint in a plain LRU raised hit-rate on workload-a, while tail insertion gave mixed results across cycles. The segmented incumbent has never tried insertion depth. This hypothesis tests whether that lever stacks on the probation list. If the gain does not appear, the depth effect is specific to the plain-LRU recency order rather than a general property of fill placement.
