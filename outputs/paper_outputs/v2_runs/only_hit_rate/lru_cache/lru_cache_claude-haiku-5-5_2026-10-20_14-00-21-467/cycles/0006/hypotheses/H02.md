# H02

Promoting a node to MRU only on its second hit, with new keys inserted at the LRU tail, raises workload-a hit-rate at size 2048 over the 0.7348 incumbent by filtering one-touch keys more strictly than periodic MRU insertion does.

## Parent

cycle/0003/v001

## Changes

Start from cycle/0003/v001, which skips relinks when a hit node is already the MRU head. Add a one-bit reuse flag to each node, cleared when the node is inserted. In the insertion routine, link new nodes at the LRU tail instead of the MRU head. In the hit path, if the node's reuse flag is clear, set it and leave the node in place; if the flag is already set, move the node to the MRU head as the existing code does. Keep the head-hit relink skip: a node already at the head is never relinked. Eviction still removes from the LRU end, unchanged. Do not add a second list, a counter table, or a ghost set. Keep the key index and all list-link invariants intact, and make sure a node's flag is reset if the slot is reused.

## Rationale (optional)

Cycle 0005's v003 gained hit-rate by inserting new keys at the tail, but it still promotes on every hit. This hypothesis tests a stricter scan filter: a key must be re-referenced once before it earns MRU placement. It differs from H01 in that it changes the promotion rule rather than the periodic insertion. It is the one hypothesis here that leaves the hit-path promotion rule altered, so per-op time should be recorded alongside hit-rate.
