# H03

Pre-sizing the baseline's key index to the cache capacity at construction will cut per-op-time by removing rehashing from the insert path, with hit-rate unchanged.

## Parent

baseline

## Changes

Leave the eviction policy and node layout untouched. In the constructor, reserve the key-index capacity up front to the configured cache size (for example `HashMap::with_capacity(capacity)` or the equivalent for whatever index type the baseline uses), so the index never grows or rehashes during a run that stays within capacity. Preserve the existing behaviour when the index is at capacity, including the eviction call on insert. If the baseline already reserves capacity, do not make this change and report that the hypothesis has no effect. Do not change the hash function, since that could alter iteration or collision behaviour that the metrics depend on.

## Rationale (optional)

Cycle 0001 did not measure per-op-time for any variant, and the leaderboard shows per-op-time held by baseline with no challenger. This hypothesis targets that dimension directly from the unmodified baseline, so it is an independent route to a per-op-time win that does not depend on the v001 or v003 lineages. Because it leaves eviction order alone, its hit-rate should match the baseline's 0.665.
