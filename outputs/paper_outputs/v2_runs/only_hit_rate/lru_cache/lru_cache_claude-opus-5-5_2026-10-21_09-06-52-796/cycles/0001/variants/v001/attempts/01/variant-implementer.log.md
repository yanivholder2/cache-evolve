I wrote the v001 overlay, which replaces LRU with S3-FIFO as hypothesis H01 specifies. I couldn't build or run anything because this session had no shell. The four gates and the new unit tests have only been checked by reading the code against what each gate asserts.

The only file changed is `overlay/src/lru_cache/mod.rs`. The public names the JNI layer and the two bins depend on keep the same signatures: `LruCache`, `Node`, `try_new`, `new`, `get`, `put` and the `framework::Cache` impl. The pinned gate files and `lru_cache_jni.rs` are untouched.

**Data layout:**
- **`Node`:** now holds only `key`, `value`, `freq` and `in_main` (no list links), so it's smaller. The metadata-size bin measures this struct, so that number should drop.
- **Cache:** keeps the key-to-slot `map` (slots are now `u32`) and adds `small` and `main` queues, `small_target = max(1, cap/10)`, and a ghost queue plus set.
- **Ghost size:** the ghost holds at most `max(1, cap - small_target)` keys.

**Behaviour:**
- **`get`:** a hit only raises `freq` (capped at 3) and moves nothing.
- **Overwriting an existing key:** replaces the value, raises `freq`, and leaves the entry where it is.
- **Putting a new key:** if the cache is full it evicts one entry and reuses that slot. The new key goes into `main` if it was in the ghost, otherwise into `small`, with `freq` 0.
- **Eviction:** if `small` holds at least `small_target` entries or `main` is empty, it takes the oldest entry in `small`. That entry moves to `main` if it was used since it went in; otherwise it is evicted and its key goes into the ghost. Otherwise it takes the oldest entry in `main`, which goes back to the end with `freq` lowered by one if it was used, or is evicted and not added to the ghost. Each pass either lowers a `freq` or frees a slot, so eviction always ends.
- **Capacity 1:** works. Evictions come from `small` unless a ghost hit has put the single entry in `main`.

**Tests:** I removed the seven strict-LRU tests named in the hypothesis. I kept the miss, overwrite, capacity and eviction-chain tests. I added tests for:
- one-hit entries being evicted from `small` first;
- a used `small` entry moving to `main`;
- a key in the ghost going straight into `main` when put again;
- entries evicted from `main` not being added to the ghost;
- a 10,000-operation run checking the size limit, that each entry is in exactly one queue, and that stored values read back correctly.

One known approximation, which follows the spec as written: when a key leaves the ghost because it was put again, its old entry stays in the ghost queue. When that old entry later reaches the front and is dropped, it also removes any newer ghost record for the same key, so that key can lose its ghost status early. This could cost a few ghost hits but cannot break correctness.
