# H02

Raising the saturating access-frequency cap `MAX_FREQ` from 3 to 7 raises hit-rate on workload-a because frequently reused keys then survive more CLOCK sweeps of `main` before eviction.

## Parent

cycle/0005/v001

## Changes

In `src/lru_cache/mod.rs`, change `const MAX_FREQ: u8 = 3;` to
`const MAX_FREQ: u8 = 7;`.

Change nothing else. These all stay as they are:
- `get` and the update branch of `put` keep their saturating
  `freq += 1` up to `MAX_FREQ`.
- In `evict_one`, the `small` branch keeps resetting `freq` to 0 when it
  promotes into `main`. Promotion still needs just one hit.
- The `main` branch keeps decrementing `freq` by 1 and reinserting at
  the back.
- The ghost (`capacity / 8`), `small_target` (`capacity / 10`), and
  ghost-hit admission into `main` with `freq = 0`.

The termination argument still holds: every loop iteration either
lowers some node's freq or frees a slot. A full sweep can now take up to
7 passes, but that is still bounded.

No test asserts the cap value directly, so existing tests should pass
unchanged. Add one small test. Put a key into a small cache and call
`get` on it more than 7 times. Check that its `freq` saturates at 7. Use
the `nodes` arena through `map`, as the `in_main` helper does.

## Rationale (optional)

Every winner so far has tuned admission, and cycle 5 says admission
filtering is close to saturated. This tests the other lever: how long
`main` keeps keys that are already admitted. With a 2-bit counter, a key
hit 10 times and a key hit 3 times look the same to `main`'s eviction.
LIRS traces mix hot sets with loops, so a wider counter could protect
the hot set from loop pressure. If hit rate drops, the cap is too sticky:
stale formerly-hot keys clog `main`, and that would argue for a
decay-style policy next.
