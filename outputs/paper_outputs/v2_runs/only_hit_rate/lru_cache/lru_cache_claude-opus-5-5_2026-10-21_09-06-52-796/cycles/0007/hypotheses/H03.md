# H03

Admitting ghost-hit keys into `main` with one frequency credit (`freq = 1`) instead of `freq = 0` will raise hit-rate above cycle/0006/v003's 0.7364, because proven re-referenced keys survive their first pass through `main`'s eviction scan.

## Parent

cycle/0006/v003

## Changes

In `src/lru_cache/mod.rs`, `LruCache::put`, in the new-key path after `ghost_hit` is computed: set the inserted node's `freq` to `if ghost_hit { 1 } else { 0 }` instead of always 0. Apply this in both branches:
- the slot-reuse branch after `evict_one()`, where `node.freq = 0;` becomes the conditional;
- the `self.nodes.push(Node { ... freq: 0, ... })` branch.

Do not change any of the following:
- `MAX_FREQ` stays 3;
- `small_target = max(1, capacity / 20)` and `ghost_cap = max(1, capacity / 8)`;
- `get`;
- `evict_one`. A `small` promotion still resets freq to 0 when moving to `main`, and a `main` pass still decrements by 1 and reinserts;
- `push_ghost`.

Only ghost-hit admissions change. Keys promoted from `small` keep their current behaviour, so this isolates the "ghost path arrives with no protection" weakness that v003's insight called out.

Tests: extend `ghost_hit_admitted_into_main` to assert the readmitted node has `freq == 1` right after the `put`. Add a test at capacity 16: ghost-hit key 1 into `main`, then insert enough fresh keys to force one `main` eviction scan. Assert that key 1 survives the first scan with freq decremented to 0, while a `main` resident with `freq == 0` is evicted ahead of it. Existing invariants in `capacity_bound_under_churn` must hold. Termination of `evict_one` is preserved, because each `main` pass still lowers freq or frees a slot.

## Rationale (optional)

This is a lever no earlier cycle tried: the initial retention credit given on the ghost path. Since v003 moved more admissions onto the ghost path, those keys get evicted first among `main` entries unless they are hit again before the CLOCK hand reaches them. One credit treats the ghost hit as the reuse it signals, which cycle 4 found reliable once the window is short. Unlike widening MAX_FREQ (H01), this doesn't change how hot keys accumulate credit. Unlike the split change (H02), it doesn't change which keys get admitted.
