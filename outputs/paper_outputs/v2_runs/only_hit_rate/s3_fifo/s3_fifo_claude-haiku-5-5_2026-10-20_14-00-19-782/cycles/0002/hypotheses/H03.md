# H03

Move the `freq` counter out of `Entry` into parallel `u8` deques so `Entry` shrinks from 24 to 16 bytes, lowering metadata-size while leaving hit-rate at the parent's value.

## Parent

cycle/0001/v002

## Changes

In `src/s3_fifo/s3_fifo.rs`, remove `freq` from `Entry<K, V>`, leaving `{ key: K, value: V }`, and update `Entry::new` to match. Add two fields to `S3Fifo`: `small_freq: VecDeque<u8>` and `main_freq: VecDeque<u8>`. Invariants: `small_freq.len() == small.len()` and `main_freq.len() == main.len()` at every point between operations. Keep `ghost` as `VecDeque<K>`, because ghost entries carry no frequency.

Mirror every queue operation in the parallel deque, at the same position:

- `put()`, existing-key branch: only the value changes, so no frequency change.
- `put()`, ghost-hit branch (routed through `small` as in the parent v002): `small.push_front(...)` also does `small_freq.push_front(0)`.
- `put()`, miss branch: `small.push_front(...)` also does `small_freq.push_front(0)`.
- `get()`: find the hit with `iter().position` over `small` then `main`, then update the matching deque: `small_freq[i]` or `main_freq[j]`, using `saturating_add(1).min(MAX_FREQ)`. Return the value reference as before.
- `evict_main()`: pop from `main` and `main_freq` together. If the frequency is > 0, decrement it and `push_front` both. Otherwise break, as now.
- `evict_small()`: pop from `small` and `small_freq` together. If the frequency is > 1, call `evict_main()` when full, then `main.push_front` the entry and `main_freq.push_front` the frequency. Otherwise push the key to `ghost` as now, and drop the frequency.

Keep the admission and eviction decisions identical to the parent, so hit-rate must match exactly. Update the existing tests that read `.freq` on entries (`main_eviction_uses_frequency_second_chance` and the test helpers that set `freq`) so they use the parallel deques.

Report two numbers so the saving is not overstated. First, `size_of::<Entry<i64, i64>>()`, expected to fall from 24 to 16, which is the metadata-size the leaderboard uses. Second, the effective per-entry bytes including one frequency byte, expected to be 17. Also report per-op-time, since the extra indexed lookups may change it.

## Rationale (optional)

The `metadata-size=24` figure is the size of `Entry<i64, i64>` with `freq` padded to 8-byte alignment, so moving the one-byte field out of the struct is the only lever on that dimension that keeps the eviction policy intact. Cycle 0001 never reported metadata-size, and this hypothesis tests whether a layout change moves it at no hit-rate cost. The parent is v002 so that its ghost re-admission path, which is the most complex branch to mirror, is exercised.
