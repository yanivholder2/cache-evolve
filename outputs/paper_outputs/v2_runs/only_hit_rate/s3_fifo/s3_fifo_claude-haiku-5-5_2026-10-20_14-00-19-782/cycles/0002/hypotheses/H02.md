# H02

Raise `MAX_FREQ` from 3 to 7 so frequently hit main-queue residents survive more second-chance rotations, raising hit-rate on lirs workload-a at size 2048 above the parent's 0.7164.

## Parent

cycle/0001/v003

## Changes

In `src/s3_fifo/s3_fifo.rs`, change the constant `const MAX_FREQ: u8 = 3;` to `const MAX_FREQ: u8 = 7;`. That is the only edit.

The existing code already handles the wider range: `get()` clamps with `saturating_add(1).min(MAX_FREQ)`, and `Entry::freq` is a `u8`. Keep `evict_small()` promoting on `tail.freq > 1`, so the admission path is unchanged. Keep `evict_main()` as is: it decrements `freq` by one per rotation and evicts at the first tail with `freq == 0`. Keep the partition from the parent (`capacity / 10`) and the ghost logic unchanged. Do not add fields, so metadata-size stays at 24.

Report hit-rate, metadata-size and per-op-time. A higher cap lengthens the chain of rotations that `evict_main()` can run before it finds an eviction victim, so per-op-time may rise; record it rather than tuning it away.

## Rationale (optional)

Cycle 0001 tested the promotion bar, ghost routing and small-queue ratio, but never the main-queue frequency cap. The current cap of 3 means a main resident that was hit three times is treated the same as one hit a hundred times, so bursty hot keys may be evicted during scan bursts. A cap of 7 gives hot keys more second chances at the cost of extra rotations. This is an orthogonal axis to the cycle 0001 changes and is a single constant, so any hit-rate movement can be attributed to it.
