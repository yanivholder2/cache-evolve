# H01

Adding a resident-key hash set so misses in `get()` and `put()` return without scanning the queues should reduce per-op-time without changing hit-rate, targeting per-op-time.

## Parent

cycle/0002/v001

## Changes

Keep the ghost-membership `HashSet` that cycle/0002/v001 introduced. Add a second `HashSet<K>` field, `resident`, that holds exactly the keys currently in `small` and `main`. The invariant is that `resident` equals the union of the two queues' keys at all times.

Maintain `resident` at every site that changes queue membership:
- `put()`: insert the key when it is pushed to `small` (new key) or to `main` (ghost re-admission).
- `evict_small()`: when the tail moves to `main`, the key stays resident. When the tail moves to `ghost`, remove it from `resident`.
- `evict_main()`: remove the key of any entry it drops. The `freq == 0` branch pops the tail and breaks without re-pushing it, so that key leaves the cache and must be removed from `resident`.

In `get()` and `put()`, check `resident.contains(key)` first. If the key is absent, return `None` (for `get`) or skip the linear `find_entry_mut` scan (for `put`). Only scan the queues when the key is present.

Change the inherent `impl` bounds from `K: PartialEq + Clone` to `K: PartialEq + Eq + Hash + Clone` as needed. The `framework::Cache` impl already has these bounds.

Do not change the eviction order, the promotion bar, `MAX_FREQ`, or `small_size`. Hit-rate must match the parent exactly (0.7164 on lirs workload-a at 2048). Report per-op-time and metadata-size in the fitness vector. The hypothesis is confirmed on cost only if per-op-time drops and the hit-rate is unchanged.
