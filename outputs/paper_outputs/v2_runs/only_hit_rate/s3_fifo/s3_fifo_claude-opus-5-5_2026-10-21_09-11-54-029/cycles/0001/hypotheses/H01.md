# H01

Shrinking the small queue from 25% to 10% of capacity, as the S3-FIFO paper recommends, gives the main queue more of the cache and raises hit rate on workload-a at capacity 2048.

## Parent

baseline

## Changes

In `S3Fifo::try_new` (src/s3_fifo/mod.rs), change how `small_size` is derived.
Replace `(capacity / 4).max(1).min(capacity - 1)` with
`(capacity / 10).max(1).min(capacity - 1)`. Keep the `capacity == 1` special
case (`small_size = 1`). `main_size = capacity - small_size` stays as it is, so
small + main still add up to exactly `capacity`. At capacity 2048 this gives
small = 204 and main = 1844, compared with 512 / 1536 in the baseline.

The ghost queue stays sized to `main_size`, both in its `VecDeque::with_capacity`
call and in the `self.ghost.len() >= self.main_size` bound in `evict_small`. It
therefore grows along with the main queue and remembers more demoted keys.

Leave everything else unchanged: graduation threshold (`freq > 1`), the
second-chance loop in `evict_main`, ghost re-admission in `put`, `MAX_FREQ`, and
`Entry` layout. Existing unit tests use capacity 4 or 5, where
`capacity / 10` is 0 and `.max(1)` gives 1. Those tests build their state by
hand or only check queue membership and the capacity bound, so they should still
pass. Check that `small_eviction_promotes_to_main_after_multiple_hits` and
`ghost_hit_promotes_back_to_main` still hold with a small queue of size 1. If
either one relied on the size-1 small queue behaving differently, update only
that test's setup and not the policy.

## Rationale (optional)

This tests one partition parameter in isolation. The paper's 10% small queue is
meant to filter one-hit wonders quickly while giving reused keys a larger
second-chance resident set. The fitness change shows directly whether workload-a
rewards a bigger main queue more than a longer probation window.
