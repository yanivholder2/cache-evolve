# H03

Raise the main-queue frequency cap `MAX_FREQ` from 3 to 7 so that keys reused many times survive more second-chance laps in main, raising hit-rate on workload-a.

## Parent

cycle/0002/v003

## Changes

In `src/s3_fifo/mod.rs`, change `const MAX_FREQ: u8 = 3;` to `const MAX_FREQ: u8 = 7;`. Nothing else changes.

- `get` already saturates with `.min(MAX_FREQ)`, so a key can now build up to 7 credits.
- `evict_main` keeps its current loop: pop the tail, and if `freq > 0`, decrement by 1 and `push_front`, otherwise drop it. A key at the cap can now survive up to 7 laps of main without being accessed, instead of 3.
- The graduation rule in `evict_small` (`tail.freq > 1`) is unchanged. A small-queue entry still needs 2 hits to graduate, so the larger cap does not loosen admission. It only changes retention inside main.
- Leave the 5% partition, ghost sizing (`main_size`), and ghost-hit insertion (main front, freq 0) unchanged.

Tests: `repeated_get_clamps_frequency` still passes. Add one test that does 10 `get`s on a main-resident key and asserts `freq == 7`. Add another that checks such a key survives 7 `evict_main` passes and is evicted on the 8th when it is not re-accessed.

Invariant: `evict_main` must always terminate. Every pass through the loop decrements some entry's freq, so the loop ends after at most `main.len() * MAX_FREQ` rotations. This bound is now larger, which is a per-op-time risk worth noting, but termination is still guaranteed.

## Rationale (optional)

The cross-cycle lesson is that workload-a rewards protecting main capacity for keys with proven repeated reuse. A cap of 3 cannot distinguish a key reused 3 times from one reused 50 times. A higher cap gives main a better frequency signal and lets the hottest keys outlast keys reused only a few times during bursts of one-time insertions. This is a single-variable test of main-queue retention, an axis no earlier cycle has touched. The earlier cycles changed partition, graduation, and ghost instead.
