# H01

Halving a main-queue entry's frequency on each eviction-sweep rotation, instead of decrementing it by 1, will raise hit-rate on workload-a because stale formerly-hot keys stop holding main capacity for up to 15 laps.

## Parent

cycle/0004/v002

## Changes

In `src/s3_fifo/mod.rs`, change only the credit-spending rule in `S3Fifo::evict_main`. Today the loop pops the main tail and, if `tail.freq > 0`, does `tail.freq -= 1` and `push_front`. Change it to `tail.freq >>= 1` (integer halving) and then `push_front`. If `tail.freq == 0`, keep the existing break, which drops the popped tail exactly as before. Under `MAX_FREQ = 15`, a saturated key now survives at most 4 laps (15→7→3→1→0) instead of 15. The key's full reuse count still decides how many laps it gets, but on a log scale.

Keep everything else unchanged:
- `MAX_FREQ` stays 15.
- `get` still increments with saturation at `MAX_FREQ`.
- The 5% small-queue split is unchanged.
- `evict_small`'s `freq > 1` graduation is unchanged.
- Ghost re-admission is still front-of-main at freq 0.
- The ghost bound is unchanged.

The loop must still terminate. Every rotation strictly decreases some entry's freq, so the number of rotations is bounded by `main.len() * 4`.

Update the unit tests that encode linear decrement:
- Replace `max_freq_key_survives_fifteen_main_passes_then_evicted_on_sixteenth` with a test showing a freq-15 key survives exactly 4 passes and is evicted on the 5th.
- Adjust `main_eviction_uses_frequency_second_chance` if needed. Its freq-1 and freq-2 entries become freq 0 and freq 1 after one rotation, so the expected victim (key 3) should be unchanged. Re-check it anyway.
- Add a test that a single sweep turns freq 6 into 3.

## Rationale (optional)

Cycle 0004 found main retention flat on the cap axis and named "how credit is aged or spent (decay)" as the only untested retention lever. Halving keeps the order between keys based on reuse but removes the long tail of laps that lets keys that are no longer hot crowd out fresh ghost re-entries. Halving also shortens eviction sweeps (`main.len()*15` → `main.len()*4` worst case), which addresses the unmeasured per-op-time cost of the Winner's cap of 15. To refute the claim, compare hit-rate against v002's 0.729 on workload-a at size 2048.
