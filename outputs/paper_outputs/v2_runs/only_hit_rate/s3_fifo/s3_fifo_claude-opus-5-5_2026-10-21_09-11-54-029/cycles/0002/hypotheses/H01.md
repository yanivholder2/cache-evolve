# H01

Decoupling the ghost queue from main and sizing it at 2× main_size (3688 keys at capacity 2048) will raise hit-rate on workload-a by re-admitting more previously demoted keys straight into main.

## Parent

cycle/0001/v001

## Changes

In `src/s3_fifo/mod.rs`, add a `ghost_size: usize` field to `S3Fifo`. In `try_new`, keep v001's 10% small split unchanged (`small_size = (capacity / 10).max(1).min(capacity - 1)`, `main_size = capacity - small_size`). Set `ghost_size = main_size.saturating_mul(2).max(1)` and allocate `ghost: VecDeque::with_capacity(ghost_size)`.

In `evict_small`, change the ghost bound check from `self.ghost.len() >= self.main_size` to `self.ghost.len() >= self.ghost_size`. Leave everything else exactly as in v001: graduation threshold (`freq > 1`), ghost re-admission to main with `Entry::new` (freq 0), `evict_main` second-chance logic, `MAX_FREQ = 3`, and the linear-scan data structures.

Invariants: the ghost holds keys only, so resident entries stay at `small.len() + main.len() <= capacity`. Keep the existing unit tests passing, including `small_queue_is_ten_percent_of_capacity`. Add one inline test asserting `ghost_size == 2 * main_size` at capacity 2048.

## Rationale (optional)

v001's insight credits part of its gain to the ghost queue growing along with main. This variant tests that mechanism alone, holding the partition fixed. If hit-rate rises, ghost memory is the lever. If it stays flat or drops, v001's gain came from main residency. The longer linear ghost scan will cost per-op-time, which should be noted if it is measured.
