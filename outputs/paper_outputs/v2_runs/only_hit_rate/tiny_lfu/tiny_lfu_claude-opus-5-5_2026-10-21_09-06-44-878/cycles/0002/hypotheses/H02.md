# H02

Adding plain halving-based aging to v003's sketch with a long sample period (all counters halved after every 64×capacity increments) and no conservative update will raise hit-rate on workload-a at size 2048 above v003's 0.7372.

## Parent

cycle/0001/v003

## Changes

All edits are in `src/tiny_lfu/mod.rs`, inside `CountMinSketch` and where `try_new` builds it. The LRU list, `get`/`put` control flow, victim choice (LRU head), the strict `>` contest and v003's hashing all stay as they are. Counters stay `u32`, and the depth and width are unchanged, so `heap_bytes()` and `sketch_heap_bytes()` do not change.

1. **Fields.** Add `additions: usize` and `sample_size: usize` to `CountMinSketch`. Change `CountMinSketch::new(width)` to `new(width, sample_size)`. In `try_new`, pass `sample_size = capacity.saturating_mul(64).max(1024)`. At size 2048 that is 131072 increments. Note that `get` and `put` both increment, so this is roughly 64×capacity sketch events, not 64×capacity requests.
2. **Increment stays standard.** `increment_hashed` keeps incrementing **all** 4 row cells (saturating at `MAX_COUNT`). This is deliberately **not** conservative update, so the effect of aging can be isolated from the confounded v002 change. After the loop, do `self.additions += 1`, and if `self.additions >= self.sample_size`, call `self.reset()`.
3. **`fn reset(&mut self)`.** Shift every element of `self.counts` right by one (`*c >>= 1`), then set `self.additions /= 2`. Use one pass over the flat `Vec<u32>`.
4. **No other changes.** `estimate_hashed` stays a plain row minimum.
5. **Tests.** The in-module tests do fewer than 20 increments, far below the 1024 minimum, so they must pass unchanged. Add one unit test on `CountMinSketch` directly: build it with `sample_size = 16`, increment one key 16 times, and assert its estimate drops to 8 after the reset.

## Rationale (optional)

v002 combined conservative update with aggressive halving every 10×capacity, and it lost about 5 points. The cycle-0001 insight says it is unknown which of the two did the damage. This hypothesis tests aging alone, at a period about 6× longer than v002's. That period is long enough to keep the long-run history that workload-a rewards, and short enough that keys which were hot long ago eventually stop winning every contest against newly hot keys. If this also falls below v003, the conclusion is that workload-a does not benefit from freshness at all. If it beats v003, sweeping the period is the next step.
