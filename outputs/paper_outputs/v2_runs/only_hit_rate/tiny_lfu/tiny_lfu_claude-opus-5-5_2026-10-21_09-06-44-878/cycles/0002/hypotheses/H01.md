# H01

Picking the eviction victim as the lowest-frequency entry among the 8 oldest LRU entries, instead of always taking the LRU head, will raise hit-rate on workload-a at size 2048 above v003's 0.7372.

## Parent

cycle/0001/v003

## Changes

All edits are in `src/tiny_lfu/mod.rs`. Keep v003's hashing (`LocalFastHasher`, `hash_key`, flat `CountMinSketch` with `positions`/`increment_hashed`/`estimate_hashed`), the sketch geometry (so `sketch_heap_bytes()` does not change), the `get` path, and the single intrusive LRU list.

1. **Constant.** Add `const VICTIM_SAMPLE: usize = 8;`.
2. **New helper `fn select_victim(&self) -> (usize, u32)`.** Start at `self.head` and walk forward through `next` pointers for up to `VICTIM_SAMPLE` nodes, stopping early at the end of the list. For each node, compute `self.sketch.estimate(&self.nodes[idx].key)`. Return the index and estimate of the node with the **smallest** estimate. On a tie, keep the node found first, which is the one closer to the LRU head. For example, compare with `<`, never `<=`.
3. **In `put`, on the full-cache branch:** replace
   `let victim_idx = self.head.expect(...); let victim_freq = self.sketch.estimate(...)`
   with `let (victim_idx, victim_freq) = self.select_victim();` (the `expect` still applies when `head` is `None`). Keep the strict `incoming_freq > victim_freq` contest. If the incoming key wins, evict `victim_idx`, which may now sit in the middle of the list: `unlink` already handles mid-list nodes. Then reuse its slot exactly as v003 does: overwrite the key and value, `push_back`, and update `map`. If the incoming key loses, nothing changes.
4. **Invariants.** `map.len() == nodes.len() <= capacity`. The list holds every resident node exactly once. Hits still move nodes to MRU.
5. **Tests.** The existing in-module tests run at capacity 2. There the sample covers the whole cache, so the victim becomes the colder of the two keys. Check by hand that `eviction_prefers_hot_items`, `low_frequency_new_item_is_rejected` and `update_promotes_existing_item_and_admits_hot_arrivals` still hold. In each of them the LRU head is already the colder key or ties with it, and on a tie the head is chosen. If a test's expectation truly encodes "victim is always the head", update it to assert minimum-frequency-among-oldest semantics instead. Add one test at capacity 4: make the LRU head the hottest key, then confirm a warm newcomer evicts a colder, more recent key instead.

## Rationale (optional)

Cycle 0001 found that the admission contest is the bottleneck. With pure-LRU victim choice, the incoming key is always compared against the head. If the head is a hot key that simply hasn't been touched lately, the newcomer is rejected even when a cold key sits right next to it. Sampling a few of the oldest entries keeps recency as the main ordering, but frequency gets to pick among the stale candidates. Newcomers then face the weakest nearby victim, which makes admission more likely and evicts colder items. The cost is at most 8 extra estimates on miss-puts, each a single fast hash in v003.
