# H03

Making v001's W-TinyLFU admission window adaptive through hit-rate hill-climbing, instead of fixing it at 1% of capacity, will raise hit-rate on workload-a at size 2048 above v003's 0.7372.

## Parent

cycle/0001/v001

## Changes

All edits are in `src/tiny_lfu/mod.rs`. Keep v001's three-segment layout (WINDOW / PROBATION / PROTECTED intrusive lists), its `on_hit` promotion and demotion, its `contest` (strict `>`), its sketch and its public API. `sketch_heap_bytes()` stays the same.

1. **Climber state.** Add these fields to `TinyLfuCache`:
   - `hits_in_sample: usize`
   - `ops_in_sample: usize`
   - `sample_period: usize`, set to `max(64, 10 * capacity)`
   - `prev_hit_rate: f64`, starting at 0.0
   - `step: f64`, starting at `0.0625 * capacity as f64`, so 128 slots at size 2048
   - `direction: i64`, starting at `+1`, meaning grow the window
   
   Keep the initial `window_cap = max(1, capacity / 100)`.
2. **Sampling.** In `get`, increment `ops_in_sample` on every call, and also `hits_in_sample` when the call is a hit. `put` does not count, because the simulator's miss path is get→put. Once `ops_in_sample >= sample_period`, call `self.climb()`, then zero both counters.
3. **`fn climb(&mut self)`:**
   - Compute `hr = hits/ops`. If `hr < prev_hit_rate`, flip `direction`. Set `prev_hit_rate = hr`.
   - Compute `delta = (step.round() as usize).max(1)`. Multiply `step` by 0.98, and stop adapting once `step < 1.0`.
   - Compute the new window cap: `new_w = clamp(window_cap ± delta, 1, capacity * 80 / 100)`.
   - Call `self.resize_window(new_w)`.
   
   Skip all of this when `capacity < 3`, so the tiny-capacity tests keep their fixed layout.
4. **`fn resize_window(&mut self, new_w)`.** First set `window_cap = new_w`, `main_cap = capacity - new_w` and `protected_cap = main_cap * 80 / 100`. Then rebalance while keeping the total resident count:
   - **Shrinking:** while `win_len > window_cap`, move the window LRU (`win_head`) to the probation MRU.
   - **Growing:** while `win_len < window_cap` and `prob_len + prot_len > main_cap`, move the probation LRU (or the protected LRU if probation is empty) to the window MRU.
   - **Both cases:** finally, while `prot_len > protected_cap`, demote the protected LRU to the probation MRU.
   
   No key is evicted during a resize. Before the cache is full, the main region may hold fewer than `main_cap` entries, and that is fine.
5. **Full-cache `put`.** The existing logic takes the window LRU as the candidate and runs the contest against the main victim. It still works after a resize, as long as `win_len >= 1` when full. Keep the `window_cap >= 1` clamp so that holds.
6. **Invariants.** `map.len() == nodes.len() <= capacity` and `win_len + prob_len + prot_len == nodes.len()`. Once full, `win_len <= window_cap` and `prot_len <= protected_cap` after every op. Extend `check_structure` in the tests to call these through, and add a stress test (capacity 300, 50k ops, mixed scan and loop pattern) that forces multiple climbs and calls `check_structure` after each op.

## Rationale (optional)

v001 matched the baseline because a 1% window at size 2048 is only about 20 slots. That is too small to hold recency-driven re-references on a LIRS-style trace, so the contest decided everything. Rather than guess a fixed size, Caffeine's hill-climber lets the trace pick the window size. On a frequency-skewed phase the window shrinks back toward 1%, and on recency or loop phases it grows. This is the "larger or adaptive window" open question from cycle 0001, tested without the confounding aging change. It derives from v001, not v003, because v001 already has the segmented machinery. Porting v003's fast hashing is left for a later cycle, so that this change's hit-rate effect stays isolated.
