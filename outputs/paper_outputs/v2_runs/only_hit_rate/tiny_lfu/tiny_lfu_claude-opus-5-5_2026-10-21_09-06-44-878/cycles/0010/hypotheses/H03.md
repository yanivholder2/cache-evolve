# H03

Counting cache hits with weight 2 in the sketch, while misses keep weight 1, favours keys with proven resident reuse and raises hit-rate on workload-a.

## Parent

cycle/0009/v003

## Changes

In `src/tiny_lfu/mod.rs`, add an `add: u32` parameter to `CountMinSketch` by introducing `fn increment_hashed_by(&mut self, h: u64, add: u32)`. It adds `add` to each of the `SKETCH_DEPTH` counters with saturation (`counter.saturating_add(add).min(MAX_COUNT)`). Keep `increment_hashed(h)` as a wrapper for `increment_hashed_by(h, 1)`.

`TinyLfuCache::get` currently increments before the map lookup. Move the increment after the lookup:
- On a hit, call `increment_hashed_by(h, HIT_WEIGHT)` with a new constant `const HIT_WEIGHT: u32 = 2;`.
- On a miss, call `increment_hashed_by(h, 1)` and set `pending_miss_hash` as before.

In `put`, the non-deduped increment stays at weight 1. A `put` that updates an existing key goes through `on_hit`, but its increment stays at weight 1 as well. Only `get` hits are weighted. Do not change admission (strict `>` plus ghost tie), victim sampling, the promotion gate or `select_demotion`. `hit_freq` in `on_hit` must still be read after the increment, so the gate sees the weighted count. Update any unit tests whose hard-coded estimates assume weight 1 on hits, such as `cold_probation_hit_does_not_displace_hotter_protected` and `victim_is_min_frequency_among_oldest_not_lru_head`, recomputing the expected values instead of weakening the asserts. Add one test showing that a single `get` hit raises the estimate by 2.

## Rationale (optional)

Every earlier lever that shifted the contest toward newcomers or recency lost: tie-admit, random admit, ghost margins and aging. The cross-cycle evidence says resident value on this trace comes from long-reuse keys that lifetime counts protect. Weighting hits sharpens exactly that signal. It is the opposite direction from aging, and no earlier cycle has tested it. It is a single lever on what an estimate means, separate from sketch width, conservative update, cap or decay, all of which are exhausted. If it loses, the result shows that the plain access count is already the right currency.
