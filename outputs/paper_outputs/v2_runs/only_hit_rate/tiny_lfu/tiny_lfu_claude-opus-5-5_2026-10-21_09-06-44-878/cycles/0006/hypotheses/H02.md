# H02

Fold cycle-0005 v002's half-width u16 conservative-update sketch into the SLRU winner to cut sketch metadata-size by 4× with no change in hit-rate.

## Parent

cycle/0005/v001

## Changes

Edit `src/tiny_lfu/mod.rs` only. Leave all SLRU list logic, `select_victim`, dedup and the strict `>` contest exactly as they are in the parent.

- Set `SKETCH_WIDTH_FACTOR` to `8` (was `16`) and `MAX_COUNT` to `u16::MAX` (type `u16`).
- In `CountMinSketch`, change `counts: Vec<u32>` to `Vec<u16>`. Make `heap_bytes()` return `depth * width * size_of::<u16>()`, and update the doc comments on `heap_bytes` and `sketch_heap_bytes` to match.
- Replace `increment_hashed` with conservative update, copied from cycle/0005/v002. Compute `positions(h)` once and take the minimum counter. If the minimum equals `MAX_COUNT`, return (saturated). Otherwise increment only the counters equal to that minimum.
- `estimate_hashed` still returns `u32`. Take the minimum over the `u16` counters and widen it with `as u32`, so every caller keeps comparing `u32` values.
- In the in-file test `sketch_width_is_sixteen_times_capacity`, rename it to `sketch_is_eight_wide_u16` and assert `cache.sketch_heap_bytes() == 4 * 16384 * 2` for capacity 2048.

At capacity 2048 the sketch shrinks from 512 KiB to 128 KiB.

## Rationale (optional)

Cycle 5 showed that v002's narrow conservative-update sketch reproduced the parent's admission and victim decisions exactly (hit-rate 0.7439, the same as its parent), because width and conservative update correct the same collision error and lifetime counts stay far below u16 saturation. The SLRU winner still carries the over-provisioned 16× u32 sketch. The leaderboard now lists a metadata-size dimension, so this combination should keep hit-rate at about 0.745 while cutting sketch memory by 4×. If hit-rate drops measurably, that answers the open question of how small the sketch can get in the SLRU setting, where probation-only sampling makes victim estimates more decisive.
