# H03

Quadrupling the count-min sketch width (from 4×capacity to 16×capacity counters per row) will raise hit-rate on workload-a by cutting the collision-inflated estimates that let cold victims and cold newcomers look warmer than they are.

## Parent

cycle/0002/v001

## Changes

Single lever: sketch geometry in `src/tiny_lfu/mod.rs`.

- Change `const SKETCH_WIDTH_FACTOR: usize = 4;` to `const SKETCH_WIDTH_FACTOR: usize = 16;`. At capacity 2048 the width goes from 8192 to 32768 per row, with the same `next_power_of_two` rounding and the same `MIN_SKETCH_WIDTH`. `SKETCH_DEPTH` stays 4, and `CountMinSketch::positions` stays as written (its mask derives from `width`).
- Do not change the hash function, `increment_hashed`/`estimate_hashed`, `select_victim` (8-entry sample), the strict-`>` contest, or the get/put flow.
- `sketch_heap_bytes()` must keep reporting `depth * width * 4` truthfully, so metadata-size reflects the 4× larger sketch.
- All existing inline tests must still pass.

## Rationale (optional)

Cycle-0001 v003 showed that hit-rate moves when the hash/collision pattern changes. The v001 insight attributes the remaining rejected contests to "stale-high" estimates. Some of that inflation is plain count-min overcounting from collisions, not real history. This hypothesis tests that apart from any policy change: if hit-rate does not move, collision noise is not a meaningful factor at this width and future sketch work should go elsewhere. The trade-off on metadata-size is deliberate and will be visible in the fitness vector.
