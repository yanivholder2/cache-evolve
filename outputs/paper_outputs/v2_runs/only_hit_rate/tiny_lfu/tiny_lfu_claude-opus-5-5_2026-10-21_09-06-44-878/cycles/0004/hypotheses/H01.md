# H01

Count each miss only once in the sketch, so the get-miss-then-put replay stops giving every new key a free second count, to raise hit-rate by letting the strict-`>` contest reject one-hit wonders.

## Parent

cycle/0003/v003

## Changes

All edits are in `src/tiny_lfu/mod.rs`. Leave sketch geometry (`SKETCH_WIDTH_FACTOR = 16`, `SKETCH_DEPTH = 4`), `VICTIM_SAMPLE = 8`, `select_victim`, and the strict `incoming_freq > victim_freq` contest exactly as they are in v003.

1. Add a field `pending_miss_hash: Option<u64>` to `TinyLfuCache`, initialised to `None` in `try_new`.
2. In `get()`, hash the key once with `hash_key(key)` and call `self.sketch.increment_hashed(h)`. Do not call `increment(key)`, which would hash it a second time. On a miss (`map.get` returns `None`), set `self.pending_miss_hash = Some(h)` before returning `None`. On a hit, set `self.pending_miss_hash = None`.
3. In `put()`, after computing `key_hash`, read and clear the flag with `let deduped = self.pending_miss_hash.take() == Some(key_hash);`. Call `self.sketch.increment_hashed(key_hash)` only when `!deduped`. Run the rest of `put` (update-in-place, fill, select_victim/contest) unchanged. A bare `put` of a key not preceded by a get-miss still increments once. A put that follows a get-miss of a different key also still increments, and the flag is cleared either way.
4. Update the in-file unit test `victim_is_min_frequency_among_oldest_not_lru_head`. With the dedup, key 5 has freq 1 after `get(&5); put(5, 50)`, which ties the victim and is rejected. Add a second `cache.get(&5);` before the put so key 5 again reaches freq 2. Leave the test's intent and assertions unchanged. The other existing tests should pass without changes; the implementer should verify this.

Invariants: map/nodes stay consistent; the sketch counter range is unchanged; `sketch_heap_bytes()` is unchanged. The only metadata added is 16 bytes per cache. Per-op cost falls slightly, because `get` hashes once and dedup'd puts skip a 4-counter increment.

## Rationale (optional)

The cycle-0003 insight found that the replay double-bumps every new key. A newcomer therefore enters the contest with estimate ≥2 on its first-ever access, while a resident that was accessed once has estimate 2 as well, so frequency cannot separate them. Now that v003's wider sketch has removed most collision noise, estimates are close to the true per-key counts. Making those counts equal true access counts is the cleanest test of the "doorkeeper/dedup" open question. If hit-rate drops, that tells us the double count was acting as a useful admission bias on workload-a.
