# H01

Computing each key's per-row sketch indices once and reusing them across estimate and increment should lower per-op-time while leaving hit-rate exactly at 0.7362.

## Parent

cycle/0002/v003

## Changes

Keep the flattened `Vec<u32>` counter array from v003 and its `row * width + pos` mapping unchanged. In the sketch's increment path and in the admission path's `estimate`, stop recomputing the per-row hash and position for the same key. Compute the `depth` indices once per key into a fixed-size stack array (e.g. `[usize; DEPTH]`, with `DEPTH` the existing row count constant) and pass that array to both the read (`estimate`) and the write (increment) so each row is hashed exactly once per access. Use the same hash function and seed as the parent so every (row, position) pair maps to the same logical counter as before. Do not change the saturation constant, the admission comparison, or any decay/reset behaviour. Where the code currently hashes the key inside a loop over rows, hoist the hash out of the loop and derive positions from the precomputed value without altering the derived values.

## Rationale (optional)

v003's insight notes that its predicted per-op-time gain was never measured and that the fitness vector carries only hit-rate. This hypothesis is a pure-speed change: the logical counter mapping is preserved by construction, so hit-rate should match the parent exactly, and the claim is falsified if hit-rate moves at all or if per-op-time does not drop against the 132 baseline figure.
