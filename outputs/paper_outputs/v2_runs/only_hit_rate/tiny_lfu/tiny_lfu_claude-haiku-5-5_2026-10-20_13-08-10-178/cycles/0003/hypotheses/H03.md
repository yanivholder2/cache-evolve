# H03

Narrowing the sketch counters from u16 to u8 with saturation at 255 should halve the counter storage again while keeping hit-rate within noise of 0.7362 on workload-a.

## Parent

cycle/0002/v001

## Changes

Keep v001's `CountMinSketch` structure, flattened or nested as the parent has it, its row count, width, and hash mapping unchanged. Change the counter element type from `u16` to `u8` and set `MAX_COUNT` to `u8::MAX` (255). Keep the saturating increment (only increment if below `MAX_COUNT`) and keep the `as u32` widening in `estimate` so the admission comparison stays a strict `>` on `u32` values. Do not add halving, decay, or reset: the sketch keeps its existing non-decaying behaviour and only the counter width and saturation point change. Update any size or footprint constants that assume two-byte counters so the metadata accounting reflects one-byte counters. Make no changes to the admission rule, the window, or the main LRU.

## Rationale (optional)

v001's insight flags that saturation can produce admission ties under the strict `>` test and that this was not ruled out for hot-key workloads. This hypothesis tests the limit of that family directly: a lower saturation point is the sharpest version of the tie risk, so if hit-rate holds at 255 the layout gain is real, and if it drops the cycle learns where the saturation boundary sits. Falsified if hit-rate falls below 0.7362 by more than noise, which would show that the u16 counter is already close to the saturation floor for this trace.
