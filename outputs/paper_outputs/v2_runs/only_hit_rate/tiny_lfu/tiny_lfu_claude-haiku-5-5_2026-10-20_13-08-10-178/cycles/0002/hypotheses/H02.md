# H02

Adding a small LRU admission window of about 1% of capacity in front of the main LRU should raise hit-rate on recency-heavy bursts while the sketch and the strict `>` admission test stay intact.

## Parent

baseline

## Changes

In `TinyLfuCache` (src/tiny_lfu/mod.rs), split the resident entries into two intrusive LRU segments, a window and a main, both threaded through the existing `Node.prev`/`Node.next` fields and the `nodes` slot store.

Add the fields `window_cap: usize` (set to `max(1, capacity / 100)` in `try_new`), `main_cap: usize` (set to `capacity - window_cap`), `window_len`/`main_len: usize`, `window_head`/`window_tail: Option<u32>`, and a per-node `in_window: bool`. Keep `capacity`, the `sketch`, and the `map` as they are. Keep the `try_new` guards for capacity 0 and capacity above `u32::MAX`, and size the sketch from the full capacity as now.

Generalise `unlink` and `push_back` to take the segment (window or main), or add window-specific variants, so each segment has its own head and tail.

`put` for a new key: call `sketch.increment` as today. If the cache is not full, insert the node at the window tail. If it is full, pop the window head `w` (the oldest window entry) as the candidate. If `main_len < main_cap`, move `w` to the main tail. Otherwise compare `sketch.estimate(&candidate_key) > sketch.estimate(&main_head_key)`. If true, remove the main head from the map and move the candidate into the main tail. If false, drop the candidate from the map and reuse its slot for the new key at the window tail. Adjust the lengths as you go.

`get` for a window hit moves the node to the window tail. A main hit moves it to the main tail, as today. Both still call `sketch.increment` first, and the sketch's `position`, `estimate`, and counter layout are unchanged.

Invariants to preserve: `map.len() == window_len + main_len <= capacity`, and every slot index in the map is live in exactly one segment. The existing unit tests in tests/ are not to be edited; the in-module tests in mod.rs must still pass, though some of their expectations may need a comment if the window changes which key is evicted.

## Rationale (optional)

Cycle 0001 found that changes to the sketch and to the admission comparison lost hit-rate, so this hypothesis leaves both alone. It instead adds a short recency window in which new keys are not judged by the sketch until they have survived one pass through it. This targets the one-touch burst case that the frequency-only admission currently rejects. The main risk is that the window changes which items compete at admission time, so hit-rate on workload-a at size 2048 is the number to watch.
