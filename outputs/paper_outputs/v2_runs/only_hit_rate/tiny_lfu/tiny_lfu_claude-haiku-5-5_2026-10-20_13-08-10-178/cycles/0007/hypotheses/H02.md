# H02

Adding one row to the count-min sketch, while keeping its width fixed, will raise hit-rate on workload-a at size 2048 by lowering the min-across-rows estimate's collision error.

## Parent

baseline

## Changes

In the sketch constructor (the code path that sets the number of rows used by `CountMinSketch`), increase the row count by one, keeping the per-row width unchanged. Give the new row its own hash seed, derived the same way the existing rows derive theirs, so the new row's collisions are independent of the others. Leave `CountMinSketch::increment` and `estimate()` as they are: both already iterate over all rows, so the new row should be picked up without logic changes. Keep the conservative-update rule, the counter type, and the aging behaviour exactly as in the baseline, and leave the window, the probation/protected split, and the admission path in `put()` untouched.

Preserve the invariant that the estimate is still the minimum across rows. Do not change the counter saturation limit.

## Rationale

Cycle 0005 showed that removing a sketch row hurt hit-rate, because the min-across-rows estimate needs enough independent rows to suppress collisions. The natural counterpart, adding a row, has not been tried. It is the same lever, going the other direction, applied to the baseline rather than to a stacked parent, so it tests whether depth is still a bottleneck once width is fixed at the baseline value. The added memory and per-op cost are unmeasured and should be reported, but this hypothesis is judged on hit-rate.
