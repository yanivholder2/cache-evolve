# H03

Reserving at least one probationary slot by capping the protected segment at `bucket_size - 1` without demotion makes unproven newcomers evict the probationary slot instead of churning proven keys, raising hit-rate.

## Parent

cycle/0007/v002

## Changes

In the parent, once a bucket fills entirely with protected keys, every new
admission evicts a protected (proven-hot) key at the LRU end — a brand-new,
unproven one-hit-wonder displaces a key that has already demonstrated reuse on a
trace that rewards immortality. This explores the "looser/larger protected
sizing" open question the cross-cycle insights flag, in its one untested,
*non-eroding* form: keep a permanent probationary buffer so the proven set is
never sacrificed to a newcomer, while never demoting an already-protected key
(the demotion that sank the capped-protected variants in cycles 0003/0004).

Edit `src/associative_cache/associative_cache_bucket.rs`:

1. Introduce a protected cap of `max_size - 1` (reserve one probationary slot).
   In `get_from_position`, when a probationary item (`lfu_counter == 0`) is hit:
   - if `protected_count < max_size - 1`, promote it exactly as the parent does
     (set `lfu_counter = 1`, increment `protected_count`, move to the MRU back);
   - if `protected_count == max_size - 1` (cap reached), do **not** promote:
     leave `lfu_counter = 0` and instead move it to the most-recent probationary
     position (give it a fresh probation lap) so a repeatedly-hit key still
     survives, but `protected_count` does not grow.
   Hits on already-protected items are unchanged (move to back, keep counter).

2. Leave `eviction_candidate_index` as the parent's "oldest probationary"
   formula. Because `protected_count` can now never equal `len` when the bucket
   is full, the all-protected fallback (evicting a protected key at index 0)
   becomes unreachable while full — newcomers always evict the reserved
   probationary slot. Keep the fallback branch for the not-yet-full edge cases.

3. `evict_item`/`protected_count` bookkeeping stays as in the parent; with the
   cap, an evicted victim is always probationary, so `protected_count` is left
   unchanged on eviction.

Invariants to preserve: `put` still admits new keys at the probationary front
and returns `(&inserted, Option<evicted>)`; bucket size never exceeds `max_size`
(P1); routing untouched (P2). The cap must be `max_size - 1`, not a fixed
constant, so it scales with the parent's widened (single-halving) buckets.

## Rationale (optional)

This makes the proven working set effectively immortal against newcomer churn —
the single most direct expression of the "once-hot immortality" pattern that has
won every prior cycle. Distinct from H02 (which reorders eviction *within* the
protected set) and from the failed protected caps (which demoted proven keys);
here promotion is only withheld under saturation and the withheld key keeps
re-earning laps rather than being stranded.
