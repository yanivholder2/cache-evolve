# H01

Replace `Item.timestamp: Instant` with a u64 logical clock to shrink `Item<u64,u64>` from 40 to 32 bytes, improving metadata-size without changing hit-rate.

## Parent

cycle/0007/v002

## Changes

In `src/shared/item.rs`, change the `timestamp` field type from
`std::time::Instant` (16 bytes) to `u64` (8 bytes). Source the value from a
process-global monotonically increasing counter (e.g. a
`static AtomicU64` with `fetch_add(1, Relaxed)`) instead of `Instant::now()`.
`Item::new` assigns the next counter value; drop the `use ... Instant` import.

In `src/shared/eviction_policy.rs`, update every site that reads or writes
`timestamp` to use the new counter type: the refresh at line ~63
(`items[position].timestamp = Instant::now()`) becomes a counter bump, and the
`min_by_key` / `max_by_key` selections (lines ~71, ~80) keep working unchanged
because a monotonic u64 preserves the same age ordering an `Instant` provided
(smaller = older). Adjust the `Display` impl in `item.rs` to format a `u64`.

Invariants to preserve: the timestamp-LRU policy must still evict the
oldest-stamped resident (verified by the inline `timestamp_lru_*` bucket tests),
and the SLRU lineage's segmented logic (which never reads `timestamp`) must be
untouched, so hit-rate stays identical. Do not alter `lfu_counter`, the
prefix/suffix `protected_count` invariant, or the geometry overlay.

## Rationale (optional)

`Instant` is a 16-byte two-word value but the only requirement placed on
`timestamp` anywhere in the codebase is a total age order; a u64 counter
satisfies that while halving the field's footprint, landing a clean
metadata-size win (40 → 32) that hit-rate-only cycles have left on the table.
This stacks on the best-so-far lineage so the size gain costs no hit-rate.
