# H01

Requiring two probationary hits (not one) before promotion to the protected segment will raise hit-rate by demanding stronger proof of reuse before a key earns protection.

## Parent

cycle/0003/v002

## Changes

Modify the segmented bucket in
`src/associative_cache/associative_cache_bucket.rs` to raise the promotion
threshold from one hit to two, turning `lfu_counter` from a binary flag into a
small saturating count (0, 1, 2).

- `get_from_position` (the hit path): replace the current
  `if lfu_counter == 0 { lfu_counter = 1 }; remove+push` logic with a
  threshold rule. On a hit, increment `lfu_counter` saturating at 2. Only when
  the post-increment value reaches the promotion threshold of **2** do you
  remove the item and push it to the protected back (MRU). A hit that takes an
  item from 0→1 must leave it **in place** (do not reorder), so it keeps its
  FIFO age. A hit on an already-protected item (`lfu_counter >= 2`) moves it to
  the back as today.
- `eviction_candidate_index`: keep the FIFO-among-probation behaviour but
  across two sub-levels. Scan from the highest index downward and return the
  oldest item with `lfu_counter == 0` first; if none exists, return the oldest
  item with `lfu_counter == 1`; only if every resident item is protected
  (`lfu_counter >= 2`) fall back to the protected LRU end (index 0). This
  preserves the property that a freshly admitted key gets a full lap before it
  can be evicted, while now a once-hit-but-unproven key is preferred over a
  twice-hit protected key.
- `put` is unchanged: new keys still admit to the probationary front (index 0)
  with `lfu_counter == 0`.

Preserve all existing invariants: in-place value update on key match, eviction
only when full, and the return-reference contract of `put`/`get_from_position`.
The single tunable introduced is the promotion threshold constant (2); keep it
named so it is easy to sweep later.
