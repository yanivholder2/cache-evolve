# H03

Skip the redundant remove-and-push when a hit lands on an already-protected key that is already at the MRU back, banking per-op-time with no hit-rate change.

## Parent

cycle/0003/v002

## Changes

The parent's `get_from_position` performs `self.items.remove(position)` followed
by `self.items.push(item)` on *every* hit, even when the hit item is already
protected and already sitting at the MRU back. That `remove`+`push` is an
O(bucket_size) memmove whose result is byte-identical to the starting state in
that case — pure wasted work on the hottest path (high-reuse keys are exactly
the ones repeatedly re-hit at the back). Add a fast path:

1. At the top of `get_from_position`, if `position == self.items.len() - 1`
   (already the MRU back) *and* `self.items[position].lfu_counter >= 1`
   (already protected, so no promotion is due), return
   `&self.items[position]` immediately without the `remove`/`push`.

2. Otherwise fall through to the parent's exact existing behaviour: promote a
   probationary item (`lfu_counter` 0 -> 1) if needed, then `remove(position)`
   and `push` to the MRU back.

This is provably hit-rate-neutral: in the elided case `remove(len-1)` + `push`
restores the identical vector and the counter was already `>= 1`, so neither
ordering nor promotion state changes. `eviction_candidate_index`, admission, and
promotion semantics are all untouched.

## Rationale (optional)

The cross-cycle open questions flag the per-op O(bucket_size) shift as
"largely unmeasured" and ask whether remaining gains are "cost-side only." This
banks the reorder-free case directly against the per-op-time dimension while
holding hit-rate exactly at the incumbent's 0.7267, diversifying the cohort
toward a different fitness axis than H01 and H02.
