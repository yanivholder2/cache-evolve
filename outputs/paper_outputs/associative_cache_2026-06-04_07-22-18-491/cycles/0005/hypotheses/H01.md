# H01

Removing the unused `timestamp: Instant` field from `Item<K,V>` reduces per-entry memory overhead from 40 to 24 bytes without changing hit rate on ClassicLRU-based configurations.

## Parent

cycle/0003/v003

## Changes

Two files require changes, both relative to the cycle/0003/v003 overlay (which inherits the
baseline `item.rs` and the baseline `eviction_policy.rs` unchanged).

### `src/shared/item.rs`

1. Remove `use std::time::Instant;` from the imports.
2. Remove the `pub timestamp: Instant,` field from the `Item<K, V>` struct.
3. Remove `timestamp: Instant::now(),` from the body of `Item::new()`.
4. In `impl Display for Item<K, V>`, remove the `timestamp: {:?}` segment and its
   corresponding `self.timestamp` argument from the `write!` format string.
5. No test changes are needed — none of the existing unit tests assert the timestamp
   field directly (the `new_initializes_fields` test does not check `timestamp`).

After these changes `mem::size_of::<Item<u64,u64>>()` drops from 40 to 24 bytes
(key=8, value=8, lfu_counter=8), which the `evolve_metadata_size` binary will
surface in the fitness vector for the first time in any variant.

### `src/shared/eviction_policy.rs`

`TimestampLRU` references `item.timestamp` and `Instant::now()`, both of which are
removed. Replace its three method bodies with position-based equivalents so the file
compiles without a timestamp field:

1. Remove `use std::time::Instant;`.
2. Replace `TimestampLRU::get_from_position` with move-to-back behavior identical to
   `ClassicLRU`:
   ```rust
   fn get_from_position(&self, items: &mut Vec<Item<K, V>>, position: usize) -> usize {
       let item = items.remove(position);
       items.push(item);
       let back = items.len() - 1;
       items[back].lfu_counter += 1;
       back
   }
   ```
3. Replace `TimestampLRU::eviction_candidate_index` with a fixed return of `0`
   (evict the oldest by insertion order, i.e., FIFO):
   ```rust
   fn eviction_candidate_index(&self, items: &[Item<K, V>]) -> usize {
       0
   }
   ```
4. Replace `TimestampLRU::promotion_candidate_index` with the last-position return:
   ```rust
   fn promotion_candidate_index(&self, items: &[Item<K, V>]) -> usize {
       items.len() - 1
   }
   ```

The benchmark configuration uses `ClassicLRU`, which never reads `timestamp`, so
hit rate is unaffected. `TimestampLRU` degrades gracefully to FIFO-with-LRU-touch
behaviour; it is not exercised by workload-a.

The `AssociativeCacheBucket` overlay from cycle/0003/v003 (stash, +2 promotion
credit) is carried over unchanged — it does not reference `timestamp` anywhere.

## Rationale

Four cycles of stash variants have left the `metadata-size` dimension invisible in
every variant's fitness vector because no variant modified `item.rs`. The `timestamp`
field is structurally dead weight on the ClassicLRU path: it is written on every
`Item::new()` call but never read by the eviction logic. Removing it is the minimal
change that will finally surface `metadata-size` as a measured fitness dimension,
making memory-efficiency trade-offs verifiable for the first time. If the evaluator
scores this variant, the result either confirms a clean 40-point improvement
(metadata-size 40→24 with no hit-rate regression) or reveals a measurement gap in
the evaluator itself — both outcomes are informative.
