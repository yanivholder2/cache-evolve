# H03

A 4x-narrower count-min sketch paired with conservative update holds hit-rate within noise at a quarter of the estimator's memory, converting now-wasted sketch width into an efficiency/cost win.

## Parent

baseline

## Changes

This is the efficiency pivot the cross-cycle insights have repeatedly
requested: cycles 0002–0004 showed sketch width plateaus once cells separate
the trace's distinct keys, and that conservative update (CU) is redundant *with*
the wide sketch — leaving open whether CU can hold accuracy at *lower* width and
therefore lower memory.

Two changes to the baseline `mod.rs`:

1. Narrow the sketch: change `const SKETCH_WIDTH_FACTOR: usize = 64;` to
   `const SKETCH_WIDTH_FACTOR: usize = 16;` (a 4x reduction; `try_new`'s
   `next_power_of_two` rounding and `MIN_SKETCH_WIDTH` floor are preserved).
2. Convert `CountMinSketch::increment` (lines 295–303) to conservative update:
   first compute the current estimate `let m = self.estimate(key);` (the min
   across rows), then for each row increment its counter only when that
   counter's current value equals `m` and is below `MAX_COUNT`. Rows already
   above the minimum are left untouched, which limits over-counting and largely
   recovers the accuracy lost to the narrower, more-collision-prone rows. Keep
   `estimate` and `position` unchanged.

Preserve all policy mechanics (SLRU split, admission gate, promotion,
`protected_cap`) exactly — this hypothesis isolates the estimator. Success is
hit-rate holding within measurement noise of the baseline (≈0.736) at 1/4 the
sketch memory; a measurable hit-rate drop would refute CU's ability to
compensate for the narrower width on this workload.

## Rationale (optional)

The standing open question across cycles 0003–0006 is whether accuracy can be
held at lower memory cost. With hit-rate near its ceiling, the productive axis
is cost: if CU lets a narrow sketch match a wide one, the cache gets cheaper for
free; if not, it bounds exactly how much width this trace actually needs.
