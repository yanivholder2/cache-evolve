# H02

Halving the count-min sketch depth from 4 rows to 2 holds the ceiling hit-rate while cutting estimator hash/min work per access, firing the long-deferred efficiency pivot.

## Parent

cycle/0009/v003

## Changes

Cross-cycle history records that sketch *depth* was proven redundant at the high
end (depth-8 bought nothing in cycle 0008) while the estimator stayed accurate;
the current winners run `const SKETCH_DEPTH: usize = 4;`. Trim depth to the next
free step down and verify the hit-rate ceiling survives.

Concretely:

1. Change `const SKETCH_DEPTH: usize = 4;` to `const SKETCH_DEPTH: usize = 2;`.
   This is the only change.

Everything else stays byte-for-byte identical to v003: `SKETCH_WIDTH_FACTOR`
remains 64, `PROMOTE_FLOOR` remains 2, `ADMISSION_MARGIN` remains 1, and the
SLRU promotion/eviction logic is untouched. `CountMinSketch::new` already derives
its row count from `SKETCH_DEPTH`, and `increment`/`estimate` iterate `0..depth`,
so reducing the constant halves the number of hash evaluations and the width of
the `min` reduction on every `get`/`put` with no other code change.

The testable assertion: with the generous `width = capacity * 64` cells per row,
collisions are already near-zero, so two rows should estimate as accurately as
four and hit-rate should hold at 0.744. If hit-rate instead drops materially,
depth-2 is too shallow at this width and the redundancy floor sits at depth-4 —
either outcome is informative about where the estimator's free capacity ends.
