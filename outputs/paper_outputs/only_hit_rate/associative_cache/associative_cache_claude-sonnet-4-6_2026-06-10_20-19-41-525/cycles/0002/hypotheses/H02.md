# H02

Preferring cold items (lfu_counter==0) as the eviction candidate in ClassicLRU will improve hit-rate on the LIRS workload by shielding recurrently-accessed items from eviction by one-hit scan traffic, building on v001's wider-bucket geometry.

## Parent

cycle/0001/v001

## Changes

Overlay `src/shared/eviction_policy.rs` (keep v001's `geometry.rs` overlay unchanged). Modify only the `ClassicLRU` struct's two methods; all other policies (TimestampLRU, Lifo, Lfu, Fifo, Swap) and all enum/dispatch code remain identical to the baseline:

1. **`get_from_position`**: Before the existing `remove + push` logic, increment `items[position].lfu_counter` by 1. This marks every item that receives a GET hit as "warm" (counter ≥ 1). The remove-and-push ordering (O(n) strict LRU) is preserved exactly as in the baseline — only the counter increment is added.

   ```rust
   fn get_from_position(&self, items: &mut Vec<Item<K, V>>, position: usize) -> usize {
       items[position].lfu_counter += 1;
       let item = items.remove(position);
       items.push(item);
       items.len() - 1
   }
   ```

2. **`eviction_candidate_index`**: Scan `items` from front to back for the first item whose `lfu_counter == 0` (a cold/scan item that has never been accessed after insertion). If found, return that index. If no cold item exists, fall back to index 0 (the standard LRU front), preserving strict LRU eviction order among the warm items.

   ```rust
   fn eviction_candidate_index(&self, items: &[Item<K, V>]) -> usize {
       items.iter().position(|item| item.lfu_counter == 0).unwrap_or(0)
   }
   ```

The `promotion_candidate_index` method is unchanged (still returns `items.len() - 1`). The `name()` method still returns `"ClassicLRU"`. The `lfu_counter` field already exists on `Item<K, V>` in both the baseline and v001 (v001 only overlays geometry, not item.rs).

## Rationale

v001's wider buckets reduced premature eviction of live items by enlarging the LRU pool. However, with a flat LRU, a sequential scan inserting new cold items still pushes warm items toward the eviction front at the same rate. By preferring counter==0 items as eviction candidates, scan pollution is absorbed first, and items that have been accessed at least once get a second chance. The wider 64-slot buckets from v001 give this strategy room to accumulate a meaningful cold/warm gradient before the fallback kicks in.
