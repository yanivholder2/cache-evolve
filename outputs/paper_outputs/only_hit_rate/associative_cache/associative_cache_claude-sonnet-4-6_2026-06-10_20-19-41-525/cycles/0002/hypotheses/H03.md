# H03

Inserting new items at the bucket midpoint rather than the MRU back will improve hit-rate on the LIRS workload by preventing one-hit scan items from immediately occupying the most-protected positions and displacing warm entries toward the eviction front.

## Parent

baseline

## Changes

Overlay `src/associative_cache/associative_cache_bucket.rs`. Add a `put()` override to `AssociativeCacheBucket`'s `Bucket<K, V>` impl that inserts new (non-existing) items at the midpoint of the current items vector instead of pushing to the back. The existing-key update path and the eviction path are unchanged.

Concretely, replace the default `put()` method with this implementation inside the `impl<K, V> Bucket<K, V> for AssociativeCacheBucket<K, V>` block:

```rust
fn put(&mut self, item: Item<K, V>) -> (&Item<K, V>, Option<Item<K, V>>) {
    // Existing-key update: refresh value and apply policy's access side-effect
    if let Some(position) = self.get_position(&item.key) {
        self.items[position].value = item.value;
        let pushed_item = self.get_from_position(position);
        return (pushed_item, None);
    }
    // Evict first so we compute midpoint on the post-eviction size
    let evicted_item = if self.is_full() { self.evict_item() } else { None };
    // Insert at midpoint: new items land in the middle of the recency order,
    // neither as the hottest (back) nor the coldest (front) item.
    let mid = self.items.len() / 2;
    self.items.insert(mid, item);
    (&self.items[mid], evicted_item)
}
```

All other methods in `AssociativeCacheBucket` (`new`, `get_items`, `get_items_mut`, `get_max_size`, `get_eviction_policy`, `get_from_position`, `Display`) are kept identical to the baseline. The eviction policy remains ClassicLRU (unchanged), so GET hits still invoke `remove + push` moving the accessed item to the back — the change only affects where *new* items enter the list.

## Rationale

In the baseline ClassicLRU, a newly inserted item is pushed to the back (position `len-1`), making it the least-likely candidate for immediate eviction. This means a sequential scan that inserts many cold items places all of them at the MRU end, pushing warm/recurrent items toward the eviction front. Mid-point insertion is used in production systems (e.g., MySQL InnoDB's buffer pool) specifically to defend against this pattern: cold items start at a middle position and drift toward the eviction front if never accessed again, while a single GET hit will still promote them all the way to the back. This tests whether the LIRS workload-a trace has enough scan-like traffic to benefit from this protection without touching the eviction-policy or geometry axes.
