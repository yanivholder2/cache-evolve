# H03

Adding a post-decay cold re-scan in the warm-lock eviction path (instead of unconditionally removing index 0) will raise hit-rate by ensuring cold-first selection is honored even for items that become cold only after the decay pass.

## Parent

cycle/0008/v003

## Changes

In `evict_item()` in `src/associative_cache/associative_cache_bucket.rs`, change the final
step of the warm-lock path to re-scan for the first cold item after applying the bulk
`saturating_sub(2)` decay, rather than blindly removing the LRU front at index 0:

Current code (Step 2, after decay loop):
```rust
// Evict the LRU front (index 0); it is now cold (or near-cold) after decay.
Some(self.remove_at(0))
```

New code (Step 2, after decay loop):
```rust
// Re-scan for the first cold item that the decay pass just created.
// Items that had counter 1 or 2 are now cold (counter == 0).
// Fall back to index 0 (LRU front) if none are cold — this can only happen
// when all items had counter >= 3 before decay, i.e., all are now counter >= 1.
let post_decay_cold = self.items.iter().position(|item| item.lfu_counter == 0);
Some(self.remove_at(post_decay_cold.unwrap_or(0)))
```

No other changes: the pre-decay cold-first scan (Step 1), the decay loop magnitude
(`saturating_sub(2)`), mid-point insertion in `put()`, the counter cap at 4 in
`eviction_policy.rs`, and the factor-4 wide-bucket layout in `geometry.rs` all remain as-is.

The `unwrap_or(0)` fallback is sound: it fires only when all items had counter ≥ 3 before
decay (all now counter ≥ 1 after saturating_sub(2)), which is a valid warm state — removing
the LRU front (index 0, the oldest item) remains the correct tie-break.

## Rationale

Under mid-point insertion combined with LRU promotion-to-back, index 0 holds the item that
has been in the bucket the longest without a GET hit — which makes it a good eviction candidate.
However, there is no guarantee that index 0 has the lowest counter. An item inserted at the
mid-point that was never accessed (counter 0) would already have been caught by Step 1's
pre-decay scan. But consider a scenario where: index 0 has counter 3 (it accumulated three
hits since the last decay and was gradually pushed toward the front by subsequent
insertions/promotions); while an item at a middle index has counter 1 (inserted at mid-point
and accessed once, but now aging). After decay-by-2, index 0 → counter 1 (still warm),
middle item → counter 0 (cold). The current code evicts index 0 (warm, counter 1) instead of
the genuinely colder middle item. The post-decay re-scan corrects this by honoring cold-first
semantics even in the warm-lock recovery path, at the cost of one additional O(n) scan pass —
a cost that only fires during the rare warm-lock event, not on every eviction call.
