# H02

Changing the SLRU probationary/protected segment split from 50/50 to 25/75 will raise hit-rate by giving the confirmed hot working set a larger residency budget per bucket, reducing displacement of protected items by one-hit wonders.

## Parent

cycle/0009/v003

## Changes

In `src/associative_cache/associative_cache_bucket.rs` (the SLRU bucket implementation from
cycle/0009/v003), change `prob_cap()` to allocate only 25% of `max_size` to the probationary
segment instead of 50%:

Current code:
```rust
fn prob_cap(&self) -> usize {
    self.max_size / 2
}
fn prot_cap(&self) -> usize {
    self.max_size - self.prob_cap()
}
```

New code:
```rust
fn prob_cap(&self) -> usize {
    // 25% probationary; at least 1 slot to keep the tier active.
    (self.max_size / 4).max(1)
}
fn prot_cap(&self) -> usize {
    // 75% protected — the remaining capacity after the probationary reserve.
    self.max_size - self.prob_cap()
}
```

For a 64-slot bucket (factor-4 wide geometry with default 2048 capacity):
- Before: 32 probationary + 32 protected
- After:  16 probationary + 48 protected

All other logic from cycle/0009/v003 is preserved unchanged:
- Probationary insertion at the back of the probationary segment.
- Promotion from probationary to protected on the first GET hit (`get_from_position`).
- Demotion of the oldest protected item to probationary-front when protected is full.
- Cold-first eviction scan across probationary only (Step 1 of `evict_item`).
- Decay-by-2 warm-lock confined to probationary (Step 2 of `evict_item`).
- Fallback eviction of the oldest probationary item, then oldest protected if probationary is empty.
- Wide-bucket factor-4 geometry from `geometry.rs`.

The `prob_count` field semantics are unchanged; the only behavioral difference is how
`prob_cap()` and `prot_cap()` constrain the segment boundaries.

## Rationale

Cycle 0009 explicitly identifies the 50/50 split as the top open question for the SLRU branch:
"What proportion of SLRU's deficit is attributable to the 50/50 segment split? A protected-heavy
split (e.g., 25/75) might retain more of the working set per bucket." With a 50/50 split and
wide (64-slot) buckets, the protected tier holds only 32 items per bucket. If the hot working
set per bucket exceeds 32 items, legitimate hot items are demoted back to probationary and
become eviction candidates alongside true one-hit wonders. A 75% protected allocation raises
the hot-item retention budget to 48 slots per bucket, reducing unnecessary demotion of the
working set. The probationary filter still exists at 25% (16 slots per wide bucket) — enough
to absorb typical scan bursts before they reach the protected tier.
