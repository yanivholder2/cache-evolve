# H01

Re-scanning for the first genuinely-cold item after the bulk-decay pass — instead of blindly removing index 0 — will raise hit-rate by ensuring warm-lock eviction targets only items whose counter has actually reached zero.

## Parent

cycle/0005/v003

## Changes

Modify only `src/associative_cache/associative_cache_bucket.rs`; all other overlay files (eviction_policy.rs with the counter cap at 4, geometry.rs with the factor-4 wide-bucket layout) are inherited unchanged from cycle/0005/v003.

In `evict_item()`, the warm-lock fallback currently decays all counters by 1 and then unconditionally removes `index 0`:

```rust
for item in self.items.iter_mut() {
    item.lfu_counter -= 1;
}
Some(self.remove_at(0))
```

Replace `remove_at(0)` with a post-decay cold scan that mirrors the normal cold-first logic:

```rust
for item in self.items.iter_mut() {
    item.lfu_counter -= 1;
}
// After decay, evict the first item that is now genuinely cold (counter == 0).
// Falls back to index 0 if no item reached counter == 0 (all had counter >= 2 before decay).
let cold_idx = self.items
    .iter()
    .position(|item| item.lfu_counter == 0)
    .unwrap_or(0);
Some(self.remove_at(cold_idx))
```

**Why this matters:** after the bulk decay, items that were at `lfu_counter == 1` before the pass become cold (`lfu_counter == 0`). Items that were at `lfu_counter >= 2` are still warm. The current code ignores this distinction and evicts index 0 regardless of its post-decay counter, which can mean evicting a still-warm item (counter >= 1) at the front while a genuinely cold item (counter == 0) sits at a higher index. The fix aligns the warm-lock resolution with the same cold-first principle used on the normal path: prefer the first cold item in insertion order; only fall back to index 0 if no item reached zero after decay. The invariant that all items have `lfu_counter >= 1` before the decay pass is preserved (unchanged from the parent), so the `saturating_sub` / direct `- 1` is still safe.
