# H02

Capping the protected segment at half the bucket and demoting the oldest protected key back into probation (instead of evicting it) will raise hit-rate by guaranteeing rising keys a longer FIFO probation lap.

## Parent

cycle/0003/v002

## Changes

Add explicit segment sizing to the segmented bucket in
`src/associative_cache/associative_cache_bucket.rs`. Cycle 0003's v003 capped
the protected segment at `(max_size*4)/5` and the cap never fired because the
protected segment never grew that large; this hypothesis sets a **much tighter
cap** so the cap is live, and **demotes** rather than evicts so no proven key is
discarded.

- Define a protected cap `protected_cap = max_size / 2` (at least 1).
- In `get_from_position`, when promoting a probationary item (the 0→1
  transition that moves it to the protected back), first count how many items
  are currently protected (`lfu_counter >= 1`). If that count is already at
  `protected_cap`, demote the **oldest protected item** before promoting:
  find the protected item nearest the protected LRU end (lowest index with
  `lfu_counter >= 1`), reset its `lfu_counter` to 0, and move it to the
  probationary front (index 0) so it re-enters the FIFO probation queue as the
  newest probationary entry. Then perform the normal promotion of the hit item
  to the protected back. This keeps total occupancy unchanged (a demotion plus
  a promotion, no eviction).
- Leave `put` (admit at probationary front) and `eviction_candidate_index`
  (evict oldest `lfu_counter == 0`, fall back to protected LRU at index 0)
  exactly as in the parent.

The intended effect is that at least `max_size - protected_cap` slots are always
probationary, so a newly admitted key gets a longer lap to earn its second hit
before becoming the eviction candidate. Preserve all bucket invariants:
occupancy never exceeds `max_size`, eviction still only happens on a full `put`,
and the demotion path must not change which item is returned by
`get_from_position`.
