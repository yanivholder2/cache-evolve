# H03

A segmented (SLRU-style) bucket that admits new keys to a probationary front region and only promotes them to a protected back region on their second hit raises hit-rate by demanding proof of reuse before granting protection.

## Parent

baseline

## Changes

Start from the baseline `AssociativeCacheBucket` (delegates to the ClassicLRU
policy: hit moves item to back, victim is index `0`). Implement an in-bucket
Segmented-LRU without adding any `EvictionPolicyKind` variant. Treat each item's
existing `lfu_counter` field as a promotion flag: 0 = probationary, ≥1 =
protected. Override `put` so a *new* key is inserted at index `0` with
`lfu_counter = 0` (probationary front), after evicting one item when full (P1).
Override `get_from_position` so that on a hit: if the item is still probationary
(`lfu_counter == 0`), set `lfu_counter = 1` and move it to the back (promote into
the protected region); if already protected, just move it to the back
(MRU within the protected region) and leave the counter at 1. Override
`eviction_candidate_index` to evict the *probationary* item nearest the front
first — scan from index `0` for the first item with `lfu_counter == 0` — and only
fall back to index `0` (the protected LRU end) when every item is protected. This
gives a true two-segment SLRU: scan/one-hit-wonder keys churn through the
probationary front and are evicted before any protected key, while a key proven
by a second access is shielded. Keep bucket geometry, routing, capacity
invariants, and the JNI ordinal mapping untouched.

## Rationale (optional)

This is structurally distinct from H01/H02: rather than tuning a frequency
scalar, it partitions the bucket into protected/probationary segments with an
explicit promote-on-second-hit rule — the canonical scan-resistant admission
scheme, testing whether segmentation beats both pure-frequency and
single-position admission.
