# H03

Lowering the main-queue eviction threshold from `freq > 1` to `freq > 0` grants items one additional second-chance recycle pass before eviction, extending the protection window for eagerly-promoted items whose frequency was decremented to 1 at the tail and reducing their premature eviction on Zipfian traces.

## Parent

cycle/0008/v002

## Changes

In `evict_main()`, change the second-chance guard from `tail.freq > 1` to `tail.freq > 0`:

```rust
fn evict_main(&mut self) {
    while let Some(mut tail) = self.main.pop_back() {
        if tail.freq > 0 {
            tail.freq -= 1;
            self.main.push_front(tail);
        } else {
            // freq == 0: evict immediately
            break;
        }
    }
}
```

All other logic stays identical to cycle/0008/v002 — `capacity / 14` small queue, eager promotion at freq >= 2 in `get()`, ghost cap at `main_size / 2`, and MAX_FREQ = 5. Update the comment in `evict_main()` to reflect the new threshold semantics.

The rationale: eager promotion (introduced in cycle 0007) deposits items into main at freq==2. Under the current `freq > 1` threshold, such an item is recycled once (freq 2→1, pushed to front), and then evicted on its second pass to the tail (freq==1 is not > 1). The `freq > 0` threshold gives that same item one additional recycle pass (freq 1→0, pushed to front), so it is only evicted when it reaches the tail a third time at freq==0. This matches the intuition from the cycle 0008 open question about a "frequency-relative" threshold: rather than an absolute cutoff that misfires when entry frequencies shift due to structural changes, extending the recycle window by one pass accommodates the higher entry frequency established by eager promotion without requiring a separate metadata field. The downside is that marginal items at freq==1 survive longer in main; on a Zipfian workload the hot set accumulates frequency far faster than the eviction drain, so those extra passes should be claimed by genuinely hot items rather than cold squatters.
