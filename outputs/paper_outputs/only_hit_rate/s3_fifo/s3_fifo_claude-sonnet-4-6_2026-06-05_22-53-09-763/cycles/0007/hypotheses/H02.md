# H02

Selecting the weakest eviction candidate from among the last three items in main, rather than blindly evicting the tail item, raises hit rate by avoiding accidental eviction of temporarily-low-positioned but genuinely warm items.

## Parent

cycle/0006/v001

## Changes

Replace the eviction-victim selection logic inside `evict_main()` with a small tournament among the rear-most candidates.

Current v001 `evict_main()`:
```
while let Some(mut tail) = self.main.pop_back() {
    if tail.freq > 1 { tail.freq -= 1; self.main.push_front(tail); }
    else { break; }
}
```

New logic:
```
loop {
    let len = self.main.len();
    if len == 0 { break; }
    let window = len.min(3);
    let start = len - window;
    // Find the index with the minimum freq; break ties toward the rearmost (highest index).
    let worst_idx = (start..len)
        .max_by_key(|&i| (MAX_FREQ - self.main[i].freq, i))
        .unwrap();
    let mut entry = self.main.remove(worst_idx).unwrap();
    if entry.freq > 1 {
        entry.freq -= 1;
        self.main.push_front(entry);
        // A slot was not freed; continue until we evict one item.
    } else {
        // freq <= 1: evict (discard entry, break).
        break;
    }
}
```

Key implementation notes:
- `self.main.remove(worst_idx)` on a `VecDeque<Entry<K,V>>` is O(min(idx, len-idx)), which is acceptable for small indices from the rear end.
- The loop terminates because every iteration either evicts an item (loop exits) or decrements the freq of one item by 1. Since MAX_FREQ is bounded and the total freq budget of the queue is finite, the loop cannot spin indefinitely.
- The `>` direction in `max_by_key` for the freq component ensures the *lowest* freq item is chosen (we maximise `MAX_FREQ - freq`). Ties in freq go to the rearmost index (`i`) which matches the existing tail-first convention.
- All other v001 invariants are preserved: `small_size = capacity / 10`, `ghost_size = main_size / 2`, `MAX_FREQ = 5`, promotion threshold `freq > 1` in `evict_small`, and the unchanged `get()` and `put()` paths.

## Rationale

Move-to-front continuously repositions recently-accessed items toward the head of main, so the tail naturally accumulates the least-recently-accessed entries. However, position and frequency can diverge: a freq=0 item can sit one slot ahead of the tail item that has freq=1, because it arrived at its current position earlier but was never re-accessed. The current evict_main always takes the tail, evicting the freq=1 item and leaving the freq=0 item — the wrong choice by frequency signal. A window of three items is large enough to capture such local inversions without scanning deep into main (which would degrade the recency signal that move-to-front provides) and imposes negligible overhead on each eviction call.
