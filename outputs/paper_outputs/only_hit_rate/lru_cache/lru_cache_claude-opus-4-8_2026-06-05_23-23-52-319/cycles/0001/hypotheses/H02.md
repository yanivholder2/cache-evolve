# H02

Insert new keys at a midpoint of the LRU list instead of the MRU tail, so one-hit-wonders sink and evict quickly while reused keys earn the hot region, raising hit-rate.

## Parent

baseline

## Changes

Change the insertion position for new (miss) entries in `put`. Today a
new/reused slot is appended at the tail (MRU) via `push_back`. Instead,
insert new entries at a **midpoint** of the list: a fixed fraction
(start with 5/8 of the way from head to tail, i.e. closer to the MRU
end) rather than the very tail.

Implementation:
- Add a helper `insert_at_midpoint(idx)` that walks `next` pointers from
  `head` for `floor(len * 5 / 8)` steps and splices the node in there,
  updating the four neighbouring `prev`/`next` links. For `len <= 1`
  this degenerates to `push_back`.
- Keep `get` promotion unchanged: a hit still moves the node to the true
  tail (MRU) via `unlink` + `push_back`. This is what lets a genuinely
  reused key climb above the midpoint into the protected region; a key
  that is never re-accessed stays below the midpoint and reaches `head`
  (eviction) sooner than under tail insertion.
- Eviction still removes `head` and reuses its slot; capacity is
  untouched, so P1 holds. Values are only stored for resident keys, so
  P2/P3 hold.

Keep the change to a single contiguous list — no extra segments or
per-node flags — so this stays mechanically distinct from a segmented
design.

## Rationale (optional)

Midpoint insertion (as used by some production LRUs) protects the hot
region from scan/one-hit-wonder pollution without the bookkeeping of two
segments, isolating the value of insertion-position bias for hit-rate.
