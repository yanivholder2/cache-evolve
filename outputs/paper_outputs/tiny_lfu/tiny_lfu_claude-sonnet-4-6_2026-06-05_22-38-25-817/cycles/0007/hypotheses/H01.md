# H01

Doubling the CountMinSketch width factor from 4× to 8× capacity halves the expected per-row hash collision rate, sharpening frequency estimates further beyond what conservative update alone provides to raise hit rate.

## Parent

cycle/0006/v002

## Changes

In `src/tiny_lfu/mod.rs`, change the module-level constant:

```rust
const SKETCH_WIDTH_FACTOR: usize = 4;
```

to:

```rust
const SKETCH_WIDTH_FACTOR: usize = 8;
```

No other changes are needed. The computed sketch width in `try_new()` —
`(capacity * SKETCH_WIDTH_FACTOR).max(MIN_SKETCH_WIDTH).next_power_of_two()` —
doubles automatically for any capacity ≥ 4, giving a sketch width of 8× capacity
rounded up to the next power of two (e.g., 16 384 columns for capacity=2048).

All other logic inherited from cycle/0006/v002 is preserved unchanged: the
conservative CMS update in `increment()`, `PROMO_THRESHOLD=8` with the
`was_protected` bypass in `get()`, the k=4 minimum-frequency victim scan in
`put()`, the simple LRU-order demotion in `maybe_demote_from_protected()`, and the
90/10 protected/probationary split in `try_new()`.

## Rationale

Conservative update (cycle/0006/v002) reduced the effect of hash collisions by
only incrementing rows at the current minimum, but it cannot eliminate collisions
— two keys sharing a counter cell still inflate each other's estimates.  A wider
sketch reduces the probability that any two keys hash to the same position in a
given row, cutting the base collision rate in half.  The two mechanisms are
complementary: width reduces how often collisions happen; conservative update
limits how much they inflate estimates when they do happen.  Combining a wider
sketch with conservative update should produce tighter frequency estimates than
either change alone, enabling the k=4 victim scan and PROMO_THRESHOLD gate to
make fewer wrong decisions.
