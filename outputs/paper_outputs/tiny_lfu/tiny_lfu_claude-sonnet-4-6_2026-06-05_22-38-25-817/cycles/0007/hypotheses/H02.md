# H02

Lowering PROMO_THRESHOLD from 8 to 4 recalibrates the promotion gate for the tighter frequency estimates produced by conservative CMS update, admitting genuinely medium-hot items that now stall below the original threshold to raise hit rate.

## Parent

cycle/0006/v002

## Changes

In `src/tiny_lfu/mod.rs`, change the module-level constant:

```rust
const PROMO_THRESHOLD: u32 = 8;
```

to:

```rust
const PROMO_THRESHOLD: u32 = 4;
```

No other changes are needed. The promotion check in `get()` —
`if freq >= PROMO_THRESHOLD || self.nodes[idx].was_protected` — uses this
constant directly; the `was_protected` bypass remains intact and unchanged.
All other logic (conservative update, width factor=4, k=4 victim scan,
90/10 split) is preserved.

## Rationale

`PROMO_THRESHOLD=8` was originally calibrated against standard CMS update, which
inflates estimated frequencies via hash collisions.  An item with true access
count 5–6 could reach an estimated frequency of 8 simply because it shared
counter cells with other keys, clearing the threshold with artificially inflated
counts.  Conservative update eliminates this inflation: it only increments rows
already at the minimum, so the estimate stays close to the true minimum.  An item
that would have shown estimated freq=8 under standard update might now show
estimated freq=4–5 under conservative update — and never qualify for promotion
under the unchanged threshold.  These are precisely the medium-hot items in the
second tier of the Zipfian distribution (visited several times but not among the
top percentile) that belong in protected.  Lowering PROMO_THRESHOLD to 4 restores
the intended admission behaviour under the new, more accurate frequency scale
without making the gate trivially open (items must still have been accessed at
least 4 times before promotion).
