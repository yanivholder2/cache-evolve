# H02

Combining frequency-ordered demotion from the protected segment with the cycle/0009/v001 baseline (PROMO_THRESHOLD=6) will raise hit rate by preferring to evict the lowest-frequency protected resident rather than the LRU head during overflow, a combination that has not previously been evaluated together.

## Parent

cycle/0009/v001

## Changes

In `src/tiny_lfu/mod.rs`, introduce a new constant above `PROMO_THRESHOLD`:

```rust
/// Number of LRU-end protected candidates to scan when selecting the demotion
/// victim during protected-segment overflow.
const PROT_DEMOTION_SCAN_K: usize = 4;
```

Then replace the body of `maybe_demote_from_protected()` with a frequency-scan variant. Currently the function always demotes `prot_head` (the LRU head). Change it so that when `protected_len > protected_capacity` it:

1. Starts a cursor at `prot_head` and walks forward through `node.next` for up to `PROT_DEMOTION_SCAN_K` steps.
2. Tracks which candidate has the minimum `sketch.estimate(&node.key)`.
3. Calls `prot_unlink(min_idx)` on the minimum-frequency candidate rather than unconditionally on `prot_head`.
4. Continues with the existing logic: `protected_len -= 1`, `nodes[min_idx].was_protected = true`, `prob_push_back(min_idx)`, `probationary_len += 1`.
5. Repeats the loop until `protected_len <= protected_capacity`.

All other logic is unchanged: PROMO_THRESHOLD remains 6, `was_protected` bypass remains intact, probationary victim scan remains k=4.

### Why this combination is novel

Cycle 0009 v003 tested frequency-ordered protected demotion but was parented from `cycle/0008/v001`, which still had PROMO_THRESHOLD=8. Under that higher gate the protected segment's LRU tail has a very narrow frequency spread (all residents cleared 8+), so the scan rarely found a colder candidate. With PROMO_THRESHOLD=6 (the current baseline) the entry bar is lower and frequency heterogeneity within the protected segment is slightly wider, giving the scan more opportunity to make a discriminating choice.
