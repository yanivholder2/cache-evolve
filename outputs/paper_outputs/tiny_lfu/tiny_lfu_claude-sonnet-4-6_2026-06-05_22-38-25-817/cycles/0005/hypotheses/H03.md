# H03

Expanding the protected segment from 90% to 95% of capacity in cycle/0004/v003 reduces overflow-demotion pressure and improves hit rate by giving promoted hot items more room to survive.

## Parent

cycle/0004/v003

## Changes

In the cycle/0004/v003 overlay (`src/tiny_lfu/mod.rs`), inside `try_new()`, change the protected-capacity calculation from:

```rust
let protected_capacity = (capacity * 9) / 10;
```

to:

```rust
let protected_capacity = (capacity * 19) / 20;
```

This shifts the split from 90/10 to 95/5. For the benchmark size of capacity=2048: protected goes from 1843→1945 slots (+102), probationary shrinks from 205→103 slots. The `probationary_capacity` field is derived as `capacity - protected_capacity` and remains correct without further changes.

No other code is modified. The k=4 victim-scan loop in `put()`, the unconditional promotion in `get()`, `maybe_demote_from_protected()`, and the TinyLFU admission gate all carry over unchanged from v003.

Preserve the existing unit tests; `eviction_prefers_hot_items`, `low_frequency_new_item_is_rejected`, and `min_freq_victim_preferred_over_lru_head` all use capacity≤8 where the new ratio produces `protected_capacity = (8 * 19)/20 = 7`, identical to the old `(8 * 9)/10 = 7`, so the tests remain valid.

## Rationale

Every cycle from 0001 onward has benefited from a larger protected segment (80/20 → 90/10). The trend suggests more protected headroom consistently pays off on this Zipfian trace because hot items concentrate in a small key subset and benefit from a stable residence. The 90/10 boundary is arbitrary; 95/5 probes whether the gain saturates or continues. The probationary segment retains enough slots (~103) for the k=4 scan to operate meaningfully, since the scan only compares 4 candidates regardless of probationary size.
