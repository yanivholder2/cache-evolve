# H03

Segmenting the resident set into a small probationary region and a protected region (SLRU), evicting only from probationary, raises hit-rate by shielding proven-hot keys from being trampled by churn.

## Parent

cycle/0003/v001

## Changes

Start from v001 (wide sketch, `SKETCH_WIDTH_FACTOR = 64`, strict LRU-head victim). Convert the single LRU list into a two-segment SLRU within the *main* cache (this is a main-space split, NOT a W-TinyLFU admission window, which is refuted): a protected segment sized at `floor(capacity * 0.8)` and a probationary segment for the remainder (`capacity - protected_cap`, at least 1). Implement either as two head/tail link pairs over the existing `nodes` arena plus a per-node `protected: bool` flag, or two intrusive lists; reuse `unlink`/`push_back` style helpers per segment.

Behaviour:
- New admitted keys enter the probationary tail.
- On a `get`/`put` hit, increment the sketch as today, then promote the node to the protected tail; if protected now exceeds `protected_cap`, demote its head (LRU) node to the probationary tail.
- Eviction (cache full, new key) considers only the probationary head as victim and keeps the existing `incoming_freq > victim_freq` admission test against it; on admit, overwrite that probationary slot in place and leave it in probationary.

Keep the count-min sketch, increment, and estimate logic byte-for-byte from v001 — this isolates the recency-protection axis. The cross-cycle notes say recency "lives in LRU position and is easily trampled"; SLRU gives hot residents a protected tier the admission churn cannot reach directly. Preserve correctness at tiny capacities (e.g. capacity 2 → protected_cap 1, probationary 1) and update the unit tests so eviction expectations match the new segment-aware victim choice.
