# H03

Reduce sketch width from 4 to 3 to cut metadata overhead by 25% and validate whether the current width is overprovisioned for this cache size and workload.

## Parent

baseline

## Changes

In `src/tiny_lfu/mod.rs`, line 9, change the sketch width factor constant:

```rust
// Old:
const SKETCH_WIDTH_FACTOR: usize = 4;

// New:
const SKETCH_WIDTH_FACTOR: usize = 3;
```

This is the only change required. The sketch width is computed as `(capacity * SKETCH_WIDTH_FACTOR).max(MIN_SKETCH_WIDTH).next_power_of_two()` in the `try_new()` method (line 41–43), so reducing the factor automatically shrinks the hash table from 4 entries per cache slot to 3, reducing total sketch heap memory by approximately 25%.

No other code changes needed; the depth remains 3, the hash function remains unchanged, admission threshold remains `incoming_freq > victim_freq`, and eviction strategy remains LRU-only (baseline behavior). Sketch geometry is the sole tuning axis.

## Rationale

The cross-cycle insights document confirms that "Depth-3, width-4 is the stable baseline across cycles 0002–0006" and that width expansion (cycle 0001, v001) was high-ROI but became expensive at larger scales (cycle 0003, v001). This suggests the current width may be overprovisioned relative to the cache capacity and Zipfian workload characteristics. Cycle 0002's depth reduction to 3 achieved 25% per-operation latency improvement; this hypothesis tests whether an orthogonal reduction in width (from 4 to 3) can deliver metadata savings and latency recovery without unacceptable hit-rate loss. If width-3 remains competitive, it establishes a new, leaner baseline; if it degrades hit-rate significantly, it confirms width-4 is necessary. This targets both metadata-size and per-op-time dimensions, orthogonal to eviction policy or admission tuning.
