# H01

Reduce sketch width factor from 4 to 2 to validate the lower bound of sketch geometry following cycle 0007's width-3 success.

## Parent

cycle/0006/v001

## Changes

In `src/tiny_lfu/mod.rs`, line 9, change the sketch width factor constant:

```rust
// Old:
const SKETCH_WIDTH_FACTOR: usize = 4;

// New:
const SKETCH_WIDTH_FACTOR: usize = 2;
```

No other changes required. The sketch width is computed via `next_power_of_two()`, so reducing the factor shrinks the hash table width by 50%. Keep depth unchanged at 3 and preserve N=2 frequency-aware victim selection from the parent. The allocation mechanism remains identical; only the width parameter tunes the sketch's collision density.

## Rationale

Cycle 0007 v003 proved that reducing width from 4 to 3 delivers ~17% latency improvement without hit-rate loss, due to improved cache locality and leaner computation. The cross-cycle-insights document explicitly asks: "Can width shrink further than depth-3, width-3?" This hypothesis directly tests that boundary by pushing width from 4 to 2, a 50% reduction. If width-2 maintains hit-rate within 0.3% of the incumbent (0.7354), it establishes a new efficiency frontier; if it degrades hit-rate materially, it confirms width-3 is the practical lower bound. This tests the orthogonal width dimension while holding eviction policy (N=2) and depth (3) constant.
