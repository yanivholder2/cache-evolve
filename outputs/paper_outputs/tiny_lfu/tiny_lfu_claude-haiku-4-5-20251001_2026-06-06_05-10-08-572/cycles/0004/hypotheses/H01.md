# H01

Apply sketch decay at an aggressive 250k operation interval to the depth-3 baseline to maximize hit-rate responsiveness to workload phase changes while preserving per-operation latency advantages.

## Parent

cycle/0002/v002

## Changes

Add an `op_count: u64` field to the `CountMinSketch` struct to track operations since the last decay event. Implement a `decay_if_needed()` method that halves all counter values using bitwise right-shift when `op_count >= 250_000`, then resets `op_count` to 0. Call `decay_if_needed()` at the start of both `increment()` and `estimate()` methods to ensure decay is checked on every operation. This more aggressive decay schedule (250k vs. v003's 500k) reduces the window for stale frequency estimates, making admission decisions more responsive to recent workload shifts. The decay mechanism directly mirrors v003's implementation but with a shorter interval to test whether tighter temporal freshness yields improved hit-rate without the latency cost of wider sketches.
