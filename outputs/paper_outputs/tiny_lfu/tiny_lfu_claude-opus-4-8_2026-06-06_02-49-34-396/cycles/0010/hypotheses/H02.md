# H02

Drop the per-`get` LRU move-to-back so recency degrades to insertion order, lowering the scored per-op-time (get p50) and testing whether the reorder earns its cost.

## Parent

cycle/0005/v001

## Changes

In `TinyLfuCache::get`, the hit path currently runs
`self.sketch.increment(key)` then `self.unlink(idx); self.push_back(idx)` to
move the accessed node to the MRU tail on every hit. The
`unlink`+`push_back` pair is ~7 pointer writes (touching up to four nodes)
executed on *every* get, and the per-op-time fitness summary is driven by
get p50 — so this surgery sits directly on the scored metric.

Remove the reorder from `get`:

- Delete the `self.unlink(idx); self.push_back(idx);` calls in `get`,
  keeping the `sketch.increment` and the `Some(&self.nodes[idx].value)`
  return.
- Leave `put` unchanged: new admissions still `push_back`, and the
  sampled-coldest eviction walk still scans forward from `head`. The list
  therefore becomes insertion-ordered (FIFO-ish) rather than strict LRU; the
  eviction walk now samples the oldest-*inserted* (not oldest-*accessed*)
  entries.

Preserve all frequency/admission logic: eviction is still driven by
`sketch.estimate` and the `incoming_freq > victim_freq` gate, so recency only
ever influenced *which* candidates enter the sample window, not whether a hot
entry is protected. No struct changes, so metadata-size stays at 24 bytes.

## Rationale (optional)

Hit-rate is admission-bound, not recency-bound, on this trace (cross-cycle
notes: list shape is inert because the frequency gate already filters). If
that holds, removing the only remaining per-hit list work is a clean get-p50
win; if hit-rate drops, it quantifies exactly what the LRU reorder buys.
