# H03

Add a small LRU admission window (W-TinyLFU style) in front of v003's main cache so genuinely hot newcomers survive cold-start before facing the frequency filter, lifting hit-rate.

## Parent

cycle/0003/v003

## Changes

Attack the residency/admission frontier directly. v003 admits a newcomer only
when, on a full cache, its sketch estimate strictly exceeds the sampled victim's
— but a brand-new hot key has a near-zero estimate on first sight and is
rejected before it can accumulate frequency. Introduce a tiny window cache, the
W-TinyLFU pattern:

- Partition capacity into a window region (~1% of capacity, but at least 1 slot;
  e.g. `window_cap = (capacity / 100).max(1)`) and a main region
  (`main_cap = capacity - window_cap`). Track membership with a per-node region
  flag or two separate intrusive LRU chains over the existing `nodes` arena;
  reuse the existing `prev`/`next` link machinery.
- On `put` of a new key: increment the sketch (as today), then insert into the
  window LRU's MRU position. If the window is over `window_cap`, take the
  window's LRU entry as the *admission candidate*.
- Run the existing frequency-comparison admission test between the window
  candidate and the main cache's sampled-coldest victim (keep v003's
  `SAMPLE_VICTIMS` sampled-coldest walk for the main victim). If the candidate's
  estimate exceeds the main victim's, move the candidate into the main region
  and evict the main victim; otherwise drop the candidate. Keys already resident
  (window or main) keep today's promote-to-MRU-of-their-region behaviour on
  `get`/`put`.
- Preserve all of v003's efficiency machinery (FastHasher, u8 sketch,
  double-hashing) and keep the five existing unit tests passing; the small
  capacities they use (2-4) must still behave sanely with `window_cap = 1`.

The claim is that buffering newcomers in a recency window before the frequency
gate rescues hot cold-start keys that strict TinyLFU admission discards,
improving hit-rate over v003's window-less design.
