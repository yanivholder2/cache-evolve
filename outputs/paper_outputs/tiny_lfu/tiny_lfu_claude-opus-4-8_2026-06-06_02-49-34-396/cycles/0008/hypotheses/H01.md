# H01

Applying conservative (minimal-increment) counter update on the wide factor-16 sketch raises hit-rate by sharpening the frequency estimate, the only lever demonstrated to move hit-rate.

## Parent

cycle/0005/v001

## Changes

This directly answers the standing open question carried since Cycle 0006:
conservative update produced a real hit-rate gain on the *narrow* factor-4
sketch (cycle/0006/v002) — does the estimate-sharpening still pay on the
wider factor-16 base where collision over-count is already lower?

Replace the unconditional per-row increment in `CountMinSketch::increment`
with conservative (minimal-increment) counting, mirroring cycle/0006/v002:

1. Compute the base hash once via `self.base_hash(key)`.
2. Scan the `depth` rows for this key and find the current minimum counter
   value across `self.counts[row][position_for(h, row)]`.
3. If that minimum is already `>= MAX_COUNT`, return early (saturated; no
   row can be raised).
4. Otherwise increment only those rows whose counter `== min`, leaving rows
   sitting above the minimum (which carry another key's mass) untouched.

Leave `estimate`, `position_for`, `base_hash`, eviction sampling, and node
layout exactly as in the parent. The hypothesis is that on the wide sketch
the accuracy gain is smaller than on factor-4 but the per-op min-scan tax
(noted in cycle/0006/v002's insight as a broad hot-path cost) is the same,
so the net is the question under test. Preserve the MAX_COUNT saturation
invariant: no counter may exceed `MAX_COUNT`.

## Rationale (optional)

cycle/0005/v001 is the standing cross-cycle winner (hit-rate 0.7425,
metadata 24, per-op 44) and the recommended base from the Cycle 0007
continuation. Conservative update is the one live estimate-sharpening
candidate not yet ruled flat on this base.
