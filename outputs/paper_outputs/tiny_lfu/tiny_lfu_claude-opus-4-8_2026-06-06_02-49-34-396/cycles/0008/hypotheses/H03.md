# H03

Doubling the sketch width factor from 16 to 32 reduces counter collisions further and raises hit-rate, with no change to the scored metadata-size (which is node-bound at 24 B) and only a per-op-time cost.

## Parent

cycle/0005/v001

## Changes

Change the single constant `SKETCH_WIDTH_FACTOR` in the parent from `16` to
`32`. This is consumed by `TinyLfuCache::try_new`, where the sketch width is
computed as `(capacity * SKETCH_WIDTH_FACTOR).max(MIN_SKETCH_WIDTH).next_power_of_two()`,
so doubling the factor doubles the power-of-two table width (and the sketch
heap), halving the expected per-column collision load.

Leave depth (`SKETCH_DEPTH = 4`), the conservative-vs-unconditional increment,
`position_for` double-hashing, eviction sampling, and node layout untouched.

This directly tests the standing open question from the cross-cycle log: "Is
there a combined sketch width/depth sweet spot, or do per-op and heap costs
stack faster than accuracy gains past current width?" Width is recorded as the
strongest demonstrated hit-rate lever (collision recovery). Crucially, the
scored `metadata-size` summary is the per-node footprint (24 B), not the sketch
heap, so the wider table does not regress the metadata axis — only per-op-time
is at risk from the larger table's cache-line stride.

Refuted if hit-rate is already saturated at factor 16 (flat gain) while per-op
time worsens; confirmed if collisions still carry recoverable accuracy at
factor 32.

## Rationale (optional)

Orthogonal to H01 (estimate-update rule) and H02 (admission decision): this
attacks sketch *geometry*. Together the three span the only three surfaces the
cross-cycle log identifies as live hit-rate levers.
