# H02

Shrinking the per-entry `Node` from `Option<usize>` links to u32 sentinel indices will lower the metadata-size axis from 48 to 24 bytes without changing hit-rate.

## Parent

baseline

## Changes

The metadata-size fitness summary has been pinned at 48 across every
variant in cycles 0001–0002 because the reported value is
`size_of::<Node<u64,u64>>()`, and no variant has touched the node
layout — only the sketch heap (a detail field). `Node` is currently
`key: u64 (8) + value: u64 (8) + prev: Option<usize> (16) + next:
Option<usize> (16) = 48`. The `Option<usize>` links carry no niche and
cost 16 bytes each. Attack this untouched axis directly:

- Add a sentinel constant `const NIL: u32 = u32::MAX;` representing "no
  link" (the cache never holds u32::MAX entries at the evaluated
  capacities, so the sentinel is unambiguous).
- Change `Node.prev` and `Node.next` from `Option<usize>` to `u32`,
  initialising new nodes' links to `NIL`.
- Change `TinyLfuCache.head` and `tail` from `Option<usize>` to `u32`,
  initialised to `NIL`.
- Rewrite `unlink` and `push_back` to branch on `== NIL` instead of
  `match Option`, and index `self.nodes[idx as usize]` where needed.
  Convert stored `usize` indices to `u32` on write and back on read.
- The `head.expect(...)` victim lookup in `put` becomes a `head == NIL`
  check (a full cache always has a non-NIL head).

This makes `Node<u64,u64>` = 8 + 8 + 4 + 4 = 24 bytes, halving the
metadata-size summary. Preserve the exact LRU ordering and admission
test — only the link representation changes, so hit-rate and per-op-time
should be unaffected (a u32 index load is no costlier than a usize one).
