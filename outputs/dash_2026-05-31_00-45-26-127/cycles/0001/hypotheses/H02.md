# H02

Replacing ClassicLRU's O(n) remove-and-push on every hit with a single-step swap toward the back lowers per-op time without materially changing eviction order.

## Parent

baseline

## Changes

Edit only `src/shared/eviction_policy.rs`. No new `EvictionPolicyKind`
variant; the existing selection wiring keeps choosing `ClassicLRU` by name,
so mutating that policy's impl in place is what changes the runtime
behaviour. The enum, its `all` / `name` / `index` / `from_usize` /
`from_name` / `all_names` / `build` methods, and all related round-trip
tests stay byte-for-byte unchanged.

Replace the `EvictionPolicy<K, V>` impl block for `ClassicLRU` with a "lazy
bubble-back" variant — the mirror of the existing `Swap` policy (which
bubbles toward the front):

- `get_from_position(items, position)`: if `position + 1 < items.len()`,
  call `items.swap(position, position + 1)` and return `position + 1`;
  otherwise (already at the back) return `position` unchanged. No
  `Vec::remove`, no `Vec::push`, no allocation, no element shift.
- `eviction_candidate_index(items)`: return `0` (front is still the cold
  end). Identical to today.
- `promotion_candidate_index(items)`: return `items.len() - 1` (back is
  still the hot end). Identical to today.
- `name(&self)`: return `"ClassicLRU"` unchanged so the existing selection
  wiring keeps selecting this policy.

Update the in-file `ClassicLRU` unit tests that assume remove-and-push
semantics (`classic_lru_get_moves_to_back`, `classic_lru_eviction_chain`)
to instead exercise the bubble-back semantics — for example, after a single
`get(&1)` on `[1, 2, 3]` the expected order is `[2, 1, 3]`, not `[2, 3, 1]`.
Tests that only depend on "front is evicted" and "back is hottest" (e.g.
`eviction_candidate_index_classic_lru`,
`promotion_candidate_index_classic_lru_fifo_swap_is_last`) keep passing
as-is.

Do not touch `src/shared/item.rs` or `src/dash/dash_bucket.rs` — no new
fields, no struct changes; the policy alone owns this behaviour.

Invariants to preserve: `get_from_position` never shortens `items` and
always returns an in-bounds index; eviction/promotion candidate indices
are in-bounds for any non-empty bucket.

## Rationale (optional)

The configured `bucketSize = 64` means today's `Vec::remove(position)`
shifts up to 63 element slots on every hit (~32 shifts on average); a
single `mem::swap` of two `Item` slots is a constant-cost replacement.
Over many hits the item still drifts toward the back, so the LRU-ish
eviction order at position 0 is approximately preserved — a per-op-time
win at a small, measurable hit-rate cost is the testable trade-off.
