# H03

Picking the eviction victim by scanning the cold quartile of the bucket for the lowest hit count — instead of blindly evicting position 0 — raises hit rate on traces where recency and frequency disagree.

## Parent

baseline

## Changes

Edit only `src/shared/eviction_policy.rs`. This hypothesis intentionally
reuses the existing `lfu_counter: usize` field on `Item` — no new metadata,
no `EvictionPolicyKind` variant, no struct changes. The new behaviour is
delivered by mutating `ClassicLRU`'s impl in place so the existing
selection wiring picks it up.

Replace the `EvictionPolicy<K, V>` impl block for `ClassicLRU`:

- `get_from_position(items, position)`: first bump
  `items[position].lfu_counter = items[position].lfu_counter.saturating_add(1);`
  then perform the existing recency move — `let item = items.remove(position);
  items.push(item); items.len() - 1`. This keeps recency-driven ordering
  while accumulating a hit-count signal on every access.
- `eviction_candidate_index(items)`: compute
  `let window = ((items.len() + 3) / 4).max(1);` (the cold quartile of the
  bucket, at least one item) and return the index of the item in
  `items[..window]` with the smallest `lfu_counter`, breaking ties by
  lowest index. Implementation:
  `items[..window].iter().enumerate().min_by_key(|(_, it)| it.lfu_counter).map(|(i, _)| i).unwrap_or(0)`.
  This narrows the LFU scan to the recency-cold front so per-eviction cost
  is bounded by `bucket_size / 4` (16 with the configured geometry of 64).
- `promotion_candidate_index(items)`: unchanged — return
  `items.len() - 1`. Segment-level "is_hottest → promote" logic keeps its
  current MRU geometry, so the cascade structure is untouched.
- `name(&self)`: return `"ClassicLRU"` unchanged so the existing selection
  wiring keeps selecting this policy.

Update only the in-file `ClassicLRU` unit tests whose expectations change.
`classic_lru_get_moves_to_back` and `eviction_candidate_index_classic_lru`
still pass (recency move and front-of-window eviction).
`classic_lru_evicts_least_recently_used` and `classic_lru_eviction_chain`
exercise a 2-slot bucket where `window == 1`, so they also still pass (the
cold quartile collapses to "position 0", matching today's victim). Verify
each as you go.

Do not touch `src/shared/item.rs` or `src/dash/dash_bucket.rs` — `Item`'s
existing `lfu_counter` field is reused as-is and the bucket struct needs no
change.

Invariants to preserve: `get_from_position` never shortens `items` and
returns an in-bounds index; the eviction/promotion candidate indices are
in-bounds for any non-empty bucket; `Item::new(key, value)` remains the
two-argument constructor with `key` / `value` / `lfu_counter` / `timestamp`
fields intact.

## Rationale (optional)

ClassicLRU's blind front-pop loses items that are about to be re-referenced
when a workload mixes scans with recurring hot keys. Scanning only the cold
front for a frequency-weighted victim is a cheap hybrid: O(bucket_size / 4)
per eviction, zero new metadata, distinct from H01's region-partitioning
strategy and from H02's per-op-time focus.
