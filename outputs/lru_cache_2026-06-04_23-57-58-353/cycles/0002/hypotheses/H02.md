# H02

Replacing strict-LRU demotion from the SLRU protected segment with frequency-aware demotion will raise hit rate by keeping modestly-reused entries in protected longer than their recency rank alone would warrant.

## Parent

cycle/0001/v001

## Changes

Add a `freq: u8` field to `Node<K, V>`, capped at 3 via saturating arithmetic. Increment it on every hit in `get()` (both protected and probationary branches) and on every `put()` that updates an existing key. Reset it to 0 whenever a node is demoted from protected back to probationary, and also when a probationary slot is reused for a brand-new key.

Change only the overflow-demotion step inside `get()` and `put()` (the block that runs when `prot_count > prot_cap`):

Instead of always demoting `prot_head`, scan from `prot_head` forward for up to 4 nodes, tracking the node with the lowest `freq`. When the scan ends, demote that lowest-frequency node (call `unlink`, decrement `prot_count`, set `in_protected = false`, call `push_back_prob`, increment `prob_count`, reset its `freq` to 0). If multiple nodes tie on `freq`, prefer the one closest to `prot_head` (i.e., the first minimum encountered in the scan).

All other logic — insertion into probationary, promotion on a probationary hit, eviction of probationary-LRU on overflow, and the fallback to protected-LRU when probationary is empty — remains identical to v001. The 80/20 split ratio is also unchanged.

## Rationale

v001 demotes strictly the oldest (LRU-end) node from protected whenever a promotion causes overflow. A node that has been accessed many times but happened to sit at the LRU end (because it was not touched recently) is treated identically to one that was promoted exactly once and never touched again. Frequency-aware demotion selects the least-useful node in a short window instead, keeping high-reuse entries anchored in protected even through dry spells.
