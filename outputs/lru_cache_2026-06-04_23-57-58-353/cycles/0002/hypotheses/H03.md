# H03

Adding a ghost set of recently evicted probationary keys to an SLRU cache will raise hit rate by routing keys that re-appear after eviction directly into the protected segment, bypassing the probationary filter.

## Parent

baseline

## Changes

Build a full SLRU cache with the same two-segment structure and 80/20 split as v001, but add a ghost admission mechanism.

Add two fields to `LruCache<K, V>`:

```rust
ghost: std::collections::VecDeque<K>,   // ordered list of recently evicted probationary keys
ghost_set: std::collections::HashSet<K>, // O(1) membership test for the ghost queue
```

Set a ghost capacity equal to `prob_cap` (the same as probationary capacity, configurable from `try_new()`).

**On probationary eviction** (the branch in `put()` that evicts `prob_head` to make room for a new entry): after removing the evicted key from `self.map`, push the evicted key into `ghost_set` and `ghost` (the back of the deque). If the deque is already at ghost capacity, pop the front entry and remove it from `ghost_set` as well, keeping the ghost set bounded.

**On new-key insertion** in `put()`: before inserting into probationary, check `ghost_set.contains(&key)`. If the key is present in the ghost set, remove it from `ghost_set` and `ghost` (use `retain` on the VecDeque, which is infrequent), then insert the new node directly into the protected segment at protected-MRU (`push_back_prot`, increment `prot_count`) rather than into probationary. If this causes `prot_count > prot_cap`, run the normal protected-overflow demotion (demote `prot_head` to probationary-MRU) exactly as v001 does.

If the key is not in the ghost set, insert into probationary-MRU as normal (identical to v001).

**On probationary promotion** (probationary hit in `get()`): if the promoted key is still in the ghost set (it was evicted and re-requested but was reinserted into probationary rather than directly to protected — this can happen if a ghost-set insert happened and then the entry was evicted from probationary again), remove it from the ghost set on promotion. This keeps ghost_set accurate.

All other logic (protected hit, protected overflow demotion, probationary eviction when the arena is full but probationary is under cap, fallback to protected-LRU when probationary is empty) is identical to v001.

## Rationale

v001's probationary segment is a one-hit filter: only keys accessed at least twice while resident in the cache reach protected. But a key evicted from probationary and then requested again has effectively been accessed twice across two residency periods — it is a warm key the cache happened to evict too soon. The ghost set captures that cross-residency signal and routes such re-arrivals directly into protected, giving them immediate protection from scan traffic without waiting for a second in-cache access.
