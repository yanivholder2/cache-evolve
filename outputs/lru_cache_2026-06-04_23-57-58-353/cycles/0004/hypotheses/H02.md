# H02

Expanding the ghost window from probationary capacity to total cache capacity allows the cache to intercept cross-residency reuse at longer distances and raises hit rate on traces with reuse gaps wider than the probationary segment.

## Parent

cycle/0003/v002

## Changes

In `try_new()`, change `let ghost_cap = prob_cap;` to
`let ghost_cap = capacity;`. Update the two capacity-hint arguments
accordingly: `ghost: VecDeque::with_capacity(ghost_cap + 1)` and
`ghost_set: HashSet::with_capacity(ghost_cap + 1)` — these are already
expressions that reference `ghost_cap`, so they pick up the new value
automatically without further edits.

No other logic changes. The `add_to_ghost()` method, the ghost-hit
admission branch in `put()`, and the ghost-entry cleanup in `get()` all
remain identical. The only effect is that the ghost queue can now retain
up to `capacity` evicted keys (2048 at the benchmark size) instead of the
previous `prob_cap` (~410). This means evicted-probationary keys remain
trackable for roughly five times longer before ageing out, letting the
cache recognize re-arrivals that previously expired before they could
trigger the fast-path protected admission.

## Rationale

Cycle 3 confirmed that the current ghost window (bounded to probationary
capacity, ≈ 20 % of total) is too narrow to intercept the reuse gaps
typical of the LIRS-format workload-a trace. The cross-cycle insight
explicitly calls out testing ghost_cap = capacity as an open question.
Rather than a proportional step, this tests the full ceiling: if the
reuse gap distribution has a long tail that falls between probationary
capacity and total capacity, this change should capture it; if the trace's
reuse distances extend beyond even total capacity, ghost admission remains
irrelevant regardless of window size.
