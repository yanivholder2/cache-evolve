# H02

Restrict cycle/0001/v003's untouched-first eviction scan to the front half of the bucket so a freshly-inserted untouched slot at the back is given grace, raising hit-rate by sparing hot newcomers their vulnerable first-hit window.

## Parent

cycle/0001/v003

## Changes

In `src/shared/eviction_policy.rs`, modify only `ClassicLRU`'s
`eviction_candidate_index`. Compute `let half = items.len() / 2;` then
iterate the first pass over `items[..half]` (instead of all items)
looking for `lfu_counter == 0`; return that index if found. If the
front-half scan finds no untouched slot, fall back to slot 0 exactly
as the parent does. Leave `get_from_position` (the move-to-back plus
`lfu_counter += 1`) and `promotion_candidate_index` unchanged from
cycle/0001/v003. When `items.len() < 2`, treat the front half as the
single slot at index 0 (i.e. degenerate buckets behave like baseline
ClassicLRU). Do not touch any other policy, the `EvictionPolicyKind`
enum, or the tests.

## Rationale

In cycle/0001/v003 every untouched slot is a candidate regardless of
position. But a freshly-inserted item lands at the back of the bucket
with `lfu_counter == 0`, and the parent will happily sacrifice it on
the very next eviction — exactly the failure mode cycle/0002/v003
demonstrated for short-distance promotion. Front-half gating turns
"untouched" back into a *cold* signal (lingered without a hit) rather
than a *new* signal, which is the positional regime-fallback the
cross-cycle insights flagged as an open question.
