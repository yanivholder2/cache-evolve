# H01

Add a third "touched once" eviction tier between v003's untouched-first and LRU-front fallback to raise hit rate by protecting twice-hit items more strongly than once-hit ones.

## Parent

cycle/0001/v003

## Changes

In `src/shared/eviction_policy.rs`, modify the `ClassicLRU`
`EvictionPolicy::eviction_candidate_index` implementation so it performs
three passes instead of v003's two:

1. First pass: return the lowest index `i` where
   `items[i].lfu_counter == 0` (one-shot inserts that have never been
   re-touched).
2. Second pass (new): if no untouched slot exists, return the lowest
   index `i` where `items[i].lfu_counter == 1` (touched exactly once
   since insertion or last reset — i.e., a single hit).
3. Fallback: return `0` (LRU front), matching v003's fallback.

Leave `get_from_position` unchanged (it still does `remove` + `push` and
`lfu_counter += 1` on every hit, exactly as in v003 and baseline
ClassicLRU). Leave `promotion_candidate_index` returning
`items.len() - 1`. Do not change the trait, `Item`, or any other policy.

The intent is to test whether a "must survive two hits to be fully
protected" tier helps Zipfian-like workloads (where genuinely hot keys
are hit many times in succession and burn the counter well above 1
quickly) while still sacrificing single-hit "lukewarm" items before
multi-hit ones. This addresses the cycle-0001 open question about
whether a stricter survival filter helps or reintroduces v001's
"kill the hot newcomer" failure — here the newcomer is still promoted
to the back on its very first hit (no v001-style deferral), so the
first-hit vulnerability window is the same as v003's. Only the
*eviction* ranking changes.

## Rationale (optional)

v003's two-pass collapses everything from `lfu_counter == 1` up into a
single "protected" bucket; a three-pass refinement is the smallest
possible step toward finer gradations without growing per-item state or
touching the trait signature.
