# H03

Bias eviction toward never-touched items so a single access protects a slot from the next eviction, lifting hit rate against churn-heavy traces.

## Parent

baseline

## Changes

In `src/shared/eviction_policy.rs`, keep ClassicLRU's `get_from_position`
behaviour (remove at `position`, push to back) but additionally
increment `items[position].lfu_counter` by 1 inside the same method
before returning `items.len() - 1`. Then change
`eviction_candidate_index(items)` so that instead of returning `0`
unconditionally it performs a two-pass scan:

1. First pass: scan `items` from index 0 forward and return the first
   index `i` where `items[i].lfu_counter == 0`. Freshly inserted items
   (which `Item::new` constructs with `lfu_counter = 0`) thus become
   the first victims.
2. Second pass (only reached if every slot has `lfu_counter > 0`):
   return `0`, matching baseline LRU behaviour as the fallback.

Leave `promotion_candidate_index` returning `items.len() - 1`. Do not
modify `AssociativeCacheBucket`, the bucket trait, or any other policy
impl. The bucket's `is_full`, `put`, `evict_item`, and `remove_at`
paths and the P1/P2/P3 invariants are unaffected because the items
vector is still pushed/removed by the same trait-default machinery and
the new logic only changes which index `evict_item` consults.

## Rationale (optional)

This is distinct from H01 (which gates *promotion* on the second hit)
and from H02 (which removes reordering entirely). H03 keeps full
ClassicLRU recency ordering but layers a frequency-aware victim
selector on top: a key has to survive a single access to gain any
protection at all. The expected effect is a hit-rate lift on traces
where new keys arrive in bursts and most are never re-referenced — the
front of the bucket fills with `lfu_counter == 0` carcasses that get
evicted first instead of pushing out genuinely re-used items at the
back.
