# H01

On-demand halving of every slot's `lfu_counter` at the moment v003's untouched-first scan fails restores room for the untouched signal and lifts hit-rate above the parent in the all-touched regime.

## Parent

cycle/0001/v003

## Changes

Move ClassicLRU's eviction-candidate logic out of the trait method and into an override of `Bucket::evict_item` on `AssociativeCacheBucket` (which already has `&mut self`, so it can mutate `items`). In the override:

1. If the configured policy is not `ClassicLRU`, delegate to the trait default (preserving baseline behaviour for the other five policies).
2. For `ClassicLRU`: first do v003's existing scan — leftmost `lfu_counter == 0`. If found, evict that slot exactly as v003 does.
3. If no slot has `lfu_counter == 0` (the all-touched regime), perform an in-place aging pass: for every slot, set `item.lfu_counter = item.lfu_counter >> 1` (saturating shift, so any slot whose previous counter was 1 lands at 0; slots whose counter was 2 land at 1; etc.). Then re-scan leftmost-first for `lfu_counter == 0` and evict that slot.
4. Aging is guaranteed to produce at least one zero-counter slot (the previous lowest-counter slot), so the post-aging re-scan always succeeds; no further fallback is needed, but for safety keep a final `return 0` as v003 does.

Crucial differences from prior aging attempts: cycle/0003/v001 decayed counters on **every hit** (which drained genuine re-references); this change decays **only when an eviction scan finds the bucket fully touched** — i.e., precisely at v003's known weak point and nowhere else. Cycle/0002/v001's three-tier scan also handled the all-touched case but evicted a `counter == 1` slot without changing the counter, so subsequent evictions kept conflating long-resident slots with newly-once-hit ones; halving collapses lifetime hits into recent-relative hits without destroying the rank order between them.

Leave `ClassicLRU::get_from_position` (the on-hit `counter += 1` + move-to-back) unchanged. Leave `ClassicLRU::eviction_candidate_index` matching v003's behaviour so that direct trait callers (tests, other code paths) still see v003 semantics; aging lives on the bucket override.

## Rationale (optional)

The cross-cycle digest explicitly flagged that "any future counter-based policy almost certainly needs an explicit aging or decay step before tiering can compete," and that v003's all-touched fallback (slot 0) is where the parent visibly leaves hit-rate on the table. Decaying only at the regime boundary — not on every hit — is the unexplored point in the aging design space.
