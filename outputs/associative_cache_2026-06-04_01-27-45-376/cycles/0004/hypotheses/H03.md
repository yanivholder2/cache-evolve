# H03

Reverse the untouched-first scan direction — evict the rightmost (most-recently-inserted) untouched slot rather than the leftmost — to test v002-of-cycle-0003's insight that back-position untouched slots are predominantly one-shot churn, targeting hit-rate.

## Parent

baseline

## Changes

In `src/shared/eviction_policy.rs`, replace the body of
`<ClassicLRU as EvictionPolicy<K, V>>::eviction_candidate_index` so
that instead of scanning `items.iter().enumerate()` front-to-back for
the first `lfu_counter == 0`, it scans `items.iter().enumerate().rev()`
for the **last** `lfu_counter == 0` (equivalently:
`items.iter().rposition(|it| it.lfu_counter == 0).unwrap_or(0)`).
The fallback when no slot is untouched stays at slot `0` (LRU front),
matching the baseline and v003's degraded behaviour.

Leave `get_from_position` (move-to-back + counter bump) and
`promotion_candidate_index` (`items.len() - 1`) untouched. Do not
modify `src/associative_cache/associative_cache_bucket.rs`. Other
policies (`TimestampLRU`, `Lifo`, `Lfu`, `Fifo`, `Swap`) remain
exactly as in the baseline.

## Rationale (optional)

Cycle 0003 v002's insight explicitly concluded that the back-most
untouched slot on this trace is more often a fresh one-shot insert
than a hot newcomer. The v002 variant tried to *protect* the back
half from eviction, which lost — but this hypothesis inverts the
direction of the v003 scan to *target* exactly those back-of-bucket
fresh untouched slots first. Both v003 (front-first) and H03
(back-first) collapse to the same fallback (slot 0) in the
all-touched regime, so the only behavioural difference is which
untouched slot dies first when several exist. This is a one-token
change to the existing successful filter and directly tests the
inverted insight from v002's autopsy.
