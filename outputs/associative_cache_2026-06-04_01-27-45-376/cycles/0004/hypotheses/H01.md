# H01

Gap-fill insertion at the evicted slot's position (instead of pushing to back) tests the insertion-placement axis to lift hit-rate above cycle/0001/v003.

## Parent

cycle/0001/v003

## Changes

In `src/associative_cache/associative_cache_bucket.rs`, override the
`Bucket::put` default in the `impl<K, V> Bucket<K, V> for
AssociativeCacheBucket<K, V>` block. The new `put` keeps the existing
update-in-place branch (when `get_position` returns `Some`), but on a
genuine insertion replaces the `evict_item()`-then-`push` sequence with:

1. If the bucket is full, find the eviction index via
   `self.eviction_candidate_index()` (the trait default, which delegates
   to the policy — keep v003's untouched-first scan in
   `src/shared/eviction_policy.rs` exactly as-is).
2. Remove the item at that index via `self.get_items_mut().remove(idx)`
   and remember it as `evicted`.
3. Insert the new item at the same `idx` using
   `self.get_items_mut().insert(idx, item)` — so the surviving items
   in positions `idx+1..` keep their relative LRU rank instead of
   shifting one step toward the front.
4. Return `(&self.get_items()[idx], Some(evicted))`.
5. If the bucket is not full, fall back to the existing push-to-back
   path so non-full buckets behave identically to v003.

Do not touch `eviction_candidate_index`, `get_from_position`, or any
other policy method — the only behavioural change is *where the fresh
item lands*, which is the insertion-placement axis the cycle 0003 and
cross-cycle digests both flagged as the unexercised orthogonal axis to
v003's eviction filter.

## Rationale (optional)

Today every fresh insertion takes the back-most (most-protected) slot,
which v002 of cycle 0003 already showed is wrong when the back-most
slot turns out to be one-shot churn. Gap-fill insertion lands the new
item wherever the evicted untouched slot was — usually a front-half or
mid-bucket position — so it inherits the LRU rank of the slot it
replaces rather than leapfrogging genuine survivors. If "fresh insert
deserves protection" is wrong on this trace (as v002's insight
suggests), gap-fill should improve hit-rate without disturbing any
signal v003 relies on.
