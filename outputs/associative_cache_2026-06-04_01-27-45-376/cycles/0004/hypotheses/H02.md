# H02

A per-bucket rotation cursor that spreads eviction pressure across untouched slots (CLOCK-style fairness among the v003 filter's candidates) raises hit-rate by avoiding the leftmost-bias of cycle/0001/v003.

## Parent

cycle/0001/v003

## Changes

The change spans both editable files; the per-item state and the
policy struct remain untouched.

1. In `src/associative_cache/associative_cache_bucket.rs`, add a
   `victim_cursor: u8` field to `AssociativeCacheBucket<K, V>`,
   initialised to `0` in `new`. Override the `Bucket` trait's default
   `eviction_candidate_index` method on the impl block: it should call
   a new helper on the policy that takes both the items slice and a
   starting index, then advance `self.victim_cursor` by 1 (modulo
   `self.max_size as u8`) on every call so the next eviction starts
   from a different rotation point. Make the override fall back to the
   default (delegating to the policy without a cursor) for any policy
   other than `ClassicLRU` — gate this by inspecting
   `self.get_eviction_policy().name() == "ClassicLRU"` so the change is
   surgical to the winning policy.
2. In `src/shared/eviction_policy.rs`, add a free function
   `classic_lru_eviction_candidate_with_cursor` (or an inherent method
   on the `ClassicLRU` zero-sized struct — anything addressable from
   the bucket without changing the `EvictionPolicy` trait) that
   implements the same untouched-first scan as v003 but starts the
   loop at `start = cursor as usize % items.len()` and walks
   `items.len()` positions with wrap-around. The first slot with
   `lfu_counter == 0` wins; if no slot is untouched, fall back to
   slot `0` exactly as v003 does. Keep ClassicLRU's
   `EvictionPolicy::eviction_candidate_index` trait method itself
   pointed at the cursor-less v003 scan so tests and non-bucket
   callers see identical behaviour.

Preserve all other invariants: `get_from_position` (full move-to-back
plus counter bump) is unchanged, `promotion_candidate_index` is
unchanged, and the bucket struct's other fields and constructor
signature stay identical. The `victim_cursor` is plain bucket state —
not per-item — so `Item<u64,u64>` metadata size stays at 40 bytes.

## Rationale (optional)

v003 always evicts the *leftmost* untouched slot, which in
ClassicLRU's dynamics is also the longest-resident untouched slot.
When multiple untouched slots coexist, that bias keeps re-targeting
the same edge of the bucket. CLOCK-style rotation among untouched
slots spreads pressure: each untouched slot in turn gets one
"reprieve" before being eligible again. This is not a signal
refinement (the warning the cycle 0003 digest gave) — it's a
tie-breaker among slots the v003 filter already deems equally
evictable, an axis the cohort has never touched.
