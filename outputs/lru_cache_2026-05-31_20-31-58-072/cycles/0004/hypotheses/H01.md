# H01

Tainting scan-only Cold admissions via a fingerprint-seen sketch lets pass 1 evict them ahead of recency-bearing Cold slots, raising hit-rate on lirs:multi1@512.

## Parent

cycle/0003/v001

## Changes

Modify `src/lru_cache/mod.rs` to filter brand-new (non-ghost) Cold
admissions through a small first-seen sketch:

- Add a fixed-size `seen: Vec<bool>` of length `4 * capacity` (or
  `seen.len().next_power_of_two()`-style sizing, chosen so the table
  comfortably exceeds the working set) on the `LruCache` struct. Index
  it by the lower bits of `hash(key)` using `std::collections::hash_map::DefaultHasher`
  (do not pull a new crate). Set `seen[fp] = true` on every `get` and
  every `put` regardless of resident/ghost outcome.
- Add a `scan_taint: bool` field to `Entry`. Only set it on the
  brand-new-key insertion path in `put` when `from_ghost == false` and
  `seen[fp]` was `false` *before* this access marked it. Resident
  updates, ghost-promoted inserts, and slots populated below capacity
  must not be tainted.
- In `evict_one`, run a new pre-pass before pass 1 that sweeps the
  ring once for Cold ref-clear slots whose `scan_taint` is `true` and
  evicts the first one found (treating it as a Cold eviction for ghost
  purposes). If none is found, fall through to the existing pass 1 /
  pass 2 / fallback logic unchanged.
- The taint must be cleared on any subsequent `get` hit on that slot
  (a touched scan insert is no longer scan-only) at the same point
  where `referenced` is set.

Preserve invariants: ghost ring sizing, the Cold→Hot second-touch
promotion, pass-2 demotion behaviour, and the JNI-protected
`lru_cache_jni.rs` ABI remain untouched. The pre-pass must still bound
its work at `O(capacity)` so per-op time does not blow up on a fully
tainted ring.

## Rationale (optional)

Cycle-3 insight named Cold-admission filtering as an unpulled pass-1
lever. Unlike a saturating frequency counter (which regressed in
cycle 2 by shielding stale-popular keys), this filter only marks
truly-new entrants and only biases the *eviction* order against them —
it cannot shield existing Cold or Hot residents, so the recency
characteristics of the trace remain favoured.
