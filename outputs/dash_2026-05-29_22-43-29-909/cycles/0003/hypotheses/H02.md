# H02

Make ClassicLRU's eviction victim the least-frequently-reused resident instead of the LRU-front item, protecting recurring loop keys from eviction to raise hit rate on the lirs:multi1 scan/loop trace.

baseline

## Changes

Every prior cycle changed *who gets promoted* or *where promotions land*; the
eviction victim selection has been deliberately untouched. This hypothesis moves
that fresh lever and leaves the promotion path alone. Edit only the
`impl<K, V> EvictionPolicy<K, V> for ClassicLRU` block in
`src/shared/eviction_policy.rs`:

1. `get_from_position`: add `items[position].lfu_counter += 1;` as the first
   line, then keep the existing `let item = items.remove(position); items.push(item);
   items.len() - 1` unchanged. This accumulates a per-resident reuse count on
   every in-place hit (target-non-hottest hits and probing hits both flow
   through here) while preserving the exact move-to-back recency ordering.
2. `eviction_candidate_index`: replace the constant `0` with a scan that returns
   the index of the resident holding the **smallest** `lfu_counter`, breaking
   ties toward the lowest index. Concretely: iterate `items.iter().enumerate()`,
   track `(min_counter, min_index)`, and update only on a *strictly smaller*
   counter, so among equally-cold residents the lowest index (the LRU-most under
   the preserved ordering) is chosen. Precondition: `items` is non-empty (the
   trait wrapper already guards emptiness).
3. Leave `promotion_candidate_index` as `items.len() - 1` (MRU). The promotion
   trigger stays exactly recency-based — this isolates the change to *who leaves*
   the bucket, not who climbs.

Do not touch `dash_bucket.rs`, `promotion_logic.rs`, or `item.rs`. `lfu_counter`
already exists on `Item` (`usize`, initialised to 0), so metadata-size is
unchanged. Invariants P1–P5 hold: eviction still removes exactly one item, and
every resident is slot-legal, so changing *which* slot-legal resident is evicted
preserves single-eviction-per-put, slot legality, and capacity bounds. Keep the
crate compiling and reconcile the in-crate `#[cfg(test)]` cases that assert
ClassicLRU eviction order (`classic_lru_evicts_least_recently_used`,
`classic_lru_eviction_chain` in `eviction_policy.rs`/`bucket.rs`, and
`eviction_candidate_index_classic_lru`) with the new frequency-aware victim rule.

## Rationale (optional)

On a loop workload the LRU-front item is frequently a recurring key that is about
to be re-requested; evicting it churns the working set. Selecting the
least-reused resident as victim protects keys that have proven reuse while still
ordering by recency for promotion. It is expected to cost a little get latency
(the per-hit counter bump plus an O(n) victim scan on full-bucket puts), so it
should trade latency for hit rate — a different point on the front from the
admission-gate and promotion-threshold bets in this cohort.
