# H03

Promote a target item to probing on its second target hit via an O(1) per-item counter threshold instead of cycle-2 v001's strict-frequency-maximum scan, filling the hot tier without taxing get latency to raise hit rate on the lirs:multi1 scan/loop trace.

baseline

## Changes

This realizes the cycle-2 continuation cleanly: keep frequency as the
target-to-probing promotion signal, but drop both flaws of cycle-2 v001 — the
strict pre-hit maximum (ties never promote, so loop residents with similar
counts under-fill the hot tier) and the O(n) per-hit bucket scan it used to read
that maximum. Build it from baseline and edit only the **target-hit branch** of
`promotion_get` in `src/dash/segments/promotion_logic.rs`.

Today that branch is:

```
let is_hottest = Some(item_idx) == core.buckets[target_idx].promotion_candidate_index();
if is_hottest { /* remove_at + promote_to_probing + relocate */ }
else { return Some(core.buckets[target_idx].get_from_position(item_idx)); }
```

Replace the `is_hottest` recency test with an O(1) threshold read off the hit
item's own accumulated frequency:

1. Increment the hit item's counter once, explicitly (the eval path's
   `ClassicLRU::get_from_position` does not touch it):
   `core.buckets[target_idx].get_items_mut()[item_idx].lfu_counter += 1;`
2. Let `promote = core.buckets[target_idx].get_items()[item_idx].lfu_counter >= 2;`
   — this is a single field read, no bucket scan.
3. If `promote`: reset that item's `lfu_counter` to `0` (so the probing tier must
   re-earn its own promotions and the counter cannot grow unbounded), then run
   the existing `remove_at(item_idx)` → `promote_to_probing(core, data,
   insert_pos)` → relocate-and-return path with its `unreachable!` guard intact.
   Otherwise fall through to the existing else arm:
   `return Some(core.buckets[target_idx].get_from_position(item_idx));` (touch in
   place), which leaves the counter accumulated for the next hit.

Do **not** modify `eviction_policy.rs`, `dash_bucket.rs`, or `item.rs`:
`ClassicLRU` keeps its baseline positional `eviction_candidate_index` (0) and
`promotion_candidate_index` (`len - 1`), and `lfu_counter` (`usize`, init 0) is
already present, so the get path stays free of the strict-max scan and
metadata-size is unchanged. The stash-hit branch (immediate stash→target promote
at `Front`) and the probing-hit branch are unchanged.

Invariants P1–P5 hold: each promotion still removes exactly one item and
re-inserts it into a key-derived slot, so single-eviction-per-put, slot legality,
and capacity bounds are untouched. Keep the crate compiling and update the
in-crate `#[cfg(test)]` case `target_hit_hottest_promotes_to_probing` in
`promotion_cold_segment.rs` to drive the threshold (two target hits) rather than
the old "already at MRU" recency condition.

## Rationale (optional)

The cycle-2 insight asked explicitly for "a cheap threshold (e.g. second-hit
admission) that preserves the O(1) promotion path." A flat counter threshold lets
any twice-hit target key climb — fixing the under-fill that the strict-max rule
caused on a loop trace where residents share similar counts — while reading one
field instead of scanning the bucket fixes the get-latency tax cycle-2 v001
incurred. The counter reset on promotion gives a crude aging so stale-but-once-hot
keys do not stay sticky.
