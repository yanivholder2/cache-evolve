# H02

Search the hot tier (target then probing) before the stash on each get to lower per-op get latency.

## Parent

baseline

## Changes

In `promotion_get` (`src/dash/segments/promotion_logic.rs`) reorder the three
`if let Some(...)` slot lookups. The baseline order is stash → target → probing:

1. `core.stash_buckets[stash_idx].get_position(key)` → `promote_to_target`
2. `core.buckets[target_idx].get_position(key)` → hottest? `promote_to_probing`
   else intra-bucket touch
3. `core.buckets[probing_idx].get_position(key)` → touch in place

Change the order to target → probing → stash: move blocks (2) and (3) ahead of (1),
keeping each block's body byte-for-byte identical (same `promote_to_probing` /
touch-in-place / `promote_to_target` calls, same `unreachable!` post-conditions,
same `get_from_position` side effects). Keep the `stash_idx` / `target_idx` /
`probing_idx` derivations at the top unchanged.

This is behavior-preserving: the uniqueness invariant (ADR 0004) guarantees a key
resides in at most one slot, so only the count of linear `get_position` scans before
a hit changes — never which branch fires. `get_position` is an O(n) scan over a
bucket of up to 64 items; the baseline pays a full stash scan before ever touching
the hot tier.

Rationale: on Zipfian traces the small set of hot keys responsible for most
accesses is promoted into the 2-bucket normal/probing tier, while the larger
6-bucket stash holds cold and one-hit keys. Checking the hot tier first
short-circuits the common hit and skips the stash scan entirely for hot-key gets.

Invariants P1–P5 hold (identical set of moves, identical per-put eviction count).
Confirm by comparing get p50/p99 against baseline (30 ns / 120 ns) and verifying the
hit-rate summary is unchanged at ~0.94725.
