# H03

Narrow Item's lfu_counter to u32 and replace its 16-byte Instant timestamp with a 4-byte logical clock, shrinking Item<u64,u64> from 40 to 24 bytes while preserving every eviction-policy's ordering semantics.

## Parent

baseline

## Changes

The metadata-size metric is `sizeof(Item<u64,u64>) = 40`: key(8) + value(8) +
`lfu_counter: usize`(8) + `timestamp: Instant`(16). Cycle-1's v003 tried to drop
both fields entirely and produced no fitness vector — almost certainly because
removing the fields breaks the in-crate tests and the `Lfu` / `TimestampLRU`
policy bodies that read them, so the crate stops compiling. This hypothesis gets
the same 40 to 24 byte win by *narrowing* the fields instead of removing them,
keeping all field names, all policy variants, and all ordering semantics intact.

`src/shared/item.rs`:

- Change `lfu_counter: usize` to `lfu_counter: u32`.
- Change `timestamp: Instant` to `timestamp: u32` — a logical tick. Add a
  process-global monotonic counter (e.g. `static CLOCK: AtomicU32 =
  AtomicU32::new(0)` with a `pub(crate) fn next_tick() -> u32 {
  CLOCK.fetch_add(1, Ordering::Relaxed) }`). In `Item::new`, set
  `timestamp: next_tick()` instead of `Instant::now()`.
- Drop `use std::time::Instant;`, add the `AtomicU32` / `Ordering` imports, and
  update the `Display` impl to print `timestamp` as a plain integer.

`src/shared/eviction_policy.rs`:

- `TimestampLRU::get_from_position`: set `items[position].timestamp =
  next_tick();` instead of `Instant::now()`. Its `eviction_candidate_index`
  (min timestamp) and `promotion_candidate_index` (max timestamp) keep working
  unchanged on `u32`, preserving evict-oldest-touched ordering. Remove the now
  unused `use std::time::Instant;`.
- `Lfu` is unchanged in behavior (`lfu_counter += 1`, min/max selection) — it
  just operates on `u32` now.

Resulting layout: u64 + u64 + u32 + u32 = 24 bytes, no padding. The eval path
uses `ClassicLRU`, whose `get_from_position` (remove+push) and positional
candidate indices read neither narrowed field, so bucket-movement and hit-rate
are unchanged — this is a pure metadata win on the front. Do **not** touch
`promotion_logic.rs`, `promotion_cold_segment.rs`, or `dash_bucket.rs`.

Invariants P1–P5 are layout-agnostic (they depend on slot derivation and per-put
eviction counting, not item field widths) and continue to hold. Keep the crate
compiling: the `u32` field types are drop-in for the existing `== 0` / `+= 1`
unit-test assertions; only the `timestamp` source changes from wall-clock to
logical tick, which preserves the monotonic ordering those tests rely on. The
u32 tick wraps after 2^32 operations — acceptable for the benchmark and trace
sizes used here.

## Rationale (optional)

This is the metadata lever retried as a clean, behavior-preserving change that
fixes the likely cause of v003's non-realization (field removal breaking the
policy contract and tests). It delivers the full 40 to 24 byte reduction while
leaving the ClassicLRU hit-rate and per-op paths untouched, so it can only
dominate on the metadata axis.
