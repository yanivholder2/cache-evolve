# H02

Keep v001's O(1) back-push promotion but admit a stash item into the hot tier only after its second hit, so single-touch scan keys never receive MRU protection, raising hit rate without giving up v001's latency profile.

## Parent

cycle/0001/v001

## Changes

v001 overlays `src/dash/dash_bucket.rs` so `put_at` ignores `InsertPosition` and
always pushes to `Back` (MRU). That gave the O(1) promotion-insert latency win
but, because every stash hit is promoted into the hot tier *at the protected MRU
end on its first touch*, scan keys flood and displace genuinely hot residents —
the hit-rate regression noted in v001's insight. This hypothesis keeps v001's
`dash_bucket.rs` change exactly as-is and adds a one-more-chance admission gate
in `promotion_get` (`src/dash/segments/promotion_logic.rs`).

In the stash-hit branch of `promotion_get` (the
`core.stash_buckets[stash_idx].get_position(key)` block):

1. Increment the stash resident's `lfu_counter` by 1 (do it explicitly; the eval
   path runs `ClassicLRU`, which never touches the counter).
2. If the counter is now `< 2` (first hit while resident in stash), do **not**
   promote: touch the item in place inside its stash bucket
   (`core.stash_buckets[stash_idx].get_from_position(item_idx)`) and return a
   reference to it, leaving it resident in the stash slot.
3. Only when the counter reaches `>= 2` do the existing promotion: remove from
   stash, `promote_to_target`, then re-locate and return the resident as today.

Leave the target-hit and probing-hit branches, `promote_to_target`,
`promote_to_probing`, `demote_from_normal_bucket`, and both `unreachable!`
post-conditions unchanged. New keys still enter stash via the default `put`.

Invariants P1–P5 hold: the gate keeps a not-yet-admitted key resident in its own
stash slot (slot-legal) and adds no item and no extra eviction, so
single-eviction-per-put, capacity bounds, and stash-terminal semantics are
preserved. Keep the crate compiling and update any in-crate `#[cfg(test)]` cases
that assume a stash hit promotes on the first touch
(e.g. `stash_hit_inserts_at_front_of_target`) to drive two hits before asserting
the promotion.

## Rationale (optional)

This refines the only Pareto winner so far: it retains v001's cheap back-push
(the latency structure the cross-cycle notes asked us to preserve) while
repairing the exact mechanism that cost hits — first-touch admission of scan
keys into the MRU-protected hot tier. Requiring a second stash hit turns the
stash into a scan filter, the reuse-aware behavior the LIRS trace rewards.
